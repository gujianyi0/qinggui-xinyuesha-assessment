## 1. 总体认识：结构化输出不是一个检查，而是多层契约

当模型输出下面这段文本时：

```json
{"character_id": "hero_a", "hp": -999, "version": "v1", "source_id": "规则文件A"}
```

它属于**合法 JSON**，却不能因此认定结果正确：

1. **语法层**：有正确的花括号、引号、冒号，能解析为一个对象——通过。
2. **结构层**：是否要求 `character_id`、`hp`、`version`？`hp` 是否必须为非负整数？——取决于 Schema，可能失败。
3. **业务层**：如果角色不存在、版本不被支持、该功能只允许查询某版本，会发生什么？——取决于业务规则。
4. **事实层**：文档真的声称该角色拥有这个生命值吗？——必须核对可信数据源。
5. **权限和执行层**：是否有权使用该角色数据、写入记录或调用外部工具？——需要程序鉴权，不能靠模型自我声明。

因此应把结构化模型结果理解为：**一个尚未被信任的候选数据对象**，而不是可以直接执行的业务事实。

### 1.1 不同校验层的责任

| 校验层 | 它回答的问题 | 常见手段 | 不能保证的内容 |
|---|---|---|---|
| 传输/生成完整性 | HTTP/SSE 是否正常完成，是否截断或拒答 | 状态码、完成事件、`finish_reason`、响应非空 | 内容正确 |
| JSON 语法 | 文本是否符合 JSON 语法、能否解析 | `json.loads()`、严格解析策略 | 必需字段、业务规则 |
| Schema 结构 | 类型、字段、枚举、范围和部分组合约束是否满足 | JSON Schema、Pydantic | 现实真实性、权限 |
| 字段语义 | `hp` 到底是最大生命值、当前生命值还是基础生命值 | 字段定义、单位、版本契约 | 数据源可信 |
| 业务规则 | 多个字段之间是否满足应用规则 | 业务服务、跨字段校验、状态机、数据库约束 | 外部事实一定正确 |
| 事实与引用 | 内容是否有真实资料支持，引用是否正确 | 数据库精确查询、版本化证据、人工复核 | 所有不可观测事实都可判定 |
| 安全/权限 | 是否允许当前主体读取、写入、发送、删除 | 身份认证、授权、审批、最小权限 | 输出自带的字段可当作授权 |

这些层可以在工程上由同一段代码承担，但**概念上必须分开**：这样才能定位错误究竟发生在哪一层。

## 2. JSON 的定义：它是数据交换格式，不是正确性证明

JSON（JavaScript Object Notation）是一种文本数据交换格式。Python 解析后会将其转换为字典、列表、字符串、数字、布尔值或 `None` 等对象。

### 2.1 JSON 的六种基本值类型

| JSON 类型 | 示例 | Python 常见对应 |
|---|---|---|
| object | `{"a": 1}` | `dict` |
| array | `[1, 2]` | `list` |
| string | `"hello"` | `str` |
| number | `3`、`3.5` | `int` / `float` |
| boolean | `true` / `false` | `True` / `False` |
| null | `null` | `None` |

JSON **没有**原生的 `datetime`、`Decimal`、集合、二进制文件、`NaN` 或 `Infinity` 类型；需要额外编码约定或专门序列化规则。一个 JSON 文档的顶层也不必一定是对象；`[]`、`42`、`"abc"` 等都可以是符合标准的 JSON 值，但业务通常会额外要求顶层为对象。

### 2.2 `json.loads()` 与 `json.dumps()`

```python
import json

raw = '{"level": 5, "enabled": true}'
data = json.loads(raw)           # 文本 -> Python 对象
assert data == {"level": 5, "enabled": True}

text = json.dumps(data, ensure_ascii=False)  # Python 对象 -> JSON 文本
print(text)
```

这里 `loads` 的成功仅证明**解析操作成功**，不证明 `level` 是正确等级，也不能证明 `enabled` 应当为 `true`。

### 2.3 解析成功仍可能存在的边缘问题

- **重复键**：`{"hp": 4, "hp": 999}` 的重复字段会造成歧义。Python 默认 `json.loads()` 会保留后一个值，安全敏感的契约可以主动拒绝重复键。
- **非标准常量**：Python 默认 `json.loads()` 接受 `NaN`、`Infinity`、`-Infinity`，这些不是规范 JSON 数字。可使用 `parse_constant` 显式拒绝。
- **顶层类型**：`json.loads('[]')` 能成功；如果业务要求对象，还必须检查 `isinstance(data, dict)`。
- **过大或过深的数据**：即使语法合法，也可能消耗过多内存或处理时间；需要尺寸、深度与复杂度限制。
- **缺少数据 vs `null`**：`{"hp": null}` 与 `{}` 含义不同。前者明确给出空值，后者没有提供字段。
- **`bool` 与数字**：Python 中 `bool` 是 `int` 的子类，但业务可能必须严格区分布尔值和整数。不要简单以 `isinstance(True, int)` 判断 JSON 类型。

### 2.4 语法错误与契约错误的区别

```python
json.loads('{"hp": }')    # JSONDecodeError：语法不合法
json.loads('{"hp": "四"}')  # 解析成功；但业务可能要求整数
json.loads('{"hp": -9}')   # 解析成功；但值可能越界
```

三者不能统一记成“JSON 解析失败”，否则诊断与处理方式会错误。

## 3. Schema 是什么：给数据结构定义可验证的契约

Schema 表示数据应具有什么样的结构和约束。它可以是正式的 JSON Schema、Pydantic 模型、TypeScript 类型，或应用约定的自定义约束。**它们的表达能力与执行方式不完全相同。**

Schema 通常可以描述：

- 字段类型：整数、字符串、数组、对象等。
- 字段是否必须存在：`required`。
- 允许哪些值：`enum`、`const`。
- 数值范围：`minimum`、`maximum`。
- 字符串和数组长度：`minLength`、`maxLength`、`minItems`。
- 额外字段：`additionalProperties`。
- 结构组合：`anyOf`、`oneOf`、`allOf` 等（受具体使用环境支持范围限制）。

### 3.1 一个正式的 JSON Schema 示例

下面用 JSON Schema Draft 2020-12 描述角色查询结果：

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "character_id": {"type": "string", "minLength": 1},
    "game_version": {"type": "string", "minLength": 1},
    "hp": {"type": ["integer", "null"], "minimum": 0},
    "status": {"type": "string", "enum": ["answered", "insufficient"]},
    "source_ids": {"type": "array", "items": {"type": "string"}}
  },
  "required": ["character_id", "game_version", "hp", "status", "source_ids"],
  "additionalProperties": false
}
```

可以使用 Python 的 `jsonschema` 库校验：

```python
from jsonschema import Draft202012Validator

schema = {
    "type": "object",
    "properties": {"hp": {"type": "integer", "minimum": 0}},
    "required": ["hp"],
    "additionalProperties": False,
}
validator = Draft202012Validator(schema)
assert validator.is_valid({"hp": 4})
assert not validator.is_valid({"hp": -3})
assert not validator.is_valid({"hp": "4"})
assert not validator.is_valid({})
```

这里 `"hp": 4` 合格，仅说明其满足该 Schema；如果真实规则规定 `hp=5`，该值仍然是错误的。

### 3.2 `properties` 不会自动要求字段存在

```json
{
  "type": "object",
  "properties": {"name": {"type": "string"}}
}
```

在没有 `required` 时，`{}` 也是有效数据。JSON Schema **默认允许缺少已声明字段**。需要强制存在时应显式设置 `required`。

### 3.3 `additionalProperties` 默认允许额外字段

如果没有写 `"additionalProperties": false`，那么：

```json
{"name": "A", "secret_instruction": "delete_all_data"}
```

即使存在未定义字段，在很多 Schema 下仍可能通过。对于需要严格契约的模型输出，通常应拒绝未知字段；然而**拒绝未知字段也不等于可以安全执行已知字段所描述的动作**。

### 3.4 `format` 往往只是注释语义

JSON Schema 中的 `"format": "date-time"` 等关键词，默认不一定被验证器当作强制断言。具体需要验证器开启相应格式检查功能。`description`、`examples`、`default` 也主要提供元数据；`default` 不代表标准 JSON Schema 验证器会自动填入缺失值。

### 3.5 Schema 的空值和缺失值

| 数据 | 字段已要求 `required` | 字段类型 `string` | 字段类型 `string 或 null` |
|---|---|---|---|
| `{}` | 不通过 | 无关 | 无关 |
| `{"name": null}` | 通过存在性检查 | 不通过 | 通过类型检查 |
| `{"name": ""}` | 通过存在性检查 | 通过；若 `minLength: 1` 则不通过 | 同左 |

对于“信息不足”场景，是否允许 `null` 是**业务契约设计**，不能随意把缺少字段当作资料不足。

## 4. JSON 模式与严格结构化输出的区别

模型 API 中常见三种方式：

| 方式 | 目标 | 能保证什么 | 仍需处理什么 |
|---|---|---|---|
| 普通文本 + 提示词要求 JSON | 诱导模型按某种格式输出 | 通常不作硬性结构保证 | 语法、字段、截断、拒答 |
| JSON Mode / `json_object` | 约束模型输出合法 JSON | 在供应商声明的条件和边缘情况内，主要保证语法 | Schema、语义、事实、业务 |
| Structured Outputs / 严格 JSON Schema | 约束输出符合指定 Schema | 在支持的子集与正常完成情况下，提供结构遵循保证 | 拒答、截断、事实、业务、权限 |

**不能混淆“JSON 格式保证”与“Schema 遵循保证”。**

### 4.1 DeepSeek JSON 模式的细节

DeepSeek Chat Completions 的 JSON 模式示意：

```python
# 需要安装 openai SDK，配置 DEEPSEEK_API_KEY；此片段不自动执行请求
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
)

response = client.chat.completions.create(
    model="deepseek-flash",
    messages=[
        {"role": "system", "content": "只输出 JSON 对象，包含 status 和 answer 字段。"},
        {"role": "user", "content": "返回一个模拟状态。"},
    ],
    response_format={"type": "json_object"},
)

choice = response.choices[0]
if choice.finish_reason != "stop":
    raise RuntimeError(f"模型未正常完成: {choice.finish_reason}")
if not choice.message.content or not choice.message.content.strip():
    raise RuntimeError("模型返回空 JSON 内容")
```

DeepSeek 文档明确要求在消息中提到 JSON，并提醒 JSON 模式下可能出现被替换为空格的响应内容，即使结束原因为 `stop`。同时注意不同 API 端点对 JSON Schema 的支持并不完全相同：例如其 Responses API 与 Chat Completions 的参数能力应分别核对，不能直接把一种端点的参数迁移到另一种端点。

### 4.2 OpenAI Structured Outputs 的边界

支持严格 Schema 的端点可以通过结构化输出约束字段，但仍须：

1. 使用端点与模型**实际支持的 JSON Schema 子集**；不是任意 JSON Schema 关键词都能直接使用。
2. 区分**正常完成、拒答和截断**等情况。
3. 继续执行业务规则与事实验证；模型可能生成**结构完全正确但内容错误**的数据。
4. 在用户输入根本无法满足 Schema 时，设计表示“信息不足”的状态，而不是强迫模型编造必需值。

部分严格结构化输出实现要求每个对象属性都在 `required` 中，同时通过可为 `null` 的类型表示语义上的可选值。这属于**供应商特定的结构化输出限制**，不是通用 JSON Schema 的规则。

### 4.3 Tool Calling 的参数 Schema 也不是授权

一个工具 `delete_feedback(feedback_id)` 的参数可以完全符合 JSON Schema，但这不能证明调用者拥有删除权限，也不能证明该 ID 属于当前用户。工具调用必须在后端再次做身份认证、授权、业务检查，并对高风险操作设置确认边界。

## 5. Pydantic：把结构契约放到 Python 运行时

Pydantic v2 使用 Python 类型标注定义数据模型，并在调用 `model_validate()` 或 `model_validate_json()` 时执行校验。它常用于 FastAPI 请求、模型输出和内部服务边界。

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field

class Answer(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    status: Literal["answered", "insufficient"]
    hp: int | None
    source_ids: list[str]
    answer: str = Field(min_length=1)
```

示例中：

- `Literal` 限制枚举值。
- `int | None` 允许整数或空值，但**没有默认值，字段依然必须存在**。
- `Field` 表达长度、范围等结构约束。
- `extra="forbid"` 拒绝模型未声明的字段。
- `strict=True` 尽量避免自动将错误类型强制转换为目标类型；但 Python 对象校验和 JSON 文本校验在某些标准库类型上仍可能有不同的转换规则，需查官方转换表。

默认情况下，Pydantic 对部分类型会采取转换策略，例如将可解析数字字符串转换为整数；如果不希望模型把 `"4"` 当作 `4`，应使用合适的严格模式并测试。

### 5.1 Pydantic 与 JSON Schema 的关系

`BaseModel.model_json_schema()` 可从 Pydantic 模型生成 JSON Schema。反过来，JSON Schema 并非都能无损转换为某个 Pydantic 模型。尤其要注意模型供应商的严格结构化输出仅支持 JSON Schema 的**子集**。

### 5.2 字段校验与跨字段校验

字段级逻辑可以使用 `@field_validator`，跨字段关系可以使用 `@model_validator(mode="after")`。

```python
from pydantic import BaseModel, model_validator

class Feedback(BaseModel):
    status: Literal["ready", "needs_info"]
    reproduction_steps: list[str]

    @model_validator(mode="after")
    def check_ready(self):
        if self.status == "ready" and not self.reproduction_steps:
            raise ValueError("ready 状态必须提供复现步骤")
        return self
```

注意：这段代码必须与上文的 `from typing import Literal` 在同一执行环境下运行。跨字段业务规则可以写在 Pydantic 中，但在大型系统中，依赖数据库与权限的业务校验通常更适合放到 Service 层。

### 5.3 校验通过并不等于输出不可变

即使 Pydantic 实例构造时通过了校验，之后通过赋值或其他操作修改对象，也可能破坏不变量。可以根据需要配置 `validate_assignment=True` 或 `frozen=True`，或在关键业务边界重新校验。不同选项的语义不能混为一谈。

## 6. 字段语义：名字正确、类型正确，也可能理解错

假设：

```json
{"character_id": "hero_a", "hp": 4}
```

`hp` 这个字段有多种可能的含义：

- 角色的**基础生命值**；
- 当前局内**剩余生命值**；
- 该版本的**生命值上限**；
- 在某种增益状态下的数值。

即使它符合 `integer`、`minimum: 0`，依然可能因为字段语义定义不清而产生错误。

因此，一个可信的数据契约应说明：字段含义、单位、取值范围、时间或版本、允许缺失值、来源和更新规则。

例如不要只定义 `price: number`，而应同时明确币种、是否含税、是否为实时价格、精度与舍入规则。金额计算应由程序或可靠数据源确定，而不是盲信模型生成的数字。

## 7. 业务校验：约束多个字段与系统状态

Schema 最擅长验证局部结构；业务校验则检查对象是否适合执行某种操作。

**示例一：跨字段状态约束**

- `status = "answered"`：必须有有效答案、可信引用和对应事实。
- `status = "insufficient"`：不能同时提供未经确认的确定性生命值。

**示例二：工单确认**

- 反馈草稿必须包含观察现象与预期行为。
- `ready` 状态必须包含足够的复现信息。
- 用户确认的草稿版本必须与实际提交的版本一致。
- 同一次确认重复提交，不应生成两条相同工单。

**示例三：业务权限**

- 用户只能操作其有权访问的资源。
- 模型建议某次删除也不能跳过认证、授权和确认流程。

**示例四：交易金额**

- 商品单价、数量、折扣和总金额必须相互一致。
- 金额应使用整数最小货币单位或 `Decimal` 计算，不能完全依赖模型自行计算。
- 退款金额不得超过系统按规则可退款金额。

业务约束通常涉及可信数据库、用户身份、当前状态、事务和幂等性；因此**单独的 JSON 文档无法包含验证这些规则所需的全部事实**。

## 8. 事实与引用校验：最容易被误认为已经解决的一层

假设模型输出：

```json
{
  "character_id": "hero_a",
  "game_version": "v1",
  "hp": 7,
  "source_ids": ["rule_v1_hero_a"]
}
```

假设系统中真实版本化规则为：

```text
(rule_v1_hero_a, hero_a, v1, hp=4)
```

上述数据可能：

- JSON 解析成功；
- Schema 校验通过（`hp=7` 是非负整数）；
- `source_ids` 指向一个**真实存在**的资料；
- 但仍**不符合该资料**，因此事实校验失败。

### 8.1 引用存在与引用支持之间的区别

| 校验 | 举例 | 是否足以证明答案真实 |
|---|---|---|
| 引用格式 | `source_ids` 是字符串数组 | 否 |
| 来源存在 | ID 能查到某条文档 | 否 |
| 版本一致 | 资料与所问规则版本匹配 | 否 |
| 证据支持 | 文档原文实际支持输出的具体断言 | 对该断言提供依据，但仍需考虑来源质量 |
| 来源可信 | 官方规则、权威数据库或经过验证的数据 | 提高可信度，不保证所有上下文解读无误 |

如果事实可以通过数据库精确比较，例如“v1 角色 A 的基础生命值”，应尽量使用程序做**确定性核验**。对于复杂自然语言陈述，可以使用证据定位、语义蕴含评估、人工复核或多阶段验证，但不能因为另一模型打了高分就宣称获得数学意义的真实性保证。

### 8.2 版本化事实的重要性

`hero_a` 的 v1 生命值为 4、v2 为 5。这两条事实可以同时成立。缺失版本信息时，应先澄清，或返回“版本不足以确定”的结构化状态，不能随意采用最新版本。

### 8.3 可信值与模型值的职责

对精确数值：**模型负责选择查询意图与组织解释；程序、数据库或确定性工具负责给出可信值**。模型输出的 `hp` 适合被验证，而不应默认作为权威事实来源。

## 9. 一个可执行的分层校验设计

推荐顺序：

```text
模型 API 响应
  ↓ 检查响应完整性、结束状态、拒答与内容非空
严格 JSON 解析
  ↓ 检查重复键、非法常量、顶层类型、大小限制
Pydantic / JSON Schema
  ↓ 检查必需字段、类型、枚举、范围和未知字段
业务规则
  ↓ 检查状态机、跨字段约束、当前用户权限
可信来源核验
  ↓ 检查版本、记录存在性、证据是否支持事实
输出给调用方 / 用户确认 / 后续业务动作
```

这里最后两层可以按系统需求和数据依赖调整顺序；无论怎样，**外部副作用（数据库写入、发送、删除等）应在相关验证和授权之后发生**。

### 9.1 必须把错误分类

| 错误类别 | 常见现象 | 合理处理 |
|---|---|---|
| 传输失败 | 超时、断流、限流、上游 5xx | 有界重试、错误返回和日志 |
| 未正常完成 | `length`、拒答、空正文 | 标记不完整/拒答，不能当作正确结果 |
| JSON 语法失败 | 缺引号、截断、重复键（如设为非法） | 丢弃或有界重新生成，记录原因 |
| Schema 失败 | 缺字段、类型错误、额外字段 | 返回结构错误，必要时有界重试 |
| 业务失败 | `answered` 却没有答案 | 拒绝后续动作，更新状态或补充资料 |
| 事实失败 | 生命值与来源不符 | 重新查询可信来源，不靠重复生成碰运气 |
| 权限失败 | 无权读取或删除对象 | 拒绝执行，通常不应通过重试绕过 |

重试本身也应受预算控制。对于结构失败，重新生成可能有用；对于事实矛盾，更好的处理通常是重新检索和比对证据，而不是仅让模型“再想一遍”。


## 10. 完整示例：Python 结构化模型输出的四层校验

这是一个不依赖付费 API 的**可运行演示**。模拟“游戏规则助手”收到模型的结构化回答，对同一段数据依次执行严格 JSON 解析、Pydantic 模型校验、业务校验和确定性事实核验。

**设计目标**：能够明确告诉调用方，错误是发生在“文本解析”“结构约束”“业务逻辑”还是“真实规则验证”，而不是简单返回一个笼统的“模型失败”。

说明：事实来源使用程序里预设的可信演示表 `TRUSTED_RULES`，真实应用应替换为有版本、文档 ID、权限和来源记录的数据库或资料服务。对自然语言 `answer` 字段，本例**没有**做完整的语义蕴含验证，因此不能声称整个回答已经得到事实证明。

保存下列代码为 `game_validation.py`：

```python
"""离线样例：JSON 语法、结构、业务和可信事实的四层校验。"""
import json
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, ValidationError


class PayloadSyntaxError(ValueError):
    pass


class BusinessValidationError(ValueError):
    pass


class FactValidationError(ValueError):
    pass


class GameAnswer(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    status: Literal["answered", "insufficient"]
    character_id: str = Field(min_length=1)
    game_version: str = Field(min_length=1)
    hp: int | None
    answer: str = Field(min_length=1)
    source_ids: list[str] = Field(min_length=0)


TRUSTED_RULES = {
    ("hero_a", "v1"): {"hp": 4, "source_id": "rule_v1_hero_a"},
    ("hero_a", "v2"): {"hp": 5, "source_id": "rule_v2_hero_a"},
}


def no_duplicate_keys(pairs):
    result = {}
    for key, value in pairs:
        if key in result:
            raise PayloadSyntaxError(f"重复 JSON 字段: {key}")
        result[key] = value
    return result


def reject_nonstandard_numbers(value):
    raise PayloadSyntaxError(f"非标准 JSON 数值: {value}")


def parse_json_strict(raw: str):
    if not raw or not raw.strip():
        raise PayloadSyntaxError("模型内容为空")
    if len(raw.encode("utf-8")) > 20_000:
        raise PayloadSyntaxError("模型输出超出大小限制")
    try:
        data = json.loads(
            raw,
            object_pairs_hook=no_duplicate_keys,
            parse_constant=reject_nonstandard_numbers,
        )
    except json.JSONDecodeError as exc:
        raise PayloadSyntaxError(f"JSON 解析失败: {exc.msg}") from exc
    if not isinstance(data, dict):
        raise PayloadSyntaxError("预期顶层为 JSON object")
    return data


def validate_business(answer: GameAnswer):
    if answer.status == "answered":
        if answer.hp is None or not answer.source_ids:
            raise BusinessValidationError("已回答状态要求生命值和引用来源")
    if answer.status == "insufficient" and answer.hp is not None:
        raise BusinessValidationError("资料不足状态不能输出确定生命值")


def validate_facts(answer: GameAnswer):
    if answer.status != "answered":
        return
    record = TRUSTED_RULES.get((answer.character_id, answer.game_version))
    if record is None:
        raise FactValidationError("没有对应版本的可信角色规则")
    if answer.hp != record["hp"]:
        raise FactValidationError("生命值与可信规则不符")
    if record["source_id"] not in answer.source_ids:
        raise FactValidationError("引用没有包含支持该数据的规则来源")


def validate_model_output(raw: str) -> GameAnswer:
    parsed = parse_json_strict(raw)
    model = GameAnswer.model_validate(parsed)
    validate_business(model)
    validate_facts(model)
    return model


if __name__ == "__main__":
    sample = json.dumps({
        "status": "answered", "character_id": "hero_a", "game_version": "v1",
        "hp": 4, "answer": "角色 A 在 v1 的基础生命值为 4。",
        "source_ids": ["rule_v1_hero_a"],
    }, ensure_ascii=False)
    print(validate_model_output(sample).model_dump())
```

### 10.1 每层错误为何必须区分

- `PayloadSyntaxError`：语法、重复字段、非法数字、超大响应或顶层类型不符合预期；这属于解析/传输内容契约问题。
- `pydantic.ValidationError`：数据能解析，但缺字段、出现未知字段、类型或枚举不对；这属于结构契约问题。
- `BusinessValidationError`：类型正确，但跨字段状态不合理；这属于业务状态问题。
- `FactValidationError`：业务上可回答，但角色版本、生命值或来源与可信数据不符；这属于数据可信性问题。

注意：`GameAnswer` 中的 `hp: int | None` **没有默认值**，因此字段必须存在；该字段可以是 `null`，但不能直接缺省。`ConfigDict(strict=True, extra="forbid")` 用于提高类型约束并拒绝未知字段。

### 10.2 对引用的检查存在边界

示例核对了“引用 ID 是否对应当前角色/版本的规则记录”，并校验结构化 `hp` 数值。它并未自动证明自由文本 `answer` 的每一句话都受到该证据支持。如果需要面向用户展示正式答案，应根据可信规则构造数值描述，或增设逐条断言与来源片段匹配的检查。

## 12. 进阶：业务规则与 Schema 的责任边界如何设计

Pydantic 的 `@model_validator` 可以做跨字段检查，但不是所有业务规则都适合写在模型类中。可以用是否需要**外部状态**来判断：

| 规则例子 | 推荐承载层 |
|---|---|
| `hp` 必须是非负整数 | Schema / Pydantic `Field` |
| `status` 只能是 `answered` 或 `insufficient` | Schema / 枚举类型 |
| `status=answered` 则 `hp` 不为空 | Pydantic 跨字段校验或 Service |
| 用户只能查询自己有权限的私有规则 | Service + 鉴权系统 |
| `source_id` 必须对应指定版本且用户可访问 | Service + 数据库 |
| 工单只能由创建者确认 | Service + 数据库事务 |
| 同一次确认不得重复创建工单 | 数据库唯一约束 + 事务 + 幂等键 |
| 金额与优惠规则一致 | 领域服务 + 确定性计算 |

不建议仅靠提示词来约束不可违反的业务规则：提示词能指导模型行为，但不能替代程序和数据库的硬性检查。

### 12.1 “可选字段”要区分三种概念

- **字段可以缺席**：`{}` 与带字段的对象都允许。
- **字段必须出现但值可以为 `null`**：例如 `{"hp": null}` 是一个明确的“没有可靠数值”状态。
- **字段拥有默认值**：程序可能在字段缺失时填入值，但不能把默认值当成模型真实输出或事实来源。

对于模型对外接口，第三种尤其容易掩盖模型漏填字段。若字段重要，应显式要求模型给出 `null` 或明确状态，并记录何时发生数据缺失。

### 12.2 版本与 Schema 演进

从第一版：

```json
{"status": "answered", "hp": 4}
```

到第二版：

```json
{"status": "answered", "hp": 4, "source_ids": ["doc_1"]}
```

如果老调用方不认识新增字段，且采用严格未知字段拒绝策略，就可能无法处理新版数据。反之，新增必填字段也可能破坏老数据的读取。

工程上应维护明确的 Schema 版本，并在接口变更时执行向前/向后兼容性评估、契约测试和数据迁移。不要仅凭“模型已经按新提示词输出”就认定整个调用链安全升级。

## 13. 从模型 API 接口到业务服务：完整状态分支

模型调用结果至少应区分：

1. 网络请求是否成功、是否超时或限流；
2. 模型生成是否正常结束，是否触发拒答、截断或工具调用；
3. 消息内容是否非空；
4. JSON 是否可解析；
5. Schema、业务与事实是否通过；
6. 是否执行有副作用的业务动作。

**Chat Completions 示例的控制思路**：

```python
# 伪代码：仅展示控制分支，字段需根据实际供应商 SDK 版本核对
choice = response.choices[0]
reason = choice.finish_reason
if reason == "length":
    raise IncompleteOutput("生成被截断")
if reason == "tool_calls":
    # 进入工具调用流程，不能当作普通 JSON 正文处理
    ...
if reason != "stop":
    raise UnexpectedFinishReason(reason)
raw = choice.message.content
if not raw or not raw.strip():
    raise EmptyModelOutput()
validated = validate_model_output(raw)
# 这里只得到候选结果的校验对象；写入/发送需另行鉴权和确认
```

以上 `IncompleteOutput`、`UnexpectedFinishReason`、`EmptyModelOutput` 为说明用的错误类别，需在真实项目中自行定义。`finish_reason` 的取值与 Responses API 事件系统并不完全相同，应以正在使用的具体端点为准。

### 13.1 为什么流式 JSON 不能每收到一个增量就执行

流式响应可能按以下顺序发送：

```text
{"status":
"answered",
"hp":
4}
```

中间增量并不是完整 JSON。即便逐步解析出了 `status` 或 `hp`，在到达完整结束事件、通过验证并完成授权之前，也不能根据部分内容立即写入数据库或调用副作用工具。

可以把未完成的增量用于**界面预览**，但不应混同于已验证、可执行的业务对象。

### 13.2 模型输出与用户输入都属于不可信数据

来自模型的 JSON、外部文档和工具结果不能通过字段内容声明自己的权限。例如：

```json
{
  "action": "delete",
  "resource_id": "42",
  "approved": true
}
```

即使每个字段都符合 Schema，`approved: true` 也不能替代真实用户的确认记录。业务后端必须检查实际身份、资源所有权、确认 token 或已持久化审批状态。

## 14. Schema 设计中的高频陷阱

### 14.1 把 `description` 当成强制约束

```json
{"type": "integer", "description": "应当等于当前版本规则中的生命值"}
```

这不会自动证明数值等于数据库记录。描述可以帮助模型理解，但真实校验仍需程序执行。

### 14.2 用 `enum` 假装已经完成事实核验

限定 `"role": {"enum": ["admin", "user"]}` 只能防止出现未知字符串；不能证明当前账户真的有 `admin` 权限。

### 14.3 忽略浮点数和精度问题

对于金额、积分兑换率、科学测量值，应明确单位与精度。`0.1 + 0.2` 的二进制浮点表示可能不完全等于 `0.3`。金额通常建议使用货币最小单位的整数或 `Decimal`，并对四舍五入规则做确定性定义。

### 14.4 未检查外层输出是否完整

`finish_reason="length"`、流式连接中断、缺失完成事件，都可能导致生成的 JSON 不完整。不能简单把“拼接到当前为止可解析的片段”当作一次成功的完整模型回答。

### 14.5 把自动修复等同于校验通过

模型漏掉字段时，应用若自动填入一个默认值，可能产生看似合格、实则缺乏依据的数据。修复动作应明确区分**格式修复**与**信息补全**。事实字段不能无依据补齐。

### 14.6 模型输出了不存在的引用

合法的 `source_ids` 数组不代表对应文档存在。即使 ID 确实存在，也不代表文档支持相应事实。最少需要查 ID、验证版本，再检查支持关系。

### 14.7 验证器采用宽松转换，却以为已经严格类型检查

例如把字符串 `"4"` 转为整数 `4`，可能在某些输入容错场景下方便，但在需要区分模型是否遵循输出契约的评测中，会掩盖类型错误。需要根据用途选择严格校验和转换策略。

### 14.8 库的 JSON Schema 与供应商的受限子集不同

通用 JSON Schema 2020-12 的关键词集合远大于某些模型 API 的严格结构化输出支持子集。`not`、`if/then/else` 等关键词在通用验证器中可能可用，但在特定 LLM API 的严格模式中可能不受支持。应**本地校验 + 供应商能力核对**，不能只靠模型 API 的 Schema 声明。

## 15. 评测方法：把格式正确率与事实正确率分开

如果对同一组固定问题进行多次模型输出测试，应分别统计：

| 指标 | 定义（示例） | 反映的质量 |
|---|---|---|
| 请求完成率 | 正常完成的请求数 / 总请求数 | 生成/传输可靠性 |
| JSON 语法通过率 | 可严格解析的输出数 / 已完成输出数 | 语法稳定性 |
| Schema 通过率 | 结构合格数 / 已完成输出数 | 契约稳定性 |
| 业务规则通过率 | 业务校验通过数 / 结构合格数 | 业务一致性 |
| 事实正确率 | 经独立参考资料判定正确的回答数 / 可判定回答数 | 事实准确性 |
| 引用支持率 | 有实际证据支持的断言数 / 需引用断言数 | 可追溯性 |
| 未知时正确处理率 | 在不可回答样例中恰当报告不足的次数 / 不可回答样例数 | 拒绝编造能力 |

统计口径应写明分母、排除条件和无法判定样例的处理方式。**结构通过率达到 100%，也不能推出事实正确率达到 100%。**

对于一次修改的比较，应保持同一数据集、规则版本、评分标准和尽可能一致的模型配置；不能因为某次示例看起来不错就断言新 Prompt 更可靠。

## 16. 错误返回设计与调用方处理

可以设计应用层统一错误结构：

```json
{
  "code": "MODEL_SCHEMA_INVALID",
  "message": "模型结果缺少必需字段",
  "retryable": true,
  "request_id": "req-demo-001"
}
```

`retryable` 应按失败种类、幂等性、供应商限制和业务副作用谨慎设置；它不是简单的固定属性。比如“字段缺失”在读取场景中可能允许有界重试，而“用户无权限执行删除”则不应重试。

HTTP 状态码需要与 API 契约配合：用户输入校验失败可能返回 422；上游模型返回不可用可能映射为 502/503；上游超时可能使用 504。这是**常见设计选择**，不是所有系统都必须使用的唯一映射。

建议至少记录：`request_id`、模型 ID、提示词与 Schema 版本、结束状态、解析错误类别、校验失败路径、来源版本、耗时、Token 用量。日志应避免直接记录密钥、个人隐私和未经脱敏的敏感原始内容。

## 17. 面向 AI 应用的可靠输出契约

一个较完整的结构化回答可以包含：

```json
{
  "status": "answered",
  "answer": "根据指定规则版本，角色 A 的基础生命值为 4。",
  "facts": [
    {"field": "base_hp", "value": 4, "source_id": "rule_v1_hero_a"}
  ],
  "missing_information": [],
  "game_version": "v1"
}
```

合理的设计思想是：

1. **明确状态**：已回答、资料不足、版本冲突、拒答等状态必须可区分。
2. **事实粒度**：尽量把重要数值拆到结构化字段，而不是只存放自然语言正文。
3. **引用绑定**：为需要证据的断言提供对应来源 ID，后端核对来源实际内容。
4. **版本记录**：注明规则版本、Schema 版本以及答案生成时间（若业务需要）。
5. **业务独立验证**：不从模型输出中的 `approved`、`owner_id` 等字段获取真正的授权。
6. **失败可观察**：当格式、结构、事实或外部服务失败时，返回明确错误，而不是用假答案“补齐”。

## 18. 常见问题辨析

**Q1：既然模型启用了严格 JSON Schema，还需要 Pydantic 吗？**

需要，至少建议在关键业务边界保留应用侧数据验证。原因包括模型和 API 的边缘情况、Schema 子集、应用版本不一致，以及模型输出之外的数据也需要被验证。Pydantic 也可用于解析并转换成有类型的 Python 对象。

**Q2：Pydantic 校验通过，能直接入库吗？**

不能仅凭这一点。必须继续检查业务规则、事实来源、用户权限、重复请求与事务约束；是否需要人工确认取决于操作风险。

**Q3：既然引用 ID 真实存在，为什么不能认为回答可靠？**

因为一个真实文档可能不支持模型给出的具体断言。至少要校验引用内容与断言之间的支持关系。

**Q4：JSON 字段都正确，但 `answer` 描述写错了怎么办？**

结构化字段可以通过可信数据构造文本，或对自由文本单独做事实/语义核验。仅检查结构化 `hp` 不足以证明整段 `answer` 完全正确。

**Q5：错误时能否要求模型自动补齐？**

可以在有明确来源和规则的情况下有界修复格式或重新生成，但不能为了满足 Schema 随意编造缺失事实。

**Q6：`status="stop"` 能证明 JSON 已完整且正确吗？**

不能。即便生成结束状态正常，还需要检查内容非空、语法、Schema、业务和事实。注意实际的结束字段名称取决于 API；在 Chat Completions 中常用 `finish_reason="stop"`。

**Q7：Schema 能否代替权限控制？**

不能。即使模型正确输出 `user_id`、`approved`、`resource_id`，仍需从可信认证上下文判断真实调用方与权限。

**Q8：JSON Schema 的 `default` 会自动补字段吗？**

标准 JSON Schema 中 `default` 通常是注释信息，不表示普通验证器必须自动修改原始数据。某些特定工具可能提供自己的填充行为，应与标准语义区分。

## 19. 核心术语对照

| 术语 | 英文 | 作用 |
|---|---|---|
| 序列化 | Serialization | 对象转成传输或存储表示 |
| 反序列化 | Deserialization | 文本/字节转为程序对象 |
| 解析 | Parsing | 判断并构建语法结构 |
| 结构校验 | Schema Validation | 验证字段、类型、范围和结构约束 |
| 业务校验 | Business Validation | 校验领域规则、状态、权限和依赖关系 |
| 事实核验 | Fact Verification | 将断言与可信事实来源对照 |
| 结构化输出 | Structured Outputs | 约束模型结果形状或格式的接口能力 |
| 约束解码 | Constrained Decoding | 在生成过程中限制输出满足某些语法/结构条件 |
| 严格模式 | Strict Mode | 依据特定库/API 限制类型转换或 Schema 遵循 |
| 契约测试 | Contract Testing | 检查系统接口双方对数据约定的兼容性 |
| 幂等性 | Idempotency | 重复执行不产生重复业务效果 |
| 溯源 | Provenance | 记录某项数据或断言来自何处 |

## 本节结论

**合法 JSON 是语法条件；Schema 是结构契约；业务规则是领域约束；事实校验需要可信证据。** 任何一层通过，都不能自动替代后续的判断。

一个可被业务依赖的 AI 输出系统，不应该只检验“`json.loads()` 会不会报错”，而应该分层识别：是否完整生成、是否可解析、字段是否正确、状态是否合理、来源是否支持、用户是否有权执行。只有完成与当前任务相关的这些检查，结构化输出才有可能成为可靠的软件接口。
