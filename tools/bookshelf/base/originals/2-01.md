## 1. 先建立一张概念地图

一次典型的大语言模型请求可以概括为：

```text
应用构造请求
  ├── 系统/开发者指令
  ├── 当前用户消息
  ├── 选择性加入的历史消息
  ├── 工具定义、检索资料、工具返回结果
  └── 输出格式与其他参数
         │
         ▼
   文本编码 / Tokenization
         │
         ▼
   Token ID 序列（输入 Token）
         │
         ▼
  模型处理输入（通常称 Prefill）
         │
         ▼
  自回归逐 Token 生成（Decode）
         │
         ▼
  输出 Token → 解码为文本/结构化内容
         │
         ├── API 响应与 Usage 统计
         ├── 应用层校验、事实核对
         └── 如有需要：持久化会话或检索记忆
```

这一过程中，各个名词回答的问题不同：

| 名称 | 核心问题 | 不能混同为 |
|---|---|---|
| Token | 模型以什么离散单位读写文本？ | 字符、单词、知识点 |
| Tokenizer | 文字如何变成 Token ID？ | Embedding 模型、词义理解 |
| 上下文窗口（Context Window） | 一次生成时能容纳多少上下文内容？ | 模型实际可靠利用的信息量 |
| 输入 Token 用量 | 送入模型的内容用了多少 Token？ | 只算用户输入的字数 |
| 输出 Token 用量 | 模型生成用了多少 Token？ | 只算可见答案的字数 |
| 自回归生成 | 输出是怎样一步步产生的？ | 查数据库并复制事实 |
| 幻觉（Hallucination） | 为什么生成内容可能没有事实依据？ | 仅仅是语法错误 |
| 长期记忆 | 信息如何跨请求、跨会话保存和取回？ | 把所有聊天都塞入 Prompt |

## 2. Token 的严格含义

### 2.1 Token 是离散编码单位，不固定等于一个“字”

文本 Token 是由指定 **Tokenizer（分词/编码器）** 产生的离散单位。每个 Token 通常对应一个整数标识符（Token ID），然后由模型转换成可计算的向量表示。

一个 Token 可能对应：

- 一个常见单词；
- 单词的一部分（例如常见后缀）；
- 一个中文字、多个中文字，或中文字的编码片段；
- 空格、标点、换行及其组合；
- 特定的控制标记，例如消息分隔标记。

**不能普遍断言“1 Token = 1 个汉字”或“1 Token = 4 个字符”。** 官方给出的英文近似换算只适合做粗略估算；实际数量依赖模型使用的编码、语言、文本形式和空格等细节。[1][2]

### 2.2 从文字到 Token ID

概念上可以表示为：

```text
原始文本
  ↓  Unicode 文本 / 内部字节表示
Tokenizer
  ↓
[Token ID 19, Token ID 450, Token ID 72, ...]
  ↓
模型的 Token Embedding 表
  ↓
向量序列
```

这里的数字只是概念示例，不对应任何真实模型词表。

常见的编码方法包括 BPE（Byte Pair Encoding）、Unigram Language Model 等。不同模型可能采用不同版本的分词器、词表和特殊标记集合。

**BPE 的基本直觉**：从较小的基础单元开始，将训练统计中经常连续出现的片段合并为更大的 Token 单元。实际实现细节因分词器而异，不应把所有分词器都当作完全相同的 BPE。

### 2.3 为什么同一个词在不同位置可能得到不同 Token 数？

Tokenization 不一定以人类语言学的“词”为边界。例如，前导空格、大小写、标点、换行都会影响切分。某个常见英文单词在带前导空格与不带前导空格时，可能被编码为不同 Token；中文与混合代码也存在类似差异。

因此，准确计数应使用**目标模型对应的 tokenizer 或供应商的 token-count API**，而不是简单调用 Python 的 `len(text)`。

### 2.4 特殊 Token 与聊天消息的额外开销

除了可见文本，一些模型协议还使用特殊 Token 或内部结构表示：

- 消息开始和结束；
- 不同角色或通道；
- 工具调用及工具结果边界；
- 结构化数据或多模态内容。

所以一条“用户仅输入十几个字”的请求，实际输入用量也可能包括系统指令、工具描述、历史消息、图片处理成本及协议包装开销。**消息如何序列化、哪些部分计入 Usage，是 API 协议与模型实现的具体约定。**

### 2.5 Tokenizer 与 Embedding 不是同一件事

- **Tokenizer**：把文本拆为离散 Token ID。
- **Token Embedding**：在语言模型内部把 Token ID 映射为连续向量。
- **检索用 Text Embedding 模型**：把片段或文档编码为适合相似度检索的向量。

检索用 Embedding 不等同于生成模型内部的 Token Embedding；二者目的与训练方式可以不同。

## 3. 输入 Token、输出 Token、缓存 Token 与推理 Token

### 3.1 输入用量（Input / Prompt Tokens）

输入用量通常包含实际传递给模型的以下内容中适用的部分：

1. 系统与开发者指令；
2. 当前用户输入；
3. 本次重新提交或服务器维护的会话历史；
4. 工具定义（名称、描述、参数 Schema）；
5. 检索的资料片段、工具返回值；
6. 其他多模态内容及协议开销。

因此，一个聊天产品的“本轮用户消息只有 50 字”，不代表输入 Token 仅有几十个。越长的历史、越多的工具定义，可能使每轮请求的输入成本上升。

### 3.2 输出用量（Output / Completion Tokens）

输出是模型本次生成的 Token。对纯文本模型而言，通常与答案长度有关，但可能包括用于生成工具调用参数的 Token 等。

**推理模型的特殊情况**：某些 API 将不可直接展示给用户的推理 Token 计入输出用量；它们与最终可见文字不是一回事，也不应该在总输出 Token 外再次重复相加。[1][3]

### 3.3 API Usage 的示意

以下是 **Chat Completions 风格的示意 JSON**，不保证所有提供商都使用这些字段：

```json
{
  "usage": {
    "prompt_tokens": 12000,
    "completion_tokens": 1800,
    "total_tokens": 13800,
    "prompt_tokens_details": {
      "cached_tokens": 8000
    },
    "completion_tokens_details": {
      "reasoning_tokens": 500
    }
  }
}
```

解释：

- 输入共 12,000 Token，其中示例中的 8,000 属于可复用缓存输入的子集；
- 输出共 1,800 Token，其中 500 是推理 Token 的子集；
- 总量是 12,000 + 1,800 = 13,800 Token；
- **不能**再把 `cached_tokens` 和 `reasoning_tokens` 额外加到总量上。

实际 API 可能使用 `input_tokens`、`output_tokens` 或其他字段名；其统计粒度、缓存写入与读取字段、多模态 Token、是否包含服务端维护的历史等都可能不同。请以响应结构和官方说明为准。[3]

### 3.4 Prompt Caching 缓存了什么？

Prompt Cache 通常指服务端识别到可复用的相同提示词前缀后，复用其先前计算状态（例如 Transformer 的 KV 状态），减少重复的输入处理计算。它不是“模型永久学会了这段内容”。[4]

应区分：

| 维度 | 是否因输入缓存自动消失？ |
|---|---|
| 逻辑上的输入上下文占用 | 否，通常仍算在上下文中 |
| 必须重新完成的输入计算 | 可能减少 |
| 费用 | 可能按缓存输入的不同费率计算 |
| 跨会话长期记忆 | 否 |
| 模型参数是否被更新 | 否 |

缓存命中条件、存活期、费率和多模态支持属于供应商特定行为。

### 3.5 费用不能只用总 Token 数直接乘同一个单价

对于一个同时区分普通输入、缓存输入、缓存写入和输出的假想 API，可以写成：

\[
C = N_{\mathrm{uncached}}P_{\mathrm{input}} + N_{\mathrm{cached}}P_{\mathrm{cached}} + N_{\mathrm{output}}P_{\mathrm{output}} + C_{\mathrm{other}}
\]

其中：

- `N` 是各类 Token 数量；
- `P` 是相应计费单价（要与每 Token / 每百万 Token 的单位一致）；
- `C_other` 可能包含工具、存储或其他独立收费项目。

某些服务还会单独计缓存写入价格或其他类别。**这个公式是理解分类计费的框架，不是对所有供应商费率结构的通用声明。**

## 4. 上下文窗口到底是什么

### 4.1 容量，而不是记忆质量

**上下文窗口**是模型在一次生成过程中能够处理的上下文序列长度限制，通常以 Token 计量。

它不是：

- 模型训练时看过的数据总量；
- 模型参数中储存的知识量；
- 模型永久保存所有会话的容量；
- “窗口内每条信息都能被准确调用”的保证。

根据 API 协议，一次请求中的上下文预算可能需要覆盖输入与新生成的输出；一些服务同时设置独立的最大输出长度。具体限制以模型文档为准。[2][5]

### 4.2 上下文预算的示意计算

假设一个**虚构模型**支持总共 64,000 Token 的上下文，且本次还需要预留 6,000 Token 的输出：

| 内容 | 示例 Token 数 |
|---|---:|
| 系统指令和工具定义 | 4,000 |
| 历史对话 | 30,000 |
| 检索资料 | 20,000 |
| 当前用户消息 | 2,000 |
| 输出预留 | 6,000 |
| **合计** | **62,000** |

这在示意模型的 64,000 Token 总预算之内，但距离上限只有 2,000 Token 缓冲。若还有未计入的序列化、多模态或工具开销，就可能超限。

可以写作：

\[
N_{\mathrm{input}} + N_{\mathrm{output\ reserve}} + N_{\mathrm{other}} \leq W
\]

其中 `W` 为上下文容量上限。该关系适用于“输入和输出共同消耗同一窗口”的模型，但某些 API 对输出另设上限，还可能有更严格的输入限制；不要把上式当作供应商的完整校验规则。

### 4.3 最大上下文与最大输出是两个指标

例如一个模型即使具有很大的总上下文，也可能有更小的单次最大输出上限。因此：

- 能读入大量文档 ≠ 能一次性输出同样长的回答；
- 可以申请 `max_output_tokens=20000` ≠ 该模型一定允许这么多输出；
- 输入已经接近窗口上限时，留给输出的空间可能很少。

### 4.4 多轮聊天为何会不断消耗上下文

对于一种常见的**无服务端会话状态 API**，应用每次需要自行拼接历史：

```text
第 1 轮：系统 + 用户1
第 2 轮：系统 + 用户1 + 助手1 + 用户2
第 3 轮：系统 + 用户1 + 助手1 + 用户2 + 助手2 + 用户3
...
```

因此，“对话已经持续几小时”并不意味着模型持有一个不断增长且永不丢失的隐藏内存。更常见的是应用重发历史、裁剪内容、提供摘要、使用检索或依靠服务端会话存储重建输入。

这几种做法的保留能力和成本不同。服务端有会话 API，也不意味着模型参数发生在线学习。

### 4.5 达到窗口限制后会发生什么？

常见策略包括：

1. 请求被拒绝，提示输入过长；
2. 服务端或应用裁剪早期内容；
3. 应用生成历史摘要并替换原文；
4. 分块处理资料，按需检索相关部分；
5. 更换允许更大窗口的模型。

究竟执行哪一种，不是由“LLM”这一概念自动决定的，而是 API 和应用架构决定的。

## 5. 自回归生成（Autoregressive Generation）

### 5.1 “预测下一个 Token”的严格表述

对于给定输入上下文 `x` 和输出序列 `y_1, y_2, ..., y_T`，自回归语言模型把完整序列的条件概率拆解成连续的下一 Token 条件概率：

\[
P(y_1,\ldots,y_T\mid x) = \prod_{t=1}^{T} P(y_t\mid x,y_1,\ldots,y_{t-1})
\]

直观理解：模型先结合 `x` 选择第一个输出 Token，再把刚生成的结果加入上下文，选择第二个，依此继续，直到结束标记或到达输出限制。

这不意味着模型只能机械模仿上一句话，也不意味着它完全没有抽象能力。大量参数训练后，下一 Token 分布可以表达语法、语义、世界知识、推理模式和行为偏好；但**生成目标本身不提供对现实世界的逐条事实保证**。

### 5.2 两个阶段：Prefill 与 Decode

许多 Transformer 推理系统可以简化为两段：

**Prefill（处理输入）**：一次处理已经提供的大段输入，为后续生成建立内部表示或缓存状态。

**Decode（增量生成）**：逐步产生新的 Token，利用已有状态继续生成。通常会使用 KV Cache 等机制，避免每一步都从零计算完整历史。

这些是常见推理实现术语，不代表所有模型、硬件或服务都严格采用同一种内核。

```text
输入 Token：A B C D
  └─ Prefill ─→ 内部状态
                   │
                   ├─ 预测下一个 Token：E
                   ├─ 追加 E，再预测：F
                   ├─ 追加 F，再预测：G
                   └─ ...直到结束
```

### 5.3 因果 Attention 与“不能看到未来”

典型的自回归 Transformer 使用因果注意力掩码（Causal Mask），使某个位置只能利用允许的历史位置，而不能直接使用尚未生成的未来输出。训练时可以并行计算多个训练位置的损失；实际生成新 Token 时通常依赖之前已经生成的结果。

### 5.4 训练目标与交叉熵

在基础的下一 Token 预训练中，模型通过最小化实际 Token 的负对数概率来学习：

\[
\mathcal{L} = -\sum_t \log P_{\theta}(x_t\mid x_{<t})
\]

其中 `θ` 表示模型参数。训练还可以包含指令微调、偏好优化或其他目标，因此**不能简单认为所有现代模型只有这一个训练目标**。

这个公式解释了一个关键问题：基础预训练的直接目标是使训练序列的后续 Token 概率较高，而不是为每一条生成的事实提供独立证据。

## 6. 从概率分布到实际输出：采样与解码

模型在某一步生成时，通常先计算各候选 Token 的分数（Logits），再转换为概率分布，例如：

\[
P_i = \frac{\exp(z_i/T)}{\sum_j \exp(z_j/T)}
\]

其中 `z_i` 是候选 Token 的 Logit，`T` 是温度参数（Temperature，`T>0` 的标准 Softmax 写法）。

- `T` 较高，分布通常更平坦，低概率候选更容易被采样；
- `T` 较低，概率更集中；
- `T=0` 在 API 中通常是一个特别定义的解码模式，而不是把上式直接除以零；
- **Temperature 低不等于输出必然正确，也不保证跨机器、跨版本或多次调用完全确定。**

还有常见的候选限制策略：

- **Top-k**：只考虑概率最高的 `k` 个候选；
- **Top-p / Nucleus Sampling**：只考虑累计概率达到阈值的一组较高概率候选；
- **Greedy Decoding**：直接选择当前概率最大的候选；
- **Beam Search**：维护若干候选路径（不一定被聊天 API 提供）。

不同模型可能限制、忽略或不支持某些参数，尤其是专门的推理模型。

### 6.1 为什么越往后生成越可能累积错误？

模型第 `t` 步依赖前面已经生成的 `y_1...y_{t-1}`。如果前面给出了错误日期、错误实体或错误前提，那么后续生成可能围绕这个错误继续构造一个流畅而内部一致的故事。

因此，对关键事实的验证应在信息进入后续链路之前进行，例如工具返回值校验、检索证据引用、确定性数值计算。

### 6.2 一个最小概率采样演示

下面的 Python 程序只演示“从概率分布抽取一个选项”，**它不是神经网络，也不代表真实 Tokenizer 的行为**：

```python
import random

next_token_probs = {
    "正确答案": 0.60,
    "错误但流畅的答案": 0.30,
    "不知道": 0.10,
}

rng = random.Random(42)
choices = list(next_token_probs)
weights = list(next_token_probs.values())

for _ in range(5):
    print(rng.choices(choices, weights=weights, k=1)[0])
```

它说明：只要一个错误候选具有非零概率，单次采样就可能输出错误内容。真实模型生成的概率分布复杂得多，错误也不仅来自随机采样。

## 7. 为什么模型会编造事实（幻觉）？

### 7.1 幻觉的定义与边界

在事实性任务中，幻觉通常指模型输出与可核验事实不一致、或者输出缺乏可靠支持的信息。它并非简单等同于：

- 正常的文学虚构或角色扮演；
- 主观意见；
- 由于工具或数据库本身出错导致的所有错误；
- 无效 JSON 或格式错误。

用户明确要求写小说时，虚构内容不是问题；用户要求查询真实公告时，捏造公告就属于问题。

### 7.2 原因一：生成目标与事实核验目标不相同

模型可以学会：某种句式里最自然出现的是一个年份、论文名称或人物姓名，却不一定具有辨别该事实真伪所需的权威证据。高概率的 Token 序列可能只是文本上**看起来像正确答案**。

研究指出，预训练中的下一词预测任务并没有为每条句子附带真假标签，训练和测评又可能奖励猜测而不是表达不确定性，因此模型在缺乏依据时仍有动力生成具体陈述。[6][7]

### 7.3 原因二：训练数据不完备、冲突或过时

模型训练语料可能包含：

- 同一事件的多个相互冲突版本；
- 已经失效的旧政策或旧价格；
- 广告、谣言、推测和讽刺文本；
- 某些人物、地区、产品的严重数据不足。

这些问题不是把温度降到 0 就能解决的。

### 7.4 原因三：问题本身缺少信息

例如：

> “某公司上周发布的内部产品版本号是多少？”

如果模型没有内部资料或可靠外部来源，就不应在缺少信息时凭空猜测。

这类问题应返回“缺少依据”，或调用有权限的外部查询工具，而不是根据公司常见版本号格式进行补全。

### 7.5 原因四：长上下文检索失败或证据冲突

即使正确答案已经出现在上下文里，模型仍可能：

1. 没有关注到正确段落；
2. 混淆不同文档的版本；
3. 将相近术语错误合并；
4. 优先使用参数中记住的旧答案；
5. 在两份冲突资料之间选择错误来源。

长上下文中信息位置影响效果的问题已被研究观察到，但其程度依赖模型、任务与提示构造，不能假定所有模型都表现相同。[8]

### 7.6 原因五：形式正确不代表内容可靠

例如：

```json
{
  "source": "2026年某公司官方公告",
  "effective_date": "2026-01-01",
  "status": "confirmed"
}
```

这个 JSON 在语法上合法，字段也可以满足 Schema，但如果真实公告不存在，那么整体仍然是幻觉。

所以要分开：

1. **语法合法性**：能否解析；
2. **结构合法性**：是否满足字段、类型及范围；
3. **事实正确性**：有无真实来源支持；
4. **业务正确性**：是否满足业务规则与权限边界。

### 7.7 常见幻觉类型

| 类型 | 例子 | 合适的核查方法 |
|---|---|---|
| 实体幻觉 | 编造不存在的产品或论文 | 权威目录、官方文档 |
| 数值幻觉 | 捏造价格、库存、统计值 | 数据库、计算、最新来源 |
| 时间幻觉 | 将旧政策当作现行政策 | 发布日期、版本、有效期 |
| 引用幻觉 | 引用不存在的页码或段落 | 逐条核对引用片段 |
| 因果幻觉 | 将相关性当作因果性 | 研究设计与证据链 |
| 工具幻觉 | 声称已经执行实际未执行的操作 | 工具执行日志与状态回执 |

## 8. 语言流畅、语气自信与可信度不是同一指标

模型的文字可以写得极具说服力，但这不能作为真假判定依据。

应区分：

- **Fluency（流畅性）**：语言是否自然；
- **Coherence（连贯性）**：论述前后是否一致；
- **Factuality（事实性）**：是否符合可核查事实；
- **Groundedness（有据性）**：是否由指定资料支持；
- **Calibration（校准性）**：模型表达的置信程度与实际正确概率是否匹配。

模型“看起来非常确定”不代表其实际正确率高。模型写出冗长的推理过程，也不等于推理中的每一步都能独立得到证明。

尤其在工程场景中，不应将模型自评的“正确率 99%”直接视为可用指标；应使用独立的测试集与外部事实源。

## 9. 长上下文为什么不等于可靠记忆

### 9.1 上下文是临时工作材料，不是持久化数据库

可以类比计算机系统：

- 上下文窗口像当前正在工作的任务所能直接访问的一块**有限工作区**；
- 模型参数像训练后固化下来的统计与知识表示；
- 外部数据库或记忆库像持久化存储。

这个比喻仅用于区分职责，并不表示 LLM 与 CPU / RAM / 磁盘完全等价。

一次请求结束后，普通无状态模型调用不会自动把聊天内容写入模型参数。下一次能否回忆，需要应用是否重新提供历史、摘要或检索记忆。某些产品有持久化 Memory 功能，但这是**产品级存储、检索与上下文管理**，不是单次 `context_window` 自发产生的能力。

### 9.2 “放得下”与“找得准”不同

长上下文能力至少有三个不同层次：

1. **可接收（Capacity）**：接口能够接收较长的 Token 序列；
2. **可定位（Retrieval）**：模型能从中找到相关段落；
3. **可正确使用（Reasoning/Grounded Generation）**：模型能引用正确证据，解决问题，不把相近内容混淆。

第 1 项成立，不等于第 2、3 项必然成立。

《Lost in the Middle》指出，在其受测模型中，相关信息位于长上下文开头或结尾时，部分任务表现更好，而放在中间时会下降。这是一个具有代表性的经验发现，不应夸大为所有模型的固定规律。[8]

### 9.3 上下文越长，干扰也可能越多

增加上下文不仅增加可能有用的信息，也可能加入：

- 重复但不一致的版本；
- 历史上已经被纠正的错误回答；
- 与当前问题无关的长篇内容；
- 不可信外部文本中的命令或诱导；
- 高相似度却不是目标版本的资料。

若无来源管理和版本优先级机制，模型可能在大量候选信息中选错。**更多上下文是容量增长，不是信息质量自动提升。**

### 9.4 多轮历史会发生四种典型损失

**裁剪损失**：最早的消息可能被删除。  
**摘要损失**：长文压缩为短摘要时，细节、数值、例外条件可能消失。  
**检索损失**：相关资料未召回，或者被相似但错误的材料替代。  
**使用损失**：正确资料已召回，但生成时未能遵守它。

这些是不同故障层，不能统称为“模型记忆不好”后就只采取增加上下文窗口的方案。

### 9.5 KV Cache、Prompt Cache、对话历史和长期记忆的区别

| 名称 | 目的 | 是否天然跨会话持久 | 能否独立保证事实正确 |
|---|---|---|---|
| KV Cache（推理态） | 减少生成时的重复计算 | 否 | 否 |
| Prompt Cache | 复用相同前缀的输入计算 | 依服务缓存生命周期，非可靠业务记忆 | 否 |
| 对话历史 | 保留既往交互文本 | 由应用存储策略决定 | 否 |
| 历史摘要 | 降低长历史的上下文消耗 | 由存储策略决定 | 否，可能丢细节 |
| RAG 知识库 | 检索外部文档证据 | 可以，取决于存储系统 | 不保证，需要检查来源 |
| 结构化业务数据库 | 保存精确的状态、数值和版本 | 通常可以 | 在约束和数据治理范围内更可验证 |
| 用户长期记忆库 | 保存可再次检索的用户相关信息 | 可以，取决于应用设计 | 不保证，需更新、删除、校验 |

## 10. 训练知识、当前上下文与外部记忆的三个层次

### 10.1 参数化知识（Parametric Knowledge）

模型训练时学到的信息，以分布式方式反映在参数中。这并不是可直接遍历的事实数据库。

特点：

- 无法保证知道训练截止后的新闻；
- 很难按单条事实可靠地删除、更新和证明来源；
- 同名人物、相似实体、不同年份可能相互干扰；
- 不能认为“模型曾在训练中见过”就一定能正确复述。

### 10.2 上下文内信息（In-Context Information）

当前请求中直接提供的提示词、对话和文档。模型无需修改参数就能在本轮使用这些信息。其使用效果受上下文长度、布局、干扰、模型能力影响。

### 10.3 外部持久化记忆（External Memory）

由程序将信息存入数据库、搜索索引、向量库或文件，并在需要时检索。

优点：

- 可以保留来源、创建时间、版本和访问权限；
- 可以明确更新、撤销和删除；
- 可以跨进程和服务重启保存；
- 可以为每次回答追溯证据。

但外部记忆同样有质量问题：如果写入内容本身错误、检索命中错误或版本失效，就仍可能输出错误答案。

## 11. 怎样让模型在知识型任务中更可靠

### 11.1 把确定性事实交给确定性系统

例如：

| 任务 | 优先依赖 |
|---|---|
| 计算价格与手续费 | 程序计算 |
| 查询用户订单状态 | 有权限的业务数据库 |
| 查询最新政策 | 有日期与出处的官方材料 |
| 总结多篇文章 | 文档检索与模型摘要 |
| 生成草稿 | 模型生成 + 用户确认 |
| 判断是否具有删除权限 | 后端权限检查 |

模型可以负责理解自然语言、提取字段、组织解释，但不能把未经验证的生成内容直接当作业务真相。

### 11.2 RAG 的基本机制

```text
用户提问
   ↓
识别任务 / 确定版本与权限
   ↓
检索文档、数据库或工具
   ↓
获取带 source_id、version、timestamp 的证据
   ↓
模型依据证据生成候选回答
   ↓
校验引用是否支持相应陈述
   ↓
返回回答、引用或“证据不足”
```

RAG 主要解决的是“把相关外部知识提供给模型”，而不是自动解决模型所有幻觉问题。

### 11.3 为重要陈述保留可核查的来源

每个检索片段至少可记录：

```json
{
  "source_id": "game_rule_2026_11",
  "document_version": "1.4",
  "section": "角色技能/技能A",
  "updated_at": "2026-11-01",
  "content": "示例规则文本……"
}
```

模型输出中可引用 `source_id` 和章节；应用可进一步检查引用确实属于已检索到的材料。**存在来源 ID ≠ 引用已支持具体结论**，还需要语义上的证据核验。

### 11.4 明确“资料不足”是合法结果

可靠的系统需要支持：

- 当前资料未收录；
- 资料版本不明确；
- 多个来源相互冲突；
- 数据无法验证；
- 外部工具调用失败。

不要把“必须给出一个具体答案”作为所有任务的成功标准。能正确拒绝猜测，也是事实性系统的重要能力。

## 12. 长对话如何管理：历史、摘要、检索与结构化状态

### 12.1 四种常见策略

**策略 A：全量历史**  
优点是简单、细节保留充分；缺点是成本随轮次增长、可能达到窗口上限，并且存在干扰。

**策略 B：滑动窗口**  
只保留最近若干轮，成本可控；缺点是容易忘记很早之前的约束。

**策略 C：历史摘要**  
将较早内容压缩，适合保留整体方向；缺点是细节与证据可能丢失。重要数值不宜只保留自然语言摘要。

**策略 D：外部记忆 + 按需检索**  
将历史事实、偏好、任务状态写入结构化存储，需要时检索；复杂度更高，但可治理、可追溯。

实际应用通常会组合使用，而不是只选一种。

### 12.2 结构化记忆示意

```json
{
  "subject_id": "user_1001",
  "fact_type": "preferred_language",
  "value": "zh-CN",
  "source": "user_confirmed",
  "updated_at": "2026-11-11T09:00:00Z",
  "version": 2,
  "is_active": true
}
```

这个结构使系统可以更新值、区分信息来源和有效状态。实际开发还需要认证、访问控制、隐私治理和删除能力。

### 12.3 保存记忆前应考虑的检查

- 是用户确认的事实，还是模型推断？
- 是长期稳定信息，还是短期情境？
- 是否需要保存敏感数据？是否获得必要授权？
- 新旧事实发生冲突时如何更新？
- 何时过期，如何撤回或删除？
- 下次检索如何保证不会误用其他用户的信息？

**长期记忆是一套数据管理机制，而不只是更长的 Prompt。**

## 13. API 开发中如何正确统计与限制 Token

### 13.1 尽量使用响应 Usage，而非字数估算

```python
# 演示如何避免重复统计缓存 Token、推理 Token。
usage = {
    "prompt_tokens": 12000,
    "completion_tokens": 1800,
    "total_tokens": 13800,
    "prompt_tokens_details": {"cached_tokens": 8000},
    "completion_tokens_details": {"reasoning_tokens": 500},
}

input_tokens = usage["prompt_tokens"]
output_tokens = usage["completion_tokens"]

# 缓存与推理用量是各自总量的子集（按此示例 API 结构）。
assert input_tokens + output_tokens == usage["total_tokens"]
print("input:", input_tokens, "output:", output_tokens)
```

注意：一些 API 在流式输出过程中只在结束事件提供完整 Usage；若连接提前断开，应用可能拿不到完整统计。不同服务还可能分别提供网关用量和最终账单口径。

### 13.2 使用目标 Tokenizer 估算输入

下例使用 OpenAI 的 `tiktoken`，但**目标模型的编码必须确认存在对应映射**：

```bash
python -m pip install tiktoken
```

```python
import tiktoken

# 示例模型名称仅用于说明 API 用法；
# 应按实际部署模型选择正确编码与计数方式。
encoding = tiktoken.get_encoding("cl100k_base")

texts = [
    "Hello, world!",
    "你好，世界！",
    "def add(a, b): return a + b",
]

for text in texts:
    token_ids = encoding.encode(text)
    print(repr(text), "=>", len(token_ids), "tokens", token_ids)
```

此程序用于比较一种具体编码对不同文本的切分；它不能代替任意模型的精确 API 请求计数。聊天消息包装、工具定义、多模态输入和供应商专用格式可能另有额外成本。

### 13.3 上下文预算应预留余量

应用可以在提交模型前预估：

```python
def can_fit_context(
    input_tokens: int,
    reserved_output_tokens: int,
    context_limit: int,
    estimated_overhead: int = 0,
) -> bool:
    return (
        input_tokens + reserved_output_tokens + estimated_overhead
        <= context_limit
    )

assert can_fit_context(52000, 6000, 64000)
assert not can_fit_context(62000, 6000, 64000)
```

该代码体现通用预算思路，真实应用仍需叠加模型最大输出限制、API 专用规则、工具开销与输入计数误差。

### 13.4 为什么不能机械地把历史追加到无限大

如果每一轮都重复发送所有历史，即使本轮问题很短，输入 Token 也可能接近历史累计长度。这样会同时带来：

1. 成本上升；
2. 输入处理延迟增加；
3. 截断与上下文溢出风险；
4. 相关信息被不相关历史稀释；
5. 更大的隐私与数据治理负担。

对于长期运行的 Agent，要把**工作状态、会话历史、工具记录、知识库和用户长期记忆**区分存储，按任务需要组装上下文。

## 14. 一个典型故障：模型“记得”错误的规则

假设有游戏规则：

- 旧版 1.0：角色 A 的技能每回合可使用 2 次；
- 新版 1.4：同一技能每回合只能使用 1 次；
- 用户问：“当前版本中可以使用几次？”

如果模型回答“2 次”，可能有多种不同原因：

| 故障层 | 实际情况 | 应如何修复 |
|---|---|---|
| 资料录入 | 知识库只有 1.0 版 | 导入 1.4 版并登记版本 |
| 检索过滤 | 同时召回 1.0 和 1.4 | 根据用户版本做元数据过滤 |
| 上下文组织 | 新版内容被截断 | 调整预算和资料组织 |
| 模型生成 | 看到新版仍回答旧版 | 强化证据约束、测试并核查引用 |
| 版本定义 | 用户没说“当前”指哪一版 | 使用可查证的最新版本或询问澄清 |

仅仅把上下文窗口从 32K 加到 128K，无法保证自动修复这些问题。

## 15. 关键概念的对照与误区澄清

| 常见说法 | 更准确的认识 |
|---|---|
| “一千汉字就是一千 Token。” | Token 数与具体编码及文本有关，应实际计数。 |
| “上下文窗口 1M 就能准确记住 1M 内容。” | 容纳能力和可靠检索、理解、引用能力是不同指标。 |
| “每次对话后模型就学会了我的新信息。” | 一般无状态 API 不会因此修改模型参数；持续记忆需外部机制。 |
| “低温度输出就不会出错。” | 降低随机性不能解决过时知识和证据缺失。 |
| “JSON 合法就说明答案可信。” | 结构合法不等于事实正确。 |
| “Prompt Cache 是长期记忆。” | 缓存复用计算，不是可信持久记忆库。 |
| “输出里有来源链接就代表是真的。” | 来源必须存在，并实际支持对应陈述。 |
| “只要多给模型资料，它就会更准确。” | 无关、重复、冲突和过时资料可能降低表现。 |
| “模型答错一定是 Prompt 不够好。” | 可能是训练信息、检索、版本、工具、数据或生成问题。 |
| “模型说自己有 99% 把握就可信。” | 自述置信度不能代替独立评测和证据。 |

## 16. 如何验证长上下文与幻觉问题：实验设计

### 16.1 固定内容，改变证据位置

准备三份内容基本相同的长输入，唯一差别是正确证据的位置：

- 版本 A：证据在开头；
- 版本 B：证据在中间；
- 版本 C：证据在末尾。

对每个版本使用同一问题、同一模型和一致的解码参数，重复运行，记录：

1. 是否答对；
2. 是否引用正确证据；
3. 延迟、输入输出用量；
4. 错误来自未命中、误引用还是错误推断。

此实验可以研究位置敏感性，但结论必须限定到实际测试的模型、样例和输入长度。

### 16.2 区分“无答案”与“答错”

评测至少应包括：

- 材料中存在明确答案；
- 材料中没有答案；
- 新旧版本冲突；
- 多份文档中存在相似但不同的对象；
- 有外部证据与无外部证据两种条件。

如果数据集中只有“有答案”的问题，就无法测试系统是否会在无依据时停止猜测。

### 16.3 可量化指标

- **Exact Match / Accuracy**：最终答案是否正确；
- **Evidence Support Rate**：引用是否真正支持答案；
- **Abstention Accuracy**：该回答“不知道”时是否正确拒绝猜测；
- **Version Consistency**：是否按指定版本回答；
- **Latency**：响应耗时；
- **Input / Output Tokens**：实际用量和成本。

真实模型评测与程序单元测试应分开：前者评估事实和任务效果，后者验证固定逻辑、预算检查、异常处理、权限和持久化行为。

## 18. 总结：这条知识目标的技术逻辑

1. **Token 决定模型处理文本的离散单位。** Token 数量不是固定的字数换算，应以实际编码和 API Usage 为准。
2. **上下文窗口定义容量。** 输入、工具内容及输出预算之间存在约束，不能只看当前用户消息的长度。
3. **自回归模型通过条件概率逐步生成。** 概率高与事实真实是不同概念，因此流畅自然的答案也可能错误。
4. **幻觉是系统性风险。** 模型可能受到训练目标、数据、证据缺失、检索失败和生成过程共同影响。
5. **长上下文不是可靠记忆。** 保留、检索、更新、撤销和验证信息，必须依赖上下文管理、外部存储及适当的证据机制。
6. **工程上最重要的边界是把“生成”与“事实”分开。** 关键数据通过数据库和工具得到，证据通过来源与版本核对，模型主要承担理解、组织和表达。
