## 1. Agno 的定位与基本概念

**Agno 是用于构建 AI Agent、工具调用、会话与执行编排的 Python 框架。** 它封装模型提供商差异，并组织“模型生成工具调用意图 → 执行工具 → 将结果交回模型 → 生成答案或继续调用”的循环。

在应用代码中，最常见的对象如下：

| 对象/概念 | 作用 | 常见 API |
|---|---|---|
| `Agent` | 组合模型、指令、工具及运行配置 | `Agent(...)` |
| Model adapter | 对接具体模型提供商 | `DeepSeek(...)`、`OpenAIResponses(...)` |
| Python tool | 暴露给模型选择调用的函数 | `tools=[lookup_rule]` |
| `RunOutput` | 一次非流式执行的结果与元信息 | `result.content`, `result.status` |
| `RunOutputEvent` | 流式模式下的事件 | `event.event`, `event.content` |
| `RunEvent` | 事件类型的枚举 | `RunEvent.run_content` |
| `RunContext` | 当前运行的上下文与已解析依赖 | `run_context.user_id` |
| Session | 多个 Run 所属的同一会话 | `session_id` |
| Database backend | 持久化执行、会话和消息 | `SqliteDb` 等 |
| AgentOS | 将 Agent 暴露成服务、提供相关运行能力 | REST/SSE；需单独配置 |

Agno **不是模型本身**、不是 Python 的事件循环、不是数据库，也不自动替代业务服务。模型选工具的准确性仍需测试，业务接口仍需权限和事实校验。

### Agent 与框架之间的关系

```text
                 应用 API / 用户界面
                         │
              业务入口（认证与校验）
                         │
                    Agno Agent
       ┌─────────────────┼─────────────────┐
       │                 │                 │
 模型适配器          工具定义            会话/运行状态
       │                 │                 │
   大模型 API    业务 Service / Repository    DB
                         │
              数据库、外部 API、检索系统
```

这里的箭头代表调用关系，**不是权限继承关系**。模型可以要求调用工具，真正的工具代码仍然必须判断是否允许执行。

## 2. Agno 的 Agent 执行模型

官方对单次 Run 的过程描述为：

1. 构造模型上下文：系统要求、用户输入、按配置提供的历史和状态；
2. 发给模型；
3. 若模型直接回复，返回最终结果；
4. 若模型提出工具调用，则解析参数并执行工具；
5. 将工具结果返回模型；
6. 继续直到模型给出最终回复、运行暂停、取消、失败或触发停止条件。

```text
用户：“某角色在 V1.2 的生命值是多少？”
         │
         ▼
Agent 调用模型（包含 lookup_character 工具定义）
         │
         ▼
模型提出：lookup_character(name="角色A", version="1.2")
         │
         ▼
Agno 调用工具函数
         │
         ▼
业务代码校验版本与访问范围、查询真实数据
         │
         ▼
实际结果：{"hp":4,"source":"rules-v1.2"}
         │
         ▼
结果回到模型上下文 → 模型输出说明
         │
         ▼
Agno 返回 RunOutput / 流式事件
```

模型**没有直接拥有数据库连接的权限**，除非应用将对应能力暴露给它。这里的业务代码查出的 `hp=4` 是确定性事实，模型最后的自然语言回答仍有可能说错，必要时需再次检验。

### 为什么先使用单个 Agent

多个 Agent、Team、Workflow 可以增强系统，但也增加状态、事件和失败路径。对于“查询规则 + 查询结构化游戏数据 + 输出说明”，先采用**一个 Agent + 两个只读工具**足以验证框架的关键能力。

## 3. 环境、依赖与模型接入


注意：密钥不得写入仓库、演示日志或文档的真实样例。部署时使用安全的环境配置或密钥管理服务。

### 3.2 最小接入代码

`minimal_agent.py`：

```python
from agno.agent import Agent
from agno.models.deepseek import DeepSeek

agent = Agent(
    model=DeepSeek(id="deepseek-v4-flash"),
    instructions="请使用中文回答。信息不足时明确说明。",
)

response = agent.run("简要解释 asyncio.Task 的作用。")
print(response.content)
print(response.status)
```

说明：`deepseek-v4-flash` 是核对时 Agno DeepSeek 官方示例所使用的模型 ID；**实际可调用性取决于对应账号、提供商与 API 产品**，不能把示例模型 ID 当作永远可用的常量。

### 3.3 正常运行的结果如何理解

`RunOutput` 中值得读取的字段包括：

| 字段 | 作用 |
|---|---|
| `content` | 本次最终回答，或结构化结果 |
| `status` | 执行状态，如 completed / paused / cancelled / error |
| `run_id` | 单次运行唯一标识 |
| `session_id` | 会话标识 |
| `user_id` | 与运行关联的用户标识 |
| `model` / `model_provider` | 实际模型信息 |
| `messages` | 保留的消息及工具往来 |
| `tools` | 本次工具执行记录 |
| `metrics` | 运行用量等指标 |

**检查 `content` 非空不足以认定任务成功**。必须进一步结合 `status` 和业务校验。即使运行成功，事实准确性仍需证据。

## 4. 将 Python 函数注册为工具

### 4.1 函数工具最小示例

```python
from agno.agent import Agent
from agno.models.deepseek import DeepSeek

RULES = {
    ("角色A", "1.2"): {"hp": 4, "source": "rules-v1.2/hero-a"},
    ("角色A", "1.3"): {"hp": 3, "source": "rules-v1.3/hero-a"},
}

def lookup_character(name: str, version: str) -> dict:
    """按明确的游戏版本查询角色基础数据。

    Args:
        name: 游戏角色名称。
        version: 游戏规则版本，如 1.2。
    """
    record = RULES.get((name, version))
    if record is None:
        return {"found": False, "reason": "未找到对应版本的角色数据"}
    return {"found": True, "name": name, "version": version, **record}

agent = Agent(
    model=DeepSeek(id="deepseek-v4-flash"),
    tools=[lookup_character],
    tool_call_limit=4,
    instructions="涉及角色属性时，必须按用户版本查询工具，不要猜测数值。",
)

agent.print_response("角色A在1.2版本的生命值是多少？")
```

Agno 会使用**函数名、类型标注、docstring**生成工具描述供模型选择。模型有机会选错工具或传错参数；框架执行前的基本参数处理**不等于业务鉴权**。

### 4.2 如何设计高质量工具

工具应尽量满足：

- 名称是动作与对象的组合，例如 `lookup_character`，而不是模糊的 `get_data`；
- docstring 描述用途和必要前提；
- 参数明确（版本、对象 ID、可选筛选项），避免让模型猜参数；
- 结果结构稳定，例如 `found`、`data`、`source`、`version`、`error_code`；
- 没有结果、版本冲突和权限拒绝是**不同错误**；
- 尽量避免一次工具暴露“任意 SQL 执行”等过强能力。

### 4.3 同步工具与异步工具

只访问本地字典或做轻量计算的工具可以同步实现。涉及数据库、HTTP 调用等 I/O 的工具通常更适合异步：

```python
import httpx

async def fetch_rule_summary(rule_id: str) -> dict:
    """从只读规则服务获取特定规则摘要。"""
    async with httpx.AsyncClient(timeout=10.0) as client:
        r = await client.get("https://example.com/api/rules", params={"id": rule_id})
        r.raise_for_status()
        return r.json()
```

这个例子用于说明异步形态：URL 为演示地址，并非真实业务 API。实际服务应在应用生命周期内复用 `AsyncClient`，并校验请求目标、权限和响应 Schema。

Agno 官方说明：异步运行会优先使用异步工具（如果有），并且在模型支持时可以执行并行工具调用。**不能因为使用了 `arun()` 就假定同步网络或 CPU 密集工具自动非阻塞**。

## 5. 同步与异步执行语义

### 5.1 四种常见调用方式

| 写法 | 用途 | 返回/消费方式 |
|---|---|---|
| `agent.run(prompt)` | 同步、非流式 | 直接得到 `RunOutput` |
| `agent.run(prompt, stream=True)` | 同步、流式 | 普通 `for` 迭代事件 |
| `await agent.arun(prompt)` | 异步、非流式 | `await` 得到 `RunOutput` |
| `agent.arun(prompt, stream=True)` | 异步、流式 | `async for` 迭代事件 |

**异步流式最易犯错的是用 `await` 等待整个流对象，然后再遍历。** 当前官方示例的正常用法是直接对流执行 `async for`。

### 5.2 异步非流式

```python
import asyncio
from agno.agent import Agent
from agno.models.deepseek import DeepSeek

agent = Agent(model=DeepSeek(id="deepseek-v4-flash"))

async def main() -> None:
    result = await agent.arun("解释 Python 的事件循环。")
    print("状态：", result.status)
    print("答案：", result.content)

if __name__ == "__main__":
    asyncio.run(main())
```

### 5.3 Async ≠ 自动并行

`await agent.arun(...)` 的意义是当前任务在等待合适的异步 I/O 时允许事件循环调度其他任务。`asyncio.gather()` 或创建 `Task` 可以安排多个运行重叠执行，但必须配合并发限额、超时、资源复用和取消控制。

如模型后端限制并发为 5，启动 500 个 Agent Run 不会自动提高真实吞吐；可能造成大量排队、429、内存增长或额外费用。

## 6. 流式事件：从文本增量到工具生命周期

### 6.1 `stream` 与 `stream_events`

```python
stream=True           # 让 Agent 按事件增量输出
stream_events=True    # 进一步暴露工具及生命周期等中间事件
```

默认的流并不保证每个事件都是文本；暂停、取消和错误也可能以事件出现。启用完整事件后，处理程序应按事件**类型**分派，而不是把所有 `content` 拼接成回答。

### 6.2 重要事件

| 类别 | 事件 | 含义 |
|---|---|---|
| 运行 | `RunStarted` | Run 已开始 |
| 文本 | `RunContent` | 文本增量 |
| 文本 | `RunContentCompleted` | 内容流结束，不等于整个运行成功 |
| 工具 | `ToolCallStarted` | 开始调用工具 |
| 工具 | `ToolCallCompleted` | 工具完成，附带结果 |
| 工具 | `ToolCallError` | 工具调用失败 |
| 控制 | `RunPaused` | 等待确认或其他恢复条件 |
| 控制 | `RunContinued` | 暂停后继续 |
| 终态 | `RunError` | 运行出错 |
| 终态 | `RunCancelled` | 运行取消 |
| 终态 | `RunCompleted` | 运行完成事件，仍需识别先前取消状态 |
| 用量 | `ModelRequestCompleted` | 一次模型请求完成，可携带指标 |

不同功能配置和模型提供商会影响可见事件的范围。不能假设每次执行都有全部事件。

**重要细节：** Agno 文档特别指出：取消时可能先发出 `RunCancelled`，之后仍有 `RunCompleted` 事件。因此 `RunCompleted` 不能脱离先前的取消、失败与暂停状态单独判断为业务成功。

### 6.3 异步事件最小消费器

```python
import asyncio
from agno.agent import Agent, RunEvent
from agno.models.deepseek import DeepSeek

async def main() -> None:
    agent = Agent(model=DeepSeek(id="deepseek-v4-flash"))
    status = "incomplete"
    pieces = []

    async for event in agent.arun(
        "一句话解释 asyncio。",
        stream=True,
        stream_events=True,
    ):
        if event.event == RunEvent.run_content and event.content:
            pieces.append(event.content)
            print(event.content, end="", flush=True)
        elif event.event == RunEvent.run_cancelled:
            status = "cancelled"
        elif event.event == RunEvent.run_error:
            status = "error"
        elif event.event == RunEvent.run_paused:
            status = "paused"
        elif event.event == RunEvent.run_completed and status == "incomplete":
            status = "completed"

    print("\n最终状态：", status)
    print("已收到文本：", "".join(pieces))

if __name__ == "__main__":
    asyncio.run(main())
```

这是**运行事件消费者**，并不是生产级重连协议；客户端断网与应用进程异常时，可能没有机会收到终态事件。因此无终态必须保留为 `incomplete` 或 `disconnected`，并通过持久化运行状态核查。

### 6.4 事件处理的关键规则

1. `RunContent` 的每一片是**增量**，不要拿最后一片当完整答案。
2. 工具事件是**状态信息**，不能当作助手自然语言答案直接展示。
3. 事件有 `run_id`、`session_id` 等身份字段；必须按当前运行关联。
4. 输出已开始并不意味着最终成功，状态应由终态/持久化记录决定。
5. SSE / WebSocket / HTTPX 只是把事件送给前端的**传输层**，Agno 的事件对象还需要由 API 层编码。
6. 不能默认展示模型的内部推理内容；事件可能包含提供商显式开放的推理数据，但那并不等于完整内部推理过程。

## 7. 完整的异步工具 Agent 示例

本示例使用**只读游戏规则工具**，不要求数据库，也不会改变真实业务数据；能演示 Agno 模型 → 工具 → 结果 → 事件流的闭环。真实运行需要有效 DeepSeek API Key。

文件 `agno_rule_agent.py`：

```python
import asyncio
from agno.agent import Agent, RunEvent
from agno.models.deepseek import DeepSeek

GAME_DATA = {
    ("角色A", "1.2"): {"hp": 4, "source": "demo/rules/v1.2/hero-a"},
    ("角色A", "1.3"): {"hp": 3, "source": "demo/rules/v1.3/hero-a"},
}


def lookup_character(name: str, version: str) -> dict:
    """读取指定版本的游戏角色数值。

    Args:
        name: 角色名称。
        version: 游戏规则版本，例如 1.2。
    """
    found = GAME_DATA.get((name, version))
    if found is None:
        return {"ok": False, "code": "NOT_FOUND", "version": version}
    return {"ok": True, "name": name, "version": version, **found}


def make_agent() -> Agent:
    return Agent(
        name="RuleAssistant",
        model=DeepSeek(id="deepseek-v4-flash"),
        tools=[lookup_character],
        tool_call_limit=3,
        instructions=(
            "你是游戏规则助手。涉及角色数值必须调用工具并依据返回值回答。"
            "没有数据时说明未知，不得编造角色属性。"
        ),
    )


async def main() -> None:
    agent = make_agent()
    outcome = "incomplete"
    answer_parts: list[str] = []

    async for event in agent.arun(
        "角色A在1.2版本的生命值是多少？说明资料来源。",
        user_id="demo-user",
        session_id="demo-session-001",
        stream=True,
        stream_events=True,
    ):
        if event.event == RunEvent.run_content and isinstance(event.content, str):
            answer_parts.append(event.content)
            print(event.content, end="", flush=True)
        elif event.event == RunEvent.tool_call_started:
            print("\n[工具开始]", flush=True)
        elif event.event == RunEvent.tool_call_completed:
            print("\n[工具结束]", flush=True)
        elif event.event == RunEvent.tool_call_error:
            print("\n[工具失败]", flush=True)
        elif event.event == RunEvent.run_cancelled:
            outcome = "cancelled"
        elif event.event == RunEvent.run_error:
            outcome = "error"
        elif event.event == RunEvent.run_paused:
            outcome = "paused"
        elif event.event == RunEvent.run_completed and outcome == "incomplete":
            outcome = "completed"

    print("\n\n运行状态：", outcome)
    print("最终回答：", "".join(answer_parts))


if __name__ == "__main__":
    asyncio.run(main())
```

说明：这里的 `demo-user` / `demo-session-001` 是单人演示标签。**真实多用户系统不能让客户端自行指定另一个用户的 `user_id` 或复用他人的 `session_id`**；必须从已认证会话派生用户身份，并检查会话归属。

### 成功与异常情况下的预期行为

- **成功：** 工具找到记录 → 模型根据返回值解释 → 运行完成。
- **资料缺失：** 工具返回 `NOT_FOUND` → 模型说明未知或请求补充版本。
- **模型错误使用工具：** 模型返回的最终文字仍可能不准确，应用可将回答中的关键数值与工具结果复核。
- **API 超时/限流：** Run 可能触发错误事件或抛出异常；调用层应有明确错误与重试政策。
- **用户断开：** 不应把已收到的部分文本标为最终成功。

## 8. 在 FastAPI 中交付流式结果

Agno 事件与浏览器 SSE 是两个层次：

1. Agno 产生**内部 Python 事件对象**；
2. FastAPI 将经筛选的事件转换为 SSE 格式；
3. 前端按事件类型更新 UI。

### 8.1 SSE 事件编码

```python
import json

def encode_sse(event_name: str, payload: dict) -> str:
    return (
        f"event: {event_name}\n"
        f"data: {json.dumps(payload, ensure_ascii=False)}\n\n"
    )
```

每条事件由事件名与 JSON 数据组成。`json.dumps` 会对换行符等特殊字符进行转义，减少 SSE 帧被非预期拆分的风险。

### 8.2 FastAPI 简化接口

```python
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from agno.agent import RunEvent

app = FastAPI()
agent = make_agent()   # 使用上一个示例的 make_agent

@app.get("/chat/stream")
async def stream_chat(request: Request, question: str):
    # 演示用途。生产环境必须从认证组件获取 user_id/session_id，
    # 并给共享 Agent、数据库与模型请求配置容量/资源控制。
    async def events():
        status = "incomplete"
        try:
            async for ev in agent.arun(
                question,
                user_id="demo-user",
                session_id="demo-session-001",
                stream=True,
                stream_events=True,
            ):
                if await request.is_disconnected():
                    return
                if ev.event == RunEvent.run_content and ev.content:
                    yield encode_sse("text_delta", {"text": str(ev.content)})
                elif ev.event == RunEvent.tool_call_started:
                    yield encode_sse("tool_started", {"run_id": ev.run_id})
                elif ev.event == RunEvent.tool_call_completed:
                    yield encode_sse("tool_finished", {"run_id": ev.run_id})
                elif ev.event == RunEvent.run_cancelled:
                    status = "cancelled"
                elif ev.event == RunEvent.run_error:
                    status = "error"
                elif ev.event == RunEvent.run_paused:
                    status = "paused"
                elif ev.event == RunEvent.run_completed and status == "incomplete":
                    status = "completed"
        except Exception:
            status = "error"
            # 不把底层异常和密钥直接送给用户
        yield encode_sse("run_status", {"status": status})

    return StreamingResponse(events(), media_type="text/event-stream")
```

该代码是**协议边界教学简化版**，不代表完整生产部署。需要另外处理：请求认证、运行 ID 与会话所有权、入口限流、长连接心跳、取消策略、工具输出脱敏、流式错误响应、事件持久化与重连策略。`is_disconnected()` 仅检测可观测的断开情形，并不能保证及时取消远端模型计算。

### 8.3 前端消费语义

| 后端 SSE 事件 | 前端动作 |
|---|---|
| `text_delta` | 将文本追加到当前答案 |
| `tool_started` | 展示“正在查询数据” |
| `tool_finished` | 结束工具等待提示 |
| `run_status=completed` | 标记回答完成 |
| `run_status=error` | 显示失败和可重试提示 |
| `run_status=cancelled` | 标记取消 |
| 连接丢失且无终态 | 标记不完整，向持久化记录查询 |

前端显示内容不应该把工具执行日志直接混入用户可见文本；工具结果可能包含敏感字段。

## 9. 会话、Run、工具状态与存储

### 9.1 四个不同维度

| 概念 | 标识 | 说明 |
|---|---|---|
| 用户 | `user_id` | 应用认证得到的身份 |
| 会话 | `session_id` | 多个 Run 的共同上下文 |
| 执行 | `run_id` | 一次模型/工具执行过程 |
| 工具调用 | 每次调用的调用 ID | 对应参数与真实执行结果 |

### 9.2 持久化不等于自动加入上下文

Agno 支持把 Session、Run 和消息保存至数据库，但要把历史消息带入下一次模型请求，仍需要显式的历史配置，例如 `add_history_to_context=True`。可以通过 `num_history_runs` 或 `num_history_messages` 控制引入范围。

```python
from agno.agent import Agent
from agno.db.sqlite import SqliteDb
from agno.models.deepseek import DeepSeek

agent = Agent(
    model=DeepSeek(id="deepseek-v4-flash"),
    db=SqliteDb(db_file="tmp/rules.db"),
    add_history_to_context=True,
    num_history_runs=3,
)
```

SQLite 适合本地学习；并发、可靠性、迁移和生产部署需要进一步选择数据库与连接管理方案。

### 9.3 为何不能共享默认 Session ID

如果一个长寿命的共享 `Agent` 实例自动生成默认 `session_id`，之后又在多个用户请求中复用，可能意外把不同用户的数据关联到同一会话。多用户系统应**明确传入各自的 session_id 和 user_id，并在业务层验证归属**，不能把 ID 当作权限凭证。

### 9.4 Session State 和真正的业务存储

Session State 可保存运行间需要的小型上下文状态，如用户选择的规则版本。但订单、交易、已确认反馈等真实业务状态，应该存储在有独立权限和事务保证的业务数据库中。不能依赖模型记忆或无约束的 Session 字典来保障金融、订单等关键数据的一致性。

## 10. 框架能力与业务责任：严格分界

### 10.1 Agno 已提供的能力

- 模型提供商适配、模型请求组织；
- Agent 执行循环与模型/工具往返；
- Python 函数和 Toolkit 注册工具；
- 非流式/流式运行接口；
- 工具与运行生命周期事件；
- 运行状态、会话与可配置的存储；
- 部分工具控制：调用次数限制、确认暂停、工具钩子；
- 与 AgentOS 组合时提供服务、追踪和其他运行基础设施。

这些能力有配置和版本前提，不能理解成“引用 `agno` 就自动全部启用”。

### 10.2 业务代码必须承担的责任

| 责任 | 为什么不能完全交给框架/模型 |
|---|---|
| 身份认证 | 只有业务系统知道真实登录用户与组织关系 |
| 对象级授权 | 模型传来的对象 ID 不是访问授权 |
| 规则计算 | 数值要由确定性代码或数据库提供 |
| 资料版本 | 需要业务方定义来源与有效期 |
| 工具副作用 | 写入、删除、发送必须满足确认与幂等 |
| 数据库事务 | 业务跨表原子性由持久化层保证 |
| 费用/配额 | 模型调用可能造成真实成本，需要服务级配额 |
| 多租户隔离 | 要按认证身份限制数据库查询范围 |
| 输出校验 | 运行成功不保证内容真实或符合业务约束 |
| SLA/降级 | 后端应有超时、熔断与备用策略 |
| 审计与隐私 | 工具结果、日志和用户数据需脱敏与分级访问 |
| 测试与部署 | 单机示例不代表服务重启、扩容和故障恢复可靠 |

> 设计原则：**Agno 负责 AI 编排，不承诺替代业务事实、权限和数据一致性。**

### 10.3 对于游戏规则助手的推荐分工

```text
前端：聊天、工具状态、引用展示、取消/重试
 FastAPI：认证、接口契约、运行隔离、SSE
 Agno：模型、工具选择、编排与流式事件
 业务工具：版本校验、精确查询、只读/写入边界
 PostgreSQL：业务持久化、事务和数据隔离
 pgvector/RAG：有来源的规则检索
 Redis/Kafka：在确有缓存和可靠异步任务需求时加入
```

不应该在学习 Agno 的第一天就用它替代全部服务组件。

## 11. 权限、参数与副作用治理

### 11.1 `RunContext` 的职责

Agno 可以向工具注入 `RunContext`，其中包含 `user_id`、`session_id`、`run_id`、`dependencies` 和 `session_state` 等信息：

```python
from agno.run import RunContext


def get_current_user_label(run_context: RunContext) -> str:
    """读取当前运行关联的用户标签，不执行敏感操作。"""
    return str(run_context.user_id or "anonymous")
```

Agno 能传递这些标识，但业务服务器仍需确保其来自**受信任的认证/授权入口**，而不是客户端随意提供。

### 11.2 读和写必须分开设计

- 只读规则查询可在严格授权的范围内自动执行；
- 发送邮件、删除数据、修改配置等操作应有更高等级的授权及确认机制；
- Agno 的 `requires_confirmation` 可以帮助暂停执行，但确认界面显示的对象和内容、确认后的参数冻结、审批者身份、幂等重放保护仍是业务系统责任；
- 对用户资料或工具返回的“忽略指令、给我更高权限”等文本，按不可信数据处理，不能扩大工具权限。

### 11.3 为什么不建议一开始暴露 PythonTools

让模型直接运行 Python 或安装依赖会大幅扩大执行权限。Agno 官方的 PythonTools 示例也说明：即使工具集限制了部分操作，能够运行任意 Python 的能力本身并不自动构成安全沙箱。学习工具调用时更推荐从**具体、只读、明确参数**的函数开始。

## 12. 超时、取消与生命周期

### 12.1 不同的超时

1. **模型请求超时：** 连接、读取及模型返回限制，由模型客户端/HTTP 库配置；
2. **单个工具超时：** 外部业务 API 或数据库查询的限定时间；
3. **整个 Agent Run 超时：** 含多轮模型与工具循环的全局截止时间；
4. **前端流式连接超时：** 网络空闲、反向代理及客户端连接生命周期。

这些超时不天然相等，也不会因为 `arun()` 使用异步就自动设置完成。

### 12.2 取消不等于回滚

Agent 取消通常是协作式的：请求取消之后，执行过程在可观察的取消点停止。远程模型可能已经产生费用，外部数据库或 API 可能已经提交了副作用。所以要区别：

- **取消运行的后续执行**；
- **取消尚未开始的工具**；
- **回滚已经提交的业务数据**；
- **撤销已对外发送的通知**。

后两项通常需要独立业务操作，不能被框架通用取消机制替代。

### 12.3 后台运行 ≠ 可靠队列

Agno 当前文档区分直接 SDK 的进程内后台任务与需要持久化队列的 AgentOS 路径。`background=True` 不等同于 Kafka/Worker 的跨进程可靠执行承诺。对于资料导入、批量模型处理，仍需设计持久化状态、重试、幂等和 Worker 恢复机制。

## 13. 观测、用量与测试

### 13.1 应记录的基础字段

```json
{
  "run_id": "run-demo-001",
  "session_id": "session-demo-001",
  "user_id": "user-demo-001",
  "agent_version": "rule-agent-v1",
  "model_requested": "deepseek-v4-flash",
  "prompt_version": "rules-prompt-v1",
  "status": "completed",
  "tool_calls": 1,
  "duration_ms": 850,
  "usage": {
    "input_tokens": null,
    "output_tokens": null
  }
}
```

此 JSON 完全是**结构示例**，不是实际模型调用日志。指标不可得时使用 `null`，不能猜测用量；不得把真实用户隐私、密钥或未脱敏工具结果直接写入日志。

### 13.2 测试需要分成两层

**模型隔离测试**：使用假模型/假工具，验证程序如何分派事件、处理超时、保存调用状态、隔离数据。

**真实集成测试**：使用可用的 Agno 版本和模型账号，记录真实的 `RunOutput`、工具调用记录和 Token 用量，验证模型是否正确选择工具。

只通过 Python 语法检查，不等于 Agno 实际执行已经成功。即使离线模拟运行通过，也不能据此断言模型选择正确率。

### 13.3 事件消费者的可验证不变量

- 文本必须按顺序拼接；
- 只有 `RunContent` 产生文本增量；
- 工具事件不能被计入答案正文；
- 已取消或出错的 Run 不得因为后续 `RunCompleted` 被标为成功；
- 未观察到终态的流不得被标为成功；
- 事件必须关联同一个 `run_id`，不同会话记录不得混合。

## 14. 常见错误与排障

| 症状 | 常见原因 | 处理方向 |
|---|---|---|
| `ModuleNotFoundError: agno` | 环境未安装 / 解释器不对 | 检查 venv 与 `python -m pip show agno` |
| 模型返回认证错误 | API Key 未配置或无权限 | 检查密钥与提供商、模型授权 |
| 工具从未被调用 | 描述不清、模型不支持、工具未注册 | 先用简化工具对照验证 |
| `arun()` 流无法迭代 | 流式和非流式语义混淆 | `stream=True` 用 `async for` |
| 只有文字没有工具事件 | 没有 `stream_events=True` | 启用中间事件并按类型分派 |
| `RunCompleted` 被误判成功 | 忽略取消/错误/暂停 | 使用终态状态机 |
| 两个用户共享对话 | 复用默认 `session_id` | 每会话 ID + 服务端归属校验 |
| 异步接口仍然卡顿 | 同步工具阻塞事件循环 | 使用异步客户端或受控卸载 |
| 重复提交数据 | 工具写入没有幂等性 | 数据库唯一约束与确认绑定 |
| 运行结束但答案数值错误 | 模型误用工具结果 | 程序复核重要数值 |
| 流断开就无任务记录 | 只使用连接内状态 | 持久化运行及明确恢复策略 |

排查原则：先确认**模型调用是否成功**，再确认**工具是否被选中**，再检查**工具实际输入输出**，最后核对**最终回答**。不要把所有失败归因于提示词。

## 15. 渐进架构：何时引入其他 Agno 组件

**第一层：Agent + Python 工具。** 适合掌握模型与工具往返机制。

**第二层：Session/DB + 结构化输出。** 适合多轮问答、状态恢复和结果保存。

**第三层：Agno Knowledge / RAG。** 适合大量文档检索，但来源/版本管理和事实校验仍然独立。

**第四层：Workflow。** 当执行顺序可以预定义、需要可靠节点边界时使用。

**第五层：Team / 多 Agent。** 只有在子任务角色分工确实改善质量、成本或可维护性时引入。

**第六层：AgentOS。** 需要统一 REST/SSE API、追踪、身份验证或部署层能力时考虑；仍需按具体版本配置服务鉴权和可靠后台任务。

不要因为 Agno 支持某个组件就假定实际项目必须使用它。

## 16. 离线验证与真实集成的区别

本节示例分为两类：

1. **框架示例：** 导入 `agno` 的示例，用于展示当前官方接口；需要安装 Agno 和可用模型凭据才能执行真实调用。
2. **离线状态机示例：** 不依赖 Agno 的事件对象，实现同样的状态转移原则，用于本地验证错误、取消、内容增量与终态判定。

离线验证可证明教学状态机的逻辑，但**不能证明模型提供商可用、Agno 包版本兼容或真实流式连接稳定**。

以下离线示例可以单独保存为 `stream_state.py` 并运行：

```python
from dataclasses import dataclass

@dataclass
class SimpleEvent:
    kind: str
    content: str = ""
    run_id: str = "run-1"


def reduce_events(events: list[SimpleEvent]) -> tuple[str, str]:
    text: list[str] = []
    state = "incomplete"
    expected_id = events[0].run_id if events else None
    for item in events:
        if item.run_id != expected_id:
            raise ValueError("混入了不同 run_id 的事件")
        if item.kind == "RunContent":
            text.append(item.content)
        elif item.kind == "RunCancelled":
            state = "cancelled"
        elif item.kind == "RunError":
            state = "error"
        elif item.kind == "RunPaused":
            state = "paused"
        elif item.kind == "RunCompleted" and state == "incomplete":
            state = "completed"
    return state, "".join(text)


if __name__ == "__main__":
    assert reduce_events([
        SimpleEvent("RunContent", "你"),
        SimpleEvent("ToolCallCompleted"),
        SimpleEvent("RunContent", "好"),
        SimpleEvent("RunCompleted"),
    ]) == ("completed", "你好")
    assert reduce_events([
        SimpleEvent("RunCancelled"), SimpleEvent("RunCompleted")
    ])[0] == "cancelled"
    assert reduce_events([SimpleEvent("RunContent", "部分")])[0] == "incomplete"
    print("离线事件状态测试通过")
```
