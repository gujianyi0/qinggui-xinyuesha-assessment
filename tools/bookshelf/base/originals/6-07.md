# 消息队列与后台任务可靠性（七）：消费延迟、在途任务、优雅停机、重平衡与真实业务进度

> 对应学习目标：消费延迟、在途任务、优雅停机和重平衡，区分进程存活与任务真正推进。
>
> 知识范围：Apache Kafka 传统 Consumer Group、Kafka 4.x 新 Consumer Rebalance Protocol、Python asyncio 与 aiokafka、PostgreSQL 中的持久化业务状态。示例侧重理解运行机制和安全边界，使用可离线运行的教学模拟器；真实 Broker 与数据库行为另行区分。
>
> 核心判断：**Worker 进程还活着 ≠ Kafka Consumer 仍持有有效分区 ≠ 正在获取消息 ≠ 正在处理消息 ≠ 业务成功落库 ≠ Kafka 已安全提交进度。**

---

## 01. 为什么消费可靠性不等于进程可靠性

考虑一个资料导入任务：HTTP 接收上传并在 PostgreSQL 创建任务 → 生产者发送 Kafka 事件 → Worker 获取事件 → 解析文档 → 调用 Embedding/LLM API → 写入向量与资料状态 → 提交 Kafka Offset。

其中任一环节都可能独立失败：

1. Worker 在运行，但网络连接异常，无法读取 Kafka。
2. Consumer 正常心跳，但业务协程一直等待一个没有结束的模型 API。
3. Consumer 取得消息，调用外部服务成功，却在数据库提交前失败。
4. 业务数据库已成功提交，但 Kafka Offset 未提交；进程重启后重复消费。
5. 业务计算已经完成，但由于同分区更早的消息未完成，安全提交水位不能前进。
6. 消费组发生 Rebalance，旧 Worker 仍持有尚未结束的本地 Task，但它可能已经失去处理该分区的资格。

所以必须独立观察**进程、消费关系、领取情况、在途任务、持久化业务结果以及安全提交进度**六个层面。

### 1.1 关键时序

```text
Kafka 生产者           Consumer/Worker             PostgreSQL
    |                     |                           |
    |--任务事件----------->|                           |
    |                     |--登记任务为 RUNNING------>|
    |                     |--调用外部模型...          |
    |                     |   (可持续数十秒)           |
    |                     |--写入业务结果------------>|
    |                     |<-------事务已提交---------|
    |                     |--commit(offset+1)-------->Kafka
    |                     |                           |
```

“正在心跳”只覆盖消费组协调层，不能直接证明右侧 PostgreSQL 的写入成功。

## 02. Kafka Consumer 相关 Offset：五个容易混淆的位置

一个 Kafka `TopicPartition` 包含多个不同位置概念，必须按**分区**分别讨论：

- **Record Offset**：消息自身的日志位置。
- **Consumer Position**：消费者下一次可返回给应用的消息位置；读取操作会推动它。
- **Committed Offset**：已持久化的消费组恢复位置，重启、重分配时用于确定从何处开始。
- **Log End Offset（LEO）**：日志末端位置；常见监控工具以此计算差距，需注意复制和事务隔离的具体可见性边界。
- **Business Progress**：业务数据库中已经完成并符合约束的任务或记录；它与上面任何一个 Offset 都不必然相同。

假设分区已经读取到 119（Position=120），但业务仅安全完成到 111（Committed Offset=112），日志末端是 130：

```text
分区日志               112           120              130
                       |-------------|----------------|
已提交安全位置          ^
已交给应用的位置                      ^
Kafka 日志末端                                          ^
```

此时读取较快不意味着业务处理得快。未完成的消息可能已经积压在应用内部。

**重要**：Kafka Offset 可能存在间隙（压缩、事务记录等情形），不能机械地认为 `LEO - Committed Offset` 是等待处理的实际有效记录条数。该差值主要是位置差指标。

### 2.1 `read_committed` 与 LSO

对启用事务的生产者，`read_committed` 消费者可能只能读取到 Last Stable Offset（LSO），即开放事务之前的稳定边界。未结束的事务会让用户误以为“日志有数据，但消费者拿不到”。监控必须明确所使用的隔离级别与末尾位置定义。

## 03. Consumer Lag 是什么：按位置、时间和业务结果分别看

### 3.1 Offset Lag

一种常见的消费组监控口径：

```text
Committed Lag = Log End Offset - Group Committed Offset
```

这是一个便利的**分区位置差**，而不是被证明未完成的独立业务任务数。

客户端指标 `records-lag-max` 往往是**当前位置（Position）与末端的差距**，并不一定等于管理员工具根据提交位点计算的消费组 Lag。不要将两个同名或相近名称的指标当成完全等价。

### 3.2 时间延迟（Latency）

还需要测量：

- **Queue Age**：消息生产到开始执行的等待时间。
- **Oldest Pending Age**：最老未完成消息已经等待了多久。
- **Processing Duration**：工作开始到完成的时间。
- **End-to-End Latency**：消息生产到业务结果持久化的端到端时间。
- **Commit Delay**：业务结果落库到 Offset 安全提交的延迟。

同样的 Lag=100，在每秒生产 1000 条消息的系统与每小时生产 100 条消息的系统中，严重程度完全不同。

### 3.3 处理速率与追赶能力

令输入速率为 λ，业务成功完成速率为 μ：

- `μ > λ`：有可能逐步追上积压；还取决于重试、单分区瓶颈和资源限制。
- `μ ≈ λ`：积压可能长期维持。
- `μ < λ`：在没有限流和扩容的情况下，积压通常增加。

不能只看 `records-consumed-rate`（从 Kafka 取数的速度），应观察 `business_success_rate`（真正持久化成功的速度）。

## 04. 在途任务（In-flight）到底包含什么

日常语言里 In-flight 常指“正在执行的任务”，但正式监控应明确包含哪些状态。一个可操作的定义：

```text
Kafka 已返回给应用但尚未达到终态的消息
= 应用内排队 + 正在处理 + 等待重试 + 等待业务确认的记录
```

对于通过 PostgreSQL 和独立 Worker 处理的任务，还应额外记录：

- `PENDING`：已接受但还未领取。
- `RUNNING`：Worker 已领取且租约有效。
- `RETRY_WAIT`：等待下次重试。
- `SUCCEEDED`：业务事务已完成并持久化结果。
- `FAILED`：达到最终失败条件，失败原因已持久化。
- `CANCELLED`：已取消；已发生的外部副作用不一定被撤销。

在途任务计数最好区分 `fetched_not_started`、`running`、`retry_waiting` 和 `durable_completed_not_committed`。后者**业务已完成**但 Kafka 提交尚未推进，它不能被当作仍需重新执行业务的普通待办。

### 4.1 在途数量与资源占用

如果每条任务会调用模型、占用连接池或存储大文件，盲目预取会让在途任务堆积并耗尽内存。应设计：

- 全局和每个分区的 in-flight 上限。
- 队列容量与饱和后的背压行为。
- 模型 API 并发上限、数据库连接池上限。
- 长耗时任务转为持久化任务并由独立 Worker 运行。
- 在 Redis 或内存进度丢失时，能从 PostgreSQL 恢复真实任务状态。

## 05. Liveness、Readiness 与 Progress：三种不同的健康

### 5.1 Liveness：进程还在吗

进程 PID、HTTP `/health/live` 或 event loop tick 可以证明某个程序仍能回答简单探针。但一个进程完全可能处于“活锁”：持续运行与心跳，业务没有推进。

### 5.2 Readiness：现在适合接活吗

关注 Kafka 分区有效分配、依赖连接、数据库写入、队列容量、是否正在优雅停机，以及内存/连接池是否已达到无法安全继续领取工作的程度。

Readiness 不是直接把“Kafka 临时离线”简化成进程必须重启；它主要决定是否继续接收或领取新工作。

### 5.3 Progress：工作实际推进了吗

需要至少一组**不可伪造为成功**的业务指标：

- 最新成功持久化时间 `last_business_commit_at`。
- `business_success_total` 和每分钟成功速率。
- 失败、重试、取消和结果未知数量。
- oldest in-flight age 与租约超时数量。
- 业务结果和 Kafka Offset 提交进度。

**空闲不等于卡死**：Kafka 没有新消息、in-flight=0、Lag=0、暂时没有成功记录，是正常状态。判定停滞需要结合“确实存在待处理工作”和“超过适用的时限”。

## 06. 四类典型“看起来活着、其实没干活”

| 现象 | 进程 | 心跳 | Fetch/Position | 业务结果 | 初步定位 |
|---|---|---|---|---|---|
| 真正空闲 | 正常 | 正常 | 无新消息 | 无新增 | 不需要报警 |
| 获取消息但模型卡死 | 正常 | 可能正常 | 持续前进 | 长时间无新增 | 外部模型超时、在途过多 |
| 数据库写入失败 | 正常 | 正常 | 可前进 | 成功率 0，错误增多 | DB 连接、事务、约束 |
| Rebalance 频繁 | 正常 | 断续 | 分区反复转移 | 速率下降 | 消费组协调、网络或 poll 间隔 |
| 提交 Offset 卡住 | 正常 | 正常 | 已读取 | 业务可能成功 | CommitFailed、协调器、分区所有权 |
| 旧任务仍在写入 | 正常 | 可能已失效 | 分区已转移 | 旧 Worker 仍有副作用 | 缺少租约/代际保护 |

后端业务进度的仪表板不应只展示 Kafka 消费组的 Lag 和 Worker 存活数量。

## 07. 手动提交的安全水位与并发处理

同分区消息的**获取顺序**和**完成顺序**不同。比如：

```text
Offset    100      101      102      103
状态      成功      执行中    成功      成功
```

即使 103 完成，也不能提交 104。因为 101 尚未完成；提交 104 后进程崩溃，重启可能跳过 101。

正确做法是维护**已持久化完成的可提交前缀（safe commit frontier）**。在上例中，最多提交下一条 `101`。当 101 最终完成，安全提交位点才能向前推进。

Kafka Offset 可能有空洞，因此推进算法应依据消费者**确实已经交付给应用的按序记录集合**，而不能简单要求每个整数 Offset 都出现。

需要区分：

1. 成功返回的 Future 不一定表示数据已持久化。
2. 业务事务完成后，才可以把相应记录标为可提交。
3. 本地“准备提交”不等于 Kafka Broker 确认提交。
4. 如果提交失败，保留较低恢复位置，接受重放并使用业务幂等去重。

## 08. 优雅停机的定义和边界

Graceful Shutdown（优雅停机）的目标不是“进程退出时尽量 sleep 几秒”，而是**在有限窗口内完成安全交接，同时不丢失业务结果、不错误提交消费进度**。

### 8.1 正常步骤

```text
SIGTERM / 部署滚动更新
      ↓
状态设为 DRAINING；不接收新任务，不领取新 Kafka 消息
      ↓
对已领取工作尝试有界等待
      ↓
完成的工作先持久化业务结果
      ↓
按分区安全水位提交 Offset；失败则保持重放可能性
      ↓
超时任务请求取消，保留未完成持久化状态
      ↓
关闭 Consumer、HTTP 客户端、数据库资源
      ↓
进程退出
```

### 8.2 为什么不能先关闭数据库

已运行的 Worker 如果仍需提交事务，提前 `engine.dispose()` 或关闭数据库连接池，会破坏在途任务完成的可能性。因此通常先管理任务生命周期，再释放它们依赖的资源。

### 8.3 Drain Deadline 和 Force Kill

如果容器编排系统只给 30 秒终止宽限，而单次模型调用可能耗时 2 分钟，就不能假设所有任务都能完成。必须有：

- 明确终止总时限和二级取消清理时限。
- 剩余时间不足时拒绝领取新任务。
- 将任务状态、重试次数、业务幂等键持久化。
- 对外部调用结果未知的情况进行核对，而非无条件再次发起副作用。
- 旧 Worker 的临时租约最终失效，新 Worker 能恢复。

Python `Task.cancel()` 是**协作式取消**，并不等价于强制停止进程或撤销第三方 HTTP 请求。

## 09. 停机时哪些操作必须先做，哪些不一定能做

**必须做：**

1. 停止领取新工作。
2. 对在途任务做状态收敛：完成、等待恢复、请求取消或保留状态未知。
3. 记录业务已提交的结果及足以重放的幂等信息。
4. 对仍持有分区所有权的已处理前缀执行安全提交。
5. 释放网络和数据库资源。

**不能保证：**

- 在 SIGKILL 后仍执行 Python `finally`。
- Python 协程取消就让远端模型立即停止计费。
- Kafka Commit 失败就说明业务事务失败。
- 旧 Consumer 离组后不会有尚未结束的后台 Task 继续产生副作用。
- `consumer.stop()` 能自动回滚或终结全部业务任务。

因此，**优雅停机和故障恢复是两个互补设计**：前者降低故障窗口，后者处理正常流程无法保证的情况。

## 10. Rebalance 是什么，为什么会影响在途任务

Consumer Group Rebalance 指消费组协调器重新确定 Topic 分区的消费归属。常见触发包括：

- 有 Consumer 加入或离开。
- Consumer 宕机或被判定失联。
- Topic 分区数发生变化。
- 消费者订阅或元数据发生变化。
- 组协议迁移以及成员/协调器事件。

旧成员可能正在处理原本分配给它的分区。当分区分配给新成员时，旧成员必须停止新的读取和失效提交；业务侧还需防止它“晚到的写入”覆盖新 Worker 的结果。

### 10.1 Rebalance 的一般阶段

```text
稳定状态（ASSIGNED）
    → 将移走的分区标记 REVOKING
    → 停止该分区的新工作
    → 尽量处理已完成任务并提交安全 Offset
    → 撤销该分区所有权 REVOKED / LOST
    → 新 Consumer 获得 ASSIGNED
    → 从可恢复状态开始处理
```

不同协议的回调和阶段可能不同，尤其需要区分 Classic 与 Kafka 4.x 新 Consumer 协议。

## 11. Classic 与 Kafka 4.x Consumer Rebalance Protocol

Kafka 4.0 开始，新 Consumer Rebalance Protocol（KIP-848）成为通用可用能力。其特点包括增量协调、服务端分配策略，以及与 Classic 不同的 heartbeat/session timeout 配置控制。

| 对比 | Classic | Consumer 新协议 |
|---|---|---|
| 协议名称 | `classic` | `consumer` |
| 典型组协调 | 传统分组加入与同步 | 更增量化的协调 |
| 分配策略 | 客户端配置与组协调 | 由 Broker 侧控制为主 |
| 心跳超时参数 | 经典客户端参数 | 服务端参数主导 |
| 兼容性 | 较多成熟客户端支持 | 需要客户端实际支持 |

**不能假设 aiokafka 已完全支持 Java Consumer 在 Kafka 4.4 的所有新行为。** 应检查项目锁定的 aiokafka 版本、支持的 Group Protocol 和回调 API。本文后续的 aiokafka 示例仅使用其文档明确公开的传统接口。

## 12. 心跳、session.timeout 与 max.poll.interval 的区别

在传统 Java Consumer 中：

- `heartbeat.interval.ms`：心跳发送间隔（在 Classic 协议等适用场景下）。
- `session.timeout.ms`：协调器判定成员失联的宽限。
- `max.poll.interval.ms`：应用连续两次 `poll()` 之间的最大时间，目的是防止表面存活却不再领取和处理工作的 Consumer 无限占有分区。

但在新 Consumer 协议下，客户端部分配置被服务器端参数替代，不能照搬旧参数。

而在 **aiokafka** 中，心跳与抓取机制由异步客户端后台任务协调，客户端的行为与 Java 调用线程模型并不完全相同。即使心跳正常，业务协程仍可能处于等待外部 API 或数据库的状态。`max_poll_interval_ms` 的实际应用方式应按 aiokafka 所用版本文档核实。

**结论**：心跳、poll 活动和业务成功率必须独立监控，不能互相代替。

## 13. Rebalance 回调和分区所有权保护

对 aiokafka，`ConsumerRebalanceListener` 可注册：

- `on_partitions_revoked(revoked)`：处理将被撤销的分区。
- `on_partitions_assigned(assigned)`：初始化新分配的分区。

在 revoke 期间：

1. 标记分区进入 `REVOKING`，不再领取新消息。
2. 对相关在途任务有界等待并保存可恢复状态。
3. 只在业务已经持久化完成的范围内提交安全水位。
4. 遇到 `CommitFailedError` 或已经失去所有权时不能盲目重试提交。
5. 撤销后拒绝旧 Worker 的无效业务提交；新 Worker 从数据库任务状态与已提交 Offset 重建。

**死锁风险**：官方 aiokafka 文档提醒，rebalance 监听器由客户端等待完成，会阻塞 `getmany()` / `getone()` 等调用。不能在 `getmany()` 持有某个异步锁时，让 rebalance 回调也试图获取相同的锁。

并且 Rebalance 回调本身也不能作为唯一恢复机制，因为进程被强杀时通常无法运行任何回调。

## 14. 失去分区后的“迟到结果”如何处理

即使 Consumer 已被撤销分区，旧 Worker 发起的外部 API 可能刚刚返回。假如旧 Worker 随后直接写 PostgreSQL，就可能和新 Worker 争抢同一任务。

可采用**任务租约与代际保护**：

```sql
UPDATE tasks
SET state = 'SUCCEEDED', result = :result, updated_at = NOW()
WHERE id = :task_id
  AND state = 'RUNNING'
  AND worker_generation = :generation
  AND lease_owner = :worker_id
RETURNING id;
```

只有仍持有有效代际、符合业务约束的 Worker 才能更新成功；如果受影响行数是 0，则必须判定为**失去执行资格或状态已变化**，不能简单重试覆盖。

真实系统还应维护任务级幂等键、最终结果唯一约束，以及操作前权限和当前状态验证。依赖 Redis 锁单独保证最终唯一性并不充分。

## 15. 如何建立统一的 Worker 状态机

建议将进程与业务任务分开记录：

### 15.1 进程级

```text
STARTING → READY → DRAINING → STOPPED
                    ↘ UNREADY / FAILED
```

### 15.2 分区级

```text
UNASSIGNED → ACTIVE → REVOKING → REVOKED
                      ↘ LOST
```

### 15.3 任务级

```text
PENDING → RUNNING → SUCCEEDED
              ↘ RETRY_WAIT → RUNNING
              ↘ FAILED
              ↘ CANCELLED
```

不能仅凭进程健康把所有业务任务自动标为成功。任务终态应由数据库中的受控状态转换决定。

## 16. 背压、消费速率与在途上限

当模型服务变慢或数据库写入变慢时，应该降低领取量，避免无限创建 Task。

可实施的机制：

- 为 Consumer 的每个分区设置 `max_in_flight`。
- 使用全局 `asyncio.Semaphore` 控制外部 API 并发。
- 使用有界 `asyncio.Queue` 缓冲待处理工作。
- 对长期任务优先持久化后交给独立 Worker，不在 HTTP 请求中等待。
- 在达到容量上限后减少主动 fetch，而不是无限缓存。

对于 aiokafka，官方文档推荐利用 `getmany(*partitions)` 显式选择当前需要读取的分区；不要未经版本核实就假设它支持与 Java Client 完全相同的 `pause()/resume()` API。

注意：**限制并发不自动等于限制队列长度**；Semaphore 如果包在每个新创建的 Task 内，仍可能先产生大量等待中的 Task。应用层需要同时控制创建 Task 的数量与缓冲区容量。

## 17. 安全地组合异步模型调用与 Kafka Consumer

下面是便于理解的简化串行处理示例，它不模拟多分区并发，但有一个显著优势：每条消息只有在业务提交成功后才推进 Offset。

```python
import asyncio
from aiokafka import AIOKafkaConsumer, TopicPartition

async def persist_business_result(msg):
    # 必须由真实数据库事务实现：成功返回意味着事务已提交。
    # 业务幂等键/唯一约束要能处理同一消息的重放。
    await asyncio.sleep(0.01)

async def main():
    consumer = AIOKafkaConsumer(
        "import-tasks",
        bootstrap_servers="localhost:9092",
        group_id="import-worker-v1",
        enable_auto_commit=False,
        auto_offset_reset="earliest",
    )
    await consumer.start()
    try:
        while True:
            msg = await consumer.getone()
            await persist_business_result(msg)
            tp = TopicPartition(msg.topic, msg.partition)
            await consumer.commit({tp: msg.offset + 1})
    finally:
        await consumer.stop()

if __name__ == "__main__":
    asyncio.run(main())
```

**示例边界**：此例没有生产级重试/DLQ、Rebalance 回调、SIGTERM 接管、HTTP 调用取消、数据库真实事务、容器宽限期和日志体系；`persist_business_result` 是占位实现。不能将它直接部署为高可靠服务。

## 18. 多任务并发 Worker 的安全设计

多任务并发时，需要额外的分区与任务注册表：

```text
TopicPartition
  ├── Assignment Generation
  ├── Next Fetched Offset
  ├── 已交付记录集合
  ├── 已持久化完成记录集合
  ├── Safe Commit Frontier
  ├── Kafka Confirmed Commit Offset
  ├── 在途 Task 与 Deadline
  └── ACTIVE / REVOKING / REVOKED / LOST
```

关键循环如下（伪代码，强调控制逻辑而不是具体库的语法）：

```text
while RUNNING:
    检查总在途与每个分区容量
    从允许读取的分区获取消息
    为每条消息登记 (tp, offset, generation)
    执行受限并发的业务处理
    仅在数据库事务成功后标记该记录完成
    每个分区分别计算安全提交水位
    仅在本 Consumer 持有有效分区所有权时提交 Offset

on_revoke(partitions):
    停止这些分区的新工作
    有界等待相关 Task；持久化未完成状态
    仅提交已安全完成的前缀
    标记分区不可再写入和提交
```

若进程崩溃在业务完成与 Offset 提交之间，仍通过业务幂等处理重放；不会因为未提交而直接把消息当成“丢失”。

## 19. 任务进度监控的最小指标体系

| 指标名示例 | 单位 | 解释 |
|---|---|---|
| `worker_process_up` | 0/1 | 进程健康探针 |
| `consumer_heartbeat_age_seconds` | 秒 | 最近有效心跳距今时间 |
| `consumer_group_committed_lag` | Offset 差 | 按已提交位置计算的积压 |
| `consumer_fetch_lag` | Offset 差 | 按当前读取位置计算的积压 |
| `worker_inflight_tasks` | 条 | 已领取且未完成的工作 |
| `worker_oldest_inflight_age_seconds` | 秒 | 最老在途任务执行年龄 |
| `business_completed_total` | 次 | 业务结果成功持久化的累计次数 |
| `business_failed_total` | 次 | 业务失败累计次数 |
| `business_last_success_age_seconds` | 秒 | 上次成功完成到现在的时间 |
| `offset_commit_failure_total` | 次 | Kafka Offset 提交失败次数 |
| `consumer_rebalance_total` | 次 | 本实例经历的重平衡次数 |
| `worker_drain_pending_tasks` | 条 | 停机窗口结束仍未终结的任务 |

应避免只有单一“健康=绿灯”的面板。建议针对进程、分区、业务任务、数据库和外部依赖分别展示指标。

## 20. 故障定位流程：从现象到根因

### 场景 A：Lag 高，但消费很慢

1. 查看生产速率是否大于成功处理速率。
2. 对比 Consumer Position 与 Committed Offset。
3. 看当前 in-flight 数量及最老在途年龄。
4. 如果业务成功率低，检查模型响应、DB 事务与异常。
5. 如果业务成功率高但 Offset 落后，检查安全水位、提交失败、分区乱序处理。
6. 检查是否发生频繁 Rebalance 或分区过少造成并行度瓶颈。

### 场景 B：Lag 几乎为零，但用户看不到结果

1. 检查 Lag 使用的是 Position 还是 Committed Offset。
2. 检查数据库中的最终业务状态与成功记录。
3. 检查 Redis 缓存或前端状态是否没有刷新。
4. 检查是否先提交 Offset 后处理业务，造成消息跳过。
5. 检查任务是否只被标记为 `RUNNING` 而没有成功完成。

### 场景 C：扩容后反而变慢

1. 检查 Topic 分区数与 Consumer 数量；Consumer 数量超过分区数时不会继续提高单组分区并发度。
2. 检查 Rebalance 总量和时长。
3. 检查新 Consumer 是否反复加入/退出、出现 `CommitFailedError`。
4. 检查数据库连接池、第三方 API 限流是否成为新瓶颈。
5. 检查每条分区是否被重复分发、旧 Worker 是否仍可写入。

### 场景 D：滚动更新后少量任务重复

1. 找到业务提交时间和 Kafka Commit 时间。
2. 检查是否在二者之间退出或分区被撤销。
3. 用业务幂等键检查最终记录是否只有一条。
4. 检查 Outbox/Inbox 是否留有可靠处理痕迹。
5. 如果有外部发送，核查第三方结果后再判断是否补发。

## 21. 常见误区与反例

**误区 1：心跳正常就是消费正常。** 心跳维护组成员身份，不证明业务成功。

**误区 2：Lag=0 就是全部任务成功。** Lag 的统计口径、已取未处理、提前提交和数据库结果都可能改变判断。

**误区 3：Worker 关闭时 `await consumer.stop()` 就能保证全部任务完成。** Consumer 管理 Kafka 客户端资源，不自动等待你自行创建的所有业务 Task。

**误区 4：在 Rebalance 回调里无期限等待所有任务最安全。** 长时间等待可能让组协调卡住，还可能超过关闭时限。

**误区 5：提交最大已完成 Offset 就可以。** 若分区中较早 Offset 未完成，就可能漏处理。

**误区 6：只要旧 Worker 不再心跳，它的远端调用就不可能成功。** 第三方 API 不会因为你的 Kafka 分区所有权变化自动撤销业务副作用。

**误区 7：`Task.cancel()` 保证被取消的任务马上终结。** 协程可以在合适检查点响应取消，但也可能吞掉取消，外部操作可能继续。

**误区 8：Kafka 4.x 的所有客户端都采用新 Consumer 协议。** 必须核实客户端与配置，不能因为 Broker 版本高就假定协议行为一致。

## 23. 示例实现的设计边界

下面附录的 Python 标准库教学代码提供：

1. `PartitionTracker`：基于已经交付的消息和已持久化完成的结果，计算安全提交水位。
2. `ProgressSnapshot`：比较按 Committed Offset 与 Position 计算的 Lag，以及在途任务状态。
3. `classify()`：将进程、心跳、可接单状态与业务进度综合成分类，不把未知情况自动判为停滞。
4. `bounded_drain()`：尝试有界等待，随后请求取消，并明确报告仍在运行的任务。
5. `WorkerLifecycle`：在停机期间拒绝新工作，并区分完全停止与仍有未结束任务的危险状态。

**重要限制**：`PartitionTracker` 仅是对 Kafka 按分区、有序交付给该 Worker 的消息进行本地跟踪；它本身并不执行 Kafka 提交，也不能阻止已经失去执行资格的旧进程在数据库中写入，真正的分布式防护仍须依赖事务、租约代际、唯一约束与实际 Consumer 组所有权机制。

## 附录 A：完整 Python 教学模拟器

运行环境：Python 3.11 或更新版本，**不需要安装 Kafka 客户端**。保存以下代码为 `kafka_lifecycle_demo.py`：

```python
"""Kafka lifecycle semantics teaching model; no actual Kafka broker used.

Important: Tests prove this model's state transitions, NOT real broker integration.
"""
from __future__ import annotations

import asyncio
from dataclasses import dataclass, field
from enum import Enum
from typing import Awaitable, Callable


class PartitionPhase(str, Enum):
    ACTIVE = "ACTIVE"
    REVOKING = "REVOKING"
    REVOKED = "REVOKED"
    LOST = "LOST"


@dataclass
class PartitionTracker:
    """Tracks successfully persisted Kafka records, not just fetched records.

    Each instance is tied to a single partition assignment generation.
    Kafka fetches deliver offsets in ascending order but offsets may have holes.
    A caller must pass all delivered records, in their received order, to observe().
    """
    generation: int
    initial_next_offset: int
    phase: PartitionPhase = PartitionPhase.ACTIVE
    seen: list[int] = field(default_factory=list)
    succeeded: set[int] = field(default_factory=set)
    last_commit: int | None = None
    _safe_index: int = 0
    _safe_next_offset: int = field(init=False)

    def __post_init__(self):
        self._safe_next_offset = self.initial_next_offset
        self.last_commit = self.initial_next_offset

    def observe(self, offset: int, generation: int) -> bool:
        if self.phase != PartitionPhase.ACTIVE or generation != self.generation:
            return False
        if offset < self.initial_next_offset:
            raise ValueError("offset lower than assignment start")
        if self.seen and offset <= self.seen[-1]:
            raise ValueError("newly fetched offsets must ascend")
        self.seen.append(offset)
        return True

    def complete(self, offset: int, generation: int) -> bool:
        if generation != self.generation or self.phase not in {PartitionPhase.ACTIVE, PartitionPhase.REVOKING}:
            return False
        if offset not in self.seen:
            raise ValueError("cannot finish an unobserved record")
        self.succeeded.add(offset)
        while self._safe_index < len(self.seen) and self.seen[self._safe_index] in self.succeeded:
            processed = self.seen[self._safe_index]
            self._safe_next_offset = processed + 1
            self._safe_index += 1
        return True

    @property
    def safe_next_offset(self) -> int:
        return self._safe_next_offset

    @property
    def unfinished_count(self) -> int:
        return len(self.seen) - len(self.succeeded)

    def commit_succeeded(self, target: int, generation: int) -> bool:
        if generation != self.generation or self.phase not in {PartitionPhase.ACTIVE, PartitionPhase.REVOKING}:
            return False
        if target > self.safe_next_offset:
            raise ValueError("cannot commit past safe frontier")
        if target < (self.last_commit or 0):
            raise ValueError("commit must not go backwards")
        self.last_commit = target
        return True

    def start_revoke(self):
        if self.phase != PartitionPhase.ACTIVE:
            return False
        self.phase = PartitionPhase.REVOKING
        return True

    def revoke(self):
        self.phase = PartitionPhase.REVOKED

    def lost(self):
        self.phase = PartitionPhase.LOST


@dataclass(frozen=True)
class ProgressSnapshot:
    process_alive: bool
    heartbeat_recent: bool
    latest_end_offset: int
    committed_next_offset: int
    fetched_position: int
    in_flight: int
    last_success_age_s: float | None
    oldest_inflight_age_s: float | None = None
    backlog_wait_age_s: float | None = None
    ready: bool = True

    @property
    def committed_lag(self) -> int:
        """Simple single-partition lag proxy; not exact number of physical messages."""
        return max(0, self.latest_end_offset - self.committed_next_offset)

    @property
    def fetch_lag(self) -> int:
        return max(0, self.latest_end_offset - self.fetched_position)

    @property
    def uncommitted_gap(self) -> int:
        return max(0, self.fetched_position - self.committed_next_offset)


def classify(snapshot: ProgressSnapshot, stale_after_s: float = 30) -> str:
    if not snapshot.process_alive:
        return "DOWN"
    if not snapshot.ready or not snapshot.heartbeat_recent:
        return "UNREADY"
    if snapshot.committed_lag == 0 and snapshot.in_flight == 0:
        return "IDLE_HEALTHY"
    # Missing last-success timestamp alone is NOT proof of stalled work.
    inflight_stale = (snapshot.oldest_inflight_age_s is not None
                      and snapshot.oldest_inflight_age_s > stale_after_s)
    no_progress_stale = (snapshot.last_success_age_s is not None
                         and snapshot.last_success_age_s > stale_after_s)
    backlog_stale = (snapshot.backlog_wait_age_s is not None
                     and snapshot.backlog_wait_age_s > stale_after_s)
    if snapshot.in_flight > 0 and (inflight_stale or no_progress_stale):
        return "STALLED_IN_FLIGHT"
    if snapshot.committed_lag > 0 and (no_progress_stale or backlog_stale):
        return "STALLED_BACKLOG"
    if snapshot.committed_lag > 0 and snapshot.last_success_age_s is None and snapshot.oldest_inflight_age_s is None and snapshot.backlog_wait_age_s is None:
        return "PROGRESS_UNKNOWN"
    if snapshot.committed_lag > 0:
        return "BACKLOG_PROGRESSING"
    return "WORKING"


@dataclass
class DrainReport:
    completed: int
    cancelled: int
    errors: int
    pending: int


async def bounded_drain(
    tasks: list[asyncio.Task], timeout_s: float,
    *, cancel_grace_s: float = 0.05, on_cancel: Callable[[], None] | None = None
) -> DrainReport:
    """Wait a fixed period, request cancellation for remaining tasks, join them.

    External I/O may continue even when local coroutine is cancelled; this
    function cannot guarantee completion before a process force-kill.
    """
    if timeout_s < 0 or cancel_grace_s < 0:
        raise ValueError("timeouts must be nonnegative")
    if not tasks:
        return DrainReport(0, 0, 0, 0)
    done, pending = await asyncio.wait(tasks, timeout=timeout_s)
    if pending:
        if on_cancel:
            on_cancel()
        for task in pending:
            task.cancel()
        stopped, pending = await asyncio.wait(pending, timeout=cancel_grace_s)
        done.update(stopped)
    errors = sum(t.exception() is not None for t in done if not t.cancelled())
    completed = sum(not t.cancelled() and t.exception() is None for t in done)
    cancelled = sum(t.cancelled() for t in done)
    return DrainReport(completed, cancelled, errors, len(pending))


class WorkerLifecycle:
    def __init__(self):
        self.accepting = True
        self.phase = "RUNNING"
        self.tasks: set[asyncio.Task] = set()

    def submit(self, coro: Awaitable):
        if not self.accepting:
            if hasattr(coro, 'close'):
                coro.close()
            raise RuntimeError("worker draining")
        task = asyncio.create_task(coro)
        self.tasks.add(task)
        task.add_done_callback(self.tasks.discard)
        return task

    async def shutdown(self, timeout_s: float) -> DrainReport:
        self.accepting = False
        self.phase = "DRAINING"
        report = await bounded_drain(list(self.tasks), timeout_s)
        self.phase = "STOPPED" if report.pending == 0 else "UNSAFE_TO_CLOSE"
        return report

```
