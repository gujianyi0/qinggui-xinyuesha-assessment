# 消息队列与后台任务可靠性（二）：Kafka 自动提交、手动提交 Offset 与业务处理顺序

> 对应学习目标：**自动提交与手动提交位点的差别；在业务完成之前或之后提交，分别有什么风险。**  
> 主题：Apache Kafka 消费者 Offset、处理确认、崩溃恢复、业务幂等、aiokafka。  
> 适用场景：文档导入、批量模型调用、后台索引、批量反馈整理等异步任务。  
> 范围说明：本文深入讨论传统 Kafka Consumer Group 的 Offset 提交，不把 Kafka 4.x Share Group 的逐消息确认机制混为一谈。文末的离线程序不连接真实 Kafka 集群。

---

## 1. 学习目标对应的本质问题

一个 Kafka Consumer 至少涉及三个不同的“完成”：

1. **读取完成**：Consumer 从 Kafka 获取某条消息。
2. **业务处理完成**：应用解析文档、调用模型或者提交数据库事务，并得到可解释的成功结果。
3. **消费进度已提交**：Consumer Group 向 Kafka 持久化可用于后续恢复的 Offset。

这三个动作之间不是一个原子事务。**从 Kafka 读到消息，不代表业务已经处理；业务处理结束，不代表消费进度已经提交。** 如果在动作之间出现进程退出、网络超时、重新平衡（Rebalance），重新启动时可能重复处理，也可能跳过尚未处理的消息。

### 1.1 最基础的时序

```text
Kafka:       [Offset 40] [Offset 41] [Offset 42]
Consumer:         |            
                  v
           读出 Offset 40
                  |
                  v
           执行业务逻辑
                  |
                  v
           数据库成功提交
                  |
                  v
           Kafka commit(41)
```

最后提交的是 **41，不是 40**，因为 Kafka 提交位置表示“下一个准备开始读取的 Offset”。在正常无重复情况下，40 已处理，所以 41 是可恢复位置。

## 2. 四个容易混淆的 Offset 概念

| 概念 | 说明 | 例子 |
|---|---|---|
| Record Offset | 消息在一个 Topic-Partition 日志中的位置 | 消息位于 Offset 40 |
| Consumer Position | 当前客户端接下来准备向应用交付的消息位置 | 已交付 40，Position 常变为 41 |
| Committed Offset | 消费组已保存的恢复起点 | Commit 还停在 37 |
| Log End / High Watermark | Broker 日志的不同边界概念，影响积压、可读范围 | 不能简单等价为“业务完成位置” |

用符号写成：

- `p = position`：当前 Consumer 的读取位置。
- `c = committed_offset`：该组已确认的恢复位置。
- `b = business_completed`：业务已可靠完成的消息集合。

在普通、按分区顺序处理的工作流中，应确保 **提交位置之前的相关业务消息均已经安全完成**。已经提交到 `c`，但仍存在未完成的、位于 `c` 之前的可读业务消息，就是潜在的跳过风险。

### 2.1 举例：为什么自动提交可能提前

```text
消息                Offset 100   101   102
已交付给应用            ✓       ✓     ✓
实际业务完成            ✓       ×     ×
客户端读取 Position                  103
如果此刻把 103 提交给 Kafka：
重启后从 103 继续，101、102 可能不再由该组重新交付。
```

这里的 `position` 是**读取进度**，不是业务进度。

### 2.2 Offset + 1 的细节

按顺序处理最后一条 Offset 为 `n` 的消息时，常见提交值为 `n + 1`。但 Kafka 日志中的实际可读 Offset **未必连续**，例如压缩日志或事务记录可能让后续可见消息跳号；在某些 SDK 中提供的 `nextOffsets` / position 更能准确表示恢复起点。业务代码不要假设“消息必然逐个连续出现”。

### 2.3 Offset 与业务 ID 完全不同

`topic + partition + offset` 标识 Kafka 中的一条日志记录；`job_id`、`feedback_id`、`document_version_id` 是业务实体标识。相同业务动作可能经重试被发布成不同 Offset，单凭 Kafka Offset 去重不能阻止此类重复业务效果。

## 3. 自动提交（Auto Commit）是什么

消费者配置：

```properties
enable.auto.commit=true
auto.commit.interval.ms=5000
```

含义：在客户端维护消费进度，并按照客户端实现的调度机制定期向 Kafka 提交。`5000` 毫秒为 Kafka 客户端的常见默认自动提交间隔，具体客户端及版本的执行时机要以实际 SDK 为准。**自动提交不会主动等待你的数据库事务完成，也不会理解模型 API 是否调用成功。**

### 3.1 优点

- 接入简单，适合无副作用或允许丢失、重放的轻量消息消费。
- 不必为每一条消息显式执行提交。
- 消费进度持续推进，开发复杂度低。

### 3.2 风险一：先提交后完成业务——可能丢失业务处理

```text
12:00:00  poll() 得到消息 A、B
12:00:01  开始处理 A，B 尚未执行
12:00:05  自动提交已读取 Position（覆盖 B）
12:00:06  Worker 崩溃
12:00:08  Worker 重启并从已提交位置继续
结果：B 可能被跳过，虽然数据库没有 B 的处理结果。
```

请注意：不是说开启 Auto Commit 一定丢消息。危险在于**某次自动提交提前于真正业务完成**，特别是处理很慢、批量消息积压、消息被丢到线程池或后台 Task 的场景。

### 3.3 风险二：业务先完成、自动提交还没发生——可能重复

```text
12:00:00  读取 A
12:00:01  写入业务数据库成功
12:00:02  进程崩溃
12:00:05  计划中的自动提交未发生
12:00:10  重启后 A 再次交付
结果：A 可能再次执行。
```

因此，**Auto Commit 不能简单等同于 At-most-once，也不能简单等同于 At-least-once**；结果与循环处理模式、自动提交时间、是否把工作转移给后台任务等因素有关。Kafka 官方文档明确指出：在保证每次 `poll()` 返回的数据都处理完、再继续拉取或关闭时，自动提交也可以得到至少一次处理语义；否则可能提前提交而跳过未完成记录。

## 4. 手动提交（Manual Commit）是什么

消费者配置：

```python
consumer = AIOKafkaConsumer(
    "document-import-jobs",
    bootstrap_servers="localhost:9092",
    group_id="document-import-workers",
    enable_auto_commit=False,
    auto_offset_reset="earliest",
)
```

此时由应用主动决定何时提交消费进度：

```python
await consumer.commit({tp: last_processed_msg.offset + 1})
```

这里 `tp` 是某个 `TopicPartition`，不是整个 Topic；这使应用可以分别跟踪每个分区的安全进度。

### 4.1 手动提交的真正收益

手动提交不是“强制每条消息只处理一次”，而是让**Kafka 进度推进的时机由业务代码控制**。例如，只有数据库事务成功后才提交 Offset，从而避免因为消费进度提前推进而漏掉业务。

### 4.2 手动提交的代价

- 需要管理失败重试、重复投递和幂等。
- 需要处理 Rebalance（分区收回时停止旧任务并处理剩余进度）。
- 需要处理并发执行的完成顺序。
- 需要在关闭时合理等待并完成必要提交。
- 提交本身可能失败或结果未知。

## 5. 先提交，再处理（Commit Before Processing）

### 5.1 时间线

```text
读取 A (offset=12)
    |
    v
commit(13)   ← Kafka 已认为 A 不再需要重放
    |
    +------ 在这里崩溃 ------> A 没有产生业务结果
    |
    v
处理业务 A
```

这类策略倾向于 **At-most-once（至多一次处理尝试）**：可以降低重试产生的重复效果，但承受丢失业务处理的风险。严格说它的完整保障还取决于生产端、Broker 持久化以及消费者的实现方式。

### 5.2 适用边界

可能接受：临时、不重要、可丢失的遥测事件；即使个别事件处理失败也无业务影响的场景。

通常不应接受：文档导入任务、模型批处理结果、用户反馈写入、订单状态修改、账务记录等必须可恢复的业务。

### 5.3 注意“已提交”含义

提交成功意味着消费组的 Offset 已获确认，而不是该数据从 Kafka 物理删除。Kafka 消息仍受保留期与日志策略控制，其他消费组仍然可以独立读取，管理员也可能重置该组 Offset。这里的“丢失”指**正常消费组恢复路径下未处理消息被跳过**。

---

## 6. 先处理，再提交（Process Before Commit）

### 6.1 时间线

```text
读取 A (offset=12)
    |
    v
处理业务并提交数据库
    |
    +------ 在这里崩溃 ------> 数据库已处理，Kafka 还没确认
    |
    v
commit(13)
```

如果数据库成功而 Kafka Commit 尚未成功，重启后会再次读取 A。这类策略倾向于 **At-least-once（至少一次处理尝试）**：依赖消息仍保留、消费者可恢复并最终继续处理等前提，允许重复投递，但能降低未处理业务被跳过的风险。

### 6.2 为什么不是 Exactly-once

SQL 数据库事务与 Kafka Offset Commit 并不是自动组成一个原子事务。数据库 `COMMIT` 成功、Kafka Commit 失败，是两个独立系统之间的故障窗口。相反顺序也有问题。**仅仅改变先后顺序，无法消除跨系统的原子性缺口。**

### 6.3 幂等应在哪里实现

最重要的是在**目标业务系统**中实现：

- 创建反馈：`UNIQUE(user_id, confirmation_id)`。
- 导入资料：`UNIQUE(tenant_id, document_id, document_version)`。
- 消费事件审计：`UNIQUE(consumer_group, topic, partition, offset)`。
- 修改状态：条件更新 `WHERE state = 'PENDING'` 或乐观锁版本号。
- 对外发送：使用业务幂等键、Outbox 和受支持的下游幂等能力。

一个消息重复到达，处理程序仍可能执行两次，但通过数据库约束与事务，使其产生**一次有效业务效果**。

## 7. 故障窗口总表

| 故障发生位置 | 当前业务结果 | Kafka 已提交位置 | 重启后风险 | 防护 |
|---|---|---|---|---|
| 消息尚未读取 | 未处理 | 旧值 | 正常恢复 | 保证保留期与正常消费 |
| 读取后，业务前，提前提交成功 | 未处理 | 已越过该消息 | 跳过业务 | 不提前提交 |
| 业务执行期间、提交前 | 不确定或部分完成 | 旧值 | 重复或残留中间状态 | 事务、幂等、状态机 |
| 数据库提交后，Kafka Commit 前 | 已成功 | 旧值 | 重复消费 | 幂等与唯一约束 |
| Kafka Commit 请求发出，但响应丢失 | 不确定 | 可能新值也可能旧值 | 重复或不必要重试 | 查询/复用业务状态，不盲目重复副作用 |
| Kafka Commit 成功之后 | 已成功 | 新值 | 常规恢复不重放 | 审计与终态记录 |
| Rebalance 正在发生 | 取决于在途任务 | 可能提交失败 | 新旧 Consumer 重叠 | 停止旧任务、分区授权与幂等 |

**特别注意：一次网络超时不证明 Kafka Commit 失败，也不证明外部 API 处理失败。** 请求可能已经在远端成功，只是客户端没收到结果。

## 8. 三种交付语义：定义与局限

| 语义 | 业务效果 | 优点 | 代价 / 风险 |
|---|---|---|---|
| At-most-once | 处理可能被跳过，尽量避免重复 | 简单 | 可能丢失业务 |
| At-least-once | 出错重试后仍可能被重复处理 | 适合可靠后台任务 | 需要幂等 |
| Exactly-once effect | 对特定目标系统呈现一次有效业务效果 | 避免重复副作用 | 需要跨系统配合或目标系统的去重事务 |

Kafka 在 Kafka-to-Kafka 数据链路中提供事务性生产、原子写入输出 Topic 和提交消费 Offset 等机制；这并不能直接扩展成“任意外部 PostgreSQL、邮件、支付接口都恰好执行一次”。与外部存储协作时，通常仍需要数据库事务、幂等键、业务状态机或协调机制。

## 9. aiokafka：自动提交示例

以下示例只是理解机制，**不推荐直接用于不能丢失业务结果的耗时导入任务**。

```python
import asyncio
from aiokafka import AIOKafkaConsumer

async def main():
    consumer = AIOKafkaConsumer(
        "document-import-jobs",
        bootstrap_servers="localhost:9092",
        group_id="document-import-workers",
        enable_auto_commit=True,
        auto_commit_interval_ms=5000,
        auto_offset_reset="earliest",
    )
    await consumer.start()
    try:
        async for msg in consumer:
            await handle_document_import(msg.value)
    finally:
        await consumer.stop()

# handle_document_import 必须由实际业务代码实现
```

当每次循环都完整等待处理、不会将消息处理扔到未被管理的后台 Task 时，风险与“先拿一批消息、然后异步排队处理”不同。但为了显式界定完成边界，后台任务系统一般优先考虑手动提交。

## 10. aiokafka：逐条手动提交示例

```python
from aiokafka import AIOKafkaConsumer, TopicPartition

async def run_worker():
    consumer = AIOKafkaConsumer(
        "document-import-jobs",
        bootstrap_servers="localhost:9092",
        group_id="document-import-workers",
        enable_auto_commit=False,
        auto_offset_reset="earliest",
    )
    await consumer.start()
    try:
        async for msg in consumer:
            # process_document 必须返回“业务已可靠持久化”的结果。
            # 失败时抛出异常；不要吞掉异常后仍然提交。
            await process_document(msg.value)
            tp = TopicPartition(msg.topic, msg.partition)
            await consumer.commit({tp: msg.offset + 1})
    finally:
        await consumer.stop()
```

核心不在 `commit` 语法，而在 `process_document` 的含义。它必须保证可定义的“已完成”——通常是数据库中的业务事务真正提交，而不只是模型请求已发起或把工作提交给内存中的 Task。

### 10.1 为什么必须 `await`

`await consumer.commit(...)` 让代码等待提交操作完成或明确报错。没有 `await`，可能创建了未执行的协程对象；提交结果和异常都无法被正确处理。

### 10.2 为什么不能把异常吞掉

```python
try:
    await process_document(msg.value)
except Exception:
    logger.exception("业务处理失败")

await consumer.commit({tp: msg.offset + 1})  # 错误：失败仍推进 Offset
```

除非已经用可靠的失败处理逻辑将消息转成业务允许的终态（例如记录不可恢复错误并成功入库，且设计上明确允许跳过），否则不能推进消费进度。

## 11. aiokafka：批量手动提交与分区边界

```python
from aiokafka import AIOKafkaConsumer

async def run_batches():
    consumer = AIOKafkaConsumer(
        "document-import-jobs",
        bootstrap_servers="localhost:9092",
        group_id="document-import-workers",
        enable_auto_commit=False,
        auto_offset_reset="earliest",
    )
    await consumer.start()
    try:
        while True:
            batches = await consumer.getmany(timeout_ms=1000, max_records=100)
            for tp, messages in batches.items():
                if not messages:
                    continue
                # 串行、完整处理该分区当前批次的所有消息。
                # 中途失败直接抛出，不向前提交。
                for msg in messages:
                    await process_document(msg.value)
                await consumer.commit({tp: messages[-1].offset + 1})
    finally:
        await consumer.stop()
```

此例假设 `process_document` 可靠且幂等；若处理第 1～5 条成功、第 6 条失败，整个批次对应的 Offset 都不向前提交。这意味着 1～5 条下次可能重复，仍需要数据库幂等。

更完善的实现还要具备分区撤销回调、在途任务跟踪、失败消息记录、退避重试、超时与优雅停机。不能直接将这个最小示例当作完整生产 Worker。

## 12. 最容易遗漏的问题：同一分区异步并发与完成乱序

假设 Offset 依次为 `20、21、22`，三个任务并发：

```text
投递顺序：      20      21      22
完成时间：      慢      快      快
已完成状态：    ×       ✓       ✓
```

**不能因为 22 已完成就提交 23。** 如果 20 尚未完成，这样提交后进程崩溃，恢复会跳过 20。

正确策略是维护每个分区的 **连续完成水位（Contiguous Completion Frontier）**，只提交所有更早消息已可靠完成的安全位置。

### 12.1 水位算法示意

```python
class Frontier:
    def __init__(self, next_offset=20):
        self.next_offset = next_offset
        self.finished = set()

    def mark_finished(self, offset):
        self.finished.add(offset)
        while self.next_offset in self.finished:
            self.finished.remove(self.next_offset)
            self.next_offset += 1
        return self.next_offset

f = Frontier()
assert f.mark_finished(22) == 20
assert f.mark_finished(21) == 20
assert f.mark_finished(20) == 23
```

这是**Offset 连续且从当前安全边界开始**的概念模型。真实 Kafka 日志可以存在 Offset 跳号，生产系统更适合依据从 Consumer 实际交付的消息顺序、下一可读位置与已完成集合来追踪，不应仅靠对整数依次 `+1` 假定所有 Offset 都存在。

另外，并行任务不能在分区所有权已转移后仍不受控地提交旧分区 Offset。需要与 Rebalance 和在途任务取消配合。

## 13. Rebalance：分区所有权变化后的提交风险

Consumer Group 重新平衡通常发生在 Consumer 加入、退出、故障或分区分配变化时。分区可能从 Worker A 转移到 Worker B。

```text
Worker A:  获取分区 0 的消息，正在导入资料
             |
             |  Rebalance
             v
Worker B:  获得分区 0，开始重读尚未提交部分
             |
             v
Worker A:  旧任务随后完成，试图提交原分区 Offset
```

此时可能产生重复业务执行、提交失败或者旧 Worker 与新 Worker 共同写业务的竞态。

### 13.1 ConsumerRebalanceListener 的作用

aiokafka 提供分区撤销/重新分配回调，以便：

1. 暂停或限制旧分区的新工作。
2. 等待/取消受影响的在途任务。
3. 对已可靠完成的消息推进安全 Offset（前提是仍能合法提交）。
4. 将剩余未完成工作交由新持有者恢复。

aiokafka 官方明确警告：某些手动提交在重新平衡后可能抛出 `CommitFailedError`。回调里的锁与 `getmany()` 如果使用不当，还可能造成死锁。

### 13.2 旧 Worker 的完成不一定还能提交

一旦分区控制权发生变化，旧任务可能已经失去合法提交机会。**业务幂等与版本/租约检查才是避免旧 Worker 造成重复副作用的最后一道防线。**

## 14. 数据库事务和 Kafka Commit 为什么不能互相替代

```text
PostgreSQL 事务：
BEGIN
  INSERT ...
  UPDATE ...
COMMIT

Kafka Consumer：
commit(offset=next_position)
```

它们是两个系统中的两个提交动作。假设数据库成功后 Kafka 失败：

- 业务记录存在。
- 消费进度仍旧。
- 消息重复交付。

**这是符合“至少一次”设计预期的故障，而不是 Kafka 自己弄错了数据。** 应用应实现业务去重与结果重用。

### 14.1 数据库幂等示例

```sql
CREATE TABLE processed_messages (
    consumer_group TEXT NOT NULL,
    topic TEXT NOT NULL,
    partition_id INTEGER NOT NULL,
    offset_id BIGINT NOT NULL,
    PRIMARY KEY (consumer_group, topic, partition_id, offset_id)
);

CREATE TABLE document_import_results (
    tenant_id UUID NOT NULL,
    document_id UUID NOT NULL,
    version TEXT NOT NULL,
    result JSONB NOT NULL,
    PRIMARY KEY (tenant_id, document_id, version)
);
```

一项业务处理需要多张表共同改变时，应把“处理标记”和“实际业务输出”放入同一个事务。在处理标记已经存在时，可以跳过重复业务写入，前提是前一次结果可核实。

### 14.2 关于 Exactly-once 的更精确说法

- Kafka 内部 Topic→Topic：可以使用事务性 Producer 与 Offset 的原子提交。
- Kafka→PostgreSQL：可以通过业务唯一约束、事务性处理标记等实现“每个业务记录只产生一次有效结果”，但 Kafka 仍可能重新交付消息。
- Kafka→外部邮件/API：还要考虑请求已经发送但响应丢失、第三方是否支持幂等键、是否有可查询的发送状态。

“恰好一次业务效果”应明确**目标系统和受保护的副作用范围**，不能泛称所有操作绝对只执行一次。

## 15. auto_offset_reset 不负责已提交进度的正常恢复

`auto_offset_reset="earliest"` 不等于“每次重启从头开始”。它主要在消费组没有有效已提交 Offset，或原位置因日志保留等原因不可用时决定位置选择。

| 场景 | 恢复行为 |
|---|---|
| 组已有有效 Committed Offset | 优先从该组的提交位置恢复 |
| 没有有效 Offset，设置 earliest | 从可用最早位置开始 |
| 没有有效 Offset，设置 latest | 从当前可用最新位置开始，可能跳过旧记录 |
| 配置 none 并且没有位置 | 抛出错误，由程序处理 |

因此，想修复错误提交，不能只修改 `auto_offset_reset`。可能需要人工核对业务记录、重置特定消费组的 Offset 或用补偿任务修复，但任何重放都应先确保业务处理幂等。

## 16. 后台导入任务的推荐消费方案

针对资料导入、批量模型调用等时间很长的工作：

```text
HTTP 创建任务
   ↓
PostgreSQL 保存 task_id、状态、业务幂等键
   ↓
可靠发布 Kafka 任务消息（必要时 Outbox）
   ↓
Consumer 手动拉取消息
   ↓
校验任务状态 / 权限 / 是否已成功
   ↓
执行解析、模型调用或索引
   ↓
数据库事务写入最终业务记录及状态
   ↓
手动提交 Kafka Offset
```

这里的“先处理、后提交”不表示**一个耗时数小时的任务必须独占单个 Consumer 的拉取循环**。实际系统可采用有限的在途任务数、分区暂停、独立处理协程、持久化检查点、续租/锁状态等方式来提高吞吐，但必须严格维护每个分区的安全提交位置。

### 16.1 模型 API 调用失败后的状态

- 还未开始：保留 `PENDING` 或可恢复的排队状态。
- 正在执行：可标记 `RUNNING` 并带心跳与租约信息。
- 暂时失败：有限重试、退避后进入 `RETRYING`。
- 永久失败：事务性保存 `FAILED` 与错误原因后，才可以按既定策略认定消息完成并推进 Offset。
- 进程崩溃：不能永久停留在 `RUNNING`，应由租约过期、恢复扫描等机制重新接管。

重点是：**一次消息可以结束为成功，也可以结束为已持久化的可解释失败；但不应该“丢掉错误然后继续提交”。**

## 17. 操作观测：哪些指标可以揭示提交问题

| 指标/日志 | 含义 | 故障信号 |
|---|---|---|
| `consumer_position` | 当前交付进度 | 比已完成业务大很多 |
| `committed_offset` | 消费组恢复起点 | 长时间不动或超前 |
| `processed_offset` / 安全水位 | 已可靠完成进度 | 与 Commit 不匹配 |
| `records_lag` | 消费积压 | 持续增长 |
| `commit_latency` | 提交耗时 | 急剧升高 |
| `commit_failed_total` | 提交失败次数 | Rebalance/网络异常 |
| `duplicate_detected_total` | 幂等去重次数 | 重试和重复消费升高 |
| `task_inflight` | 当前处理中的任务 | 长期过大或一直不降 |
| `task_state_duration` | 状态停留时间 | RUNNING 永远不结束 |

日志建议记录：`group_id`、`topic`、`partition`、`offset`、`task_id`、业务事务 ID、尝试次数、完成状态、Commit 尝试结果。不要记录模型密钥、身份令牌和未经脱敏的用户敏感数据。

## 18. 常见误区与澄清

**误区一：拿到消息就可以提交。** 不行；读取进度不等于业务成功。

**误区二：用手动提交就绝不会丢数据。** 不行；提交时机错误、外部系统失败、保留期过短和错误恢复策略仍可能造成数据问题。

**误区三：处理后提交一定恰好一次。** 不行；数据库成功之后、Kafka 提交之前仍可能崩溃，导致重放。

**误区四：幂等只要用 Kafka Offset 当 Key 即可。** 不行；同一业务意图可能被重新发布到不同 Offset，需要业务层唯一约束。

**误区五：一次批量消息处理了 9 条，就可以把最后的 Offset 提交。** 不行；如果第 4 条失败，即使第 9 条完成，也不能越过未完成的第 4 条。

**误区六：Kafka Commit 成功就能证明数据库事务成功。** 不行；这是不同系统的确认。

**误区七：关闭 Consumer 会自动修复所有尚未完成任务。** 不行；需要停止接单、处理在途任务、提交安全进度并保证持久化恢复。

**误区八：换成 `auto_offset_reset="earliest"` 就能修复提交错位。** 不行；已有的有效 Committed Offset 通常优先生效。

**误区九：`await consumer.commit()` 之后所有外部副作用都被原子确认。** 不行；Kafka 不会把数据库或第三方 API 自动纳入 Consumer 的提交事务。

---

## 19. 本节应建立的因果关系

```text
业务进度 > Kafka 已提交进度
     ↓
重启会重新读取已处理消息
     ↓
重复处理风险
     ↓
靠幂等、唯一约束与结果复用保护

Kafka 已提交进度 > 安全完成进度
     ↓
重启跳过尚未完成的消息
     ↓
业务结果缺失风险
     ↓
靠正确提交时机与连续完成水位预防
```

**归纳：Offset Commit 是“恢复到哪里”的声明，不是“已经创造了正确业务结果”的证明。**

## 20. 离线验证示例与测试结果

下面的程序使用纯 Python 模拟 Kafka 交付进度、手动提交与崩溃恢复；同时使用 SQLite 模拟一个事务性业务去重表。它不启动 Kafka Broker，也不声称模拟所有消费组协调、日志保留、Kafka Broker 故障行为。

测试涵盖：

- 读取位置推进，但 Kafka Committed Offset 不变。
- 自动提交提前 → 未完成业务被跳过。
- 自动提交延后 → 业务可能重复执行。
- 手动提交过早 → 业务被跳过。
- 业务处理后尚未提交 → 重启重复。
- 完整处理再提交 → 从下一位置恢复。
- 数据库事务失败 → 处理标记与业务结果一起回滚。
- 相同业务 ID 在不同 Offset 出现 → 仍只有一条业务记录。
- 并发任务完成乱序 → 安全水位不能越过缺口。
- 不同 Partition 的进度独立。

**本次运行结果：20 项离线单元测试通过。** 实际 Kafka Broker 连接、Rebalance、Broker 故障注入和 PostgreSQL 并发事务未执行。

### 20.1 完整 Python 离线示例

```python
"""离线教学模拟：仅模拟 Offset/业务提交，不是实际 Kafka Broker。"""
from __future__ import annotations
from dataclasses import dataclass, field
from typing import Callable
import sqlite3
import unittest

@dataclass(frozen=True)
class Message:
    topic: str
    partition: int
    offset: int
    business_id: str
    value: str

@dataclass
class ConsumerSimulation:
    messages: list[Message]
    position: int = 0
    committed: int = 0
    outputs: list[str] = field(default_factory=list)
    completed_offsets: set[int] = field(default_factory=set)

    def poll(self) -> Message | None:
        for m in self.messages:
            if m.offset >= self.position:
                self.position = m.offset + 1
                return m
        return None

    def process(self, msg: Message) -> None:
        self.outputs.append(msg.value)
        self.completed_offsets.add(msg.offset)

    def commit_position(self) -> None:
        self.committed = self.position

    def commit_processed(self, msg: Message) -> None:
        assert msg.offset in self.completed_offsets
        assert msg.offset + 1 <= self.position
        self.committed = msg.offset + 1

    def crash_restart(self) -> None:
        self.position = self.committed
        self.completed_offsets.clear()

class DurableLedger:
    def __init__(self):
        self.db = sqlite3.connect(':memory:')
        self.db.execute('CREATE TABLE effects (business_id TEXT PRIMARY KEY, payload TEXT NOT NULL)')
        self.db.execute('CREATE TABLE consumed (topic TEXT, partition_id INTEGER, offset_id INTEGER, business_id TEXT, PRIMARY KEY(topic, partition_id, offset_id))')

    def apply(self, msg: Message, *, fail_before_commit=False) -> bool:
        try:
            with self.db:
                cur = self.db.execute('INSERT OR IGNORE INTO consumed VALUES (?, ?, ?, ?)', (msg.topic, msg.partition, msg.offset, msg.business_id))
                if cur.rowcount == 0:
                    return False
                self.db.execute('INSERT OR IGNORE INTO effects VALUES (?, ?)', (msg.business_id, msg.value))
                if fail_before_commit:
                    raise RuntimeError('simulated DB fault')
            return True
        except RuntimeError:
            raise

    def count(self):
        return self.db.execute('SELECT count(*) FROM effects').fetchone()[0]

class PartitionFrontier:
    def __init__(self, next_offset: int = 0):
        self.next_offset = next_offset
        self.done = set()

    def mark_finished(self, offset: int):
        if offset < self.next_offset:
            return self.next_offset
        self.done.add(offset)
        while self.next_offset in self.done:
            self.done.remove(self.next_offset)
            self.next_offset += 1
        return self.next_offset

MSG = [Message('jobs',0,0,'A','effect-A'), Message('jobs',0,1,'B','effect-B')]

class OffsetTests(unittest.TestCase):
    def test_poll_advances_position(self):
        s=ConsumerSimulation(MSG); self.assertEqual(s.poll().offset, 0); self.assertEqual(s.position,1); self.assertEqual(s.committed,0)
    def test_commit_next_position(self):
        s=ConsumerSimulation(MSG); s.poll(); s.commit_position(); self.assertEqual(s.committed,1)
    def test_auto_early_commit_data_loss(self):
        s=ConsumerSimulation(MSG); s.poll(); s.commit_position(); s.crash_restart(); self.assertEqual(s.poll().offset,1); self.assertEqual(s.outputs,[])
    def test_auto_delayed_commit_duplicates(self):
        s=ConsumerSimulation(MSG); m=s.poll(); s.process(m); s.crash_restart(); s.process(s.poll()); self.assertEqual(s.outputs,['effect-A','effect-A'])
    def test_manual_before_processing_loss(self):
        s=ConsumerSimulation(MSG); s.poll(); s.commit_position(); s.crash_restart(); self.assertEqual(s.poll().offset,1)
    def test_manual_after_processing_duplicate(self):
        s=ConsumerSimulation(MSG); s.process(s.poll()); s.crash_restart(); s.process(s.poll()); self.assertEqual(s.outputs,['effect-A','effect-A'])
    def test_manual_success(self):
        s=ConsumerSimulation(MSG); m=s.poll(); s.process(m); s.commit_processed(m); s.crash_restart(); self.assertEqual(s.poll().offset,1)
    def test_unprocessed_forbidden(self):
        s=ConsumerSimulation(MSG); m=s.poll()
        with self.assertRaises(AssertionError): s.commit_processed(m)
    def test_lagging_commit(self):
        s=ConsumerSimulation(MSG); s.poll(); s.poll(); s.committed=1; s.crash_restart(); self.assertEqual(s.poll().offset,1)
    def test_no_data(self):
        self.assertIsNone(ConsumerSimulation([]).poll())
    def test_durable_once_business_effect(self):
        ledger=DurableLedger(); self.assertTrue(ledger.apply(MSG[0])); self.assertFalse(ledger.apply(MSG[0])); self.assertEqual(ledger.count(),1)
    def test_db_fault_rollback(self):
        ledger=DurableLedger()
        with self.assertRaises(RuntimeError): ledger.apply(MSG[0], fail_before_commit=True)
        self.assertEqual(ledger.count(),0)
        self.assertTrue(ledger.apply(MSG[0]))
    def test_different_offsets_dedup_business(self):
        ledger=DurableLedger(); ledger.apply(MSG[0]); ledger.apply(Message('jobs',0,7,'A','effect-A')); self.assertEqual(ledger.count(),1)
    def test_next_frontier_on_order(self):
        f=PartitionFrontier(); self.assertEqual(f.mark_finished(0),1); self.assertEqual(f.mark_finished(1),2)
    def test_next_frontier_out_of_order(self):
        f=PartitionFrontier(); self.assertEqual(f.mark_finished(1),0); self.assertEqual(f.mark_finished(0),2)
    def test_next_frontier_gaps(self):
        f=PartitionFrontier(); self.assertEqual(f.mark_finished(3),0); self.assertEqual(f.mark_finished(1),0); self.assertEqual(f.mark_finished(0),2); self.assertEqual(f.mark_finished(2),4)
    def test_next_frontier_duplicate(self):
        f=PartitionFrontier(); f.mark_finished(0); self.assertEqual(f.mark_finished(0),1)
    def test_biz_vs_offset_identifiers(self):
        ledger=DurableLedger(); ledger.apply(MSG[0]); ledger.apply(Message('jobs',1,0,'B','effect-B')); self.assertEqual(ledger.count(),2)
    def test_partition_independent(self):
        a,b=PartitionFrontier(),PartitionFrontier(); a.mark_finished(0); self.assertEqual(b.next_offset,0)
    def test_db_transaction_atomic(self):
        ledger=DurableLedger(); ledger.apply(MSG[0]); ledger.apply(MSG[1],fail_before_commit=False); self.assertEqual(ledger.count(),2)

if __name__ == '__main__':
    unittest.main(verbosity=2)
```

## 21. 真正集成 Kafka 时需要再验证什么

要把离线示例升级成实际 Kafka + PostgreSQL 测试，应完成如下可观察操作：

1. 启动一个真实 Kafka Broker、一个 PostgreSQL 实例及独立 Worker。
2. 用固定 Producer 发布具有唯一 `task_id` 的消息，保留 Topic/Partition/Offset 记录。
3. 关闭自动提交，只在事务成功后提交每个分区的安全进度。
4. 故意在数据库 Commit 成功后、Kafka Offset Commit 前强制停止 Worker。
5. 重启后观察同一消息被再次读取，而业务结果未重复创建。
6. 制造 Consumer Group Rebalance，验证旧 Worker 不会无控制地提交旧分区。
7. 制造单分区多任务乱序完成，验证不会越过未完成消息提交。
8. 记录 Kafka Commit、业务记录、幂等冲突、最终任务状态，检查一致性。

上述是**需额外执行的真实集成验证要求**，不能和本节的 20 项离线单元测试混为一谈。

**本节结论：** 当业务要求“请求断开或 Worker 重启后还能可靠恢复”，通常应将 Kafka 消费进度的提交放在可验证的业务持久化完成之后；同时必须接受可能重复投递，并依靠幂等和事务来防止重复业务效果。自动提交与手动提交的根本差异，是**谁来决定消费进度的安全边界**，而不是哪个配置开关天然保证绝不丢失或绝不重复。
