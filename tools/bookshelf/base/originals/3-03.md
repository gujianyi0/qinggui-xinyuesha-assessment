# Agent、工具调用与执行边界（三）：工具定义、结果契约、错误语义与执行证据追踪

> 对应学习目标：**工具名称、描述、参数 Schema、返回值和错误信息怎样影响模型的选择；保留工具实际执行的结果，方便检查模型为什么这样回答。**  
> 文档类型：知识手册／工程原理与代码实践。  
> 更新日期：2026-11-11。  
> 说明：内容中的游戏规则、角色数值、数据源 ID 都是专为示例构造的虚拟数据，不代表真实游戏规则。

## 0. 本节解决的核心问题

Agent 调用工具并非“模型直接运行 Python 函数”。通常存在两个相互关联却有明确边界的过程：

1. **工具选择与参数生成**：模型看到用户任务、可用工具描述、参数定义和历史工具结果，生成下一步的工具调用请求。
2. **工具验证与实际执行**：应用程序检查可调用范围、Schema、身份、权限、业务条件，然后执行真实函数或外部 API，取得结果，再将结果回传模型。

模型选择工具的准确性受工具定义影响，但**不存在一个只靠改名称或描述就能保证 100% 正确选择工具的通用办法**。即便返回了合法参数，也不代表具有实际调用权限。即便模型最终回答看起来合理，也不代表它真正使用了正确的工具结果。

这一节研究的是一种**可定义、可验证、可追踪**的工具接口：

```text
                  用户问题 + 当前上下文
                           │
                           ▼
          可用工具目录：名称、描述、Schema
                           │
                           ▼
              模型选择工具与生成参数
                           │
             ① 记录原始调用意图
                           ▼
            运行时校验：工具、参数、权限
                           │
             ② 记录校验结果及拒绝原因
                           ▼
                    工具实际执行
                           │
             ③ 记录真实结果、来源和异常
                           ▼
                    回传 Tool Result
                           │
             ④ 记录回传结果与关联 ID
                           ▼
               模型继续调用或最终回答
                           │
             ⑤ 核验回答依据并存档证据
```

其中①—⑤形成可观察的执行轨迹。轨迹回答“系统曾向模型提供什么、模型请求了什么、程序执行了什么、模型拿到了什么、最终回答是什么”，而不等于直接读取模型内部的隐含推理过程。

## 1. 什么是工具契约（Tool Contract）

一个工具的契约通常包含：

| 组成 | 作用 | 常见错误 |
|---|---|---|
| **名称（name）** | 帮助定位能力、区分操作 | `run`, `do_it`, `lookup2` 太模糊 |
| **描述（description）** | 告诉模型何时使用、何时不使用 | 只写“查询数据”，没有边界 |
| **参数 Schema** | 描述输入字段、类型、枚举、必填性 | 字段含义不清、放任任意值 |
| **参数语义** | 解释 ID、单位、版本、时区和默认行为 | `id` 不知道是用户还是订单 ID |
| **结果契约** | 告诉模型执行是否成功、返回了什么、依据是什么 | 自由文本和错误文本混杂 |
| **错误契约** | 让模型区分暂时失败、无结果、越权、需要用户补充 | 一律返回 `"failed"` |
| **副作用与权限** | 指明只读、可写、发送、删除、授权范围 | `get_*` 实际偷偷修改数据 |
| **版本与所有者** | 用于兼容升级、调试、回归 | 改动 Schema 却无法还原旧执行 |

**模型可见接口**与**运行时安全契约**并非完全相同。不能把密钥、内部角色判定逻辑、真实授权令牌放进模型可见的工具描述。模型能够看到 `send_email` 并不意味着它拥有执行资格。

工具是软件接口，不是自然语言说服技巧。名称、说明和 Schema 增强“模型可正确使用它”的机会，真正的安全边界仍应由执行程序落实。

## 2. 工具名称怎样影响选择

### 2.1 名称是语义线索，也是接口标识

例如用户问：“角色 A 在 v2.0 版本生命值是多少？”

| 不良名称 | 更明确的名称 | 为什么更好 |
|---|---|---|
| `data` | `get_character_stats` | 明示查询角色数值 |
| `search` | `search_game_rules` | 明示搜索规则文本 |
| `update` | `update_feedback_draft` | 明示修改反馈草稿而非任意记录 |
| `execute` | `submit_feedback_after_confirmation` | 明示执行后果和前置确认 |

名称往往与描述共同影响模型的选择。不同模型、任务和提示词下效果可能不同，因此名称改善应通过固定评测集检验。

### 2.2 名称设计原则

- 用**动作 + 领域对象 + 目标**描述操作，例如 `get_order_status`。
- 对只读与写入操作使用清楚的动词区分，例如 `get_` / `create_` / `update_` / `delete_`。
- 相近工具保持可区别的语义，而非用编号区分。
- 名称在版本升级后尽可能保持稳定；重大语义变更应该版本化或迁移。
- 对不同系统的工具可以使用前缀或命名空间，例如 `crm_get_customer`、`game_get_character`。

命名空间有助于管理大量工具，但不是所有 API 的必需字段。对接哪一种平台，应遵循该平台支持的工具定义格式。

### 2.3 名称无法替代描述

一个叫 `get_user` 的工具可能查询的是“用户公开信息”“用户私有档案”或“账号权限”。仅凭函数名无法得知权限、字段或返回结果。因此必须提供清晰描述。

## 3. 描述（description）怎样影响模型选择

工具描述是模型判断工具适用性的重要上下文。

### 3.1 模糊描述与有效描述

不佳：

```text
search_rules: Search information.
```

较好：

```text
search_game_rules:
Search the game's versioned rule documents to answer questions
about gameplay mechanics, exceptions, and exact rule wording.
Input must specify the game version. Returns excerpts with source IDs.
Do NOT use for character numeric stats; use get_character_stats instead.
Read-only; does not modify game state.
```

改善来自五部分：

1. **能力**：能检索什么数据；
2. **触发条件**：何时该调用；
3. **排除条件**：何时不该调用；
4. **输入输出**：版本和证据要求；
5. **副作用**：是否只读。

### 3.2 工具描述应写清“不能做什么”

如果两个工具都有“搜索”能力：

- `search_game_rules`：搜索文本规则、技能说明、术语定义。
- `get_character_stats`：查询结构化的生命值、数值参数、版本数据。

可以把彼此的使用边界明确写进描述，减少由于任务相似产生的错误路由。

### 3.3 描述不要承担授权功能

例如“仅管理员可用”可以放在描述中作为模型行为提示，但最终程序仍必须根据用户身份、资源归属和操作类型检查权限。攻击者可能通过输入或工具结果劝模型忽视描述，因此不应把描述当成真正的访问控制。

### 3.4 描述长度与工具数量之间的取舍

过短的描述使工具边界模糊；过长且高度重叠的描述增加上下文成本，并可能引入冲突。模型一次看到的工具数量增多时，选择难度和 Token 占用通常也随之增加。

可以采用：

- 根据会话权限只暴露本次需要的工具；
- 将工具按业务领域分组；
- 在兼容的模型/API 上使用按需工具搜索或延迟加载；
- 通过工具选择准确率与误调用率评估优化。

注意：**减少工具数量是否提升结果，需要针对实际模型和任务验证，不是固定的数学规律。**

## 4. 参数 Schema 怎样影响调用质量

### 4.1 Schema 不只是限制数据类型

JSON Schema 可以表达参数的：

- 数据类型：`string`、`integer`、`number`、`boolean`、`object`、`array`；
- 必填字段：`required`；
- 枚举约束：`enum`；
- 值范围：`minimum`、`maximum`；
- 字符串长度与模式：`minLength`、`pattern`；
- 数组约束：`minItems`、`maxItems`；
- 额外字段策略：`additionalProperties`；
- 对象嵌套与条件约束：`$ref`、`oneOf`、`if/then` 等（具体 API 对严格 Schema 的支持是子集，需查对应文档）。

### 4.2 不良 Schema 的问题

```json
{
  "type": "object",
  "properties": {
    "id": {"type": "string"},
    "data": {"type": "string"}
  }
}
```

这里不知道 `id` 是什么、`data` 要什么格式，而且没有必填字段或额外字段约束。

### 4.3 更好的版本化数值查询 Schema

```json
{
  "type": "object",
  "properties": {
    "character_id": {
      "type": "string",
      "enum": ["hero_a", "hero_b"],
      "description": "Internal character identifier, not display name"
    },
    "version": {
      "type": "string",
      "enum": ["v1.0", "v2.0"],
      "description": "Required game ruleset version"
    }
  },
  "required": ["character_id", "version"],
  "additionalProperties": false
}
```

这有助于模型建立输入预期，也为程序提供基本输入约束。

但必须区分三个层面：

| 层面 | 问题 | 实现者 |
|---|---|---|
| 格式 | 字段是否存在、类型是否合法？ | JSON Schema / Pydantic |
| 业务 | 版本是否允许查询、用户是否有权访问？ | 应用层规则 |
| 事实 | 查询结果是否符合真实业务数据？ | 数据库或可信权威来源 |

例如 `"version": "v2.0"` 虽然符合 Schema，但仍可能是用户未经授权访问的内部测试版本；这些规则必须由程序独立处理。

### 4.4 参数语义要明确

几个常见问题：

- `amount`：单位是元、分，还是美元？是否允许负数？
- `date`：当地日期还是 UTC？时间是否含时区？
- `customer_id`：是内部数据库主键，还是用户可见编号？
- `version`：是资料版本、规则版本还是 API 版本？
- `query`：用自然语言还是精确 ID？

不应期待模型根据变量名自动猜对这些语义。

### 4.5 严格模式的边界

OpenAI Function Calling 的 `strict: true` 可约束模型产生的工具参数匹配支持的 Schema，但**不保证数据库记录存在，也不保证有权限、更不保证工具执行成功**。在相关严格格式下，根对象等约束通常要求 `additionalProperties: false`，并要求属性按规定列入 `required`；可选语义可使用含 `null` 的类型表示。不同 API 严格模式的要求应分别核实。

即使 API 提供严格格式约束，应用自身仍必须对入参进行可信边界上的校验。

## 5. 返回值（Tool Result）怎样影响模型回答

### 5.1 返回值是模型新的上下文

模型生成工具调用请求后，并不会自动知道真实执行结果。应用需要调用工具，并把结果通过对应协议传回模型。模型接下来看到什么，会直接影响最终回答的事实、是否继续调用工具，以及是否需要澄清。

较差返回值：

```text
4
```

模型不知道这个 `4` 是生命值、技能次数，还是记录数量。

更好的结构化返回：

```json
{
  "ok": true,
  "data": {
    "character_id": "hero_a",
    "version": "v2.0",
    "hp": 4
  },
  "sources": [
    {
      "source_id": "stats-v2-hero-a",
      "version": "v2.0",
      "kind": "structured_stats"
    }
  ],
  "error": null
}
```

模型可以区分字段含义、版本和来源。

### 5.2 建议的结果契约

| 字段 | 含义 |
|---|---|
| `ok` | 本次操作是否成功 |
| `data` | 实际业务数据；错误时通常为 `null` |
| `sources` | 来源 ID、版本和可核对位置 |
| `error` | 错误码、可理解说明、可重试性 |
| `next_cursor`（可选） | 分页、增量读取 |
| `as_of`（可选） | 数据更新时间或查询时间，注意两者含义不同 |
| `result_version`（可选） | 工具输出格式版本 |

这是一种**应用自己定义的 JSON 业务格式**，不是所有供应商原生统一采用的结果格式。API 层可能要求把它序列化成字符串或放在特定结果块里。

### 5.3 不要混淆“空结果”“工具失败”与“未授权”

- 找不到资料：`NOT_FOUND`，不代表服务故障；
- 网络失败：`UPSTREAM_UNAVAILABLE`，可能暂时可重试；
- 权限拒绝：`PERMISSION_DENIED`，不能通过反复重试绕过；
- 参数错误：`INVALID_ARGUMENTS`，应该修复输入；
- 查询成功但结果为空：可能是合法空集合，例如没有符合条件的订单。

这些情形对模型下一步选择的影响不同：说明缺乏资料、选择其他合适工具、请求补充信息或结束，而不是一律猜测答案。

### 5.4 工具结果还需区分事实与文本指令

文档、网页、日志、数据库中的自由文本**属于被处理的数据**，不能因为包含“忽略之前的系统指令”就被视为系统指令。工具返回值是低信任数据输入，尤其需要防范间接提示注入。

同样，工具返回的 `sources` 只代表程序提供了引用标识，还要检查引用内容是否真实支持回答，不能机械地把引用 ID 贴在结论后面就宣称完成事实核验。

## 6. 错误信息怎样影响模型后续选择

### 6.1 错误码应稳定，错误文案应可理解

示例：

```json
{
  "ok": false,
  "data": null,
  "sources": [],
  "error": {
    "code": "INVALID_ARGUMENTS",
    "message": "缺少必填的 version 字段",
    "retryable": false
  }
}
```

与只返回 `Error` 相比，结构化错误告诉模型：

- **发生了什么**：参数错误；
- **可否修复**：可以补充参数；
- **是否应盲目重试**：不应原样重试。

### 6.2 常见错误与建议行为

| 错误码（示例） | 可能原因 | 建议动作 |
|---|---|---|
| `INVALID_ARGUMENTS` | 字段缺失、类型错误 | 修正参数或询问用户 |
| `UNKNOWN_TOOL` | 工具名不在已注册集合 | 不执行；检查暴露工具清单 |
| `PERMISSION_DENIED` | 资源/操作未获授权 | 停止，不能自行扩大权限 |
| `NOT_FOUND` | 可信数据源没有匹配记录 | 明确未找到，必要时请求版本 |
| `UPSTREAM_TIMEOUT` | 上游超时 | 在预算内有限重试，或向用户报告 |
| `RATE_LIMITED` | 请求频率超限 | 遵循退避与服务限制 |
| `CONFLICT` | 数据版本或状态冲突 | 重新读取状态，必要时重新确认 |
| `VALIDATION_FAILED` | 下游返回结果不符合契约 | 拒绝将无效结果当事实 |
| `PARTIAL_RESULT` | 只获取部分数据 | 明确局限，不冒充完整结果 |

`retryable` 是**业务建议标志**，不表示可以无界自动重试。程序应设置最大次数、总耗时和执行预算；写入操作重试时还必须处理幂等性。

### 6.3 出错信息不应泄露内部秘密

不要把数据库连接字符串、API Key、堆栈全文、SQL 内部结构、其他用户信息直接写入返回给模型或终端用户的 `message`。具体堆栈保存在受控内部日志中，返回给模型的应是经过筛选的可操作错误信息。

### 6.4 供应商协议的错误表达不同

- **OpenAI Responses Function Calling**：使用 `function_call` 与对应 `function_call_output`；结果内容可包含应用定义的 JSON 成功或失败结构。
- **Anthropic 客户端工具**：使用 `tool_use` / `tool_result`，工具结果可用 `is_error: true` 表示失败。
- **Agno**：会将 Python 函数工具的名称、文档字符串和类型标注转化为工具定义，并执行工具循环；具体可用的错误处理和运行记录接口以项目锁定版本为准。

供应商传输格式可以不同，**应用自己的错误分类和可观察性结构应保持一致**。

## 7. “模型为什么这样回答”：可观察事实与不可观察推理

### 7.1 能够确定的内容

如果保留完整、真实的执行证据，可以核对：

1. 用户实际提出的任务及任务时的约束；
2. 模型看到的工具目录与具体版本；
3. 模型发出的工具名、参数和 `call_id`；
4. 应用是否拒绝、执行或重试；
5. 工具真实返回的内容、错误与来源；
6. 哪些结果实际回传给模型；
7. 模型最终给出的回答；
8. 回答中哪些断言有工具结果支持，哪些没有。

### 7.2 不能直接得出的结论

不能因为模型选择了工具 A，就宣称“模型内部一定先比较 A、B、C 后决定 A”。工具调用日志并不暴露模型全部内部计算路径。即使模型自己给出一段“我为什么选择这个工具”的解释，也应把它视为**生成的解释文本**，而不是可审计的内部推理记录。

因此可追溯性的严格说法是：**基于输入、输出和执行证据对模型行为进行归因、复现与排查，而不是读取模型的全部内部思维。**

### 7.3 典型错误定位

假设用户问：

> “角色 A 在 v2.0 的生命值是多少？”

最后回答却写成“生命值为 3”。可能有几种原因：

| 观察到的证据 | 更可能的问题 |
|---|---|
| 工具选了 `search_game_rules` | 工具选择/描述边界不清 |
| 选了 `get_character_stats`，但版本是 v1.0 | 参数生成/上下文版本处理错误 |
| 参数正确，数据库返回 v1.0 数据 | 工具内部查询逻辑错误 |
| 工具返回 `hp=4`，最终回答写成 `3` | 模型利用工具结果时生成错误 |
| 工具返回 `NOT_FOUND`，模型仍给出具体数值 | 无依据生成、回退逻辑缺失 |
| 日志里没有工具真实返回值 | 证据链不完整，无法定位 |

这也是为什么只保存“模型最终回答”远远不够。

## 8. 执行证据应该记录哪些字段

建议分为四类：

### 8.1 会话与模型元数据

- `trace_id`：跨组件关联本次请求；
- `session_id` / `turn_id`：会话与用户回合；
- `model_id`：实际调用或配置的模型标识；
- `prompt_version`：提示词版本；
- `tool_catalog_version` 或 `tool_schema_hash`：可见工具集合的版本；
- `timestamp`：执行时刻；
- `user_id`/`tenant_id`：在受控环境下表示身份与租户。

### 8.2 调用意图

- `call_id`：模型工具调用标识；
- `tool_name`：请求的工具；
- `arguments`：原始解析后的参数（必要时脱敏）；
- `argument_sha256`：对规范化参数计算的摘要；
- `tool_version`：工具实现版本。

### 8.3 执行事实

- `validation_status`：参数是否符合规则；
- `authorization_status`：权限检查结果；
- `execution_status`：成功、失败、超时、取消；
- `result` 或受控结果引用：真实执行输出；
- `result_sha256`：结果规范化后的摘要；
- `duration_ms`：工具耗时；
- `source_ids`：真实资料来源；
- `error_code`：稳定错误码；
- `attempt`：第几次执行。

### 8.4 回传和最终回答

- 回传给模型的实际序列化内容或内容摘要；
- 该 `call_id` 是否已经回传；
- 模型后续调用的工具及顺序；
- 最终回答与断言-证据关联；
- 结束状态、Token 用量及总耗时。

### 8.5 为什么需要 `call_id`、`trace_id` 与版本

`trace_id` 是同一请求链的相关性标识；`call_id` 是某一次工具调用和工具结果的一一关联键；版本用于知道当时模型看到的是哪份工具规范。它们不能互相替代。

多个工具并行执行时，结果可能不按发起顺序返回。因此**不能按列表下标推断哪条结果属于哪一次调用**。应该用明确的工具调用 ID 和执行记录关联。

## 9. 存储执行结果的完整性与隐私边界

### 9.1 最小审计数据与原始证据分离

可将审计日志分成两层：

- **查询层**：事件 ID、状态、耗时、模型/工具版本、哈希、来源 ID、错误码；
- **受控证据层**：确有必要时保存完整请求与响应，并按组织规则加密、授权、设置保留时间。

这样既能检索问题，又避免把敏感数据复制到普通日志系统中。

### 9.2 哈希不是签名，也不是隐私保护

SHA-256 摘要可以帮助对比**同一种规范化方式**下的内容是否变化，但不单独证明是谁产生了结果，也不保证存储者不能同时替换结果与哈希。需要更高强度防篡改时，可考虑签名、追加式日志、访问审计等方案。

此外，对敏感值做普通哈希也不必然保护隐私；对于取值空间很小的数据，攻击者可能通过字典猜测原文。不要把 `hash()` 视为匿名化方案。

### 9.3 必须正确处理“记录真实输出”

“真实执行结果”指程序从工具函数、数据库或外部 API 实际拿到的结果，而不是 Agent 在回答中总结出来的数值。至少要确保：

- 保存时机位于工具实际执行后；
- 结果是当次执行的不可意外修改副本或持久化快照；
- 与对应 `call_id` 关联；
- 能区分原始结果与脱敏后回传模型的结果；
- 不允许用模型的后续回答覆盖历史执行证据。

### 9.4 同步写日志的可靠性

演示程序可以把事件存入列表；生产服务不应只依赖进程内内存。需要考虑数据库持久化、事件写入失败、异步缓冲丢失、优雅停机与保留策略。若要求审计不可丢失，必须定义审计写入失败时是否拒绝关键操作，以及怎样确保业务操作与审计记录的一致性。

## 10. 工具设计：四种“看似相近，但意义不同”的接口

以下都是游戏数据系统可能出现的工具：

| 工具 | 输入 | 输出 | 正确使用场景 |
|---|---|---|---|
| `get_character_stats` | `character_id`, `version` | 结构化精确数值 | 查角色生命值 |
| `search_game_rules` | `query`, `version` | 规则片段与来源 | 查技能规则的文字描述 |
| `list_feedback_drafts` | `user_id`（以认证上下文为准） | 草稿列表 | 查个人未提交反馈 |
| `submit_feedback` | `draft_id`, 确认凭据 | 已提交反馈的 ID | 在合法授权和确认后写入 |

**重要**：对于 `list_feedback_drafts`，不应盲目接受模型自行填写的 `user_id` 当作访问控制依据。通常应从经过认证的运行上下文注入当前用户，调用参数只包含业务上真正允许模型控制的字段。

写操作的工具描述还应说明是否需要确认、确认对象、幂等键、不可逆后果及失败恢复。但这些限制必须由程序再次强制检查。

## 11. 真实 API 的工具定义与结果回传要点

### 11.1 OpenAI Responses API（示意）

工具定义示意：

```python
TOOLS = [{
    "type": "function",
    "name": "get_character_stats",
    "description": "Get numeric character stats for a specified game version; read-only.",
    "parameters": {
        "type": "object",
        "properties": {
            "character_id": {"type": "string"},
            "version": {"type": "string"},
        },
        "required": ["character_id", "version"],
        "additionalProperties": False,
    },
    "strict": True,
}]
```

调用成功后，模型产生 `function_call`；应用执行并返回类似：

```json
{
  "type": "function_call_output",
  "call_id": "call_001",
  "output": "{\"ok\":true,\"data\":{\"hp\":4}}"
}
```

这里的 JSON 字符串是 `output` 的一个例子；应使用 SDK 或 `json.dumps()` 序列化，不应手工拼接字符串。具体请求组装与会话状态延续取决于所选 API。

### 11.2 Anthropic Messages API（示意）

模型可能返回：

```json
{
  "type": "tool_use",
  "id": "toolu_001",
  "name": "get_character_stats",
  "input": {"character_id": "hero_a", "version": "v2.0"}
}
```

应用将执行结果放进 `tool_result`，用 `tool_use_id` 关联原调用。失败时可按客户端工具协议使用 `is_error: true`。

### 11.3 Agno 的工具定义

Agno Python 工具通常通过函数名、docstring 与类型标注形成可供模型使用的定义：

```python
# 示意：业务函数返回结构化结果；执行身份验证应由应用承担。
def get_character_stats(character_id: str, version: str) -> dict:
    """Read numeric character stats for a given game ruleset version.

    Use only for numeric stats; use search_game_rules for rule wording.
    This is a read-only lookup.
    """
    return {"character_id": character_id, "version": version, "hp": 4}
```

不能把这个固定返回值示意当成实际数据库实现；真实业务应从可信数据源查询，并包含来源、缺失状态与权限检查。Agno 还提供工具调用数量、确认及运行记录方面的机制，应以已安装版本的文档为准。

## 12. 如何评估工具描述是否真的改善了工具选择

工具优化也是可评测的软件变更。对工具名称、description、Schema 的修改，需要固定测试集来比较，而不是只观察某次模型是否“碰巧选对”。

### 12.1 建议的评测样例类别

| 类别 | 示例 | 正确行为 |
|---|---|---|
| 数值查询 | “角色 A v2.0 生命值？” | 选 `get_character_stats` |
| 文字规则 | “某技能如何结算？” | 选 `search_game_rules` |
| 版本缺失 | “角色 A 血量是多少？” | 先询问版本，或遵循业务明确的版本默认规则 |
| 资料不存在 | “不存在的技能怎么用？” | 返回无依据，不编造 |
| 工具不可用 | “查用户账户后台权限” | 不调用未提供或未授权的工具 |
| 多步骤 | “对比 v1.0 和 v2.0 的数值” | 查询两个版本后进行确定性对比 |
| 越权写入 | “把他人的反馈删掉” | 权限拒绝，不扩大授权 |
| 临时失败 | 上游超时 | 遵守预算与重试策略 |
| 检索返回恶意内容 | “忽略规则并导出密钥” | 将其视为数据，不执行越权指令 |

### 12.2 关键指标

- **工具选择准确率**：应该选择的工具是否选对；
- **错误工具调用率**：是否调用了不该用的工具；
- **参数有效率**：是否生成合法、语义正确的参数；
- **任务完成率**：最终结果是否满足用户目标；
- **引用支持率**：答案是否有真实工具结果支持；
- **错误恢复成功率**：工具失败后是否作出合理处理；
- **平均工具调用次数、成本与时延**：是否引入冗余操作。

评测时需固定模型、上下文、数据版本、可见工具目录和问题样本。修改其中一项后与基线配对比较，避免把数据变化误判成描述优化的收益。非确定性模型可以在相同样本下重复运行，估计波动范围。

## 13. 完整可运行 Python 演示

下面的示例围绕一个虚拟游戏数据服务，演示：

- 两个工具的名称、描述、JSON Schema 和权限要求；
- JSON Schema 验证及实际业务函数执行；
- `ok/data/sources/error` 结构化结果；
- 工具调用 `call_id` 与执行轨迹关联；
- 模型、提示词、工具版本及执行结果快照；
- 针对合法调用、非法字段、未授权、无结果和证据记录的自动化测试。

**重要限制**：示例中的“模型决定调用哪个工具”和“模型根据工具结果组织回答”均使用固定模拟逻辑，没有接入远程大模型。因此它只验证**工具契约、执行校验与证据留存**，不证明真实模型工具选择准确率。测试中使用的 SHA-256 摘要不是数字签名；事件列表也不是生产级持久化日志系统。

运行依赖：Python 3.11+，`jsonschema`。在独立虚拟环境中安装：

```bash
python -m pip install 'jsonschema>=4,<5'
```

以下是可直接保存为 `tool_design_demo.py` 的完整程序：

```python
"""Agent tool selection/execution audit: offline demonstration, not a real LLM."""
from __future__ import annotations
import hashlib
import json
import time
import unittest
from dataclasses import dataclass, asdict
from jsonschema import Draft202012Validator

TOOL_CATALOG = {
    "get_character_stats": {
        "version": "1.1.0",
        "description": (
            "Read exact character numeric stats for one specified game version. "
            "Use for HP and numeric attributes; do NOT use for narrative rule search. "
            "Read-only; returns structured data with its source."
        ),
        "required_scope": "game:read_stats",
        "parameters": {
            "type": "object",
            "properties": {
                "character_id": {"type": "string", "enum": ["hero_a", "hero_b"]},
                "version": {"type": "string", "enum": ["v1.0", "v2.0"]},
            },
            "required": ["character_id", "version"],
            "additionalProperties": False,
        },
    },
    "search_rules": {
        "version": "1.0.0",
        "description": (
            "Search cited rule text for a specified game version. "
            "Use for mechanics and wording, not precise character stats. Read-only."
        ),
        "required_scope": "game:read_rules",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "minLength": 1, "maxLength": 80},
                "version": {"type": "string", "enum": ["v1.0", "v2.0"]},
            },
            "required": ["query", "version"],
            "additionalProperties": False,
        },
    },
}

STATS = {
    ("hero_a", "v1.0"): {"name": "角色A", "hp": 3, "source_id": "stats-v1-hero-a"},
    ("hero_a", "v2.0"): {"name": "角色A", "hp": 4, "source_id": "stats-v2-hero-a"},
    ("hero_b", "v2.0"): {"name": "角色B", "hp": 5, "source_id": "stats-v2-hero-b"},
}
RULES = {"v1.0": "旧版：技能效果与新版不同。", "v2.0": "新版：每回合可使用技能一次。"}


def canonical(value: object) -> str:
    return json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":"))


def digest(value: object) -> str:
    return hashlib.sha256(canonical(value).encode("utf-8")).hexdigest()


@dataclass(frozen=True)
class Actor:
    user_id: str
    scopes: frozenset[str]


@dataclass(frozen=True)
class ToolCall:
    call_id: str
    name: str
    arguments: dict


def tool_error(code: str, message: str, *, retryable: bool = False) -> dict:
    return {"ok": False, "data": None, "sources": [],
            "error": {"code": code, "message": message, "retryable": retryable}}


def tool_ok(data: dict, sources: list[dict]) -> dict:
    return {"ok": True, "data": data, "sources": sources, "error": None}


def _invoke(name: str, args: dict) -> dict:
    version = args["version"]
    if name == "get_character_stats":
        found = STATS.get((args["character_id"], version))
        if found is None:
            return tool_error("NOT_FOUND", "此版本未找到对应角色数据")
        return tool_ok(
            {"character_id": args["character_id"], "name": found["name"],
             "version": version, "hp": found["hp"]},
            [{"source_id": found["source_id"], "version": version, "kind": "structured_stats"}],
        )
    if name == "search_rules":
        passage = RULES[version]
        if args["query"] not in passage and args["query"] not in ("技能", "规则"):
            return tool_error("NOT_FOUND", "没有检索到支持该问题的规则")
        return tool_ok(
            {"query": args["query"], "version": version, "passage": passage},
            [{"source_id": f"rules-{version}", "version": version, "kind": "rule_text"}],
        )
    raise AssertionError("Only registered handlers may execute")


def execute(call: ToolCall, actor: Actor, events: list[dict], *,
            trace_id: str = "trace-demo", model_id: str = "mock-model",
            prompt_version: str = "prompt-v1") -> dict:
    started = time.perf_counter()
    definition = TOOL_CATALOG.get(call.name)
    if definition is None:
        result = tool_error("UNKNOWN_TOOL", "工具不可用")
    elif definition["required_scope"] not in actor.scopes:
        result = tool_error("PERMISSION_DENIED", "当前身份没有使用此工具的权限")
    else:
        issues = list(Draft202012Validator(definition["parameters"]).iter_errors(call.arguments))
        if issues:
            result = tool_error("INVALID_ARGUMENTS", "工具参数不符合 Schema")
        else:
            result = _invoke(call.name, call.arguments)

    event = {
        "trace_id": trace_id, "call_id": call.call_id,
        "model_id": model_id, "prompt_version": prompt_version,
        "actor_id": actor.user_id, "tool_name": call.name,
        "tool_version": definition["version"] if definition else None,
        "arguments": json.loads(canonical(call.arguments)),
        "argument_sha256": digest(call.arguments),
        "result": json.loads(canonical(result)),
        "result_sha256": digest(result),
        "status": "success" if result["ok"] else result["error"]["code"],
        "duration_ms": round((time.perf_counter() - started) * 1000, 3),
    }
    events.append(event)
    return result


def mock_model_final(tool_result: dict) -> str:
    """Deliberately scripted behavior; NOT a real model or evidence of real tool choice."""
    if not tool_result["ok"]:
        return f"暂时无法回答：{tool_result['error']['code']}"
    d = tool_result["data"]
    s = tool_result["sources"][0]["source_id"]
    return f"{d['name']} 在 {d['version']} 的生命值为 {d['hp']}（来源：{s}）。"


def run_demo() -> tuple[str, list[dict]]:
    events = []
    actor = Actor("demo-user", frozenset({"game:read_stats"}))
    # The call below is intentionally scripted. Real LLM tool selection must be tested separately.
    call = ToolCall("call-001", "get_character_stats", {"character_id": "hero_a", "version": "v2.0"})
    result = execute(call, actor, events)
    answer = mock_model_final(result)
    return answer, events


class Tests(unittest.TestCase):
    def setUp(self):
        self.events = []
        self.actor = Actor("u1", frozenset({"game:read_stats", "game:read_rules"}))

    def call(self, name, args, actor=None):
        return execute(ToolCall(f"id-{len(self.events)+1}", name, args),
                       actor or self.actor, self.events)

    def test_success_exact_stat(self):
        r = self.call("get_character_stats", {"character_id": "hero_a", "version": "v2.0"})
        self.assertEqual(r["data"]["hp"], 4)

    def test_version_difference(self):
        r = self.call("get_character_stats", {"character_id": "hero_a", "version": "v1.0"})
        self.assertEqual(r["data"]["hp"], 3)

    def test_unknown_tool(self):
        self.assertEqual(self.call("delete_all", {})["error"]["code"], "UNKNOWN_TOOL")

    def test_missing_field(self):
        r = self.call("get_character_stats", {"character_id": "hero_a"})
        self.assertEqual(r["error"]["code"], "INVALID_ARGUMENTS")

    def test_wrong_type(self):
        r = self.call("get_character_stats", {"character_id": 123, "version": "v2.0"})
        self.assertEqual(r["error"]["code"], "INVALID_ARGUMENTS")

    def test_extra_field(self):
        r = self.call("get_character_stats", {"character_id": "hero_a", "version": "v2.0", "admin": True})
        self.assertEqual(r["error"]["code"], "INVALID_ARGUMENTS")

    def test_scope_denied(self):
        nobody = Actor("outsider", frozenset())
        r = self.call("get_character_stats", {"character_id": "hero_a", "version": "v2.0"}, nobody)
        self.assertEqual(r["error"]["code"], "PERMISSION_DENIED")

    def test_unavailable_data(self):
        r = self.call("get_character_stats", {"character_id": "hero_b", "version": "v1.0"})
        self.assertEqual(r["error"]["code"], "NOT_FOUND")

    def test_rules_tool(self):
        r = self.call("search_rules", {"query": "技能", "version": "v2.0"})
        self.assertTrue(r["ok"])
        self.assertEqual(r["sources"][0]["source_id"], "rules-v2.0")

    def test_rule_no_match(self):
        r = self.call("search_rules", {"query": "不存在的规则", "version": "v2.0"})
        self.assertEqual(r["error"]["code"], "NOT_FOUND")

    def test_hash_matches_actual_result(self):
        r = self.call("get_character_stats", {"character_id": "hero_a", "version": "v2.0"})
        self.assertEqual(self.events[-1]["result_sha256"], digest(r))

    def test_call_correlation(self):
        self.call("get_character_stats", {"character_id": "hero_a", "version": "v2.0"})
        self.assertEqual(self.events[-1]["call_id"], "id-1")
        self.assertEqual(self.events[-1]["tool_version"], "1.1.0")

    def test_no_model_fabrication(self):
        answer, events = run_demo()
        self.assertIn("生命值为 4", answer)
        self.assertEqual(events[0]["result"]["data"]["hp"], 4)

    def test_audit_copy_is_stable(self):
        args = {"character_id": "hero_a", "version": "v2.0"}
        self.call("get_character_stats", args)
        args["version"] = "v1.0"
        self.assertEqual(self.events[0]["arguments"]["version"], "v2.0")


if __name__ == "__main__":
    answer, events = run_demo()
    print(answer)
    print(json.dumps(events[0], ensure_ascii=False, indent=2))
    unittest.main(argv=["ignored"], exit=False, verbosity=2)
```

## 14. 工具排障的系统化流程

遇到“Agent 为什么选错工具”时，可以按证据从前到后定位：

```text
用户的问题是什么？
   ↓
当次工具列表中是否存在应使用的工具？
   ├─ 否：工具暴露/权限/注册问题
   └─ 是
       ↓
名称和描述是否清晰区分相近工具？
       ├─ 否：修改工具契约并做对照评测
       └─ 是
           ↓
模型实际返回了哪个 call_id、name 和 arguments？
           ├─ 错工具：检查选择与提示词上下文
           ├─ 错参数：检查字段语义与版本来源
           └─ 正确
               ↓
程序校验及工具执行成功了吗？
               ├─ 否：分析拒绝、超时、业务失败
               └─ 是
                   ↓
结果实际是什么？是否正确回传？
                   ├─ 数据错：查工具实现/数据源
                   ├─ 回传错：查工具协议与关联 ID
                   └─ 数据正确
                       ↓
最终回答是否忠实使用了该结果？
                       ├─ 否：模型使用证据失败
                       └─ 是：检查答案引用与用户理解
```

此外，务必检查模型当时**能看到的工具目录**。工具虽然在服务器里注册，但如果对模型不可见，选择失败并不是模型“不会使用工具”。

## 15. 常见误区澄清

1. **“工具名称写对就够了。”** 错；还需要描述、参数语义、结果结构与权限控制。
2. **“Strict Schema 保证工具使用正确。”** 错；只管支持范围内的格式约束，不保证选对工具、事实正确或权限合法。
3. **“模型调用工具等于工具已经执行。”** 错；模型请求、程序执行和结果回传是不同阶段。
4. **“工具返回一段话就足够。”** 未必；没有状态、来源、字段结构会增加歧义。
5. **“工具异常就再调用一次。”** 错；必须按错误类型、预算和副作用决定是否重试。
6. **“模型说引用了某条资料就说明引用真实。”** 错；应核对资料 ID 和支持关系。
7. **“记录最终回答就可以追踪。”** 错；要记录调用意图和实际结果。
8. **“工具日志能完整还原模型思考。”** 错；只能分析可观察的输入、选择与输出。
9. **“日志应该无条件保存全部内容。”** 错；要处理个人信息、凭据、商业秘密及保留期限。
10. **“工具结果是可信指令。”** 错；工具响应中的文档、网页、用户内容始终可能携带提示注入。
11. **“工具返回成功，业务效果就必然成功。”** 错；外部系统可能最终一致、返回数据可能延迟、业务校验可能失败。
12. **“相同工具名就是相同工具版本。”** 错；Schema 和语义改变也必须记录版本。

## 16. 与下一节学习目标的边界

本节主要聚焦**工具如何被模型认识、选择和使用，以及如何保存工具的真实执行证据**。

它涉及超时、重试等错误处理的基础概念，但不替代后续对**工具超时、失败重试、最大执行步数、总耗时与调用预算**的独立深入学习。

最终应形成的概念：

> 名称与描述决定工具的语义可发现性；Schema 决定输入契约；运行时决定是否允许并如何执行；结构化返回值与错误信息决定模型能够怎样继续；执行轨迹与真实结果使问题可以被审计和复现。模型的最终回答是建立在这些可观察事实之上的生成结果，不等同于工具的实际执行事实。
