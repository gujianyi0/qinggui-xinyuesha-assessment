HTTP 服务、SQL、数据库与缓存（四）

业务唯一性、并发修改、重复请求：数据库约束、事务和幂等机制

对应学习目标：业务唯一性、并发修改和重复请求；数据库约束与事务如何防止重复记录和不完整结果。

知识范围：关系数据库与 PostgreSQL 的并发一致性，SQLAlchemy 2.x 的事务/版本管理，HTTP API 幂等设计，以及数据库和外部消息系统之间的边界。

示例环境：Python 3.11+、SQLAlchemy 2.x、pytest、SQLite 文件数据库用于离线实验。PostgreSQL 的专属 SQL 与并发规则按官方文档说明；本文未声称运行了真实 PostgreSQL 集成测试。

1. 四个看起来相似、实际不同的问题

假设一个游戏反馈服务支持 POST /feedback/confirm。用户点击“确认”后，应把反馈保存到数据库，并生成后续通知事件。

  • 业务唯一性（Business Uniqueness）：同一个用户、同一份草稿只能生成一条最终反馈。数据库中不能出现两个逻辑上相同的业务对象。
  • 重复请求（Duplicate Request）：用户重复点击、浏览器重发或代理超时重试时，同一个请求可以到达多次；系统应按预定义语义返回相同的业务结果，而不是重复执行。
  • 并发修改（Concurrent Modification）：两个工作人员同时编辑同一条反馈，不能让后提交的修改在毫无提示的情况下覆盖前一次修改。
  • 部分提交（Partial Commit）：反馈创建成功，但关联的任务或 Outbox 记录失败，数据库不能保留“半完成”的业务事务。

这四个问题需要不同且互相配合的机制：

问题 典型机制 单独使用的局限
同一业务对象被创建多次 UNIQUE、唯一索引、业务键 不能证明相同 HTTP 请求应返回什么，也不防止其他副作用重复
相同请求重放 幂等键、请求指纹、已提交响应记录 不能代替业务层独立唯一性，换一个幂等键仍可能重复创建
并发覆盖旧数据 version 乐观锁、条件更新、行锁 不能阻止在不同事务中重复创建业务对象
多张表只写入一半 同一数据库事务的原子提交 不会自动回滚邮件、Kafka、支付等外部系统

核心公式不是“加一个锁就解决全部问题”，而是：数据库约束维护不变量，事务维护原子性，并发控制维护状态一致性，幂等协议维护请求重复执行的语义。

2. 从数据库角度定义“同一条业务记录”

2.1 物理标识与业务标识

feedback.id = 1024 是数据库主键，能够唯一标识一行，但它不等于“同一业务”的规则。

假设业务规则是“同一租户内，同一个用户的一份草稿只能确认一次”，则可把唯一性写成：

text
business_key = (tenant_id, user_id, draft_id)

两次提交即使生成不同 UUID、不同创建时间，也不能因为数据库主键不同而绕过业务规则。

2.2 唯一性范围与规范化

业务唯一性必须回答：

  1. 约束覆盖整个系统、一个租户、一个用户，还是特定时间窗口？
  2. 逻辑上相同的键值是否存在大小写、前后空格、Unicode 标准化等差异？
  3. 草稿删除后重新提交，算新业务还是原业务？
  4. 历史版本是否保留多条记录？
  5. 状态为 CANCELLED 的对象是否继续占用唯一键？

例如电子邮件地址是否需要大小写不敏感，取决于具体业务契约；不能盲目把所有字符串统一 lower()。唯一键的规范化必须与业务规则一致，并在所有写入入口保持一致。

3. 数据库约束：最后一道并发防线

3.1 PRIMARY KEY、UNIQUE、NOT NULL、FOREIGN KEY、CHECK

sql
CREATE TABLE feedbacks (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    user_id TEXT NOT NULL,
    draft_id TEXT NOT NULL,
    content TEXT NOT NULL,
    version_id BIGINT NOT NULL DEFAULT 1,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_feedback_business UNIQUE (tenant_id, user_id, draft_id),
    CONSTRAINT ck_feedback_not_blank CHECK (length(trim(content)) > 0),
    CONSTRAINT ck_feedback_version CHECK (version_id >= 1)
);
  • PRIMARY KEY 防止表中的物理行标识重复。
  • UNIQUE 把业务唯一性落实为数据库级约束。
  • NOT NULL 确保重要字段必须有值。
  • FOREIGN KEY 保证关联的数据库对象存在（但不自动实现租户权限检查）。
  • CHECK 保证单行数据满足可用 SQL 表达的局部约束。

PostgreSQL 为普通 UNIQUE 约束自动创建相应的唯一 B-tree 索引。唯一性不仅是在 Python 中做“事前判断”，而是在并发写入时由数据库本身仲裁。

3.2 NULL 对唯一约束的影响

PostgreSQL 中，普通 UNIQUE 默认把 NULL 值视为互不相同，因此包含可空字段的复合唯一约束可能允许多条看似重复的数据。

sql
-- PostgreSQL 15+ 可用：需要把 NULL 当作相同值时
UNIQUE NULLS NOT DISTINCT (tenant_id, user_id, external_id)

与之相比，直接将必须参与业务唯一性的字段定义为 NOT NULL 通常更清晰。

3.3 软删除与部分唯一索引

如果系统允许删除后再次创建同一业务对象，但历史记录仍留在表中，可以考虑：

sql
CREATE UNIQUE INDEX uq_active_feedback
ON feedbacks (tenant_id, user_id, draft_id)
WHERE deleted_at IS NULL;

这要求表中存在 deleted_at 字段，并且业务规则明确规定“只有未删除记录必须唯一”。部分唯一索引与普通唯一约束并不完全等价；尤其要检查外键引用、索引谓词和 ON CONFLICT 的匹配方式。

3.4 为什么不能只靠 SELECT 检查

错误模式：

text
请求 A: SELECT ... WHERE draft_id='D'  →  未找到
请求 B: SELECT ... WHERE draft_id='D'  →  未找到
请求 A: INSERT ...                     →  成功
请求 B: INSERT ...                     →  如果没有 UNIQUE，也成功

即便两个请求都严格遵守“先查询后插入”，并发时仍会在检查与写入之间发生竞争，即 TOCTOU（检查与使用之间的时间差）。因此：

先查询可以改善错误提示，但不能替代数据库唯一约束。

4. PostgreSQL 的 ON CONFLICT 与 UPSERT

4.1 遇到冲突时不插入

sql
INSERT INTO feedbacks (tenant_id, user_id, draft_id, content)
VALUES ('t1', 'u1', 'draft-7', '游戏在特定步骤崩溃')
ON CONFLICT (tenant_id, user_id, draft_id)
DO NOTHING
RETURNING id;

未发生冲突时，返回新记录 ID；冲突而执行 DO NOTHING 时，通常不会返回新插入记录。

不能因此认定冲突方“必定是当前请求原先创建的记录”。应结合请求身份、业务键和输入指纹查询并核对已有记录。

4.2 冲突时更新

sql
INSERT INTO player_settings (tenant_id, user_id, theme)
VALUES ('t1', 'u1', 'dark')
ON CONFLICT (tenant_id, user_id)
DO UPDATE SET theme = EXCLUDED.theme
RETURNING user_id, theme;

DO UPDATE 适合“业务语义就是创建或覆盖”的场景，例如某些用户设置；不适合默认用来实现不可重复的付款、发送、反馈确认。否则重复请求反而会改动原先结果。

4.3 原子性与返回结果

PostgreSQL 的 ON CONFLICT DO UPDATE 能在唯一键冲突时提供原子插入/更新行为，但原子 UPSERT 并不自动解决幂等键内容不一致、外部 API 副作用或跨表事务问题。

SQLAlchemy PostgreSQL 方言也提供 insert(...).on_conflict_do_nothing() / on_conflict_do_update()；这属于 PostgreSQL 专属 DML 特性，不应假定所有数据库方言完全相同。

5. 事务：避免多个数据库修改只完成一半

5.1 事务边界决定回滚范围

假设一次反馈确认包含：

  1. 创建反馈记录；
  2. 创建幂等结果记录；
  3. 创建等待发布的 Outbox 事件。

理想情况下，三步属于同一个数据库事务：

text
BEGIN
  INSERT feedbacks
  INSERT idempotency_records
  INSERT outbox_events
COMMIT

其中任何一步因约束或程序错误失败，就：

text
ROLLBACK

结果是三张表中的本次未提交修改整体撤销，而不是保留“已创建反馈但未保存请求记录”的中间状态。

5.2 flush、commit、rollback 的区别

操作 含义 对其他事务的可见性
session.add() 将对象登记为待处理 尚未写入数据库
session.flush() 发送 SQL 到当前事务 通常还未提交，其他事务不可读到该修改
session.commit() 提交事务并使修改持久化 提交后按隔离规则可见
session.rollback() 撤销当前未提交事务 不影响此前已提交事务

flush 在拿到自增 ID、触发约束时非常有用，但它不是提交。注意 PostgreSQL 的序列号分配不随事务回滚归还，因此 ID 出现间隔是正常现象。

5.3 事务不能跨越外部系统自动撤销

text
BEGIN
INSERT feedbacks
POST /email/send  ← 第三方已接受邮件
ROLLBACK          ← 邮件不会因此被撤销

数据库事务只能对它管理的数据库状态提供原子性。对于 Kafka、支付接口、邮件和其他外部服务，需要 Outbox、外部幂等键、状态查询与补偿机制，而不是期待普通 SQL 回滚生效。

5.4 SQLAlchemy 事务上下文

python
with SessionFactory.begin() as session:
    session.add(feedback)
    session.add(idempotency_record)
    session.add(outbox_event)
# 没有异常时提交；有异常时回滚。

异步版：

python
async with AsyncSessionFactory.begin() as session:
    session.add(feedback)
    await session.flush()
    session.add(outbox_event)

Session/AsyncSession 是事务性、有状态的对象。并发任务不应复用同一 Session 实例，而应共享 Engine / 工厂、按操作创建独立 Session。

6. 并发修改：从丢失更新（Lost Update）理解竞争

假设某条反馈的 status='OPEN'，两位工作人员同时读取到旧版本：

text
用户 A 读取：version=3, status=OPEN
用户 B 读取：version=3, status=OPEN
用户 A 保存：status=IN_REVIEW
用户 B 保存：status=CLOSED

如果业务没有并发控制，B 的修改可能覆盖 A 的决定，而 B 根本没有看到 A 的修改。不同隔离级别与更新语句的具体行为需要区分，但应用级“读对象—修改—保存”通常应该明确其并发策略。

6.1 乐观并发控制（Optimistic Concurrency Control）

通过 version_id 表示记录版本：

sql
UPDATE feedbacks
SET content = '新的反馈内容', version_id = version_id + 1
WHERE id = 1024 AND tenant_id = 't1' AND version_id = 3
RETURNING id, version_id;
  • 返回 1 行：原版本仍匹配，更新成功。
  • 返回 0 行：可能记录不存在、权限范围不匹配或版本已变化，需进一步判断并报告冲突。

此时让用户重新读取并决定如何合并，而不是偷偷覆盖别人的修改。

6.2 SQLAlchemy 的 version_id_col

python
class Feedback(Base):
    # ... 其他字段略
    version_id: Mapped[int] = mapped_column(Integer, nullable=False, default=1)
    __mapper_args__ = {"version_id_col": version_id}

ORM 在 Flush 更新时会把旧版本加入 WHERE 条件；更新不到预期行时抛出 StaleDataError。这通常只适用于 ORM 单对象 Flush 路径，不自动覆盖所有 Core 批量 UPDATE/DELETE。

6.3 悲观并发控制（Pessimistic Locking）

在确实要串行操作某个现存对象时：

sql
BEGIN;
SELECT id, status FROM feedbacks WHERE id = 1024 FOR UPDATE;
-- 检查状态后更新
UPDATE feedbacks SET status = 'APPROVED' WHERE id = 1024;
COMMIT;

FOR UPDATE 对选中的行加锁，其他竞争写入可能等待事务结束。但要注意：

  • 锁住的是已经存在的行，不是凭空替代“尚不存在行的唯一约束”。
  • 锁持有越久，等待和死锁风险越大。
  • 不要在持有数据库行锁时长时间等待模型 API 或第三方网络请求。
  • 多行加锁尽量采用固定顺序，降低死锁风险。

6.4 单语句条件更新通常比“先读后写”更简单

例如库存扣减：

sql
UPDATE inventory
SET remaining = remaining - 1
WHERE sku = 'sku-1' AND remaining > 0
RETURNING remaining;

让数据库在一个原子语句内检查条件并修改数据，可以减少竞态窗口。若任务还要求记录订单、库存流水和幂等请求，则仍应把这些变更放在同一事务内。

7. 事务隔离级别与 MVCC

PostgreSQL 使用多版本并发控制（MVCC）支持并发读写。隔离级别决定事务可以观察到哪些并发变化。

隔离级别 PostgreSQL 中的关键表现 典型注意点
Read Committed（默认） 语句级快照；连续两次 SELECT 可能看到不同提交结果 读后写仍需唯一约束、锁或条件更新
Repeatable Read 事务快照更稳定；并发更新冲突可能导致事务失败 应准备完整事务重试
Serializable 尝试提供串行执行等效语义 可能返回序列化失败，需要重新执行事务

“读到一致快照”与“业务绝不可能冲突”并不是同一回事。即使选择 Serializable，也必须合理定义唯一约束、业务身份以及外部副作用。

7.1 写偏差（Write Skew）

例如两个值班医生分别读取“至少还有一位医生在线”，两人各自把自己设为离线。两人修改的是不同行，单行版本号不一定能直接保证“至少一位在线”的跨行规则。

这类跨对象不变量需要更强的事务隔离、适当锁定共同的协调行、约束设计或其他确定性协调机制。不能把“所有更新都有 version 字段”误认为全局业务规则已经安全。

8. HTTP 幂等：重复请求如何获得一致业务结果

8.1 产生重复请求的来源

  • 用户双击按钮；
  • 网络断开，浏览器不知道结果是否提交；
  • API 网关或客户端重试；
  • 消息队列重复投递；
  • Worker 崩溃后再次消费；
  • 用户刷新页面重新提交。

任何一个系统层都不应该仅依赖前端禁用按钮来防重。

8.2 幂等键与业务键不能混淆

示例请求：

http
POST /feedback/confirm
Idempotency-Key: confirm-request-2026-001
Content-Type: application/json

{"draft_id":"draft-7","content":"游戏在特定步骤崩溃"}
  • 业务键：(tenant_id, user_id, draft_id)，回答“哪一个最终反馈对象”。
  • 幂等键：(tenant_id, user_id, endpoint, Idempotency-Key)，回答“是否同一个请求意图的重放”。
  • 请求指纹：对规范化且安全的业务参数进行稳定哈希，回答“相同键是否代表相同内容”。

如果同一个幂等键携带不同的请求内容，应返回明确冲突，而不是悄悄复用旧结果，也不能按新内容覆盖旧结果。

8.3 同一次提交的典型处理

text
客户端提交 key=K, payload=P
  ↓
先检查（租户、用户、接口、K）的既有记录
  ├─ 已完成 + 指纹相同：返回此前保存的业务结果
  ├─ 已完成 + 指纹不同：409 Conflict
  ├─ 正在处理中：返回状态或可重试提示，禁止重复执行
  └─ 尚无记录：尝试以数据库唯一约束抢占该键
        ↓
在事务中创建业务记录 + 结果 + Outbox
        ↓
提交成功，返回结果

上面的“正在处理中”状态适合跨事务的长任务；对于短小且能放在同一数据库事务内完成的操作，可以采用原子写入结果记录的简化设计。

8.4 幂等记录应保存什么

sql
CREATE TABLE idempotency_records (
    tenant_id TEXT NOT NULL,
    user_id TEXT NOT NULL,
    operation TEXT NOT NULL,
    request_key TEXT NOT NULL,
    request_hash CHAR(64) NOT NULL,
    status TEXT NOT NULL,
    response_json JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, user_id, operation, request_key)
);

实际生产还需确定：记录保留期限、内容脱敏、重试窗口、响应是否包含易失字段、结果查询授权、任务超过期限时如何恢复，以及相同业务对象跨不同幂等键创建的冲突处理。

8.5 原请求的响应丢失怎么办

text
请求 A → 数据库已 COMMIT → 网络在返回 201 前断开
请求 B（相同 key）→ 查询已提交幂等记录 → 返回同一个 feedback_id

这就是幂等记录的实际价值：不知道上次网络返回了什么，不意味着上次业务没有成功。

9. 四种防护机制的分层组合

text
HTTP API
 ├─ 认证/对象授权
 ├─ 请求参数与请求指纹
 └─ 幂等键范围核验
          ↓
业务服务
 ├─ 业务规则与状态迁移
 ├─ 预期版本（Optimistic Lock）
 └─ 确定事务边界
          ↓
PostgreSQL 事务
 ├─ UNIQUE / FK / CHECK / NOT NULL
 ├─ INSERT ON CONFLICT 或条件 UPDATE
 ├─ 反馈 + 幂等记录 + Outbox 同事务提交
 └─ 失败时整体 ROLLBACK
          ↓
Outbox 发布器 / Worker
 ├─ 至少一次投递情况下的重复处理保护
 ├─ 外部 API 幂等能力与结果查询
 └─ 成功、失败、未知状态的明确区分

9.1 不要把 Redis 锁当作数据库唯一约束

Redis SET ... NX PX 可以用于分布式临时协调，但锁可能过期、持有方可能暂停、网络可能分区。无论是否使用锁，数据库仍需要保持业务唯一约束和正确事务；必要时还要考虑 fencing token。

9.2 不要把“完全一次执行”当成默认能力

消息队列可能至少一次投递；外部调用超时后可能处于“已经执行但响应丢失”的不确定状态。生产系统一般追求的是可重放且业务效果幂等，而不是只靠一个标志就保证每段代码的物理执行次数恰好为一次。

10. Outbox：跨数据库与消息系统时避免丢事件

典型不可靠方式：

text
数据库提交成功
    ↓
进程崩溃
    ↓
Kafka 发送尚未发生 → 事件丢失

一种常见解决方案是 Transactional Outbox：

text
BEGIN
  写入反馈
  写入 Outbox 待发布事件
COMMIT
    ↓
独立发布器扫描 Outbox，发送到 Kafka
    ↓
保存发布结果 / 重试

注意三个边界：

  1. Outbox 使“业务数据与待发布记录”在同一数据库事务中原子保存，但并不意味着发布器只会发送一次。
  2. 发布器可能发送成功后崩溃，导致事件重发；消费者仍需根据事件 ID 进行幂等处理。
  3. 对支付、邮件等第三方操作，是否可安全重试取决于对方是否支持幂等键和状态查询；不支持时应保留 UNKNOWN 状态，避免盲目重复外部副作用。

11. 并发时常见的数据库错误与处理原则

PostgreSQL 错误码（SQLSTATE）：

SQLSTATE 名称 典型处理
23505 unique_violation 根据约束名称区分幂等重放与业务冲突
23503 foreign_key_violation 核对被引用对象及业务状态
23502 not_null_violation 修复请求/程序数据契约
23514 check_violation 报告违反的业务不变量
40001 serialization_failure 有界重试整个事务
40P01 deadlock_detected 有界重试事务，审查加锁顺序

不要对所有 IntegrityError 无条件执行重试。 唯一冲突一般需要判定“相同请求重放”“业务对象已经存在”还是“数据模型设计错误”。序列化失败和死锁则通常属于适合有限重试的事务级故障。

重试应遵循：创建新的 Session/事务，重新读取状态、重新判断条件；不要在已经失败的事务中直接复用旧对象继续提交。

11.1 退避重试

python
# 伪代码，重点在策略：
for attempt in range(MAX_ATTEMPTS):
    try:
        return execute_one_complete_db_transaction()
    except RetryableTransactionError:
        if attempt == MAX_ATTEMPTS - 1:
            raise
        sleep(min(cap, base * (2 ** attempt)) + jitter())

如果事务函数包含外部发送请求，盲目“整体重试”可能重复发送；应把不可回滚副作用移至 Outbox / 可幂等的外部工作流中。

12. HTTP API 应怎样表达结果

场景 建议响应 说明
首次成功创建 201 Created 返回新建对象 ID
相同请求幂等重放 200 OK 或重放原响应 事先固定协议，保持返回结果一致
同键但不同内容 409 Conflict 拒绝把两个不同动作解释为同一请求
业务对象已被不同请求确认 409 Conflict 返回冲突信息与允许公开的现有资源状态
客户端旧版本更新 409 Conflict 或 412 Precondition Failed 如果使用 HTTP ETag/If-Match，412 更贴近条件请求语义
校验失败 422 Unprocessable Content（FastAPI 常见） 请求没有满足输入契约
系统并发故障重试耗尽 503 Service Unavailable 等 不可将失败伪装为业务成功
幂等长任务仍在处理 202 Accepted 返回 task_id 和查询方式

这里的 HTTP 状态是推荐契约，不是唯一合法映射。关键在于前后端对错误码、是否可以重试、已完成结果能否复用保持一致。

14. 无法完全靠事务约束解决的情况

14.1 数据库约束不是身份授权

UNIQUE (tenant_id, user_id, draft_id) 保证键唯一，不保证请求方有权操作该用户和草稿。后端必须以认证身份决定可访问的租户与资源范围；不能直接信任客户端提交的 tenant_id。

14.2 事务不是跨系统分布式原子提交

本地 PostgreSQL 提交成功，不代表缓存更新、Kafka 投递、邮件发送也完成。需要消息记录、Outbox、重试与对账。

14.3 事务隔离不等于无限可靠

Serializable 可能主动中止事务；冲突和重试逻辑是其可用性契约的一部分。外部调用不应该放在无法安全重试的事务中。

14.4 幂等不是永久缓存一切

幂等键保留期限应根据业务和客户端重试窗口设计。清理旧键后，同一个键再次使用会如何处理，必须有明确协议；重要业务仍要靠业务唯一约束长期阻止重复记录。

15. 如何定位真实系统中的重复记录和数据不一致

建议沿着可观测链路排查：

text
request_id → 已认证 user / tenant
   ↓
Idempotency-Key + 规范化 payload_hash
   ↓
调用方是否重新请求 / 网关是否重试
   ↓
服务进入事务的次数与状态
   ↓
发生冲突的约束名 / SQLSTATE
   ↓
实际 COMMIT / ROLLBACK 情况
   ↓
Outbox event_id / Worker 消费记录
   ↓

推荐记录 request_id、trace_id、业务键的脱敏形式、幂等键的哈希、事务结果、冲突类型、版本号和重试次数；不要把支付密钥、隐私信息、完整访问令牌或原始敏感请求直接写入日志。

常见排查结论：

现象 首要排查方向
同一草稿两条最终反馈 缺少正确业务唯一约束；软删除谓词或业务键范围错误
相同请求创建多个资源 幂等键未验证、记录过早删除、未加数据库唯一约束
修改被覆盖 缺少版本条件；使用了绕过 ORM version 的批量更新
数据库出现半完成流程 多次分散 commit()；跨系统副作用不受事务保护
大量 23505 高并发竞争，或业务唯一键设计/客户端重试异常
大量 40001/40P01 热点记录、隔离级别、锁顺序、事务时间过长
消息重复通知 Outbox/消息消费者缺乏去重；外部操作缺少幂等支持

16. 一组具体的端到端语义

业务规则：同租户同用户同草稿只生成一条最终反馈；收到相同幂等请求时返回相同反馈 ID；不同内容复用键时拒绝；反馈与待发布事件同事务提交。

假设第一次请求：

json
{
  "tenant_id": "tenant-a",
  "user_id": "user-1",
  "draft_id": "draft-9",
  "request_key": "confirm-k-001",
  "content": "进入战斗后立刻闪退"
}

期待结果：

json
{"status": "SUCCEEDED", "feedback_id": 1}

随后存在三种差异：

  1. 同一请求原样重放：仍返回 feedback_id=1，不会多生成反馈和 Outbox。
  2. 同一幂等键但内容改为“进入商店闪退”：拒绝，不能偷偷改写原反馈。
  3. 使用新幂等键但仍试图确认同一草稿：业务唯一约束拒绝，不能生成第二条最终反馈。

为了验证这些语义，下一附录提供一个不依赖真实外部服务的 SQLAlchemy 完整教学实现。

18. 核心机制归纳

必须维护的不变量 最直接的数据库/程序机制 还需要配合
同业务对象最多一条 UNIQUE / 部分唯一索引 明确业务键与软删除规则
同请求重复不重复生效 幂等键 + 请求指纹 + 保存结果 数据库唯一约束、事务
同记录编辑不无声覆盖 乐观锁 version_id 或条件更新 冲突提示、重读与人工合并
跨表变化要么全成要么全败 数据库事务 合理的约束与事务边界
并发库存不扣成负数 原子条件更新/锁/约束 同事务业务流水
数据库成功但服务崩溃不丢通知 Transactional Outbox 发布器、消费者去重、外部幂等
事务序列化失败后正确恢复 对 40001 等有界重试整事务 避免不可回滚外部副作用

一句话理解：数据库是业务不变量的最终执行者；事务保证一个数据库动作集合的原子性；幂等设计使重复到达的请求产生受控的业务效果；版本与锁负责协调并发修改。四者互补，不可相互代替。

附录 A：完整、可运行的 Python 代码（example.py）

以下代码作为 SQLite 离线教学实验，展示 SQLAlchemy 的复合唯一约束、幂等请求记录、同事务 Outbox、版本字段与重复请求处理。请在单独目录保存为 example.py。

python
"""SQLite teaching demo. PostgreSQL semantics are discussed separately in the guide."""
from __future__ import annotations

import hashlib
import json
from dataclasses import dataclass
from pathlib import Path
from sqlalchemy import ForeignKey, Integer, String, Text, UniqueConstraint, create_engine, select
from sqlalchemy.exc import IntegrityError
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, sessionmaker


class Base(DeclarativeBase):
    pass


class Feedback(Base):
    __tablename__ = "feedbacks"
    __table_args__ = (
        UniqueConstraint("tenant_id", "user_id", "draft_id", name="uq_feedback_business"),
    )

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    tenant_id: Mapped[str] = mapped_column(String(60), nullable=False)
    user_id: Mapped[str] = mapped_column(String(60), nullable=False)
    draft_id: Mapped[str] = mapped_column(String(60), nullable=False)
    content: Mapped[str] = mapped_column(Text, nullable=False)
    version_id: Mapped[int] = mapped_column(Integer, nullable=False, default=1)

    __mapper_args__ = {"version_id_col": version_id}


class IdempotencyRecord(Base):
    __tablename__ = "idempotency_records"
    __table_args__ = (
        UniqueConstraint("tenant_id", "user_id", "request_key", name="uq_request_identity"),
    )

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    tenant_id: Mapped[str] = mapped_column(String(60), nullable=False)
    user_id: Mapped[str] = mapped_column(String(60), nullable=False)
    request_key: Mapped[str] = mapped_column(String(100), nullable=False)
    payload_hash: Mapped[str] = mapped_column(String(64), nullable=False)
    response_json: Mapped[str] = mapped_column(Text, nullable=False)


class OutboxEvent(Base):
    __tablename__ = "outbox_events"
    __table_args__ = (UniqueConstraint("event_key", name="uq_outbox_event_key"),)

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    event_key: Mapped[str] = mapped_column(String(160), nullable=False)
    feedback_id: Mapped[int] = mapped_column(ForeignKey("feedbacks.id"), nullable=False)
    event_type: Mapped[str] = mapped_column(String(50), nullable=False)
    payload: Mapped[str] = mapped_column(Text, nullable=False)


class IdempotencyConflict(Exception):
    pass


class DuplicateBusinessObject(Exception):
    pass


def make_factory(db_path: Path):
    engine = create_engine(f"sqlite+pysqlite:///{db_path}", future=True)
    Base.metadata.create_all(engine)
    return engine, sessionmaker(engine, expire_on_commit=False)


def digest_payload(draft_id: str, content: str) -> str:
    stable = json.dumps({"draft_id": draft_id, "content": content}, ensure_ascii=False,
                        sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(stable.encode("utf-8")).hexdigest()


def submit_feedback(factory, *, tenant_id: str, user_id: str,
                    request_key: str, draft_id: str, content: str) -> dict:
    """Atomic create + outbox + replay record, without real external side effects."""
    if not all((tenant_id, user_id, request_key, draft_id, content.strip())):
        raise ValueError("Required arguments must be non-empty")
    payload_hash = digest_payload(draft_id, content)

    def lookup_existing():
        with factory() as session:
            row = session.scalar(select(IdempotencyRecord).where(
                IdempotencyRecord.tenant_id == tenant_id,
                IdempotencyRecord.user_id == user_id,
                IdempotencyRecord.request_key == request_key,
            ))
            if row is None:
                return None
            if row.payload_hash != payload_hash:
                raise IdempotencyConflict("Same request_key used for different content")
            return json.loads(row.response_json)

    old = lookup_existing()
    if old is not None:
        return old

    try:
        with factory.begin() as session:
            obj = Feedback(tenant_id=tenant_id, user_id=user_id,
                           draft_id=draft_id, content=content)
            session.add(obj)
            session.flush()  # Get PK; not yet committed.
            reply = {"status": "SUCCEEDED", "feedback_id": obj.id}
            session.add(OutboxEvent(
                event_key=f"feedback_created:{tenant_id}:{user_id}:{draft_id}",
                feedback_id=obj.id,
                event_type="FEEDBACK_CREATED",
                payload=json.dumps({"feedback_id": obj.id}, sort_keys=True),
            ))
            session.add(IdempotencyRecord(
                tenant_id=tenant_id, user_id=user_id,
                request_key=request_key, payload_hash=payload_hash,
                response_json=json.dumps(reply, sort_keys=True),
            ))
        return reply
    except IntegrityError as exc:
        # Winning concurrent transaction may have committed by now. Re-query.
        replay = lookup_existing()
        if replay is not None:
            return replay
        raise DuplicateBusinessObject("Draft was already submitted or constraint failed") from exc
