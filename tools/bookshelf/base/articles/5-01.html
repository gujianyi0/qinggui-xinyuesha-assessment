1. HTTP API 的执行模型与分层契约

1.1 HTTP 请求和响应

HTTP 是客户端与服务器之间交换表示信息的应用层协议。一条典型请求由方法、URL、请求头、请求体组成；响应由状态码、响应头、响应体组成。

http
POST /v1/messages HTTP/1.1
Host: api.example.test
Content-Type: application/json
Authorization: Bearer <token>

{"text":"请解释角色技能"}
http
HTTP/1.1 201 Created
Content-Type: application/json
X-Request-ID: 14fb...

{"message_id":"...","answer":"已收到：请解释角色技能"}

不要混淆四个层次：

  • 传输层结果：DNS、TCP、TLS、代理、请求是否真正到达。网络失败时可能根本没有 HTTP 响应。
  • HTTP 结果：200、201、202、404、422、500 等，表示这次 HTTP 交互的语义。
  • 业务执行状态：如 PENDING、RUNNING、SUCCEEDED、FAILED。与单次 HTTP 状态码不是同一回事。
  • 前端交互状态：如正在提交、等待结果、展示成功、展示错误。它是客户端对前三者的映射。

1.3 什么是接口契约

接口契约需要明确：

  1. 输入契约：路径、查询、头、正文各有哪些参数；类型、范围、默认值和约束。
  2. 成功契约：成功时的 HTTP 状态、响应模型和业务语义。
  3. 错误契约：每类错误对应的状态码、稳定错误码、可重试性及字段定位。
  4. 异步契约：接收任务、查询任务、最终状态和结果是否可恢复。
  5. 生命周期契约：客户端断开、服务重启或取消请求时任务如何处理。

接口契约不仅用于生成 API 文档，更直接决定前端能否正确显示界面。

2. HTTP 请求从何处获取参数

FastAPI 可以把请求的不同部分转换成 Python 参数：

来源 声明方式 典型用途 示例
Path 路径参数 / Path() 资源标识 /users/12
Query 普通简单参数 / Query() 排序、分页、过滤 ?page=2
Body Pydantic 模型 / Body() 创建、更新资源 JSON 对象
Header Header() 认证、幂等键、条件请求 If-Match
Cookie Cookie() 会话相关值 Session Cookie
Dependency Depends() 认证、会话、共享逻辑 当前用户
python
from fastapi import FastAPI, Path, Query, Header
from pydantic import BaseModel, Field

app = FastAPI()

class ProductChange(BaseModel):
    name: str = Field(min_length=1)
    count: int = Field(ge=0)

@app.put('/products/{product_id}')
async def update_product(
    data: ProductChange,
    product_id: int = Path(ge=1),
    dry_run: bool = Query(False),
    if_match: str | None = Header(default=None),
):
    return {
        'product_id': product_id,
        'data': data.model_dump(),
        'dry_run': dry_run,
        'if_match': if_match,
    }

关键细节：

  • URL 路径中与参数同名的字段通常按路径处理；简单类型参数通常按查询处理；Pydantic 模型通常来自请求体。
  • JSON 正文并不意味着可以无条件信任。必须校验格式、类型、字段、长度、值域与业务合法性。
  • Query 等输入来自 URL 文本，FastAPI/Pydantic 可进行适当转换；是否采用严格类型应依据业务场景决定。
  • Header 映射的客户端值不是天然可信的认证主体；Authorization 要经真实身份验证。
  • 前端传来的 user_id / tenant_id 不能代替后端认证与对象级授权。
  • 对 GET 请求不建议使用 JSON Body；虽然某些框架能接收，但客户端、代理与规范化工具的兼容性较差。

3. FastAPI 请求模型与 Pydantic 校验

3.1 从 JSON 到 Python 对象

python
from pydantic import BaseModel, Field, ConfigDict

class ChatRequest(BaseModel):
    model_config = ConfigDict(extra='forbid', strict=True)

    text: str = Field(min_length=1, max_length=200)

@app.post('/chat')
async def chat(data: ChatRequest):
    return {'answer': f'收到：{data.text}'}

请求处理的关键步骤是：收到请求体 → 识别 Content-Type 和 JSON → 构造 Pydantic 模型 → 逐字段校验 → 成功时才进入路由业务逻辑。

如果 text 是空字符串、长度超限、类型错误，或者包含 extra='forbid' 禁止的未知字段，FastAPI 可以在路由函数执行前返回请求验证错误。

3.2 Python 类型标注与 Pydantic 的不同

python
def f(x: int):
    return x

f('123')  # 普通 Python 类型标注默认不会拒绝字符串

而 Pydantic 在构造模型时会进行运行时检查。默认模式下，某些类型可以被转换；严格模式会限制许多自动转换。

python
from pydantic import BaseModel, ConfigDict

class StrictCount(BaseModel):
    model_config = ConfigDict(strict=True)
    count: int

# StrictCount(count='12') 会触发校验错误

注意：严格模式不是所有业务校验的替代品。例如 count=3 通过整数类型检查，也未必满足库存、权限或交易规则。

3.3 字段验证与跨字段验证

字段验证关心单个数据元素，例如 min_length、ge、le、pattern。跨字段验证用于检查两个或多个字段的关联条件，例如结束时间必须晚于开始时间。

python
from datetime import datetime
from pydantic import BaseModel, model_validator

class Period(BaseModel):
    start: datetime
    end: datetime

    @model_validator(mode='after')
    def check_period(self):
        if self.end <= self.start:
            raise ValueError('结束时间必须晚于开始时间')
        return self

Pydantic 的校验只保证定义了的约束被检查。数据库唯一性、资源归属、库存扣减以及外部事实等，仍需服务层或数据库执行。

4. 字段可选、默认值、可空与严格类型

这些概念不同，尤其是 Pydantic v2：

python
class Sample(BaseModel):
    a: str                   # 必填，不能为 None
    b: str | None            # 必填，但允许 None
    c: str | None = None     # 可省略，默认 None
    d: int = 10              # 可省略，默认 10

T | None 表示值域允许 None，而不是自动让字段可省略。 是否必填主要由默认值决定。

如果接口对更新采用 PATCH，应区分“不提供字段”与“显式把字段置为 null”。通常可检查 Pydantic 的 model_fields_set，或使用 model_dump(exclude_unset=True) 获取真正提交的字段。

例如：

python
class UserPatch(BaseModel):
    display_name: str | None = None

patch = UserPatch.model_validate({})
assert 'display_name' not in patch.model_fields_set

patch2 = UserPatch.model_validate({'display_name': None})
assert 'display_name' in patch2.model_fields_set

在涉及用户资料、数据库列和前端表单时，这个区别能避免不必要地覆盖已有数据。

5. 输入校验发生在哪一步，为什么经常看到 422

FastAPI 默认使用 422 Unprocessable Content（也常见旧称 Unprocessable Entity）表示有效 HTTP 请求中包含不满足接口输入契约的数据。

例如：

http
POST /v1/messages
Content-Type: application/json

{"text":""}

本教学应用返回：

json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请求数据不符合约定格式",
    "retryable": false,
    "details": [
      {"path": "body.text", "type": "string_too_short"}
    ]
  },
  "request_id": "..."
}

错误定位的两个关键字段：

  • loc / path：发生错误的位置，例如 body.text、path.item_id、query.include_note。
  • type：错误类别，例如 missing、int_parsing、string_too_short、extra_forbidden。

如果直接使用 FastAPI 默认处理器，通常收到 {"detail":[...]}；本教学项目将其转换成业务统一错误结构，便于前端消费。

注意区分：

  • 400：通常用于业务约定的非法请求、格式问题等（具体协议另行设计）。
  • 401：没有通过认证。
  • 403：已识别身份，但不允许访问。
  • 404：资源不存在；出于防止泄露对象存在性，有时也可对未授权资源返回 404。
  • 409：请求与资源当前状态冲突。
  • 422：请求输入未通过结构、类型或字段约束校验。

不要为了“统一”而把所有错误都返回 200 + success:false，那样会破坏标准 HTTP 语义，使监控、代理和 SDK 难以准确判断失败。

6. 响应模型、序列化和字段过滤

FastAPI 的 response_model 定义返回给客户端的数据契约，并参与返回值校验、序列化及输出字段过滤。

python
class UserPublic(BaseModel):
    user_id: int
    nickname: str

@app.get('/users/{user_id}', response_model=UserPublic)
async def get_user(user_id: int):
    return {
        'user_id': user_id,
        'nickname': 'Alex',
        'password_hash': 'sensitive-data',
    }

响应结果只包含 UserPublic 允许的字段：

json
{"user_id":12,"nickname":"Alex"}

输出过滤是有用的防线，但敏感数据依然不应无必要地进入业务序列化对象、日志或追踪数据。也不要把它当成权限系统。

6.1 声明方式

  • 路由装饰器 @app.get(..., response_model=SomeModel)：显式指定 FastAPI 响应模型。
  • 函数返回类型 async def fn() -> SomeModel：也可能被 FastAPI 用于响应模型推断。
  • 返回原始 Response / JSONResponse：通常跳过 FastAPI 依据 response_model 的自动转换和过滤；需由开发者自己保证正确性。

6.2 输出约束与输入约束不对称

输入不符合请求模型，通常是客户端 422。服务器返回的数据不符合声明的 response_model，通常是服务器编程错误，会导致 500，而非返回 422 要求用户修改输入。

如果应用要保留完整内部数据，同时对外只发送受限字段，推荐显式使用公开响应模型而不是依赖前端忽略多余字段。

7. 响应模型错误的传播

text
外部请求 / 前端输入
  ├─ 请求体未通过 Pydantic → 422（客户端输入错误）
  └─ 请求校验通过
       └─ Service 返回结果
            ├─ 业务拒绝 → 409 / 403 / 404 等
            ├─ 外部依赖失败 → 502 / 503 / 504 等（取决于服务边界）
            ├─ 返回值不符合响应模型 → 500（服务端契约违反）
            └─ 响应模型通过 → 200 / 201 / 202 等

这里需要区分三类校验：

  1. 输入校验：客户端送来的内容是否合法。
  2. 输出校验：服务端承诺的返回结构是否真实遵守。
  3. 业务校验：操作是否有权限，当前状态是否允许，真实事实是否正确。

结构通过不代表业务成功；请求进入路由也不代表事务已经提交。

8. HTTP 状态码与业务执行状态的关系

HTTP 状态 典型解释 前端处理参考
200 OK 当前 HTTP 查询成功 继续检查 body 中业务状态
201 Created 资源已创建 可以展示已创建资源
202 Accepted 请求已接收，但处理未完成 转入等待/轮询状态
204 No Content 成功但不返回正文 不应强制调用 response.json()
400 / 422 输入有问题 高亮字段并给出修改提示
401 认证失败或缺失 引导重新登录或刷新认证
403 未获授权 禁止继续尝试受保护操作
404 资源不存在 显示不存在或已被删除
409 当前业务状态冲突 刷新数据、提示冲突、避免盲目重复
429 触发限流 按服务端策略等待，考虑 Retry-After
500 服务端内部错误 错误反馈与追踪 ID
502 / 503 / 504 上游或服务可用性问题 有界重试，保留上下文

不应仅靠某个 HTTP 状态码判断 AI 结果是否可靠。例如 /tasks/{id} 查询成功返回 200，但任务自身的 state 可能为 FAILED。

8.1 业务状态适合用明确枚举

text
PENDING → RUNNING → SUCCEEDED
                  └→ FAILED

生产任务还可能有 RETRYING、CANCEL_REQUESTED、CANCELLED、EXPIRED 等状态。务必明确终态与允许的状态转换。

9. 错误对象设计：机器可读与人类可读要分开

不推荐把前端逻辑写成 if (message.includes('超时'))。错误消息可能被翻译或调整；应提供稳定错误码。

json
{
  "error": {
    "code": "BUSINESS_CONFLICT",
    "message": "当前状态不允许此操作",
    "retryable": false,
    "details": null
  },
  "request_id": "f8e2..."
}

字段含义：

  • code：稳定、供客户端程序判断的错误代码，例如 VALIDATION_ERROR。
  • message：供用户阅读或开发调试的解释，不应包含堆栈、密钥或敏感对象。
  • retryable：服务端评估的当前失败是否可能适合重试；并不自动表示操作安全可重放。
  • details：字段路径、规则错误等结构化信息，注意脱敏。
  • request_id：用于关联日志与响应。

9.1 自定义异常与异常处理器

推荐在 Service 抛出明确的领域异常，由接口层统一映射成 HTTP 状态与错误响应。

python
class DomainError(Exception):
    def __init__(self, status: int, code: str, message: str):
        self.status = status
        self.code = code
        self.message = message

@app.exception_handler(...) 注册异常处理器。FastAPI 还可以覆盖 RequestValidationError 的默认处理，但不要将 exc.body 原样返回给客户端或写到不受保护的日志：它可能包含口令、验证码、Cookie 或个人信息。

9.2 什么时候适合返回 HTTPException

小型应用可以在路由直接 raise HTTPException(status_code=404, detail='...')。在较大的代码库中，领域层采用独立异常更容易复用和测试，接口适配层负责把领域错误映射成 HTTP。

10. 网络失败、HTTP 失败和业务失败

这三种错误在浏览器中看起来都可能是“请求失败”，但排查与重试策略完全不同。

类型 示例 是否存在 HTTP Response 典型处理
网络失败 DNS、断网、CORS 阻止、连接重置 不一定可被 JS 读取 网络错误提示、检查连接
HTTP 失败 后端返回 422、409、503 通常有 解析错误对象、按状态处理
业务失败 GET /jobs/42 返回 200，但 state=FAILED 有，可能是 200 读取任务状态与业务错误

一个极易忽略的事实：浏览器的 fetch() 在服务器返回 HTTP 404 或 500 时通常不会自动 reject Promise；只有网络等请求失败才通常 reject。因此必须检查 response.ok 或 response.status。

javascript
const response = await fetch('/api/data');
if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}
const data = await response.json();

同样需要处理“HTTP 成功，但返回正文不是有效 JSON”、“204 没有正文”、浏览器因跨域策略无法读取响应，以及前端主动取消请求等情况。

11. 202 Accepted 与处理中的任务

某些操作（导入资料、批量 Embedding、长时间模型推理）无法在短时间内完成。可以提供任务式 API：

http
POST /v1/jobs
{"prompt":"建立索引"}
http
HTTP/1.1 202 Accepted
Location: /v1/jobs/aabbcc...
Retry-After: 1

{"job_id":"aabbcc...","state":"PENDING"}

随后：

http
GET /v1/jobs/aabbcc...
json
{"job_id":"aabbcc...","state":"RUNNING","result":null,"error":null}

任务完成：

json
{"job_id":"aabbcc...","state":"SUCCEEDED","result":"处理完成：建立索引","error":null}

任务失败时，查询接口依然可能返回 HTTP 200：

json
{
  "job_id":"aabbcc...",
  "state":"FAILED",
  "result":null,
  "error":{"code":"JOB_FAILED","message":"任务执行失败","retryable":false,"details":null}
}

因为 “GET 查询执行成功” 和 “该任务在过去执行成功” 并不是同一命题。

11.1 客户端等待超时后怎么办

  • 前端可以停止轮询，但不能直接断言服务器任务已经失败。
  • 应保留任务 ID，允许稍后恢复查询。
  • 取消后台任务需要单独设计 cancel API 和明确的取消范围。
  • 写入型请求如果发生网络超时，不应未经幂等设计就自动重新发起相同操作。

11.2 演示任务与可靠后台任务的区别

本文件的演示服务使用 asyncio.create_task() 和进程内字典，只适合说明 HTTP 202、轮询和状态转换。在多进程、容器重启或强制退出时不能保证任务持久化。

真实需要恢复的任务，应使用持久化任务记录、独立 Worker、消息队列、重试与幂等控制。BackgroundTasks 也不自动等价于可靠的跨重启任务队列。

12. 前端状态机：提交、处理中、成功与失败

常见 UI 状态应明确区分：

text
IDLE
  │ 用户点击
  ▼
SUBMITTING ─── 网络/HTTP 失败 ───▶ FAILED
  │ HTTP 202，获得 job_id
  ▼
PROCESSING ─── 查询不到任务/HTTP 失败 ─▶ ERROR / UNKNOWN
  ├── state=SUCCEEDED ───────────▶ SUCCEEDED
  ├── state=FAILED ──────────────▶ FAILED
  └── 客户端等待超时 ────────────▶ UNKNOWN（可继续查询）
  • SUBMITTING：提交 HTTP 请求仍在飞行中。
  • PROCESSING：服务器已经接收任务，但后台尚未达到终态。
  • SUCCEEDED：已确认业务实际完成。
  • FAILED：明确收到了 HTTP 错误或业务失败结果。
  • UNKNOWN：客户端未能确定最终状态，例如前端截止时间到达；此时不应伪造“任务失败”。

12.1 典型 React 状态

javascript
const [jobUi, setJobUi] = useState({phase: 'idle'});

// 展示逻辑（示意）
// submitting -> 提交中
// processing -> 正在处理 + 进度提示
// succeeded -> 展示结果
// failed -> 错误提示与允许的恢复动作
// unknown -> 保留任务 ID，允许重新查询

另外还要处理页面跳转时的 AbortController、过期请求回写 UI、重复点击与表单禁用。前端停止等待，不等于服务器执行已经取消。

12.2 超时、重试和幂等

  • 客户端单次请求超时：例如 10 秒，解决前端无限等待问题。
  • 业务任务截止时间：例如 5 分钟，由后端维护，不能与客户端超时混为一谈。
  • 轮询间隔：应有限制，并可参考服务端 Retry-After；生产系统可使用退避与抖动。
  • 重试策略：只对已判定可以安全重试的操作执行；创建、支付、发送等应支持幂等键。
  • 未知结果：请求超时可能发生在服务器已提交事务之后；客户端不能据此判断事务没有发生。

13. FastAPI 生命周期（Lifespan）

13.1 为什么需要生命周期管理

某些资源需要在应用启动时创建，并被多个请求复用：

  • httpx.AsyncClient 及 HTTP 连接池。
  • SQLAlchemy AsyncEngine 及数据库连接池。
  • 本地推理模型、缓存客户端、监控资源。
  • 配置、索引句柄和需要显式释放的后台资源。

若每次请求都重新创建，通常会增加开销；若从不关闭，则可能泄漏套接字或数据库连接。

13.2 推荐方式：lifespan

python
from contextlib import asynccontextmanager
import httpx
from fastapi import FastAPI, Request

@asynccontextmanager
async def lifespan(app: FastAPI):
    client = httpx.AsyncClient(timeout=10.0)
    app.state.http_client = client
    try:
        yield  # 此期间处理请求
    finally:
        await client.aclose()

app = FastAPI(lifespan=lifespan)

@app.get('/upstream')
async def upstream(request: Request):
    client: httpx.AsyncClient = request.app.state.http_client
    resp = await client.get('https://example.com')
    return {'status': resp.status_code}

启动阶段执行 yield 之前的代码，关闭阶段执行之后的清理代码。需要注意，若同时传入 lifespan，传统 @app.on_event('startup') / shutdown 不再按原方式运行；新项目应优先采用 lifespan。

13.3 数据库 Engine 与 Session 的不同生命周期

  • Engine / Pool：通常在单个应用进程生命周期中创建一次，关闭时 dispose()。
  • Session：每次请求、事务或并发任务使用相互独立的 Session；不把同一个 AsyncSession 同时交给多个并发 Task。
  • 事务：要明确 commit()、rollback() 的时机；不能因为 HTTP 返回了 200，就假设外部系统或所有数据库写入都已原子成功。

13.4 服务停止与在途任务

常见的优雅停机顺序：停止接收新工作 → 等待在途请求 → 在期限内完成必要清理 → 取消无法继续的进程内任务 → 释放连接池 → 退出进程。

这部分职责既涉及 Uvicorn/ASGI Server，也涉及业务自己创建的 Task、Worker 和外部依赖。lifespan 的清理逻辑不能使内存任务在进程崩溃后自动恢复。

14. 中间件、依赖注入与异常处理

14.1 Middleware

中间件包围请求与响应处理过程，常用于：

  • 分配 X-Request-ID；
  • 日志、耗时计时；
  • CORS 与安全头；
  • 统一指标。

不要在中间件中无差别读取并保存敏感请求体。异常传播顺序可能受到中间件排列与异常处理器注册方式影响；具体行为应通过集成测试确认。

14.2 依赖注入 Depends

python
from fastapi import Depends

def get_settings():
    return {'mode': 'dev'}

@app.get('/settings')
async def settings(data: dict = Depends(get_settings)):
    return data

实际应用可通过依赖注入获取认证用户、业务 Service、数据库 Session。使用带 yield 的依赖时，依赖结束时机与响应、流式响应、背景任务的关系需要注意版本和 scope。不要把已经结束的请求 Session 交给独立后台 Worker 继续使用。

14.3 请求验证异常与内部异常不同

  • RequestValidationError：客户端输入不符合请求约定，可以转换为统一 422 响应。
  • HTTPException：业务接口显式表达的 HTTP 失败。
  • ResponseValidationError：服务器输出不符合声明约定，应作为内部问题处理。
  • 未捕获的其他异常：默认按内部错误处理；生产环境对客户端提供通用错误信息，在受保护日志中记录诊断信息。

不要把数据库堆栈、SQL、API Key 或内部文件路径放到错误响应里。

15. CORS、浏览器同源策略与联调

当前端在 http://localhost:5173，后端在 http://localhost:8000，端口不同意味着不同源。浏览器可能在跨域请求前发起 OPTIONS 预检。

python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=['http://localhost:5173'],
    allow_methods=['GET', 'POST'],
    allow_headers=['Content-Type', 'Authorization'],
)

请区分：

  • CORS 是浏览器跨域访问控制，不是服务器 API 的身份认证机制。
  • 服务端直接调用 API 通常不依赖浏览器 CORS 放行。
  • 预检请求失败时，浏览器 JS 可能拿不到后端真实返回内容。
  • 与 Cookie、凭证相关的跨域访问还涉及 allow_credentials、精确来源、SameSite、Secure 和 CSRF 策略。
  • 在安全敏感的服务中，不要随意设置允许任意来源并发送凭证。

16. 可观测性与 Request ID

生产问题常表现为“某位用户说请求失败，但开发人员无法复现”。推荐每次 HTTP 请求分配关联 ID：

text
X-Request-ID: a9c4...

同时记录：

json
{
  "request_id": "a9c4...",
  "route": "/v1/jobs",
  "http_status": 202,
  "duration_ms": 18,
  "job_id": "...",
  "error_code": null
}

这种日志能回答“哪次请求、经过哪个服务、返回了什么 HTTP 结果”，但不要将请求 ID 当作鉴权凭据。

与 Agent、模型调用或数据库操作联动时，还需要 trace_id、span_id、run_id 和 job_id，避免把不同层次 ID 混为一谈。

前端在异常页面展示可复制的请求 ID 有助于排查；日志要进行访问控制和敏感字段脱敏。

"""教学用 FastAPI HTTP 契约演示；任务仅存放进程内存，不可用于生产持久队列。"""
import asyncio
import logging
from contextlib import asynccontextmanager
from enum import Enum
from typing import Any
from uuid import uuid4

from fastapi import FastAPI, Path, Request, Response
from fastapi.exceptions import RequestValidationError
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import JSONResponse
from pydantic import BaseModel, ConfigDict, Field
from starlette.exceptions import HTTPException as StarletteHTTPException

logger = logging.getLogger(__name__)

class ApiError(BaseModel):
    code: str
    message: str
    retryable: bool = False
    details: list[dict[str, Any]] | None = None

class ErrorEnvelope(BaseModel):
    error: ApiError
    request_id: str

class MessageIn(BaseModel):
    model_config = ConfigDict(extra='forbid', strict=True)
    text: str = Field(min_length=1, max_length=200)

class MessageOut(BaseModel):
    message_id: str
    answer: str

class ItemOut(BaseModel):
    item_id: int
    title: str
    note: str | None = None

class JobCreate(BaseModel):
    model_config = ConfigDict(extra='forbid', strict=True)
    prompt: str = Field(min_length=1, max_length=200)
    delay_ms: int = Field(default=100, ge=10, le=1000)
    simulate_failure: bool = False

class JobState(str, Enum):
    PENDING = 'PENDING'
    RUNNING = 'RUNNING'
    SUCCEEDED = 'SUCCEEDED'
    FAILED = 'FAILED'

class JobReceipt(BaseModel):
    job_id: str
    state: JobState

class JobView(BaseModel):
    job_id: str
    state: JobState
    result: str | None = None
    error: ApiError | None = None

class DomainError(Exception):
    def __init__(self, status: int, code: str, message: str, retryable: bool = False):
        self.status = status
        self.code = code
        self.message = message
        self.retryable = retryable

class DemoStore:
    def __init__(self):
        self.jobs: dict[str, JobView] = {}
        self.tasks: set[asyncio.Task[None]] = set()
        self.accepting = True
        self.closed = False

async def process_job(store: DemoStore, job_id: str, prompt: str, delay_ms: int, fail: bool):
    job = store.jobs[job_id]
    job.state = JobState.RUNNING
    try:
        await asyncio.sleep(delay_ms / 1000)
        if fail:
            raise RuntimeError('教学模拟任务失败')
        job.state = JobState.SUCCEEDED
        job.result = f'处理完成：{prompt}'
    except asyncio.CancelledError:
        job.state = JobState.FAILED
        job.error = ApiError(code='SHUTDOWN_CANCELLED', message='服务关闭，任务被取消', retryable=True)
        raise
    except Exception:
        logger.exception('模拟后台任务失败 job_id=%s', job_id)
        job.state = JobState.FAILED
        job.error = ApiError(code='JOB_FAILED', message='任务执行失败', retryable=False)

@asynccontextmanager
async def lifespan(app: FastAPI):
    store = DemoStore()
    app.state.store = store
    try:
        yield
    finally:
        store.accepting = False
        for task in tuple(store.tasks):
            task.cancel()
        if store.tasks:
            await asyncio.gather(*tuple(store.tasks), return_exceptions=True)
        store.closed = True

app = FastAPI(title='FastAPI 请求响应与状态示例', lifespan=lifespan)
app.add_middleware(
    CORSMiddleware,
    allow_origins=['http://localhost:5173'],
    allow_methods=['GET', 'POST'],
    allow_headers=['Content-Type', 'Authorization'],
)

def error_response(request: Request, status: int, error: ApiError) -> JSONResponse:
    body = ErrorEnvelope(error=error, request_id=request.state.request_id)
    return JSONResponse(status_code=status, content=body.model_dump(mode='json'))

@app.middleware('http')
async def attach_request_id(request: Request, call_next):
    request.state.request_id = uuid4().hex
    try:
        response = await call_next(request)
    except Exception:
        logger.exception('Unhandled HTTP error request_id=%s', request.state.request_id)
        response = error_response(request, 500, ApiError(code='INTERNAL_ERROR', message='服务器内部错误', retryable=False))
    response.headers['X-Request-ID'] = request.state.request_id
    return response

@app.exception_handler(RequestValidationError)
async def validation_error(request: Request, exc: RequestValidationError):
    details = [
        {'path': '.'.join(str(part) for part in err['loc']), 'type': err['type']}
        for err in exc.errors()
    ]
    return error_response(request, 422, ApiError(
        code='VALIDATION_ERROR', message='请求数据不符合约定格式', details=details
    ))

@app.exception_handler(DomainError)
async def domain_error(request: Request, exc: DomainError):
    return error_response(request, exc.status, ApiError(
        code=exc.code, message=exc.message, retryable=exc.retryable
    ))

@app.exception_handler(StarletteHTTPException)
async def http_error(request: Request, exc: StarletteHTTPException):
    # 未知资源等路径层错误；避免把未受控 detail 原样返回
    code = 'NOT_FOUND' if exc.status_code == 404 else 'HTTP_ERROR'
    return error_response(request, exc.status_code, ApiError(
        code=code, message='资源不存在' if code == 'NOT_FOUND' else 'HTTP 请求失败'
    ))

@app.get('/health/live')
async def live():
    return {'alive': True}

@app.get('/health/ready')
async def ready(request: Request):
    if not request.app.state.store.accepting:
        return error_response(request, 503, ApiError(code='NOT_READY', message='不再接收新任务', retryable=True))
    return {'ready': True}

@app.post('/v1/messages', response_model=MessageOut, status_code=201)
async def create_message(payload: MessageIn):
    if payload.text == 'conflict':
        raise DomainError(409, 'BUSINESS_CONFLICT', '当前状态不允许此操作')
    # 多返回字段不会对外暴露（仍需业务层避免生成敏感值）
    return {'message_id': uuid4().hex, 'answer': f'已收到：{payload.text}', 'internal_secret': 'never-return'}

@app.get('/v1/items/{item_id}', response_model=ItemOut)
async def get_item(item_id: int = Path(ge=1), include_note: bool = False):
    if item_id != 1:
        raise DomainError(404, 'ITEM_NOT_FOUND', '未找到对应条目')
    return ItemOut(item_id=item_id, title='示例条目', note='附加说明' if include_note else None)

@app.post('/v1/jobs', response_model=JobReceipt, status_code=202)
async def create_job(payload: JobCreate, request: Request, response: Response):
    store: DemoStore = request.app.state.store
    if not store.accepting:
        raise DomainError(503, 'NOT_READY', '服务正在关闭', retryable=True)
    job_id = uuid4().hex
    store.jobs[job_id] = JobView(job_id=job_id, state=JobState.PENDING)
    task = asyncio.create_task(process_job(store, job_id, payload.prompt, payload.delay_ms, payload.simulate_failure))
    store.tasks.add(task)
    task.add_done_callback(store.tasks.discard)
    response.headers['Location'] = f'/v1/jobs/{job_id}'
    response.headers['Retry-After'] = '1'
    return JobReceipt(job_id=job_id, state=JobState.PENDING)

@app.get('/v1/jobs/{job_id}', response_model=JobView)
async def get_job(job_id: str, request: Request):
    store: DemoStore = request.app.state.store
    job = store.jobs.get(job_id)
    if job is None:
        raise DomainError(404, 'JOB_NOT_FOUND', '任务不存在')
    return job

18. 浏览器端 JavaScript 示例

下面示例不依赖 React：它把状态更新交给传入的 setState 函数，可以在 React、Vue 或其他前端体系中包装使用。

核心约束是：

  1. 首先检查网络层有无响应；
  2. 再检查 HTTP 状态码；
  3. 检查业务状态枚举；
  4. 有明确最终结果才显示“成功”；
  5. 客户端等待超时只能标为“结果未确定”，不能替服务器宣布任务失败；
  6. 对于页面主动取消和服务端仍在运行的任务，需要分离处理。
javascript
/** 浏览器端示例：将网络/HTTP/业务状态分开处理。 */
export class ApiFailure extends Error {
  constructor(code, message, { status = 0, retryable = false, requestId = null } = {}) {
    super(message);
    this.name = 'ApiFailure';
    this.code = code;
    this.status = status;
    this.retryable = retryable;
    this.requestId = requestId;
  }
}

export async function requestJson(url, options = {}) {
  let response;
  try {
    response = await fetch(url, options);
  } catch (error) {
    if (error?.name === 'AbortError') {
      throw new ApiFailure('REQUEST_CANCELLED', '请求已取消或达到客户端截止时间');
    }
    throw new ApiFailure('NETWORK_ERROR', '网络连接失败，请检查网络', { retryable: true });
  }

  const requestId = response.headers.get('X-Request-ID');
  const contentType = response.headers.get('content-type') || '';
  let body;
  try {
    body = response.status === 204 ? null
      : contentType.includes('application/json')
        ? await response.json()
        : await response.text();
  } catch {
    throw new ApiFailure('INVALID_RESPONSE', '服务器返回的数据无法解析', {
      status: response.status, requestId,
    });
  }

  if (!response.ok) {
    const err = body && typeof body === 'object' ? body.error : null;
    throw new ApiFailure(err?.code || 'HTTP_ERROR', err?.message || `HTTP ${response.status}`, {
      status: response.status, retryable: Boolean(err?.retryable), requestId,
    });
  }
  return { httpStatus: response.status, body, requestId };
}

function wait(ms, signal) {
  return new Promise((resolve, reject) => {
    if (signal?.aborted) {
      reject(new DOMException('已取消', 'AbortError'));
      return;
    }
    const timeout = setTimeout(() => { cleanup(); resolve(); }, ms);
    function onAbort() { clearTimeout(timeout); cleanup(); reject(new DOMException('已取消', 'AbortError')); }
    function cleanup() { signal?.removeEventListener('abort', onAbort); }
    signal?.addEventListener('abort', onAbort, { once: true });
  });
}

/** setState 接收 {phase, ...}；signal 允许页面离开时取消前端等待。 */
export async function submitAndTrack(prompt, setState, { signal, maxWaitMs = 15_000 } = {}) {
  const started = Date.now();
  setState({ phase: 'submitting' });
  try {
    const receipt = await requestJson('/v1/jobs', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ prompt, delay_ms: 100 }),
      signal,
    });
    if (receipt.httpStatus !== 202) {
      throw new ApiFailure('UNEXPECTED_STATUS', '未收到预期的任务接收响应');
    }
    const jobId = receipt.body.job_id;
    setState({ phase: 'processing', jobId });

    while (Date.now() - started < maxWaitMs) {
      if (signal?.aborted) throw new ApiFailure('REQUEST_CANCELLED', '前端停止等待');
      const { body: job } = await requestJson(`/v1/jobs/${encodeURIComponent(jobId)}`, { signal });
      if (job.state === 'SUCCEEDED') {
        setState({ phase: 'succeeded', result: job.result, jobId });
        return;
      }
      if (job.state === 'FAILED') {
        setState({ phase: 'failed', code: job.error?.code || 'JOB_FAILED', jobId });
        return;
      }
      await wait(200, signal);
    }
    // 前端等待超时不表示后端任务失败；保留任务 ID 供稍后查询。
    setState({ phase: 'unknown', reason: 'CLIENT_WAIT_TIMEOUT', jobId });
  } catch (error) {
    const code = error?.name === 'AbortError' ? 'REQUEST_CANCELLED'
      : error instanceof ApiFailure ? error.code : 'UNKNOWN_ERROR';
    setState({ phase: 'failed', code });
  }
}

18.1 JavaScript 为什么需要再检查业务状态

假设轮询成功拿到了 HTTP 200，返回如下：

json
{"job_id":"123", "state":"FAILED", "error":{"code":"JOB_FAILED"}}

此时 Fetch 是成功完成一次 HTTP 查询，response.ok === true。但业务本身失败。前端必须读取 state 并展示失败，而不是执行 if (response.ok) showSuccess()。

18.2 前端真实项目还需要补充什么

  • 为 GET 轮询设置合理重试间隔、总重试预算以及上限。
  • 对提交重复触发实施按钮禁用或幂等键，但按钮禁用本身不是服务端幂等保证。
  • 用稳定的 job_id 恢复页面或刷新之后的查询。
  • 组件卸载或页面切换时，使用 AbortController 中止前端请求，并处理过期请求覆盖新 UI 状态。
  • 将 401 与 403、409、422 等错误分别映射到适当界面。
  • 对长任务优先展示实际服务端进度，不要用伪进度条冒充真实任务完成率。
  • 在更正式的 SDK 里，解析响应后还可以使用运行时 Schema 校验，避免后端契约变化导致前端异常。

def wait_for_job(c, job_id, terminal, timeout=2):
    deadline = time.monotonic() + timeout
    while time.monotonic() < deadline:
        r = c.get('/v1/jobs/' + job_id)
        assert r.status_code == 200
        job = r.json()
        if job['state'] in terminal:
            return job
        time.sleep(.015)
    raise AssertionError('job did not finish')

20. 常见错误、成因和排查

20.1 422 总在出现，但感觉输入“明明正确”

检查：

  1. 请求是 application/json，还是把 JSON 字符串当普通文本发送？
  2. 字段是否真的存在，名字是否大小写一致？
  3. 字段是 None 还是根本没有提交？
  4. 严格模式是否拒绝了字符串形式的数字？
  5. 额外字段是否被 extra='forbid' 拒绝？
  6. 错误定位是 body、path、query 还是 header？

422 不应一律通过“放宽 Schema”解决，先确认前端的数据形态与 API 契约是否一致。

20.2 后端返回 200，前端却认为失败

可能原因：

  • 业务状态实际为 FAILED 或未完成；
  • 响应体字段与前端 TypeScript 类型定义不一致；
  • 前端 response.json() 解析失败；
  • 组件状态被过期请求覆盖；
  • 前端把 202 当作最终成功。

检查 Network 面板的 HTTP 状态和响应体，结合 X-Request-ID 定位对应服务端日志。

20.3 前端提示 Network Error，但服务器有日志

可能是 CORS 响应头不匹配、预检失败、代理断开或浏览器安全策略阻止了 JavaScript 读取响应。需要检查浏览器 Console、Network 预检、代理和服务端日志；不能只检查业务路由是否执行。

20.4 服务启动后立刻抛 AttributeError：没有 app.state.xxx

检查：

  • 是否正确传入并运行了 lifespan；
  • 测试中是否进入 TestClient 上下文；
  • 是否在模块导入时错误访问了只在启动后创建的资源；
  • 多个 Worker 是否各自拥有独立资源状态。

20.5 流式响应或后台任务偶尔中断

可能是客户端断开、ASGI 取消传播、服务器关闭期限、代理空闲超时或者资源已被提前释放。进程内 Task 并不持久；需要强可靠任务时，应转到任务持久化章节设计独立队列和 Worker。

20.6 所有错误都统一 except Exception: return {"success": false}

这种写法会丢失 HTTP 状态、堆栈记录、类型信息与恢复语义，甚至错误地把 500 变成 200。推荐按领域错误、请求验证错误和未知内部错误分别处理。

20.7 测试通过，但是生产环境仍然出错

测试断言是其覆盖范围内的证据，不是生产保障。TestClient 的进程内测试无法自动覆盖真实浏览器 CORS、反向代理、TLS、多 Worker、负载均衡、数据库事务、外部依赖或长期稳定性。

21. 延伸知识与官方参考资料

21.1 当前知识点与后续模块的关系

  • SQL 与数据库：接口成功不等于事务成功；需要了解事务隔离、唯一约束与连接池。
  • Redis 缓存：缓存命中是性能行为，不等于持久化业务状态。
  • 后台任务：202 之后的持久化状态、Worker、重试与幂等需要单独学习。
  • AI 模型调用：模型返回可能是流式的，结束事件、取消和部分输出要有额外协议。
  • 前端工程：React/Vue 负责展示、交互与状态，必须根据服务器真实契约行事。
  • Agent 工具执行：模型提出操作不等于已获权限；服务端认证与授权仍是最终边界。

结论

FastAPI 的请求/响应模型主要回答的是：一次 HTTP 调用接受什么、返回什么、输入输出有哪些结构约束。

HTTP 错误机制回答的是：这次请求为什么无法按约定完成。

业务状态机回答的是：已经启动的真实业务任务目前处于什么阶段，以及是否最终成功。

lifespan 回答的是：服务在启动与关闭时如何准备和释放资源。

前端必须把这四层分开处理，才能做到“失败说得清楚、处理中不会假装成功、真正完成后才显示成功”。
