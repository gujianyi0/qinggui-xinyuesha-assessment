RAG、来源引用与知识更新（二）：分块大小、重叠、Top-K、元数据过滤与分层故障定位

对应学习目标：分块大小、重叠、Top-K 和元数据过滤如何影响结果；能区分资料没收进来、检索没找到和模型答错。

文档性质：知识性技术手册。示例以游戏规则 RAG 为背景，但原理同样适用于企业知识库、政策问答、客服与文档检索。

技术范围：文档入库、Chunking、Embedding 检索、PostgreSQL/pgvector、查询过滤、Reranking、上下文选择、可观测性与故障归因。更新核对日期：2026-11-11。

01. 本节的核心问题：RAG 是一条有状态的证据传递链

一次 RAG 回答并不等于“把问题交给模型”。它至少经历：

text
原始资料
  ↓ 解析（extract/parse）
文本、表格、段落、来源位置
  ↓ 分块（chunking）
可检索片段 + 文档 ID + 版本 + 权限元数据
  ↓ Embedding / 索引
稀疏或稠密检索数据结构
  ↓ 查询与元数据过滤
合法且符合版本的候选片段
  ↓ 排序、Top-K、重排、去重
用于生成回答的候选证据
  ↓ 上下文组装（Token 预算）
模型实际接收到的证据
  ↓ 生成、引用核验
最终回答

这里至少有三个性质完全不同的失败：

  1. 资料没有进入可检索系统：原文件未导入、解析失败、分块遗漏、Embedding 或索引未完成。即使模型能力完美，也无法根据不存在的证据回答。
  2. 资料已经进入系统，但没有被正确检索或送入上下文：过滤错误、检索语义偏差、Top-K 太小、近似索引召回不足、重排误删、上下文裁剪等。
  3. 正确证据已经进入模型实际输入，但模型输出仍然错误：数值抄错、忽略限定条件、混淆版本、推断超出证据或引用不支持结论。

注意“资料导入”与“已可检索”之间还存在中间状态：文件已保存，但其文本可能尚未解析；文档文本已解析，但还没有完成索引。运维上必须分别记录各阶段状态，不能只使用一个模糊的 imported=true。

02. 理解 Chunk：它是检索单元，不一定是原始文档的自然段落

**Chunk（文档片段）**是检索、Embedding 和提供证据时使用的基本文本单元。常见实现把一份文档切成多个 Chunk，每个 Chunk 关联父文档和位置元数据。分块策略会改变：

  • 检索粒度：一次检索命中的是一小条事实，还是一整个大章节；
  • 语义完整性：定义、适用条件和例外情况是否出现在同一片段；
  • 索引规模：需要向量化和存储多少个片段；
  • 检索排序：文本混合多个主题时，Embedding 表征可能不够聚焦；
  • 生成成本：传入模型的总文本量；
  • 引用精度：能否把答案关联到具体段落，而非宽泛章节。

Chunk 不是越短越好，也不是越长越好。它要在能够独立表达事实与足够聚焦便于检索之间取得平衡。不同文档可能需要不同策略，例如 API 文档优先按标题和代码块切分，游戏规则优先保留条款与例外，财务数据优先保留表头及单位。

2.1 Chunk 大小的计量单位

  • 字符数：按 Unicode 字符串长度近似控制。实现简单，但不能等同于模型 Token。
  • 词数：适合有稳定分词边界的语言，但对中文、代码、混合文本要特别小心。
  • Token 数：使用指定 Tokenizer 计数。更容易与 Embedding 模型或 LLM 的上下文限制对应。
  • 语义单元：标题、段落、句子、列表、表格或 AST 节点；长度可变。

因此 chunk_size=512 的含义必须结合框架与分块器明确确认：512 Token 不是 512 个汉字。

2.2 Chunk 不宜切断哪些关系

对于一条规则：

角色 A 的“火焰术”消耗 3 点法力；但在沉默状态下不可释放。本规则适用于 v2.1 及以上版本。

如果切成三个互相独立的片段：

  • 火焰术消耗 3 点法力
  • 沉默状态下不可释放
  • 适用于 v2.1 及以上

那么模型可能只检索第一条，并给出无条件允许释放的错误回答。更合理的做法是让单个规则原子单元包含主要条件、例外和版本；必要时把父标题（如“v2.1 / 法术规则”）嵌入每个子块。

03. Chunk Size 过小与过大分别会发生什么

维度 块过小 块过大
语义完整性 容易切断条件、单位和指代 上下文通常更完整
检索聚焦性 细粒度信息更容易被区分 多个主题混合，向量可能失焦
索引体量 Chunk 数量增加 Chunk 数量减少
引用精度 可精确到小片段，但可能缺上下文 引用定位宽泛，需要二次精确定位
生成上下文 可灵活组合不同证据 每个结果占用更多 Token
嵌入开销 调用次数/片段元数据可能增加 单片段文本更多，注意模型输入上限
关键风险 信息碎片化 信息稀释

这只是一般趋势，实际质量受文档类型、分块器、Embedding 模型、检索器和问题分布影响。检索效果必须通过样例集测量，不能从 Chunk Size 单独推断。

3.1 示例：短块和长块的差异

用户问：角色 A 在沉默状态下能否释放火焰术？

  • 50 Token 块可能检索到“消耗 3 法力”，但丢失“沉默禁止”的限制。
  • 200 Token 的规则块若包含两个条件，能够直接支持正确回答。
  • 2000 Token 大块包含十几名角色和多种规则时，“沉默条件”可能被其他内容稀释，甚至检索不到。

工程含义：对有强依赖关系的内容，应优先以逻辑边界分块，而非机械地追求固定字数。

3.2 一个可解释的初始实验范围

对普通中文知识文档，可以试验例如 256 / 512 / 1024 Token 等不同块大小，适当加入语义边界保护；它们是待评测候选值，而不是行业通用最佳参数。对规则条款、FAQ、代码片段等结构化资料，应优先按条目、标题和作用域切块。

04. Chunk Overlap：为什么相邻片段需要重叠

Overlap（重叠）：相邻 Chunk 之间重复保留一部分文本，降低重要信息刚好落在切分边界时被拆散的概率。

假设原始 Token 序列为：

text
A B C D E F G H I J K L

chunk_size=5, overlap=2 时：

text
Chunk 1: A B C D E
Chunk 2:       D E F G H
Chunk 3:             G H I J K
Chunk 4:                   J K L

在最简单的固定滑动窗口分块中，相邻窗口的步长：

[ S = C - O ]

其中 C 为块长度，O 为重叠长度，要求 0 ≤ O < C。对于长度 L 的序列，当 L > C 时：

[ N = 1 + \left\lceil\frac{L-C}{C-O}\right\rceil ]

这里 N 是分块数；L ≤ C 时 N=1。公式适用于固定步长的完整覆盖滑动窗口，实际按段落或语义边界调整的分块器不一定严格遵循该公式。

例子：L=1000，C=300，O=60，则步长 S=240，N=1+ceil(700/240)=4。最后一个块往往不足 300 Token。

4.1 Overlap 带来的好处

  1. 保留跨边界的前后语义；
  2. 缓解代词、条件和结论被分开的情况；
  3. 允许同一个关键信息从多个相邻片段命中。

4.2 Overlap 的代价

  1. 重复 Embedding 与索引体量：同一段文字被多次表示与存储。
  2. 检索结果冗余：Top-K 可能大部分来自同一段附近，挤占其他证据。
  3. 生成 Token 增加：不去重直接拼接会重复消费上下文。
  4. 结果相关性偏差：重复内容可能提高同一文档在排序中的存在感，但不代表增加了独立证据。
  5. 更新代价增加：修改源文档时，受影响的相邻块可能需要一起重新索引。

一般应优先通过语义边界分块、父子块检索、相邻块扩展、去重减少对大比例 Overlap 的依赖。

4.3 为什么 Overlap 不能修复所有错误

重叠只能减少相邻边界问题。它无法修复：OCR 识别错误、文档缺页、版本缺失、复杂表格被拆乱、embedding 质量差、错误的权限过滤或生成阶段的事实幻觉。

05. Overlap 的选择及重复证据处理

常见实验会比较：0% / 10% / 20% 重叠比例，但必须结合原始内容结构和评测结果确定。没有适用于所有资料的最优重叠率。

5.1 结果去重的层次

  • 完全重复：相同 document_id + start_offset + end_offset，可直接合并。
  • 相邻高度重合：检索后合并重叠范围，避免重复输入模型。
  • 同一事实的多个副本：例如转存规则和官方源规则，不应把副本误当成多份独立支持证据。
  • 同一事实的不同版本：不能仅因为文本相似就合并，必须保留版本差异。

5.2 Parent–Child Retrieval

常见改进是对较小的子 Chunk 建立索引，用它进行精确检索；命中后再向上取其父段落或父章节，向模型提供更完整上下文。这将检索粒度与生成证据粒度解耦。

但父块扩展必须受版本、权限、长度预算限制。不能因为子块命中就把整篇未经授权的父文档发送给模型。

06. Top-K 究竟控制了什么

Top-K通常指按照某个排序标准返回前 K 个候选，但在完整 RAG 管线里可能有多个不同的 K：

text
向量/关键词检索：candidate_top_k = 40
      ↓
混合检索合并与去重：40 个候选
      ↓
Reranker：rerank_top_n = 10
      ↓
上下文选择：context_top_n = 4（并受 Token 预算限制）
      ↓
模型回答

不能把检索器的 top_k、重排器的 top_n、实际传给模型的片段数混为一谈。

6.1 K 太小

  • 更快、输入更短；
  • 但可能漏掉排位靠后的关键证据；
  • 多跳问题可能缺少另一条必要规则；
  • 与当前问题相关但排名不够高的来源无法进入上下文。

6.2 K 太大

  • 初始召回机会通常提高，但会带来更多无关片段；
  • 如果全部传给 LLM，Token 和延迟增加；
  • 同类或重叠片段可能占满上下文；
  • 旧版本和相互冲突资料可能造成生成混淆；
  • 增加 K 并不能修复索引缺失或错误过滤。

严格地说：在同一静态排序列表、过滤条件不变、没有阈值和其他截断的前提下，扩大 K 不会让原先已出现的候选“消失”；但一旦涉及近似检索、重排、上下文预算或特定 API，最终提供给模型的证据集合可能发生变化。

6.3 数值案例

假设排序结果：

排名 Chunk 内容 是否为正确依据
1 A 游戏背景介绍 否
2 B 角色基本介绍 否
3 C 火焰术法力消耗规则 是
4 D 旧版本技能规则 否
5 E 当前版本沉默限制 是

问题是“当前版本沉默时能否释放火焰术，消耗多少法力？”

  • Top-K=2：两条必要依据都没有进入；
  • Top-K=3：只得到消耗数值，缺少沉默限制；
  • Top-K=5：有可能得到完整证据，但还需要版本过滤和上下文筛选。

对于这个问题，两条规则是联合充分证据。只看是否命中一条相关 Chunk，会高估实际可回答性。

07. 元数据（Metadata）是什么

元数据不是文档正文，而是描述文档或 Chunk 的结构化属性。例如：

json
{
  "tenant_id": "tenant-42",
  "document_id": "rule-2026-v2",
  "chunk_id": "rule-2026-v2:section-3:part-2",
  "title": "角色 A / 火焰术",
  "version": "2.1",
  "language": "zh-CN",
  "source_type": "official_rule",
  "status": "published",
  "effective_from": "2026-10-01T00:00:00Z",
  "effective_to": null,
  "section_path": ["角色", "角色 A", "技能"],
  "embedding_model": "embedding-model-v3",
  "content_hash": "sha256:..."
}

其中字段名和格式仅为推荐示例，不是通用协议。

元数据最重要的作用是：把语义相近与业务允许且真实适用分开。即使 v1 和 v2 的技能描述相似，也不代表可以把它们混在一起回答。

08. 元数据过滤的五类核心场景

8.1 权限过滤

根据经过身份认证的租户、用户、角色、资源 ACL 排除无权访问的资料。不可由模型自行决定是否绕过，也不能仅凭用户在问题里写的 tenant_id 判断身份。

8.2 版本过滤

游戏规则、API 文档、产品政策往往同时存在多个版本。必须区分：

  • source_version：源文档版本；
  • effective_version：问题所在业务版本；
  • index_version：索引的构建版本；
  • embedding_model_version：向量生成模型版本。

这些不是同一概念。重新建立索引不意味着业务规则升级。

8.3 发布时间与生效时间

一条规则的发布时间和正式生效时间可能不同。用户问历史时点的问题时，要按相关时间区间筛选，且明确时区和闭开区间（如 effective_from <= time < effective_to）。

8.4 资料类型和可信等级

可按官方公告、玩家攻略、内部反馈等类型过滤或排序。来源可信度不是指令权限；即使来源可靠，文档正文中的命令也不具有 Agent 执行权。

8.5 文档状态

常见状态：draft、published、deprecated、deleted、indexing。已删除或已撤回资料即使残留向量索引，也不应继续出现在普通查询中。

09. 过滤顺序：Pre-filter 与 Post-filter 的区别

概念上可以分为：

先过滤后检索（Pre-filter）：先限制符合权限与版本的候选，再在允许的范围内排序。这是业务语义上的理想条件，但底层数据库是否如此执行取决于查询计划和索引结构。

先近似扫描后过滤（Post-filter）：向量索引先产生候选，再把不符合条件的候选剔除。如果符合过滤条件的记录占比小，最终返回结果可能少于 K 条。

9.1 pgvector 的实际差异

pgvector 官方说明：普通精确最近邻查询能够得到完整候选中的精确排序；HNSW 和 IVFFlat 是近似索引，会以一定召回率换取查询效率。使用近似索引时，过滤条件可能在索引扫描结果上应用，导致返回不足 K 条。

针对这种问题可评估：

  1. 调整 hnsw.ef_search；
  2. 在适合的版本和场景中使用 iterative index scan；
  3. 对少量常见过滤值建立部分 HNSW 索引；
  4. 使用 PostgreSQL 分区，将数据限制在业务分区内；
  5. 在选择性高的条件下先利用 B-tree 等关系索引，再进行精确向量排序；
  6. 对同一固定测试集比较近似与精确检索的 Recall@K。

在 pgvector 0.8.0+ 可使用例如：

sql
SET hnsw.iterative_scan = strict_order;

但扫描仍受到参数与资源限制，不能保证任何查询都恰好返回 K 条。

安全注意：即使基础 SQL 的 WHERE tenant_id = ... 由数据库执行，仍必须在应用或数据库层实现真正的对象授权。不能把向量过滤器替代身份认证与资源权限检查。

10. Chunk Size、Overlap、Top-K 与过滤参数是耦合关系

它们不能脱离彼此独立优化。

  • Chunk 变小：相同文档被切成更多片段；要覆盖同等原文范围，可能需要更大的 Top-K，或者采用父子块扩展。
  • Overlap 增大：相邻块更加相似；需要去重、最大同源块数限制，否则 Top-K 容易被重复内容占据。
  • Top-K 增大：候选召回可能改善，但 Reranker、上下文截断和成本必须同步调整。
  • Metadata 过滤严格：减少错误版本与越权片段，但也可能暴露源数据质量不足、索引分区不均、ANN 后过滤不足等问题。
  • Index ANN 参数变化：候选集合可能改变，导致在同样 Top-K 下出现不同命中情况。

一个常用实验矩阵如下（只作为实验配置，不代表默认推荐）：

方案 Chunk Size Overlap 候选 Top-K 重排后上限
A 256 Token 0 20 5
B 512 Token 64 20 5
C 512 Token 64 40 5
D 1024 Token 128 40 5

对每个方案都应执行相同评测问题，保持数据快照、Embedding 版本、查询逻辑和权限范围可比较；如果不同方案需要重建索引，应明确记录它们不是相同的索引快照。

11. 三种错误的严格定义与边界

11.1 资料未收进来（Ingestion / Indexing Failure）

问题所需的可信资料在原始知识源中确实存在，但数据链路中丢失或不可检索。

常见情况：

  • 文件未被扫描到；
  • 下载失败或权限受限；
  • PDF 某页抽取为空，表格列关系被破坏；
  • 分块器跳过了附录、标题、图表；
  • Embedding 请求失败或索引队列没有消费；
  • 索引构建任务失败，但 UI 显示“上传成功”；
  • 向量索引仍指向旧版数据。

判定证据：原始文件清单、内容哈希、解析产物、Chunk 数量、Embedding 数量、索引版本、导入任务状态。

修复方向：重新抽取、重分块、补充缺失页、重建索引、修复导入状态与告警。

11.2 检索未找到（Retrieval Failure）

需要的证据已经成功索引且符合查询权限/版本条件，但没有进入最终可供模型读取的证据集合。

常见情况：

  • Query 用词与文档术语偏差较大；
  • Top-K 过小；
  • 过滤条件错误排除正确版本；
  • ANN 召回不足；
  • Reranker 错排；
  • 相邻重复 Chunk 挤占名额；
  • Context Builder 将检索到的正确 Chunk 裁掉。

严格区分：检索器没有命中与检索到了但上下文未包含。二者都可能导致模型看不到证据，但优化位置不同。

修复方向：查询改写、术语扩展、Hybrid Search、参数评测、版本过滤修复、重排优化、去重、上下文预算调整。

11.3 模型答错（Generation / Grounding Failure）

正确而充分的证据已经进入模型实际接收到的上下文，模型仍给出与证据不符或缺乏依据的回答。

常见情况：

  • 数值、条件或否定词理解错误；
  • 把旧规则与现行规则合并；
  • 将示例内容误当成通用规定；
  • 引用正确文件，但引用段落不支持结论；
  • 明明资料不足，却编造一个确定答案。

修复方向：结构化提取和程序计算、明确引用约束、答案验证、困难样例评测、模型或提示词对比、降低无依据推断。

另有第四种情况：资料本身错误或过期。 即使检索和生成完全忠实，也可能产生客观上错误的回答。应单独记录 SOURCE_QUALITY_ERROR，由数据治理修复，不能将它完全归咎于生成模型。

在查询时，先通过经过认证的租户、业务版本与状态限制合法资料：

SELECT c.id, c.content,
       c.embedding <=> '[0.2,0.3,0.4]'::vector AS cosine_distance
FROM document_chunks AS c
JOIN source_documents AS d ON d.id = c.document_id
WHERE d.tenant_id = :authenticated_tenant
  AND d.version = :requested_version
  AND d.status = 'active'

ORDER BY c.embedding <=> '[0.2,0.3,0.4]'::vector
LIMIT 5;

16. 评估检索质量：先看证据能否找到，再看模型能否回答

16.1 Recall@K

设针对某查询的黄金证据集合为 G，前 K 个检索结果集合为 R_K：

[ Recall@K = \frac{|G \cap R_K|}{|G|} ]

如果问题必须联合引用两段规则，G 有 2 条而只找回 1 条，Recall@K = 0.5；虽然有一条相关结果，但仍不足以支持完整答案。

16.2 Precision@K

[ Precision@K = \frac{|G \cap R_K|}{K} ]

这里使用二元相关性作为简化定义。更真实的检索系统可采用等级相关性指标（如 nDCG），并考虑一条 Chunk 是否完整支持某个事实。

16.3 Evidence Coverage / Answerability

对于多项事实要求，使用：

[ Coverage = \frac{已被检索证据覆盖的必要事实数}{全部必要事实数} ]

但有的任务是“所有条件必须同时成立”，单纯平均覆盖率并不足以表示最终是否可回答，应另加 answerable=true/false 判断。

16.4 生成质量指标

  • Faithfulness / Groundedness：答案是否被提供的证据支持；
  • Answer Correctness：答案是否与独立真值一致；
  • Citation Support：引用是否支持其对应结论；
  • Abstention Correctness：信息不足时是否恰当拒绝猜测。

不要把“返回的相似度分数很高”直接解释成“模型答案一定可信”。向量相似度并不是经过校准的事实正确概率。

17. 固定样例的参数比较方法

为了知道一次参数修改的收益与代价，固定以下条件：

  • 同一批问题、黄金来源及必要事实；
  • 同一份原始资料快照与权限范围；
  • 同一模型和 Embedding 版本（除非本次实验专门研究其差异）；
  • 记录被改变的参数：Chunk Size、Overlap、Top-K、过滤表达式等；
  • 记录检索延迟、索引规模、召回、上下文 Token、最终正确率、引用支持率。

建议生成配对评测报表：

指标 配置 A 配置 B 解释
Recall@5 实测 实测 正确证据进入 Top-5 的程度
Answerability 实测 实测 是否获得完整必要证据
Citation Support 实测 实测 引用是否支持陈述
P95 检索延迟 实测 实测 延迟风险

索引片段数 实测 实测 存储和重建成本

上表不填造假的数值。任何“某个参数一定提高准确率”的结论都必须有同一评测集的实证支持。

18. 常见误区与必要澄清

误区 1：Chunk 越小，检索越精确。 小块可能更聚焦，但也可能丢失条件、标题与例外。

误区 2：Overlap 越大越可靠。 重叠过大造成冗余，还可能降低有效证据多样性。

误区 3：Top-K=10 就一定返回 10 条。 过滤、阈值、数据不足和 ANN 行为均可能使结果少于 10 条。

误区 4：增加 K 能解决资料缺失。 不存在于索引中的文本无法通过增大 K 找回。

误区 5：有引用就说明回答真实。 引用必须确实存在、版本正确，并支持对应结论。

误区 6：元数据过滤只是提高准确率。 权限过滤还涉及信息安全，是不可跳过的后端控制。

误区 7：提高 Embedding 相似度阈值一定更好。 阈值可能降低噪音，也可能增加漏检；还需确认分数方向与校准方式（距离越小越近，或相似度越大越近）。

误区 8：文档导入成功代表检索就绪。 原文件保存、解析、Chunk、Embedding、索引提交属于不同阶段。

误区 9：模型答错就应该改 Prompt。 若证据未到达模型，先修复检索和上下文组装。

误区 10：对外返回详细故障阶段有助排查。 内部诊断要详细，但对未授权用户应避免泄露私有资料是否存在、其版本或具体位置。

19. 延伸：改变分块参数为什么要重建索引

对于普通的文本 Embedding RAG，向量由每个 Chunk 的文本计算得到：

[ \mathbf{e}_i = Embed(chunk_i) ]

当 Chunk Size 或 Overlap 改变时，chunk_i 的边界与内容通常也发生变化。因此：

  • Chunk ID 和文本哈希需要重新计算；
  • Embedding 应按新 Chunk 重新生成；
  • 旧索引需要更新、替换或使用版本化索引切换；
  • 来源位置元数据与引用索引要重新验证；
  • 对外查询应避免同时混用不兼容的老、新索引版本。

一个稳妥的更新模式是：构建新索引 → 固定样例验证 → 进行版本切换 → 保留必要的回滚机制 → 清理旧索引。

例外：如果只改变在线检索的 Top-K，不改变向量和索引结构，通常无需重新生成 Embedding；改变元数据过滤的查询条件也不必天然重算向量，但可能需要修复或迁移元数据索引。

20. 知识要点总结

  1. Chunk Size决定检索文本单元的粒度与语义完整性。
  2. Overlap减少边界割裂，但增加重复、索引和上下文开销。
  3. Top-K控制特定检索阶段的候选数量，不能替代证据完整性判断。
  4. Metadata Filtering决定哪些候选具有业务资格；权限过滤还承担安全边界责任。
  5. 同一个 RAG 错误可能发生在原始资料、解析、索引、检索、重排、上下文或生成阶段。
  6. 先检查证据有没有入库，再检查有没有被检索和送到模型，最后检查模型是否忠实使用证据。
  7. 每一类问题都应留下可定位、可复现的版本和执行记录。
  8. 参数优化应以固定样例、黄金证据、延迟和成本的共同度量为依据。

附录 A：离线可执行的故障归因示例

下面是一段确定性、教学性质的 Python 程序。它不调用真实 Embedding 模型或向量数据库，而是通过明确的词项集合模拟候选相关性，以验证分层定位逻辑。不得把这些离线测试结果误当作真实模型 RAG 的检索准确率。

将以下代码复制为 diagnose.py，使用 Python 3.11+ 执行 python diagnose.py。

python
"""RAG 三类错误的可执行、确定性最小演示（不调用模型和向量数据库）。"""
from __future__ import annotations
from dataclasses import dataclass, replace
from enum import StrEnum

class Stage(StrEnum):
    SUCCESS = 'SUCCESS'
    ACCESS_DENIED = 'ACCESS_DENIED'
    SOURCE_NOT_INGESTED = 'SOURCE_NOT_INGESTED'
    EXTRACTION_OR_CHUNKING_FAILED = 'EXTRACTION_OR_CHUNKING_FAILED'
    INDEX_NOT_READY = 'INDEX_NOT_READY'
    FILTER_EXCLUDED = 'FILTER_EXCLUDED'
    RETRIEVAL_MISS = 'RETRIEVAL_MISS'
    GENERATION_ERROR = 'GENERATION_ERROR'

@dataclass(frozen=True)
class Document:
    id: str
    tenant_id: str
    version: str
    status: str = 'active'

@dataclass(frozen=True)
class Chunk:
    id: str
    document_id: str
    terms: frozenset[str]
    text: str
    indexed: bool = True

@dataclass(frozen=True)
class Result:
    stage: Stage
    retrieved_ids: tuple[str, ...] = ()
    detail: str = ''


def diagnose(
    docs: list[Document], chunks: list[Chunk], *,
    tenant_id: str, source_doc_id: str, version: str,
    gold_chunk_id: str, query_terms: frozenset[str], top_k: int,
    generated_answer: str, expected_answer: str,
) -> Result:
    if top_k < 1:
        raise ValueError('top_k must be >= 1')
    owned = next((d for d in docs if d.id == source_doc_id and d.tenant_id == tenant_id), None)
    if owned is None:
        if any(d.id == source_doc_id for d in docs):
            return Result(Stage.ACCESS_DENIED, detail='source belongs to another tenant')
        return Result(Stage.SOURCE_NOT_INGESTED)

    source_chunks = [c for c in chunks if c.document_id == source_doc_id]
    if not source_chunks:
        return Result(Stage.EXTRACTION_OR_CHUNKING_FAILED)
    if not any(c.indexed for c in source_chunks):
        return Result(Stage.INDEX_NOT_READY)

    # 先依据已认证租户、版本与启用状态限定可见候选；不能先全库选 Top-K 再做权限过滤。
    allowed_docs = {d.id for d in docs if d.tenant_id == tenant_id and d.version == version and d.status == 'active'}
    eligible = [c for c in chunks if c.document_id in allowed_docs and c.indexed]
    if gold_chunk_id not in {c.id for c in eligible}:
        return Result(Stage.FILTER_EXCLUDED)

    def score(c: Chunk) -> int:
        return len(query_terms & c.terms)

    ranked = sorted((c for c in eligible if score(c) > 0), key=lambda c: (-score(c), c.id))
    retrieved = tuple(c.id for c in ranked[:top_k])
    if gold_chunk_id not in retrieved:
        return Result(Stage.RETRIEVAL_MISS, retrieved)
    if generated_answer != expected_answer:
        return Result(Stage.GENERATION_ERROR, retrieved)
    return Result(Stage.SUCCESS, retrieved)


def fixture():
    docs = [Document('rule-v2', 'tenant-A', 'v2'), Document('decoy', 'tenant-A', 'v2')]
    chunks = [
        Chunk('support', 'rule-v2', frozenset({'火焰术'}), '火焰术消耗 3 法力。'),
        Chunk('decoy-1', 'decoy', frozenset({'火焰术', '法力'}), '火焰术的法力相关背景说明。'),
    ]
    args = dict(tenant_id='tenant-A', source_doc_id='rule-v2', version='v2',
                gold_chunk_id='support', query_terms=frozenset({'火焰术','法力'}),
                top_k=2, generated_answer='3', expected_answer='3')
    return docs, chunks, args


if __name__ == '__main__':
    import unittest

    class Tests(unittest.TestCase):
        def setUp(self):
            self.docs, self.chunks, self.args = fixture()
        def check(self, expected, docs=None, chunks=None, **kw):
            params = self.args | kw
            result = diagnose(self.docs if docs is None else docs,
                              self.chunks if chunks is None else chunks, **params)
            self.assertEqual(result.stage, expected)
            return result
        def test_success(self): self.check(Stage.SUCCESS)
        def test_source_absent(self): self.check(Stage.SOURCE_NOT_INGESTED, docs=[])
        def test_cross_tenant_refused(self): self.check(Stage.ACCESS_DENIED, tenant_id='tenant-B')
        def test_no_chunks(self): self.check(Stage.EXTRACTION_OR_CHUNKING_FAILED, chunks=[])
        def test_not_indexed(self): self.check(Stage.INDEX_NOT_READY, chunks=[replace(c,indexed=False) for c in self.chunks])
        def test_version_mismatch(self): self.check(Stage.FILTER_EXCLUDED, version='v1')
        def test_disabled_source(self): self.check(Stage.FILTER_EXCLUDED, docs=[replace(self.docs[0],status='deleted'),self.docs[1]])
        def test_top_one_miss(self): self.check(Stage.RETRIEVAL_MISS, top_k=1)
        def test_top_two_hit(self): self.check(Stage.SUCCESS, top_k=2)
        def test_no_matching_query(self): self.check(Stage.RETRIEVAL_MISS, query_terms=frozenset({'冰霜'}))
        def test_model_error(self): self.check(Stage.GENERATION_ERROR, generated_answer='5')
        def test_target_unindexed_but_other_indexed(self): self.check(Stage.INDEX_NOT_READY, chunks=[replace(self.chunks[0],indexed=False),self.chunks[1]])
        def test_topk_invalid(self):
