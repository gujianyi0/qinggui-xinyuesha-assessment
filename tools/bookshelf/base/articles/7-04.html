测试、部署与效果验证（四）：请求与任务关联、结构化日志、调用追踪及敏感信息保护

对应学习目标：用请求号或任务号关联模型、工具和持久化记录；记录状态、耗时、重试和错误，日志不暴露密钥及敏感内容。

知识性质：工程原理与可复现的离线教学示例；适用于 Python、FastAPI、AI Agent、SQLAlchemy、PostgreSQL、Kafka Worker 等系统。

1. 核心问题：为什么“打印日志”不等于可观测性

一个 AI 应用的执行通常跨越多个边界：HTTP 路由接收请求，Agent 决定是否调用工具，工具读取数据库，模型生成回答，后台任务可能进入队列，Worker 再处理并写入最终结果。只记录一句“调用模型失败”，无法回答以下问题：

  • 哪个用户请求或后台任务失败？同一次用户操作是否产生过多个 HTTP 请求？
  • 失败发生在模型、工具、数据库还是消息队列？
  • 当前任务已经尝试了几次？第一次与第二次是否调用同一工具和模型版本？
  • 数据库是否已经写入结果？为什么前端仍然显示“处理中”？
  • 某个模型服务商的失败请求能否用服务商提供的 Request ID 追查？
  • 记录问题时，是否意外把 API Key、用户上传资料、私人聊天或模型输出写进日志？

要让这些问题可以定位，需要分清身份关联标识、事件日志、分布式调用链、持久化业务状态、度量指标和敏感数据存储六种东西。它们互相补充，而不应彼此替代。

1.1 四种观测手段

手段 主要记录什么 适合回答的问题 不适合承担的职责
Logs（日志） 某时刻发生的结构化事件 哪次调用失败，错误码是什么 不应作为唯一业务状态存储
Traces（链路追踪） 请求跨进程、跨服务的调用关系 哪一段耗时最久，父子调用如何关联 不能证明模型内部推理的真实原因
Metrics（指标） 聚合计数、耗时分布和资源用量 错误率是否上升，P95 延迟是否退化 不能保存每个请求的完整历史
持久化记录（DB / Audit） 业务最终结果、状态和必要执行证据 重启后任务有没有完成，谁创建了结果 不宜直接将所有原始事件无限写入主业务表

OpenTelemetry 使用传播的上下文把日志、指标和 Trace 联系起来，标准跨服务追踪常使用 W3C traceparent。见官方 Context Propagation。

2. 标识符体系：Request、Task、Trace、Run、Tool Call

这些 ID 的生命周期不同，不能全部混用成一个“请求 ID”。

标识符 含义 典型产生时机 生命周期 关系
request_id 一次 HTTP 请求的内部关联标识 HTTP 入口 当前请求 一个业务操作可触发多次 HTTP 请求
task_id 可持久化的后台任务身份 业务接受异步任务时 跨进程、跨重启 一个任务可多次执行与重试
trace_id 一条分布式调用链的身份 Trace 入口或提取可信上游上下文 一条追踪链 一条 Trace 下包含多个 Span
span_id 一次局部操作的追踪片段 调用某服务或工具时 单次操作 带父子关系，组成 Trace
run_id 一次 Agent / Worker 执行尝试 每次执行或重试开始时 单次执行 重试仍用同一 task_id，但不同 run_id
tool_call_id 一次具体工具请求身份 模型提出工具调用或框架生成时 单次工具调用 匹配请求与对应工具结果
provider_request_id 上游模型服务商的请求标识 服务商接受 API 请求时 单次上游请求 帮助与服务商侧排查关联
result_id 一条已持久化结果记录的身份 数据库成功写入结果时 业务记录保存期间 可从任务与日志反查
session_id 一段用户会话身份 会话创建时 可跨多轮请求 与 request_id、task_id 不同

2.1 示例：用户启动一次批量资料导入

text
浏览器 POST /imports
  request_id = REQ-A
  trace_id   = TRACE-A
  创建 task_id = TASK-17
     │
     ├─ 数据库 tasks 保存 TASK-17 / QUEUED
     └─ Kafka 发送 task_id=TASK-17, trace context
                          │
          Worker 第一次领取 TASK-17
          run_id=RUN-1
          ├─ tool_call_id=TOOL-1: parse_documents 成功
          ├─ model_call_id=MODEL-1: embedding API 超时
          └─ tasks 改为 RETRYING
                          │
          Worker 第二次领取 TASK-17
          run_id=RUN-2
          ├─ tool_call_id=TOOL-2: parse_documents 完成或复用已有输出
          ├─ model_call_id=MODEL-2: embedding API 成功
          └─ result_id=RESULT-1 / tasks=SUCCEEDED
                          │
浏览器 GET /tasks/TASK-17
  request_id = REQ-B （新的 HTTP 请求）
  返回：TASK-17 已完成，result_id=RESULT-1

这里 REQ-A 和 REQ-B 不同，但 TASK-17 不变。Worker 的 RUN-1 和 RUN-2 不同，因此可以分别归档耗时、错误、工具调用和模型版本。

重要边界：trace_id 不是业务授权凭证，task_id 不是会话访问令牌，provider_request_id 也不等于本地 request_id。这些标识符只负责关联，不替代身份认证和对象级授权。

2.2 哪个 ID 由客户端生成？

安全且常见的做法是：服务端为 HTTP 请求生成内部可信的 request_id；异步任务被持久化接受时生成 task_id；由标准追踪组件创建或从可信且经过校验的上下文提取 Trace。不要直接把未经验证的用户自填 X-Request-ID 当成数据库归属关系或日志主键。

可以在响应中返回服务端生成的 X-Request-ID，让使用者报错时向支持人员提供。对于模型服务商，另保存其返回的 x-request-id，并按需使用供应商支持的客户端请求 ID 头。OpenAI 的官方 API Overview 介绍了服务商的 x-request-id 和 X-Client-Request-Id：它们与应用自定义的业务任务 ID 是不同层次。

3. 一次调用的事件链应该记录哪些内容

建议至少捕获以下业务事件，具体命名可按团队约定。

事件 发生时机 重点字段
http.request_started 接收到请求 request_id、trace_id、路由模板、时间
task.submitted 任务被持久化接收 request_id、task_id、状态
task.started Worker 领取某次任务 task_id、run_id、attempt_no
tool.started 工具开始执行 tool_call_id、tool_name、run_id
tool.completed 工具完成 status、duration_ms、result_ref
tool.failed 工具失败 error_code、retryable、duration_ms
model.started 请求模型 model_id、prompt_version、attempt_no
model.completed 模型返回 provider_request_id、Token 用量、duration_ms
model.failed 模型失败 error_code、HTTP 状态或超时类别
result.persisted 最终结果事务提交成功 task_id、result_id、状态
task.retry_scheduled 已持久化下次重试计划 next_retry_at、attempt_no
task.completed 任务进入成功终态 result_id、总耗时
task.failed 任务进入失败终态 error_code、attempt_no

注意：日志只是观察记录，数据库事务成功是业务结果是否真正持久化的权威依据。例如网络断开可能导致日志尚未送到采集端，但数据库已经提交成功；这时不能仅凭缺少日志判定“任务失败”。

4. Structured Logging：结构化日志与字段契约

生产系统优先采用结构化日志，例如 JSON Lines，每行对应一个事件。与自由文本相比，结构化字段更适合筛选、聚合和关联。

json
{
  "at": "2026-11-12T03:12:04Z",
  "level": "INFO",
  "event": "model.completed",
  "request_id": "req_a1",
  "task_id": "task_17",
  "trace_id": "a0830000000000000000000000000001",
  "run_id": "run_2",
  "model_id": "model-x",
  "prompt_version": "rules-v1.3",
  "provider_request_id": "req_provider_01",
  "duration_ms": 842.7,
  "input_tokens": 420,
  "output_tokens": 96,
  "status": "SUCCESS"
}

这是人工示例，不是实际 API 调用结果。字段设计应满足：统一字段名、稳定的状态枚举、统一时间单位、版本可追踪、必要标识符可关联、敏感字段不进入普通日志。

4.1 结构化日志与任意 JSON 的区别

日志内容即使可以 json.loads()，也不代表已经安全。比如 {"prompt": "用户私人问题", "authorization": "Bearer xxx"} 虽然是合法 JSON，仍然泄露了秘密。

因此应该使用字段白名单：仅允许既定的日志元数据字段，遇到未知字段默认丢弃，并限制字段长度、字符集和单条日志大小。不要默认把请求体、模型完整输入/输出、HTTP 头或 ORM 对象直接序列化成日志。

4.2 错误日志必须保留可定位性，同时避免泄密

推荐：

json
{"event":"model.failed","task_id":"task_17","run_id":"run_2","error_code":"MODEL_TIMEOUT","duration_ms":30000,"status":"ERROR"}

不推荐：

text
模型请求失败，完整异常：HTTP headers={'Authorization':'Bearer secret-...'}, body='用户私人内容...'

异常消息、SDK 调试日志、数据库连接字符串和堆栈上下文中都可能带有敏感信息。安全系统最好由专门的错误分类函数将异常转换为确定的错误码；需要原始堆栈时，也应通过受控诊断通道保存、限制访问和保留时间，而不是未经处理公开打印。

OWASP 的 Logging Cheat Sheet 对需要排除、掩码、过滤的敏感数据和日志注入风险有系统说明。

5. 模型、工具和持久化结果的关联方式

5.1 数据库模型

推荐将任务、模型调用、工具调用和最终结果分别设计为不同关系表：

sql
CREATE TABLE tasks (
    task_id UUID PRIMARY KEY,
    request_id TEXT NOT NULL,
    trace_id TEXT NOT NULL,
    status TEXT NOT NULL,
    attempt_no INTEGER NOT NULL DEFAULT 0,
    result_id UUID,
    error_code TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE tool_calls (
    call_id UUID PRIMARY KEY,
    task_id UUID NOT NULL REFERENCES tasks(task_id),
    run_id UUID NOT NULL,
    tool_name TEXT NOT NULL,
    status TEXT NOT NULL,
    duration_ms DOUBLE PRECISION NOT NULL,
    error_code TEXT
);

CREATE TABLE model_calls (
    call_id UUID PRIMARY KEY,
    task_id UUID NOT NULL REFERENCES tasks(task_id),
    run_id UUID NOT NULL,
    model_id TEXT NOT NULL,
    prompt_version TEXT NOT NULL,
    provider_request_id TEXT,
    duration_ms DOUBLE PRECISION NOT NULL,
    input_tokens INTEGER,
    output_tokens INTEGER,
    status TEXT NOT NULL,
    error_code TEXT
);

CREATE TABLE results (
    result_id UUID PRIMARY KEY,
    task_id UUID NOT NULL UNIQUE REFERENCES tasks(task_id),
    -- 真实输出通常需要单独的受保护数据表/对象存储；此处只给结构示例。
    protected_content_ref TEXT NOT NULL
);

这只是用于理解关联关系的简化 PostgreSQL 结构。实际多租户业务还需要所有权、租户外键、授权查询、索引、状态约束、幂等键，以及数据保护与保留策略。results.task_id UNIQUE 可以避免同一任务产生重复的最终结果记录。

5.2 查询一项任务的执行历史

sql
SELECT task_id, status, attempt_no, result_id, error_code
FROM tasks
WHERE task_id = :task_id;

SELECT run_id, tool_name, status, duration_ms, error_code
FROM tool_calls
WHERE task_id = :task_id
ORDER BY run_id;

SELECT run_id, model_id, prompt_version, provider_request_id,
       status, duration_ms, input_tokens, output_tokens, error_code
FROM model_calls
WHERE task_id = :task_id
ORDER BY run_id;

这些查询必须放在已经完成身份认证和对象级授权的后端，不能让普通用户通过改变 task_id 查看别人的模型、工具或私人资料。

6. 记录状态、重试和错误：先定义状态机

常见的持久化任务状态包括：QUEUED（等待）、RUNNING（执行中）、RETRYING（等待重试）、SUCCEEDED（成功）、FAILED（最终失败）和 CANCELLED（已取消）。

对于每次执行，至少记录：

  • task_id：哪项逻辑任务。
  • run_id：哪一次实际执行尝试。
  • attempt_no：已经进行了第几次尝试（从 1 开始）。
  • status：当前运行状态与最终状态。
  • error_code：经过分类的稳定错误码。
  • retryable 与 next_retry_at：是否可重试、何时重试。
  • result_id：已持久化的业务结果引用，未完成则为空。

需要特别避免把 retry_count 与 attempt_no 混为一谈。例如 attempt_no=3 一般表示执行了三次，其中重试两次。团队内部应明确命名含义并保持一致。

错误分类可以按来源与性质拆分：INPUT_INVALID、AUTH_DENIED、MODEL_TIMEOUT、MODEL_RATE_LIMITED、TOOL_TIMEOUT、TOOL_VALIDATION_FAILED、DB_CONFLICT、DB_UNAVAILABLE、RETRY_EXHAUSTED。错误码应稳定，错误细节可以拥有单独的安全诊断记录。

状态机必须有终态保护。SUCCEEDED 不能被旧 Worker 的迟到失败覆盖；持久化记录的 FAILED 也不应被任意重试直接改写成成功。实际系统应结合数据库条件更新、租约/代际标识、事务和消息幂等处理。

7. 耗时记录的正确方法

7.1 墙上时间与单调时钟

  • 事件时间戳：使用带时区的 UTC，例如 datetime.now(timezone.utc)，用于关联不同机器发生的事件。
  • 同一进程中一次操作的耗时：使用 time.perf_counter() 或 time.monotonic() 的差值，不使用容易受系统时间调整影响的墙上时钟求差。
python
from datetime import datetime, timezone
from time import perf_counter

started_at = datetime.now(timezone.utc)
t0 = perf_counter()
# 执行某次操作...
elapsed_ms = (perf_counter() - t0) * 1000

7.2 应拆开的耗时指标

指标 说明
HTTP 端到端耗时 从接收请求到返回状态/响应结束
队列等待耗时 从任务入队到被 Worker 实际领取
工具耗时 一次工具执行的开始到结束
模型首字时间（TTFT） 发起模型请求到接收到首个可展示增量
模型总耗时 发起模型请求到模型响应全部结束
持久化耗时 开始数据库事务到成功提交/失败
任务端到端耗时 从任务接受到最终业务终态

注意模型供应商返回的处理耗时与应用实际端到端耗时可能不同：网络往返、连接复用、排队和下游处理可能额外增加时间。

7.3 平均值与分位数

平均值可能掩盖慢请求。真实业务监控通常会观察 P50、P95、P99，配合调用成功率与重试率综合判断。聚合指标中不宜把每个 task_id 或 user_id 当成时间序列标签，因为这会带来极高的标签基数和监控成本。Trace / 日志适合保存单次关联 ID，Metrics 适合低基数字段聚合。

8. 模型调用记录与供应商 Request ID

一条模型调用记录建议包含：

call_id、task_id、run_id、model_id、prompt_version、provider_request_id、status、finish_reason、input_tokens、output_tokens、duration_ms、error_code。

对于流式响应，还可能需要 ttft_ms、stream_completed、stream_interrupted、partial_output 是否存在等状态元数据。默认不要把实际的部分生成文本写入普通日志。

8.1 OpenAI Python SDK 中的请求标识

下面是 API 机制示意，需要真实密钥才可执行：

python
import openai
from openai import OpenAI

client = OpenAI()  # 从服务器环境读取 OPENAI_API_KEY
try:
    response = client.responses.create(
        model="<your-available-model>",
        input="演示内容"
    )
    provider_request_id = response._request_id
except openai.APIStatusError as exc:
    provider_request_id = exc.request_id
    # 将异常分类后记录错误码与 provider_request_id；不要直接打印原始请求体或认证头

_request_id 是 SDK 文档明确公开支持的特例属性，其他以下划线开头的 SDK 字段不能随意视为稳定接口。参考 openai-python 官方 README。

还要考虑 SDK 内置自动重试：一个逻辑模型调用可能产生多个上游 HTTP 尝试。是否能获得每次网络尝试的 Request ID，取决于 SDK 与 instrumentation 的粒度；不能假设顶层响应 ID 自动包含所有底层重试细节。

9. Trace Context 与后台 Worker 的跨进程关联

9.1 为什么 Python ContextVar 只能解决一部分问题

contextvars.ContextVar 能帮助异步 Python 任务在一个进程内持有独立的上下文，例如 request_id 和 trace_id，比在全局变量上保存“当前用户”安全。但它不会自动在 Kafka 消息或不同操作系统进程之间传播上下文。

跨服务应采用标准追踪上下文，例如 W3C Trace Context，由 OpenTelemetry instrumentation 注入和提取；可以额外在 Kafka 任务消息头或任务表中保存合法的 task_id、correlation_id 作为业务关联依据。参考 OpenTelemetry Python Propagation。

text
API Server
  trace_id=TRACE-A, request_id=REQ-A
  └─ Kafka message headers: traceparent=..., task_id=TASK-17
                          ↓
Worker
  从经过验证的 trace context 创建子 Span
  通过 task_id 查持久化记录并进行业务权限检查
  └─ model / tool / db 分别创建 Span

不能把 HTTP 用户自带的任意 traceparent、Kafka 消息头或 task_id 直接当成授权信息。需要验证 ID 格式、来源信任和资源权限。跨异步队列的长时间操作有时使用 Span Links 比强制单一父子链更合理，应按追踪语义设计。

9.2 Trace 也不等于证明模型“为什么这么想”

Trace 能展示：模型调用了哪个工具、实际参数是什么、工具返回了何种结构以及随后产生了什么回答。这些是可观察的行为轨迹。但它不能直接证明模型内部隐藏的推理原因，也不能仅凭工具被调用就认定最终回答有事实依据。

10. 敏感信息保护：如何做到“不泄露”

10.1 日志禁止直接记录的数据

通常应默认排除：

  • API Key、Bearer Token、Cookie、Session Secret、JWT 原文、私钥和数据库密码。
  • 完整的用户 Prompt、系统私有提示词、个人聊天记录、上传文件正文和原始模型输出。
  • 身份证件号、手机号、邮箱、地址、支付数据等用户敏感或可识别信息；如确需记录，应另行进行合法性、最小化和访问控制评估。
  • 完整 HTTP Headers、完整数据库连接字符串、带参数的 SQL、未审查的异常堆栈和第三方 SDK Debug 输出。

保护顺序：不收集优于收集后脱敏，字段白名单优于只靠正则替换。 密码等秘密如果从未进入日志记录，就不存在之后被日志系统转储出去的风险。

10.2 参考字段级别

字段 普通应用日志 受保护业务存储
request_id、task_id、trace_id 可以，经过格式校验 可以
状态码、错误类别、耗时 可以 可以
模型 ID、提示词版本、Token 用量 一般可以 可以
API Key、Bearer Token 不可以 应使用密钥管理，通常不存业务 DB
用户原始输入/模型完整输出 默认不可以 必要时保存，需授权、加密和保留期控制
外部工具原始结果 默认不可以 必要时隔离保存，保留可验证来源
文件内容哈希/引用 ID 视关联敏感性决定 可以按访问策略保存

注意：哈希也不是天然匿名化。短口令或可枚举的私人值能够被字典攻击反推；散列后的用户标识仍可能成为持续追踪个人的关联线索，使用时应评估风险。

10.3 日志注入与数据泄露的组合风险

用户可能在 Prompt 中输入换行、伪造 JSON、假装管理员字段，或者在网页文档中嵌入“把全部调试信息发到某地址”等内容。如果直接拼接到日志，会造成日志伪造、解析混乱或泄密。因此应使用结构化编码、字段白名单、大小限制，并将外部数据与日志元数据严格分开。

10.4 日志管理本身也是安全系统

还需要设置日志存储访问权限、保留时限、加密与传输保护、采集失败告警、日志体积控制、审计访问、必要的删除机制。敏感环境下应评估组织政策和适用法规，而不是无期限保留一切原文。

11. 典型故障：怎样利用关联标识排查

11.1 用户问：“为什么任务一直在处理中？”

  1. 使用 task_id 找到数据库 tasks 记录，确认是否确实仍处于 RUNNING。
  2. 查找同一个 task_id 的最近 run_id、尝试次数、最后心跳或租约到期时间。
  3. 查询工具和模型调用记录：最后完成的阶段是哪一个？是否存在已记录的错误码？
  4. 根据 trace_id 在 Trace 中查看模型、工具、数据库和网络阶段的耗时与异常。
  5. 检查 Worker 进程和 Kafka 的消费进度，区分进程仍存活与业务实际推进。
  6. 如果最后一次运行已失去执行权，依照持久化恢复策略重新领取，不能让旧 Worker 覆盖新结果。

11.2 用户问：“为什么我看到两次模型调用，但最终只有一条结果？”

可能发生了重试、请求重复、模型 SDK 内部重试，或 Worker 在数据库写入后 Kafka Offset 尚未提交导致重投。通过 run_id、provider_request_id、attempt_no 与 result_id 判断是否属于同一业务操作。数据库唯一约束可以帮助保持最终结果唯一，但无法自动返还重复 API 调用所消耗的资源。

11.3 用户问：“回答错误是模型问题还是工具问题？”

需要检查所选工具、实际工具输出的受控来源记录及模型收到的上下文版本。如果工具返回了正确事实，但模型最终引用错误，属于模型解释或上下文利用阶段的问题。如果查询阶段选错了工具或资料版本，故障来源更靠前。普通日志只保存证据引用，不应直接泄露受保护的原文。

12. 生产级可观测性指标

推荐根据业务建立以下指标与告警：

指标 指标类型 适用场景
http_requests_total Counter HTTP 请求量与失败比例
http_request_duration_seconds Histogram API 响应 P50/P95/P99
ai_model_calls_total Counter 模型调用成功/失败/超时
ai_model_duration_seconds Histogram 模型耗时分布
ai_model_input_tokens_total Counter 输入用量聚合
ai_model_output_tokens_total Counter 输出用量聚合
agent_tool_calls_total Counter 各工具调用成功和失败
background_inflight_tasks Gauge 正在执行的后台任务数
background_task_retries_total Counter 重试频次
background_task_completed_total Counter 最终完成任务数

指标标签尽量使用低基数值：service、operation、model_family、status、error_code 等。不要把 request_id、task_id、原始 Prompt 或私人标识当成 Metrics 标签，否则会形成高基数和泄露风险。

附录提供一套只使用 Python 标准库的教学系统，实现：

  1. contextvars 为异步执行保存请求和任务上下文。

15. 常见误区与澄清

误区 正确认识
“所有系统使用同一个 request_id 就够了” HTTP 请求和持久化任务的生命周期不同，需要 request_id + task_id + run_id 等
“程序打印成功就代表数据库写入成功” 最终业务状态以事务提交结果和可查询记录为准
“请求超时一定没有消耗模型 API 费用” 超时不保证服务商未执行，也不保证不会计费
“一个 Trace 就知道模型内部为什么作出决策” Trace 记录可观察行为，不揭示内部隐藏推理
“日志中的用户 ID 可以充当授权依据” 关联标识不是授权凭证，读取诊断记录仍要做权限控制
“只要把日志输出成 JSON 就安全” JSON 仍可能泄露 token、原始输入和敏感异常
“只记录失败事件就足够排查” 需要开始、完成、状态变化、重试、结果引用与实际调用记录
“OpenTelemetry 会自动保存业务最终结果” Trace 是观测数据，持久化业务状态仍需数据库与事务
“contextvars 会自动穿越 Kafka 和进程边界” 跨进程传播必须显式使用可信消息元数据或标准 instrumentation
“平均延迟低就说明服务稳定” 还需关注尾延迟、错误率、在途任务和业务完成率

"""教学示例：任务、模型、工具与持久化结果的可关联安全日志。仅用标准库。"""
from __future__ import annotations

from contextlib import contextmanager
from contextvars import ContextVar
from dataclasses import dataclass
from datetime import datetime, timezone
import json
import logging
import math
import re
from pathlib import Path
import sqlite3
from time import perf_counter
from typing import Protocol
from uuid import uuid4

REQUEST_ID = ContextVar("request_id", default=None)
TASK_ID = ContextVar("task_id", default=None)
TRACE_ID = ContextVar("trace_id", default=None)
RUN_ID = ContextVar("run_id", default=None)

# 显式列举允许进入普通日志的元数据。绝不记录 prompt、response、headers、SQL 参数等。
LOG_FIELDS = frozenset({
    "event", "request_id", "task_id", "trace_id", "run_id", "status",
    "attempt_no", "duration_ms", "error_code", "provider_request_id",
    "model_id", "prompt_version", "input_tokens", "output_tokens",
    "tool_name", "result_id"
})
EVENT_NAMES = frozenset({
    "task.submitted", "task.started", "tool.completed", "tool.failed",
    "model.completed", "model.failed", "task.completed", "task.failed",
    "async.done"
})
SAFE_TEXT = re.compile(r"^[a-zA-Z0-9_.:-]{1,160}$")
logger = logging.getLogger("safe_observability_demo")
logger.addHandler(logging.NullHandler())


def utc_now() -> str:
    return datetime.now(timezone.utc).isoformat()


def log_event(event: str, **kwargs: object) -> None:
    raw = {
        "event": event if event in EVENT_NAMES else "unknown.event",
        "request_id": REQUEST_ID.get(),
        "task_id": TASK_ID.get(),
        "trace_id": TRACE_ID.get(),
        "run_id": RUN_ID.get(),
        **kwargs,
    }
    safe = {}
    for key, value in raw.items():
        if key not in LOG_FIELDS or value is None:
            continue
        # 只记录长度有限的原始值；对控制字符转义，防止日志伪造。
        if isinstance(value, (int, float)) and not isinstance(value, bool):
            if math.isfinite(value):
                safe[key] = value
        elif isinstance(value, str) and SAFE_TEXT.fullmatch(value):
            safe[key] = value
    safe["at"] = utc_now()
    logger.info(json.dumps(safe, ensure_ascii=False, separators=(",", ":")))


@contextmanager
def trace_scope(request_id: str, task_id: str, trace_id: str, run_id: str | None = None):
    vars_ = (REQUEST_ID, TASK_ID, TRACE_ID, RUN_ID)
    values = (request_id, task_id, trace_id, run_id)
    tokens = [var.set(value) for var, value in zip(vars_, values)]
    try:
        yield
    finally:
        for var, token in reversed(list(zip(vars_, tokens))):
            var.reset(token)


class TemporaryFailure(Exception):
    """可重试的外部依赖故障。"""


class PermanentFailure(Exception):
    """不可重试的业务故障。"""


@dataclass(frozen=True)
class ModelResponse:
    content: str
    provider_request_id: str
    input_tokens: int
    output_tokens: int


class Model(Protocol):
    model_id: str
    prompt_version: str

    def generate(self, prompt: str, tool_data: str) -> ModelResponse:
        ...


class Tool(Protocol):
    name: str

    def execute(self) -> str:
        ...


class DemoModel:
    model_id = "demo-model"
    prompt_version = "v1.0"

    def generate(self, prompt: str, tool_data: str) -> ModelResponse:
        return ModelResponse(
            content=f"基于工具结果：{tool_data}",
            provider_request_id="provider-demo-1", input_tokens=24, output_tokens=12
        )


class DemoTool:
    name = "lookup_rules"

    def execute(self) -> str:
        return "演示规则 1.0"


@contextmanager
def open_db(path: str | Path):
    """显式提交/回滚并关闭连接；SQLite 的 with conn 只管理事务，不负责 close。"""
    conn = sqlite3.connect(str(path), timeout=10)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA foreign_keys = ON")
    try:
        with conn:
            yield conn
    finally:
        conn.close()


def init_db(path: str | Path) -> None:
    with open_db(path) as conn:
        conn.executescript("""
        CREATE TABLE IF NOT EXISTS tasks (
            task_id TEXT PRIMARY KEY,
            request_id TEXT NOT NULL,
            trace_id TEXT NOT NULL,
            status TEXT NOT NULL,
            attempt_no INTEGER NOT NULL DEFAULT 0,
            error_code TEXT,
            result_id TEXT,
            updated_at TEXT NOT NULL
        );
        -- 教学环境中保留原文以演示重启后恢复；生产需按敏感级别访问控制与加密。
        CREATE TABLE IF NOT EXISTS private_payloads (
            task_id TEXT PRIMARY KEY REFERENCES tasks(task_id),
            prompt TEXT NOT NULL
        );
        CREATE TABLE IF NOT EXISTS private_results (
            result_id TEXT PRIMARY KEY,
            task_id TEXT NOT NULL UNIQUE REFERENCES tasks(task_id),
            answer TEXT NOT NULL
        );
        CREATE TABLE IF NOT EXISTS tool_calls (
            call_id TEXT PRIMARY KEY,
            task_id TEXT NOT NULL REFERENCES tasks(task_id),
            run_id TEXT NOT NULL,
            tool_name TEXT NOT NULL,
            status TEXT NOT NULL,
            duration_ms REAL NOT NULL,
            error_code TEXT
        );
        CREATE TABLE IF NOT EXISTS model_calls (
            call_id TEXT PRIMARY KEY,
            task_id TEXT NOT NULL REFERENCES tasks(task_id),
            run_id TEXT NOT NULL,
            model_id TEXT NOT NULL,
            prompt_version TEXT NOT NULL,
            provider_request_id TEXT,
            status TEXT NOT NULL,
            duration_ms REAL NOT NULL,
            input_tokens INTEGER,
            output_tokens INTEGER,
            error_code TEXT
        );
        """)


def submit_task(path: str | Path, prompt: str) -> tuple[str, str, str]:
    request_id, task_id, trace_id = uuid4().hex, uuid4().hex, uuid4().hex
    with open_db(path) as conn:
        conn.execute("""INSERT INTO tasks(task_id,request_id,trace_id,status,updated_at)
                        VALUES (?,?,?,'QUEUED',?)""",
                     (task_id, request_id, trace_id, utc_now()))
        conn.execute("INSERT INTO private_payloads(task_id,prompt) VALUES (?,?)", (task_id, prompt))
    with trace_scope(request_id, task_id, trace_id):
        log_event("task.submitted", status="QUEUED")
    return task_id, request_id, trace_id


def process_task(path: str | Path, task_id: str, model: Model, tool: Tool,
                 max_attempts: int = 2) -> str:
    # 简化演示：单线程领取任务；多 Worker 时必须使用数据库原子认领及租约。
    with open_db(path) as conn:
        task = conn.execute("SELECT * FROM tasks WHERE task_id=?", (task_id,)).fetchone()
        if task is None:
            raise KeyError("unknown task")
        if task["status"] in {"SUCCEEDED", "FAILED"}:
            return task["status"]
        if task["status"] not in {"QUEUED", "RETRYING"}:
            raise RuntimeError("task is already running")
        attempt = task["attempt_no"] + 1
        conn.execute("""UPDATE tasks SET status='RUNNING',attempt_no=?,updated_at=?
                        WHERE task_id=?""", (attempt, utc_now(), task_id))
        prompt = conn.execute("SELECT prompt FROM private_payloads WHERE task_id=?", (task_id,)).fetchone()[0]
    run_id = uuid4().hex
    with trace_scope(task["request_id"], task_id, task["trace_id"], run_id):
        log_event("task.started", status="RUNNING", attempt_no=attempt)
        tool_t0 = perf_counter()
        try:
            tool_data = tool.execute()
        except (TemporaryFailure, PermanentFailure) as exc:
            elapsed = round((perf_counter() - tool_t0) * 1000, 3)
            code = "TOOL_TEMPORARY" if isinstance(exc, TemporaryFailure) else "TOOL_PERMANENT"
            with open_db(path) as conn:
                conn.execute("""INSERT INTO tool_calls VALUES (?,?,?,?,?,?,?)""",
                             (uuid4().hex, task_id, run_id, tool.name, "ERROR", elapsed, code))
            log_event("tool.failed", status="ERROR", tool_name=tool.name,
                      attempt_no=attempt, duration_ms=elapsed, error_code=code)
            return _fail(path, task_id, attempt, max_attempts, code, isinstance(exc, TemporaryFailure))
        elapsed = round((perf_counter() - tool_t0) * 1000, 3)
        with open_db(path) as conn:
            conn.execute("INSERT INTO tool_calls VALUES (?,?,?,?,?,?,?)",
                         (uuid4().hex, task_id, run_id, tool.name, "SUCCESS", elapsed, None))
        log_event("tool.completed", tool_name=tool.name, status="SUCCESS", duration_ms=elapsed)

        model_t0 = perf_counter()
        try:
            response = model.generate(prompt, tool_data)
        except (TemporaryFailure, PermanentFailure) as exc:
            elapsed = round((perf_counter() - model_t0) * 1000, 3)
            code = "MODEL_TEMPORARY" if isinstance(exc, TemporaryFailure) else "MODEL_PERMANENT"
            with open_db(path) as conn:
                conn.execute("""INSERT INTO model_calls VALUES (?,?,?,?,?,?,?,?,?,?,?)""",
                             (uuid4().hex, task_id, run_id, model.model_id, model.prompt_version,
                              None, "ERROR", elapsed, None, None, code))
            log_event("model.failed", status="ERROR", model_id=model.model_id,
                      prompt_version=model.prompt_version, attempt_no=attempt,
                      duration_ms=elapsed, error_code=code)
            return _fail(path, task_id, attempt, max_attempts, code, isinstance(exc, TemporaryFailure))
        elapsed = round((perf_counter() - model_t0) * 1000, 3)
        result_id = uuid4().hex
        with open_db(path) as conn:
            conn.execute("INSERT INTO model_calls VALUES (?,?,?,?,?,?,?,?,?,?,?)",
                         (uuid4().hex, task_id, run_id, model.model_id, model.prompt_version,
                          response.provider_request_id, "SUCCESS", elapsed,
                          response.input_tokens, response.output_tokens, None))
            conn.execute("INSERT INTO private_results(result_id,task_id,answer) VALUES (?,?,?)",
                         (result_id, task_id, response.content))
            conn.execute("""UPDATE tasks SET status='SUCCEEDED',result_id=?,error_code=NULL,
                            updated_at=? WHERE task_id=?""", (result_id, utc_now(), task_id))
        log_event("model.completed", status="SUCCESS", model_id=model.model_id,
                  prompt_version=model.prompt_version, provider_request_id=response.provider_request_id,
                  input_tokens=response.input_tokens, output_tokens=response.output_tokens,
                  duration_ms=elapsed)
        log_event("task.completed", status="SUCCEEDED", attempt_no=attempt, result_id=result_id)
        return "SUCCEEDED"


def _fail(path: str | Path, task_id: str, attempt: int, max_attempts: int,
          code: str, retryable: bool) -> str:
    status = "RETRYING" if retryable and attempt < max_attempts else "FAILED"
    with open_db(path) as conn:
        conn.execute("UPDATE tasks SET status=?,error_code=?,updated_at=? WHERE task_id=?",
                     (status, code, utc_now(), task_id))
    log_event("task.failed", status=status, error_code=code, attempt_no=attempt)
    return status

class Recorder(logging.Handler):
    def __init__(self):
        super().__init__()
        self.events = []

    def emit(self, record):
        self.events.append(json.loads(record.getMessage()))


class FaultyTool:
    name = "lookup_rules"

    def __init__(self, errors):
        self.errors = list(errors)

    def execute(self):
        if self.errors:
            raise self.errors.pop(0)
        return "规则 2.0"


class FaultyModel(DemoModel):
    def __init__(self, errors):
        self.errors = list(errors)

    def generate(self, prompt, tool_data):
        if self.errors:
            raise self.errors.pop(0)
        return super().generate(prompt, tool_data)


class ObservabilityTests(unittest.TestCase):
    def setUp(self):
        self.tmp = tempfile.TemporaryDirectory()
        self.path = Path(self.tmp.name) / "audit.db"
        init_db(self.path)
        self.handler = Recorder()
        logger.addHandler(self.handler)
        logger.setLevel(logging.INFO)

    def tearDown(self):
        logger.removeHandler(self.handler)
        self.tmp.cleanup()

    def submit(self, prompt="private prompt 13"):
        return submit_task(self.path, prompt)

    def query(self, sql, args=()):
        with open_db(self.path) as conn:
            return conn.execute(sql, args).fetchall()

    def test_submission_has_correlation_ids(self):
        task_id, req, trace = self.submit()
        row = self.query("SELECT * FROM tasks")[0]
        self.assertEqual((row['task_id'], row['request_id'], row['trace_id']), (task_id, req, trace))

    def test_ids_not_equal(self):
        task_id, req, trace = self.submit()
        self.assertEqual(len({task_id, req, trace}), 3)

    def test_submitted_event_correlates(self):
        task_id, req, trace = self.submit()
        ev = self.handler.events[0]
        self.assertEqual((ev['task_id'], ev['request_id'], ev['trace_id']), (task_id, req, trace))

        task_id, _, _ = self.submit()
        self.assertEqual(process_task(self.path, task_id, DemoModel(), DemoTool()), 'SUCCEEDED')
        self.assertEqual(self.query("SELECT count(*) n FROM private_results")[0]['n'], 1)

        self.assertEqual(tool['run_id'], model['run_id'])

    def test_model_usage_recorded(self):

    def test_contextvars_isolate_async_tasks(self):

            with trace_scope(req, req + 't', req + 'x'):
                await asyncio.sleep(0)
                log_event('async.done')
        async def main():

        asyncio.run(main())
        data = [e for e in self.handler.events if e['event'] == 'async.done']
