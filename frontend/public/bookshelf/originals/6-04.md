# 消息队列与后台任务可靠性（四）：数据库已写入但 Offset 未提交、Worker 中途退出与并发重复消息的恢复

> 所属模块：《消息队列与后台任务可靠性》· 第四节  
> 主题范围：Kafka Consumer、PostgreSQL 业务事务、任务状态机、执行租约、幂等恢复、故障注入。  
> 示例运行范围：Python 标准库 + SQLite 的可复现实验；另给出 PostgreSQL/aiokafka 的工程写法与限制。

---

## 1. 学习目标的本质：至少一次交付下实现可恢复的业务效果

Kafka 消费一条消息时，实际上至少存在两套独立的状态：

1. **消息状态：** Kafka 某个 Consumer Group 针对 Topic/Partition 保存的已提交 Offset。
2. **业务状态：** PostgreSQL 中某次导入、某份反馈整理或某个模型批处理的状态与最终结果。

二者没有天然的跨系统原子提交关系。特别是外部 API 调用也不会自动加入 PostgreSQL 事务。

因此“消息处理完成”要拆解为三个具体断言：

- 业务结果已持久化并满足唯一性/完整性约束；
- 同一业务请求重复执行时，不会再生成第二份有冲突的最终结果；
- Consumer 只在允许恢复语义的前提下推进 Kafka Offset。

**目标不是宣称 Worker 永远不崩溃，而是保证 Worker 崩溃后存在明确的恢复路径。**

### 1.1 一个典型资料导入任务

```text
前端：POST /imports
    ↓
FastAPI：验证身份 + 创建任务记录（task_id / business_key）
    ↓
Kafka Topic：document-imports
    ↓
Worker-A：读取消息（partition 2, offset 41）
    ↓
PostgreSQL：认领任务 → RUNNING
    ↓
解析文件 / Embedding / 调用外部模型
    ↓
PostgreSQL：同一事务保存最终结果 + SUCCEEDED
    ↓
Kafka：提交 offset = 42
```

`offset = 42` 代表下一次应读取的位置，并不是把“消息 42 已成功”写入 Kafka。假设 Worker 在结果提交数据库之后、提交 Kafka Offset 之前退出，重启后 Offset 41 可能再次被读取。此时程序应该识别它已完成，并复用持久化结果，而不是重新导入一遍。

### 1.2 什么叫“可靠恢复”

至少满足以下不变量：

| 编号 | 系统不变量 | 主要保障机制 |
|---|---|---|
| I1 | 同一租户、同一业务操作最多存在一份最终结果 | `UNIQUE(tenant_id, business_key)` |
| I2 | 任务成功与对应最终结果保持一致 | 同一数据库事务提交 |
| I3 | 旧 Worker 失去任务所有权后无法完成写入 | 租约 + generation/Fencing Token + 条件更新 |
| I4 | 不可解释的处理中状态不能无限期存在 | 任务超时、恢复扫描、重试策略 |
| I5 | 重复消息不会悄悄修改已完成结果 | 幂等键 + 输入指纹 + 终态不可覆盖 |
| I6 | Kafka Offset 不会越过尚未安全处理的消息 | 分区连续进度与受控提交 |
| I7 | 出错仍能追溯 | task_id、event_id、topic/partition/offset、attempt 与错误记录 |

这些不变量需要由代码、数据库和自动化测试共同保证，不能只在提示词或部署文档里声明。

## 2. 最小术语体系

| 名称 | 含义 | 与恢复的关系 |
|---|---|---|
| `event_id` | 一次逻辑事件的唯一标识 | 识别同一事件重投；不同事件仍可能指向同一业务 |
| `business_key` | 一次逻辑业务操作的幂等键 | 判断两条消息是否要求同一次导入/反馈生成 |
| `task_id` | 任务记录 ID | 面向用户查询进度与最终结果 |
| `payload_hash` | 规范化输入的指纹 | 发现同一业务键被用于不同参数 |
| Topic/Partition/Offset | Kafka 内部消息位置 | 识别当前 Consumer 应提交的下一位置 |
| `attempts` | 业务认领/执行尝试次数 | 记录重试和诊断故障，不应与 Kafka 投递次数混为一谈 |
| `lease_until` | 任务执行租约过期时间 | 判断可能失联的 Worker 是否可被接管 |
| `generation` | 每次重新认领递增的代际编号 | 拒绝旧 Worker 的迟到写入 |
| `final_results` | 业务最终结果表 | 最终结果的唯一性和持久性来源 |
| Inbox / Processed Events | 消费侧事件记录表 | 保留消息身份与处理证据 |
| Outbox | 数据库内的待发布事件表 | 可靠传递跨系统后续动作 |

**重要区分：** `event_id`、`business_key` 和 Kafka Offset 不是同一个东西。Kafka Offset 在 `(topic, partition)` 范围内标识日志位置；`event_id` 标识逻辑事件；`business_key` 标识业务操作。Producer 重试可能生成不同 Kafka 记录，但它们仍可以属于同一次业务。

## 3. 故障场景 A：业务写入成功，但 Kafka Offset 未提交

### 3.1 完整时间线

```text
时间 →

Kafka:       交付 offset=41 ───────────────────────────── 重新交付 41
Worker-A:              读取 → 处理 → DB COMMIT → ✕ 进程退出
PostgreSQL:                              SUCCEEDED + result 已持久化
Kafka Offset:            仍指向 41 ───────────────────── 41
Worker-B:                                             读取 41 → 查重 → 不再写业务 → Commit 42
```

Kafka 负责的只是“从哪里继续读”。它不知道 PostgreSQL 已经保存了结果。Kafka 可以再次提供相同消息，Consumer 不能把它当作首次操作直接重做。

### 3.2 正确恢复过程

1. Consumer 重启并重新获得分区分配，从已提交 Offset 恢复读取；
2. 解析消息并验证 `event_id`、`business_key`、`payload_hash`；
3. 查询任务最终状态或唯一业务结果；
4. 如果业务已成功，返回 `ALREADY_SUCCEEDED`，复用已保存结果；
5. 确认业务状态可持久追溯，再提交当前消息对应的下一 Offset。

核心操作可描述为：

```text
process(message):
    if final_result_exists(business_key):
        return ALREADY_SUCCEEDED
    else:
        run_idempotent_transaction(message)
        return SUCCEEDED

commit_kafka_offset(message.offset + 1)
```

这里的“查重”不能只有 `SELECT`。两个 Worker 都可能在同一时刻查不到记录。数据库必须以唯一约束、条件更新或事务性插入真正裁定哪一个请求可以创建最终结果。

### 3.3 为什么不能先提交 Offset

如果先提交 Offset 42，然后业务事务失败或 Worker 被终止，重启后 Kafka 从 42 继续读取，可能不再交付 Offset 41，从而造成未处理的业务被跳过。

反过来，**先数据库提交、再 Kafka 提交**，保留了可重投窗口；只要业务幂等实现正确，重复投递不会破坏最终结果。这个权衡是常见的 At-least-once 消费设计。

### 3.4 三种容易混淆的“成功”

- `DB_COMMITTED`：数据库事务成功；
- `KAFKA_OFFSET_COMMITTED`：Kafka Group 保存了新的恢复位置；
- `EXTERNAL_EFFECT_CONFIRMED`：外部 API 真正执行成功，且有可核验的结果。

这三个状态不能互相推导。数据库已成功不保证外部邮件已发送；Kafka Offset 已更新也不代表模型请求已完成。

## 4. 故障场景 B：任务正在 RUNNING 时 Worker 退出

### 4.1 为什么 RUNNING 可能永久卡住

一种常见实现：

```python
UPDATE tasks SET status = 'RUNNING' WHERE id = :task_id;
# Worker 开始耗时处理
# 此时进程被杀死
UPDATE tasks SET status = 'SUCCEEDED' WHERE id = :task_id;
```

第一条更新已持久化，第二条从未执行。若系统仅依靠 `status = 'RUNNING'` 判断任务正在正常处理，就无法区分“仍在工作”和“Worker 已死亡”。

### 4.2 租约（Lease）

给每次认领加上期限：

```text
status = RUNNING
owner = worker-A
generation = 7
lease_until = 2026-11-12T10:00:30Z
```

只要租约尚有效，正常情况下其他 Worker 不主动接管同一任务；租约超时意味着“原执行权可能已经失效”，可以触发恢复程序。

但**租约超时不等于原 Worker 必然已经停止**。网络暂停、GC、CPU 饱和、操作系统调度和时钟问题都可能让旧进程迟到恢复，因此必须结合后述的代际标识阻止其继续写入。

### 4.3 心跳与续租

对长任务，可以在执行过程中定期续租：

```sql
UPDATE tasks
SET lease_until = clock_timestamp() + INTERVAL '30 seconds'
WHERE task_id = :task_id
  AND status = 'RUNNING'
  AND owner = :owner
  AND generation = :generation
  AND lease_until > clock_timestamp();
```

若更新影响行数为 0，说明该 Worker 不再拥有有效的执行权，应停止后续写入并尝试取消尚未完成的工作。

**务必注意：** 租约属于跨进程持久状态，应该尽量以数据库权威时间判断有效性，而不是将进程本地的 `time.monotonic()` 原样持久化到数据库。`monotonic()` 适合计算单进程内耗时与截止时间，不适合作为跨重启的可比较时间戳。

### 4.4 恢复扫描（Reaper / Sweeper）

恢复程序可以定期查找：

```sql
SELECT task_id
FROM tasks
WHERE status = 'RUNNING'
  AND lease_until < clock_timestamp();
```

然后按约定策略：

- 将任务重新变成 `PENDING`，等待下次分配；
- 或由新 Worker 在事务中直接认领并递增 generation；
- 记录旧 Worker 的最后心跳、原始错误、重试次数；
- 对多次失败任务应用退避、最大重试次数和终态 `FAILED`。

**前提条件：** 如果 Kafka 消息已经提前被错误确认，单纯将状态改回 `PENDING` 还不够；还需要有可靠的任务分派或重新发布机制（如持久化任务扫描 + Outbox），否则可能永远没有 Worker 再次执行。

### 4.5 执行代际编号（Generation / Fencing）

假设：

```text
Worker-A 获取 generation=7
A 长时间暂停，租约过期
Worker-B 获取 generation=8
B 完成任务并提交结果
A 恢复并试图写入旧结果
```

如果 A 仅凭旧的 `task_id` 执行 `UPDATE`，就可能覆盖 B。正确做法是对完成操作使用条件更新：

```sql
UPDATE tasks
SET status = 'SUCCEEDED', result_id = :result_id
WHERE task_id = :task_id
  AND status = 'RUNNING'
  AND owner = :owner
  AND generation = :generation
  AND lease_until > clock_timestamp();
```

只有实际影响 1 行时才能继续提交本事务；影响 0 行即认为执行权已过期、已被接管或状态不再允许完成。

数据库端的条件检查属于真正的并发控制。`generation` 不能只由客户端在内存中比较。

## 5. 故障场景 C：重复消息同时到达两个 Worker

### 5.1 并发竞态

错误方式：

```text
Worker-A                         Worker-B
SELECT ... 结果不存在            SELECT ... 结果不存在
       ↓                                 ↓
INSERT result                     INSERT result
       ↓                                 ↓
最终可能产生两个业务结果
```

即便有 `if not exists` 判断，也无法防止两个事务同时通过检查。

### 5.2 数据库唯一性是最后防线

```sql
CREATE TABLE final_results (
    tenant_id UUID NOT NULL,
    business_key TEXT NOT NULL,
    result_json JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, business_key)
);
```

两个 Worker 可以都尝试写入，但同一 `(tenant_id, business_key)` 最终至多成功插入一条记录。业务层仍需要根据冲突结果决定返回已有结果还是报告参数不一致。

### 5.3 SQL 原子认领，不能依赖 Python 全局锁

可以使用 PostgreSQL 原子 `INSERT ... ON CONFLICT`，或在事务中执行 `SELECT ... FOR UPDATE`、带条件的 `UPDATE ... RETURNING`。

例如：

```sql
INSERT INTO tasks (tenant_id, business_key, payload_hash, status, generation)
VALUES (:tenant, :key, :hash, 'PENDING', 0)
ON CONFLICT (tenant_id, business_key) DO NOTHING;
```

这里只是安全地保证任务记录最多一条，**还没有完成执行权认领**。接着应在事务中锁定目标行、检查状态/指纹/租约，并原子更新认领者与 generation。

```sql
BEGIN;
SELECT status, generation, lease_until, payload_hash
FROM tasks
WHERE tenant_id = :tenant AND business_key = :key
FOR UPDATE;
-- 校验 hash / 状态 / 租约
UPDATE tasks SET status = 'RUNNING', owner = :worker,
    generation = generation + 1,
    lease_until = clock_timestamp() + INTERVAL '30 seconds'
WHERE tenant_id = :tenant AND business_key = :key;
COMMIT;
```

上面的 SQL 是事务片段，必须补上校验条件与异常处理，不能把它当作可以直接部署的完整 Worker。行锁应只覆盖很短的“认领”事务，**不要把一个耗时十分钟的模型请求包在数据库事务和行锁内**。

### 5.4 不同 Kafka 分区也可能处理同一业务

即使传统 Consumer Group 对同一分区通常只分配给一个消费者，也仍有以下并发来源：

- 不同事件可能写入不同分区，却携带相同业务幂等键；
- 一个消费者在同一分区内部并发调度多个任务；
- Rebalance 或租约过期后，旧执行进程可能尚未完全停下；
- 后台恢复扫描与 Kafka 消费者同时发现同一待处理任务。

因此，**Kafka 分区分配不是跨分区或跨系统的业务唯一锁**。将同一业务 Key 用作 Kafka Message Key 有助于保持单 Topic/固定分区布局下的路由一致性，却不能取代数据库唯一约束。

## 6. 一套完整的任务状态机

```text
                   ┌─────────────┐
                   │   PENDING   │
                   └──────┬──────┘
                          │ 原子认领
                          ▼
                   ┌─────────────┐
             ┌─────│   RUNNING   │─────┐
             │     └─────────────┘     │
       超时/重试等待              业务事务成功
             │                         │
             ▼                         ▼
         RETRY_WAIT                SUCCEEDED
             │
             └──────────────→ PENDING

     不可恢复错误/重试耗尽 → FAILED
     已获准取消且停止执行 → CANCELLED
```

教学代码为简化状态，只使用 `PENDING / RUNNING / SUCCEEDED / FAILED`。实际系统应考虑 `RETRY_WAIT`、`CANCEL_REQUESTED`、`CANCELLED`、`UNKNOWN_EXTERNAL_RESULT` 等状态。

各状态应有明确约束：

| 当前状态 | 可允许的下一状态 | 必须满足的条件 |
|---|---|---|
| PENDING | RUNNING | 取得任务执行权 |
| RUNNING | SUCCEEDED | 当前 generation 有效，结果事务提交 |
| RUNNING | RETRY_WAIT | 可恢复错误、符合重试预算 |
| RETRY_WAIT | PENDING | 已到下次重试时间 |
| RUNNING | FAILED | 不可恢复错误或重试耗尽 |
| RUNNING | CANCELLED | 确认取消已生效，不能回滚已发生副作用 |
| SUCCEEDED | — | 正常不应再被覆盖 |
| FAILED / CANCELLED | — | 如允许人工重新执行，应产生新任务代际或新业务操作 |

**状态是持久化业务事实，不是一个 Worker 的局部变量。**

## 7. 如何设计数据库表：事件、任务、结果三层分开

```sql
CREATE TABLE tasks (
    tenant_id UUID NOT NULL,
    business_key TEXT NOT NULL,
    payload_hash TEXT NOT NULL,
    status TEXT NOT NULL CHECK (
        status IN ('PENDING','RUNNING','RETRY_WAIT',
                   'SUCCEEDED','FAILED','CANCELLED')
    ),
    owner TEXT,
    generation BIGINT NOT NULL DEFAULT 0,
    lease_until TIMESTAMPTZ,
    attempts INTEGER NOT NULL DEFAULT 0,
    next_retry_at TIMESTAMPTZ,
    last_error_code TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, business_key)
);

CREATE TABLE inbox_events (
    consumer_group TEXT NOT NULL,
    event_id UUID NOT NULL,
    tenant_id UUID NOT NULL,
    business_key TEXT NOT NULL,
    payload_hash TEXT NOT NULL,
    topic TEXT NOT NULL,
    partition_id INTEGER NOT NULL,
    message_offset BIGINT NOT NULL,
    received_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_group, event_id)
);

CREATE TABLE final_results (
    tenant_id UUID NOT NULL,
    business_key TEXT NOT NULL,
    content JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, business_key),
    FOREIGN KEY (tenant_id, business_key)
        REFERENCES tasks(tenant_id, business_key)
);

CREATE INDEX ix_tasks_expired_running
    ON tasks (lease_until)
    WHERE status='RUNNING';
```

这里列出的是教学用 DDL 骨架，真实生产系统还需要：外键关联的租户范围、审计、任务尝试记录、错误保留策略、版本字段、资源权限和迁移脚本。

### 7.1 为什么需要 Inbox

Kafka 消息包含 Topic/Partition/Offset，但同一个逻辑事件可能因生产者重试产生不同物理记录。Inbox 让程序能够知道“哪个逻辑事件在什么消费组、对应什么业务操作”。

`inbox_events` 不等于“已经成功处理的事件”，因为本表例子只记录**接收过**。若要支持确认成功后安全跳过，需要额外存储 `processing_status` / `completed_at`，并让完成标记与最终业务结果在同一事务中写入。不要将“接收记录存在”误判为“业务已经完成”。

### 7.2 为什么最终结果要有独立唯一约束

仅用任务表的 `status='SUCCEEDED'` 防重，容易在多个事务并发检查时出现竞态。结果表自己的唯一键是最终数据库约束，和状态机形成双重保护。

### 7.3 为什么 Payload Hash 很重要

同一个 `business_key` 如果先用于导入文档 A，之后又用于导入文档 B，程序不能不加区分地返回 A 的结果。

推荐规范：

```text
business_key = 调用方生成的、在约定作用域内稳定不变的操作 ID
payload_hash = 对规范化输入计算的 SHA-256
```

当同一业务键对应不同 `payload_hash`，应报告冲突（例如 HTTP 409），而不是复用旧结果或覆盖旧任务。

## 8. PostgreSQL 中怎样安全完成结果提交

以下是一个独立事务内部的关键步骤：

```sql
BEGIN;

-- 先证明当前 Worker 仍然拥有执行权
UPDATE tasks
SET status = 'SUCCEEDED', updated_at = clock_timestamp(),
    owner = NULL, lease_until = NULL
WHERE tenant_id = :tenant
  AND business_key = :key
  AND status = 'RUNNING'
  AND owner = :owner
  AND generation = :generation
  AND lease_until > clock_timestamp()
RETURNING tenant_id, business_key;

-- 应用程序必须检查上面的 RETURNING 恰好有一行；否则 ROLLBACK。
INSERT INTO final_results (tenant_id, business_key, content)
VALUES (:tenant, :key, :result_json);

-- 可选：同一事务记录相应 Event 的完成状态/Outbox 事件
COMMIT;
```

同一事务里，`UPDATE tasks` 和 `INSERT final_results` 一起成功，才能形成 `SUCCEEDED + final_result` 的一致状态。插入发生唯一性冲突、JSON 数据非法或者数据库连接丢失时，事务应整体失败并回滚。

不要把模型 API 调用或较慢的文件上传包进这个事务中。可以先计算候选结果，再用一个短事务提交已完成的结果。

### 8.1 `ON CONFLICT` 不能隐藏不同输入

如果选择：

```sql
INSERT INTO final_results (tenant_id, business_key, content)
VALUES (:tenant, :key, :content)
ON CONFLICT (tenant_id, business_key) DO NOTHING;
```

冲突被忽略并不自动代表这两次输入等价。应单独验证 `payload_hash` 与原业务记录一致，再决定是否复用结果。对于业务幂等性，**数据库冲突是信号，不是可以盲目忽略的错误。**

---

## 9. 租约不能完全消除旧执行者风险

租约本质上是时间限制，而非强制杀死旧进程。

```text
时间 0：A 获取租约，generation=12
时间 20：A 被暂停
时间 31：A 租约失效
时间 32：B 获取租约，generation=13
时间 33：B 写入新结果
时间 34：A 恢复，试图写入旧结果
```

通过 `WHERE generation = 12` 的数据库条件更新，可以阻止 A 在数据库内提交旧结果。

但如果 A 在暂停前已经调用外部服务（发送邮件、调用支付接口、发起模型任务），数据库里的 generation 校验无法撤销已发生的外部副作用。对于这些操作，还需要：

- 第三方 API 支持的幂等键；
- 外部系统结果查询与对账；
- Outbox / Inbox 结合可靠发送；
- 不可撤销操作采用审批、预算和补偿流程；
- 将“外部结果未知”视为独立状态，不盲目立即重试。

若采用 Fencing Token，要求**真正执行资源变更的服务端**拒绝较小的 Token；只在 Worker 本地比较 Token 不起作用。

## 10. Kafka Offset 的安全推进与并发完成顺序

同一 Partition 内收到：

```text
Offset 41 → 耗时任务 A，尚未完成
Offset 42 → 快速任务 B，已完成
Offset 43 → 快速任务 C，已完成
```

如果在 A 未完成时提交 Offset 44，之后 Worker 崩溃，重启可能直接从 44 开始，导致 A 被跳过。

因此可选方案为：

1. **按分区串行处理并提交：** 简单、最容易证明安全；
2. **并发执行但使用连续完成水位：** 只提交已安全处理的连续前缀，不能越过未完成记录；
3. **先将各消息可靠写入数据库任务队列，再确认 Kafka：** 需要将消息登记与处理状态分离，并配套独立的恢复/调度机制。

注意 Kafka 日志 Offset 不一定数值上严格连续（例如事务控制记录可能产生可见的间隙）；水位算法应该以**实际消费到的记录顺序及处理状态**为基础，而不是简单假定每一个整数 Offset 都对应一条需要业务处理的消息。

### 10.1 分区 Rebalance

旧 Consumer 可能处理了数据库事务，却在随后 `commit()` 时遇到 `CommitFailedError`，因为它已失去分区所有权。此时不能自作主张跳过失败的 Offset；新持有者重新读取消息后，依靠数据库幂等逻辑处理重投。

实现中应明确处理分区撤销事件和在途任务，必要时停止认领或完成可安全提交的任务，并保护已经失去所有权的旧 Worker。

## 11. aiokafka 的最小安全消费模式

下面展示真实接口形态；`process_until_durable()` 是业务模块函数的占位抽象，并不是 aiokafka 自带方法：

```python
import asyncio
from aiokafka import AIOKafkaConsumer, TopicPartition

async def process_until_durable(message):
    """业务实现必须只有在结果已持久化、或已确认重复成功时才返回。"""
    raise NotImplementedError

async def main():
    consumer = AIOKafkaConsumer(
        "document-imports",
        bootstrap_servers="localhost:9092",
        group_id="document-indexer-v1",
        enable_auto_commit=False,
        auto_offset_reset="earliest",
    )
    await consumer.start()
    try:
        async for msg in consumer:
            tp = TopicPartition(msg.topic, msg.partition)
            # 该最小示例顺序处理消息，不把 BUSY 当作处理成功。
            await process_until_durable(msg)
            # 只有确认业务结果已经持久化，才推进消费进度。
            await consumer.commit({tp: msg.offset + 1})
    finally:
        await consumer.stop()

asyncio.run(main())
```

### 11.1 此示例故意没有承诺的能力

- 没有完成模型超时、错误类型、重试策略和死信机制；
- 没有实现数据库幂等、租约或任务状态机；
- 没有完成再均衡监听与并发任务隔离；
- 没有保证 `process_until_durable()` 可以无限等待；
- 没有实现跨 Kafka 与 PostgreSQL 的原子提交。

其目的只是展示**可证明安全的 Offset 提交位置**：只有本次记录已被可靠处理，或者被持久化业务状态证明已经处理，才可以推进。实际遇到 `BUSY` 时不应直接把它当成成功；可以等待已存在执行完成、终止当前消费循环以便重投，或使用设计好的持久化后台任务转移机制。

## 12. 发生故障后的恢复决策树

```text
收到消息 / 重新读取消息
            │
            ▼
       验证业务标识
            │
       输入指纹不一致？ ── 是 ─→ 冲突 / 人工处理，不覆盖
            │ 否
            ▼
   数据库里已有最终结果？ ── 是 ─→ 复用结果，允许确认该消息
            │ 否
            ▼
      状态为 RUNNING？
        │ 是          │ 否
        ▼             ▼
      租约有效？      原子认领新任务
      │ 是  │ 否           │
      ▼     ▼              │
     BUSY  新 Worker 接管 ←─┘
      │          │
      │          ▼
      │     执行业务操作
      │          │
      │          ▼
      │    校验代际及权限
      │          │
      │          ▼
      │     事务提交最终结果
      │          │
      │          ▼
      └─ 不得提前确认 ──→ 业务完成后确认 Kafka
```

这个决策树省略了一些复杂生产分支，例如任务已 `FAILED`、取消、超限、第三方结果未知、Redis 不可用和 Rebalance。实际系统必须给这些分支独立状态，不能把它们简单归为 `BUSY` 或 `SUCCESS`。

## 13. 不同故障发生点的恢复矩阵

| 故障发生点 | 数据库可见结果 | Kafka 可能状态 | 正确恢复动作 |
|---|---|---|---|
| 读取消息前崩溃 | 未开始 | Offset 未推进 | 新 Consumer 正常读取 |
| 认领事务提交前崩溃 | 无有效认领 | Offset 未推进 | 消息重投并重新认领 |
| 认领事务提交后、业务处理中崩溃 | RUNNING / 无结果 | Offset 未推进 | 租约过期后重新认领，增加 generation |
| 外部调用后、结果事务前崩溃 | 可能有外部副作用，DB 无结果 | Offset 未推进 | 查询第三方操作状态/幂等重试，不能盲目重复 |
| 最终结果事务提交后、Offset 提交前崩溃 | SUCCEEDED / 有结果 | Offset 未推进 | 重投后复用结果，再提交 Offset |
| Offset 请求发出后失联 | 业务成功 | Kafka 提交是否成功可能未知 | 允许重投，通过 DB 幂等抑制重复 |
| 同业务消息并发到达 | 可能处于 RUNNING | 多条消息在途 | 仅一个执行者获得有效认领，其余等待或复用 |
| 处理期间发生 Rebalance | 旧 Worker 可能已完成业务 | Offset Commit 可能失败 | 新消费者重投 + DB 幂等；旧 Worker 不得越权继续 |

“Offset 请求返回超时”不一定意味着 Broker 未提交。程序必须允许两种情况出现，而不是依赖一次 RPC 返回值猜测世界状态。

## 14. 同时到达的两条不同消息如何去重

举例：

```json
{
  "event_id": "evt-001",
  "tenant_id": "tenant-A",
  "business_key": "import-document-42",
  "payload_hash": "sha256:abc",
  "source": "upload"
}
```

```json
{
  "event_id": "evt-002",
  "tenant_id": "tenant-A",
  "business_key": "import-document-42",
  "payload_hash": "sha256:abc",
  "source": "retry"
}
```

`event_id` 不同意味着它们是两个逻辑事件；但 `business_key` 与输入指纹相同，意味着它们应该落到**同一份最终业务结果**。

而如果两条消息的 `business_key` 相同，`payload_hash` 不同，系统应将其识别为冲突，而不是自动认为后者是合法重试。

## 15. 进程退出与服务优雅停机

### 15.1 正常收到关闭信号

1. 停止认领新任务；
2. 停止/暂停消费或让负载接管新的消息；
3. 对现有任务等待有限的清理时间；
4. 对完成的业务安全提交结果和 Kafka Offset；
5. 对未完成的工作释放或让租约超时，保留恢复所需状态；
6. 关闭 aiokafka Consumer、数据库引擎和 HTTP 客户端。

### 15.2 发生 `SIGKILL` / 容器被强制终止

没有机会运行 `finally`，也不能依赖 `atexit`、进程内 Task Registry 或内存字典恢复。所有能保证恢复的关键数据必须在故障前已经持久化，或者可通过 Kafka 消息重新构造。

### 15.3 租约释放时也要防止“释放了别人的锁”

Worker-A 的租约过期后，Worker-B 取得新租约。此时 A 的清理逻辑若执行无条件：

```sql
UPDATE tasks SET owner=NULL, status='PENDING' WHERE task_id=:id;
```

就会破坏 B 的执行权。正确释放也必须附带 `owner` 和 `generation` 等条件。

## 16. 失败重试、失败终态与死信处理

可靠恢复不代表所有失败都要无限重试。

建议按性质分类：

| 类型 | 示例 | 典型策略 |
|---|---|---|
| 暂时故障 | 连接中断、数据库短暂不可用 | 有限次数 + 指数退避与抖动 |
| 配置故障 | API Key 无效、权限错误 | 终止重试并报警 |
| 永久业务错误 | 不支持的文件、非法数据 | 保存失败原因，转失败终态 |
| 外部结果未知 | API 超时但可能已成功 | 先查询或对账，避免重复副作用 |
| 重复投递 | 已有 `SUCCEEDED` 结果 | 幂等复用，不重新执行 |
| 旧 Worker 迟到 | generation 已过期 | 拒绝写入，保留审计记录 |

对于失败任务，不应让一条坏消息无限阻塞整个分区。可以将失败原因持久化，并在明确的终态或可靠重试转移完成后推进原消息 Offset；如果采用死信队列或重试 Topic，还需要确保失败任务的落库/发布不会出现丢失窗口。

**注意：** “失败后把消息扔到 DLQ 再提交原 Offset”这两步本身也需要设计可靠性。常见方法包括用 Outbox 持久化待发布的失败事件，再由发布程序重试。

## 17. 如果业务结果很大、耗时很长怎么办

例如批量 Embedding 1000 份文件，需要持续数分钟。

不建议把全部工作放进一段长数据库事务，更不应该长时间持有行锁。可以分阶段：

```text
任务认领（短事务）
    ↓
读取文件 / 分批计算 Embedding（事务外）
    ↓
保存可校验的批次进度（短事务）
    ↓
继续处理其他批次
    ↓
校验 generation、最终数据完整性
    ↓
写入最终结果、标记 SUCCEEDED（短事务）
```

其中增量中间结果应带上 `task_id`、批次编号和版本信息；恢复时可识别已完成批次，避免重复计算。但如果某个批次对应第三方 API 费用，重复提交仍可能发生，必须依赖外部幂等或缓存与对账机制。

对具有多阶段副作用的任务，需要设计中间状态与补偿协议，不能仅凭一个 `status` 字段描述全部已发生事实。

## 18. 恢复系统需要哪些可观测性指标

### 18.1 核心记录字段

```json
{
  "task_id": "import-42",
  "tenant_id": "tenant-A",
  "event_id": "evt-001",
  "consumer_group": "document-indexer-v1",
  "topic": "document-imports",
  "partition": 2,
  "offset": 41,
  "worker_id": "worker-B",
  "generation": 8,
  "attempt": 3,
  "status": "SUCCEEDED",
  "last_error_code": null,
  "result_id": "result-42"
}
```

所有字段均为示意值。生产日志应避免打印完整用户隐私数据、模型密钥、访问令牌与大段文档原文。

### 18.2 指标

- 任务总数、RUNNING 数量、租约超期数量；
- 任务重试率、租约抢占率、重复投递命中率；
- Kafka Group Lag、Offset Commit 失败率；
- 最终结果唯一性冲突次数；
- 任务处于 RUNNING 的持续时间分布；
- `SUCCEEDED` 却缺少结果、结果存在却状态非成功的不变量告警；
- 第三方 API 结果未知或需人工对账的数量。

注意 Kafka Lag 仅反映消费进度位置，不直接等于业务任务全部成功；如果先把消息登记进数据库任务表并提前推进 Offset，还需要监控数据库内待处理任务的队列延迟。

## 19. 常见错误及正确替代

| 常见错误 | 为什么错误 | 更合理的方式 |
|---|---|---|
| `SELECT` 不存在再 `INSERT` | 并发检查竞态 | 唯一约束 + 原子写入 |
| 在 `RUNNING` 时立即提交 Kafka | Worker 后续崩溃可能失去重投路径 | 仅在业务已持久化或可靠转移处理权后提交 |
| 任务超过 30 秒就认定旧 Worker 已结束 | 原进程可能只是暂停 | 租约接管 + generation 条件更新 |
| `Redis SETNX` 就保证只执行一次 | 锁可能失效，业务约束仍缺失 | 数据库约束、事务及 Fencing |
| `ON CONFLICT DO NOTHING` 后直接当成功 | 同业务键可能携带不同输入 | 验证 payload_hash 与现有结果 |
| 数据库 COMMIT 后盲目重试模型 API | 外部操作可能已发生 | 第三方幂等键、结果查询与对账 |
| 只保存 `status` 不记录尝试 | 无法解释故障前发生了什么 | 持久化 attempts、错误、时间和执行代际 |
| 异步任务都完成前提交最大 Offset | 可能跳过未完成任务 | 分区顺序处理或安全连续水位 |
| 依赖优雅停机确保一定恢复 | SIGKILL 不运行清理逻辑 | 持久化状态、租约和重投 |
| 进程内锁当成多实例锁 | 只能约束当前进程 | 数据库原子操作与业务唯一性 |

## 20. 故障注入测试应该验证什么

至少需要区分“代码正确执行”“状态正确写入”“重启后正确恢复”三个层次。下面是可执行的测试矩阵：

| 测试 | 注入时机 | 必须检查的结果 |
|---|---|---|
| T1 | 数据库完成后、Kafka Commit 前崩溃 | 重投后只存在 1 条最终结果 |
| T2 | 创建 RUNNING 后进程退出 | 租约失效后可重新认领 |
| T3 | 旧 Worker 在新 Worker 完成后恢复 | 旧 generation 无法提交 |
| T4 | 6 个线程并发认领相同业务 | 至多一个有效认领者 |
| T5 | 同一 event_id 重投 | 事件不重新定义为新业务 |
| T6 | 不同 event_id、相同 business_key | 共用相同业务结果 |
| T7 | 相同 business_key、不同 payload_hash | 抛出冲突，不覆盖数据 |
| T8 | 最终结果插入后、DB Commit 前崩溃 | 结果插入与成功标记一同回滚 |
| T9 | RUNNING 租约未过期 | 第二 Worker 不可接管 |
| T10 | 任务已经 SUCCEEDED | 不能被迟到完成覆盖 |
| T11 | 不同租户使用相同业务键 | 结果分别隔离 |
| T12 | Worker 进程重启 | 数据库中的任务和结果仍然存在 |
| T13 | 重试耗尽进入 FAILED | 重投不自动复活终态 |
| T14 | Kafka Rebalance / Offset Commit 失败 | 不丢失已完成数据库结果，允许消息重新消费 |
| T15 | 同分区处理完成乱序 | 不提交越过未完成消息的 Offset |
| T16 | 外部服务超时但已经执行 | 不盲目重复不可撤销副作用 |

本节提供的离线代码覆盖其中可用 SQLite/线程可靠验证的部分；真实 Kafka Rebalance、Broker 故障与 PostgreSQL 锁语义需要独立集成测试。

## 21. Python 教学实现：核心设计说明

附录 A 提供一份不依赖任何外部服务的 `TaskStore`：

- SQLite 文件数据库模拟**持久化任务状态**；
- `BEGIN IMMEDIATE` 在 SQLite 内部串行化写事务；
- `tasks(tenant,business_key)` 唯一键代表业务唯一性；
- `seen_events` 保留事件身份；
- `final_results` 以唯一键禁止重复最终结果；
- `generation` 与 `owner` 约束迟到 Worker 的写入；
- `lease_until` 允许任务超时接管；
- `complete()` 将状态更新和结果插入放在同一数据库事务；
- 提供 `fail_after_result_insert` 故障注入，确保事务回滚；
- 模拟数据库完成、Kafka 位点未提交后事件重新到达。

这里的 SQLite 原子写事务机制只是一个简洁教学手段。PostgreSQL 的实际 `FOR UPDATE`、并发隔离、行锁等待、死锁处理和多个 Worker 的分区再平衡并不能靠 SQLite 测试代替。

程序还有一个值得注意的细节：`sqlite3.Connection` 的 `with con:` 主要管理事务提交/回滚，**不会自动关闭连接**；示例使用 `contextlib.closing()` 释放连接资源。生产系统应使用数据库连接池与结构化生命周期管理。

## 22. 真实 Kafka + PostgreSQL 集成测试建议

可以将 Kafka、PostgreSQL 与 Worker 放进 Docker Compose，建立以下端到端测试：

1. 向 Kafka 写入同一业务的重复消息；
2. Worker 从分区取得记录并写入 PostgreSQL；
3. 在数据库 COMMIT 之后、Kafka Offset COMMIT 之前强制退出进程；
4. 重启 Worker，观察同一 Offset 是否重新交付；
5. 检查数据库最终结果数量始终为一；
6. 在任务 RUNNING 时强杀 Worker，等待租约超时并运行恢复扫描；
7. 启动两个 Worker 并发竞争同一业务键，核对认领代际和最终结果；
8. 人为触发 Rebalance，验证旧消费者不再继续写入或确认失效分区进度；
9. 运行长时间压力测试，检查有没有任务永久停留 RUNNING；
10. 验证第三方 API 失败与结果未知的处理，不把网络超时当作确定失败。

这是一组**待在真实服务环境中执行的验证方案**，并非本次离线程序已经完成的集成测试。

## 23. 核心结论

1. **结果提交后 Kafka Offset 未提交：** 允许消息重投；通过业务幂等键、唯一结果和事务识别已成功任务，再提交下一 Offset。
2. **Worker 在执行中途退出：** 利用持久化状态与租约判断是否允许重新认领，重领时增加 generation，旧 Worker 不得再写入。
3. **多个重复消息并发到达：** 通过数据库唯一约束与事务原子认领裁决执行权，而非依赖“先检查有没有记录”。
4. **跨系统副作用：** PostgreSQL 事务无法撤销第三方操作，必须设计外部幂等、Outbox、状态查询或对账。
5. **安全提交位点：** 不越过未安全处理的消息；多分区和多线程情况下要明确每个分区的进度与任务归属。
6. **可靠性不是静态配置，而是可验证行为：** 必须人为制造崩溃、重复、并发竞争和重启，检查数据库最终状态与错误记录。

## 附录 A：完整 Python 故障恢复教学实现

以下代码可另存为 `recovery_demo.py`，使用 Python 3.13 标准库运行。

```python
"""Deterministic local lab for Kafka consumer business recovery.

Only sqlite3 is used; this is NOT a Kafka or PostgreSQL integration test.
`now` represents a database-authoritative epoch timestamp in this lab.
"""
from __future__ import annotations

from dataclasses import dataclass
from contextlib import closing
import sqlite3
from pathlib import Path


@dataclass(frozen=True)
class Claim:
    outcome: str
    generation: int | None = None
    result: str | None = None


class TaskStore:
    def __init__(self, path: str | Path) -> None:
        self.path = str(path)
        with closing(self._connect()) as con:
            con.executescript("""
                CREATE TABLE IF NOT EXISTS tasks (
                    tenant TEXT NOT NULL,
                    business_key TEXT NOT NULL,
                    payload_hash TEXT NOT NULL,
                    status TEXT NOT NULL CHECK (
                      status IN ('PENDING','RUNNING','SUCCEEDED','FAILED')
                    ),
                    owner TEXT,
                    generation INTEGER NOT NULL DEFAULT 0,
                    lease_until REAL,
                    attempts INTEGER NOT NULL DEFAULT 0,
                    result TEXT,
                    PRIMARY KEY (tenant, business_key)
                );
                CREATE TABLE IF NOT EXISTS seen_events (
                    event_id TEXT PRIMARY KEY,
                    tenant TEXT NOT NULL,
                    business_key TEXT NOT NULL,
                    payload_hash TEXT NOT NULL
                );
                CREATE TABLE IF NOT EXISTS final_results (
                    tenant TEXT NOT NULL,
                    business_key TEXT NOT NULL,
                    content TEXT NOT NULL,
                    PRIMARY KEY (tenant, business_key)
                );
            """)

    def _connect(self) -> sqlite3.Connection:
        con = sqlite3.connect(self.path, timeout=5, isolation_level=None)
        con.row_factory = sqlite3.Row
        return con

    def claim(
        self, *, event_id: str, tenant: str, business_key: str,
        payload_hash: str, owner: str, now: float, lease_seconds: float = 30,
    ) -> Claim:
        if lease_seconds <= 0:
            raise ValueError('lease_seconds must be positive')
        with closing(self._connect()) as con:
            con.execute('BEGIN IMMEDIATE')  # SQLite-only write serialization
            try:
                con.execute(
                    'INSERT OR IGNORE INTO seen_events VALUES (?, ?, ?, ?)',
                    (event_id, tenant, business_key, payload_hash),
                )
                event = con.execute(
                    'SELECT * FROM seen_events WHERE event_id=?', (event_id,)
                ).fetchone()
                if (event['tenant'], event['business_key'], event['payload_hash']) != (
                    tenant, business_key, payload_hash
                ):
                    raise ValueError('event_id reused for different operation')

                row = con.execute(
                    'SELECT * FROM tasks WHERE tenant=? AND business_key=?',
                    (tenant, business_key),
                ).fetchone()
                if row is None:
                    con.execute(
                        '''INSERT INTO tasks
                           (tenant, business_key, payload_hash, status, owner,
                            generation, lease_until, attempts)
                           VALUES (?, ?, ?, 'RUNNING', ?, 1, ?, 1)''',
                        (tenant, business_key, payload_hash, owner, now + lease_seconds),
                    )
                    outcome = Claim('CLAIMED', 1)
                else:
                    if row['payload_hash'] != payload_hash:
                        raise ValueError('business key reused with different payload')
                    if row['status'] == 'SUCCEEDED':
                        outcome = Claim('ALREADY_SUCCEEDED', result=row['result'])
                    elif row['status'] == 'FAILED':
                        outcome = Claim('TERMINAL_FAILED')
                    elif row['status'] == 'RUNNING' and row['lease_until'] > now:
                        outcome = Claim('BUSY')
                    else:  # PENDING or expired RUNNING
                        generation = row['generation'] + 1
                        con.execute(
                            '''UPDATE tasks SET status='RUNNING', owner=?,
                               generation=?, lease_until=?, attempts=attempts+1
                               WHERE tenant=? AND business_key=?''',
                            (owner, generation, now + lease_seconds, tenant, business_key),
                        )
                        outcome = Claim('CLAIMED', generation)
                con.execute('COMMIT')
                return outcome
            except BaseException:
                con.execute('ROLLBACK')
                raise

    def complete(
        self, *, tenant: str, business_key: str, owner: str,
        generation: int, now: float, result: str,
        fail_after_result_insert: bool = False,
    ) -> bool:
        with closing(self._connect()) as con:
            con.execute('BEGIN IMMEDIATE')
            try:
                updated = con.execute(
                    '''UPDATE tasks SET status='SUCCEEDED', result=?,
                       owner=NULL, lease_until=NULL
                       WHERE tenant=? AND business_key=? AND status='RUNNING'
                         AND owner=? AND generation=? AND lease_until>?''',
                    (result, tenant, business_key, owner, generation, now),
                ).rowcount
                if updated != 1:
                    con.execute('ROLLBACK')
                    return False
                con.execute(
                    'INSERT INTO final_results VALUES (?, ?, ?)',
                    (tenant, business_key, result),
                )
                if fail_after_result_insert:
                    raise RuntimeError('simulated crash before DB commit')
                con.execute('COMMIT')
                return True
            except BaseException:
                con.execute('ROLLBACK')
                raise

    def requeue_expired(self, now: float) -> int:
        """Recovery scanner: change expired RUNNING rows to PENDING."""
        with closing(self._connect()) as con:
            con.execute('BEGIN IMMEDIATE')
            count = con.execute(
                '''UPDATE tasks SET status='PENDING', owner=NULL, lease_until=NULL
                   WHERE status='RUNNING' AND lease_until<=?''', (now,)
            ).rowcount
            con.execute('COMMIT')
            return count

    def get_task(self, tenant: str, business_key: str) -> dict | None:
        with closing(self._connect()) as con:
            r = con.execute(
                'SELECT * FROM tasks WHERE tenant=? AND business_key=?',
                (tenant, business_key),
            ).fetchone()
            return dict(r) if r else None

    def result_count(self, tenant: str, business_key: str) -> int:
        with closing(self._connect()) as con:
            return con.execute(
                'SELECT COUNT(*) FROM final_results WHERE tenant=? AND business_key=?',
                (tenant, business_key),
            ).fetchone()[0]

    def event_count(self) -> int:
        with closing(self._connect()) as con:
            return con.execute('SELECT COUNT(*) FROM seen_events').fetchone()[0]

    def fail_permanently(
        self, *, tenant: str, business_key: str, owner: str,
        generation: int, now: float,
    ) -> bool:
        with closing(self._connect()) as con:
            con.execute('BEGIN IMMEDIATE')
            count = con.execute(
                '''UPDATE tasks SET status='FAILED', owner=NULL, lease_until=NULL
                   WHERE tenant=? AND business_key=? AND status='RUNNING'
                     AND owner=? AND generation=? AND lease_until>?''',
                (tenant, business_key, owner, generation, now),
            ).rowcount
            con.execute('COMMIT')
            return count == 1


def demonstration(db_path: str) -> list[str]:
    store = TaskStore(db_path)
    args = dict(tenant='acme', business_key='import-42', payload_hash='sha256:x')
    first = store.claim(event_id='event-1', owner='worker-A', now=100, **args)
    assert first.outcome == 'CLAIMED'
    assert store.complete(tenant='acme', business_key='import-42', owner='worker-A',
                          generation=first.generation, now=110, result='indexed=15')
    # Crash before Kafka offset commit -> redelivery on restart.
    replay = store.claim(event_id='event-1', owner='worker-B', now=120, **args)
    assert replay.outcome == 'ALREADY_SUCCEEDED'
    return [first.outcome, 'SIMULATED_CRASH_BEFORE_OFFSET_COMMIT',
            replay.outcome, f'final_results={store.result_count("acme", "import-42")}']


if __name__ == '__main__':
    from tempfile import TemporaryDirectory
    with TemporaryDirectory() as folder:
        for line in demonstration(str(Path(folder) / 'tasks.db')):
            print(line)

```

from pathlib import Path
import threading

class RecoveryTests(unittest.TestCase):

        self.assertEqual(c.generation, 2)
