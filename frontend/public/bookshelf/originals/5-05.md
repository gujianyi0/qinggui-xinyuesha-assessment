## 1. Redis 在系统中的角色

Redis 是以内存访问为主要性能优势的数据存储系统。常见用途有：热点查询缓存、计数器、短期会话辅助状态、临时任务进度、限流窗口、短时去重标记、排行榜和实时消息功能。Redis 能根据部署配置采用快照或追加日志进行持久化，但这**不意味着任何 Redis 键都适合成为业务真相的唯一副本**。

在一个 AI 问答与反馈系统里，建议把数据按照“丢失后是否允许重建”和“是否需要跨故障恢复”划分：

| 数据示例 | 逻辑性质 | 典型主存储 | Redis 职责 | 丢失 Redis 时 |
|---|---|---|---|---|
| 游戏资料当前版本 | 可审计的事实记录 | PostgreSQL | 相关检索/版本读缓存 | 从 PostgreSQL 重建 |
| Agent 会话与最终消息 | 持久业务历史 | PostgreSQL | 可选的近期查询缓存 | 历史不应丢失 |
| 已确认的反馈记录 | 强一致业务结果 | PostgreSQL，约束/事务 | 通常不承担唯一真相 | 不得重建出重复反馈 |
| 长任务最终状态 | 需恢复、查询的业务状态 | PostgreSQL | 缓存最近状态 | 以 PostgreSQL 为准 |
| 长任务“当前约完成 60%” | 可丢弃的临时进度 | Redis | 保存短期进度，附 TTL | 前端显示未知进度或回查 |
| 资料检索结果 | 可重算的派生数据 | 向量索引/原始资料 | 缓存查询结果 | 重新检索 |
| 每分钟临时计数 | 短期窗口状态 | Redis（依场景） | 原子自增并按期到期 | 按定义降级/拒绝，不可随意假设可靠 |
| 支付/发送操作幂等凭据 | 直接决定不可逆副作用 | PostgreSQL 等可靠账本 | 可选加速、短时拦截 | 不能仅靠易过期的键保证唯一 |

把 Redis 作为缓存，与把 Redis 当成业务数据库，是**不同的工程选择**。Redis 可以配置持久化以承担更重要的数据角色，但需要单独论证故障模型、数据丢失窗口、复制一致性、备份与恢复，不能直接套用“缓存丢了也没关系”的前提。

## 2. Key（键）的组成、命名、命名空间

Redis 的数据项通常以 `key -> value` 的方式访问；键本质上是二进制安全的字节序列，应用程序为了可维护性一般使用可读的字符串键。

### 2.1 推荐命名方式

```text
cache:profile:v1:tenant-42:user-1001
temp:run-progress:run-7f3a
rate-limit:api:user-1001:2026-11-12T08:00
lock:document-index:doc-22
```

结构常采用 `用途:实体:模式版本:租户:对象标识`。分隔符 `:` 只是约定，不是 Redis 强制语法。业务标识应进行规范化或编码：如果 ID 本身可包含 `:`，直接拼接容易产生歧义或键碰撞。多租户查询还必须在**后端授权后**生成键，不能只依赖客户端传来的 `tenant_id`。

键的设计至少考虑：

- **唯一范围**：全局、租户、用户、会话还是运行实例？
- **数据版本**：更改序列化结构或检索策略后，旧键应否被读取？
- **TTL 规则**：每次读取是否刷新过期时间？是否允许永久不过期？
- **删除策略**：业务更新时删除哪些缓存键？
- **隐私风险**：键名是否包含邮箱、手机号、访问令牌或明文敏感数据？
- **内存成本**：大量小键也会带来显著元数据开销。

`KEYS *` 可能对大型生产库造成负担；遍历时通常使用增量 `SCAN`，仍需要谨慎安排频率。`SCAN` 是渐进式遍历，不承诺操作期间动态变化键集合的完整一致快照。

### 2.2 命名空间不能代替权限隔离

`cache:tenant-a:*` 和 `cache:tenant-b:*` 分开命名，解决的是避免键冲突，不会自动实现租户授权。若应用持有 Redis 的广泛读写凭据，任何后端代码错误都可能读取其他租户的数据。需要在业务层验证已认证身份与资源归属，必要时通过 Redis ACL、独立实例、独立凭据或更严格的网络隔离减小风险。

## 3. 常见 Redis 数据类型与访问命令

| Redis 类型 | 典型命令 | 适合存储什么 | 关键注意事项 |
|---|---|---|---|
| String | `GET`、`SET`、`INCR`、`MGET` | JSON 字符串、数值计数、短暂凭据 | `SET` 默认覆盖原值与旧 TTL |
| Hash | `HSET`、`HGET`、`HGETALL`、`HINCRBY` | 小型对象与字段计数 | Hash 字段与 key 的 TTL 不是一回事；部分新版本有字段级过期 |
| List | `LPUSH`、`RPOP`、`BLPOP` | 有序元素、简单工作列表 | 不等于带确认与恢复的可靠任务队列 |
| Set | `SADD`、`SISMEMBER`、`SREM` | 去重集合、临时标签集合 | 无序，集合大小影响内存 |
| Sorted Set | `ZADD`、`ZRANGE`、`ZREM` | 排名、按时间排序的任务 | 需要明确分数与排序语义 |
| Stream | `XADD`、`XREADGROUP`、`XACK` | 消息事件、消费组 | 需配置保留、Pending 与重试等机制 |

多数基础数据类型都依附于一个顶层 key，其是否存在与 TTL 往往由这个 key 管理。复杂结构的字段级 TTL、流消费组等是扩展主题，不应把它们混成通用规则。

```redis
SET cache:greeting "你好" EX 60
GET cache:greeting
HSET temp:import:42 progress 65 stage embedding
HGETALL temp:import:42
INCR rate:user-1:minute-10
SADD temp:active-users user-1
```

以上是 Redis CLI 命令示意。键的访问权限、类型错误以及并发更新语义需要在真实环境中另行测试。

## 4. TTL 是什么：生存时间与过期时间

**TTL（Time To Live）** 是键允许存活的剩余时间。在 Redis 中可以设定相对过期时间，也可以设定绝对到期时间。

```redis
SET cache:answer "..." EX 60
TTL cache:answer
PTTL cache:answer
EXPIRE cache:answer 120
PERSIST cache:answer
```

- `SET ... EX 60`：写入字符串，并设置 60 秒的相对过期时间。
- `EXPIRE key 120`：设置相对过期时间，单位是秒。
- `PEXPIRE key 1500`：设置相对过期时间，单位是毫秒。
- `EXPIREAT`/`PEXPIREAT`：以 Unix 时间戳设定到期时刻。
- `TTL`/`PTTL`：查看剩余时间，单位分别是秒/毫秒。
- `PERSIST`：去掉已有的过期时间，让键继续保留（直到显式删除、驱逐或其他原因消失）。

### 4.1 `TTL` 的返回值

| 返回值 | 准确含义 |
|---|---|
| `>= 0` | 剩余生存时间，秒级精度 |
| `-1` | 键存在，但没有设置过期时间 |
| `-2` | 键不存在，或在访问时已经到期 |

`TTL = -1` **绝不是**“已经过期”。这是实际排错中非常常见的混淆。

### 4.2 `SET` 如何影响 TTL

```redis
SET temp:a "first" EX 20
TTL temp:a
SET temp:a "second"
TTL temp:a
```

第二次 `SET` 默认会清除原 TTL，因此最终 `TTL temp:a` 为 `-1`。如需继续保留过期时间，可以在支持的 Redis 版本中使用 `SET ... KEEPTTL`。`INCR` 这类原地修改字符串数值的操作通常会保留 key 的现有 TTL。具体命令是否保留 TTL，应查阅各自文档，不应从“写操作”一概推断。

### 4.3 条件式过期

Redis 的 `EXPIRE` 支持 `NX`、`XX`、`GT`、`LT` 等条件（这些选项从 Redis 7.0 开始支持）：

```redis
EXPIRE temp:a 60 NX
EXPIRE temp:a 120 GT
```

- `NX`：键还没有过期时间时才设置。
- `XX`：键已经有过期时间时才设置。
- `GT`：新到期时间比现有到期时间更晚才设置。
- `LT`：新到期时间比现有到期时间更早才设置。

注意：这些条件比较的是过期状态/截止时间，不是在业务层确认数据版本。某个临时任务应否续期，需要另加业务判定。

### 4.4 惰性过期与主动过期

Redis 结合两种机制清理到期键：

1. **被动（惰性）过期**：访问某个键时检查是否已过期。
2. **主动过期**：Redis 在后台周期性抽样检查并清理已到期键。

因此，业务逻辑应把“已到期的键不可再作为有效数据”与“底层占用内存何时完全回收”区分开。TTL 不是一个保证在某毫秒触发业务回调的调度器，更不能作为支付、发送或数据库事务的唯一完成依据。

## 5. 过期（Expiration）与逐出（Eviction）不一样

过期由键自己的有效期决定。**逐出**由内存容量与 `maxmemory-policy` 决定：缓存键可能在 TTL 还没到时就被逐出。

常见策略：

| 策略 | 行为 |
|---|---|
| `noeviction` | 达到内存限制后拒绝会增加内存占用的写入，而非自动删除旧键 |
| `allkeys-lru` | 从所有键中近似淘汰近期较少使用的键 |
| `allkeys-lfu` | 从所有键中近似淘汰访问频率较低的键 |
| `volatile-lru` | 仅在设置过 TTL 的键中选出近期较少使用的键 |
| `volatile-ttl` | 倾向于驱逐剩余 TTL 较短的键 |

策略可能随 Redis 版本和产品形态增加新选项，应核对实际部署版本。`maxmemory-policy` 决定的是内存压力下的行为，不会提供业务级完成保障。

**重要推论：如果任务最终结果只放 Redis，键即使尚未到期也可能消失；如果设置了 `noeviction`，缓存更新可能开始报错。** 两者都需要被应用显式处理。

## 6. Redis 的“原子操作”到底意味着什么

原子性至少要分清三个层面：

1. **单条 Redis 命令的原子执行**：一个命令执行期间，不会与其他客户端普通命令的内部步骤交错。
2. **多条 Redis 命令的组合原子性**：必须使用事务、脚本或其他符合需要的服务端机制。
3. **跨系统业务原子性**：Redis 与 PostgreSQL、Kafka、外部邮件 API 之间，不能依靠 Redis 命令原子性直接实现。

例如，以下两步有竞态：

```python
value = int(await redis_client.get("counter") or 0)
await redis_client.set("counter", value + 1)
```

两个进程都可能读取 10，然后都写 11，丢失一次更新。

更合理的是：

```python
new_value = await redis_client.incr("counter")
```

`INCR` 把读取、计算和更新合并为服务端单条原子命令。但它**只保证这个 Redis 键的更新语义**，不会同步更新 PostgreSQL，也不会自动设置 TTL 或提供持久业务账本。

## 7. `SET NX EX`：原子式“不存在才写入”

```redis
SET temp:once:job-7 token-123 NX EX 30
```

含义是在同一条命令里：

- `NX`：仅在键不存在时写入。
- `EX 30`：同时赋予 30 秒有效期。

这比“先 `SETNX` 再单独 `EXPIRE`”更不容易出现服务在两条命令之间崩溃导致键永久留下的问题。

Python 异步客户端可写为：

```python
ok = await redis_client.set(
    "temp:once:job-7", "token-123", nx=True, ex=30
)
if ok:
    print("本次暂时获得执行资格")
else:
    print("键尚未过期，已有其他持有者")
```

**边界：`SET NX EX` 不等于永久的业务幂等。** 键会到期、可被逐出或因 Redis 故障丢失；不能据此推断“永久不会重复发送”。对于不可重复的反馈创建、付款或邮件发送，应使用可靠的数据库业务唯一约束、操作账本和外部服务支持的幂等机制。

## 8. 多条操作如何组合：Pipeline、MULTI/EXEC、WATCH

### 8.1 Pipeline 主要是减少往返

如果需要连续发送多条 Redis 命令，客户端可以使用 Pipeline 将命令批量提交，提高效率。但**Pipeline 并不天然等于数据库事务**；不同客户端、配置和 `transaction` 参数会影响是否使用事务封装。

```python
async with redis_client.pipeline(transaction=False) as pipe:
    pipe.set("cache:a", "1", ex=60)
    pipe.set("cache:b", "2", ex=60)
    values = await pipe.execute()
```

上面的代码是批量执行，并不主张它具有完整事务原子性。

### 8.2 `MULTI` / `EXEC` 的保证

Redis 事务使用 `MULTI`、`EXEC`、`DISCARD`。`EXEC` 执行队列中的命令时，不会被其他客户端的普通命令插入其中。

```redis
MULTI
INCR count:a
INCR count:b
EXEC
```

注意 Redis 事务**并不是 PostgreSQL 的 ACID 回滚事务**：事务内某条命令在执行期间出现错误，并不保证已执行的其他命令自动回滚。因此，不应以为 `MULTI/EXEC` 可以直接替代 PostgreSQL 的业务事务。

### 8.3 `WATCH` 提供乐观并发检查

```redis
WATCH counter
GET counter
MULTI
SET counter 101
EXEC
```

程序实际应根据 `GET` 的值构造更新。若被监视的键在 `WATCH` 到 `EXEC` 之间发生冲突，`EXEC` 会失败，程序需要有界重试。典型做法是配合 `redis-py` 的 Pipeline 和 `WatchError`。

这与 SQLAlchemy 的 `version_id_col` 类似地体现了乐观并发控制思想，但**Redis WATCH 不能取代 PostgreSQL 的行版本约束**。

## 9. Lua 脚本：多步骤 Redis 逻辑的服务端原子执行

限流计数经常需要同时完成两件事：增加计数，第一次增加时设置 TTL。

容易出错的写法：

```python
count = await redis_client.incr(key)
if count == 1:
    await redis_client.expire(key, 60)
```

如果进程恰好在 `INCR` 后崩溃，TTL 可能没设置，计数键长期存在。Redis 官方对 `INCR` 限流示例也特别说明了这种竞态。

可以使用服务端 Lua：

```lua
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('EXPIRE', KEYS[1], tonumber(ARGV[1]))
end
return count
```

```python
script = """
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('EXPIRE', KEYS[1], tonumber(ARGV[1]))
end
return count
"""
count = await redis_client.eval(script, 1, "rate:user-17:fixed-window", 60)
allowed = count <= 20
```

此时 `INCR` 与首次 `EXPIRE` 在 Redis 内作为一个脚本执行，不会被其他客户端普通命令插入。不过：

- Lua 原子执行**不等于出错自动回滚所有先前写入**。
- 脚本运行期间会阻塞 Redis 对其他命令的处理，应避免长时间计算或不受控循环。
- 客户端超时不等于脚本一定没有执行；不应盲目重试具有副作用的脚本。
- 这只是固定窗口计数的示例，不是完整生产级限流方案；还要考虑窗口对齐、限额配置、拒绝计数、Redis 不可用时的处理策略。

## 10. 简单分布式锁的边界

`SET key random-token NX PX milliseconds` 可建立一个带时限的临时占用标记：

```redis
SET lock:index:doc-42 f45be4 NX PX 30000
```

释放时不能简单 `DEL lock:index:doc-42`，因为原持有者超时后，另一位持有者可能已经重新获得该键。旧持有者如果无条件删除，就会误删新锁。

应使用原子式“值仍等于我的 token 才删除”，如匹配部署版本的条件删除命令或 Lua 比较后删除。即便这样也无法自动保证外部 PostgreSQL 更新不会被过期持有者继续执行。

关键问题包括锁过期、进程暂停、网络分区、主从故障切换以及**Fencing Token（防陈旧持有者令牌）**。重要业务写入的最终正确性应由数据库版本条件、唯一约束、事务等机制兜底。Redis 官方分布式锁文档也特别讨论了这些一致性风险。

## 11. Cache-Aside：最常见的缓存设计

Cache-Aside（旁路缓存）将 PostgreSQL 视为权威数据源，Redis 只保存可重建的查询结果。

### 11.1 读路径

```text
用户查询
  ↓
Redis GET
  ├─ 命中 → 返回缓存（确认键与版本/权限符合约定）
  └─ 未命中 → 查询 PostgreSQL
               ↓
             结果写 Redis（附 TTL）
               ↓
             返回结果
```

### 11.2 写路径

```text
业务修改 → PostgreSQL 事务提交成功 → 删除或失效相关 Redis 缓存键
```

关键原则是**先在权威数据源完成提交，再处理缓存的可见性**。如果先删缓存、后提交数据库，其他请求可能在中间重新把旧数据填入缓存。

但“先提交再删缓存”也不是绝对无竞态：读请求可在写入提交前读到旧数据、之后才回填缓存。严格一致性场景需考虑版本化缓存键、数据库版本校验、延迟双删的局限或干脆绕过缓存。

### 11.3 失效、更新与回源的区别

- **Invalidate**：删除旧缓存，让下次查询重新从数据库加载。
- **Refresh**：主动重新计算缓存。
- **Write-through**：更新数据库时同步处理缓存，但仍需处理跨系统失败。
- **Write-behind / Write-back**：先写缓存，稍后异步写数据库；如果失败，丢失尚未落库数据的风险显著增大。

写回策略不能仅凭“Redis 更快”决定，需要结合数据丢失容忍度、重复操作和故障恢复机制。

## 12. 一致性、缓存版本和陈旧数据

TTL 只提供一个**缓存存在时间的上限**，不保证过期前与数据库实时一致；在读写竞态时，一条刚写入 Redis 的缓存也可能是旧内容。

### 12.1 最典型的读写竞态

```text
时间点 1：读请求 R 发现缓存未命中
时间点 2：R 从数据库读取旧版本 v1
时间点 3：写请求 W 提交新版本 v2
时间点 4：W 删除缓存
时间点 5：R 把旧版本 v1 回填到缓存
```

结果：缓存内又出现旧版本 v1。

### 12.2 常见缓解方法

- 对数据变化很少、允许短期过期的读路径：设置较短 TTL，并接受有界陈旧。
- 对经常更新的对象：使用版本号，把版本包含在键名或缓存值中，并在读取时验证业务版本。
- 对必须强一致的操作：读取 PostgreSQL、采用事务/行版本机制，不把 Redis 缓存作为最终裁决依据。
- 对重要缓存失效：记录更新事件、监控删除失败、必要时用 Outbox 安排重试，但要考虑乱序和重放。

不能简单声称“缓存 TTL 是 60 秒，所有读结果最多陈旧 60 秒”：这还取决于谁负责 TTL 刷新、并发回填以及故障时是否继续使用旧值。

## 13. 缓存穿透、击穿和雪崩

这是缓存系统的三个不同问题：

### 13.1 缓存穿透（Penetration）

用户不断查询根本不存在的数据，Redis 总是未命中，全部访问数据库。缓解措施包括：输入校验、有限时间的空结果缓存、布隆过滤器等。

空值缓存必须带短 TTL，且写入真实数据时需要处理失效，否则新创建的数据可能短暂“查不到”。权限受限或越权请求**不应该通过共享空值缓存混淆成不存在**。

### 13.2 热点键击穿（Stampede / Hot-Key Breakdown）

热门键到期，大量请求同时回源，造成数据库突发负载。可使用有界的请求合并（singleflight）、限制并发回源、预热和抖动 TTL。

### 13.3 大批键同时到期（Avalanche）

大量键在同一时间失效或 Redis 服务整体不可用，大量流量落到数据库。常见缓解措施：合理 TTL 分布、加入随机抖动、分层限流、回源并发控制、熔断与降级。

例如基准 TTL 300 秒，可以按场景随机分散到 270～330 秒。随机抖动是降低同时失效概率，并不提供严格的过期上界保证。

## 14. 缓存、临时状态与持久化业务记录的分工

### 14.1 缓存：可以丢、可以重建

缓存是可从其他可靠来源重新推导的数据。适合：

- 最近查询的用户展示名称、公开角色资料。
- 检索候选结果，键中包含资料版本和检索策略版本。
- 价格展示或其他可重复计算的数据，前提是业务允许短暂陈旧。

一个健壮的缓存系统，Redis 全部清空后，最多导致性能下降或可接受的延迟增加，不能永久丢失权威记录。

### 14.2 临时状态：可以过期，但应该明确“丢失意味着什么”

例如资料导入任务：

```text
PostgreSQL:
  task_id = run-17
  state = RUNNING
  attempt = 2
  updated_at = ...

Redis:
  temp:progress:run-17 = 65
  TTL = 30s
```

Redis 中的进度数字可能在 Worker 重启、服务切换或 TTL 到期后消失，此时前端不能把进度缺失直接解释成任务失败或完成。应回查 PostgreSQL 的权威状态，并把进度展示为“未知/等待更新”。

业务上必须保留的任务 `SUCCEEDED`、`FAILED`、`CANCELLED` 和最终结果，不应该只依赖会过期的缓存键。

### 14.3 持久化记录：必须可审计、可恢复、可约束

例如反馈确认：

```sql
CREATE TABLE feedbacks (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    user_id TEXT NOT NULL,
    confirmation_id TEXT NOT NULL,
    content JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, user_id, confirmation_id)
);
```

使用 PostgreSQL 唯一约束及事务，确保同一个确认业务不会被重复插入。Redis 可以临时缓存提交状态，**但不能用一个会过期的 `SET NX` 作为唯一性保障的最终替代品**。

## 15. 临时计数器、限流与长期统计

同一个“计数”字眼可能对应三类不同需求：

| 需求 | 示例 | 处理方式 |
|---|---|---|
| 临时窗口计数 | 每用户每分钟 API 请求数 | Redis 原子计数 + TTL，明确故障策略 |
| 用于实时展示的近似指标 | 正在运行的任务数 | Redis 聚合/应用指标，可重建 |
| 财务、计费、审计统计 | 已支付金额、应收账款、调用费账单 | PostgreSQL 或专门账本，保留不可篡改来源 |

`INCR` 原子性只解决“并发计数不丢更新”，并不自动解决“一次业务事件是否应该计数一次”。例如网络重发同一个计费事件，原子执行两次 `INCR` 仍会统计为两次；需要从数据库业务事件 ID 去重。

## 16. Redis 持久化：RDB、AOF、复制的边界

Redis 可配置：

- **RDB（快照）**：按时间点保存数据集的快照。故障可能丢失上次快照后的修改。
- **AOF（追加日志）**：记录写命令以便重放，具体数据丢失窗口取决于 `appendfsync` 等配置与故障类型。
- **RDB + AOF**：可组合使用，仍需备份、恢复演练和故障模型评估。
- **无持久化**：适用于可以完整重建的数据缓存。

复制、主从切换、AOF 和 RDB 关注的是不同方面：**复制不等于同步强一致提交，持久化也不等于业务级精确一次执行。**

如果选择使用 Redis 持久化保存重要状态，必须对 RPO（最大可接受数据丢失量）、RTO（可恢复时间）、磁盘故障、主从切换、AOF fsync 行为和重放造成的副作用作明确评估。

## 17. Redis 不可用时的降级策略

系统需要分别处理“键不存在”和“Redis 请求失败”：

- `GET` 返回缺失：正常缓存未命中，可以回源。
- 网络超时、认证失败、连接池耗尽：是基础设施错误，不能一律当作缓存缺失。
- `SET` 失败：如果 Redis 只负责派生缓存，可在日志中记录后继续返回数据库结果。
- Redis 是安全限流或严格容量控制的组成部分：应明确 Fail-open 或 Fail-closed，不能随意绕过约束。

| 场景 | 常见降级选择 | 潜在风险 |
|---|---|---|
| 查询展示性缓存 | 绕过 Redis 读取权威库 | 大量回源可能压垮数据库 |
| 临时进度缓存 | 标记进度未知，回查业务状态 | 用户暂时看不到精确进度 |
| 可丢失的热点统计 | 暂停统计，记录监控事件 | 数字不完整 |
| 权限校验与关键频控 | 依业务安全要求拒绝或使用替代强制控制 | Fail-open 可能越权或超额使用 |
| 不可逆操作幂等 | 只按持久化业务账本继续处理 | 延迟增加，但避免重复执行 |

对于 Redis 超时和连接失败应设置较短的超时、有限重试、熔断与并发上限，避免大量请求堆积并拖慢 FastAPI 事件循环。

## 18. Python 访问 Redis：同步与异步客户端

`redis-py` 提供同步 `redis.Redis` 和异步 `redis.asyncio.Redis`。FastAPI 的 `async def` 路由中通常使用异步客户端，避免在事件循环线程上执行同步网络 I/O。

安装（具体版本应由项目锁文件固定）：

```bash
python -m pip install redis
```

基础异步操作：

```python
import asyncio
import redis.asyncio as redis

async def main():
    async with redis.Redis(
        host="127.0.0.1",
        port=6379,
        decode_responses=True,
        socket_connect_timeout=2,
        socket_timeout=2,
    ) as client:
        await client.set("cache:hello", "world", ex=60)
        result = await client.get("cache:hello")
        remaining = await client.ttl("cache:hello")
        print(result, remaining)

asyncio.run(main())
```

### 18.1 连接复用与关闭

每个请求都创建新的 Redis 客户端，会造成频繁连接与资源浪费。通常共享应用级 Redis 客户端与其连接池；应用停止时调用 `await client.aclose()`。

Redis 的 Pipeline 和 PubSub 是有状态对象，不宜在无额外协调的情况下被多个并发任务共享；可以复用客户端，但要让每个任务管理自己使用的 Pipeline/PubSub 生命周期。

### 18.2 客户端取消与执行是否完成

请求超时可能发生在服务端执行完成、客户端尚未收到结果的时间段。因此，对 `INCR`、写入锁、发送消息等带副作用的操作，**超时并不意味着没有执行**。需要基于操作幂等性、结果读取或业务账本决定是否重试。

## 19. FastAPI `lifespan` 中的 Redis 生命周期

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI, Request
import redis.asyncio as redis

@asynccontextmanager
async def lifespan(app: FastAPI):
    client = redis.Redis(
        host="127.0.0.1",
        port=6379,
        decode_responses=True,
        socket_connect_timeout=2,
        socket_timeout=2,
        max_connections=50,
    )
    # 此处根据业务需要决定 Redis 启动不可用是否阻止应用启动。
    app.state.redis = client
    try:
        yield
    finally:
        await client.aclose()

app = FastAPI(lifespan=lifespan)

@app.get("/cache-demo/{name}")
async def cache_demo(name: str, request: Request):
    client = request.app.state.redis
    value = await client.get(f"cache:demo:{name}")
    return {"value": value}
```

这只是生命周期示例。生产系统必须明确缓存 Key 的参数校验、认证授权、Redis 不可用的错误处理、连接池容量以及敏感数据策略。不能仅凭一个 `PING` 就认定所有业务依赖已就绪。

## 20. Redis + PostgreSQL：推荐数据模型与更新顺序

```text
           用户/前端
               |
             FastAPI
               |
          业务 Service
          /           \
 Redis（派生缓存）  PostgreSQL（权威业务数据）
   TTL/逐出           约束/事务/历史版本
   /     \                 |
读命中   读未命中 ----------+
               回源后可回填缓存
```

建议维护一份清晰的数据职责清单：

| 对象 | Redis Key 示例 | TTL 示例 | 最终真相 |
|---|---|---|---|
| 用户头像展示数据 | `cache:profile:v2:t:u` | 60 秒 | PostgreSQL |
| 检索候选 | `cache:rag:v3:hash(query,version,scope)` | 300 秒 | 向量索引 + 文档版本 |
| 导入任务进度 | `temp:progress:run-id` | 30 秒 | PostgreSQL 任务状态，不保存精确瞬时进度 |
| 固定窗口限流计数 | `rate:user-1:minute-...` | 60 秒附近 | Redis 为实时窗口控制；关键账单另存 |
| 写入幂等键 | `temp:request:id` | 短期、按需 | PostgreSQL 持久确认记录 |

以上 TTL 只是教学示例。应按数据更新频率、缓存命中率、可接受陈旧窗口和可用性指标选择，而不是把“60 秒”视作通用最优值。

## 21. 监控 Redis 不能只看命中率

应关注：

- **缓存命中率**：命中次数 /（命中 + 未命中）。
- **Redis 请求耗时**：P50/P95/P99、超时占比、连接池等待时间。
- **回源压力**：缓存未命中导致的 PostgreSQL 查询速率及连接池负载。
- **过期/逐出**：`expired_keys`、`evicted_keys` 与业务预期是否一致。
- **内存压力**：`used_memory`、`maxmemory`、内存碎片、客户端数量。
- **高频键**：热点 Key 与大 Key 的访问频次和内存占用。
- **Redis 持久化与复制**：若启用，关注 AOF/RDB 状态和副本延迟。
- **缓存正确性**：陈旧命中率、版本错配、无权限命中、回填失败。

需要区分 Redis 自身的 `keyspace_hits`/`keyspace_misses` 与业务请求级命中率：Redis 命令级统计可能包含非业务缓存的读取。

指标监控不应记录 Redis 值中的密钥、个人消息正文或完整访问令牌。错误日志宜记录脱敏的键类别和关联请求 ID。

## 22. 测试与故障注入应覆盖什么

一个合理的 Redis 方案至少验证：

1. 缓存未命中能回源，回源成功才写缓存。
2. 缓存键到期或被清空，不会丢失 PostgreSQL 权威记录。
3. 更新已提交后，缓存失效；并发回填场景有明确陈旧容忍度或防护。
4. TTL 为 `-1`、`-2` 时采取不同处理。
5. `SET NX EX` 重复竞争只有一方成功；到期后允许新持有者。
6. `INCR` 并发调用不出现典型读-改-写的丢失更新。
7. Redis 断开时按业务分类降级，而不是假装缓存命中。
8. 临时进度过期不自动改变任务最终状态。
9. `noeviction` 写入失败与逐出策略触发时行为可解释。
10. 不同租户、不同版本的缓存键不能混用；业务授权仍在后端验证。
11. 多命令组合需要实测并发和失败路径；不可只看正常情况。
12. 数据库写入失败时不得错误更新 Redis 为“成功”。

**注意测试证据等级**：`FakeRedis` 可以测试应用对指定返回值的处理，不能证明真实 Redis 的网络行为、Lua 执行、Sentinel/Cluster、AOF 耐久或故障切换语义。真实集成测试需使用固定 Redis 版本及实际 Docker/本机服务。

## 23. 可运行教学示例：权威数据与可丢失缓存

以下演示用 SQLite 表示持久化权威数据库，用可控时钟的内存缓存模拟 Redis 关键语义：`GET`、`SET EX NX`、`TTL`、`INCR` 和 `DELETE`。目标是验证数据分工与失效处理，而不是复刻 Redis 本身。

**演示性质**：

- 无需 Redis 服务端和付费 API，Python 标准库可运行。
- 通过 SQLite 证明“Redis 类比缓存清空后，权威记录仍存在”。
- 通过 `FakeClock` 让 TTL 测试无需真实等待。
- 用线程锁模拟单个缓存实例的原子递增，**不代表跨进程真实 Redis 的集群语义**。
- `ProfileService` 只做教学用缓存回源，没有实现分布式并发缓存一致性、认证和生产级回源限流。

完整演示代码如下。

```python
"""离线教学模型：以 SQLite 表示权威数据库，以内存对象模拟 Redis 语义。
注意：这不是 Redis 服务端、真实 TTL 引擎或分布式一致性测试。
"""
from __future__ import annotations

import json
import sqlite3
import threading
from dataclasses import dataclass
from contextlib import closing
from pathlib import Path
from typing import Callable


class CacheUnavailable(RuntimeError):
    pass


class FakeClock:
    def __init__(self):
        self.now = 1000.0

    def advance(self, seconds: float):
        self.now += seconds


class FakeRedis:
    def __init__(self, now: Callable[[], float]):
        self._now = now
        self._data: dict[str, tuple[str, float | None]] = {}
        self._guard = threading.RLock()
        self.online = True

    def _check(self):
        if not self.online:
            raise CacheUnavailable("cache offline")

    def _purge(self, key: str):
        current = self._data.get(key)
        if current is not None and current[1] is not None and current[1] <= self._now():
            self._data.pop(key, None)

    def get(self, key: str) -> str | None:
        with self._guard:
            self._check()
            self._purge(key)
            item = self._data.get(key)
            return None if item is None else item[0]

    def set(self, key: str, value: str, *, ex: int | None = None,
            nx: bool = False) -> bool:
        with self._guard:
            self._check()
            self._purge(key)
            if nx and key in self._data:
                return False
            if ex is not None and ex <= 0:
                raise ValueError("ex must be positive")
            expires_at = None if ex is None else self._now() + ex
            self._data[key] = (value, expires_at)
            return True

    def delete(self, key: str) -> int:
        with self._guard:
            self._check()
            self._purge(key)
            return int(self._data.pop(key, None) is not None)

    def ttl(self, key: str) -> int:
        import math
        with self._guard:
            self._check()
            self._purge(key)
            item = self._data.get(key)
            if item is None:
                return -2
            if item[1] is None:
                return -1
            return max(0, math.ceil(item[1] - self._now()))

    def incr(self, key: str) -> int:
        with self._guard:
            self._check()
            self._purge(key)
            item = self._data.get(key)
            value = int(item[0]) + 1 if item is not None else 1
            # Redis INCR 保留原 TTL；新建 key 默认没有过期时间
            self._data[key] = (str(value), item[1] if item else None)
            return value


@dataclass(frozen=True)
class Profile:
    tenant_id: str
    user_id: str
    display_name: str
    version: int


class ProfileService:
    """权威数据写 SQLite；Redis 仅作加速读取的可丢失缓存。"""
    TTL_SECONDS = 60

    def __init__(self, db_path: Path, cache: FakeRedis):
        self.db_path = db_path
        self.cache = cache
        with closing(sqlite3.connect(db_path)) as db, db:
            db.execute("""CREATE TABLE IF NOT EXISTS profiles (
                tenant_id TEXT NOT NULL,
                user_id TEXT NOT NULL,
                display_name TEXT NOT NULL,
                version INTEGER NOT NULL,
                PRIMARY KEY (tenant_id, user_id)
            )""")

    @staticmethod
    def cache_key(tenant_id: str, user_id: str) -> str:
        # 教学示例仅接受约定字符，生产中应统一编码与验证输入
        for value in (tenant_id, user_id):
            if not value or ":" in value:
                raise ValueError("invalid cache key component")
        return f"cache:profile:v1:{tenant_id}:{user_id}"

    def put(self, profile: Profile):
        key = self.cache_key(profile.tenant_id, profile.user_id)
        with closing(sqlite3.connect(self.db_path)) as db, db:
            db.execute("""INSERT INTO profiles VALUES (?, ?, ?, ?)
                ON CONFLICT(tenant_id, user_id)
                DO UPDATE SET display_name = excluded.display_name,
                              version = excluded.version""",
                (profile.tenant_id, profile.user_id,
                 profile.display_name, profile.version))
            db.commit()
        # 此处是常见的 post-commit best effort invalidation；
        # 在分布式并发更新下不能完全消除旧缓存回填竞态。
        try:
            self.cache.delete(key)
        except CacheUnavailable:
            pass

    def get(self, tenant_id: str, user_id: str) -> Profile | None:
        key = self.cache_key(tenant_id, user_id)
        try:
            raw = self.cache.get(key)
            if raw is not None:
                return Profile(**json.loads(raw))
        except (CacheUnavailable, ValueError, TypeError, KeyError):
            pass
        with closing(sqlite3.connect(self.db_path)) as db, db:
            row = db.execute("""SELECT tenant_id, user_id, display_name, version
                FROM profiles WHERE tenant_id = ? AND user_id = ?""",
                (tenant_id, user_id)).fetchone()
        if row is None:
            return None
        profile = Profile(*row)
        try:
            self.cache.set(key, json.dumps(profile.__dict__), ex=self.TTL_SECONDS)
        except CacheUnavailable:
            pass
        return profile


class TransientProgress:
    """临时进度提示：只做 UI 体验，不记录最终业务状态。"""
    def __init__(self, cache: FakeRedis):
        self.cache = cache

    def report(self, run_id: str, percentage: int):
        if not 0 <= percentage <= 100:
            raise ValueError("percentage outside [0,100]")
        self.cache.set(f"temp:progress:{run_id}", str(percentage), ex=30)

    def read(self, run_id: str) -> int | None:
        raw = self.cache.get(f"temp:progress:{run_id}")
        return None if raw is None else int(raw)
```

### 23.1 自动化测试源码

下面 19 项测试验证了缓存的丢失可恢复性、键 TTL 语义、原子计数的教学模型、隔离命名以及 Redis 故障降级行为。测试文件与上述源码放在同一目录。

```python
import tempfile
import unittest
from concurrent.futures import ThreadPoolExecutor
from pathlib import Path

from redis_boundary_demo import (
    FakeClock, FakeRedis, CacheUnavailable, Profile,
    ProfileService, TransientProgress

class RedisBoundaryTests(unittest.TestCase):
    def setUp(self):

        self.clock = FakeClock()
        self.cache = FakeRedis(lambda: self.clock.now)
        self.service = ProfileService(Path(self.tmp.name) / 'main.sqlite3', self.cache)

        self.tmp.cleanup()

        self.assertEqual(self.cache.ttl('absent'), -2)

    def test_ttl_permanent(self):
        self.cache.set('a','v')
        self.assertEqual(self.cache.ttl('a'), -1)

    def test_ttl_expires(self):
        self.cache.set('a','v',ex=5)
        self.clock.advance(5)
        self.assertIsNone(self.cache.get('a'))
        self.assertEqual(self.cache.ttl('a'), -2)

    def test_set_overwrites_ttl(self):
        self.cache.set('a','old',ex=5)
        self.cache.set('a','new')
        self.assertEqual(self.cache.ttl('a'), -1)

    def test_set_nx(self):
        self.assertTrue(self.cache.set('a','first',ex=5,nx=True))
        self.assertFalse(self.cache.set('a','second',ex=5,nx=True))
        self.assertEqual(self.cache.get('a'), 'first')

    def test_set_nx_expired_key(self):
        self.cache.set('a','first',ex=1,nx=True)
        self.clock.advance(2)
        self.assertTrue(self.cache.set('a','second',ex=5,nx=True))

    def test_incr_preserves_ttl(self):
        self.cache.set('c', '1', ex=9)
        self.clock.advance(2)
        self.assertEqual(self.cache.incr('c'), 2)
        self.assertEqual(self.cache.ttl('c'), 7)

        with ThreadPoolExecutor(max_workers=8) as workers:
            counts = list(workers.map(lambda _: self.cache.incr('counter'), range(300)))
        self.assertEqual(len(set(counts)),300)
        self.assertEqual(self.cache.get('counter'),'300')

    def test_cache_aside_miss_and_hit(self):
        self.assertEqual(self.service.get('tenant-a','u-1'), self.profile)
        key = self.service.cache_key('tenant-a','u-1')
        self.assertGreater(self.cache.ttl(key),0)
        self.assertEqual(self.service.get('tenant-a','u-1'), self.profile)

    def test_cache_aside_after_expiry(self):
        self.service.get('tenant-a','u-1')
        self.clock.advance(61)
        self.assertEqual(self.service.get('tenant-a','u-1'), self.profile)

        self.service.get('tenant-a','u-1')
        changed = Profile('tenant-a','u-1','New',2)
        self.service.put(changed)
        self.assertEqual(self.service.get('tenant-a','u-1'),changed)

    def test_cache_unavailable_db_still_available(self):

        self.assertEqual(self.service.get('tenant-a','u-1'),self.profile)
        changed = Profile('tenant-a','u-1','Changed',2)
        self.service.put(changed)
        self.assertEqual(self.service.get('tenant-a','u-1'), changed)

    def test_cache_can_be_cleared_without_losing_truth(self):

        self.cache._data.clear()  # 教学测试：模拟缓存丢失
        self.assertEqual(self.service.get('tenant-a','u-1'),self.profile)

    def test_multi_tenant_isolation(self):
        self.assertIsNone(self.service.get('tenant-b','u-1'))
        self.assertNotEqual(self.service.cache_key('tenant-a','u-1'), self.service.cache_key('tenant-b','u-1'))

    def test_invalid_key_component(self):

            self.service.cache_key('a:b', 'u-1')

        status.report('run1',33)
        self.assertEqual(status.read('run1'),33)
        self.clock.advance(30)
        self.assertIsNone(status.read('run1'))

    def test_transient_progress_rejects_invalid(self):

    def test_connection_failure_is_not_a_miss(self):
        self.cache.online = False

            self.cache.get('missing')

    def test_sqlite_preserves_after_cache_replaced(self):
        new_cache = FakeRedis(lambda:self.clock.now)
        second = ProfileService(Path(self.tmp.name) / 'main.sqlite3', new_cache)
        self.assertEqual(second.get('tenant-a','u-1'), self.profile)
```

### 23.2 这些测试不能证明什么

- 没有启动真实 Redis 服务，因此不证明 Redis 协议解析、网络重连、持久化或键逐出。
- 测试中的时钟模拟与 Redis 自身的过期扫描机制不同。
- SQLite 用于表现权威存储与事务提交，不等于 PostgreSQL 的隔离级别、行锁或复制行为。
- 线程锁只用于模拟同一对象内的原子修改，不是跨进程或跨机锁。
- 最后写入缓存的读写并发竞态、缓存雪崩和多实例并发限流，需要更高层级的故障/负载测试。

## 24. 关键知识辨析

| 看似相同的描述 | 实际应区分 |
|---|---|
| Redis 有 TTL，所以数据一定在指定时刻物理删除 | 到期不可作为有效值 ≠ 内存立即完全回收 |
| Key 还没有到 TTL，所以它一定存在 | 可能被 `DEL`、内存逐出、故障丢失或覆盖 |
| `SET NX` 能阻止重复业务提交 | 只能限制当前键存在期间的竞争，不能替代永久业务唯一性 |
| `INCR` 原子，所以收费统计准确 | 原子计数 ≠ 业务事件去重 ≠ 可审计账本 |
| Pipeline 很快，所以具备 ACID 事务 | 减少网络往返 ≠ SQL 式事务回滚 |
| `MULTI/EXEC` 不被并发插入，所以失败就全回滚 | Redis 事务没有 SQL 式执行错误自动回滚保证 |
| Lua 脚本是原子的，所以永远安全 | 脚本原子执行 ≠ 自动回滚 ≠ 外部系统原子性 |
| Redis 开了 AOF，就一定不会丢任何数据 | 取决于 fsync、故障类型、部署和恢复策略 |
| 命中缓存，就代表记录真实且最新 | 必须考虑版本、权限、更新竞态和数据来源 |
| Redis 不可用就当作未命中 | 必须区别基础设施错误和不存在；降级与安全性相关 |
| 临时进度键消失，说明任务已经失败 | 进度提示可丢；最终任务状态以持久化记录为准 |
| Redis 锁能防止数据库并发覆盖 | 锁有有效期，需数据库约束/版本或 Fencing Token 兜底 |

## 26. 术语速查

- **Cache Hit**：缓存命中。
- **Cache Miss**：缓存未命中。
- **TTL**：Time To Live，生存时间。
- **Expiration**：按约定到期时间失效。
- **Eviction**：因内存压力按策略逐出。
- **Atomic Operation**：在指定执行范围内不可被并发步骤交错的操作。
- **CAS**：Compare-And-Set，比较并交换/条件更新。
- **Pipeline**：将多条命令批量发送以减少往返。
- **WATCH**：用于 Redis 乐观并发控制的监视机制。
- **Cache-Aside**：应用控制缓存查询与回填，数据库为权威来源。
- **Cache Stampede**：热点键同时失效导致大量请求回源。
- **Fail-open**：依赖故障时允许继续访问，可能降低安全约束。
- **Fail-closed**：依赖故障时拒绝敏感操作，可能降低可用性。
- **RPO**：Recovery Point Objective，恢复点目标。
- **RTO**：Recovery Time Objective，恢复时间目标。
- **Fencing Token**：防止过期持有者继续修改受保护资源的单调标识机制。
- **Source of Truth**：系统指定的权威事实记录来源。

---

**本节结论**：Redis 的关键价值是以低延迟提供可复用的数据与原子操作；TTL 控制有效期，原子命令控制单节点局部竞态。但缓存一致性、业务唯一性、跨系统原子性和历史可恢复性，需要分别由应用协议、数据库约束、事务及可靠任务体系保证。最重要的职责分工是：**可重新计算的内容放缓存，允许遗失的实时提示放临时状态，必须追溯和恢复的业务事实放可靠持久存储。**
