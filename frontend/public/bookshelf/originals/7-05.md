# 测试、部署与效果验证（五）：Dockerfile、Docker Compose、环境变量、数据卷、健康检查与故障排查

> 范围：Docker Engine、Docker Compose v2、Linux 容器、Python 3.13 / FastAPI、PostgreSQL、Redis。示例适合个人本地开发与学习；生产部署还需完善密钥托管、备份、指标监控、CI、权限与供应链安全。
>
> 文档知识核对时间：2026-11-12。文末列出 Docker 官方文档。本文中可运行的工程与离线测试进行了独立验证，但当前环境**没有 Docker Engine**，并未声称已经实际启动真实容器、PostgreSQL 或 Redis。

## 1. 为什么需要容器化：进程、环境与交付的区别

传统的“在本机执行 `python main.py`”依赖当前机器的 Python 版本、第三方包、系统库、环境变量、目录和网络状态。代码在开发机正常运行，不代表同样的指令在另一台机器上也一定正常。容器化将应用及其用户态依赖组合为可复用的**镜像（Image）**，在运行时由 Docker Engine 创建隔离的**容器（Container）**。

容器不是完整的虚拟机：Linux 容器通常与宿主机内核共享内核，依靠命名空间和控制组隔离进程、网络与资源；Docker Desktop 在 Windows 上通常通过 Linux 虚拟化环境运行 Linux 容器。因此，容器化并不等于跨任意操作系统运行相同二进制程序，也不等于强安全沙箱。

| 对象 | 含义 | 生命周期/典型用途 |
|---|---|---|
| Dockerfile | 制作镜像的声明式构建说明 | 版本控制，随代码演进 |
| Image | 只读层组成的应用运行包 | 构建、推送、拉取、版本化 |
| Container | 镜像运行时的进程及其可写层 | 可创建、停止、销毁和重建 |
| Volume | Docker 管理的数据存储 | 容器重建后仍可持久保存 |
| Network | 容器之间的命名与网络通信范围 | 服务发现、流量隔离 |
| Compose | 用 YAML 描述多服务应用的配置与运行 | 定义应用拓扑并执行构建、启动和关闭 |

Dockerfile 解决“**一个服务如何构建**”，Compose 解决“**多个服务如何协作运行**”，Volume 解决“**容器消失后数据如何保留**”，健康检查解决“**运行中的服务能否提供需要的功能**”。这些问题是互补关系，不是替代关系。

### 1.1 镜像、容器和持久化数据的典型关系

```text
                   Dockerfile
                       │ docker build
                       ▼
                 Python API Image
                       │ docker compose up
                       ▼
                   API Container ──────────┐
                       │                   │
           Compose Network / Service DNS   │ stdout/stderr
             ┌─────────┴──────────┐        ▼
             ▼                    ▼     Docker Logging Driver
        db:5432              redis:6379
      PostgreSQL              Redis
             │
             ▼
      postgres_data Volume
```

容器被替换并不意味着 Volume 被删除；但也不能把 Volume 理解为自动完成备份。数据库的备份、恢复、一致性校验依旧要单独设计。

## 2. Dockerfile：构建语义与进程启动

### 2.1 常见指令

| 指令 | 发生阶段 | 核心作用 | 容易误解之处 |
|---|---|---|---|
| `FROM` | 构建 | 指定基础镜像 | 标签不等于不可变内容标识 |
| `WORKDIR` | 构建与运行配置 | 设置后续工作目录 | 不等于声明宿主机目录 |
| `COPY` | 构建 | 将构建上下文的文件放进镜像 | 会受到 `.dockerignore` 影响 |
| `RUN` | 构建 | 安装软件、生成构建产物 | 不会在容器每次启动时运行 |
| `ENV` | 镜像配置 | 设置默认运行环境变量 | 不应装入 API Key 等秘密 |
| `ARG` | 构建 | 传入构建参数 | 不是秘密存储机制 |
| `USER` | 运行配置 | 指定容器进程身份 | 并不能替代全部安全措施 |
| `EXPOSE` | 镜像元数据 | 表示服务预期监听的端口 | **不会自动发布宿主机端口** |
| `CMD` | 运行 | 默认启动命令 | 可以被 Compose 的 `command` 覆盖 |
| `ENTRYPOINT` | 运行 | 稳定的主要执行入口 | Shell 形式容易引入信号传递问题 |

Dockerfile 的 exec 形式 `CMD ["python", "..."]` 让应用直接收到适当的终止信号；Shell 形式可能先启动 `/bin/sh -c`，如果没有通过 `exec` 正确传递信号，优雅停机会受到影响。`RUN` 是构建时指令，`CMD` 是容器启动时指令，两者不可混淆。

### 2.2 缓存层与构建效率

Docker 构建会利用层缓存。如果先复制整个项目、再安装依赖，那么任意源代码改动都可能导致依赖安装层无法命中缓存。通常应先复制依赖声明并安装，再复制易变动的业务源码：

```dockerfile
COPY requirements.txt ./
RUN python -m pip install --no-cache-dir -r requirements.txt
COPY app/ ./app/
```

`--no-cache-dir` 是 pip 不使用下载缓存的选项，并不是关闭 Docker 层缓存。构建的可复现性还取决于依赖锁定、基础镜像摘要、平台架构与外部包源。

### 2.3 基础镜像与多阶段构建

`python:3.13-slim` 适合教学和多数纯 Python Web 服务，但较小并不必然意味着更安全；镜像补丁更新、依赖版本和实际运行权限同样重要。需要编译原生依赖时，可使用多阶段构建：构建阶段安装编译工具，运行阶段只复制运行所需产物，以降低最终体积和暴露面。

不要在镜像构建中写入真实 `.env`、私钥或 API Key。即使后来通过 `RUN rm` 删除，构建层和构建记录中仍可能存在泄漏风险。对于构建时所需的秘密，应使用 BuildKit Secret Mount 等安全机制。

## 3. Docker Compose：描述多服务系统

Compose 不负责把整个项目编译成单一可执行程序。它读取 `compose.yaml` 并根据配置创建服务容器、网络和存储。常见元素：

- `services`：定义 API、数据库、缓存、Worker 等服务。
- `image` / `build`：使用现有镜像，或基于 Dockerfile 构建镜像。
- `environment` / `env_file`：将配置放入容器运行环境。
- `ports`：将容器端口映射到宿主机。
- `volumes`：挂载持久化存储或宿主机目录。
- `depends_on`：描述启动与停止依赖。
- `healthcheck`：检查服务是否能够提供特定能力。
- `networks`：限制不同服务可互相访问的网络。
- `restart`：配置特定退出后的重启策略。
- `logging`：选择日志驱动和保留策略。
- `stop_grace_period`：等待容器正常关闭的时间窗口。

`docker compose config` 用于解析并验证 YAML、变量插值和合并结果；`docker compose up --build -d` 构建并启动；`docker compose ps` 查看状态；`docker compose logs` 查看输出；`docker compose down` 删除项目容器和默认网络。

### 3.1 `depends_on` 的启动语义

仅使用：

```yaml
api:
  depends_on:
    - db
```

只能表达依赖的创建/启动顺序，不能保证 PostgreSQL 已经完成初始化并能正确服务。数据库可能仍在创建数据目录、执行初始化 SQL 或进行恢复。

更准确的是：

```yaml
api:
  depends_on:
    db:
      condition: service_healthy
```

结合 `db.healthcheck`，Compose 在**初始启动依赖服务**时等待健康检查成功。不过：

1. 依赖条件不等于运行期自动重连；数据库以后掉线，API 自己仍必须处理连接错误、回退和恢复。
2. Compose 不会仅因为容器状态变为 `unhealthy` 就保证自动重启它；`restart: unless-stopped` 主要针对进程退出，而非健康检查失败。
3. `service_completed_successfully` 适用于一次性的数据库迁移等前置任务，前提是任务确实成功退出。
4. 健康检查要判断真正的就绪性，不能仅检查进程 PID 存在。

## 4. 环境变量：运行环境、插值和敏感数据

环境变量在 Compose 中容易产生三种混淆：

**第一类：Compose 插值变量。** `${POSTGRES_PASSWORD}` 是在 Compose 读取 YAML 时被替换，用于构造最终配置。默认 `.env` 文件可参与插值，但**在 `.env` 中声明变量不代表它自动进入每个服务容器**。

**第二类：容器运行变量。** `services.api.environment` 或 `env_file` 决定容器进程实际能读取什么。应用在容器中通过 `os.environ` 获取这些值。

**第三类：构建变量。** Dockerfile 的 `ARG` / `ENV` 与运行时 Compose 变量不是同一件事。即使字段名字相同，注入时机和暴露范围也不同。

### 4.1 插值语法

| 表达式 | 行为 |
|---|---|
| `${NAME}` | 展开变量；未设置时可能警告并得到空字符串 |
| `${NAME:-fallback}` | 未设置或为空时使用 fallback |
| `${NAME-fallback}` | 未设置时使用 fallback；空字符串仍被保留 |
| `${NAME:?message}` | 未设置或为空时直接报错 |
| `$$NAME` | 让 `$NAME` 保留给容器 Shell，而不是被 Compose 提前插值 |

例如 PostgreSQL 的健康检查：

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U \"$${POSTGRES_USER}\" -d \"$${POSTGRES_DB}\""]
```

这里 `$$` 很关键：命令应在容器内部读取 PostgreSQL 的环境变量，而不是由 Compose 在解析 YAML 时先替换。

### 4.2 环境变量优先级

Compose 有两套相关但不同的优先级：**插值来源优先级**与**容器内最终环境变量优先级**。插值时，Shell 环境、`--env-file` 和默认 `.env` 的来源关系会影响最终解析；容器环境还会受到 CLI `-e`、`environment`、`env_file`、Dockerfile `ENV` 等影响。不要用“`.env` 永远优先”或“environment 永远优先”这样的简单规则代替实际验证。

排查时可用：

```powershell
# 验证最终 Compose 结构，不输出完整敏感配置
docker compose config --quiet

# 下列命令可能显示敏感环境变量值，慎重使用和保存输出
# docker compose config
# docker compose config --environment
```

### 4.3 密钥安全

本地演示可在不提交 Git 的 `.env` 中使用测试密码；生产环境优先使用 Docker Compose Secrets 或外部密钥管理系统。通过 `environment` 注入的密码可能出现在容器环境、诊断输出、崩溃信息或调试日志中。

Compose Secrets 通常作为 `/run/secrets/<name>` 下的文件提供。是否可以直接使用，取决于应用和基础镜像是否支持读取对应密钥文件。不要把“密码没有写进 compose.yaml”误认为“密码已经安全”。

## 5. 网络：`localhost`、服务名与端口映射

这是多服务容器最常见的配置错误之一。

在默认 Compose 网络内，容器间通常使用**服务名**寻址：

```text
API 容器 -> db:5432
API 容器 -> redis:6379
Windows 宿主机浏览器 -> 127.0.0.1:8000（在 API 的 8000 端口被发布时）
```

容器里的 `localhost` 指**当前容器自身**，不是 Windows 主机，也不是同一个 Compose 项目中的其他容器。因而：

```text
postgresql://localhost:5432/demo   # 作为 API 容器中的数据库地址通常是错误的
postgresql://db:5432/demo          # 同网络的服务名与容器端口
```

`ports: ["127.0.0.1:8000:8000"]` 中，前面的 `127.0.0.1:8000` 是宿主机绑定地址和端口，后面的 `8000` 是容器内部端口。对后端数据库通常不需要发布宿主机端口；API 可以直接访问 `db:5432`。

### 5.1 `EXPOSE`、`ports`、`expose` 的区别

- `EXPOSE 8000`：镜像元数据，并不让宿主机自动访问。
- `ports`：发布宿主机端口，例如 Windows 的 `localhost:8000`。
- Compose `expose`：声明容器间端口，不负责发布到宿主机。多数情况下服务即使没有显式 `expose`，同网络容器仍可通过监听端口互相访问。

还需注意服务本身监听地址：如果 Uvicorn 在容器内部只监听 `127.0.0.1`，其他容器或端口转发可能无法访问；典型容器服务需要监听 `0.0.0.0`。

### 5.2 错误分类

| 错误表现 | 可能原因 | 首要检查 |
|---|---|---|
| `Name or service not known` | 服务名错误、网络不同、DNS 问题 | 服务名、Compose 网络、DNS 解析 |
| `Connection refused` | 地址可达但没有进程监听 | 服务是否启动、端口、监听地址 |
| `Connection timed out` | 网络不通、防火墙或服务没有响应 | 路由、端口、容器网络、超时 |
| `password authentication failed` | 凭证或数据库角色错误 | PostgreSQL 用户和密码，不要公开密码 |
| `database does not exist` | 数据库未创建、连接目标错误 | 数据库名、初始化记录、持久化 Volume |
| `port is already allocated` | 宿主机端口冲突 | `docker compose ps`、`netstat`、端口绑定 |

不要把所有连不上服务的问题都改成增大超时时间；地址错误、认证失败和目标没监听通常不会因为增加超时而解决。

## 6. Volume、Bind Mount 与数据寿命

### 6.1 三类存储概念

| 类型 | 管理方式 | 常见用途 | 注意事项 |
|---|---|---|---|
| Named Volume | Docker 管理 | PostgreSQL 数据目录 | 容器重建后保留；需要独立备份 |
| Bind Mount | 宿主机目录映射 | 开发时代码热更新、配置文件 | Windows 路径、权限和文件同步行为不同 |
| Container writable layer | 容器自己的可写层 | 临时运行时文件 | 容器删除/重建后不可依赖其内容 |

例如：

```yaml
volumes:
  - postgres_data:/var/lib/postgresql/data
```

这是 PostgreSQL 17 示例的数据目录。不同大版本的官方 PostgreSQL 镜像可能改变推荐挂载位置，升级镜像前必须查对应版本的说明，不能想当然把旧 Volume 挂到新位置。

### 6.2 `down` 与 `down -v`

```powershell
docker compose down      # 停止并删除容器和默认网络，通常保留命名卷
docker compose down -v   # 同时删除项目声明的命名卷及关联匿名卷，危险
```

**`down -v` 可能直接删除实验数据库全部数据**，不应作为常规故障排查命令。`docker compose up --force-recreate` 重建容器与 `docker compose down -v` 删除持久数据也不相同。

### 6.3 初始化变量只对首次建库生效的情况

PostgreSQL 官方镜像通过 `POSTGRES_USER`、`POSTGRES_PASSWORD`、`POSTGRES_DB` 等变量初始化**空的数据目录**。已有 Volume 再次启动时，单纯修改 `.env` 不会自动重建用户或改变既有数据库密码。正确处理通常是执行对应 SQL 修改角色、执行迁移或制定数据迁移计划，而不是删除 Volume 强行重来。

数据卷不是多实例数据库共享写入的通用解决方案。两个独立 PostgreSQL 实例不应该同时随意挂载并写入同一个数据目录。

## 7. 健康检查：启动成功、存活和就绪

容器可以处于 `running`，但服务仍不可用。例如 Uvicorn 进程已经启动，却仍无法连接数据库。需要区分：

| 检查类别 | 回答的问题 | 示例 |
|---|---|---|
| Liveness | 应用进程是否仍具有基本响应能力？ | `GET /health/live` |
| Readiness | 当前实例能否处理依赖数据库或缓存的业务请求？ | `GET /health/ready` |
| Startup | 是否完成较长的启动准备？ | 初始化/迁移状态（部署机制决定） |
| Business progress | 后台任务是否真正推进？ | 最近成功时间、完成速率、失败率 |

`/health/live` 通常不应每次都查询 PostgreSQL，否则数据库短暂故障可能把正常的 API 进程错误归类为需要重启。Readiness 则可以检查当前业务真正依赖的系统（根据功能差异，不是所有非核心依赖失败都必须让整个 API 不就绪）。

健康检查的常见参数：`interval`（周期）、`timeout`（一次探测期限）、`retries`（失败次数阈值）、`start_period`（启动宽限期）。探测命令退出码 `0` 表示健康，非零一般表示失败；需要使用基础镜像中实际存在的命令。

在教学项目中，API 的 healthcheck 使用 Python 标准库 `urllib.request` 而不是 `curl`，因为 `python:slim` 不保证预装 curl。PostgreSQL 使用 `pg_isready`，Redis 使用 `redis-cli ping`。

健康检查不等于业务恢复机制。若数据库在运行中失联，应用仍需连接重试、连接池失效处理、幂等重试和故障降级。对 Kafka Worker，心跳正常也不能证明消费位点和业务处理在推进。

## 8. 日志：标准输出、结构化日志与保留策略

Docker 通常收集容器的 stdout/stderr，经由 Logging Driver 存储或转发。Python 服务应将运行日志写到标准输出，而不是只写入容器临时目录中的文本文件。

```powershell
docker compose logs --tail=100 api
docker compose logs -f --tail=100 api
docker compose logs --since=10m db
docker compose ps
```

`PYTHONUNBUFFERED=1` 减少 Python 标准输出缓冲带来的日志延迟。日志内容宜包含时间、级别、服务、`request_id` / `task_id`、操作状态、耗时、错误类别和必要的执行上下文；绝不应该随意输出 API Key、数据库密码、完整授权头、原始私密文档或未经处理的用户消息。

### 8.1 日志保留和磁盘空间

Docker Engine 常见默认日志驱动 `json-file` 若未配置轮转，长期运行可能导致磁盘被日志占满。Compose 可以使用 `local` 日志驱动，并限制大小和保留文件数量：

```yaml
logging:
  driver: local
  options:
    max-size: "10m"
    max-file: "3"
```

日志保留不是业务审计记录的替代。需要长期追踪的任务执行结果、失败消息和事件状态，应写入适当的持久化存储。

### 8.2 常用诊断工具的职责

| 命令 | 查看内容 |
|---|---|
| `docker compose ps -a` | 容器状态、端口、退出信息 |
| `docker compose logs <service>` | stdout/stderr 中的应用和依赖日志 |
| `docker compose exec <service> <cmd>` | 在已经运行的容器中执行诊断命令 |
| `docker compose run --rm <service> <cmd>` | 启动一次性容器执行命令（需注意依赖与卷的副作用） |
| `docker inspect <container>` | 健康状态、配置、挂载、退出码、OOMKilled |
| `docker stats` | 容器 CPU、内存、网络 I/O 的实时概览 |
| `docker compose config --quiet` | 仅验证 Compose 文件是否能被解析 |
| `docker volume ls` | 列出数据卷 |

`docker inspect` 或 `docker compose config` 可能包含敏感环境变量，不应未经检查就复制到公开讨论或日志平台。


## 9. 可复现的教学工程：FastAPI + PostgreSQL + Redis

本例使用三个服务：API 负责请求和就绪探测，PostgreSQL 保存持久化数据，Redis 承担缓存或临时状态。该例**没有启动 Kafka**，目的是把 Dockerfile、网络、环境变量、Volume 与健康检查的基本行为解释清楚。Kafka 和独立 Worker 可在掌握这些概念后加入 Compose。

### 9.2 Python 依赖文件 `requirements.txt`

以下依赖范围是用于教学的**可安装约束**，不是精确锁文件；生产 CI 应采用锁定依赖与基础镜像摘要。

### 9.3 Dockerfile

```dockerfile
FROM python:3.13-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /srv/app

COPY requirements.txt ./
RUN python -m pip install --no-cache-dir -r requirements.txt \
    && useradd --uid 10001 --create-home appuser

COPY --chown=appuser:appuser app/ ./app/
USER appuser
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--timeout-graceful-shutdown", "20"]
```

- 将依赖安装放在源码复制之前，以便复用构建缓存。
- 业务进程使用非 root 身份运行，降低进程权限。
- `EXPOSE` 声明容器端口但不负责发布宿主机端口。
- `--host 0.0.0.0` 让服务能够接受容器网络内的请求。
- 使用 exec 形式 `CMD`，便于正常接收信号。
- `--timeout-graceful-shutdown 20` 与 Compose 的 `stop_grace_period: 30s` 一起为关闭资源提供时间窗口；但仍不能保证每个外部调用已完成。

### 9.6 完整 `compose.yaml`

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-demo}
      POSTGRES_DB: ${POSTGRES_DB:-demo}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Set POSTGRES_PASSWORD in .env}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U \"$${POSTGRES_USER}\" -d \"$${POSTGRES_DB}\" ]"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 20s
    restart: unless-stopped
    logging: &log_config
      driver: local
      options:
        max-size: "10m"
        max-file: "3"

  redis:
    image: redis:7.4-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped
    logging: *log_config

  api:
    build:
      context: .
      dockerfile: Dockerfile
    environment:
      DB_HOST: db
      DB_PORT: "5432"
      DB_NAME: ${POSTGRES_DB:-demo}
      DB_USER: ${POSTGRES_USER:-demo}
      DB_PASSWORD: ${POSTGRES_PASSWORD:?Set POSTGRES_PASSWORD in .env}
      REDIS_HOST: redis
      REDIS_PORT: "6379"
    ports:
      - "127.0.0.1:${API_PORT:-8000}:8000"
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    init: true
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health/ready', timeout=4)"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 15s
    stop_grace_period: 30s
    restart: unless-stopped
    logging: *log_config

volumes:
  postgres_data:
```

解释：

1. PostgreSQL 和 Redis **没有发布到宿主机**，API 可以通过同网络的 `db` 和 `redis` 访问它们。
2. 仅 API 在宿主机回环地址发布端口，避免教学服务意外暴露到局域网。若有外部访问需求，应明确配置代理、认证和网络防火墙。
3. PostgreSQL Volume 独立于容器生命周期。
4. `depends_on` 结合两个依赖的健康检查，避免最常见的“数据库尚未准备好就启动 API”的初始竞态。
5. `init: true` 加入轻量 init 进程协助信号转发和子进程回收；业务层仍需实现自己的资源清理。
6. 使用 YAML 锚点 `&log_config` 和别名 `*log_config` 复用日志配置。这是 YAML 语法，不是 Compose 独有机制。
7. 示例镜像标签固定在主/次版本层级，用于便于学习；生产部署应评估补丁与摘要固定，并制定升级方案。
8. 数据库密码经环境变量传入，只适合本地演示；正式部署推荐 Secrets 或密钥服务。

**PostgreSQL 镜像版本说明**：示例选择 `postgres:17`，因此使用 `/var/lib/postgresql/data` 作为数据卷挂载点；更换到新的数据库大版本不是单纯修改 `image:` 标签就能保证安全升级。数据格式迁移需要单独规划。

### 9.7 `app/main.py`：实际健康检查与资源关闭

```python
import asyncio
import logging
import os
from contextlib import asynccontextmanager

from fastapi import FastAPI, HTTPException, Request
from redis.asyncio import Redis
from sqlalchemy import text
from sqlalchemy.engine import URL
from sqlalchemy.ext.asyncio import create_async_engine

logger = logging.getLogger(__name__)


def make_db_url() -> URL:
    return URL.create(
        drivername="postgresql+asyncpg",
        username=os.environ["DB_USER"],
        password=os.environ["DB_PASSWORD"],
        host=os.environ.get("DB_HOST", "db"),
        port=int(os.environ.get("DB_PORT", "5432")),
        database=os.environ["DB_NAME"],
    )


@asynccontextmanager
async def lifespan(app: FastAPI):
    engine = create_async_engine(make_db_url(), pool_pre_ping=True)
    redis = Redis(
        host=os.getenv("REDIS_HOST", "redis"),
        port=int(os.getenv("REDIS_PORT", "6379")),
        decode_responses=True,
        socket_connect_timeout=2,
        socket_timeout=2,
    )
    app.state.engine = engine
    app.state.redis = redis
    try:
        yield
    finally:
        await redis.aclose()
        await engine.dispose()


app = FastAPI(lifespan=lifespan)


@app.get("/health/live")
async def live():
    return {"status": "alive"}


async def check_dependencies(request: Request):
    async with request.app.state.engine.connect() as connection:
        await connection.execute(text("SELECT 1"))
    if not await request.app.state.redis.ping():
        raise RuntimeError("redis ping failed")


@app.get("/health/ready")
async def ready(request: Request):
    try:
        await asyncio.wait_for(check_dependencies(request), timeout=3)
    except Exception as exc:
        logger.warning("readiness dependency unavailable: %s", type(exc).__name__)
        raise HTTPException(
            status_code=503,
            detail="dependencies not ready",
        ) from None
    return {"status": "ready"}
```

此示例展示：

- 应用级共享 `AsyncEngine` / Redis Client，而不是每次请求创建一个新客户端。
- 使用 SQLAlchemy `URL.create` 构造数据库 URL，避免密码包含 `@`、`:` 等字符时自行拼接 URL 造成解析错误。
- `liveness` 不依赖数据库和 Redis，`readiness` 检查真实依赖。
- 探测失败返回 HTTP 503，不将数据库凭证、底层连接字符串或 SQL 细节回传给用户。
- `lifespan` 的 `finally` 负责关闭 Redis 客户端和 SQLAlchemy Engine。

**限制：** 这是教学最小实现，不包含数据库迁移、正式业务接口、应用层授权、完善的重试策略和请求追踪。对于 Redis 仅用于可降级缓存的产品，Readiness 是否强依赖 Redis 应根据实际功能决定，而不是一律作为硬依赖。

## 10. Windows / PowerShell 的实际启动与检查命令

在安装了 Docker Desktop、并已启用 Linux 容器运行环境的 Windows 上，可以从项目目录执行：

```powershell
# 查看 Docker/Compose 是否可用
docker version
docker compose version

# 创建本地环境变量文件并自行修改演示密码
Copy-Item .env.example .env
notepad .env

# 校验 Compose，不打印所有插值配置
docker compose config --quiet

# 构建并启动容器
docker compose up --build -d

# 查看服务与健康状态
docker compose ps

# 分别检查存活与就绪接口
Invoke-RestMethod http://127.0.0.1:8000/health/live
Invoke-RestMethod http://127.0.0.1:8000/health/ready

# 查看应用与依赖日志
docker compose logs --tail=100 api
docker compose logs --tail=100 db
docker compose logs --tail=100 redis

# 停止并删除容器（保留命名卷）
docker compose down
```

如果第一次启动需要下载镜像和安装 Python 包，持续时间取决于网络与镜像缓存。若 `docker version` 只有 Client 没有 Server，优先解决 Docker Desktop / Docker Engine 状态，而不是修改 Python 代码。

为了进一步确认后端网络，可以在 API 容器中运行：

```powershell
# API 容器是否能解析 PostgreSQL 服务名
docker compose exec api python -c "import socket; print(socket.gethostbyname('db'))"

# 容器内是否能访问 PostgreSQL TCP 端口
docker compose exec api python -c "import socket; s=socket.create_connection(('db',5432),timeout=3); print('db tcp ok'); s.close()"

# Redis 是否可响应
docker compose exec redis redis-cli ping

# PostgreSQL 是否已准备接受连接
docker compose exec db pg_isready -h 127.0.0.1 -U demo -d demo
```

上述 `demo` 应根据实际环境变量替换。TCP 连接成功只能证明端口可达，不代表数据库账号验证、SQL 权限和业务迁移都已正确。

## 11. 最小故障排查方法：由外向内、逐层缩小范围

一个有效的排查顺序是：

```text
[1] Docker Engine 可用？
       │ 否 -> 修复 Docker Desktop/WSL/引擎
       ▼
[2] Compose 语法和插值正确？
       │ 否 -> docker compose config --quiet
       ▼
[3] 相关容器在运行？
       │ 否 -> ps -a / logs / inspect ExitCode
       ▼
[4] 依赖是否健康？
       │ 否 -> db/redis logs、healthcheck、初始化
       ▼
[5] 容器网络解析和 TCP 可达？
       │ 否 -> service DNS、网络、监听、端口
       ▼
[6] 认证、权限、数据库和迁移正确？
       │ 否 -> 数据库只读诊断、权限、迁移历史
       ▼
[7] API 业务请求和后台进度正确？
       │ 否 -> 应用日志、Trace、任务表与依赖状态
       ▼
    明确故障原因并验证修复
```

这个顺序的目的是避免“所有问题都重启一次”“为了能连上就暴露所有端口”“报错就删数据卷”等破坏性做法。

### 11.1 故障诊断矩阵

| 现象 | 优先怀疑 | 应如何验证 | 推荐修复方向 |
|---|---|---|---|
| `docker` 命令无法连接 daemon | Docker Desktop 未启动、WSL 后端异常 | `docker version`、Desktop 状态 | 恢复引擎，不先改业务代码 |
| `services... must be a mapping` | YAML 缩进/类型错误 | `docker compose config --quiet` | 修复 YAML，谨慎使用 Tab |
| 环境变量替换成空值 | `.env` 不在期望位置、变量名错误 | 检查插值来源和必填表达式 | 使用 `${VAR:?error}`，检查优先级 |
| `api` 反复退出 | Python import、配置、监听进程失败 | `docker compose ps -a`、`logs api` | 修正启动命令和依赖，不仅依赖重启策略 |
| PostgreSQL 初次启动很慢 | 数据目录初始化、恢复中 | `logs db`、`pg_isready` | `service_healthy`，合理健康检查窗口 |
| API 连 `localhost:5432` 被拒绝 | 容器 localhost 指错 | 检查 `DB_HOST` | 使用 `db:5432` |
| 宿主机访问 API 失败 | 端口未发布、API 未监听 0.0.0.0 | `ps`、端口映射、应用日志 | 配置 `ports`、`--host 0.0.0.0` |
| 端口绑定冲突 | 宿主机已有服务占用 | Windows `netstat -ano` | 改宿主机映射端口，内部端口保持不变 |
| PostgreSQL 密码不匹配 | 已有 Volume 保存旧凭证 | 认证日志、角色与数据目录状态 | 正确修改数据库角色/秘钥，不删除 Volume |
| `readiness=503` 但 `live=200` | 依赖故障或连接池问题 | API 和 db/redis 日志 | 区分依赖恢复与应用崩溃 |
| `unhealthy` 但容器还在运行 | 健康检查失败不自动退出 | `docker inspect ...Health` | 修复探针/依赖；不要假设自动重启 |
| 应用重建后数据不见 | 数据在容器写入层或挂载错误 | `docker volume ls`、挂载信息 | 使用正确命名卷、检查数据目录 |
| 数据库升级后无法启动 | 数据目录版本与镜像大版本不匹配 | `logs db`、镜像版本 | 恢复备份并执行受支持的升级流程 |
| 日志文件占满磁盘 | 缺少轮转、无界日志 | `docker system df`、Docker 日志配置 | 限制日志大小，审查日志量与磁盘容量 |
| Worker 心跳正常却无完成任务 | 业务阻塞、下游不可用、提交停滞 | 在途任务/完成率/lag/日志 | 检查业务进度和重试状态，而非只看 PID |

### 11.2 排查内存不足与 OOM

容器内存不足经常表现为进程意外退出、重启或极慢。排查时区分：

- **容器/宿主机内存限制**：可以通过 `docker stats`、`docker inspect` 的 `OOMKilled` 等信息判断是否触发容器级 OOM。
- **语言运行时堆内存限制**：例如 Kafka Broker 运行于 JVM，可能即使宿主机还有剩余内存，也因为 JVM 最大堆太小而报 `Java heap space`。此时需要检查 Broker 的 JVM 堆设置（例如实际镜像支持的 `KAFKA_HEAP_OPTS`）、容器内存预算以及堆外内存；不是单纯重试即可解决。
- **应用泄漏或负载峰值**：观察任务并发数量、缓存与缓冲区、连接池、批处理量、内存曲线和日志；避免仅通过无限提高内存上限掩盖问题。

`docker compose logs kafka` 只适用于 Compose 中确实存在名为 `kafka` 的服务。本文教学 Compose 没有 Kafka；该命令作为后续扩展项目的排障参考。Kafka 集成还涉及 advertised listeners、内部/外部地址及分区状态，不能只靠端口可达判断 Broker 工作正常。

## 12. `docker compose exec` 与 `run` 的区别

`exec` 在已经运行的容器内启动新命令，适合临时诊断：

```powershell
docker compose exec api python --version
```

`run` 创建一次性的服务容器，通常用于迁移、测试或管理任务：

```powershell
docker compose run --rm api python -m compileall -q app
```

它们不是“重启 API 的两种写法”。`run` 可能连接同一数据库和 Volume，执行迁移等操作前也必须考虑生产数据的副作用。普通后台任务应使用专门的 Worker 服务，不应每收到一个 HTTP 请求就执行 `docker compose run`。

## 13. 生命周期与优雅停机

`docker compose stop` 通常向容器主进程发送终止信号，等待宽限时间后可能强制结束。一个服务的关闭流程应包含：

1. 停止接收新的业务操作，或将实例从就绪集合中移出。
2. 对正在执行的 HTTP 请求给予有限等待时间；达到期限时明确取消语义。
3. 对后台任务停止领取新任务，保存可恢复的任务状态；必要时进行租约释放或让租约自然过期。
4. 关闭数据库 Session、连接池与 HTTP/Redis 客户端。
5. 释放文件句柄、刷新必要日志、退出进程。

`stop_grace_period` 不是“确保所有任务成功完成”的承诺。它只是为协作式关闭提供时限。对于长时间的批量模型调用、Kafka 任务或索引任务，可靠恢复必须依靠 PostgreSQL 等持久状态、幂等键、消费位点和 Worker 恢复策略；无法仅靠 Docker 进程存活保证。

## 14. 在生产环境进一步需要注意的事项

**镜像与供应链安全。** 使用可信镜像源、镜像摘要、软件供应链扫描、锁文件；避免随意执行不透明的构建脚本。镜像构建应尽量使用非 root 身份运行应用，限制不必要的能力、挂载和网络出口。

**资源与容量。** 容器的 CPU、内存和进程数要根据负载限制；高并发 API 与多 Worker 并不意味着数据库连接数没有上限。服务副本数量乘以单实例连接池大小，可能超过 PostgreSQL 最大连接数。

**网络暴露。** PostgreSQL、Redis 不应仅为了调试就默认绑定到公网。正式服务通常由反向代理或网关统一处理 TLS、认证、请求限制与可观测性。

**数据与备份。** Docker Volume 的存在不等于完成备份。PostgreSQL 需要独立的逻辑/物理备份、恢复演练、版本兼容性检查。迁移应与应用代码版本相协调；重要迁移应支持失败后恢复策略。

**日志与隐私。** 明确保留周期、访问权限、脱敏规则，避免日志进入无界存储。业务审计记录需要可查询且受权限保护，不应仅寄托于 Docker 日志。

**服务恢复。** Compose 适合单机和小规模部署；跨主机高可用、自动调度、强制健康重启、滚动升级等需要额外的基础设施与设计，不能把 Compose 的能力误描述成完整集群编排平台。

## 15. 验证：哪些是真正测试过的，哪些还没有

本节示例工程的可运行源码、Compose、Dockerfile 和静态测试被保存在同一个工作目录中，用于生成本文档。当前环境没有 Docker Engine，故无法执行 `docker compose up`、真实 PostgreSQL 握手与 Redis TCP 连接。

已执行的**15 项离线测试**包括：

- YAML 可解析、包含 `api`、`db` 和 `redis` 三个服务。
- PostgreSQL 命名 Volume 存在，数据库和 Redis 未向宿主机发布端口。
- API 依赖的服务使用 `service_healthy`，API 只在本机回环地址发布端口。
- 三个服务均有日志容量限制。
- Dockerfile 不包含数据库密码字面值，使用非 root 用户运行。
- `.dockerignore` 排除了本地 `.env`。
- Python 源码语法解析通过，停机宽限时间被明确设置。
- 用假数据库与假 Redis 测试：就绪时返回 HTTP 200；数据库或 Redis 不可用时返回 503，进程存活接口仍返回 200。
- 测试应用退出时关闭连接池与 Redis 客户端，失败响应不回传底层内部错误。
- `URL.create` 能安全处理带有特殊字符的数据库密码。

上述验证仅用于确保示例**结构与本地接口行为**合理；它们不等于已经验证 Docker 镜像构建、真实 PostgreSQL/Redis 连接、网络或数据持久化。正式部署时需要在 Docker Desktop / Linux Docker Engine 中继续执行真实集成验证。

### 15.1 Docker 上需要补做的真实验证

| 测试场景 | 操作 | 预期结果 |
|---|---|---|
| 首次启动 | `docker compose up --build -d` | API、PostgreSQL 和 Redis 成功进入正常状态 |
| API 就绪 | 查询 `/health/ready` | 依赖正常时返回 200 |
| 数据库不可用 | 停止 `db` 并查询健康检查 | `live` 可仍为 200，`ready` 返回 503 |
| 恢复数据库 | 启动 `db` 并等待健康 | API 在连接恢复后重新进入 ready |
| Redis 不可用 | 停止 `redis` | 示例 API 的 readiness 返回 503 |
| 容器重建 | 停止并重新创建应用 | 命名 Volume 中已提交的数据应保留 |
| 日志输出 | 读取 `logs api` | 有状态和错误信息，且不含密钥明文 |
| 端口隔离 | 宿主机尝试直接访问数据库端口 | 默认无数据库宿主机端口映射 |
| 停机清理 | `docker compose stop` | 资源关闭，进程在配置期限内退出 |

## 16. 常见误区汇总

1. **“容器 running 就是业务正常”**：错误。必须区分 liveness、readiness 与业务完成进度。
2. **“Compose 的 depends_on 会等待数据库完全可用”**：短语法不能保证；需要适当健康检查与依赖条件。
3. **“容器里的 localhost 就是我的 Windows 电脑”**：错误。每个容器拥有自己的网络命名空间。
4. **“EXPOSE 了端口就能从电脑浏览器访问”**：错误。需要发布端口并确认应用监听地址。
5. **“`.env` 默认自动注入所有容器”**：错误。插值和容器环境变量是不同阶段。
6. **“数据放在 Docker 容器内部就持久化了”**：错误。容器替换时可写层不可依赖。
7. **“把 PostgreSQL 密码在 .env 改掉，已有数据库密码就改了”**：错误。已有 Volume 的角色密码不会因此自动更新。
8. **“healthcheck unhealthy 会自动重启所有服务”**：错误。具体恢复行为由运行时、重启策略和编排机制决定。
9. **“使用 restart: always 就保证没有任务丢失”**：错误。数据恢复和幂等仍需业务实现。
10. **“把错误日志全部打印出来总是有利于排障”**：错误。会造成秘密与用户数据泄露。
11. **“停掉容器就是安全结束所有工作”**：错误。需要信号处理、任务取消和持久化恢复设计。
12. **“静态 YAML 测试通过就代表真实 Docker 部署通过”**：错误。必须另做容器集成验证。

## 17. 本节知识之间的联系

Dockerfile 决定**镜像如何构建、进程如何启动**；Compose 决定**服务如何连接、以何种配置运行**；环境变量决定**运行时参数**，但不应承担完整的秘密管理；Volume 决定**哪些数据不随容器销毁**；健康检查提供**当前可用性的有限信号**；日志与诊断工具帮助**从启动到失败的每个阶段定位问题**。

当某个 API 接口失败时，排查通常先从配置、容器、健康状态与网络入手，再深入权限、事务和业务逻辑。只有每个环节的行为都可解释，部署才真正具有可维护性。
