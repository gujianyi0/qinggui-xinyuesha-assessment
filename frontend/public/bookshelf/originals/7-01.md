# 测试、部署与效果验证（01）——pytest 核心逻辑、失败分支与接口/数据库/后台任务集成测试

> 技术范围：Python 3.13、pytest 9、pytest-asyncio、FastAPI、Pydantic 2、SQLAlchemy 2.x、SQLite 教学环境；区分真实 PostgreSQL/Kafka 集成测试与本地模拟测试。
>
> 本文属于知识性解释与可运行工程实例。它不将模拟环境的通过率视为生产可靠性证明。

## 1. 软件测试在验证什么

程序“运行了”和“正确”不是同义词。**测试**是在明确前提和可观察预期的条件下执行程序，判断其行为是否满足约定。正确性的依据应来自需求、接口契约、数据库约束或独立业务规则，而不能简单地把当前程序输出复制成“预期答案”。

一条可执行的测试至少由五个元素组成：

1. **前置条件（Given）**：输入、系统状态、用户身份、外部依赖状态。
2. **操作（When）**：调用函数、请求 API、消费消息、执行数据库事务。
3. **预期（Then）**：返回值、HTTP 状态、异常类型、持久化数据、消息状态等。
4. **可观测手段（Oracle）**：断言依据来自哪里，例如业务需求、Schema、唯一约束。
5. **隔离与清理（Isolation）**：测试执行后是否留下影响其他测试的状态。

例如，“用户重复提交同一反馈”不是一个足够精确的测试描述。更精确的表述是：

> Given：数据库中已存在 `owner=alice, idempotency_key=req-01` 的任务；When：同一身份、同一键、相同内容再次发送 POST；Then：仍返回原有任务 ID，数据库记录总数保持 1，不重新执行已经完成的副作用。

测试通过只能证明**被测试的输入、环境和断言所覆盖的性质**，不是对所有执行条件的形式化保证。尤其不能从单线程的离线测试推断多节点并发一定正确。

## 2. 单元测试、集成测试、端到端测试与效果评测

| 类型 | 测试对象 | 外部依赖 | 示例 | 不能直接证明 |
|---|---|---|---|---|
| 单元测试（Unit Test） | 函数、类、独立算法 | 使用固定数据或替身 | `normalize_payload()` 对空白的处理 | 数据库、HTTP、Kafka 整体正确 |
| 组件测试（Component Test） | API 应用的一部分 | 可以替换部分依赖 | FastAPI 路由 + 伪模型服务 | 真实模型、网络稳定性 |
| 集成测试（Integration Test） | 两个及以上真实组件的协作 | 至少一部分真实依赖 | FastAPI → SQLAlchemy → SQLite | PostgreSQL 特有的锁与隔离行为 |
| 端到端测试（E2E） | 从真实入口到最终系统结果 | 尽可能使用完整部署 | 前端 → API → Kafka → Worker → PostgreSQL → UI | 所有故障都已经覆盖 |
| AI 效果评测（Evaluation） | 模型/检索/工具选择质量 | 通常需真实模型和参考答案 | 固定问题、证据核对、答案评分 | 程序事务、异常分支正确 |

这些分类不是根据文件目录、测试速度或“用了多少个依赖”来划分，而是根据**验证对象和替代程度**来划分。使用 `TestClient` 并不自动意味着端到端测试；它调用的是真实 FastAPI 处理链，但并没有启动生产 HTTP Server。使用 SQLite 也不等于验证了 PostgreSQL 的隔离级别、行锁和 RLS。

### 2.1 为什么要分层

单元测试速度快、易定位错误；集成测试能发现组件之间的契约不一致；E2E 测试检验真实部署下是否能够完成业务。它们是互补关系：

- 单元测试发现 `retry_delay(0)` 没有正确拒绝。
- API 集成测试发现请求体无效却被错误地接受。
- 数据库集成测试发现插入一半时第二条记录冲突，没有正确回滚。
- Worker 集成测试发现任务失败后数据库状态未更新。
- 真正的 Kafka 集成测试才可能发现提交 Offset、Rebalance 和网络故障下的行为。

## 3. pytest 如何发现和执行测试

pytest 是 Python 测试运行器。默认按命名约定收集测试模块、函数和类，例如 `test_service.py`、`test_submit()`、`TestService.test_error()`。它通过 `assert` 判断预期，对失败断言展示表达式差异。测试中未经预期捕获的异常通常表现为 Error/Failure，意味着测试未按预期完成。

```python
# tests/test_math.py

def add(a: int, b: int) -> int:
    return a + b


def test_add_two_integers():
    # Given：整数 2、3；When：执行加法；Then：结果为 5。
    assert add(2, 3) == 5
```

常用命令：

```bash
python -m pytest -q                   # 运行全部测试，简洁输出
python -m pytest -v                   # 展示每条测试名称
python -m pytest tests/test_unit.py   # 运行指定文件
python -m pytest -k "rollback"        # 按名称筛选
python -m pytest -x                   # 第一处失败即停止
python -m pytest --lf                 # 重新运行上次失败的测试
python -m pytest --collect-only -q    # 仅检查发现了哪些测试
python -m pytest --durations=10       # 查看耗时最长的测试
```

推荐从项目根目录执行 `python -m pytest`，使 Python 解释器与当前虚拟环境一致。若直接执行 `pytest` 因环境或导入路径导致找不到模块，应排查项目安装方式与 `sys.path`，不能仅用忽略错误的方式处理。

### 3.1 失败测试与预期失败

- **PASS**：断言满足。
- **FAIL**：断言不满足或程序出现未预期错误。
- **SKIP**：当前不执行，需注明原因。
- **XFAIL**：已知缺陷/暂时不可实现且预期失败；通常建议 `strict=True`，避免缺陷意外修复后测试仍被掩盖。
- **XPASS**：标记为 XFAIL 的测试却通过了，需检查是否应取消该标记。

`pytest.raises` 用于**预期发生的异常**，不是忽略所有异常。避免 `except Exception: pass`、没有断言的“运行型测试”、依赖打印日志判断成功等做法。

## 4. 核心逻辑的单元测试

适合单元测试的代码包括：业务值规范化、状态转换、幂等键构造、重试退避、费用计算、参数边界与权限判定。它们应尽量不依赖真实数据库、模型 API 和 Kafka。

```python
import pytest

@pytest.mark.parametrize(
    "raw, expected",
    [
        pytest.param("  a   b ", "a b", id="space-collapse"),
        pytest.param("x\ny", "x y", id="newline"),
        pytest.param("你好", "你好", id="unicode"),
    ],
)
def test_normalize_payload(raw, expected):
    # Given：不同空白形式；When：规范化；Then：得到独立规定的结果。
    assert normalize_payload(raw) == expected
```

`@pytest.mark.parametrize` 的每一组参数会变成一个独立测试用例。为复杂参数添加 `id`，失败报告就能直接定位具体输入；测试用例数量以 pytest 收集结果为准，而不是源代码中的 `def test_` 数量。

### 4.1 异常分支

```python
def test_reject_blank_message():
    # Given：空白消息；When：执行规范化；Then：抛出 ValueError。
    with pytest.raises(ValueError, match="blank"):
        normalize_payload("   ")
```

异常测试至少可验证异常类型、错误码或错误信息；更加重要的是验证**错误没有造成不应发生的副作用**。例如请求 422 时，数据库中不应该产生任务。

### 4.2 为什么要验证边界

只测试正常的“黄金路径”无法证明异常处理有效。需要关注：

- 空字符串、空集合、缺失值、超长输入、非法枚举、错误类型。
- 最大与最小允许值、整数溢出（与具体业务和 DB 类型有关）、负数、精度。
- 重复请求、乱序事件、已完成状态再次执行。
- 外部调用超时、拒绝、无响应、非法 JSON、部分成功。
- 数据库唯一冲突、事务中途失败、服务重启。

失败分支是业务契约的一部分，不是“发生问题才补测试”的附属品。

## 5. Fixture、依赖注入与测试隔离

`@pytest.fixture` 定义可复用的测试前置资源。pytest 根据测试函数参数名注入它们。Fixture 可以依赖其他 Fixture，形成依赖图。常见作用域为 `function`（默认）、`class`、`module`、`package`、`session`。

```python
@pytest.fixture
def db_factory(tmp_path):
    engine = create_engine(f"sqlite+pysqlite:///{tmp_path / 'jobs.db'}")
    Base.metadata.create_all(engine)
    factory = sessionmaker(engine, expire_on_commit=False)
    yield factory
    engine.dispose()
```

这里每条测试都拥有独立临时 SQLite 文件、Schema 和 Engine。`yield` 之前是准备，之后是资源清理。`tmp_path` 是 pytest 提供的临时目录，减少文件互相污染。

以下做法容易引入误判：

- 多个测试共用全局可变字典、共享 Session 或真实开发数据库。
- 测试依赖执行顺序，例如第二个测试依赖第一个测试创建的数据。
- 只回滚主测试事务，但后台 Worker 使用另一连接，导致后台写入仍然持久化。
- 在 `session` 级 Fixture 中复用可变数据库数据，却默认测试相互独立。

### 5.1 SQLAlchemy 事务隔离测试

针对 PostgreSQL 和支持 SAVEPOINT 的驱动，可以使用外部事务 + `Session(join_transaction_mode="create_savepoint")` 的测试隔离方案；应用内部即使调用 `session.commit()`，测试结束后外层事务仍可以回滚。该模式需要数据库和驱动正确支持 SAVEPOINT，并且**只覆盖绑定到该事务/连接的工作**。如果 API 和 Worker 在不同进程、不同连接执行，单个外部测试事务不能自动回滚两者全部写入。

另一种更接近实际服务的策略是**每条测试使用独立数据库/schema，执行真实提交，测试后销毁资源**。本文可运行示例采用这种方式，以便验证重开 Session 后的数据确实存在。

## 6. 用替身替代昂贵或不可控的依赖

为了验证失败处理，通常不需要真的让模型 API 故障。可以通过受控替身强制抛出指定异常并检查后端反应。

```python
def flaky_model(prompt: str) -> str:
    raise TimeoutError("model timeout")

# 将 flaky_model 作为依赖传入业务函数，验证该异常映射到什么状态。
```

常见工具与职责：

| 技术 | 作用 | 典型场景 |
|---|---|---|
| `monkeypatch` | 临时替换函数、对象属性、环境变量 | 改写远程服务地址或模拟异常 |
| `unittest.mock.Mock` | 设置预期调用与返回值 | 断言工具被调用几次 |
| `AsyncMock` | 模拟异步调用 | 模拟 `await model_client.chat(...)` |
| `tmp_path` | 隔离文件与目录 | 状态文件、日志、SQLite 文件 |
| `caplog` | 捕获日志 | 检查错误记录且不泄露密钥 |
| 自定义 Fake | 按状态模拟替代服务 | 先失败再成功、重试耗尽 |

好的替身只替代**需要受控的边界**，不要替代整个被测试系统。否则测试只是在检查 Mock 自己是否按预设返回，并没有验证真实业务逻辑。

### 6.1 避免错误地使用 Mock

- Mock 只能证明调用发生过；不会证明真实第三方接口兼容。
- 不要大量断言函数内部实现细节，导致无行为变化的重构也造成测试失败。
- 替身应模拟有意义的协议错误，例如 HTTP 429、超时、无效模型输出。
- 必须另设少量真实第三方集成或合同测试，验证 Mock 假设未过时。

## 7. FastAPI 接口集成测试

FastAPI 提供基于 Starlette 和 HTTPX 的 `TestClient`。它能调用 ASGI 应用的真实路由、依赖、请求/响应校验和异常处理器，不必另外运行 Uvicorn 进程。

```python
def test_api_submit_returns_202_pending(submit):
    response = submit()
    assert response.status_code == 202
    assert response.json()["state"] == "pending"
    assert response.json()["attempts"] == 0
```

检查 API 时，应分三层：

1. **HTTP 层**：状态码、响应头、内容类型、错误码。
2. **契约层**：请求 Schema、响应字段、必填项和可空性。
3. **业务层**：数据库是否保存、状态是否正确、重复请求是否去重、未授权是否拒绝。

注意 HTTP `202 Accepted` 仅说明任务被接收，**并不意味着后台处理成功**。读取任务状态返回 `200 OK` 也可能读到业务状态 `FAILED`。

### 7.1 生命周期测试

使用 `with TestClient(app) as client:` 可以触发应用的 `lifespan` 启动与关闭事件（应用如果声明了 lifespan）。单纯创建 `TestClient(app)` 后不进入上下文管理器，不应假定生命周期处理已经运行。针对启动时创建的 HTTP 客户端、数据库引擎、缓存连接，应检查：

- 服务启动前资源不存在，启动后就绪；
- 启动失败不会报告虚假的健康状态；
- 正常关闭会停止新任务并释放资源；
- 运行中的请求/后台任务如何被停止或移交；
- 重复启动关闭不会泄漏连接或重复注册 Worker。

## 8. 数据库集成测试：提交、回滚与约束

数据库测试应从实际数据库状态判断结果，而不只是检查 ORM 对象字段。

```python
with db_factory.begin() as session:
    session.add(Job(owner="u", idempotency_key="existing", ...))

with pytest.raises(IntegrityError):
    with db_factory.begin() as session:
        session.add(Job(owner="u", idempotency_key="new", ...))
        session.add(Job(owner="u", idempotency_key="existing", ...))

with db_factory() as session:
    assert session.scalar(select(Job).where(Job.idempotency_key == "new")) is None
```

预期：冲突事务整体回滚，因此 `new` 也不能保留，但此前已经提交的 `existing` 记录应继续存在。

**必须区别**：

- `flush()` 在当前事务中把修改发送给数据库，不等于提交。
- `commit()` 成功之后，其他符合事务隔离规则的连接可以观察到已提交结果。
- `rollback()` 只能回滚尚未提交的同一数据库事务；不能撤销外部 API 调用。
- SQLite 的唯一约束与基本事务行为可以用于教学，但 PostgreSQL 特有的 `FOR UPDATE`、隔离级别、RLS、死锁和多事务并发需要真实 PostgreSQL 测试。

### 8.1 测试不完整结果

一项业务可能需要同时创建任务、保存反馈、写出待发布事件。预期是三者要么在同一数据库事务中全部成功，要么全部回滚。测试时应在第二或第三个写入环节注入失败，并从**新的 Session** 查询三张表的最终状态。若某些步骤跨不同数据库或外部服务，则不能仅依赖单库事务，需要 Outbox、幂等和补偿机制。

## 9. 后台任务集成测试的分层

后台任务需要验证的不仅是执行函数返回什么，还包括：

```text
HTTP POST /jobs
    ↓
数据库创建 PENDING
    ↓
Worker 领取任务 → RUNNING
    ↓
业务执行器成功/失败/退出
    ↓
数据库记录 SUCCEEDED / PENDING / FAILED / RUNNING
    ↓
HTTP GET /jobs/{id} 读取结果
```

本节示例实现了一个**本地 Worker 函数**，通过同一 SQLite 文件的不同 Session 读写状态。测试 API → 数据库 → Worker 函数 → 数据库 → API 的数据闭环；它不启动 Kafka、不提供分布式原子领取，也不自动调度任务。它因此是**本地组件集成测试**，不是 Kafka 消费系统的端到端测试。

至少要覆盖如下业务行为：

- 正常执行：PENDING → RUNNING → SUCCEEDED，结果可重开 Session 查询。
- 暂时性错误：记录错误和尝试次数，在预算内允许重试。
- 永久性错误：进入 FAILED，保留可诊断原因。
- 重试耗尽：不能无上限循环。
- 同一业务重复提交：返回相同任务或根据业务契约拒绝冲突。
- 成功任务重复执行：不重复生成业务结果。
- 模拟崩溃：在途状态可查询，并按租约与恢复策略决定是否再次处理。
- 两个 Worker 同时执行：需在**真实 PostgreSQL 事务和 Kafka**环境中验证竞态与 Offset 安全提交；本文示例不宣称覆盖。

### 9.1 服务断开与重启后的查询

若任务状态保存于数据库，HTTP 请求断开不应该自动删除任务记录。测试应重新创建客户端甚至重启独立进程，重新连接同一个持久化数据库，再检查任务状态和最终结果。单进程测试里“新开 Session”只能证明部分持久化行为，无法等价替代强制停止进程、重新启动容器和真实消息重投。

### 9.2 故障注入比等待真实故障更可靠

不要依靠真的等待 30 秒超时或者人工断网才能运行常规测试。可以注入时钟、故障执行器与网络替身，直接控制：

- 第一次请求抛 `TransientFailure`，第二次成功；
- 第三次尝试仍失败，进入终态；
- 执行器在持久化 RUNNING 之后异常中断；
- 租约未到期返回 `busy`；到期后允许接管；
- 再次调用已成功的任务时返回 `already_terminal`。

这样测试快速且确定性较强。真实容器杀进程、Broker 断链等压力测试仍需要在独立集成环境运行。

## 10. 异步与并发测试

异步函数不能仅因定义了 `async def` 就由普通 pytest 测试自动执行。配合 `pytest-asyncio`，可以：

```python
import asyncio
import pytest

@pytest.mark.asyncio
async def test_model_failure_propagates():
    async def broken():
        await asyncio.sleep(0)
        raise RuntimeError("model unavailable")

    with pytest.raises(RuntimeError, match="unavailable"):
        await broken()
```

如果测试的是异步 HTTP 路由加真实异步数据库，可以用 `httpx.AsyncClient` 和 `ASGITransport` 配合 `pytest.mark.asyncio`，并正确管理 FastAPI `lifespan`。避免在正在运行的事件循环中调用 `asyncio.run()`。

并发测试需要注意：

- `asyncio.gather()` 能测试协程调度与错误传播，但不能模拟多个独立进程。
- 使用事件或 Barrier 明确控制交错点，比依赖 `sleep(0.1)` 更可靠。
- 对数据库唯一约束应在多个连接/事务下发起竞争。
- 对 Kafka Offset 应控制消息重投、同分区完成顺序和提交窗口。
- 不要以毫秒级硬编码耗时阈值来证明业务正确性；时间断言会受到 CI 负载影响。

## 11. 如何为每个测试写出明确预期

推荐采用 `Given / When / Then` 并让测试名称可读。例如：

```python
def test_duplicate_submit_returns_same_job(submit):
    """Given 同一用户和幂等键；When 重复提交相同内容；
    Then 返回同一个任务 ID，不创建第二条业务任务。"""
    first_id = submit().json()["id"]
    second_id = submit().json()["id"]
    assert first_id == second_id
```

但这条断言仍有局限：只断言 ID 相同，**不直接证明数据库没有多一条记录**。若该性质重要，应追加 `SELECT COUNT(*)` 或唯一约束检查。测试名称、文档预期与实际断言必须一致。

### 11.1 一份测试用例记录模板

```text
Case ID：API-IDEMPOTENT-001
功能：同一请求重复提交
前提：用户 alice 的数据库初始无该任务
输入：payload='rule A'，idempotency_key='req-01'
步骤：连续发起两个 POST /jobs
预期 HTTP：两次均返回明确约定的成功/已存在状态
预期业务：两次返回同一 job_id
预期持久化：数据库中该 owner + key 仅一条记录
预期副作用：不会重复写入最终结果
失败定位：路由、唯一约束、事务、并发竞态
```

不应将“预期返回什么”留到程序运行之后才补写。否则容易出现测试只重复代码当前行为而不独立验证需求的问题。

## 12. 后台任务测试应该断言哪些维度

**至少有三类断言：**

1. **状态断言**：例如 `RUNNING` 后失败进入 `PENDING`（可重试）或 `FAILED`（终态）。
2. **数据断言**：例如最终结果只保存一条、错误原因可查询、尝试次数正确。
3. **副作用断言**：例如实际执行器调用次数、Outbox 记录数、消息确认顺序。

对于跨系统可靠性，还要追加以下真实集成测试：

- Kafka 发送成功但 HTTP 请求失败时重新提交是否去重；
- 数据库提交成功、Offset 未提交时进程强杀和重启是否重投；
- 同分区并发消息的安全提交水位是否正确；
- Consumer Group 重平衡中旧 Worker 是否被阻止继续写入；
- Worker 长任务在关闭、取消、超时、租约到期后能否恢复；
- 不能处理的消息是否有限重试并持久进入失败集合，其他任务是否仍可推进。

离线替身测试证明执行控制逻辑；真实 Broker/数据库测试证明组件之间的协作。两者都需要。

## 13. 现实中的测试环境如何划分

| 环境 | 推荐用途 | 数据隔离方式 |
|---|---|---|
| 纯内存/临时文件 | 单元测试与本地教学 | 每测试新建对象或 `tmp_path` |
| SQLite 文件 | SQLAlchemy 基本事务与 ORM 联动 | 每测试独立 DB 文件 |
| 临时 PostgreSQL 容器 | SQL、事务隔离、约束和迁移 | 每套测试独立数据库/schema |
| PostgreSQL + Kafka + Redis Compose | 集成与故障测试 | 独立 Topic、Consumer Group 和数据库 |
| 真实部署的预生产环境 | E2E、重启、性能和观测 | 与生产隔离的测试租户 |

Python Testcontainers 等工具能够在 Docker 环境中为 pytest 启动临时 PostgreSQL 实例。不要把生产数据库直接用作自动化集成测试的重置目标。

### 13.1 迁移测试与数据库重建

创建表 `Base.metadata.create_all()` 只测试 ORM 元数据建表，**不验证 Alembic 迁移文件能从旧版本升级**。针对实际项目，应从空库执行 `alembic upgrade head`，并从上一版数据库执行升级、检查历史数据回填和索引/约束。对不可逆的数据迁移不要假设 `downgrade` 必然安全。

## 14. 测试数据、重放与确定性

自动化测试应具备以下性质：

- **可重复**：相同输入和环境通常得到相同断言结果。
- **独立**：不同测试之间无执行顺序依赖。
- **可定位**：失败报告能指向具体用例及预期差异。
- **快速反馈**：常规单元测试不依赖真实付费模型。
- **可观测**：失败时保留非敏感的日志、事件及 DB 状态。

若使用随机数据，应保存随机种子和失败输入；若使用时间，应注入测试时钟；若使用模型，应保存模型与提示词版本、来源和评测集快照。不要把固定 Sleep 时间当成时序契约。

## 15. Coverage 是什么，不能证明什么

覆盖率工具可以统计行覆盖（line coverage）、分支覆盖（branch coverage），但它们不是“业务正确率”。

例如下面的代码即使每行都被执行，仍可能没有测试“负数输入”的预期：

```python
def calculate_discount(amount):
    return amount * 0.1
```

建议根据风险设计测试覆盖：

- 正常业务路径；
- 字段/范围校验；
- 权限拒绝、跨租户数据隔离；
- 事务冲突、重复提交；
- 外部错误、取消、超时；
- Worker 重试、失败终态与恢复。

可以使用 `pytest-cov` 统计覆盖率，但不应仅为了达到数值而写无意义断言。变更关键业务逻辑时，优先关注**原先失败能否被复现、修复后是否恢复、是否引入回归**。

## 16. CI 中执行什么

一条常见 CI 流程：

```text
提交 / Pull Request
    ├── 格式与静态检查（可选）
    ├── 单元测试（快速）
    ├── API + SQLite 本地集成测试
    ├── PostgreSQL 真实集成测试
    ├── Kafka/Worker 故障恢复测试（较慢）
    └── 测试报告 / 失败日志 / 必要工件
```

建议将慢速的真实环境测试标记成 `integration` 或 `e2e`，并让 CI 的检查状态清楚显示哪些被执行、哪些被跳过。`pytest -q` 全绿只能说明此次**收集并实际执行**的测试通过；若大量关键测试被 `skip`，不能对外概括为“全部能力已验证”。

## 17. 常见错误及其修正

| 错误做法 | 结果 | 更可靠的方法 |
|---|---|---|
| 只看 HTTP 200/202 | 把处理中或失败当成功 | 分开断言 HTTP、业务状态、DB 结果 |
| 只断言方法被调用一次 | 真实结果可能错误 | 从持久化状态和接口最终输出核对 |
| 每个测试复用一个全局数据库 | 测试之间污染 | 独立 DB/schema 或严格事务隔离 |
| Mock 了整个服务 | 无法验证组件协作 | 仅替换不可控边界，关键路径集成 |
| 测试预期从当前输出复制 | 错误实现也可能通过 | 使用需求、协议或独立资料作为 Oracle |
| 通过多次 `sleep` 等待 | 测试慢且不稳定 | 注入时间和状态转移触发条件 |
| 失败后直接 `pass` | 隐藏程序缺陷 | 断言具体异常和无副作用 |
| SQLite 成功即宣称 PostgreSQL 通过 | 数据库差异被忽略 | 在真实 PostgreSQL 跑迁移及并发测试 |
| 模拟 Worker 成功即宣称 Kafka 可靠 | Offset 与重平衡没测 | 接入真实 Kafka 强制故障测试 |
| 将人工模型示例当自动程序测试 | 两类指标混合 | 模型效果评测和程序测试独立报告 |

```python
from typing import Callable

class Job(Base):

    owner: Mapped[str] = mapped_column(String(80), nullable=False)

class JobCreate(BaseModel):
    payload: str = Field(min_length=1, max_length=200)
    idempotency_key: str = Field(min_length=1, max_length=80)

    id: int
    state: str
    attempts: int
    result: str | None
    error: str | None


def normalize_payload(value: str) -> str:
    """教学中的确定性归一化规则。"""
    if not isinstance(value, str):
        raise TypeError("payload must be str")
    normalized = " ".join(value.split())
    if not normalized:
        raise ValueError("payload is blank")
    return normalized


def fingerprint(payload: str) -> str:
    return sha256(normalize_payload(payload).encode("utf-8")).hexdigest()


def retry_delay(attempt: int, base: float = 0.2, cap: float = 5.0) -> float:
    if attempt < 1:
        raise ValueError("attempt starts at 1")
    return min(cap, base * (2 ** (attempt - 1)))


def create_app(factory: sessionmaker[Session]) -> FastAPI:
    app = FastAPI(title="pytest teaching service")

    def get_session():
        with factory() as session:
            yield session

    # X-Demo-User 仅模拟认证后的身份，不能作为真实登录认证方案。
    @app.post("/jobs", status_code=status.HTTP_202_ACCEPTED, response_model=JobView)
    def create_job(
        body: JobCreate,
        x_demo_user: str = Header(min_length=1),
        session: Session = Depends(get_session),
    ):
        payload = normalize_payload(body.payload)
        fp = fingerprint(payload)
        query = select(Job).where(
            Job.owner == x_demo_user,
            Job.idempotency_key == body.idempotency_key,
        )
        existing = session.scalar(query)
        if existing is not None:
            if existing.fingerprint != fp:
                raise HTTPException(409, "same key, different payload")
            return _view(existing)

        job = Job(owner=x_demo_user, idempotency_key=body.idempotency_key,
                  payload=payload, fingerprint=fp, state="pending", attempts=0)
        session.add(job)
        try:
            session.commit()
        except IntegrityError:
            session.rollback()
            existing = session.scalar(query)
            if existing is None:
                raise
            if existing.fingerprint != fp:
                raise HTTPException(409, "same key, different payload")
            return _view(existing)
        session.refresh(job)
        return _view(job)

    @app.get("/jobs/{job_id}", response_model=JobView)
    def get_job(job_id: int, x_demo_user: str = Header(min_length=1),
                session: Session = Depends(get_session)):
        job = session.scalar(select(Job).where(Job.id == job_id, Job.owner == x_demo_user))
        if job is None:
            raise HTTPException(404, "job not found")
        return _view(job)

    return app


def _view(job: Job) -> JobView:
    return JobView(id=job.id, state=job.state, attempts=job.attempts,
                   result=job.result, error=job.error)


class TransientFailure(Exception):
    pass


class PermanentFailure(Exception):
    pass


def epoch_now() -> float:
    return datetime.now(timezone.utc).timestamp()


def run_one(factory: sessionmaker[Session], job_id: int,
            executor: Callable[[str], str], *,
            now: Callable[[], float] = epoch_now,
            lease_seconds: float = 30.0, max_attempts: int = 3) -> str:
    """单进程教学 Worker。真实多 Worker 需使用数据库原子认领/代际保护。"""
    with factory.begin() as session:
        job = session.get(Job, job_id)
        if job is None:
            return "not_found"
        if job.state in ("succeeded", "failed"):
            return "already_terminal"
        if job.state == "running" and (job.lease_expires_at or 0) > now():
            return "busy"
        if job.attempts >= max_attempts:
            job.state = "failed"
            job.error = "attempts exhausted"
            job.lease_expires_at = None
            return "failed"
        job.state = "running"
        job.attempts += 1
        attempt = job.attempts
        payload = job.payload
        job.lease_expires_at = now() + lease_seconds

    # 这里模拟长耗时任务：业务并未被持久化队列自动调度。
    try:
        answer = executor(payload)
    except TransientFailure as exc:
        new_state = "pending" if attempt < max_attempts else "failed"
        with factory.begin() as session:
            job = session.get(Job, job_id)
            # 教学示例：真实并发场景应加执行代际 token 和条件 UPDATE。
            if job.state == "running" and job.attempts == attempt:
                job.state = new_state
                job.error = str(exc)
                job.lease_expires_at = None
        return new_state
    except PermanentFailure as exc:
        with factory.begin() as session:
            job = session.get(Job, job_id)
            if job.state == "running" and job.attempts == attempt:
                job.state = "failed"
                job.error = str(exc)
                job.lease_expires_at = None
        return "failed"
    # 未捕获的进程级故障可让 RUNNING 留存，下一次租约过期后接管。
    else:
        with factory.begin() as session:
            job = session.get(Job, job_id)
            if job.state == "running" and job.attempts == attempt:
                job.state = "succeeded"
                job.result = answer
                job.error = None
                job.lease_expires_at = None
                return "succeeded"
        return "stale"
```
