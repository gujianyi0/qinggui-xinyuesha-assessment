# Python 基础与异步编程（四）：事件循环阻塞、异步客户端与线程池

> 内容范围：事件循环调度原理、阻塞 I/O、CPU 密集型工作、`httpx.AsyncClient`、`asyncio.to_thread`、`ThreadPoolExecutor`、`ProcessPoolExecutor`、FastAPI 执行模型、取消与超时、测量与排错。适用于 Python 3.13+ 的主要语法；涉及解释器实现的部分单独说明。

## 1. 先明确“阻塞”的对象

在 `asyncio` 的典型使用方式中，**一个事件循环运行在一个操作系统线程上**。同一事件循环内的多个 Task 通过协作式调度交替执行：某个 Task 运行，直到它在合适的等待点挂起、结束或发生异常，其他就绪任务才获得执行机会。

“阻塞事件循环”不是指整个操作系统停止工作，而是指**运行事件循环的那个线程没办法及时回到事件循环去处理其他任务**。可能表现为：

- 已经准备好执行的其他 Task 长时间得不到调度。
- HTTP 服务中其他请求的响应被拖慢，WebSocket 心跳或 SSE 推送延迟。
- 已经到期的超时、定时器和取消请求不能及时被处理。
- CPU 使用率可能很高（忙计算），也可能很低（线程正在睡眠或等网络）。

事件循环的公平性来自协作式让出控制权，**不是**操作系统自动把一个正在执行同步代码的协程强行暂停。`async def` 本身只定义协程函数；它不改变内部同步操作的语义。

### 1.1 四个容易混淆的概念

| 概念 | 说明 | 典型现象 |
|---|---|---|
| 阻塞调用（blocking call） | 调用方在线程里等待返回 | `time.sleep()`、同步 `requests.get()` |
| 异步等待（non-blocking await） | 当前 Task 等待期间可让出事件循环 | `await asyncio.sleep()`、异步 socket I/O |
| 并发（concurrency） | 多项任务在同一时间段内交替推进 | 同一事件循环处理多个网络请求 |
| 并行（parallelism） | 多项计算在同一时刻真正执行 | 多进程使用多个 CPU 核心 |

**异步不是并行的同义词，线程池也不是“让所有 Python 代码变快”的按钮。**

## 2. 为什么 `time.sleep()` 会阻塞

`time.sleep(seconds)` 是**同步函数**。调用它的操作系统线程进入睡眠，只有等待结束才从函数返回。若这行代码发生在事件循环线程上，该线程就无法继续调度其他 Task。

```python
import asyncio
import time

async def bad_task():
    print("A 开始")
    time.sleep(2)        # 阻塞当前线程，事件循环无法调度其他任务
    print("A 结束")

async def another_task():
    print("B 开始")
    await asyncio.sleep(0.2)
    print("B 结束")

async def main():
    await asyncio.gather(bad_task(), another_task())

asyncio.run(main())
```

在默认任务调度方式和此调用顺序下，A 先进入 `time.sleep(2)`，B 通常只能等 A 结束后再启动；整体耗时约 2.2 秒。具体打印顺序受调度细节影响，不应据此推断所有情况下的绝对顺序。

正确地**异步等待**：

```python
async def good_task():
    print("A 开始")
    await asyncio.sleep(2)   # 当前 Task 挂起，事件循环可以运行 B
    print("A 结束")
```

若用 `good_task()` 替换 `bad_task()`，A 的两秒等待和 B 的 0.2 秒等待通常重叠，总耗时接近两秒（包含调度开销）。

注意 `asyncio.sleep()` 的作用是**安排异步等待**，不是执行繁重计算，也不是把调用搬到另一个线程。

### 2.1 `await` 本身不是万能的“让出执行权”

```python
async def fake_async():
    time.sleep(2)
    return "done"

async def main():
    result = await fake_async()  # 依然阻塞事件循环线程约两秒
```

因为 `fake_async()` 在返回之前并没有真正经过可以让其他任务运行的异步等待点。给一个同步阻塞函数套 `async def`，再在调用处加 `await`，不能自动消除阻塞。

再看这个例子：

```python
async def count():
    total = 0
    for i in range(30_000_000):
        total += i * i
    return total
```

它也是协程函数，但函数体没有任何挂起点；执行期间会持续占用事件循环线程。

## 3. 同步网络请求为什么会阻塞事件循环

网络请求通常经历 DNS 查询、连接建立、TLS 握手、写入请求、等待远端响应、接收数据等阶段。**等待网络的时间远远可能超过实际计算时间**。

同步 HTTP 客户端会让调用方线程等待相关操作完成：

```python
import requests

async def get_data():
    response = requests.get("https://example.com", timeout=5)
    response.raise_for_status()
    return response.text
```

这段代码虽然写在 `async def` 内，但 `requests.get()` 仍然是同步调用，可能在网络等待期间阻塞事件循环。`httpx.Client().get()`、`urllib.request.urlopen()`、同步数据库驱动、同步文件操作，也可能具有类似问题。

**容易误解：**“设置了 `timeout=5`，所以不会阻塞。”错误。超时限定的是某种等待条件，而不是把操作转为异步；只要同步调用还在运行，事件循环线程就被占用。此外，不同 HTTP 客户端对超时的定义不同，有些超时不是整个请求的绝对总时长。

### 3.1 同步与异步 HTTP 的执行过程

```text
同步请求（发生在事件循环线程中）
Task A → 发出 HTTP 请求 → [当前线程等待网络] → 收到响应 → 事件循环继续
Task B ----------------------------------------- 只能推迟执行

异步 HTTP 请求
Task A → 发出 HTTP 请求 → await（挂起） ───────────→ 收到响应后恢复
Task B --------------------→ 在 A 等待时继续执行
```

异步客户端一般借助事件循环及非阻塞 socket 等机制，在网络未就绪时挂起当前任务。不是每个底层步骤都完全零阻塞：如大量响应解码、同步 JSON 解析、复杂证书处理或第三方回调仍可能占用 CPU。因此应区分“网络等待非阻塞”和“整个函数绝对不消耗事件循环时间”。

## 4. 异步客户端适合什么场景

当**同一服务需要并发等待很多网络或其他异步 I/O 结果**时，首选异步客户端。例如：

- FastAPI 异步接口请求大模型 API、搜索 API、支付/业务 API。
- 使用异步数据库驱动访问 PostgreSQL、Redis。
- 长连接、WebSocket、SSE、持续流式模型输出。
- 一个请求需要并发读取多个外部信息源。

常用库：`httpx.AsyncClient`、`aiohttp.ClientSession`，以及真正支持异步操作的数据库客户端。**名字里有 `Async` 并不说明周边业务代码都不会阻塞**；同步密集计算仍要单独处理。

### 4.1 HTTPX 的最小示例

先安装：

```bash
python -m pip install httpx
```

```python
import asyncio
import httpx

async def fetch(url: str) -> str:
    async with httpx.AsyncClient(timeout=10.0) as client:
        response = await client.get(url)
        response.raise_for_status()
        return response.text

async def main():
    html = await fetch("https://example.com")
    print(len(html))

if __name__ == "__main__":
    asyncio.run(main())
```

关键点：

1. `AsyncClient.get()` 返回可等待操作，需要 `await`。
2. `raise_for_status()` 用于将非成功 HTTP 状态转换为异常；网络成功不等于业务成功。
3. `async with` 负责退出时关闭客户端与连接资源。
4. 上述写法适合一次性脚本和教学；**高频服务不宜在每次请求里重新创建客户端**。

### 4.2 连接复用和并发限制

高并发服务通常为一个生命周期范围内的请求复用 `AsyncClient`，利用连接池减少重复建立连接的成本：

```python
import httpx

client = httpx.AsyncClient(
    timeout=httpx.Timeout(15.0, connect=3.0),
    limits=httpx.Limits(max_connections=50, max_keepalive_connections=20),
)

# 在所属服务的生命周期内复用 client；关闭时 await client.aclose()
```

`max_connections` 是该客户端连接池的上限，不是全系统或整个集群的请求限流。仍可能需要应用级 `Semaphore`、每用户限额、超时和上游提供商配额控制。

**为什么要复用客户端？** 每次都创建客户端可能损失 Keep-Alive、连接池、TLS 会话相关优化，并造成无谓的资源开销。但也不要把全局客户端误用于跨进程共享，或在已关闭后继续复用；客户端生命周期应和拥有它的应用/事件循环相匹配。

### 4.3 FastAPI 生命周期内创建与关闭 AsyncClient

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI, Request
import httpx

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient(timeout=10.0)
    try:
        yield
    finally:
        await app.state.http.aclose()

app = FastAPI(lifespan=lifespan)

@app.get("/upstream")
async def upstream(request: Request):
    client: httpx.AsyncClient = request.app.state.http
    response = await client.get("https://example.com")
    response.raise_for_status()
    return {"status": response.status_code}
```

这个例子重点展示资源生命周期。生产使用还要考虑：可控的目标地址、鉴权、重试策略、错误映射、请求取消、响应体大小和安全日志等。

## 5. 线程池为什么能处理同步阻塞 I/O

假设一个第三方 SDK 只有同步接口，当前又不能替换。可把同步调用**卸载（offload）**到事件循环线程之外的工作线程：

```text
事件循环线程                    线程池工作线程
    |                               |
    |-- 提交同步函数 --------------->| 执行 requests.get()，等待网络
    |-- await（当前 Task 挂起）      | 
    |-- 继续调度其他 Task            |
    |<------------- 工作结果 --------|
    |-- 恢复原来的 Task             |
```

重要区别：**同步函数本身没有变为异步函数，它只是换了一个线程执行**；此时事件循环线程可以继续处理其他任务。

### 5.1 `asyncio.to_thread()`

Python 3.9+ 提供 `asyncio.to_thread(func, *args, **kwargs)`：

```python
import asyncio
import time

def blocking_sdk_call(query: str) -> str:
    time.sleep(2)             # 模拟只能同步等待的第三方 SDK
    return f"result: {query}"

async def main():
    result = await asyncio.to_thread(blocking_sdk_call, "hello")
    print(result)

asyncio.run(main())
```

**细节一：**`asyncio.to_thread(...)` 返回协程对象。只有这个协程被 `await` 或被安排成 Task 执行后，工作才会被提交到线程池。单独调用 `asyncio.to_thread(...)` 而不驱动协程，通常不会执行函数。

**细节二：**`await` 等待线程池结果时，事件循环仍可调度其他任务。单纯一个任务执行时，`to_thread` 未必让它本身更快；它的主要价值是**避免阻塞事件循环，提高其他任务的可响应性**。

**细节三：**`to_thread` 会传播当前 `contextvars.Context` 的上下文值，但并不意味着普通线程局部变量、任意共享对象都自动安全。

### 5.2 在同步 SDK 上使用 `to_thread`

```python
import asyncio
import requests

def fetch_sync(url: str) -> str:
    response = requests.get(url, timeout=(3.0, 10.0))
    response.raise_for_status()
    return response.text

async def fetch_from_async_service(url: str) -> str:
    return await asyncio.to_thread(fetch_sync, url)
```

这种写法是**无法使用原生异步客户端时的兼容方案**。若所有请求都经由网络 I/O，且现有库有质量可靠的异步实现，通常更推荐直接使用异步客户端。

`requests` 的 connect/read 超时不是严格的整次业务执行时限，重试、响应流和多个网络步骤仍须分别设计。

### 5.3 `run_in_executor()` 与显式线程池

```python
import asyncio
from concurrent.futures import ThreadPoolExecutor
import time

def blocking_job(value: int) -> int:
    time.sleep(0.2)
    return value * 2

async def main():
    loop = asyncio.get_running_loop()
    with ThreadPoolExecutor(max_workers=4) as pool:
        results = await asyncio.gather(
            *(loop.run_in_executor(pool, blocking_job, i) for i in range(6))
        )
        print(results)

if __name__ == "__main__":
    asyncio.run(main())
```

`to_thread` 通常更简单；`run_in_executor` 则方便指定线程池或进程池。注意：`with ThreadPoolExecutor(...)` 退出时会等待工作线程结束，**在异步服务中不应在每个请求里创建和销毁线程池**。应该让其生命周期受到应用统一管理。

## 6. 线程池的边界、代价与误区

### 6.1 线程不是无限资源

每个工作线程需要栈空间、调度开销，并竞争有限的 CPU、网络、数据库连接等资源。线程池队列如果持续堆积，可能出现等待时间增长、内存占用上升和服务难以停机。

例如 500 个请求都调用 `to_thread()`，不代表会瞬间创建 500 个线程；默认执行器使用有限的工作线程，其余工作会等待。即使没有阻塞事件循环，**线程池排队仍可能使接口变慢**。

### 6.2 线程安全必须独立验证

把 SDK 放到线程池后，要弄清楚它的实例能否跨线程并发调用。共享状态、连接对象、会话上下文、文件句柄等不一定线程安全；需要按 SDK 约束隔离实例，或使用锁与其他同步机制。

### 6.3 超时和取消并不等于强制停止工作线程

```python
import asyncio
import time

def non_interruptible_work():
    time.sleep(10)
    return "done"

async def main():
    try:
        async with asyncio.timeout(1):
            await asyncio.to_thread(non_interruptible_work)
    except TimeoutError:
        print("调用方已超时，但工作线程可能仍在运行")

asyncio.run(main())
```

`asyncio.timeout(1)` 会请求取消等待中的 Task，使调用方在超时后恢复控制，但**已经开始的同步线程函数通常不会因此被强制中断**；`asyncio.run()` 在退出时还会处理默认线程池关闭，示例程序本身的总运行时长可能仍接近十秒。

因此不能只给外层 Task 加超时，就宣称实际请求已经停止。需要在同步 SDK 自身设置合理超时，必要时提供协作式取消机制；不可中断的长期任务应考虑独立进程或独立 Worker，并明确强制终止及补偿策略。

## 7. CPU 密集型计算为什么也会阻塞

**I/O 密集型**表示程序大部分时间在等待外部资源，例如网络、磁盘或数据库。

**CPU 密集型**表示程序大部分时间在持续进行计算，例如大规模解析、图像处理、向量计算、复杂循环或数据转换。

```python
async def cpu_heavy():
    result = 0
    for i in range(20_000_000):
        result += (i * i) % 97
    return result
```

即使写在 `async def` 内，这段循环也不会主动让出事件循环。其他 Task 必须等它运行到挂起点、完成或抛异常后才得到调度机会。

### 7.1 `await asyncio.sleep(0)` 能否解决？

在较长的循环中**周期性**执行 `await asyncio.sleep(0)` 可以为其他 Task 提供调度机会：

```python
import asyncio

async def cooperative_compute(n: int):
    total = 0
    for i in range(n):
        total += i * i
        if i % 100_000 == 0:
            await asyncio.sleep(0)
    return total
```

但这并没有把 CPU 计算变成多核并行，也可能因频繁让出控制权增加总耗时。对特别重的计算，一般更合适的方式是移出事件循环线程，甚至使用独立进程/Worker。

## 8. GIL 与线程池执行 CPU 任务的关系

标准 CPython 解释器长期采用**全局解释器锁（GIL）**，在通常启用 GIL 的构建中，同一解释器内的多个线程不能同时运行 Python 字节码。因此：

- 对同步网络等待，线程仍然很有用，等待 I/O 时通常能够使其他线程运行。
- 对纯 Python 计算，多线程一般不能带来直接的多核计算加速；还可能增加切换开销。
- 某些 C/C++ 扩展（例如部分数值计算操作）会释放 GIL，可能从多线程获得真正的并行计算收益；是否释放由具体实现决定。

**版本说明：**Python 3.13 起提供可选的 free-threaded（无 GIL）构建；Python 3.14 的相关能力继续发展。普通 CPython 安装不能想当然地认为 GIL 已经被关闭。即使使用 free-threaded 版本，线程安全仍须单独保证。

```python
import sys
import sysconfig

print("Python:", sys.version)
print("支持自由线程构建:", sysconfig.get_config_var("Py_GIL_DISABLED"))
if hasattr(sys, "_is_gil_enabled"):
    print("当前 GIL 已启用:", sys._is_gil_enabled())
```

这里的运行结果由安装的 Python 解释器决定。

## 9. CPU 密集型任务：进程池更常用

`ProcessPoolExecutor` 可以把函数放到独立 Python 进程执行。每个进程通常拥有独立的解释器状态，因此在通常的 CPython/GIL 环境下更容易使用多个 CPU 核心。

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor

# 必须是模块顶层、可被子进程导入和序列化的函数
def heavy_calculation(n: int) -> int:
    return sum(i * i for i in range(n))

async def main():
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor(max_workers=2) as pool:
        results = await asyncio.gather(
            loop.run_in_executor(pool, heavy_calculation, 1_000_000),
            loop.run_in_executor(pool, heavy_calculation, 1_500_000),
        )
        print(results)

if __name__ == "__main__":
    asyncio.run(main())
```

Windows 通常使用 `spawn` 方式启动子进程，因此 `if __name__ == "__main__":` 的入口保护尤其重要。进程池中执行的函数和参数必须满足序列化要求；不能直接假定数据库连接、HTTP 客户端、闭包或任意复杂对象可以跨进程传递。

**进程池不是总能更快：**进程启动、数据复制或序列化、结果传输都有成本。如果任务很小，进程池开销可能超过计算本身；如果任务非常大、要跨服务恢复或需要可靠排队，则独立 Worker/任务队列往往比把任务藏在 Web 进程的进程池里更合适。

## 10. 线程池、进程池、异步客户端的场景选择

| 场景 | 优先考虑 | 理由 | 必须注意 |
|---|---|---|---|
| 频繁请求大模型 API | 异步 HTTP/SDK | I/O 等待可让出事件循环 | 连接复用、上游限流、超时 |
| 频繁读取异步数据库 | 异步数据库驱动 | 高并发 I/O 友好 | 连接池、事务、Session 隔离 |
| 只有同步接口的第三方 SDK | `asyncio.to_thread` / 有界线程池 | 减少事件循环阻塞 | 线程安全、取消不强停、池容量 |
| 同步文件操作，耗时不可忽略 | 线程池或异步文件方案 | 避免在事件循环线程等待磁盘 | 文件句柄、并发限制 |
| 纯 Python 大规模计算 | 进程池 / 独立计算 Worker | 更有机会利用多核 | 序列化、进程成本、重试 |
| NumPy 等释放 GIL 的计算 | 根据实现测试线程或进程 | 可能真正并行 | 检查具体库是否释放 GIL |
| WebSocket / SSE / 高并发网络 | 异步客户端与异步服务 | 同时处理大量连接和等待 | 背压、连接限制、断连清理 |
| 持续数分钟且必须断线恢复的任务 | 独立任务队列和 Worker | 状态可持久化、可恢复 | 幂等、重试、持久状态 |

简化决策：

```text
当前操作主要在做什么？
├─ 等待网络/数据库，且有真正异步接口
│  └─ 用异步客户端 + await
├─ 等待网络/文件，但仅有同步接口
│  └─ 用有界线程池 / asyncio.to_thread
├─ 长时间纯 Python 计算
│  └─ 用进程池或独立计算 Worker
└─ 很短的纯计算或数据整理
   └─ 可直接执行，但应监控单次耗时和事件循环延迟
```

## 11. FastAPI 中 `def` 与 `async def` 的执行区别

FastAPI 对自己负责调用的**同步路径操作函数**（普通 `def`）及同步依赖，通常会通过线程池运行，避免直接占用事件循环线程；异步路径操作函数（`async def`）直接在异步机制下运行。

```python
from fastapi import FastAPI
import time
import asyncio

app = FastAPI()

@app.get("/sync")
def sync_endpoint():
    time.sleep(2)             # FastAPI 将此普通 def 路由放进线程池
    return {"status": "ok"}

@app.get("/async-good")
async def async_good():
    await asyncio.sleep(2)
    return {"status": "ok"}

@app.get("/async-bad")
async def async_bad():
    time.sleep(2)             # 直接阻塞事件循环线程！
    return {"status": "ok"}
```

关键限制：**FastAPI 不会自动把你在 `async def` 内直接调用的任意同步辅助函数搬到线程池**。

```python
import requests

def blocking_helper():
    return requests.get("https://example.com", timeout=5).status_code

@app.get("/still-bad")
async def still_bad():
    return {"code": blocking_helper()}  # 直接执行同步函数，仍会阻塞
```

改进方法：把可控且适合异步的 I/O 改为真正异步客户端；确实只能同步执行时，显式使用 `await asyncio.to_thread(blocking_helper)`，或让整个仅使用同步栈的路由由 FastAPI 在线程池中运行。普通 `def` 路由也不是没有代价：大量慢同步调用可能占满线程池容量。

**不要反过来误解为 `def` 路由一定性能更好**。对于真正支持异步的客户端及长连接操作，`async def` 往往更符合设计目标。

## 12. 可运行对照实验：阻塞、异步等待、线程池

以下示例只用 Python 标准库，不需要网络，比较事件循环对其他任务的可响应性。保存为 `blocking_demo.py`：

```python
import asyncio
import time

async def ticker(log: list[tuple[str, float]], start: float):
    for i in range(4):
        log.append((f"tick-{i}", time.perf_counter() - start))
        await asyncio.sleep(0.1)

async def blocking_work():
    time.sleep(0.35)

async def async_wait():
    await asyncio.sleep(0.35)

async def offload_work():
    await asyncio.to_thread(time.sleep, 0.35)

async def scenario(name: str, work):
    events = []
    start = time.perf_counter()
    await asyncio.gather(ticker(events, start), work())
    print(f"\n{name}: {time.perf_counter()-start:.3f}s")
    for item, timestamp in events:
        print(f"  {item}: {timestamp:.3f}s")

async def main():
    await scenario("同步阻塞", blocking_work)
    await scenario("异步等待", async_wait)
    await scenario("线程卸载", offload_work)

if __name__ == "__main__":
    asyncio.run(main())
```

典型现象（示意，具体数值取决于机器和操作系统）：

- 同步阻塞：`tick-0` 可能先记录，但 `tick-1` 会被推迟到约 0.35 秒之后。
- 异步等待：ticker 大致每 0.1 秒得到执行机会。
- 线程卸载：ticker 同样能在工作线程等待期间继续推进。

**计时结论应看事件时间线，而不只是看总耗时。** 某些并发任务总耗时差异不大，但延迟分布和其他请求的响应性能可能差距很大。

## 13. 外层超时、底层网络超时与取消之间的区别

假设一个 AI API 查询：

```python
import asyncio

async def model_query(client, payload):
    async with asyncio.timeout(20):
        response = await client.post("https://api.example.com/v1/chat", json=payload)
        response.raise_for_status()
        return response.json()
```

这里至少有三个层次：

1. **应用超时**：例如 `asyncio.timeout(20)`，限制当前异步操作的等待窗口。
2. **HTTP 客户端超时**：连接、读取、写入、连接池等待等限制，依客户端而异。
3. **下游执行状态**：客户端不再等待，并不保证远端模型已经中止计算或计费。

如果外层是 `to_thread` 包裹同步 SDK，取消等待更不能保证工作线程立即停止。对于外部业务写入、支付、发送消息等有副作用操作，必须另外设计幂等键、最终状态确认及必要的补偿机制。

本节涉及的是阻塞行为，完整的取消、资源清理和限流会在后续学习目标中进一步展开。

## 14. 如何定位事件循环被阻塞

### 14.1 观察现象

- 某次耗时请求进行期间，连简单的健康检查也突然变慢。
- WebSocket 心跳或 SSE 更新整体卡顿后一起到达。
- CPU 可能长时间满核，也可能接近空闲。
- 定时器、取消或超时的反应明显滞后。

这些只是线索，不能仅凭一次现象断定事件循环阻塞；还可能是服务器线程/进程池饱和、数据库连接池耗尽、外部 API 配额或者反向代理排队。

### 14.2 使用 `asyncio` 调试模式

```python
import asyncio
import logging

logging.basicConfig(level=logging.DEBUG)

async def main():
    loop = asyncio.get_running_loop()
    loop.set_debug(True)
    loop.slow_callback_duration = 0.05
    # 在这里运行需要诊断的任务

asyncio.run(main())
```

在调试模式下，事件循环可以记录执行时间超过阈值的回调等信息。日志具体行为取决于版本、运行环境和回调类型。生产环境启用完整调试模式可能产生额外开销，应审慎使用。

### 14.3 事件循环延迟监测

```python
import asyncio

async def monitor_lag(interval: float = 0.1):
    loop = asyncio.get_running_loop()
    deadline = loop.time() + interval
    while True:
        await asyncio.sleep(max(0.0, deadline - loop.time()))
        lag = max(0.0, loop.time() - deadline)
        if lag > 0.05:
            print(f"event loop lag: {lag:.3f}s")
        deadline = loop.time() + interval
```

这个指标用于发现定时器预计唤醒时间与实际唤醒时间的偏差。它反映调度延迟，但并不自动告诉你是哪一个函数造成的；应结合日志、性能剖析与调用链排查。

### 14.4 沿调用链找隐藏的同步阻塞

从异步路由入口逐层检查：

```text
FastAPI async 路由
  └── Service 方法
        ├── 同步 requests.get()？
        ├── 同步数据库访问？
        ├── time.sleep()？
        ├── 大 JSON 解析或编码？
        ├── 大量循环/正则/压缩/图像处理？
        ├── 同步文件读写、日志写入？
        └── 第三方 SDK 是否实际支持异步？
```

注意：调用者是 `async def`，不代表被调函数自动具备异步执行语义。需要沿着**真正执行的同步函数**继续追踪。

## 15. 与 JavaScript、C++ 的思维对照

### 15.1 JavaScript

JavaScript `async/await` 的常见事件循环模型与 Python `asyncio` 有相似之处：`await fetch()` 期间可以处理其他任务；而在主线程里进行漫长同步计算仍会妨碍事件循环。Node.js 中 CPU 密集型工作可能需要 Worker Threads 或独立进程，浏览器中则可以考虑 Web Workers。它们和 Python 线程池并不是 API 层面一一对应的实现。

### 15.2 C++

C++ 中同步 `std::this_thread::sleep_for()` 会让当前线程休眠；同步 socket 读写也可能阻塞当前线程。异步 I/O 可通过不同操作系统或库机制实现；C++20 coroutine 也不能仅凭函数被声明为协程就自动保证调用的底层 I/O 非阻塞。具体线程调度、内存与生命周期规则需要按使用的框架理解。

**共同规律：**“同步/异步”描述等待及控制流模式；“单线程/多线程/多进程”描述执行资源；“并发/并行”描述任务推进方式。它们相关，但不是相同维度。

## 16. 典型错误与准确修正

| 错误理解或做法 | 为什么不准确 | 正确认识 |
|---|---|---|
| `async def` 内代码肯定非阻塞 | 同步函数照常执行 | 要查看每个实际调用是否让出控制权 |
| `await blocking_func()` 可解决阻塞 | 同步阻塞可能先发生，且普通返回值也不能直接被 `await` | 使用真正的异步 API 或线程卸载 |
| 只要加 `asyncio.sleep(0)` CPU 工作就变快 | 只改善调度机会，不增加计算资源 | CPU 重任务考虑进程池/Worker |
| 给同步请求加超时就不会阻塞 | 超时不改变同步执行模型 | 在异步客户端中等待，或卸载线程 |
| 一个请求超时代表线程已停止 | 线程内同步代码可能继续运行 | 底层超时、协作取消或进程隔离 |
| 线程越多吞吐越高 | 资源竞争、队列和 GIL 限制 | 有界并发，按负载测试容量 |
| CPU 计算放线程池就能多核加速 | 普通 CPython 纯 Python 计算受 GIL 影响 | 通常用进程池，注意 free-threaded/释放 GIL 的例外 |
| FastAPI 会自动处理所有同步工具函数 | 只自动卸载某些由框架调用的同步函数 | `async def` 内直接调用的同步工具仍阻塞 |
| 每次 HTTP 请求都创建 `AsyncClient` 最安全 | 损失连接复用，增加开销 | 按应用生命周期复用，并正确关闭 |
| 异步 HTTP 完全不会占用事件循环 | 响应解析、业务计算仍消耗 CPU | 对重 CPU 部分单独评估 |

## 17. 本节知识边界与总结

本节需要建立的因果链是：

1. **事件循环线程是有限的执行资源**。运行中的同步调用和不让出控制权的计算，会延迟其他 Task。
2. **`time.sleep()` 和同步网络 I/O** 都会让当前线程等待；如果发生在事件循环线程，就直接影响服务响应性。
3. **`await asyncio.sleep()` 和原生异步 HTTP 客户端** 会在等待期间挂起当前 Task，让其他 Task 获得执行机会。
4. **线程池** 是处理已有同步阻塞 I/O 的兼容机制，但有线程安全、容量、生命周期和不可强制取消等限制。
5. **CPU 密集型计算** 与等待网络不同；普通 CPython 的纯 Python 代码通常更适合进程池或独立计算 Worker，而不是指望线程池带来多核提速。
6. **正确诊断** 应同时查看事件循环延迟、请求耗时、CPU、线程池/连接池排队、底层调用链与异常记录；不能仅凭有没有 `async def` 下判断。
