# RAG、来源引用与知识更新（五）：固定评测集、独立参考依据与配对回归验证

> **文档定位**：纯知识性技术说明。覆盖 RAG 问答的评测数据构建、独立事实基准、检索与回答分层评价、A/B 配对实验、回归归因、统计与成本控制，并附可直接运行的 Python 标准库示例。
>
> **术语约定**：本文件中的游戏角色、版本与规则均为构造的教学数据，不代表真实游戏资料。离线测试评估的是评分程序与测试协议，不代表真实模型性能。

## 1. 为什么 RAG 需要固定评测集

RAG（Retrieval-Augmented Generation）系统由资料导入、解析与索引、检索、上下文组织、模型生成和引用呈现组成。任何一环发生变化，都可能影响最终回答。与常规程序的单一确定性断言相比，RAG 还存在两类困难：

1. **生成结果具有变化性**：即使问题、资料和提示词相同，模型也可能给出表述、长度或部分细节不同的回复。温度设为零或设置随机种子，也不能保证所有服务与硬件条件下完全可复现。
2. **“答案看起来合理”不等于“答案有证据”**：流畅、简洁、附带真实链接的回答，仍可能遗漏条件、引用错误版本或编造具体数值。

所谓**固定评测集（Frozen Evaluation Set）**，是指在一次可比的实验中，预先确定并冻结问题、输入条件、期望行为、独立参考答案和证据来源。不同模型、提示词或检索方案在同一组案例上运行，才能观察差异。

这里的“固定”有严格含义：仅固定问题文字是不够的。还应固定或记录知识库快照、资料权限、版本范围、参考标注、检索配置与评分规则。若资料版本本身发生改变，应将其视为实验变量，或者为新的资料快照重新建立独立基准。

### 1.1 三类必须区分的“正确”

| 类型 | 问题 | 典型评价 |
|---|---|---|
| 检索正确 | 足以回答的证据是否被取回并提供给模型？ | Recall@K、Precision@K、MRR、上下文证据覆盖 |
| 回答正确 | 最终回答是否符合独立的正确事实或期望行为？ | Answer Accuracy、事实断言正确率、任务成功率 |
| 有据可查 | 回答中的具体断言是否真的被引用的原文支持？ | Faithfulness、Citation Support、归因准确性 |

这三者彼此关联，但不能互相替代。例如：检索结果包含全部正确资料，而模型仍回答错误；又如模型碰巧答对，但引用的是错误章节。

## 2. 独立参考依据（Ground Truth / Gold Standard）是什么

独立参考依据是**在观察被测模型输出前**，依据可信、可追溯材料建立的评价标准。它不是模型的一次参考回答，也不是另一个模型对当前答案的即兴评价。

在规则型 RAG 中，一条可靠的参考标注至少包含：

- 问题及其必要限定条件，例如产品版本、规则适用范围、角色、地区或生效时间。
- 预期行为：`ANSWER`（可回答）、`CLARIFY`（必须澄清）、`ABSTAIN`（应说明信息不足）。
- 对可回答问题：正确事实、可接受的表达变体或结构化标准答案。
- 对不可直接回答的问题：缺失信息的具体原因，以及何种澄清或补充资料可以解决问题。
- 独立证据：文档 ID、版本、章节/页码/段落、引用原文位置、来源时间与内容哈希。
- 人工审定状态和标注来源；对争议案例可保留复核记录。

参考事实应从真实规则文件、权威数据库、适用的规范或其他被接受的资料源中产生。若用模型帮助生成问题，可由模型提出候选，再由人工依据原始资料审定答案与证据；**不能把候选生成直接当成真值**。

### 2.1 示例：一条带来源的黄金样例

```json
{
  "case_id": "RULE-018",
  "question": "在 2.0 版本中，角色 A 初始体力是多少？",
  "expected_behavior": "ANSWER",
  "reference_answer": {"initial_hp": 4},
  "evidence": [{
    "document_id": "manual-2.0",
    "document_version": "2.0",
    "section_path": "角色 / 角色 A / 基础属性",
    "chunk_id": "manual-2.0-role-a",
    "quote": "角色 A 的初始体力为 4。",
    "content_sha256": "<在实际导入阶段计算的哈希>"
  }],
  "source_review": "human_verified",
  "snapshot_id": "corpus-2026-11-11"
}
```

这是**结构示意**，并非真实资料。真实系统应保存该来源在指定版本中的可验证文本、可信标注记录以及访问权限，而不只是文档标题或 URL。

### 2.2 标准答案不一定是固定字符串

自然语言问答经常存在等价表达：

- “初始体力为四点”与“4 点初始体力”在结构化数值层面相同。
- “先结算 A，再结算 B”不能简单视为“先结算 B，再结算 A”，因为顺序是业务事实。
- 对多条件规则，应校验版本、触发条件、例外条款和结算顺序，而不是只看关键词。
- 合理弃答或请求澄清也是一种正确行为，不能一律计为没有回答。

因此评价可以分为确定性校验（精确数字、枚举、状态、文档 ID）与证据型人工/语义校验（是否遗漏条件、是否被原文蕴含）。不要依赖单一字符串匹配判断复杂答案。

## 3. 如何设计固定问题集：覆盖正常案例与失败边界

题目应当从真实用户任务出发，同时覆盖容易发生错误的输入，而不只是“资料里能直接找到的简单问题”。

### 3.1 20 条问题集的一个覆盖矩阵

| 类型 | 例数 | 预期验证重点 |
|---|---:|---|
| 单事实且有直接证据 | 4 | 数值、实体、对应来源 |
| 跨章节或多证据组合 | 3 | 多证据召回、条件完整性 |
| 版本限定的查询 | 3 | 版本过滤、历史答案与生效规则 |
| 多轮追问 | 2 | 上下文指代、沿用必要约束 |
| 资料不存在 | 2 | 合理弃答，不编造 |
| 问题缺少必要限定条件 | 2 | 澄清而不是猜版本 |
| 来源冲突或未生效草案 | 2 | 权威性与有效性判断 |
| 检索工具异常或数据访问限制 | 2 | 识别失败、权限拒绝与恢复路径 |
| **总计** | **20** | |

这是示例配比，可按业务实际风险调整。若核心场景是跨版本规则问答，就应增加版本歧义和版本切换案例；若系统面向多租户，还应增加隔离和权限测试。

### 3.2 样例的来源与独立性

常见来源包括：

1. 从经过隐私处理的真实问答记录抽样，再由人工标注。
2. 从资料目录、规则边界和业务流程中人工设计问题。
3. 汇总历史故障，保留真实输入和独立验证依据。
4. 利用模型生成变体问题，但必须人工审查事实正确性与覆盖价值。

**不应把被测模型刚刚生成的答案复制为参考答案。** 这会造成评价闭环自证，使错误被当作正确基准。

### 3.3 固定集、开发集和留出集

- **开发集（Development）**：可频繁查看、用于迭代检索参数和提示词。
- **回归集（Regression）**：保存已知关键案例和历史故障，作为修改后的稳定性检查。
- **独立留出集（Held-out）**：不根据其逐题结果反复优化，专门评估泛化能力。
- **线上监测集（Production Monitoring）**：从实际流量的匿名化、授权样本中持续抽样，识别数据分布变化。

反复根据同一 20 条题调 Prompt，会逐步对这 20 条题过拟合。因此固定集适合做可比回归测试，但不能单独证明对全体真实用户的泛化质量。应定期增加独立样例，维护盲测或留出评测。

## 4. 测试数据和知识库快照必须可复现

RAG 的输入不只是一个字符串问题，还包含可检索的知识范围。

### 4.1 需要冻结或记录的条件

| 条件 | 记录方式 |
|---|---|
| 评测集 | `dataset_id`、`dataset_version`、文件哈希 |
| 原始资料 | `source_id`、`source_version`、内容哈希 |
| 索引数据 | `corpus_snapshot_id`、索引构建时间 |
| 分块策略 | 分块器版本、Chunk Size、Overlap |
| Embedding | 模型 ID、维度、向量归一化方式 |
| 检索器 | 算法、过滤、候选 K、重排 K、阈值 |
| 生成模型 | 供应商、模型 ID、可用的模型快照标识 |
| 提示词 | Prompt 版本、模板哈希、完整渲染后的关键配置 |
| 生成参数 | 温度、Top-p、输出上限、工具列表 |
| 评分器 | 评分规则版本、评审模型/人工标注版本 |
| 执行记录 | Run ID、时间、原始响应、用量、延迟、错误 |

如果 A 版本使用知识库快照 1，B 版本使用快照 2，则两者的分数差异未必来自模型或提示词修改。要比较单变量效果，必须控制其他因素；如果需要同时比较升级后的完整系统，应该把“全系统比较”明确标注为另一个实验。

### 4.2 “同一组样例”至少需要满足什么

- 同一 `case_id` 必须代表同一个问题和相同的参考规则。
- 不得把 A 版失败题在 B 版中移除。
- 不得只统计 B 版成功返回的题，忽略超时、异常或格式错误。
- 同一批样例应按 ID 对齐，不能只按数组顺序假设对应。
- 如果参考答案因为原始规则修订而需要变化，应记录评测集的新版本，不能悄悄覆盖旧的 Gold Standard。

## 5. RAG 的分层评价框架

完整问答不应只得到一个总分。建议至少记录以下几个层次。

### 5.1 第一层：知识库覆盖与导入完整性

问题：**需要的原始资料是否进入了正确的知识库版本？**

常见指标：文档导入成功率、解析后文本完整度、章节覆盖、文档版本一致率、索引已发布比例。

若正确规则根本不存在于当前可访问的索引中，则不能将未召回简单归咎于检索模型。导入与索引完整性测试需要单独进行。

### 5.2 第二层：检索效果

使用人工标注的相关证据集合衡量检索：

**Recall@K（召回率）**：前 K 个结果中覆盖了多少应当命中的相关证据。

\[
\operatorname{Recall@K}(q)=\frac{|R_K(q)\cap G(q)|}{|G(q)|}
\]

其中，\(R_K(q)\) 是问题 q 实际检索到的前 K 个证据 ID，\(G(q)\) 是独立标注的 Gold Evidence ID 集合。若 \(G(q)\) 为空，应把问题当作特殊的无答案案例，而不是把分母设为零后随意赋值为 1。

**Precision@K（准确率）**：前 K 个结果中相关结果的比例。

\[
\operatorname{Precision@K}(q)=\frac{|R_K(q)\cap G(q)|}{|R_K(q)|}
\]

当实际返回结果少于 K 条时，分母口径也可选择 K（传统 Precision@K 常用固定 K）或实际结果数，**必须在评测协议中明确口径并保持一致**。

**MRR（Mean Reciprocal Rank）**：首条正确相关结果的排名倒数在题集上的平均值。适合首个命中的重要性很高的任务，但它不衡量多证据问题的完整覆盖。

**nDCG@K**：支持多级相关性评分（例如“直接支持事实”“背景相关”“无关”），可用于评价排序质量。

这些指标的前提是证据标签可靠。对于一条资料可能存在多个等价片段的情况，需要在标注中允许有效证据集合或等价组，避免把正确的其他来源误判为不相关。

### 5.3 第三层：上下文交付

**检索结果命中，不代表模型实际看到了证据。**

检索后可能发生重排、合并、去重、Token 裁剪和权限过滤。因此应另外记录：

- 实际检索结果 `retrieved_ids`；
- 经过重排/过滤后保留的结果 `selected_ids`；
- 最终进入 Prompt 的证据 `prompt_evidence_ids`；
- 每段证据是否保留了关键条件和来源信息。

如果召回成功，但 Prompt 裁剪删掉了关键段落，这属于上下文组织问题，不是检索完全失败，更不是模型在拿到充分证据后仍然答错。

### 5.4 第四层：回答准确性

**Answer Correctness** 比较生成结论与独立的真实答案，关注：

- 核心事实/数字是否正确；
- 适用版本是否正确；
- 条件、例外和范围是否完整；
- 不存在答案时有没有合理说明；
- 不明确时是否提出必要澄清。

对于结构化事实可使用程序判断；开放式文本可以使用分解后的事实断言、明确评分规程和人工复核。文本相似度只能辅助，不能直接代替事实正确性。

### 5.5 第五层：忠实度与引用支持

**Faithfulness** 检查模型回答中的断言是否得到给定上下文支持；**Citation Support** 进一步检查回答实际标注的引文是否支持其所对应的具体断言。

一个模型可能答案正确，却给出错误引用；也可能引用真实文档，但该文档没有证实回答中声称的内容。

可以按“断言 → 引用 → 原文位置 → 是否支持”逐条评价，而不能只检查链接或 Chunk ID 是否存在。引用的版本、访问权限和原文完整性也应被校验。

### 5.6 第六层：用户可感知结果与资源代价

包括完成率、合理弃答率、过度弃答率、澄清质量、用户下一步是否明确、P50/P95 耗时、Token 用量、API 成本、超时率和错误率。

一个模型可能答案略好，但 P95 耗时显著恶化；如果业务要求快速响应，就需要权衡甚至拒绝这次更新。

## 6. 区分四类典型错误的诊断矩阵

| 知识库有证据？ | 检索结果含证据？ | Prompt 含完整证据？ | 最终回答正确？ | 优先定位 |
|---|---|---|---|---|
| 否 | 否 | 否 | 否 | 导入、解析、索引与版本发布 |
| 是 | 否 | 否 | 否 | 检索、过滤、候选召回 |
| 是 | 是 | 否 | 否 | 重排、上下文选择、截断 |
| 是 | 是 | 是 | 否 | 生成、提示词、信息归纳、推理或输出验证 |
| 是 | 是 | 是 | 是，但引用错误 | 引用映射、来源定位、证据支持验证 |
| 无合法资料/无权限 | 不应提供 | 不应提供 | 编造答案 | 弃答与权限边界失败 |

这张表只是诊断框架。现实中可能同时存在多个原因，需要通过保存完整检索轨迹、实际 Prompt、模型响应和引用记录来定位。

## 7. 模型或提示词修改后的配对比较（Paired Evaluation）

为了判断修改是否有收益，建议采用**同题配对比较**：

1. 冻结一份具有来源依据的评测集。
2. 在旧版本（Baseline）上执行全部题目并保存逐题输出。
3. 只修改目标变量，例如 Prompt v1 → Prompt v2。
4. 在新版本（Candidate）上执行完全相同的题目。
5. 为两次运行分别计算检索、生成、引用和资源指标。
6. 对每条 `case_id` 检查：原来正确现在错误、原来错误现在正确、两版都对、两版都错。
7. 查看平均分之外的失败类别，决定是否回滚或进一步修复。

### 7.1 四种配对结果

| 基线 | 新版 | 含义 |
|---|---|---|
| 通过 | 通过 | 保持正确 |
| 失败 | 通过 | 改进（Improvement） |
| 通过 | 失败 | **回归（Regression）** |
| 失败 | 失败 | 未解决问题 |

只对比“平均分提高 10%”是不够的：对高风险场景，一条严重回归可能超过若干低风险改进的价值。

### 7.2 示例：总体变好，但仍有回归

假设 8 条固定问题：

- 基线：5 条通过，正确率 62.5%。
- 新版：7 条通过，正确率 87.5%。
- 新版修复了 C02、C03、C06。
- 但 C05 由通过变为失败：双证据规则的引用漏掉了其中一条。

新版**净提高 25 个百分点**，但并不是“没有退步”。是否允许上线，要看 C05 的业务严重程度与发布门槛。

## 8. 什么叫“同一组样例”之外的实验控制

### 8.1 只改一个变量最容易归因

如果要评价 Prompt 修改，尽可能固定：模型、检索器、知识库、温度、输出约束、评分逻辑和其他参数。

如果同时改模型、Embedding、分块和提示词，仍然可以做系统级 A/B 比较，但无法仅凭总分断言哪个改动造成了差异。可以通过消融实验（Ablation）逐个打开/关闭变更，分析组件贡献。

### 8.2 非确定性与重复测量

即使输入相同，生成系统也可能波动。对于结果敏感的模型与参数，可以让相同版本重复运行固定问题，报告：

- 各次测试的均值、中位数、范围；
- 逐题通过次数比例；
- 失败在不同运行间是否稳定；
- 关键指标的置信区间（样本足够时）。

**设置 Seed 不等于获得严格的跨版本确定性。** 模型后端、服务部署或并发配置变化都可能影响输出。

### 8.3 数据集大小与统计不确定性

在只有 20 条样例时，一题变化就是 5 个百分点；在只有 8 条样例时，一题变化就是 12.5 个百分点。这样的样本足以用于教学和发现具体回归，但不能单独证明大规模生产流量中性能提升的统计显著性。

若需要做正式实验，可针对配对二元结果关注“只在 A 版通过的条数”与“只在 B 版通过的条数”，使用适合配对数据的检验（例如 McNemar 检验）及置信区间；不要对高度相关的两组样例当成两个独立样本进行比较。评价集也应尽可能覆盖真实业务分布。

## 9. 设计评分规则：先定义通过，再开始跑模型

一个有效的评测协议应在实验开始前明确：

- 可回答问题必须满足哪些事实条件，是否允许多种等价答案。
- 一条回答必须提供几条支持证据，哪些证据组合属于充分证据。
- 如何评价多跳问题的遗漏条件。
- 版本未知时允许直接回答还是必须澄清。
- 未知答案时，何种弃答表达为合格。
- 模型 API 失败、超时、工具异常如何计分。
- 同一题是否使用人工复核；复核人如何盲评。
- 是否存在“一票否决”的关键安全、权限或事实错误。

### 9.1 程序评分与人工/模型评分的分工

| 可程序确定性检查 | 通常需要人工或校准过的语义评价 |
|---|---|
| JSON 可解析、字段存在、数据类型 | 文本陈述是否完整且无误导 |
| 数值、固定枚举、精确版本号 | 条件与例外是否正确解释 |
| 是否引用存在的证据 ID | 引用原文是否支持具体结论 |
| 返回状态是否符合预期 | 非标准但合理的表达是否可接受 |
| 耗时、Token、错误率 | 用户是否能够正确理解与采取下一步 |

**LLM-as-a-Judge** 可以帮助规模化评分，但它也可能有位置偏差、冗长偏好和事实性误判。应使用独立人工已标注的样本校准评分器，复核有争议或高风险案例，记录评分器版本。不能用“另一个模型说对”替代真实证据。

## 11. 完整 Python 离线配对评测程序

以下示例只使用 Python 标准库，完全不需要模型 API Key。它验证固定样例对齐、决策状态、结构化答案键、引用是否完整、引用是否属于检索结果、检索召回、平均延迟和逐题改进/回归。

**教学简化条件**：本例中每题的 `required_evidence_ids` 被视为唯一必需的证据组合；真实 RAG 可能存在多组等价有效证据，必须由人工标注可接受组合。本例的“引用校验”仅检查 ID 对齐和集合覆盖，**并未通过语义方法证明原文真正支持答案**。

程序中的 BASELINE 与 CANDIDATE 是人工构造的模拟结果，不是模型运行输出。

```python
"""离线 RAG 固定样例配对评测；不调用真实大模型或向量数据库。"""
from __future__ import annotations

from dataclasses import dataclass
from statistics import mean


@dataclass(frozen=True)
class Case:
    case_id: str
    question: str
    expected_status: str             # ANSWER / CLARIFY / ABSTAIN
    expected_key: str | None
    required_evidence_ids: frozenset[str]


@dataclass(frozen=True)
class Prediction:
    case_id: str
    status: str
    answer_key: str | None
    retrieved_ids: tuple[str, ...]
    cited_ids: tuple[str, ...]
    latency_ms: int
    input_tokens: int
    output_tokens: int


CASES = [
    Case("C01", "1.0 版角色 A 初始体力？", "ANSWER", "4", frozenset({"RULE-V1-A"})),
    Case("C02", "2.0 版角色 B 初始体力？", "ANSWER", "6", frozenset({"RULE-V2-B"})),
    Case("C03", "没有版本时，角色 C 技能是多少？", "CLARIFY", None, frozenset()),
    Case("C04", "资料库没有的未发布角色 X 数值？", "ABSTAIN", None, frozenset()),
    Case("C05", "双条件规则同时触发后效果？", "ANSWER", "先结算A再结算B", frozenset({"RULE-CHAIN-A", "RULE-CHAIN-B"})),
    Case("C06", "技能 D 每回合最多用几次？", "ANSWER", "3", frozenset({"RULE-D"})),
    Case("C07", "两个有效版本不明确时如何回复？", "CLARIFY", None, frozenset()),
    Case("C08", "规则 E 的伤害属性？", "ANSWER", "火焰", frozenset({"RULE-E"})),
]


def pred(c: Case, *, status: str | None = None, answer: str | None = None,
         retrieved: tuple[str, ...] | None = None,
         cited: tuple[str, ...] | None = None, latency_ms: int = 800) -> Prediction:
    """只用于生成可重复的人工构造测试数据。"""
    keys = tuple(sorted(c.required_evidence_ids))
    return Prediction(
        c.case_id, status or c.expected_status,
        c.expected_key if answer is None else answer,
        keys if retrieved is None else retrieved,
        keys if cited is None else cited,
        latency_ms, 400, 120,
    )


BASELINE = [pred(c, latency_ms=800 + i * 30) for i, c in enumerate(CASES)]
CANDIDATE = [pred(c, latency_ms=1050 + i * 30) for i, c in enumerate(CASES)]

# 基线：两条决策/答案错误、一条引用缺失。
BASELINE[1] = pred(CASES[1], answer="5", latency_ms=830)
BASELINE[2] = pred(CASES[2], status="ANSWER", answer="未知答案", latency_ms=860)
BASELINE[5] = pred(CASES[5], cited=(), latency_ms=950)

# 新版：修复上述三项，却在双证据规则中遗漏一条引用。
CANDIDATE[4] = pred(CASES[4], cited=("RULE-CHAIN-A",), latency_ms=1170)


def by_id(items, label: str) -> dict:
    result = {}
    for item in items:
        if item.case_id in result:
            raise ValueError(f"{label}: 重复 case_id={item.case_id}")
        result[item.case_id] = item
    return result


def validate_alignment(cases: list[Case], predictions: list[Prediction]) -> None:
    gold = by_id(cases, "gold")
    got = by_id(predictions, "run")
    if set(gold) != set(got):
        raise ValueError(f"评测集合不一致: missing={set(gold)-set(got)}, extra={set(got)-set(gold)}")


def grade(case: Case, p: Prediction) -> dict:
    """确定性校验：状态、闭集答案键、引用 ID 与检索集合，不判断自然语言语义蕴涵。"""
    if p.status not in {"ANSWER", "CLARIFY", "ABSTAIN"}:
        raise ValueError(f"非法状态: {p.status}")
    if p.latency_ms < 0 or p.input_tokens < 0 or p.output_tokens < 0:
        raise ValueError("耗时和用量不能为负数")
    retrieved, cited, required = set(p.retrieved_ids), set(p.cited_ids), set(case.required_evidence_ids)
    status_ok = p.status == case.expected_status
    answer_ok = (p.answer_key == case.expected_key) if case.expected_status == "ANSWER" else p.answer_key is None
    # 非回答场景不应伪造引用或答案。
    citation_ok = ((required <= cited) and (cited <= retrieved)) if case.expected_status == "ANSWER" else (not cited)
    all_ok = status_ok and answer_ok and citation_ok
    recall = (len(retrieved & required) / len(required)) if required else None
    return {"pass": all_ok, "status_ok": status_ok,
            "answer_ok": answer_ok, "citation_ok": citation_ok,
            "recall": recall}


def compare(cases: list[Case], baseline: list[Prediction], candidate: list[Prediction]) -> dict:
    validate_alignment(cases, baseline)
    validate_alignment(cases, candidate)
    a, b = by_id(baseline, "baseline"), by_id(candidate, "candidate")
    grades_a = {c.case_id: grade(c, a[c.case_id]) for c in cases}
    grades_b = {c.case_id: grade(c, b[c.case_id]) for c in cases}
    improved = [c.case_id for c in cases if not grades_a[c.case_id]["pass"] and grades_b[c.case_id]["pass"]]
    regressed = [c.case_id for c in cases if grades_a[c.case_id]["pass"] and not grades_b[c.case_id]["pass"]]

    def summary(grades, predictions):
        p = list(predictions)
        valid_recall = [g["recall"] for g in grades.values() if g["recall"] is not None]
        return {"passed": sum(g["pass"] for g in grades.values()),
                "total": len(cases),
                "pass_rate": sum(g["pass"] for g in grades.values()) / len(cases),
                "macro_recall": mean(valid_recall) if valid_recall else None,
                "mean_latency_ms": mean(x.latency_ms for x in p),
                "input_tokens": sum(x.input_tokens for x in p),
                "output_tokens": sum(x.output_tokens for x in p)}

    return {"baseline": summary(grades_a, baseline),
            "candidate": summary(grades_b, candidate),
            "improved": improved, "regressed": regressed,
            "per_case_baseline": grades_a, "per_case_candidate": grades_b}


if __name__ == "__main__":
    import json
    print(json.dumps(compare(CASES, BASELINE, CANDIDATE), ensure_ascii=False, indent=2))
```

## 12. Python 单元测试

以下测试使用 `unittest`，覆盖了固定题集对齐、重复 ID、缺失题、非法状态、引用遗漏、答案错误、回归识别和指标统计。

import unittest
from dataclasses import replace
from eval_demo import CASES, BASELINE, CANDIDATE, compare, grade, validate_alignment, pred


class TestOfflineEvaluation(unittest.TestCase):
    def test_case_count(self):
        self.assertEqual(len(CASES), 8)

    def test_all_ids_unique(self):
        self.assertEqual(len({c.case_id for c in CASES}), len(CASES))

    def test_missing_case_rejected(self):
        with self.assertRaises(ValueError):
            validate_alignment(CASES, BASELINE[:-1])

    def test_duplicate_id_rejected(self):
        with self.assertRaises(ValueError):
            validate_alignment(CASES, BASELINE + [BASELINE[0]])

    def test_unknown_id_rejected(self):
        with self.assertRaises(ValueError):
            validate_alignment(CASES, BASELINE[:-1] + [replace(BASELINE[-1], case_id="UNKNOWN")])

    def test_answer_requires_evidence(self):
        self.assertFalse(grade(CASES[5], BASELINE[5])["pass"])

    def test_nonanswer_requires_no_key(self):
        self.assertFalse(grade(CASES[2], BASELINE[2])["pass"])

    def test_citation_must_be_retrieved(self):
        self.assertFalse(grade(CASES[0], replace(BASELINE[0], retrieved_ids=()))["citation_ok"])

    def test_invalid_status(self):
        with self.assertRaises(ValueError):
            grade(CASES[0], replace(BASELINE[0], status="MYSTERY"))

    def test_negative_latency(self):
        with self.assertRaises(ValueError):
            grade(CASES[0], replace(BASELINE[0], latency_ms=-1))

    def test_candidate_regression(self):
        self.assertEqual(compare(CASES, BASELINE, CANDIDATE)["regressed"], ["C05"])

    def test_candidate_improvements(self):
        self.assertEqual(compare(CASES, BASELINE, CANDIDATE)["improved"], ["C02", "C03", "C06"])

    def test_answer_wrong_even_if_retrieval_perfect(self):

    unittest.main()

## 13. 将这个评测程序接入真实 RAG 系统

实际应用通常要将程序中的人工构造 `Prediction` 替换为真实系统输出。推荐在执行过程中保留：

```text
问题 Case ID
  ↓
固定知识库版本 + 已记录检索配置
  ↓
retrieved_ids（原始召回）
  ↓
selected_ids（重排、过滤后的证据）
  ↓
prompt_evidence_ids（真正送入模型的证据）
  ↓
模型原始响应 + 实际结束状态
  ↓
规范化结果（status、answer、cited_ids）
  ↓
程序自动评分 + 引用语义复核
  ↓
逐题报告 + 配对差异
```

可按下列边界组织代码：

```python
async def evaluate_one(case, rag_pipeline, grader):
    # 实际实现需要记录检索、上下文与生成各阶段输出。
    result = await rag_pipeline.answer(case.question)
    return await grader.grade(case, result)
```

以上只是接口示意。真实 `rag_pipeline` 需要明确支持固定资料快照、权限、超时和事件追踪；`grader` 需要独立参考证据和确定性的评分契约。不能把“能跑出回复”视为完成了评测。

## 14. 当模型/提示词修改后，如何定位退步原因

例如更新 Prompt 后，版本查询能力提升，但某条多规则问题出错。应从同一 `case_id` 的两次执行记录开始：

1. 检查参考答案和 Gold Evidence 是否相同，确认没有暗中改题或换资料。
2. 对比旧新版的 `retrieved_ids`，看证据是否在检索阶段丢失。
3. 对比 `prompt_evidence_ids`，看重排或上下文裁剪是否丢掉关键条件。
4. 对比最终答案与引用，判断是否存在事实错误、归因错误或漏引用。
5. 对比输出状态和错误事件，排除超时、截断、工具失败。
6. 确认修复后不仅当前案例通过，其他既有通过案例也没有回归。

以此前的 C05 为例：检索依然拿到了两条必需规则，候选版回答内容也与结构化参考一致，但最终只引用其中一条。因此在教学评分契约下这是**引用完整性回归**，不应归咎于知识库不存在或检索失败。

## 15. 如何制定上线门槛而不被平均分误导

发布门槛可以同时包含整体质量与关键约束：

| 指标类别 | 可采用的门槛思路 |
|---|---|
| 整体质量 | 重要业务问题的通过率不低于基线 |
| 检索 | 指定证据覆盖率不低于基线 |
| 引用 | 高风险事实不得出现未经证据支持的引用 |
| 权限 | 任何跨用户、跨租户资料泄漏均不接受 |
| 弃答/澄清 | 不可回答问题不能转为编造答案 |
| 稳定性 | 超时、错误率与关键延迟符合业务预算 |
| 成本 | 每次成功解决问题的平均成本不超过可接受范围 |

阈值由业务风险、用户场景和服务水平目标决定，而不是照搬某个通用“准确率 90%”要求。

如果新版本提高了平均成功率，但导致数据权限错误或关键规则引用严重错误，通常应优先修复该回归，再考虑发布。

## 16. 关键统计和质量指标的常见误解

### 16.1 Recall@K 高，不代表答案正确

检索器可以找齐所有证据，但模型仍可能遗漏结算顺序或误写数字。需要独立的回答正确性评价。

### 16.2 Faithfulness 高，不代表真实世界事实正确

如果知识库本身包含旧资料或错误数据，模型严格根据资料作答，可能具备高上下文忠实度，但事实仍然不正确。因此需要独立于模型和当前检索输出的可靠参考事实。

### 16.3 逐条准确率不同于总体用户满意度

某些问题对用户重要性极高。样例分布应与用户场景对应；必要时按业务严重程度分组，报告每组成绩与关键失败数量。

### 16.4 LLM 评分器不是真值生成器

评分器可以帮助自动标注支持关系，但必须验证它与人工独立参考的一致程度。评分器的版本变动也是评测条件变动，应与被测模型版本分开记录。

### 16.5 固定问题不等于“永远不变的唯一测试集”

固定问题用于同一轮公平比较；项目长期维护时，应不断引入独立问题并版本化评测集。新增样例应记录为什么加入，避免在历史报表中把不同题集的分数直接并排比较。

### 16.6 平均延迟改善不代表尾延迟改善

建议同时记录 P50、P95 或 P99，并注明样本量。对用户而言，少量极慢请求往往比平均延迟更显著。

### 16.7 模型正确率和端到端任务完成率不是一回事

系统还需要满足请求状态处理、来源展示、工具执行、权限、前端呈现和用户操作流程。真实服务评测需要覆盖从接口输入到最终用户结果的完整链路。

## 18. 本节与前面 RAG 知识的关系

前四节已经分别解决：RAG 全流程、分块与检索参数、来源引用定位、冲突与合理弃答。这一节则回答：

**如何证明这些机制在修改模型、Prompt 或检索实现之后仍然有效？**

完整的验证逻辑是：

```text
独立真实来源
  → 参考事实与预期行为
  → 固定问题及证据标注
  → 运行旧版与新版 RAG
  → 保存完整检索/生成/引用结果
  → 分层评分
  → 逐题配对比较
  → 定位退步与修复
  → 在同一基准上复测
```

**这套流程的本质不是追求一个好看的总分，而是让模型或提示词的每次修改都留下可核实的改进和回归证据。**

## 20. 文件与测试边界说明

- 本文包括**完整可运行的教学评测代码**和单元测试，但两组 Prediction 为人工构造，不是外部模型的真实输出。
- 代码的确定性部分只检查参考状态、封闭答案键、引用 ID 集合和检索记录；**不包含自动证明自然语言引用语义蕴涵的模型**。
- 真实生产 RAG 评测还必须接入实际检索日志、模型 API、来源版本与人工审查。
- 同题测试的独立性不仅取决于是否用了同一题集，还取决于评分参考是否在模型响应之前独立建立，以及是否使用可比的资料快照和环境。
