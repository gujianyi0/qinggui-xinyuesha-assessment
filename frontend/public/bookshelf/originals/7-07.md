# 从使用者角度验证交互

对应目标：从使用者角度验证等待、失败、重试、引用查看和取消。技术接口能调用之后，还要确认用户能理解结果、知道下一步怎么办。

接口返回200，只能说明一次请求走到了成功分支。对使用者而言，能看懂正在发生什么、能读完答案和依据、失败后知道如何继续，以及操作不会被布局或状态变化打断，才组成完整的使用过程。本章以轻归项目已经发生的反馈和复测为例；不把设计建议写成已执行结果。

## 一、把技术状态翻译成使用者能理解的状态

问答通常会经过提交、等待、检索、生成、完成，也可能失败或取消。页面需要给出与真实运行一致的反馈。

| 技术状态 | 使用者应看见什么 | 必须避免的问题 |
| --- | --- | --- |
| 正在提交 | 已接收操作的提示，避免误认为按钮无效 | 无提示地连续点发送，产生重复请求 |
| 正在检索或生成 | 当前阶段、持续变化的等待信息、可取消入口 | 一直只有静止空白；工具还没完成却声称查到资料 |
| 已完成 | 可阅读的正文、必要前提、来源入口 | 已保存成功但页面仍显示生成中 |
| 请求失败 | 可理解的原因、可否重试、保留的输入 | 原文只显示内部堆栈或静默清空草稿 |
| 已取消 | 取消结果及已发生的副作用说明 | 把断开页面等同于服务端停止，或被迟到结果覆盖 |

这些状态应来自真实请求或任务记录。计时可以在页面独立更新，但不能把等待时间伪装成模型进度百分比。提供“正在检索”有助于解释等待，却不能代替后端超时、并发控制和资源清理。

## 二、等待期间继续编辑，不等于并发发送

使用者读着回答想到补充内容时，应能先写下一条。生成中的输入框可以保持可编辑，发送入口则按当前会话的并发策略处理。两种限制需要分别实现。

轻归曾在回答期间禁用整个输入框，用户明确反馈“无法补充文本”。修正后允许编辑下一条草稿，Enter在生成中作为换行；新问题要等当前请求结束再发送。另一处竞态是在异步创建会话返回时清空输入，可能连新写的草稿一起删掉。修正将原问题的取值与新草稿分开，不用晚到的异步结果覆盖用户新输入。

验证需要覆盖：普通生成、慢建会话、建会话失败、恢复原请求和取消。检查已发送内容正确、新草稿保留、没有额外请求，而不只断言textarea没有disabled属性。

证据：入职考核项目 `docs/2.0.1-裁定话题与输入草稿修复-20261117.md`、对应真实前后运行记录及聊天组件测试。

## 三、区分失败重试与断线恢复

“再试一次”可能有两种含义：

- 原请求确定失败，按业务策略创建新尝试。
- 浏览器没有收到原请求结果，但服务端可能已经执行，需要查询原请求。

第二种情况不能直接生成一个全新的提交编号，否则可能多次调用模型、重复扣费或写入重复记录。轻归在发送前保存请求ID，断线后查询原回执或运行结果；只有确认原请求状态之后才决定下一步。页面提示也应说明是在恢复原请求，而不是暗示用户再次付费发问。

测试可在提交响应丢失、SSE断开、刷新页面和取消先于提交到达等条件下执行。预期是原请求最终记录唯一、异内容不能复用同一ID、会话归属仍受后端检查。若服务端没有持久化幂等机制，只在按钮上防重复点击并不足够。

证据：项目 `tests/test_request_recovery.py`、聊天run-transport服务及1.9断线恢复记录。

## 四、来源要能找到、读完并返回

引用不是一个装饰性链接。读者需要知道引用支持哪句话、适用哪个版本，并能查看完整正文、必要的代码或执行证据。

轻归的两轮实际反馈揭示了接口测试容易遗漏的体验问题：

1. “点击链接按钮，按钮会跑开”：来源详情放在按钮自身的flex项目内，展开后挤动其他按钮。修前实际位移约262.1px，拆分按钮排与详情区后，同一回答的按钮最大位移为0px。
2. “无法往下拉，无法查看”：来源正文存在限高和独立纵向滚动，边界又阻止滚动传递。取消这层纵向滚动后，由聊天区统一滚动；用真实鼠标滚轮检查普通、窄屏和矮窗口，确认可以看到最后一行并返回。

正文排版应保留段落、列表、标题、表格及代码的结构。把所有Markdown符号简单删除，再压成一整段，可能让规则条件和层次一起丢失。表格或代码可以独立横向查看，但不应截断纵向内容。

组件测试可检查结构与内容，按钮坐标和滚轮边界则需要真实浏览器补证。用脚本直接设置scrollTop只能准备起点，不能单独证明实际滚轮操作正常。

证据：项目1.11来源按钮修复、1.12阅读排版、1.13滚动修复报告及各自修前/修后浏览器记录。

## 五、取消必须同时检查界面和后端

点击“停止”后，需要核对四件事：按钮反馈是否及时；后端是否收到取消；最终状态是否保持取消；旧任务迟到时是否会写回成功结果。

问答取消和后台导入取消的生效点可以不同。流式模型请求应关闭拥有的客户端连接；导入任务可以在分块边界检查取消，并在最终发布事务中再次检查。已经产生的模型费用不会因取消自动消失，应按账本事实说明。不能因为页面停止显示token就断言服务端调用和费用也都停止。

轻归用取消终态测试、持久请求回执测试、Worker代次与发布竞争测试核对这些边界；实际完成范围按各轮证据阅读，不把某次测试通过推广为任意多实例部署均安全。

## 六、真人反馈怎样形成可核查的改进记录

一份记录至少包含：参与者、他想完成的事、原始操作或输入、卡住的位置、定位依据、实际修改、修改后的复测和仍未解决的限制。

当前项目中，使用者本人通过本次对话反复提交真实截图和问题，我们据此修改并复测，这属于真人试用与改进。应明确参与者是用户本人，不能因为没有另行招募同事或朋友就写成“没有真人反馈”；也不能将自动化浏览器当成额外一名真人。

反馈说明了症状，不一定直接证明根因。例如用户报告整个浏览器无响应，不能仅凭某次后端请求已结束就断定前端没有问题，也不能未经复现就归因于整机内存。可以先记录已知事实，进一步分别检查请求耗时、事件处理、滚动和布局。

## 七、一份可重复执行的体验验证表

| 场景 | 操作 | 应观察的结果 |
| --- | --- | --- |
| 等待 | 运行一条受控慢请求，并编辑下一条草稿 | 阶段和等待可理解；输入可编辑；没有重复提交 |
| 失败 | 在隔离环境注入超时或工具错误 | 提示原因和下一步，错误状态落库，输入保留 |
| 重试/恢复 | 丢弃响应或断开流后恢复 | 查询原请求，最终记录唯一，账本不重复 |
| 引用 | 展开长资料、切换来源、滚动到底 | 按钮位置稳定、段落清楚、最后一行可见、能返回 |
| 取消 | 运行中停止，再等待迟到结果 | 取消终态不被覆盖，资源与费用按实际结算 |
| 响应式和键盘 | 窄屏/矮窗口、Tab、Enter、Esc | 关键操作可达，焦点合理，不困在嵌套滚动里 |

验证报告要区分组件模拟、真实浏览器、真实模型与真实依赖。记录本次用的版本、输入、环境、预期和实际结果；失败记录保留。下一轮修改后用相同场景复测，才能说明修复有效，而不仅是换了一道更容易的问题。
