# 使用 Pydantic 校验模型结果：格式错误、缺字段、拒答与信息不足的分类处理

> **范围**：本篇讨论模型输出的解析、验证、语义分流、错误传递与对外接口契约；不展开下一条关于数值计算、运行用量或提示词版本收益分析的知识点。

## 01. 为什么模型输出不能直接作为业务结果？

模型返回的内容在传入数据库、工具、前端或其他服务之前，应视为**尚未验证的外部输入**。这与接受第三方 HTTP API 的响应相似：接口调用成功，只能说明拿到了数据，不能说明数据满足业务契约。

典型调用链：

```text
模型服务 / SDK
    ↓
供应商响应检查（状态、拒答、截断、网络错误）
    ↓
提取候选内容（文本或结构化对象）
    ↓
JSON 解析（Syntax）
    ↓
Pydantic 结构与字段校验（Schema）
    ↓
状态一致性和必要的业务校验（Semantics）
    ↓
统一的应用结果 / 错误封装（Result Envelope）
    ↓
调用方（FastAPI、前端、Worker、其他 Agent）
```

必须分清以下问题：

1. **请求是否完成？** 网络请求结束、模型结束、未被截断是三个不同事实。
2. **是否拿到了内容？** `None`、空字符串、空白文本、拒答消息都可能不存在可供解析的业务结果。
3. **内容是不是合法 JSON？** JSON 文本必须符合 JSON 语法。
4. **JSON 是否符合预期 Schema？** 字段必须存在，类型、枚举、嵌套结构满足定义。
5. **字段组合是否有意义？** 例如 `status="answered"` 时必须有有效 `answer`；`insufficient_information` 时应明确缺少哪些信息。
6. **调用方下一步做什么？** 正常展示、请求补充、展示拒答、告警、重试或人工处理，处理路径不同。

这几层不应被一个 `try: json.loads(...) except: return None` 代替。

## 02. 必须区分的四类核心结果

| 状态 | 典型症状 | 所属层级 | 推荐处理 | 是否可重试 |
|---|---|---|---|---|
| 格式错误 | 输出 `{ "a":`、多余 Markdown 包裹、非法转义 | JSON 解析 | 标记 `INVALID_JSON`，保留内部错误定位 | 可能，先检查截断原因 |
| 缺字段 | 缺少 `answer` 或 `citations` | Schema | 标记 `REQUIRED_FIELD_MISSING`，列出字段路径 | 可能，必须有限次 |
| 拒答 | 供应商返回专用 `refusal` 或明确拒绝信号 | 模型/策略 | 标记 `MODEL_REFUSAL`，前端展示可理解说明 | 通常不应自动重复相同请求 |
| 信息不足 | 资料版本未知、缺少用户提供的信息 | 业务/证据 | 标记 `NEEDS_MORE_INFO`，告诉用户缺少什么 | 需要补充信息，而非原样重试 |

另外至少应识别：**输出截断**、**空输出**、**字段类型或范围不符**、**服务超时/限流**、**来源无法验证**。这些都不能混成同一个 `False`。

### 2.1 格式错误与缺字段不是同一错误

```json
{"answer": "角色甲生命值为4"
```

这是格式错误：缺少右括号，JSON 语法不完整。

```json
{"answer": "角色甲生命值为4"}
```

这是合法 JSON，但若业务契约还规定必须返回 `status`、`citations` 和 `missing_information`，就是**缺字段**。

```json
{"status": "answered", "answer": 123, "citations": [], "missing_information": []}
```

JSON 语法合法、字段齐全，却有**字段类型错误**，且不满足 answered 状态必须有证据的规则。

### 2.2 拒答与信息不足不是同一情况

**拒答**：模型或服务决定不执行某项请求，可能与安全、策略或能力范围有关。某些提供商的响应有明确拒答字段；应优先使用该字段，不能靠搜索“抱歉”两个字来判定。

**信息不足**：请求属于可以处理的任务，但现有证据不足。例如用户问“角色甲这个技能在第几版被修改？”，但没有提供版本，资料库也无法唯一定位。正确做法是标记缺少的条件并请求补充。

“不知道”也可能只说明模型不确定，**不意味着**供应商拒答。不能用 `refusal` 一概表示所有不回答的场景。

## 03. Pydantic 在其中承担什么职责？

Pydantic v2 提供：

- `BaseModel`：声明结构化 Python 数据模型。
- `Field(...)`：配置必填、长度、范围等约束。
- `ConfigDict(strict=True, extra="forbid")`：限制隐式类型转换和多余字段。
- `model_validate(...)`：校验 Python 对象、字典等。
- `model_validate_json(...)`：解析并校验 JSON 文本或字节。
- `field_validator`：字段级自定义规则。
- `model_validator`：跨字段一致性规则。
- `ValidationError.errors()`：获取可机器处理的错误类型、路径与说明。
- `model_dump()`：导出经过验证的数据；`model_json_schema()`：生成 JSON Schema。

注意：**Pydantic 校验通过不等于外部事实正确**。在本节，我们把它用于验证输入契约与内部一致性。另一个重要细节是，`strict=True` 不保证所有 Python 模式和 JSON 模式的转换行为完全一致；具体应参考字段类型和 Pydantic 版本文档。

### 3.1 为什么应避免隐式转换

默认配置下某些输入可能被转换：字符串 `"4"` 可能在部分整数字段配置中被接受。这在读用户表单时可能方便，但在严格的模型输出契约里，会掩盖模型没有按规范输出的事实。

```python
from pydantic import BaseModel, ConfigDict, ValidationError

class StrictNumber(BaseModel):
    model_config = ConfigDict(strict=True)
    count: int

try:
    StrictNumber.model_validate({"count": "4"})
except ValidationError as exc:
    print(exc.errors()[0]["type"])  # int_type
```

如果明确允许自动转换，可以在特定字段放宽，而不是不加区分地依赖默认行为。

## 04. Pydantic 中“必填”“可为空”“有默认值”的严格区别

这是模型输出校验特别容易忽略的知识。

```python
class A(BaseModel):
    name: str              # 必须出现，且不能为 None
    note: str | None       # 必须出现，但可为 null
    remark: str | None = None  # 可省略，省略时默认为 None
```

`str | None` **不自动意味着可省略**；是否必填由有无默认值决定。

不同契约应精确选择：

- `answer: str`：必须返回非空字符串类型；但空串仍需额外 `min_length` 或跨字段校验。
- `answer: str | None`：字段必须出现，值可为字符串或 `null`。
- `answer: str | None = None`：允许模型省略这个字段，不一定适合严格的输出契约。
- `citations: list[SourceRef]`：必须出现一个数组；是否允许空数组另行规定。
- `citations: list[SourceRef] = Field(default_factory=list)`：允许省略，省略时创建新列表。

将必须返回的字段设为默认空值，会导致漏字段的模型输出被悄悄“修好”，从而丢失错误证据。

## 05. 建议的模型输出契约：明确结果状态

与其让模型在 `answer` 内自然语言描述“我不知道”，更适合定义可解析的状态字段：

```json
{
  "status": "answered",
  "answer": "角色甲在版本2的基础生命值为4。",
  "citations": [{"source_id": "rule-v2", "version": "2"}],
  "missing_information": []
}
```

信息不足时：

```json
{
  "status": "insufficient_information",
  "answer": null,
  "citations": [],
  "missing_information": ["游戏版本"]
}
```

上面的 `status` 是**业务层结果分类**，不是供应商 HTTP 响应状态。供应商如果明确拒答，应当在调用结果的外层被单独处理，而不是要求所有拒答都按照这份 JSON 结构输出。

### 5.1 跨字段规则

- `answered`：答案非空、至少一个引用、没有缺失信息清单。
- `insufficient_information`：`answer=null` 且必须列出缺失信息。
- 未声明的字段：拒绝，不应默默忽略。
- 引用 ID：必须在当前允许检索的资料集合内；仅存在 ID 不能证明内容本身与答案相符。

这就是“**结构校验 + 状态一致性校验**”的区别。

## 06. 验证错误的机器可读结构

调用 `ValidationError.errors()` 会得到包含字段路径、错误类型、错误描述等信息的列表，例如：

```python
from pydantic import BaseModel, ValidationError

class Person(BaseModel):
    name: str
    age: int

try:
    Person.model_validate({"name": "甲"})
except ValidationError as exc:
    for item in exc.errors():
        print(item["loc"], item["type"], item["msg"])
```

缺少 `age` 时，通常可以观察到：

```text
('age',) missing Field required
```

常见 `type` 包括：

| `errors()[i]["type"]` | 常见含义 |
|---|---|
| `json_invalid` | JSON 文本非法 |
| `missing` | 必填字段缺失 |
| `string_type` | 字符串类型不符合要求 |
| `int_type` | 严格整数字段类型错误 |
| `literal_error` | 不在 `Literal` 所列值中 |
| `extra_forbidden` | 出现契约未允许的字段 |
| `string_too_short` | 字符串小于长度下限 |
| `value_error` | 自定义校验器抛出的值错误 |

不要将 Pydantic 的英文完整报错原样发送给终端用户。错误对象可能含输入值、结构位置等内部细节。应用应该提取**稳定的错误代码和安全的字段路径**，原始响应只允许在适当授权、脱敏后进行排错。

## 07. 先分流供应商状态，再解析 JSON

推荐处理顺序：

1. **网络与供应商层**：认证失败、限流、超时、服务端异常，先按连接/供应商错误处理。
2. **专用拒答信号**：例如响应提供明确 `refusal` 字段，优先识别。
3. **完成状态**：例如 Chat Completions 的 `finish_reason="length"` 表示长度限制，不能把截断 JSON 简单归为生成了错误格式。
4. **空内容**：`content is None`、`""` 或纯空白内容需要独立处理。
5. **结构化解析**：使用 Pydantic 校验 JSON、字段与组合规则。
6. **业务状态**：`answered` 对应正常结果，`insufficient_information` 对应请求补充资料。
7. **引用/业务再验证**：检查数据访问范围、来源标识等应用约束。

这个顺序避免将 `refusal`、截断、工具调用、网络错误全部误判成 `JSONDecodeError`。

> **供应商差异**：OpenAI Chat Completions 的结构化输出拒答可通过专用 `refusal` 字段表达；Responses API 的输出项可以包含 `refusal` 类型。DeepSeek 或其他提供商字段可能不同，必须按 SDK 实际返回结构编写适配器。示例的 `ProviderMessage` 是统一的演示抽象，并非某一供应商 SDK 的真实响应对象。

## 08. 完整 Python 实现：把模型响应转成确定性结果

下面是经离线测试的可运行代码。只依赖 Pydantic v2，未调用付费模型服务。

**安装依赖：**

```bash
python -m pip install 'pydantic>=2,<3' pytest
```

将下述代码保存为 `validation_demo.py`：

```python
"""Provider-neutral structured LLM output inspection demo. Python 3.11+ / Pydantic 2.x."""
from dataclasses import dataclass
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, ValidationError, model_validator


class SourceRef(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    source_id: str = Field(min_length=1)
    version: str = Field(min_length=1)


class ModelAnswer(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    status: Literal["answered", "insufficient_information"]
    answer: str | None
    citations: list[SourceRef]
    missing_information: list[str]

    @model_validator(mode="after")
    def check_consistency(self):
        if self.status == "answered":
            if not self.answer or not self.answer.strip():
                raise ValueError("answered requires a nonempty answer")
            if not self.citations:
                raise ValueError("answered requires citations")
            if self.missing_information:
                raise ValueError("answered cannot claim missing information")
        else:
            if self.answer is not None:
                raise ValueError("insufficient_information requires answer=null")
            if not self.missing_information:
                raise ValueError("missing_information must name missing inputs")
        return self


@dataclass(frozen=True)
class ProviderMessage:
    content: str | None
    finish_reason: str = "stop"
    refusal: str | None = None
    provider_error: str | None = None


OutcomeStatus = Literal[
    "ok", "needs_more_info", "refused", "invalid_json", "missing_field",
    "schema_invalid", "incomplete", "empty", "provider_failure", "unverified_source"
]


class Outcome(BaseModel):
    status: OutcomeStatus
    code: str
    message: str
    retryable: bool = False
    details: list[str] = Field(default_factory=list)
    data: ModelAnswer | None = None


def inspect_response(msg: ProviderMessage, allowed_sources: set[str]) -> Outcome:
    if msg.provider_error:
        return Outcome(status="provider_failure", code="UPSTREAM_ERROR",
                       message="模型服务失败", retryable=True)
    # 供应商的专用拒答字段优先于结构化文本解析。
    if msg.refusal:
        return Outcome(status="refused", code="MODEL_REFUSAL", message="模型拒绝处理该请求")
    # 生成被截断时不能将残缺 JSON 误报为普通格式错误。
    if msg.finish_reason == "length":
        return Outcome(status="incomplete", code="OUTPUT_TRUNCATED",
                       message="模型输出未完成", retryable=True)
    if msg.finish_reason != "stop":
        return Outcome(status="incomplete", code="UNEXPECTED_FINISH",
                       message="模型未正常完成文本输出")
    if not msg.content or not msg.content.strip():
        return Outcome(status="empty", code="EMPTY_OUTPUT", message="模型返回空内容", retryable=True)
    try:
        parsed = ModelAnswer.model_validate_json(msg.content)
    except ValidationError as exc:
        issues = exc.errors(include_input=False, include_url=False)
        kinds = {item["type"] for item in issues}
        details = [f"{'.'.join(map(str, x['loc'])) or 'root'}: {x['type']}" for x in issues]
        if "json_invalid" in kinds:
            return Outcome(status="invalid_json", code="INVALID_JSON",
                           message="模型输出不是合法 JSON", retryable=True, details=details)
        if "missing" in kinds:
            return Outcome(status="missing_field", code="REQUIRED_FIELD_MISSING",
                           message="模型结果缺少必要字段", retryable=True, details=details)
        return Outcome(status="schema_invalid", code="SCHEMA_VALIDATION_FAILED",
                       message="模型输出未通过结构或条件校验", retryable=True, details=details)

    unknown = sorted({r.source_id for r in parsed.citations} - allowed_sources)
    if unknown:
        return Outcome(status="unverified_source", code="UNKNOWN_SOURCE",
                       message="引用未通过来源 ID 校验", details=unknown)

    if parsed.status == "insufficient_information":
        return Outcome(status="needs_more_info", code="NEEDS_MORE_INFO",
                       message="现有资料不足以作答", data=parsed)
    return Outcome(status="ok", code="SUCCESS", message="已获得结构化结果", data=parsed)
```

### 8.1 这份代码的设计特点

- `ProviderMessage` 表示经过供应商适配器提取的状态：文本、拒答、结束原因、供应商错误。
- `ModelAnswer` 是模型应交付的严格结构。
- `@model_validator(mode="after")` 处理 `status` 与其他字段之间的一致性。
- `Outcome` 是应用对调用方暴露的**统一结果封装**，包含 `status/code/message/retryable/details/data`。
- `inspect_response()` 把外部消息转换成稳定的应用状态，而不是返回 `None` 或捕获全部异常。
- `allowed_sources` 体现来源 ID 检查；它只验证 ID 是否在允许集合中，不替代证据内容核对。

### 8.2 推荐的状态码与调用方动作

| `Outcome.status` | `code` | 调用方动作 | 重试策略 |
|---|---|---|---|
| `ok` | `SUCCESS` | 展示答案和引用 | 无需重试 |
| `needs_more_info` | `NEEDS_MORE_INFO` | 提示用户补充字段/版本 | 补充后新请求 |
| `refused` | `MODEL_REFUSAL` | 展示可理解的拒答 | 不应机械重试相同请求 |
| `invalid_json` | `INVALID_JSON` | 内部诊断/有限次修复 | 视情况 |
| `missing_field` | `REQUIRED_FIELD_MISSING` | 记录字段路径/有限次修复 | 视情况 |
| `schema_invalid` | `SCHEMA_VALIDATION_FAILED` | 检查类型、枚举与跨字段规则 | 视情况 |
| `incomplete` | `OUTPUT_TRUNCATED` / `UNEXPECTED_FINISH` | 检查结束原因和预算 | 视情况 |
| `empty` | `EMPTY_OUTPUT` | 提示服务没有生成可用结果 | 视情况 |
| `provider_failure` | `UPSTREAM_ERROR` | 处理网络/供应商异常 | 取决于错误种类 |
| `unverified_source` | `UNKNOWN_SOURCE` | 禁止把未经核对的引用当有效证据 | 不直接放行 |

这里的 `retryable=True` 是**重试策略提示**，不意味着自动重试一定安全。例如供应商调用涉及费用，或者调用中已产生其他副作用时，还需要请求幂等、退避、次数和预算控制。真实系统应进一步区分超时、429、服务端错误与不可恢复的 4xx 错误。

## 09. 如何设计调用方能理解的返回结构

一个通用业务响应可以长成这样：

```json
{
  "status": "missing_field",
  "code": "REQUIRED_FIELD_MISSING",
  "message": "模型结果缺少必要字段",
  "retryable": true,
  "details": ["missing_information: missing"],
  "data": null
}
```

当资料不足时：

```json
{
  "status": "needs_more_info",
  "code": "NEEDS_MORE_INFO",
  "message": "现有资料不足以作答",
  "retryable": false,
  "details": [],
  "data": {
    "status": "insufficient_information",
    "answer": null,
    "citations": [],
    "missing_information": ["游戏版本"]
  }
}
```

这两种场景的 HTTP 请求都可能顺利到达服务端，但业务含义完全不同。调用方不应从 `message` 的中文措辞猜测状态，而应使用稳定 `code` 或 `status` 做分支。

### 9.1 为什么 `message` 和 `code` 要分开？

- `code`：机器判断，尽量稳定，可以适配多语言。
- `message`：面向人类的描述，可以重写或本地化。
- `details`：受控的错误定位信息，不直接泄漏原始 Prompt 或模型输出。
- `retryable`：表示重试建议；具体是否执行由上层策略决定。
- `data`：成功时或“需要补充信息”时的结构化业务数据。

前端可以根据 `code` 显示对应 UI，而不是执行 `if (message.includes("缺少"))` 之类脆弱判断。

## 10. HTTP 状态码与业务状态的分离

不能把 Pydantic 异常、模型拒答和用户提交错误都简单映射为 `HTTP 422`。

| 场景 | 合理的 HTTP 处理思路 | 说明 |
|---|---|---|
| 用户请求本身不符合输入 Schema | `422`（FastAPI 常见默认） | 是客户端输入错误 |
| 模型正常回答 | `200` | 已成功处理业务 |
| 模型合理提出补充信息 | 常见 `200` | 正常业务分支，不是服务故障 |
| 供应商明确拒答 | 常见 `200` + `refused` 业务状态；也可按产品策略定制 | 应与安全策略、产品 UI 协调 |
| 上游返回非法 JSON / 缺字段 | 可用 `502` | 上游结果不符合约定，不能怪罪客户端 |
| 模型/上游服务暂不可用 | 可用 `503` | 暂时性服务故障 |
| 调用上游超时 | 可用 `504` | 如果明确是网关或上游等待超时 |

这些并非唯一规范，关键是**设计一致、符合语义并记录在 API 契约中**。例如业务上的“拒答”并非天然等于 HTTP `403`：后者通常意味着客户端不被允许访问目标资源。不能把“模型选择不回答”与“用户没有权限访问资源”混为一谈。

### 10.1 FastAPI 演示

保存为 `api_demo.py`（需与 `validation_demo.py` 同目录）：

```python
"""Minimal FastAPI boundary example. No real model or network required."""
from fastapi import FastAPI, HTTPException
from fastapi.responses import JSONResponse
from validation_demo import ProviderMessage, inspect_response

app = FastAPI()

EXAMPLES = {
    "ok": ProviderMessage('{"status":"answered","answer":"角色甲的生命值为4","citations":[{"source_id":"rule-v2","version":"2"}],"missing_information":[]}'),
    "missing": ProviderMessage('{"status":"answered","answer":"abc","citations":[]}'),
    "refused": ProviderMessage(None, refusal="拒绝"),
    "needs_more": ProviderMessage('{"status":"insufficient_information","answer":null,"citations":[],"missing_information":["游戏版本"]}'),
    "timeout": ProviderMessage(None, provider_error="timeout"),
}
HTTP_STATUS = {
    "ok": 200, "needs_more_info": 200, "refused": 200,
    "invalid_json": 502, "missing_field": 502, "schema_invalid": 502,
    "incomplete": 502, "empty": 502, "provider_failure": 503,
    "unverified_source": 502,
}

@app.get("/demo/{scenario}")
def demo(scenario: str):
    if scenario not in EXAMPLES:
        raise HTTPException(status_code=404, detail="未知演示场景")
    result = inspect_response(EXAMPLES[scenario], {"rule-v2"})
    return JSONResponse(status_code=HTTP_STATUS[result.status], content=result.model_dump())
```

示例通过固定演示数据展示各种状态对应的 HTTP 响应，**不发起真实模型调用**。生产项目应让供应商适配器调用相应 SDK，将真实响应信息转换为内部统一结构，再执行 `inspect_response()`。

## 11. 使用 Structured Outputs 后，还需不需要 Pydantic？

**需要保留边界校验与业务分流，但可以减少重复解析代码。**

对于支持严格结构化输出的 API，传入 JSON Schema 可以显著提高模型输出符合指定结构的可靠性。但仍然存在以下情况：

1. 供应商返回明确拒答，拒答内容未必匹配业务 JSON Schema。
2. 达到长度限制或请求异常结束。
3. Schema 只约束形状，不能替代事实验证、来源授权和业务一致性。
4. 不同 API 的严格 Schema 支持范围不同，部分校验逻辑只能在应用层执行。
5. 存量数据、缓存数据和数据库记录仍可能绕过当前模型 SDK 的结构约束，需要下游验证。

OpenAI 提供与 Pydantic 集成的解析辅助；但使用 SDK 自动解析时，也应先按其约定处理拒答和未完成状态。**不要把“解析成功”当成无条件成功。**

### 11.1 Pydantic JSON Schema 与供应商 Schema 不是完全同义

```python
print(ModelAnswer.model_json_schema())
```

这会生成包含字段与约束的 JSON Schema，但供应商严格模式支持的 JSON Schema 子集可能不同。例如部分结构化输出 API 对所有属性必填、额外字段限制、对象嵌套、特定校验关键字有约束。**不能假定 `model_json_schema()` 的所有特性都能原样被所有模型服务接受。**

### 11.2 如果模型返回 Markdown 代码块怎么办？

例如：

````text
```json
{"status": "answered", ...}
```
````

在要求严格 JSON 的系统中，这应当被视为格式契约违背。可以针对已知的非严格输出建立明确、可测试的兼容层，但不要在核心处理函数中无条件删除任意字符串、用正则“猜测” JSON 起止位置再直接执行后续业务操作。修复动作必须有限、可观测、不会修改语义，并保留错误路径。

## 12. 模型的“拒答”应该从哪里判断？

推荐区分三个信号来源：

**A. 供应商显式状态**：专用拒答字段或类型化拒答事件。优先级高，最适合程序化分流。

**B. 模型按业务 Schema 返回某种状态**：例如 `insufficient_information`，表示该业务问题现有条件不足。这不是拒答字段。

**C. 普通自由文本**：模型输出“抱歉，我不能回答”。除非供应商或应用明确约定该文本属于拒答，否则字符串匹配只是启发式判断，容易误伤正常内容。

为什么不建议依赖文本关键词？

- 多语言表达不同。
- 模型可能引用“拒绝回答”作为说明文字，并非真正拒答。
- 用户输入中可以主动包含这些词。
- 文本流在中途可能只出现片段，状态尚未确定。

因此应优先使用供应商的结构化信号，必要时另设受控的输出分类器；分类器判断也可能出错。

## 13. “信息不足”应该如何设计？

信息不足不是技术异常，而是**业务无法在当前输入与证据条件下完成**。

常见场景：

- 缺少对象 ID、游戏版本、日期或其他必需参数。
- 有多个同名目标，无法确定哪一个。
- 检索没有找到支持断言的资料。
- 检索到的资料存在版本冲突。
- 用户只提供“这个技能有问题”，缺少复现步骤。

正确表达应告诉调用方**缺少什么**：

```json
{
  "status": "insufficient_information",
  "answer": null,
  "citations": [],
  "missing_information": ["发生问题的游戏版本", "复现步骤"]
}
```

注意两个原则：

1. `missing_information` 是待补充项列表，不应伪造答案填补 `answer`。
2. 一个模型返回“信息不足”也不必然证明资料真的缺失，应用可结合检索结果和业务规则再次判断。

对于 AI Agent，可以把 `needs_more_info` 转换为“向用户提问”的交互动作；对于批处理 Worker，则应进入 `WAITING_FOR_INPUT` 等持久化状态，而不是不断重试同一消息。

## 14. 错误分类的优先级为什么重要？

想象一条响应同时满足：

```text
finish_reason = "length"
content = "{\"status\": \"answered\", \"answer\": "
```

显然 JSON 不完整，但直接报告“模型产生非法 JSON”会掩盖更有价值的根因：**生成被截断**。优先分类为 `OUTPUT_TRUNCATED`，比盲目追加“请输出合法 JSON”更准确。

类似地：

```text
refusal = "I cannot help with that"
content = null
```

如果先检查 `content is None`，就会误报空内容，而非拒答。因此应先检查拒答信号。

又例如：

```text
provider_error = "HTTP 503"
content = null
```

应归类为上游服务不可用，而非模型没有输出。

**推荐的处理顺序是：供应商异常 → 明确拒答 → 未完成状态 → 空内容 → JSON 与 Schema → 业务状态。** 具体供应商响应字段的优先关系还应以其 API 文档为准。

## 15. 生产级边界：不要把校验器变成不可控的重试器

遇到模型结果不符合 Schema，一种常见做法是把原始结果和错误信息再发给模型要求修复。这可以是一种工程策略，但不应没有限制。

- 确定哪些错误可修复：例如固定 Schema 下的缺字段。
- 确定哪些不应该原样重试：拒答、信息不足、账号权限不足、确定性业务错误。
- 限制尝试次数、总耗时和请求预算。
- 避免将完整的敏感输入、内部系统提示和用户隐私数据回传给不必要的服务。
- 对可能产生副作用的操作设置事务/幂等机制，不能因结构修复触发重复执行。
- 记录重试前后是否真正通过验证，不要根据“看起来更通顺”判断。

**特别注意：校验错误不一定能靠重试解决。** 如果 Schema 本身定义错误、供应商不支持指定结构，重复请求只会造成延迟和资源消耗。

## 16. 流式响应中的结构化验证

流式模型返回的是连续增量，不一定构成完整 JSON。假设收到：

```text
chunk1: {"status": "answer
chunk2: ed", "answer": "角色
chunk3: 甲...", "citations": []}
```

在收完所有增量之前，不能把半截字符串送进业务数据库，也不能执行依赖其字段的写入操作。

正确区分：

- **UI 预览层**：可以展示暂时的文字片段，但应明确“生成中”。
- **结构化消费层**：等待结束事件，再对完整结果验证。
- **高风险执行层**：只有验证全部通过且经过必要的授权/确认，才允许落库或调用产生副作用的工具。
- **异常结束**：流断开、总超时、取消或生成截断时，应标记为未完成，不默认当作成功。

如果采用支持增量结构化解析的库，还必须明确处理“当前暂不完整”和“最终不可接受”之间的区别。

## 17. 日志、错误暴露与安全边界

为了排错，需要知道模型失败类型，但不意味着应该将完整外部数据暴露给前端。

建议在内部记录：

- `request_id`、`session_id` 或任务标识（避免不必要的身份数据）。
- 失败阶段：`provider / completion / json / schema / business`。
- 错误代码及字段路径，例如 `citations.0.source_id: missing`。
- 是否进行了重试、最终状态。
- 可选的输入指纹/脱敏摘要，帮助定位重复问题。

不应默认记录：API Key、私人聊天原文、用户密钥、完整未脱敏 Prompt、含个人信息的工具结果。

`ValidationError.errors()` 可能携带原始 `input`；对外构造 `details` 时只应复制经过审查的字段，如 `type` 和 `loc`。要注意 `loc` 中也可能含由外部数据决定的键名，需在严格隐私场景进一步过滤。

## 19. 常见错误设计及对应后果

| 错误做法 | 后果 | 正确思路 |
|---|---|---|
| `json.loads()` 成功就写入数据库 | 格式正确但字段/业务无效 | 再经 Pydantic 与业务验证 |
| 所有异常都 `except Exception: return None` | 调用方无法区分原因 | 对外使用明确状态和代码 |
| 把 `answer: str \| None` 视为可省略 | 漏字段时误判 | 正确认识 required 与 nullable |
| 给所有字段设默认值 | 模型遗漏被掩盖 | 必填字段不提供默认值 |
| 把 `refusal` 当普通文本解析 | 拒答被误判为非法 JSON | 先识别供应商专用拒答 |
| 把信息不足当服务异常 | 无意义重试 | 请求补充条件或新资料 |
| 把截断 JSON 当纯模型格式错误 | 根因被隐藏 | 优先检查完成状态 |
| 自动接受模型编造的来源 ID | 虚假引用获得信任 | 检查可访问来源及其实际内容 |
| 将 Pydantic 错误原文返回前端 | 潜在泄漏内部结构或敏感数据 | 提取安全错误码与字段路径 |
| 在流式中途就执行工具/写入 | 半成品数据、不可逆副作用 | 完成且通过验证再执行 |

## 20. 总结：四类场景的确定性处理模型

将知识归纳为一个可执行的判断树：

```text
拿到一次模型执行结果
   │
   ├── 供应商/网络失败？ ── 是 → UPSTREAM_ERROR / TIMEOUT
   │
   ├── 显式拒答？ ─────── 是 → MODEL_REFUSAL
   │
   ├── 非正常完成/截断？ ─ 是 → OUTPUT_TRUNCATED / INCOMPLETE
   │
   ├── 无内容？ ───────── 是 → EMPTY_OUTPUT
   │
   ├── JSON 不可解析？ ── 是 → INVALID_JSON
   │
   ├── Pydantic 缺字段？ ─ 是 → REQUIRED_FIELD_MISSING
   │
   ├── 类型/跨字段错误？ ── 是 → SCHEMA_VALIDATION_FAILED
   │
   ├── 资料/来源边界无效？ 是 → UNKNOWN_SOURCE / BUSINESS_INVALID
   │
   ├── status=insufficient_information
   │                    └─→ NEEDS_MORE_INFO（告知缺项）
   │
   └── status=answered ─────→ SUCCESS（向调用方提供合法结构）
```

**本节最核心的结论：Pydantic 负责把不可靠的模型文本变成符合程序契约的数据；但模型拒答、上游执行状态和业务信息不足，需要与 Pydantic 协作组成一个更完整的结果处理层。调用方应该读稳定的错误代码和业务状态，而不是猜测自由文本。**
