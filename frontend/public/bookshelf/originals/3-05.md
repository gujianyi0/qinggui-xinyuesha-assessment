# Agent、工具调用与执行边界（五）：会话历史、执行状态、工具记录与多用户数据隔离

> 内容范围：术语定义、数据模型、状态生命周期、查询与写入隔离、权限校验、会话上下文构造、并发、缓存、任务恢复、审计、测试与 Python 实现。  
> 版本说明：以 Python 3.11+、SQLite 教学实现、PostgreSQL/SQLAlchemy/FastAPI/Agno 的工程概念为背景；特定框架 API 请以实际锁定版本为准。

## 1. 核心结论与边界

Agent 应用至少存在三类不能混淆的数据：

1. **会话历史（conversation history）**：曾经发生的用户消息与助手消息，回答“此前说了什么”。
2. **执行状态（execution/run state）**：一次任务现在执行到哪里、能否继续或取消，回答“这次运行进展如何”。
3. **工具记录（tool execution records）**：模型申请调用了什么工具、程序实际做了什么、得到什么结果，回答“外部操作究竟发生了什么”。

还可能存在第四类数据：**长期记忆（long-term memory）**，即从历史中筛选、抽取并独立管理的跨会话信息。它不等于会话历史，也不等于 Agent 工作流状态。

| 维度 | 会话历史 | 执行状态 | 工具记录 | 长期记忆 |
|---|---|---|---|---|
| 主要标识 | `session_id` + 消息序号 | `run_id`、`status` | `run_id` + `call_id` | `user_id`、记忆条目 ID |
| 时间跨度 | 一段对话持续期间 | 某次执行从创建到终止 | 按工具调用逐条留存 | 可以跨对话、跨时间 |
| 典型信息 | 发言者、文本、时间、引用 | 当前步骤、进度、重试、取消 | 工具名、参数、响应、错误 | 偏好、经核准的事实、来源 |
| 用途 | 构造多轮对话上下文 | 恢复任务和判断可否执行 | 审计和排错 | 选择性个性化与知识复用 |
| 能否直接交给模型 | 仅按任务选取相关历史 | 通常仅提供必要摘要 | 通常提供经过过滤的工具结果 | 根据授权和任务选择 |
| 保密风险 | 聊天内容外泄 | 任务标识与状态越权 | 工具结果可能含密钥或 PII | 跨会话、跨目的过度共享 |

**数据已经写入数据库不代表模型已看到它；模型曾经看到某条信息也不代表应用已持久化；工具日志存在不代表操作成功。** 这三种事实分别验证。

## 2. 身份层次：租户、用户、会话、运行、调用

考虑一个多租户系统，其中 A 公司和 B 公司都在使用同一个 AI 助手。

```text
Tenant / 企业租户
  ├─ User / 用户
  │   ├─ Session / 对话线程
  │   │   ├─ Run / 一次模型执行（可能多轮工具调用）
  │   │   │    ├─ Message / 用户、助手消息
  │   │   │    ├─ ToolCall / 某次工具请求
  │   │   │    └─ ToolResult / 实际调用结果
  │   │   └─ Run / 另一轮执行
  │   └─ Session / 另一个聊天窗口
  └─ User / 另一用户
```

字段语义：

- `tenant_id`：组织或空间的边界，用于多租户隔离。不是所有应用都有租户，但有租户时不能遗漏。
- `user_id`：认证系统确认的主体，不应直接信任客户端提交的任意字符串。
- `session_id`：特定对话线程的标识符，可跨多轮消息使用；不等于授权令牌。
- `run_id`：某次 Agent 执行标识；同一会话通常产生多个 Run。
- `call_id`：模型工具调用和工具结果之间的关联标识。
- `trace_id`：分布式追踪关联标识，通常与上面几类业务 ID 不同。
- `task_id`：跨进程或长时间运行的后台任务标识，必要时再与 `run_id` 关联。

一个 `session_id` 通常不应被理解为“当前用户唯一的会话”。同一用户可以打开多个会话，不同用户绝不应靠会话 ID 的偶然不重复来保证安全。可使用全局 UUID，也可使用 `(tenant_id, session_id)` 复合键，关键是查询和权限范围始终一致。

### 2.1 会话与执行：一对多而非一对一

用户在某会话中先问“规则是什么”，第二轮问“那这个角色呢”：

```text
Session S-100
  Run R-101：用户提问 → 工具查询 → 模型回答
  Run R-102：用户追问 → 模型回答
  Run R-103：用户请求反馈草稿 → 写入草稿
```

会话历史是跨这些运行构成的有序消息；而 R-102 失败并不必然使整个 S-100 失效。

### 2.2 Agent 框架概念与应用层所有权

Agno 将 Session 看作多个相关 Run 的组合；其持久化数据库可以记录消息、Run、会话状态等，是否把历史送回模型又由独立的上下文配置决定。Agno 文档明确要求在多用户应用中由应用传入正确的 `user_id`、`session_id`，而不是共享一个默认会话。**应用仍需自行验证当前认证身份是否有权访问该会话。**

## 3. 会话历史：发生过什么

会话历史由一串有序事件构成。最简单的模式为：

```text
message_id
session_id
run_id
seq
role
content
created_at
```

真实系统往往还需要 `content_type`（文本、图片等）、数据版本、引用来源、编辑状态、模型标识、消息可见性以及消息是否被撤回等字段。

### 3.1 存储的全部历史与送给模型的上下文不同

- **完整历史（stored history）**：可审计、可检索、可恢复的原始聊天记录。
- **模型上下文（model context）**：为了当前任务从历史、系统规则、用户输入及外部资料中选出的有限集合。

`存储全部历史 ≠ 将全部历史注入每次 Prompt`。

原因包括上下文窗口限制、费用、无关信息干扰、历史资料已过期，以及跨用户数据泄漏风险。合理的上下文选择可以采用最近 N 条消息、按语义检索、固定摘要、明确的当前任务状态；仍必须保证资料权限和版本过滤。

### 3.2 事件顺序与消息序号

不能依赖数据库的自然返回顺序。使用明确的 `sequence_no`、`created_at` 与必要的唯一约束。单独使用时间戳可能出现同毫秒冲突；分布式写入时应设计单会话顺序生成机制或具备稳定排序键。

建议约束：`UNIQUE (tenant_id, session_id, sequence_no)`。

### 3.3 会话历史不是业务事实权威来源

用户说“我的订单已付款”，属于用户输入事件；不能因为它在会话历史中便认定数据库的订单状态已更改。模型说“工单已创建”，也不能替代真实的数据库写入结果或外部工单 ID。

## 4. 执行状态：现在到哪一步

一个 Run 可以包含多个阶段：任务规划、调用模型、工具等待、数据库写入、输出生成等。执行状态关注的是**控制流程**，而不是用户能看到的所有文本。

典型状态机：

```text
QUEUED ──领取──> RUNNING ──成功──> SUCCEEDED
                    │    │
                    │    ├─致命错误──> FAILED
                    │    └─取消生效──> CANCELLED
                    └─临时失败──> RETRY_WAIT ──重试──> RUNNING
```

上述是应用自定义状态机，而非所有框架都采用的统一状态名称。可以另设 `CANCEL_REQUESTED`、`PAUSED`、`TIMED_OUT` 等状态。

### 4.1 状态不变量（invariants）

1. 每次 Run 有唯一标识；其归属 Session 不可事后无痕更改。
2. 终态 `SUCCEEDED`、`FAILED`、`CANCELLED` 的最终结果不可被迟到的 Worker 覆盖。
3. 状态转换须满足预先定义的有向关系；不能从 `SUCCEEDED` 随意改回 `RUNNING`。
4. 对同一个 Run 的状态写入应具有原子性与竞争控制。
5. “进程存活”不等于“任务有进展”；故障恢复可能依赖 lease、心跳、检查点与重新派发。

### 4.2 原子状态转换

不安全：先 SELECT 状态，再在另一个步骤里无条件 UPDATE；两个 Worker 可能都认为任务仍在运行。

更稳妥的 CAS（比较并交换）式 SQL：

```sql
UPDATE runs
SET status = 'succeeded', updated_at = NOW()
WHERE tenant_id = :tenant_id
  AND session_id = :session_id
  AND run_id = :run_id
  AND status = 'running';
```

若影响行数为 0，应重新判断当前状态：可能是任务不存在、无权访问、已完成或被其他 Worker 抢先更新。并发冲突不能简单视作“成功”。

### 4.3 Run 状态与业务状态不同

Agent Run `SUCCEEDED` 只表示本次执行控制流程正常完成，不代表退款已到账、外部邮件已被收件人接收或业务事实已被审核。应该分别建模 `run_status` 和业务实体自身的状态。

## 5. 工具记录：实际上执行了什么

建议明确区分三个事件：

```text
ToolRequested   模型提出工具调用意图
ToolExecuted    应用实际调用工具，记录结果
ToolReturned    结果经过处理后回传模型
```

它们不保证永远是 1:1:1：参数错误可能导致工具未执行；外部超时可能导致是否成功未知；结果过大可能被过滤、截断或转化为摘要后回传模型。

| 重要字段 | 用途 |
|---|---|
| `call_id`、`run_id` | 将意图、执行和返回值关联 |
| `tool_name`、`tool_version` | 识别接口及契约版本 |
| `requested_arguments` | 模型原始意图 |
| `validated_arguments` | 程序实际认可的参数 |
| `principal` / `permission_decision` | 记录授权检查结果 |
| `execution_status` | 成功、失败、取消、未知 |
| `external_request_id` | 外部系统回执或请求关联 |
| `result_hash` / `result_reference` | 审计完整结果或其安全存储位置 |
| `returned_to_model` | 模型真正收到的经处理结果 |
| `started_at`、`ended_at` | 诊断延迟与超时 |

**工具记录应反映真实执行结果，而不是只保存模型对工具结果的总结。** 例如模型说“数据库查询到 4”，但日志显示工具返回 5，定位问题就应从模型使用证据环节入手。

### 5.1 日志与敏感数据

审计不是无条件记录所有原文。工具参数、检索文档及返回结果可能包含密钥、身份证明、私聊内容、支付信息。应设计字段白名单、脱敏、加密、独立权限、保留期与删除策略。

建议：结构化记录状态、哈希与证据指针；仅在授权和确有必要时保存完整敏感内容；日志系统不可成为绕过业务权限的侧门。

### 5.2 审计记录与消息历史的不同可见性

前端聊天窗口通常只显示用户与助手消息；调试与审计界面可以显示工具使用信息，但需要更严格的权限控制。不能将内部工具错误堆栈、连接串或未经筛选的第三方返回值直接加入用户可见消息。

## 6. 多用户与多会话数据串扰的根因

以下错误在 AI 应用中特别常见。

### 6.1 全局可变会话变量

```python
# 错误示例：所有请求共享同一个列表
history = []

async def handle(message: str):
    history.append(message)
    return await ask_model(history)
```

即使只部署一个服务进程，不同用户也可能在同一列表里混合输入。全局共享资源仅适合无用户特异状态的客户端或连接池，并且仍需线程/协程安全管理。

### 6.2 以客户端传入的 user_id 作为授权依据

```python
# 错误示例：客户端可以随意改 URL 中的 user_id
SELECT * FROM sessions WHERE owner_user_id = :client_supplied_user_id;
```

身份必须由可信认证流程解析（例如经过签名校验、有效期校验的令牌），后端再做对象级授权。客户端传来的 `session_id` 只是待查询资源标识。

### 6.3 只按 session_id 查询而忽略租户或所有者

```sql
-- 危险：未限制租户和所有者
SELECT * FROM messages WHERE session_id = :session_id;
```

改为经过认证主体授权的查询，例如通过已核验用户身份关联 Sessions：

```sql
SELECT m.*
FROM messages AS m
JOIN sessions AS s
  ON s.tenant_id = m.tenant_id
 AND s.session_id = m.session_id
WHERE s.tenant_id = :trusted_tenant_id
  AND s.owner_user_id = :trusted_user_id
  AND s.session_id = :session_id
ORDER BY m.sequence_no;
```

权限并不总是简单的“owner 相等”：共享协作、管理员访问、团队空间需要专门的 ACL/RBAC/ABAC 政策。但任何豁免都必须是明确的业务授权规则，而不是默认放行。

### 6.4 缓存键遗漏主体维度

```text
危险键：history:{session_id}
更严谨的作用域：history:{tenant_id}:{user_id}:{session_id}:{history_version}
```

即使数据库查询正确，若缓存键缺少租户或用户维度，也可能在缓存命中时返回别人的数据。记得同步考虑 CDN、搜索索引、向量检索、日志看板与本地内存缓存。

### 6.5 重用状态化 Agent 实例

框架对象是否安全复用取决于实际版本和内部状态管理。有的实例可以作为共享配置或无状态客户端，有的可能保留默认 `session_id` 或 `session_state`；不能假设全局单例 Agent 对不同用户天然隔离。应显式传入调用身份与会话标识，并用实际并发测试验证。

### 6.6 不安全的上下文继承

用户 B 进入新会话，却意外收到用户 A 的摘要、工具结果、检索内容或长期记忆：其泄漏点可能在**上下文组装层**，不一定在数据库。对每次发送到模型的上下文，应记录作用域与来源，构建前逐条过滤授权。

## 7. 隔离不止一个层次

实际应用需要多重防护：

| 防护层 | 应实施的约束 | 漏洞举例 |
|---|---|---|
| 身份认证 | 由服务端核验主体、租户 | 信任请求 JSON 的 user_id |
| API 授权 | 每次访问目标会话、Run、工具结果都检查对象权限 | 猜到 session_id 就能读取 |
| 数据库 | 查询条件包含作用域；唯一约束、外键、必要时 RLS | 只按 id 查消息 |
| 缓存 | 带主体范围的 Key，权限变动时失效 | 历史缓存跨用户复用 |
| Agent 上下文 | 仅注入当前授权范围内历史、记忆与文档 | 引入其他用户的工具摘要 |
| 后台队列 | 消息包含归属信息，但 Worker 仍须校验授权策略 | 消费消息时丢失租户约束 |
| 观测与日志 | Trace 可关联，但原始数据有访问控制 | 调试面板泄漏敏感内容 |

OWASP 将“对象级授权缺失”列为 API1:2023 Broken Object Level Authorization；这类漏洞既可能使用连续数字 ID，也可能使用 UUID 等不可预测 ID。因此，不可预测 ID 只是辅助措施，不能替代授权。

## 8. PostgreSQL 建模：主键、外键与隔离

下面是简化但具备基本引用完整性的 SQL 结构。实际项目可按业务选用 UUID、BIGINT 或复合键，重要的是逻辑一致性。

```sql
CREATE TABLE agent_sessions (
    tenant_id TEXT NOT NULL,
    session_id UUID NOT NULL,
    owner_user_id TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (tenant_id, session_id)
);

CREATE TABLE agent_runs (
    tenant_id TEXT NOT NULL,
    session_id UUID NOT NULL,
    run_id UUID NOT NULL,
    status TEXT NOT NULL CHECK (
        status IN ('queued','running','retry_wait','succeeded','failed','cancelled')
    ),
    version BIGINT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (tenant_id, session_id, run_id),
    FOREIGN KEY (tenant_id, session_id)
        REFERENCES agent_sessions (tenant_id, session_id)
);

CREATE TABLE agent_messages (
    tenant_id TEXT NOT NULL,
    session_id UUID NOT NULL,
    run_id UUID NOT NULL,
    message_id UUID NOT NULL,
    seq BIGINT NOT NULL,
    role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
    body TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (tenant_id, session_id, message_id),
    UNIQUE (tenant_id, session_id, seq),
    FOREIGN KEY (tenant_id, session_id, run_id)
        REFERENCES agent_runs (tenant_id, session_id, run_id)
);

CREATE TABLE agent_tool_events (
    tenant_id TEXT NOT NULL,
    session_id UUID NOT NULL,
    run_id UUID NOT NULL,
    call_id TEXT NOT NULL,
    tool_name TEXT NOT NULL,
    requested_args JSONB NOT NULL,
    validated_args JSONB,
    status TEXT NOT NULL,
    result_ref TEXT,
    result_sha256 TEXT,
    error_code TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (tenant_id, session_id, run_id, call_id),
    FOREIGN KEY (tenant_id, session_id, run_id)
        REFERENCES agent_runs (tenant_id, session_id, run_id)
);

CREATE INDEX agent_sessions_by_owner
    ON agent_sessions (tenant_id, owner_user_id, created_at DESC);
CREATE INDEX agent_runs_by_session
    ON agent_runs (tenant_id, session_id, created_at DESC);
```

### 8.1 数据库约束与权限约束不是同一回事

外键证明某条消息确实属于某个已有的 Run，并不能证明调用者有权限看到它。权限应在服务端进行，必要时再由 PostgreSQL Row-Level Security（RLS）实施纵深防御。

### 8.2 RLS 的适用条件与陷阱

PostgreSQL 的 RLS 可以根据执行数据库会话的安全上下文过滤行，但需要小心：

- 表的所有者、超级用户、具有 `BYPASSRLS` 权限的角色可能绕过常规策略；必要时使用 `FORCE ROW LEVEL SECURITY` 等机制并评估角色权限。
- 连接池复用时，必须避免上一请求的租户上下文残留；通常将上下文设置限定在事务内，并与事务生命周期绑定。
- RLS 不能替代业务级权限策略、应用认证和审计，也不会自动约束所有表和所有外部系统。
- 使用管理员/迁移账号执行数据维护时，需要独立风险控制。

下面只是策略思路示意，不是可直接部署的完整租户认证配置：

```sql
ALTER TABLE agent_sessions ENABLE ROW LEVEL SECURITY;

CREATE POLICY session_owner_select
ON agent_sessions
FOR SELECT
USING (
    tenant_id = current_setting('app.tenant_id', true)
    AND owner_user_id = current_setting('app.user_id', true)
);
```

以上 `app.tenant_id` 与 `app.user_id` 必须由可信应用在数据库事务内安全设定，不能让最终用户直接控制，也要为所有相关子表设计相应策略。

## 9. FastAPI 身份、会话和数据库操作

一个请求的授权链应当是：

```text
Authorization Header
  ↓ 服务端验签和认证
Principal(tenant_id, user_id, permissions)
  ↓ 对象级授权
Session / Run / ToolEvent
  ↓ 数据库按范围查询或变更
可返回的最小数据
```

示意代码（`get_principal` 与 Repository 为需由项目实现的接口）：

```python
from typing import Annotated
from fastapi import APIRouter, Depends, HTTPException

router = APIRouter()

@router.get('/sessions/{session_id}/history')
async def get_history(
    session_id: str,
    principal: Annotated['Principal', Depends(get_principal)],
    repo: Annotated['HistoryRepository', Depends(get_repository)],
):
    # repo 以可信 principal 过滤租户、所有者与会话，不靠 session_id 授权
    messages = await repo.read_for_principal(principal, session_id)
    if messages is None:
        raise HTTPException(status_code=404, detail='会话不存在或无权访问')
    return {'messages': messages}
```

上述函数中的依赖名称是示意接口，需要实际认证和 Repository 实现才能运行。返回 404 或 403 是产品与安全策略选择；不应通过错误信息泄露未授权资源是否存在。

### 9.1 Session 和 SQLAlchemy AsyncSession 不能混淆

- Agent 的 `session_id`：对话线程标识。
- SQLAlchemy `AsyncSession`：一次数据库工作单元/事务上下文。

两个名称都叫 Session，但含义完全不同。SQLAlchemy 明确警告：一个 `AsyncSession` 不能在多个并发 Task 间随意共享。通常为每个独立数据库工作单元创建单独的 AsyncSession，而连接池/Engine 在应用生命周期内复用。

## 10. 同一会话内的并发：不串用户仍可能乱序

即便用户和会话隔离正确，**同一会话同时发起两轮请求**仍可能导致历史乱序、摘要覆盖或不一致的工具执行状态。

例如：

```text
用户发起 A → 读到历史 H0，调用慢模型
用户发起 B → 也读到历史 H0，快速返回
A 才返回 → 两个回答都基于旧历史
```

可根据业务采用：

1. **单会话串行队列**：同一 `session_id` 一次只允许一个需要顺序的 Agent Run；简单但增加等待。
2. **乐观版本控制**：记录会话 `version`，写入时按旧版本进行 CAS，冲突则重算或拒绝提交。
3. **显式分支**：支持并行分支对话，为每个分支维护不同 Parent Message ID；适合复杂协作系统。
4. **只读并行、写入串行**：对无副作用的检索可并行，对历史追加和业务修改保证有序。

对工具调用也要明确：同一 Run 内并行工具的结果顺序不应依赖“谁先完成”，必须按 `call_id` 或确定性顺序正确关联。

## 11. 数据隔离与记忆系统的边界

如果系统支持跨会话记忆，其授权与检索范围应与会话分离建模：

```text
Session history：某用户某会话的消息
User memory：该用户跨会话可复用的已授权长期信息
Team knowledge：某团队/组织授权范围内的资料
Public knowledge：公开资料
```

四类数据不能默认互通。团队知识也不是团队聊天的全部私人消息；用户记忆更不能误写为跨租户共享资料。

一个安全的上下文构造器应该：

```python
async def build_context(principal, session_id, question):
    history = await load_authorized_history(principal, session_id)
    memory = await load_authorized_memory(principal)
    documents = await search_authorized_documents(principal, question)
    return select_relevant_context(history, memory, documents)
```

函数是架构示例。`authorized` 必须对应真实认证与权限校验，而非仅把 ID 填进数据库过滤条件。

## 12. 后台 Worker 与多进程恢复

HTTP 请求的用户身份可能来自认证令牌；Kafka Worker 没有浏览器请求上下文，因此更容易发生身份范围丢失。

建议消息包含：

```json
{
  "task_id": "task-123",
  "tenant_id": "tenant-a",
  "session_id": "session-456",
  "run_id": "run-789",
  "initiator_user_id": "user-1",
  "operation": "index_documents",
  "requested_resource_id": "doc-8"
}
```

但 Worker **不能因为消息里自称 user-1 就自动相信它**：应确保消息来自可信生产者，消费时查找持久化的任务记录、授权快照或重新验证当前权限策略，并根据业务需求处理“提交后用户被移除权限”的情况。

需要区分：

- **谁发起了任务（initiator）**；
- **谁在执行任务（service identity）**；
- **任务被允许处理哪些资源（scope）**；
- **任务完成后哪些用户可以读取结果（result ACL）**。

跨服务传递 `trace_id` 用于追踪，不应把它当作访问授权凭据。调用失败后的恢复仍需幂等标识与状态机约束。

## 13. 工具执行记录的正确观测链

追溯“为什么模型这样回答”至少要核对：

1. 实际收到的用户请求和上下文版本。
2. 模型本次可见的工具清单、参数 Schema 与权限范围。
3. 模型提出的 `tool_call` 名称与参数。
4. 程序验证后的参数，以及权限判定。
5. 工具实际运行的结果、失败状态与证据版本。
6. 回传给模型的工具结果（可能与原始结果不同）。
7. 模型最终回答及所声称的依据。

例子：

```text
Model asked: get_character("角色甲", version="1.0")
Tool executed: OK; hp=4; source=characters-v1
Returned to model: {"hp":4,"source":"characters-v1"}
Model final answer: "该角色生命值为5。"
```

定位：工具结果是 4，最后回答是 5，问题发生在模型使用工具结果生成回复的阶段，而不是凭空归因于“数据库不准”。

**日志只能还原可观察到的输入、决策请求、执行结果与输出；它无法证明模型内部不可见的推理过程。**

## 14. 隐私、保留期与删除

多用户安全不仅是“防止读错数据”，还包括按目的收集和最小化保存。

- 会话历史可能包含个人信息；为其设计访问控制、保留期、导出和删除策略。
- 工具参数可能携带 API Key、手机号、交易金额；默认不应在日志中明文记录敏感字段。
- 若法律或产品要求删除某个用户数据，应检查会话数据库、记忆库、向量索引、缓存、搜索索引、对象存储和日志副本的处理要求。
- 追踪系统使用的用户标识可考虑 pseudonymous ID；如需关联真实身份，应独立受控。
- 调试用日志权限通常应比普通聊天阅读权限更严格。

不要把“记录更多”误认为“可观测性更好”；关键是记录必要、准确、可授权访问的事件。

## 15. 常见错误及修正方法

| 常见错误 | 可能结果 | 修正思路 |
|---|---|---|
| 把所有聊天写入进程全局列表 | 用户 A 看见 B 消息 | 按用户与会话隔离存储 |
| 使用客户端提供的 `user_id` 作为身份 | 假冒其他用户 | 从认证中间件获取可信主体 |
| 仅按 `session_id` 查询 | 越权读取会话 | 对象级授权 + 租户/用户范围过滤 |
| 只保存模型最终回答 | 无法知道工具是否执行 | 保存调用请求、执行状态与结果引用 |
| 把 Tool Result 全部展示给用户 | 泄漏内部错误或敏感字段 | 区分审计可见、模型可见、用户可见 |
| 运行状态直接覆盖终态 | 已取消任务被标成功 | CAS 更新与明确终态 |
| 并发复用一个 SQLAlchemy AsyncSession | 数据事务混乱或异常 | 每个 Task 独立 AsyncSession |
| 把全部历史重复发给模型 | 成本上升、干扰、溢出 | 上下文筛选与历史压缩 |
| 缓存键不带租户、用户 | 跨用户缓存污染 | 作用域明确的缓存键和失效策略 |
| 用 trace_id 作为权限凭据 | 越权风险 | Trace 只用于观测；权限另行验证 |

## 16. 完整 Python 教学实现与测试

下面附有同目录 `session_demo.py` 的完整实现以及相应测试文件，采用 Python 标准库 `sqlite3`，便于无付费模型、无外部数据库环境独立运行。

### 16.1 教学实现与生产实现的边界

- SQLite `:memory:` 存储只在此 `Store` 对象进程内有效，进程关闭数据消失；不用于真实持久化生产。
- 认证主体 `Principal` 在测试中人工构造，真实服务应由认证中间件产生。
- 该实现演示**单进程、顺序调用**下的隔离和状态转移；它不是处理多进程抢占、跨服务事务的生产方案。
- 工具结果仅以 JSON 演示，实际需要审查脱敏、加密和保存策略。
- SQLite 的权限模型不能替代 PostgreSQL RLS、真正的认证服务或租户隔离策略。

```bash

python -m unittest -v test_session_demo.py
```

### 16.2 `session_demo.py`

```python
"""教学用单进程 SQLite 实现；不代表并发生产服务。Python >= 3.11。"""
from __future__ import annotations

import json
import sqlite3
from dataclasses import dataclass
from uuid import uuid4


@dataclass(frozen=True)
class Principal:
    # 必须来自可信认证中间件，而不是用户提交的 JSON。
    tenant_id: str
    user_id: str


class Forbidden(Exception):
    pass


class InvalidTransition(Exception):
    pass


class Store:
    def __init__(self) -> None:
        self.db = sqlite3.connect(":memory:")
        self.db.execute("PRAGMA foreign_keys=ON")
        self.db.executescript("""
        CREATE TABLE sessions (
            tenant_id TEXT NOT NULL,
            session_id TEXT NOT NULL,
            owner_user_id TEXT NOT NULL,
            PRIMARY KEY (tenant_id, session_id)
        );
        CREATE TABLE runs (
            tenant_id TEXT NOT NULL,
            session_id TEXT NOT NULL,
            run_id TEXT NOT NULL,
            status TEXT NOT NULL CHECK (status IN ('queued','running','succeeded','failed','cancelled')),
            PRIMARY KEY (tenant_id, session_id, run_id),
            FOREIGN KEY (tenant_id, session_id) REFERENCES sessions(tenant_id, session_id)
        );
        CREATE TABLE messages (
            tenant_id TEXT NOT NULL,
            session_id TEXT NOT NULL,
            run_id TEXT NOT NULL,
            position INTEGER NOT NULL,
            role TEXT NOT NULL CHECK (role IN ('user','assistant')),
            body TEXT NOT NULL,
            PRIMARY KEY (tenant_id, session_id, run_id, position),
            FOREIGN KEY (tenant_id, session_id, run_id)
                REFERENCES runs(tenant_id, session_id, run_id)
        );
        CREATE TABLE tool_events (
            tenant_id TEXT NOT NULL,
            session_id TEXT NOT NULL,
            run_id TEXT NOT NULL,
            call_id TEXT NOT NULL,
            tool_name TEXT NOT NULL,
            args_json TEXT NOT NULL,
            status TEXT NOT NULL CHECK (status IN ('ok','error')),
            result_json TEXT NOT NULL,
            PRIMARY KEY (tenant_id, session_id, run_id, call_id),
            FOREIGN KEY (tenant_id, session_id, run_id)
                REFERENCES runs(tenant_id, session_id, run_id)
        );
        """)

    def close(self) -> None:
        self.db.close()

    def create_session(self, principal: Principal, session_id: str | None = None) -> str:
        session_id = session_id or str(uuid4())
        with self.db:
            self.db.execute(
                "INSERT INTO sessions VALUES (?, ?, ?)",
                (principal.tenant_id, session_id, principal.user_id),
            )
        return session_id

    def _check_owner(self, principal: Principal, session_id: str) -> None:
        found = self.db.execute(
            "SELECT 1 FROM sessions WHERE tenant_id=? AND session_id=? AND owner_user_id=?",
            (principal.tenant_id, session_id, principal.user_id),
        ).fetchone()
        if found is None:
            # 对外可以统一用 404，避免泄漏目标是否存在。
            raise Forbidden("会话不存在或无权访问")

    def start_run(self, principal: Principal, session_id: str) -> str:
        with self.db:
            self._check_owner(principal, session_id)
            run_id = str(uuid4())
            self.db.execute(
                "INSERT INTO runs VALUES (?, ?, ?, 'running')",
                (principal.tenant_id, session_id, run_id),
            )
        return run_id

    def _check_run(self, principal: Principal, session_id: str, run_id: str) -> None:
        self._check_owner(principal, session_id)
        found = self.db.execute(
            "SELECT 1 FROM runs WHERE tenant_id=? AND session_id=? AND run_id=?",
            (principal.tenant_id, session_id, run_id),
        ).fetchone()
        if found is None:
            raise Forbidden("执行不存在或无权访问")

    def add_message(
        self, principal: Principal, session_id: str, run_id: str,
        position: int, role: str, body: str,
    ) -> None:
        if role not in ("user", "assistant"):
            raise ValueError("对话历史只记录用户与助手的可见消息")
        with self.db:
            self._check_run(principal, session_id, run_id)
            status = self.db.execute(
                "SELECT status FROM runs WHERE tenant_id=? AND session_id=? AND run_id=?",
                (principal.tenant_id, session_id, run_id),
            ).fetchone()[0]
            if status != "running":
                raise InvalidTransition("不能修改已结束的执行")
            self.db.execute(
                "INSERT INTO messages VALUES (?, ?, ?, ?, ?, ?)",
                (principal.tenant_id, session_id, run_id, position, role, body),
            )

    def record_tool(
        self, principal: Principal, session_id: str, run_id: str,
        call_id: str, tool_name: str, args: dict,
        status: str, result: dict,
    ) -> None:
        if status not in ("ok", "error"):
            raise ValueError("非法工具状态")
        with self.db:
            self._check_run(principal, session_id, run_id)
            current = self.db.execute(
                "SELECT status FROM runs WHERE tenant_id=? AND session_id=? AND run_id=?",
                (principal.tenant_id, session_id, run_id),
            ).fetchone()[0]
            if current != "running":
                raise InvalidTransition("终态执行不可增加工具记录")
            self.db.execute(
                "INSERT INTO tool_events VALUES (?, ?, ?, ?, ?, ?, ?, ?)",
                (principal.tenant_id, session_id, run_id, call_id, tool_name,
                 json.dumps(args, ensure_ascii=False), status,
                 json.dumps(result, ensure_ascii=False)),
            )

    def finish_run(self, principal: Principal, session_id: str, run_id: str, status: str) -> None:
        if status not in ("succeeded", "failed", "cancelled"):
            raise ValueError("只能转换为有效终态")
        with self.db:
            self._check_run(principal, session_id, run_id)
            changed = self.db.execute(
                "UPDATE runs SET status=? WHERE tenant_id=? AND session_id=? AND run_id=? AND status='running'",
                (status, principal.tenant_id, session_id, run_id),
            ).rowcount
            if changed != 1:
                raise InvalidTransition("执行已结束，不允许覆盖终态")

    def get_history(self, principal: Principal, session_id: str) -> list[tuple[str, str]]:
        self._check_owner(principal, session_id)
        return self.db.execute(
            """SELECT m.role, m.body FROM messages AS m
               JOIN runs AS r ON r.tenant_id=m.tenant_id AND r.session_id=m.session_id AND r.run_id=m.run_id
               WHERE m.tenant_id=? AND m.session_id=?
               ORDER BY r.rowid, m.position""",
            (principal.tenant_id, session_id),
        ).fetchall()

    def get_run_status(self, principal: Principal, session_id: str, run_id: str) -> str:
        self._check_run(principal, session_id, run_id)
        return self.db.execute(
            "SELECT status FROM runs WHERE tenant_id=? AND session_id=? AND run_id=?",
            (principal.tenant_id, session_id, run_id),
        ).fetchone()[0]

    def get_tool_events(self, principal: Principal, session_id: str, run_id: str) -> list[dict]:
        self._check_run(principal, session_id, run_id)
        rows = self.db.execute(
            """SELECT call_id, tool_name, args_json, status, result_json
               FROM tool_events WHERE tenant_id=? AND session_id=? AND run_id=? ORDER BY rowid""",
            (principal.tenant_id, session_id, run_id),
        ).fetchall()
        return [
            {"call_id": call_id, "tool_name": name, "args": json.loads(args),
             "status": status, "result": json.loads(result)}
            for call_id, name, args, status, result in rows
        ]


if __name__ == "__main__":
    store = Store()
    try:
        alice = Principal("tenant-a", "alice")
        bob = Principal("tenant-a", "bob")
        sid = store.create_session(alice)
        rid = store.start_run(alice, sid)
        store.add_message(alice, sid, rid, 1, "user", "查询角色技能")
        store.record_tool(alice, sid, rid, "call-1", "lookup_skill", {"name": "甲"}, "ok", {"skill": "闪避"})
        store.add_message(alice, sid, rid, 2, "assistant", "技能为闪避")
        store.finish_run(alice, sid, rid, "succeeded")
        print(store.get_history(alice, sid))
        print(store.get_run_status(alice, sid, rid))
        print(store.get_tool_events(alice, sid, rid))
        try:
            store.get_history(bob, sid)
        except Forbidden:
            print("Bob 无法读取 Alice 的会话：正确")
    finally:
        store.close()

```

```python
import sqlite3
from session_demo import Store, Principal, Forbidden, InvalidTransition

class Tests(unittest.TestCase):
    def setUp(self):

        self.a = Principal('t1','a')
        self.b = Principal('t1','b')
        self.c = Principal('t2','a')

    def test_history_empty(self): self.assertEqual(self.s.get_history(self.a,self.sid), [])

    def test_tool_not_in_history(self):

    def test_owner_unauthorized(self):

    def test_two_sessions_same_owner(self):

        self.s.add_message(self.a,sid2,r2,1,'user','only second')
        self.assertEqual(self.s.get_history(self.a,self.sid), [])
        self.assertEqual(self.s.get_history(self.a,sid2), [('user','only second')])
    def test_two_users_same_tenant(self):
        sidb = self.s.create_session(self.b)
        rb = self.s.start_run(self.b,sidb)
        self.s.add_message(self.b,sidb,rb,1,'user','B-msg')
        self.assertEqual(self.s.get_history(self.b,sidb), [('user','B-msg')])
        with self.assertRaises(Forbidden): self.s.get_history(self.a,sidb)
    def test_same_id_different_tenant(self):
        # tenant_id is part of session identity: same supplied id can exist in separate tenants
        self.s.create_session(self.c, session_id=self.sid)
```

## 17. 测试覆盖应如何理解

**本次本地验证结果：** Python `unittest` 共运行 23 项测试，全部通过（`Ran 23 tests ... OK`）。这些验证使用 SQLite 内存数据库，不能替代真实 PostgreSQL 或多进程生产环境测试。


上面的测试从多种角度验证教学实现：

- 同一会话的消息与工具结果分开保存；
- 同一用户的不同会话内容不会互相出现；
- 同租户不同用户及跨租户相同用户名都不能直接访问彼此会话；
- 非拥有者不能启动 Run、追加消息、记录工具或读取数据；
- 终态不能被后续状态覆盖，已完成运行不能继续写入；
- 相同 `call_id` 在相同 Run 内重复写入触发唯一性约束；
- 不存在的父级 Session 无法建立孤立 Run。

这些测试仅证明教学代码在相应环境和用例下满足预期，不是整个系统“已经安全”的证明。真实产品还要测试：

1. FastAPI 认证与鉴权的集成；
2. PostgreSQL 事务隔离和 RLS 行为；
3. 多并发请求、多个 Uvicorn Worker；
4. Redis 缓存键的租户分离；
5. Kafka Worker 的消息重复、重启及权限变化；
6. Agno 或其他框架在同一实例多会话调用下的状态隔离；
7. 日志、向量索引和长期记忆的权限穿透测试。

## 18. Agno 在会话与状态上的接口认识

Agno 当前官方文档提供 `session_id`、`user_id`、`run_id` 等标识，以及可配置的数据库持久化、历史回灌和会话状态。理解它们时应强调两个独立开关：

- **持久化**：是否将会话、Run 和状态存储到数据库，便于后续恢复和查询。
- **上下文注入**：是否在新的模型运行中加入历史消息，以及加入多少。

例如官方示例通过 `db=...` 保存 Session/Run，再通过 `add_history_to_context=True` 让后续 Run 看见相同会话的历史。没有打开历史回灌时，“历史已保存在数据库”也不表示每次请求都会自动使用全部历史。

Agno v3 的存储层对 Run 采用独立的规范化表结构；因此阅读不同版本的教程时，不能假设底层表结构一成不变。需要固定 Agno 依赖版本并以该版本迁移工具为准。

**框架支持 `user_id` / `session_id` 并不意味着自动满足应用的授权要求。** 应在 FastAPI 等应用边界核验身份，再将可信作用域与 Session 关联；针对直接访问数据表、后台任务和管理端接口的路径也须维护一致权限策略。

## 19. 可直接用于判定设计是否正确的五个问题

这里不是练习计划，而是五个数据架构设计判断标准：

**问题一：能否从最终回答定位工具的实际结果？** 需要通过 `run_id` + `call_id` 还原证据，而不是只阅读助手生成的自然语言说明。

**问题二：某条消息被存储后，下一轮是否一定看到？** 不一定；取决于上下文选择机制、权限和 Token 预算。

**问题三：用户知道另一会话的 UUID 就有权限读取吗？** 没有；UUID 是资源标识，不能代替对象级授权。

**问题四：某个 Run 已被取消，迟到结果还能覆盖吗？** 正常状态机不允许；需要 CAS 和正确的事务边界。

**问题五：后台任务没有请求上下文时如何确定用户与租户？** 从可信持久化任务记录恢复主体与授权范围，必要时重新核验；不能直接相信不受控队列消息中的身份字段。

## 20. 术语总结

- **Chat History**：按顺序保留的对话消息。
- **Session**：一段可延续的对话线程或运行上下文。
- **Run / Execution**：一次 Agent 执行实例。
- **Session State**：与会话关联的业务状态，例如当前表单草稿、已选规则版本。
- **Tool Call**：模型要求调用某工具的请求。
- **Tool Result**：工具实际运行后返回的数据或错误。
- **Long-term Memory**：独立于单次会话的可持久化记忆数据。
- **Tenant**：资源与身份的组织范围。
- **Authentication**：确认请求主体是谁。
- **Authorization**：确认主体对目标对象能做什么。
- **BOLA / IDOR**：对象级授权缺失造成的越权访问问题。
- **RLS**：PostgreSQL 的行级安全策略。
- **CAS**：比较并交换式状态更新，常通过条件 UPDATE 实现。
- **Trace ID**：分布式链路跟踪标识，不是身份认证凭据。
- **Idempotency**：重复操作在业务上产生与一次操作等价的最终效果。

**知识点结论：** 会话历史回答“说过什么”，执行状态回答“运行到哪里”，工具记录回答“系统实际执行过什么”。这三类数据具有不同的唯一标识、写入时机、保留策略与权限范围。避免跨用户或跨会话串数据，需要从身份认证、资源授权、数据库查询、缓存键、Agent 上下文构造、后台 Worker 和日志检索形成一致的隔离边界；不能只依靠一个 `session_id` 或 Agent 框架的默认行为。
