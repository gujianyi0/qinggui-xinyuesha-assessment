# Python 基础与工程知识详解

> **对应学习目标**：Python 的模块、函数、类、类型标注、异常、上下文管理器，以及虚拟环境和依赖管理。结合已有的 C++、JavaScript 经验，重点理解 Python 的差异。
>
> **适用范围**：Python 3.10+；示例以 Python 3.13 兼容写法为主。本篇聚焦语言与工程基础，不展开 `asyncio` 的协程调度与并发机制。

## 1. Python 的运行与对象模型

### 1.1 语言类型与执行方式

Python 通常被称为**动态类型、强类型、支持多范式**的语言：

- **动态类型**：变量名没有不可改变的静态类型；运行时对象有类型。`x = 1` 后可以执行 `x = "hello"`。
- **强类型**：不会在所有场景自动把不兼容的类型转换成另一种类型。例如 `1 + "2"` 会产生 `TypeError`。
- **多范式**：同时支持过程式、面向对象和函数式风格。
- **解释执行与字节码**：以常见的 CPython 为例，源码通常编译为字节码，由 Python 虚拟机执行；因此“解释型语言”不意味着完全没有编译过程。

Python 使用**缩进**表示代码块，而 C++、JavaScript 主要使用花括号。冒号 `:` 引出代码块。

```python
if True:
    print("inside")
print("outside")
```

### 1.2 变量名绑定对象，而不是将类型写死在变量上

```python
x = [1, 2]
y = x
x.append(3)
print(y)  # [1, 2, 3]
```

`x` 和 `y` 指向同一个可变列表对象。这与 JavaScript 的数组对象引用相近；和 C++ 中 `std::vector<int> y = x` 默认复制一个独立容器不同。

```python
x = 10
y = x
x = 20
print(y)  # 10
```

第二个例子中，`x = 20` 是让名称 `x` 重新绑定到整数对象，而不是修改原对象。常用的不可变类型包括 `int`、`str`、`tuple`；常用的可变类型包括 `list`、`dict`、`set`。**元组不可变仅指其元素引用不能被重新赋值，元组内部仍可能包含可变对象。**

Python 函数参数传递的核心也是**对象引用的绑定（共享传参，call by sharing）**：函数可以修改被传入的可变对象，但给形参重新赋值不会改变调用方的变量绑定。

### 1.3 与 C++、JavaScript 的核心差异

| 主题 | C++ | JavaScript | Python |
|---|---|---|---|
| 变量与类型 | 变量通常具有编译期类型 | 动态类型，TypeScript 可静态检查 | 动态类型，Type Hints 可静态检查 |
| 对象内存 | 值、引用、指针及明确的对象生命周期 | 对象通常经引用访问并由 GC 管理 | 名称绑定对象，常见 CPython 使用引用计数和循环 GC |
| 代码块 | `{}` | `{}` | 缩进 |
| 函数 | 函数、重载、模板 | 函数是一等值 | 函数是一等对象，广泛使用装饰器 |
| 模块化 | 头文件、库、C++ Modules | ESM `import` / `export` | `.py` 模块与包、`import` |
| 类型检查 | 主要在编译期 | JS 默认运行时，TS 静态检查 | 标注通常不由解释器强制检查 |
| 异常 | `try` / `catch` | `try` / `catch` | `try` / `except` |
| 资源清理 | RAII、析构函数 | `finally`、资源管理 API | `with` / `async with` |
| 依赖 | vcpkg、Conan、CMake 等 | npm、pnpm、lockfile | venv、pip、uv、pyproject.toml、lockfile |

Python 的 `None` 类似 JavaScript 的 `null`，但 Python 没有 JS `undefined` 的直接等价物；访问不存在的变量名通常会抛出 `NameError`。

## 2. 模块（Module）与包（Package）

### 2.1 模块的概念

在普通工程中，一个 `.py` 文件通常是一个 Python 模块。模块让函数、类、常量组织在独立命名空间内。

文件结构：

```text
project/
├── main.py
└── calculations.py
```

`calculations.py`：

```python
def add(a: int, b: int) -> int:
    return a + b

PI = 3.14159
```

`main.py`：

```python
import calculations
from calculations import add

print(calculations.PI)
print(add(2, 3))
```

`import calculations` 导入模块对象，调用时使用 `calculations.add(...)`；`from calculations import add` 则把 `add` 这个名称绑定到当前模块命名空间。`from module import *` 可能污染命名空间，通常不适合维护性要求较高的业务代码。

### 2.2 包的概念及 `__init__.py`

包是具有层级的模块命名空间。常见工程布局：

```text
project/
├── pyproject.toml
└── app/
    ├── __init__.py
    ├── main.py
    ├── api/
    │   ├── __init__.py
    │   └── chat.py
    └── services/
        ├── __init__.py
        └── llm.py
```

在 `app/api/chat.py` 中：

```python
from app.services.llm import call_model
```

`__init__.py` 可用于表明传统的常规包、执行包初始化代码、定义对外导出接口。**它不是所有包都强制需要的**：Python 还支持没有 `__init__.py` 的命名空间包。不过，项目学习初期采用清晰的普通包结构通常更容易理解。

### 2.3 导入机制与执行边界

导入模块时，Python 会搜索模块、创建并初始化模块对象，并执行模块顶层代码。模块通常缓存于 `sys.modules`，后续导入可能直接复用缓存对象，而不是每次重新执行顶层代码。

```python
# demo.py
print("module initialized")
VALUE = 42
```

在同一解释器进程中重复 `import demo`，通常只打印一次初始化消息。

由此带来三类典型问题：

1. **导入副作用**：模块顶层直接启动网络连接、运行数据库迁移或发送请求，会使任何导入者都触发这些行为。
2. **循环导入**：A 初始化时导入 B，B 又尝试访问尚未初始化完成的 A，可能抛出导入错误。
3. **名称遮蔽**：项目文件命名为 `json.py`、`typing.py` 等，可能意外覆盖标准库同名模块的查找结果。

入口保护：

```python
def main() -> None:
    print("start")

if __name__ == "__main__":
    main()
```

作为脚本直接执行时，`__name__` 为 `"__main__"`；作为模块导入时通常是其模块限定名。对于包内入口，常见运行形式是从项目根目录执行 `python -m app.main`，这有助于维持稳定的包导入语义。

**与 JavaScript 对比**：Python `import` 同样具有模块初始化与缓存行为，但模块解析规则、包布局、相对导入语法与 Node.js/浏览器 ESM 不完全相同。**与 C++ 对比**：Python `import` 不等价于文本包含式 `#include`。

## 3. 函数（Function）与参数语义

### 3.1 函数定义及一等对象

```python
def calculate_total(price: float, quantity: int = 1) -> float:
    return price * quantity

operation = calculate_total
print(operation(12.5, 2))  # 25.0
```

`def` 语句创建函数对象并将其绑定到一个名称。函数可以赋值、传参和作为返回值，与 JavaScript 函数类似。

C++ 对照：

```cpp
double calculate_total(double price, int quantity = 1) {
    return price * quantity;
}
```

JavaScript 对照：

```javascript
function calculateTotal(price, quantity = 1) {
  return price * quantity;
}
```

Python 的参数类型与返回类型标注并不会自动执行运行时校验。

### 3.2 位置参数、关键字参数与默认参数

```python
def connect(host: str, port: int = 5432, *, timeout: float = 5.0) -> str:
    return f"{host}:{port}, timeout={timeout}"

connect("localhost", 5432, timeout=10.0)
```

`*` 后面的 `timeout` 是**仅限关键字参数**。还有 `/` 可以标记仅限位置参数，常用于明确 API 约定。

```python
def example(a, /, b, *, c):
    return a + b + c

example(1, 2, c=3)
```

Python 可通过 `*args` 接收可变数量的位置参数（元组），通过 `**kwargs` 接收额外关键字参数（字典）：

```python
def collect(*args: object, **kwargs: object) -> tuple[tuple, dict]:
    return args, kwargs

print(collect(1, 2, mode="fast"))
```

### 3.3 默认参数在函数定义时求值

错误示例：

```python
def add_message(message: str, history: list[str] = []) -> list[str]:
    history.append(message)
    return history
```

这个默认列表在函数定义时建立，并被后续调用复用，因此可能使互不相关的调用共享同一列表。

正确写法：

```python
def add_message(message: str, history: list[str] | None = None) -> list[str]:
    if history is None:
        history = []
    history.append(message)
    return history
```

这与许多 JavaScript 开发者的直觉不同：JavaScript 的默认参数表达式在每次调用且参数为 `undefined` 时求值，而 Python 默认参数表达式一般在定义函数时求值。C++ 默认参数规则也不同：默认实参通常在调用点使用，不应类比为 Python 中被持久保存的列表对象。

### 3.4 作用域、闭包与装饰器

Python 常见名称解析遵循 **LEGB**：Local（局部）、Enclosing（外围函数）、Global（模块全局）、Built-in（内置）。`global` 与 `nonlocal` 用于显式改变赋值所作用的名称绑定范围。

```python
def make_counter():
    count = 0

    def increment():
        nonlocal count
        count += 1
        return count

    return increment

counter = make_counter()
print(counter())  # 1
print(counter())  # 2
```

函数还可以使用装饰器包装行为：

```python
from functools import wraps

def log_call(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)
    return wrapper

@log_call
def greet(name: str) -> str:
    return f"hello, {name}"
```

`@log_call` 的本质相当于在函数定义后执行 `greet = log_call(greet)`。FastAPI 中的路由装饰器也利用了装饰器语法，但其内部机制是注册路由，不等同于上述包装示例。

## 4. 类（Class）、对象与数据模型

### 4.1 实例、初始化与 `self`

```python
class ModelClient:
    def __init__(self, model_name: str):
        self.model_name = model_name
        self.request_count = 0

    def describe(self) -> str:
        self.request_count += 1
        return f"model={self.model_name}"

client = ModelClient("demo-model")
print(client.describe())
```

- `__init__` 负责初始化实例；它不是直接负责分配对象的 `__new__`。
- `self` 是实例方法中的第一个参数的惯用名称，含义类似 C++ 的 `this`，但在 Python 定义中显式写出。
- `client.describe()` 会在方法绑定后把 `client` 作为 `self` 提供。

### 4.2 类属性与实例属性的共享陷阱

```python
class BadConversation:
    messages = []  # 这是类属性，实例之间默认共享

class Conversation:
    def __init__(self):
        self.messages = []  # 每个实例自己的列表
```

Python 实例查找属性时可回退到类属性。若共享的是可变容器，直接修改该容器可能影响所有实例。与 JavaScript 原型上的共享对象有相似风险。

### 4.3 方法种类与继承

```python
class Service:
    provider = "demo"

    def instance_method(self):
        return self.provider

    @classmethod
    def class_method(cls):
        return cls.provider

    @staticmethod
    def static_method(value: int):
        return value * 2
```

- 实例方法接收 `self`。
- 类方法接收 `cls`，适用于依赖类本身的工厂逻辑等。
- 静态方法不自动接收实例或类。

Python 支持多重继承和 MRO（方法解析顺序），但业务设计中不应滥用复杂继承层次。`super()` 按 MRO 协作调用父级实现，而不是简单固定为“直接父类”的别名。

### 4.4 `dataclass` 与 Pydantic 的区别

```python
from dataclasses import dataclass, field

@dataclass
class Session:
    user_id: int
    messages: list[str] = field(default_factory=list)
```

`@dataclass` 能自动生成 `__init__`、`__repr__`、比较等常用方法；`default_factory=list` 为每个实例创建独立列表。

`dataclass` 不是运行时外部输入校验器。相比之下，Pydantic 的 `BaseModel` 主要适合解析和验证接口、配置、模型输出等外部数据：

```python
from pydantic import BaseModel, Field

class ChatRequest(BaseModel):
    user_id: int
    content: str = Field(min_length=1, max_length=2000)
```

Pydantic 默认可能执行类型转换；严格模式与业务约束需要根据接口需求另行配置。

## 5. 类型标注（Type Hints）与类型检查边界

### 5.1 静态提示，不等于运行时强制校验

```python
def add(a: int, b: int) -> int:
    return a + b

print(add("hello", " world"))  # 运行时可以拼接字符串
```

该调用违反了函数声明的静态类型契约，但 Python 运行时通常不会因标注自动阻止。**Python 类型标注主要服务于人类读者、编辑器、静态检查器（如 mypy、Pyright）及使用标注的框架。**

### 5.2 常见标注表达式

```python
name: str = "Alice"
count: int = 3
scores: list[float] = [95.5, 88.0]
index: dict[str, int] = {"A": 1}
position: tuple[int, int] = (10, 20)
maybe_name: str | None = None
```

- `list[str]` 是元素为字符串的列表的静态表达。
- `str | None` 是联合类型写法，Python 3.10+ 支持。
- `Any` 表示对静态类型检查几乎不设约束，不应滥用。
- `TypedDict` 可描述固定键结构的字典，`Protocol` 可描述结构化接口（类似 TypeScript 的结构类型）。

```python
from typing import TypedDict, Protocol

class UserRecord(TypedDict):
    id: int
    name: str

class Sender(Protocol):
    def send(self, text: str) -> None: ...
```

`TypedDict` 本身不会在运行时把普通字典变成会自动验证的对象。`Protocol` 的主要用途是静态描述“具备哪些方法/属性”即可满足接口，而不必显式继承同一基类。

### 5.3 类型系统、数据校验、业务正确性不是一回事

| 层次 | 处理的问题 | 典型工具 |
|---|---|---|
| 静态类型检查 | 调用签名、类型匹配、潜在误用 | Pyright、mypy |
| 运行时结构校验 | 字段是否存在、字符串长度、数字范围 | Pydantic |
| 业务语义校验 | 角色是否存在、用户是否有权限、版本是否匹配 | 业务服务与数据库约束 |
| 外部事实核验 | 模型生成的事实是否真实 | 数据库、检索资料、实际工具结果 |

即使模型输出符合 JSON Schema，也不能证明其内容为真。对 AI 应用而言，这些层次必须明确分开。

## 6. 异常（Exception）与错误传播

### 6.1 异常的传递机制

当代码执行 `raise` 时，当前正常控制流被中断；运行时沿调用栈寻找可处理该异常的 `except`。如果没有合适的处理器，异常继续向上传播。

```python
class ModelServiceError(Exception):
    pass

def parse_prompt(prompt: str) -> str:
    if not prompt.strip():
        raise ValueError("prompt must not be empty")
    return prompt.strip()

def service_call(prompt: str) -> str:
    try:
        return parse_prompt(prompt)
    except ValueError as exc:
        raise ModelServiceError("invalid model request") from exc
```

`raise ... from exc` 建立异常链，保留原始原因，有利于定位问题。与 JavaScript 的 `throw`、C++ 的 `throw` 概念相近，但 Python 用 `except` 而非 `catch`。

### 6.2 `try`、`except`、`else`、`finally`

```python
try:
    result = int("42")
except ValueError as exc:
    print(f"parse failed: {exc}")
else:
    print(f"parsed: {result}")  # try 块没有抛异常时执行
finally:
    print("cleanup")        # 无论正常还是异常，通常都会执行
```

`finally` 适用于清理操作；不要在 `finally` 中随意 `return`，否则可能覆盖原本的返回值或异常。

### 6.3 错误分类与处理边界

| 错误类别 | 示例 | 常见处理思路 |
|---|---|---|
| 输入错误 | 空参数、非法日期 | 返回可理解的输入错误，不盲目重试 |
| 外部暂时错误 | 网络断开、服务暂不可用 | 超时、有限重试、退避 |
| 权限错误 | 访问不属于自己的会话 | 明确拒绝，不通过重试解决 |
| 程序逻辑错误 | `TypeError`、不合理状态 | 记录上下文，修复代码 |
| 资源错误 | 文件句柄、连接耗尽 | 清理资源并限制并发 |

**应避免**：

```python
try:
    perform_operation()
except Exception:
    pass  # 吞掉错误，调用方可能误以为成功
```

更合理的是只捕获预期的异常，在合适边界转换为业务可理解的错误；不确定如何恢复时，让异常保留原因继续传播。日志中避免记录 API 密钥、令牌、私人消息等敏感内容。

**与异步的联系**：后续学习 `asyncio` 时，任务取消具有特殊语义。`asyncio.CancelledError` 在现代 Python 中继承 `BaseException`，不能简单当作普通业务失败来处理或悄悄吞掉。

## 7. 上下文管理器（Context Manager）

### 7.1 为什么需要 `with`

上下文管理器的核心是把**获取资源、使用资源、退出与释放资源**组成结构化生命周期。

```python
with open("example.txt", "w", encoding="utf-8") as file:
    file.write("hello")
```

不论代码块是正常结束还是由于异常退出，文件对象的退出方法都会得到调用，从而关闭文件。它比仅依赖对象销毁时机可靠得多。

与 C++ RAII 的目的相近，但实现方式不同：C++ 常依赖作用域结束触发析构；Python `with` 显式依赖 `__enter__` / `__exit__` 协议，不能假定 Python 对象离开局部作用域后立即销毁。

### 7.2 底层协议与异常抑制

```python
class ManagedResource:
    def __enter__(self):
        print("acquire")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        print("release")
        return False  # 不抑制 with 代码块中发生的异常

with ManagedResource() as resource:
    print("use")
```

`__exit__` 在异常情况下接收到异常的类型、实例和 traceback。若它返回真值，可能抑制该异常；因此不能为“让代码继续执行”随意返回 `True`。

### 7.3 `contextlib.contextmanager`

不一定需要自己实现整个类；可用生成器构建上下文管理器：

```python
from contextlib import contextmanager
from pathlib import Path

@contextmanager
def text_writer(path: Path):
    f = path.open("w", encoding="utf-8")
    try:
        yield f
    finally:
        f.close()

with text_writer(Path("output.txt")) as f:
    f.write("saved")
```

`yield` 之前是进入阶段，`yield` 之后的 `finally` 是退出清理阶段。

### 7.4 `async with` 的知识边界

`async with` 使用 `__aenter__` / `__aexit__` 异步上下文协议，进入与退出资源时允许等待异步操作。

```python
import httpx

async def fetch_example() -> str:
    async with httpx.AsyncClient() as client:
        response = await client.get("https://example.com")
        response.raise_for_status()
        return response.text
```

这是演示异步生命周期的代码，并非建议高并发接口在每次请求中创建 HTTP 客户端。实际服务通常复用客户端和连接池，并在应用停机阶段关闭。

数据库事务、数据库会话、文件句柄、网络连接、锁等都可能通过上下文管理器管理。**连接、会话与事务不是同一个概念**：它们的生命周期和提交/回滚边界需要分别理解。

## 8. 虚拟环境（venv）与依赖管理

### 8.1 为什么要隔离环境

假设两个工程依赖不同版本的同一库。若都安装到同一个全局 Python 环境，升级其中一个工程的依赖可能破坏另一个工程。

**虚拟环境**是在基础 Python 解释器之上创建的隔离环境，具有自己的包安装位置及相关脚本。它通常不是一份完全独立的操作系统或 Python 运行时拷贝，也不等于 Docker 容器。

常见目录：

```text
project/
├── .venv/              # 本地虚拟环境，不提交到 Git
├── src/
├── pyproject.toml      # 项目元数据与依赖声明
└── uv.lock             # 锁定后的具体依赖解析结果（使用 uv 时）
```

### 8.2 Windows 上使用标准库 `venv` 与 pip

在 PowerShell、项目根目录执行：

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install fastapi uvicorn
python -m pip list
```

如果激活受到 PowerShell 策略限制，可以**不激活虚拟环境**，直接使用其解释器：

```powershell
.\.venv\Scripts\python.exe -m pip install fastapi uvicorn
.\.venv\Scripts\python.exe -m pip list
```

`python -m pip` 的优势是明确使用当前 Python 解释器对应的 pip，降低多版本 Python 环境下“装到另一个解释器”的概率。查看实际解释器位置：

```powershell
python -c "import sys; print(sys.executable)"
```

`deactivate` 用于退出已激活的虚拟环境。`.venv` 不宜提交版本库，也不宜直接复制到其他路径作为可移植交付物；应根据依赖说明在目标环境重新创建。

### 8.3 依赖声明、解析与锁定

这里有三个不同概念：

1. **声明直接依赖**：本项目明确依赖哪些包，以及允许的版本范围。
2. **解析传递依赖**：这些包又依赖哪些子包，选取哪些兼容版本。
3. **锁定依赖结果**：记录具体解析版本，以减少不同机器或不同时点安装结果的差异。

`requirements.txt` 可以列出安装需求；若需要更严格的可复现性，应明确版本，并考虑平台差异、哈希校验或采用合适锁文件机制。`pip freeze` 能记录当前环境中的已安装包，但**不是对“哪些是项目直接依赖”的准确描述**。

现代 Python 项目常使用 `pyproject.toml`：

```toml
[project]
name = "game-ai-service"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = [
    "fastapi>=0.100",
    "uvicorn>=0.20",
]
```

这只是演示版本约束写法，并不是对当前最新版本的推荐；实际项目应根据已有代码和兼容性测试确定依赖范围。

### 8.4 `uv` 与 `pip`、`venv` 的关系

`uv` 是覆盖 Python 解释器管理、项目初始化、依赖解析、虚拟环境与运行命令等功能的工具。常见流程：

```powershell
uv init demo-project
cd demo-project
uv add fastapi uvicorn
uv lock
uv sync
uv run python main.py
```

- `uv init`：创建项目。
- `uv add`：添加并记录依赖。
- `uv lock`：解析并更新锁文件。
- `uv sync`：使环境与锁文件及项目依赖一致。
- `uv run`：在项目环境中执行命令，通常会自动检查并同步环境。

使用 uv 时，`uv.lock` 通常应提交到仓库，以便团队共享依赖解析结果。可以在 CI 中使用 `uv sync --locked`，要求锁文件与项目元数据一致而不自动更新；`--frozen` 则偏向直接遵循现有锁文件、不检查其是否与元数据保持最新，两者语义不完全相同。

### 8.5 依赖环境与机密信息

环境变量常用于配置部署差异，如 `DATABASE_URL`、`MODEL_API_KEY`。不要把真实密钥写在源码、公开 `.env`、测试日志或 Git 历史中。可提交只包含占位符的 `.env.example`。

还应区分：

- **开发依赖**：测试、格式化、静态类型检查工具。
- **运行依赖**：应用启动和提供服务所需的库。
- **系统依赖**：数据库客户端库、操作系统共享库等，不一定由 pip 完整解决。
- **锁文件**：主要锁定解析的 Python 包依赖，不保证不同操作系统、CPU 架构、Python 版本和外部系统库的行为完全一致。

## 9. 综合代码：把模块、类、类型、异常和资源管理连起来

以下例子不依赖 FastAPI，演示一个最小的“消息保存”服务：

```text
sample_project/
├── app/
│   ├── __init__.py
│   ├── domain.py
│   ├── repository.py
│   └── service.py
└── main.py
```

`app/domain.py`：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Message:
    user_id: int
    text: str

class InvalidMessageError(ValueError):
    pass
```

`app/repository.py`：

```python
import json
from pathlib import Path
from .domain import Message

class MessageRepository:
    def __init__(self, path: Path) -> None:
        self.path = path

    def save(self, message: Message) -> None:
        record = {"user_id": message.user_id, "text": message.text}
        # 追加写入的教学示例，不提供数据库事务或多进程并发保证。
        with self.path.open("a", encoding="utf-8") as file:
            file.write(json.dumps(record, ensure_ascii=False) + "\n")
```

`app/service.py`：

```python
from .domain import InvalidMessageError, Message
from .repository import MessageRepository

class MessageService:
    def __init__(self, repository: MessageRepository) -> None:
        self.repository = repository

    def submit(self, user_id: int, text: str) -> None:
        if user_id <= 0:
            raise InvalidMessageError("user_id must be positive")
        if not text.strip():
            raise InvalidMessageError("text must not be empty")
        self.repository.save(Message(user_id=user_id, text=text.strip()))
```

`main.py`：

```python
from pathlib import Path
from app.domain import InvalidMessageError
from app.repository import MessageRepository
from app.service import MessageService

def main() -> None:
    repo = MessageRepository(Path("messages.jsonl"))
    service = MessageService(repo)

    try:
        service.submit(1, "你好，Python")
    except InvalidMessageError as exc:
        print(f"input error: {exc}")
    except OSError as exc:
        print(f"storage error: {exc}")

if __name__ == "__main__":
    main()
```

此示例的主要知识关系：

- **模块/包**：代码依职责分散到 `domain`、`repository`、`service`。
- **函数/类**：`main()` 是入口；Service/Repository 通过类封装行为。
- **类型标注**：约束 API 的预期使用方式，辅助 IDE 和静态检查。
- **异常**：输入错误和存储错误向调用方传播并分类处理。
- **上下文管理器**：使用 `with` 保证文件句柄关闭。
- **依赖关系**：Service 依赖 Repository 的实例，通过构造函数传入。

此实现有意保持简单：文件写入**没有**数据库事务、用户授权、多进程安全、幂等机制，也不是稳定的生产级消息存储。这些能力属于后续 HTTP、数据库与后台任务章节。

## 10. 易混淆概念的准确区分

| 容易混淆的说法 | 正确理解 |
|---|---|
| Python 是解释型语言，所以没有编译过程 | CPython 通常会先编译源码为字节码，再解释执行 |
| 变量的类型就是声明时的类型 | Python 名称可以重新绑定到不同类型的对象 |
| 函数参数都是传值或都是传引用 | 更准确说法是共享传参：形参与实参绑定到同一对象 |
| `list[str]` 能阻止运行时插入整数 | 类型标注本身通常不强制运行时校验 |
| `dataclass` 与 Pydantic 完全等价 | 一个主要简化数据类，另一个主要解析和校验外部数据 |
| `__init__.py` 是包唯一合法的必要条件 | Python 也支持命名空间包 |
| 类属性和实例属性没有区别 | 类属性可被多个实例共享，尤其需要防范可变类属性 |
| 每次调用函数都会创建默认列表 | Python 可变默认参数对象通常在定义时创建并复用 |
| `except Exception: pass` 能提高可靠性 | 它可能掩盖错误并制造虚假的成功状态 |
| `with` 与 `try/finally` 毫无关系 | 上下文管理协议封装资源退出逻辑，与 `finally` 有相近目的 |
| 虚拟环境就是 Docker | venv 主要隔离 Python 解释器上下文与包，不隔离整个 OS |
| `pip freeze` 就是完整可复现部署方案 | 它只记录当前包列表，不涵盖所有平台、系统依赖和构建差异 |
| `uv sync --locked` 与 `--frozen` 完全相同 | 前者检查锁文件是否最新，后者跳过该检查 |
