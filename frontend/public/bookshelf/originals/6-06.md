# 消息队列与后台任务可靠性（六）：重试次数、退避、最终失败与失败消息留存

> 对应学习目标：**重试次数、退避、最终失败与失败消息留存，避免一条坏消息永远堵住正常任务。**
>
> 文档类型：独立技术知识手册。适用场景：Kafka + Python/aiokafka + PostgreSQL + 独立 Worker，尤其是文档导入、Embedding、批量模型调用和其他耗时后台任务。
>
> 修订日期：2026-11-12。文中演示参数均为教学示例，不是通用生产默认值。

## 1. 本节需要回答的根本问题

Kafka 把消息交给 Consumer，并不会保证业务处理必然成功。常见故障包括模型提供商暂时限流、数据库连接短时断开、文档格式永久错误、业务规则冲突、Worker 崩溃，以及依赖方已经执行但调用方只收到超时。

一个可靠系统需要同时满足六个条件：

1. **可判断**：区分暂时故障与永久故障，不能把所有异常都无限重试。
2. **有上限**：尝试次数、总耗时、并发数、成本都存在明确边界。
3. **能恢复**：需要重试的任务及下次可执行时间持久保存，进程重启仍能继续。
4. **不重复业务结果**：依靠幂等键、唯一约束与事务，而不是期望 Kafka 只投递一次。
5. **最终可追查**：耗尽重试后将失败原因、原始消息定位信息和必要的原文保存，支持检查和受控重新处理。
6. **不堵塞无关任务**：对可以独立处理的消息，坏消息不应无限占用同一条消费路径；若业务要求严格顺序，则必须明确顺序与吞吐量的权衡。

可概括为：

```text
                 Kafka Topic
                      │
               持久化接收 / Inbox
                      │
                 ┌────┴────┐
                 │任务 Worker│
                 └────┬────┘
                      │
              执行与错误分类
             ┌────────┼──────────┐
          成功       暂时失败      永久失败
           │           │             │
        SUCCEEDED   有界退避       FAILED
                       │             │
                   RETRY_WAIT    失败档案 / DLQ
                       │             │
                   到期再试     人工检查/修复/重放
```

此图刻意分开 **Kafka 消费** 与 **业务任务执行**。这是解决长时重试阻塞的一种设计，而非 Kafka 所有系统的唯一实现。

## 2. Kafka 的失败与重试不自动等价

需要区分三个层次：

| 层次 | 示例 | 谁负责 |
|---|---|---|
| Kafka 客户端网络重试 | Producer 向 Broker 发送请求暂时失败 | Kafka 客户端 SDK 的内置机制 |
| Consumer 业务重试 | Worker 调用模型失败，决定稍后再次处理 | 应用程序、框架或任务调度器 |
| 故障恢复重投 | 业务成功但 Offset 未提交，重启后再次读取 | Kafka 交付机制 + 应用业务幂等 |

`aiokafka` 的 `retry_backoff_ms` 是客户端重试相关配置，**不等于**给你的“模型失败任务”自动创建业务重试队列。普通 `AIOKafkaConsumer` 不会凭空给每条业务消息建立 DLQ、最大尝试次数或最终失败档案。

Kafka Connect 某些连接器内置错误容忍和 DLQ 选项，但这是 **Kafka Connect** 的能力，不能直接当作所有自写 Python Consumer 自动拥有的能力。

### 2.1 什么是 Poison Pill（毒丸消息）

指在当前处理逻辑下持续失败、可能让同一消费位置无法推进的消息。常见情况：

- JSON 无法解析，结构不符合约定。
- 当前版本不支持对应文档类型。
- 外键指向不存在且不会创建的资源。
- 必填字段永久缺失。
- 某条消息触发确定性代码缺陷。

并非所有失败消息都是毒丸。比如模型服务返回临时 `503`，一般应视为暂时性故障，而非立刻永久失败。

**解析器异常可能发生在业务函数调用之前。** 因此对原始 Kafka `value: bytes` 的留存很重要，不能先强制 JSON 解码，解码失败就使消费者永远无法获得可归档的原始数据。

## 3. 首先分类错误，才能制定重试策略

重试的依据是“再次执行是否可能成功”，不是仅凭是否抛出了 Python 异常。

| 错误示例 | 初步分类 | 推荐处理 | 备注 |
|---|---|---|---|
| 上游 HTTP 503、临时连接中断 | 短暂错误 | 有界重试 + 退避 | 检查接口幂等语义 |
| HTTP 429 / 提供商限流 | 暂时限流 | 尊重 `Retry-After`，限速/退避 | 必须同时控制全局并发 |
| 数据库短暂连接失败 | 短暂错误 | 关闭失效连接并有限重试事务 | 需判断提交是否实际成功 |
| 输入缺少必需字段 | 永久输入错误 | 直接 FAILED / 归档 | 不宜无限重试 |
| 无权读取某资源（403） | 永久授权错误 | 拒绝/归档/告警 | 不能通过重试绕过授权 |
| 文档格式不支持 | 永久或需人工修复 | FAILED，留下原文与原因 | 升级解析器后可人工重放 |
| 模型生成非法 JSON | 视策略而定 | 有界修复重试或返回结构错误 | 重试不保证有用 |
| 调用超时但远程可能已成功 | **结果未知** | 先查询结果或使用幂等键核对 | 绝不能直接视为未发生 |
| 数据库出现唯一约束冲突 | 需业务判定 | 查询现有记录、复用或拒绝 | 不是普遍意义的暂时错误 |

错误分类应由确定性业务代码完成：将 HTTP 状态码、SDK 异常、SQLSTATE、业务错误码和幂等查询结果映射到统一分类。

```python
from enum import Enum

class ErrorKind(str, Enum):
    TRANSIENT = "TRANSIENT"
    PERMANENT = "PERMANENT"
    UNKNOWN_OUTCOME = "UNKNOWN_OUTCOME"


def classify_http_status(status: int) -> ErrorKind:
    if status in {408, 425, 429, 500, 502, 503, 504}:
        return ErrorKind.TRANSIENT
    if status in {400, 401, 403, 404, 422}:
        return ErrorKind.PERMANENT
    return ErrorKind.UNKNOWN_OUTCOME
```

以上分类仅是**业务初始策略的示例**：同一状态码在不同 API 中的语义可能不同。例如部分 `404` 可能表示依赖资源尚未创建；`500` 也不保证操作尚未完成。需要结合接口契约与执行副作用进行最终判断。

## 4. Retry Count 与 Attempt Count：次数口径必须统一

“最多重试 3 次”和“最多尝试 3 次”不是一回事。

- **Attempt（尝试）**：包括首次执行在内的一次业务执行机会。
- **Retry（重试）**：首次失败之后的再次尝试。
- `max_attempts = 3`：最多执行 3 次，首次 1 次 + 最多重试 2 次。
- `max_retries = 3`：首次 1 次 + 最多重试 3 次，共最多 4 次。

不同 SDK 的命名有差异，不能凭变量名推断口径。建议在自己的业务数据库与日志中统一记录 `attempt_count` 和 `max_attempts`，在文档中写明“包含首次执行”。

| 尝试序号 | 调用情况 | 失败后的状态 |
|---|---|---|
| 第 1 次 | 首次执行 | 可重试则进入 RETRY_WAIT |
| 第 2 次 | 第 1 次重试 | 可重试则继续等待 |
| 第 3 次 | 第 2 次重试 | 若仍失败，进入 FAILED |

还应建立**总预算**：例如最长允许等待 15 分钟、消耗最多 N 个 Token 或支付费用不超过某个业务阈值。次数上限是必要条件，但不能单独限制总资源消耗。

## 5. 退避 Backoff 与随机抖动 Jitter

如果上游依赖刚发生故障，所有 Worker 立即重试，会在故障时刻进一步放大流量，形成 **Retry Storm（重试风暴）**。

### 5.1 常见退避算法

设基础等待时间为 `base`，第 `n` 次失败后（`n` 从 1 开始）可计算：

**固定退避：**

\[
D_n = base
\]

**指数退避：**

\[
D_n = \min(cap, base \times 2^{n-1})
\]

**Full Jitter：**

\[
D_n \sim U\left(0,\;\min(cap, base \times 2^{n-1})\right)
\]

其中 `cap` 是单次退避的最大值，`U` 表示均匀分布。Full Jitter 允许短间隔，并不是保证最少等待多久；如需最短等待或遵守服务端 `Retry-After`，应明确加入下界。

以 `base=2s`、`cap=30s` 为例（不加抖动）：

| 第几次失败 | 下次重试前的理论退避 |
|---|---:|
| 1 | 2 秒 |
| 2 | 4 秒 |
| 3 | 8 秒 |
| 4 | 16 秒 |
| 5 | 30 秒（封顶） |

以下 Python 使用注入随机数生成器，使测试可复现：

```python
import random

def next_delay(failed_attempt: int, base=2.0, cap=30.0, rng=None) -> float:
    if failed_attempt < 1:
        raise ValueError("failed_attempt must be >= 1")
    rng = rng or random.Random()
    return rng.uniform(0.0, min(cap, base * 2 ** (failed_attempt - 1)))

print(next_delay(3, rng=random.Random(42)))
```

### 5.2 为什么不建议 `await asyncio.sleep(600)` 占住 Worker

`asyncio.sleep` 不会阻塞事件循环，但它可能继续占用业务任务槽位、内存对象、执行租约与消费者的处理资源。更稳健的做法是把 `next_attempt_at` 持久写入数据库，然后释放 Worker 容量，由调度器在到期后重新领取任务。

对于短暂的毫秒级网络重试，可在客户端内部使用有界等待；对于数分钟甚至数小时的业务重试，通常应使用**持久化延迟队列或可恢复任务调度**。

### 5.3 Retry-After、重试预算与熔断

收到明确的 `Retry-After` 时应结合服务端语义使用，不要让随机退避导致违反明确要求的等待期限。对于持续故障，还应考虑：

- **Rate Limit**：每秒允许多少请求。
- **Concurrency Limit**：同时允许多少次模型调用。
- **Retry Budget**：重试请求占总请求的比例或次数上限。
- **Circuit Breaker**：依赖明显不可用时暂停新调用，避免不断失败。
- **Backpressure**：队列持续堆积时降低接单速率，防止内存和数据库耗尽。

更复杂并不一定更好，但每一种机制解决的是不同问题。

## 6. 最终失败：什么时候停止重试

任务最终失败通常来自两类条件：

1. **不可重试错误**：输入、权限、业务约束等不因再次执行而改变的错误。
2. **重试上限达到**：暂时错误虽然理论上可恢复，但尝试次数、总耗时或成本预算已经耗尽。

推荐使用明确的状态机：

```text
PENDING ──领取──> RUNNING ──成功──> SUCCEEDED
                      │
                 暂时失败且未耗尽
                      ▼
                  RETRY_WAIT ──到期领取──> RUNNING
                      │
                      └─耗尽或永久失败──> FAILED

FAILED / SUCCEEDED 为终态（人工重试应创建新 attempt/run 或受控重放记录）
```

`FAILED` 应是一个**可查询、可审计的完成状态**，而不是“日志里打了一句错误后悄悄丢掉消息”。

尤其要避免：

```python
while True:
    try:
        await process_message(message)
        break
    except Exception:
        await asyncio.sleep(1)
```

以上无限循环既可能卡住同一分区，又容易造成无上限模型费用；还会错误重试不可恢复的权限或数据问题。

## 7. DLQ / DLT：死信消息留存机制

**Dead Letter Queue（DLQ）** 或 **Dead Letter Topic（DLT）** 用于保存无法按正常流程完成的消息及失败上下文，供排查和受控重放。它不是自动修复器。

建议归档的字段：

| 字段 | 作用 |
|---|---|
| `event_id` / `job_id` | 唯一标识事件与业务任务 |
| `original_topic`、`partition`、`offset` | 定位原始 Kafka 消息 |
| `original_key`、`original_headers` | 原始消息路由和上下文 |
| 原始内容或安全存储引用 | 使解析失败的数据仍可复现 |
| `payload_sha256` | 证明重放内容对应原始字节 |
| `error_code`、脱敏错误摘要 | 解释失败类型 |
| `attempt_count`、`first_failed_at`、`last_failed_at` | 分析重复失败与时间跨度 |
| `model_version`、`parser_version`、`rule_version` | 复现当时的软件与知识条件 |
| `status`、`resolution`、`replay_id` | 跟踪修复与人工重放 |

**隐私与安全**：DLQ 不应该无条件公开原始 Token、API Key、身份证号、聊天正文或未授权文档。应限制访问权限、加密保存、设置合理保留期并建立脱敏策略。

### 7.1 “记录 FAILED”与“发布到 Kafka DLQ”是两件事

数据库事务可以将 `FAILED` 状态和一条 Outbox 发布事件一起提交；外部 Kafka 发送不是这个数据库事务的一部分。

```text
业务失败，达到终态
       ↓
同一数据库事务：状态=FAILED + 原始数据保留 + Outbox 事件
       ↓
提交成功后，原 Kafka 消息可安全地完成持久化交接
       ↓
独立发布器读取 Outbox
       ↓
Kafka Producer 向 DLQ Topic 发布
       ↓
收到 Broker 确认，再标记 Outbox 已发布
```

发送到 Kafka 成功后，若尚未更新数据库 `published_at` 就崩溃，可能再次发布，因此 DLQ 接收者仍需按 `event_id` 幂等处理。若依赖 Outbox 而不实现发布器与监控，就只有待发送记录，没有真正投递到 DLQ。

**关键判断**：只有在已经将原消息与恢复所需状态可靠保存到独立持久化存储（或确认成功发布到真正的死信 Topic）之后，才能考虑推进原消息的消费 Offset；不能先提交 Offset 再尝试保存失败记录，否则保存失败会使消息丢失。

### 7.2 什么时候重放 DLQ

DLQ 重放前，需要先确认：根因已经修复、数据权限仍有效、业务幂等仍成立、版本适用，必要时重新获得操作确认。建议将人工重放记作一个**新运行实例**并与原失败记录关联，避免覆盖原先的事实和诊断证据。

重放不能简单把原消息重新推回主 Topic 后不加限制地反复循环。

## 8. 如何避免一条坏消息堵住正常任务

同一分区内部消息是按 Offset 有序读取的。如果 Consumer 在 Offset 101 失败后无限原地重试，那么后面的 102、103、104 就可能长期得不到处理。这称为 **Head-of-Line Blocking（队头阻塞）**。

主要有四种架构选择：

| 方案 | 处理方式 | 好处 | 代价与约束 |
|---|---|---|---|
| A. 分区内有限重试 + 失败后 DLQ | 当前消息重试几次，失败保存并继续后续消息 | 简单、容易解释 | 在重试期间仍阻塞分区；必须确认归档成功后才能提交 |
| B. Retry Topic | 失败消息转到独立重试 Topic | 主 Topic 可快速推进 | **跨路径可能改变业务处理顺序** |
| C. 持久化 Inbox + 独立 Worker | 原消息先持久化，之后异步按状态调度 | 主 Kafka 消费与慢任务解耦，最适合长任务 | 多一套持久化任务系统、调度与监控 |
| D. 严格顺序隔离 | 对必须按顺序处理的 Key 暂停或串行处理 | 可以保住指定业务顺序 | 相关 Key 的后续任务仍需等待或人工介入 |

### 8.1 方案 A：分区内有限重试

```text
Partition-0: 100 ✅ → 101 ❌重试×3 → DLQ 持久化 ✅ → 102 ✅
```

适用于错误很少、重试时间短、强调简单流程的系统。失败归档成功后才能继续提交相应 Offset；并发处理时还应遵守前一节讲过的安全提交水位规则。

### 8.2 方案 B：Retry Topic

```text
主 Topic：100 ✅ → 101（转入 retry-5m）→ 102 ✅
                          │
                          └─5 分钟后处理 101
```

适合相互独立的任务。**不适合默认要求同一业务键严格按原顺序产生副作用**的系统，因为 102 可能先于 101 完成。如果必须保持业务键顺序，应对该 Key 建立阻塞屏障、版本检查或按 Key 串行调度。

将记录写入 retry Topic 与提交源 Offset 是跨操作的一致性问题。如果均属于 Kafka 内部主题，可考虑 Kafka 事务性生产与消费位点协调；若牵涉 PostgreSQL 和外部 API，仍需要额外的幂等或 Outbox 机制。

### 8.3 方案 C：持久化 Inbox + Worker（本章重点示例）

```text
主 Kafka Consumer
   │
   ├─收到消息（先保留原始 bytes）
   ├─数据库事务中写入 Inbox / Job
   └─持久化成功后提交源 Offset
                 │
                 ▼
          独立 Worker 调度器
           ├─ PENDING → 执行
           ├─ RETRY_WAIT → 到期重试
           ├─ SUCCEEDED → 保存最终结果
           └─ FAILED → 保存原文和 Outbox → DLQ Publisher
```

优势：长期等待的模型重试不会占住 Kafka Consumer 的循环，用户断线或 API 进程重启也不会使已经持久化的任务消失。

局限：Inbox 的持久化成功不能替代**业务唯一性、执行租约、跨进程原子领取和外部副作用的幂等保障**。还必须监控任务积压与 Worker 处理能力。

### 8.4 顺序保证与无阻塞之间的真实权衡

假设同一账户的事件：

- Offset 101：账户余额 +100。
- Offset 102：余额扣除 50。

若将 101 丢到延迟重试路径而立刻处理 102，则在余额不足时，业务结果可能错误。

此时不能仅以“避免堵塞”为由放弃顺序。应明确业务语义并采取以下之一：

- 同一账户按 Key 串行执行、不同账户并行。
- 使用单调业务版本，拒绝旧事件或延迟新事件。
- 为正在重试的 Key 设置持久化栅栏，后续事件等待该 Key 解除。
- 不可恢复时进入人工干预流程，并保持该 Key 的后续执行暂停。

**没有一种策略能在完全不牺牲顺序、不增加状态管理的情况下，让所有失败消息无限期等待而其他所有相关消息仍正常处理。**

## 9. 业务任务状态机与数据表设计

以 PostgreSQL 为例，业务任务至少需要明确：

```sql
CREATE TABLE jobs (
    job_id TEXT PRIMARY KEY,
    original_topic TEXT NOT NULL,
    partition_no INTEGER NOT NULL,
    offset_no BIGINT NOT NULL,
    payload BYTEA NOT NULL,
    payload_sha256 CHAR(64) NOT NULL,
    status TEXT NOT NULL CHECK (
      status IN ('PENDING','RUNNING','RETRY_WAIT','SUCCEEDED','FAILED')
    ),
    attempts INTEGER NOT NULL DEFAULT 0,
    max_attempts INTEGER NOT NULL CHECK (max_attempts >= 1),
    next_attempt_at TIMESTAMPTZ,
    lease_owner TEXT,
    lease_until TIMESTAMPTZ,
    generation BIGINT NOT NULL DEFAULT 0,
    last_error_code TEXT,
    last_error_message TEXT,
    result JSONB,
    UNIQUE (original_topic, partition_no, offset_no)
);

CREATE INDEX jobs_ready_idx
ON jobs(status, next_attempt_at);
```

- `attempts`：已被 Worker 正式领取的执行次数，首次执行算 1。
- `next_attempt_at`：持久化的下一次可执行时间，重启后可继续查询。
- `lease_until`：Worker 的执行租约到期时间；需要心跳续租以免长任务被误接管。
- `generation`：领取任务时增长的执行代际编号。所有最终写入应验证租约所有者与代际，防止旧 Worker 覆盖接管后的结果。
- `UNIQUE(topic, partition, offset)`：防止相同 Kafka 位置重复导入；跨不同消息表达同一业务操作时还需要业务幂等键与结果约束。

### 9.1 原子领取任务（PostgreSQL 思路）

```sql
WITH candidate AS (
  SELECT job_id
  FROM jobs
  WHERE status = 'PENDING'
     OR (status = 'RETRY_WAIT' AND next_attempt_at <= now())
     OR (status = 'RUNNING' AND lease_until <= now())
  ORDER BY job_id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs AS j
SET status = 'RUNNING',
    attempts = j.attempts + 1,
    generation = j.generation + 1,
    lease_owner = :worker_id,
    lease_until = now() + interval '30 seconds',
    next_attempt_at = NULL
FROM candidate
WHERE j.job_id = candidate.job_id
RETURNING j.*;
```

这个示意适用于多个 Worker 竞争任务，`SKIP LOCKED` 能减少相互等待。但**并不是业务最终结果的唯一性保证**：结果存储仍需独立唯一约束和事务处理。长任务还应使用续租或合理租约期限。

### 9.2 安全失败处理

失败的状态更新必须在同一个事务中完成：

- 若尚可重试：写入 `RETRY_WAIT`、`next_attempt_at`、尝试次数和错误信息。
- 若永久失败或耗尽：写入 `FAILED`、最后错误、原始数据留存；并在同一事务创建唯一的 Outbox DLQ 发布事件。
- Worker 过期或已被接管：旧 Worker 不得再写入最终状态。

## 10. 处理外部模型调用的特殊风险

模型 API 可能有成本、超时、隐式 SDK 重试、速率限制和结果不确定等问题：

1. **Token 费用**：一次失败重试仍可能产生费用；重试次数必须计入预算。
2. **429 / 503**：如果上游返回 `Retry-After`，需要按约定等待；多 Worker 应协调全局速率。
3. **请求结果不确定**：调用方超时后不能简单判定服务端未执行；具备操作副作用的工具应先检查 idempotency key 或远端执行状态。
4. **模型内容错误**：结构不合法不等于瞬时网络错误；是否重试取决于可否通过稳定的输出校验/修复策略提高成功率。
5. **SDK 内建重试**：如果 SDK 每次调用自动重试 2 次，Worker 再重试 3 次，实际请求数可能远大于日志显示的 3 次尝试。
6. **客户端断开**：如果任务需要跨重启恢复，应由独立 Worker 处理，并使用任务 ID 查询状态；客户端取消是否终止业务任务必须是明确设计。

一条错误消息不应造成无限费用或持续堵塞正常任务。

## 11. 完整 Python 离线教学实现的设计

附录代码使用标准库 `sqlite3`，**模拟持久化 Inbox + Worker 状态处理**，不需要实际 Kafka：

- `ingest()`：保存原始 Kafka 消息的字节、来源 Topic/Partition/Offset、内容哈希；重复导入原位置时检查一致性。
- `claim()`：在事务内原子领取，递增 `attempts` 和 `generation`，创建租约。
- `fail()`：在指定的可重试错误和剩余次数前提下进入 `RETRY_WAIT`；否则进入 `FAILED` 并创建 Outbox。
- `succeed()`：在仍拥有有效租约的条件下完成任务。
- `due_jobs()`：获得可领取任务列表；最终领取还需 `claim()` 原子确认，避免抢占冲突。
- `mark_published()`：仅在发布器获得 Kafka Broker 确认后调用；实际发送器不包含在此教学代码中。

实现了 **Full Jitter、最大尝试次数、持久化状态、租约代际保护、最终失败归档事件**。它不包含真实 Kafka Broker、PostgreSQL、模型 API 或生产级监控。

另外，示例中 `last_error_message` 仅限制长度；真实系统必须在存储前做凭据和敏感数据脱敏，不能把这个例子当成完整日志安全方案。

## 12. 真实 aiokafka Consumer 应如何持久化交接

下面是一个**关键接口示意**（依赖你的 `store` 实现和连接配置，不是可独立运行的全套服务）。为了保持原分区提交安全，示例按顺序保存**原始字节**，且仅在数据库持久化成功之后手动提交当前 Offset：

```python
import asyncio
from aiokafka import AIOKafkaConsumer, TopicPartition

async def consume_into_inbox(store):
    consumer = AIOKafkaConsumer(
        "documents",
        bootstrap_servers="localhost:9092",
        group_id="document-ingester",
        enable_auto_commit=False,
        auto_offset_reset="earliest",
    )
    await consumer.start()
    try:
        async for msg in consumer:
            # 用源 Topic、分区和 Offset 构成稳定导入 ID
            # 注意：它不是跨不同 Kafka 消息的业务幂等键
            source_id = f"{msg.topic}:{msg.partition}:{msg.offset}"
            # store.ingest() 是同步 SQLite 教学代码；
            # 生产中建议换成 PostgreSQL + 异步数据库访问。
            await asyncio.to_thread(
                store.ingest,
                source_id,
                msg.value,  # 原始 bytes，不先假定可 JSON 解析
                topic=msg.topic,
                partition=msg.partition,
                offset=msg.offset,
            )
            tp = TopicPartition(msg.topic, msg.partition)
            # 安全交接完成后，提交下一条待读取的位置。
            await consumer.commit({tp: msg.offset + 1})
    finally:
        await consumer.stop()
```

**这一设计的前提**：Inbox 数据库必须提供满足业务可靠性要求的持久化保证；消费者的恢复语义还依赖 Retention、Offset、分区重平衡等配置。如果数据库提交成功而 Offset 提交失败，源消息可能重投，`ingest()` 通过源位置去重；如果数据库提交失败，不得提交 Offset。

生产系统还需要处理 Rebalance 时的分区所有权、数据库不可用、Kafka Retention、指标报警及 Worker 排队能力。简化示例使用一条一提交的方式说明安全边界，吞吐量较高的生产系统可采用按分区批量持久化后提交对应的安全水位。

## 13. DLQ Publisher 的必要处理

示例代码只负责事务内创建 Outbox。真实发布器至少应做到：

```text
读取未发布 Outbox（带领取/租约，防多实例争抢）
      ↓
构造 DLQ 消息，携带 event_id 与原始来源标识
      ↓
Producer send_and_wait() 获取 Broker ACK
      ↓
把 published_at 写回 Outbox
```

如果在 `send_and_wait()` 成功后、写回 `published_at` 前崩溃，则可能再次发送同一 Outbox。DLQ 消费者依然需要按 `event_id` 幂等。**这不是设计错误，而是将跨系统非原子故障转化为可识别的重复事件。**

对于无需真正 Kafka DLQ 的小项目，也可以先使用 PostgreSQL 失败档案 + 管理后台进行人工查阅；但不要把“数据库失败档案”等同为“消息已发往 DLQ Topic”。

## 14. 故障注入与验收矩阵

| 测试场景 | 预期结果 | 核验对象 |
|---|---|---|
| 第 1 次临时失败 | RETRY_WAIT，记录下一次时间 | `jobs` 表 |
| 未到下次时间 | 不应再次领取 | `claim()` |
| 到期之后 | 新 Worker 可领取 | 租约、尝试次数 |
| 达最大尝试次数 | FAILED 且记录 Outbox | 任务与事件一致性 |
| 不可重试的格式错误 | 不浪费剩余重试预算 | 错误分类 |
| 多个 Worker 同时领取 | 仅一个成功认领 | 原子事务 |
| Worker 租约过期 | 新 Worker 可接管 | generation |
| 旧 Worker 迟到 | 不可覆盖新 Worker 结果 | 租约与 fencing |
| FAILED 已归档 | 同一任务不会继续无限重试 | 终态保护 |
| 错误任务 FAILED，后续正常任务到达 | 后续任务可领取和成功 | 独立任务处理 |
| Kafka Offset 未提交就崩溃 | 源消息重投但 Inbox 不重复 | 来源唯一性 |
| 归档事务失败 | 不允许确认源消息已安全交接 | 原子性 |
| Broker ACK 后 Outbox 更新前崩溃 | 可能重复发布，event_id 一致 | DLQ 幂等 |
| 重放前修复解析器 | 可创建受控新执行，原失败记录不丢失 | 审计与回放 |

**需区分验证层级：** 本章离线测试会真正运行 SQLite 状态机与线程竞争测试；真实 Kafka 重启、Rebalance、DLQ Producer ACK、PostgreSQL 行锁行为必须在真实服务环境中另行集成验证。

只记录“日志里发生了错误”远远不够。至少应记录：

## 16. 常见技术误区

1. **无限重试更可靠？** 错。无限重试可能让任务永久不结束，持续占用预算并放大服务故障。
2. **sleep 不阻塞事件循环，故可以无限等待？** 错。`asyncio.sleep` 不阻塞事件循环，但仍可能保留大量任务对象、等待槽位或状态；跨重启更无法依赖内存等待。
3. **Kafka 会自动把失败消息放进 DLQ？** 错。普通自写 Consumer 需要自行实现；Kafka Connect 或某些框架有专门错误处理能力。
4. **提交 Offset 就表示业务完成？** 错。只有可靠持久化交接或业务处理达到安全状态后才可提交；提交只是 Kafka 记录消费位置。
5. **FAILED 代表消息被丢掉？** 错。应该保留错误、来源、原文与重放信息。
6. **有了 DLQ 就能忽略消息顺序？** 错。把失败消息分流会改变其与后续消息之间的业务完成顺序。
7. **模型请求超时等于模型没有执行？** 错。结果未知时应检查远端或通过幂等语义处理。
8. **一条 Worker 重试失败不会影响其他任务？** 不一定。若在同一分区原地等待或独占全局队列/信号量，仍可能阻塞正常工作。
9. **设置 max_attempts 就能限制费用？** 错。一次业务尝试可能触发 SDK 内部多次重试、多个模型和工具调用。
10. **记录原始 payload 就没有隐私问题？** 错。失败归档应有权限、脱敏、加密和保留期限。

## 17. 本节知识总结

可靠后台任务不是“在异常上加一个 `try/except` 再 `sleep`”。它的核心是：

- 把错误分为暂时性、永久性和结果未知三类。
- 给重试设置明确的次数、时间与费用边界，并使用退避和抖动。
- 将等待重试状态持久化，避免进程退出后无法恢复。
- 最终失败保留原始消息、来源与错误上下文；必要时使用事务性 Outbox 将失败事件可靠投递至 DLQ。
- 通过幂等、唯一约束与执行代际阻止重复副作用和旧 Worker 覆盖结果。
- 让无关任务继续推进，同时对必须保证顺序的同一业务 Key 实施适当隔离。

# 附录 A：完整可运行的 SQLite 持久化重试教学程序

下面的代码只依赖 Python 标准库。它验证“重试次数、退避、租约、终态与 Outbox 在数据库侧的处理”，不模拟 Kafka 的全部 Broker 行为。

```python
"""Durable retry teaching demo. Python 3.10+, standard library only.
No Kafka broker is used. It models the database side of a durable handoff.
"""
from __future__ import annotations
import hashlib
import json
import random
import sqlite3
from contextlib import contextmanager
from dataclasses import dataclass
from pathlib import Path
from typing import Iterator

class BusinessConflict(Exception):
    pass

class TransientFailure(Exception):
    pass

class PermanentFailure(Exception):
    pass

@dataclass(frozen=True)
class RetryPolicy:
    max_attempts: int = 3   # inclusive of initial attempt
    base_delay: float = 2.0
    cap_delay: float = 60.0

    def __post_init__(self):
        if self.max_attempts < 1 or self.base_delay < 0 or self.cap_delay < 0:
            raise ValueError('invalid retry policy')

    def delay(self, failed_attempt: int, rng: random.Random) -> float:
        if failed_attempt < 1:
            raise ValueError('failed_attempt must be >= 1')
        # Full jitter, bounded exponential delay. Guard extreme exponents.
        exponent = min(failed_attempt - 1, 60)
        upper = min(self.cap_delay, self.base_delay * (2 ** exponent))
        return rng.uniform(0, upper)

class RetryStore:
    def __init__(self, path: str | Path, policy: RetryPolicy | None = None):
        self.path = str(path)
        self.policy = policy or RetryPolicy()
        with self._connect() as db:
            db.executescript('''
            CREATE TABLE IF NOT EXISTS jobs(
              job_id TEXT PRIMARY KEY,
              topic TEXT NOT NULL,
              partition_no INTEGER NOT NULL,
              offset_no INTEGER NOT NULL,
              original_payload BLOB NOT NULL,
              payload_hash TEXT NOT NULL,
              status TEXT NOT NULL CHECK(status IN
                ('PENDING','RUNNING','RETRY_WAIT','SUCCEEDED','FAILED')),
              attempts INTEGER NOT NULL DEFAULT 0,
              next_attempt_at REAL NOT NULL DEFAULT 0,
              lease_owner TEXT,
              generation INTEGER NOT NULL DEFAULT 0,
              lease_until REAL,
              last_error_code TEXT,
              last_error_message TEXT,
              result TEXT,
              UNIQUE(topic, partition_no, offset_no)
            );
            CREATE TABLE IF NOT EXISTS outbox(
              event_id TEXT PRIMARY KEY,
              job_id TEXT NOT NULL,
              event_type TEXT NOT NULL,
              body TEXT NOT NULL,
              published_at REAL,
              FOREIGN KEY(job_id) REFERENCES jobs(job_id)
            );
            CREATE INDEX IF NOT EXISTS jobs_due
                ON jobs(status, next_attempt_at);
            ''')

    @contextmanager
    def _connect(self) -> Iterator[sqlite3.Connection]:
        db = sqlite3.connect(self.path, timeout=5.0)
        db.row_factory = sqlite3.Row
        db.execute('PRAGMA busy_timeout=5000')
        db.execute('PRAGMA foreign_keys=ON')
        try:
            yield db
            db.commit()
        except BaseException:
            db.rollback()
            raise
        finally:
            db.close()

    def ingest(self, job_id: str, raw: bytes, *, topic='documents', partition=0, offset=0) -> str:
        """Durably copy raw Kafka record before acknowledging its offset.
        Same source offset and byte-for-byte content is idempotent.
        """
        digest = hashlib.sha256(raw).hexdigest()
        with self._connect() as db:
            db.execute('BEGIN IMMEDIATE')
            current = db.execute('SELECT * FROM jobs WHERE job_id=? OR '
                                 '(topic=? AND partition_no=? AND offset_no=?)',
                                 (job_id, topic, partition, offset)).fetchone()
            if current:
                if (current['job_id'] != job_id or current['topic'] != topic or
                    current['partition_no'] != partition or current['offset_no'] != offset or
                    current['payload_hash'] != digest):
                    raise BusinessConflict('same job_id or Kafka position with different contents')
                return 'ALREADY_SAVED'
            db.execute('''INSERT INTO jobs(job_id,topic,partition_no,offset_no,
                       original_payload,payload_hash,status)
                       VALUES(?,?,?,?,?,?,'PENDING')''',
                       (job_id, topic, partition, offset, raw, digest))
            return 'SAVED'

    def claim(self, job_id: str, worker_id: str, now: float, lease_seconds=30.0):
        """Atomic lease and monotonically growing generation (fencing)."""
        if lease_seconds <= 0:
            raise ValueError('lease_seconds must be positive')
        with self._connect() as db:
            db.execute('BEGIN IMMEDIATE')
            row = db.execute('SELECT * FROM jobs WHERE job_id=?', (job_id,)).fetchone()
            if row is None:
                return None
            can_claim = (row['status'] == 'PENDING' or
                         (row['status'] == 'RETRY_WAIT' and row['next_attempt_at'] <= now) or
                         (row['status'] == 'RUNNING' and row['lease_until'] <= now))
            if not can_claim:
                return None
            generation = row['generation'] + 1
            db.execute('''UPDATE jobs SET status='RUNNING',attempts=attempts+1,
                      generation=?,lease_owner=?,lease_until=?,next_attempt_at=0
                      WHERE job_id=?''',
                      (generation, worker_id, now + lease_seconds, job_id))
            return generation

    def _owned(self, db, job_id: str, worker_id: str, generation: int, now: float):
        row = db.execute('SELECT * FROM jobs WHERE job_id=?', (job_id,)).fetchone()
        if (row is None or row['status'] != 'RUNNING' or
            row['lease_owner'] != worker_id or row['generation'] != generation or
            row['lease_until'] <= now):
            raise BusinessConflict('worker lost execution lease / stale generation')
        return row

    def succeed(self, job_id: str, worker_id: str, generation: int,
                now: float, result: str) -> str:
        with self._connect() as db:
            db.execute('BEGIN IMMEDIATE')
            self._owned(db, job_id, worker_id, generation, now)
            db.execute('''UPDATE jobs SET status='SUCCEEDED', result=?,
                       lease_owner=NULL,lease_until=NULL,
                       last_error_code=NULL,last_error_message=NULL
                       WHERE job_id=?''', (result, job_id))
            return 'SUCCEEDED'

    def fail(self, job_id: str, worker_id: str, generation: int,
             now: float, error_code: str, message: str, *, transient: bool,
             rng: random.Random | None = None) -> str:
        # Caller must classify failure type; this class doesn't guess using text.
        rng = rng or random.Random()
        safe_message = message[:256]  # sanitize/redact upstream before storing
        with self._connect() as db:
            db.execute('BEGIN IMMEDIATE')
            row = self._owned(db, job_id, worker_id, generation, now)
            if transient and row['attempts'] < self.policy.max_attempts:
                backoff = self.policy.delay(row['attempts'], rng)
                db.execute('''UPDATE jobs SET status='RETRY_WAIT',next_attempt_at=?,
                         lease_owner=NULL,lease_until=NULL,
                         last_error_code=?,last_error_message=? WHERE job_id=?''',
                         (now + backoff, error_code, safe_message, job_id))
                return 'RETRY_WAIT'
            db.execute('''UPDATE jobs SET status='FAILED', lease_owner=NULL,
                     lease_until=NULL,last_error_code=?,last_error_message=?
                     WHERE job_id=?''', (error_code, safe_message, job_id))
            payload = {
                'job_id': job_id, 'topic': row['topic'],
                'partition': row['partition_no'], 'offset': row['offset_no'],
                'error_code': error_code, 'attempts': row['attempts'],
                'payload_sha256': row['payload_hash'],
                'raw_bytes_retained_in_jobs': True,
            }
            db.execute('''INSERT OR IGNORE INTO outbox(event_id,job_id,event_type,body)
                       VALUES(?,?,'DEAD_LETTER',?)''',
                       (f'dlq:{job_id}', job_id, json.dumps(payload, ensure_ascii=False)))
            return 'FAILED'

    def get(self, job_id: str):
        with self._connect() as db:
            row = db.execute('SELECT * FROM jobs WHERE job_id=?', (job_id,)).fetchone()
            return dict(row) if row else None

    def outbox(self):
        with self._connect() as db:
            return [dict(r) for r in db.execute('SELECT * FROM outbox ORDER BY event_id')]

    def due_jobs(self, now: float, limit=100):
        with self._connect() as db:
            return [r[0] for r in db.execute('''SELECT job_id FROM jobs WHERE
                status='PENDING' OR (status='RETRY_WAIT' AND next_attempt_at <= ?)
                OR (status='RUNNING' AND lease_until <= ?)
                ORDER BY job_id LIMIT ?''', (now, now, limit))]

    def mark_published(self, event_id: str, now: float):
        """Only call AFTER broker acknowledges publication (not before)."""
        with self._connect() as db:
            db.execute('UPDATE outbox SET published_at=COALESCE(published_at,?) WHERE event_id=?',
                       (now, event_id))
```

本次实际运行环境中，`python -m unittest -v test_retry_demo.py` 执行结果为 **26 项测试通过**。测试包括线程并发领取、失败转入 RETRY_WAIT、达到尝试上限进入 FAILED、Outbox 唯一性、租约过期后接管、旧 Worker 写入拒绝、原始消息留存和坏消息终态后正常任务仍可领取。

**验证局限**：

- 采用 SQLite 文件数据库，不是 PostgreSQL 行锁/事务隔离的实际性能验证。
- 不连接 Kafka Broker，无法证明实际 Commit、Rebalance、网络断开与 DLQ Publisher 的端到端正确性。
- 不模拟真实模型 API 的费用、时延和 Rate Limit。
- 租约示例只实现期限与代际检查，长任务在生产中还需要续租、心跳与强制资源限制。
- Outbox 仅创建与标记发布状态，不包含真实 Kafka 发布器。
- `original_payload` 直接保留字节用于教学；真实业务必须考虑加密、敏感数据保护和保留期限。
