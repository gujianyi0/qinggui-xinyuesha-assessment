# Python 基础与异步编程（三）：协程、事件循环、Task 与并发执行

> 版本基准：Python 3.13；示例通常适用于 Python 3.11+。以下讨论以标准库 `asyncio` 为主，除非特别说明，默认单线程运行一个事件循环。

## 1. 六个概念先区分

| 名称 | 它是什么 | 它本身会让代码开始运行吗？ | 主要职责 |
|---|---|---|---|
| `async def` | 定义原生协程函数的语法 | **不会**；它只是定义函数 | 描述可被异步执行的程序 |
| 协程对象（coroutine object） | 调用协程函数得到的可等待对象 | **通常不会**；只创建对象 | 保存一次协程执行的状态 |
| `await` | 等待可等待对象的表达式 | **会驱动所等待的协程/等待结果**，但不一定创建新 Task | 表达依赖，并在必要时挂起当前任务 |
| `asyncio.Task` | 包装协程、交由事件循环调度的对象 | **会安排协程执行** | 调度、追踪结果、异常与取消 |
| 事件循环（event loop） | 调度任务、处理定时器和 I/O 就绪事件的运行机制 | 事件循环运行后才持续调度 | 在多个可运行任务之间协调执行 |
| 并发（concurrency） | 多项任务在时间上交错推进 | 不是一条特定语句 | 让等待阶段可以与其他任务的工作重叠 |

务必把下列三个层次分开：

1. **定义**：`async def fetch(): ...` 定义一种可暂停执行的函数。
2. **构造**：`coro = fetch()` 创建协程对象；此时一般还没有执行函数体。
3. **执行与调度**：`await coro` 在当前任务中执行/等待它；`asyncio.create_task(coro)` 则创建一个独立、由事件循环调度的 Task。

**一句严格的表述**：`async def` ≠ 立即异步执行；`await` ≠ 自动并发；`create_task` ≠ 创建线程；并发 ≠ 多核并行。

## 2. 协程：函数、对象与暂停点

### 2.1 协程函数与协程对象

```python
import asyncio

async def greet(name: str) -> str:
    print('函数体开始执行')
    await asyncio.sleep(0.1)
    return f'你好，{name}'

async def main() -> None:
    coro = greet('A')
    print('已经创建协程对象')
    # 上一行之后，greet 内的 print 尚未执行。
    result = await coro
    print(result)

asyncio.run(main())
```

典型输出：

```text
已经创建协程对象
函数体开始执行
你好，A
```

`greet` 是**协程函数**；`greet('A')` 返回的是**协程对象**。只创建不执行的协程对象，如果最终没有被等待、安排为任务或正确关闭，通常会触发 `RuntimeWarning: coroutine ... was never awaited`。

### 2.2 协程与普通函数的本质差别

普通同步函数被调用时，直接运行其函数体，直到返回或抛出异常。原生协程函数被调用时，先产生一个协程对象；协程可以在等待点暂停，保留其局部变量和执行位置，然后恢复。

```python
import asyncio

async def work() -> None:
    x = 10
    print('暂停之前', x)
    await asyncio.sleep(0.1)
    print('恢复之后', x)
```

上例暂停期间局部变量 `x` 仍属于该协程的执行状态。与操作系统线程相比，协程的切换主要依赖**协作式调度**：代码在可等待操作真正挂起时让出执行权，而不是由操作系统随时在任意 Python 字节码位置强制切换协程。

### 2.3 协程对象不等于 Task

```python
import asyncio

async def f() -> int:
    return 42

async def main() -> None:
    coro = f()                  # coroutine object
    task = asyncio.create_task(coro)  # asyncio.Task
    print(type(coro).__name__)  # coroutine
    print(type(task).__name__)  # Task
    print(await task)            # 42

asyncio.run(main())
```

一个协程对象通常只能沿其执行过程被消耗一次。**不要对已经完成的同一个协程对象再次 `await`**；如果需要多个地方等待同一个进行中的计算，可以共享一个 Task，并分别 `await` 该 Task。

## 3. `await` 的准确语义

### 3.1 `await` 表达依赖，不自动创建并发任务

```python
import asyncio

async def get_user() -> str:
    await asyncio.sleep(1)
    return '用户A'

async def get_permissions() -> str:
    await asyncio.sleep(1)
    return '只读'

async def main() -> None:
    user = await get_user()
    permissions = await get_permissions()
    print(user, permissions)

asyncio.run(main())
```

这里**先完成 `get_user`，再开始 `get_permissions`**，两段独立的 1 秒等待在此程序中是串行的，合计约 2 秒。

原因不是 `await` “不支持异步”，而是第二个协程对象直到第一个 `await` 返回后才会创建、开始执行。

### 3.2 `await` 可能暂停，但不是每次都切换任务

```python
import asyncio

async def immediate() -> int:
    return 7

async def main() -> None:
    print('A')
    value = await immediate()
    print('B', value)

asyncio.run(main())
```

上述 `await immediate()` 没有遇到真正阻塞的等待点，可以直接完成。**`await` 表示“可能需要等待”，不保证事件循环一定在这一行切换到别的 Task。**

注意：`await` 后的表达式必须是 **awaitable（可等待对象）**。普通整数、字符串等不能直接 `await`。

### 3.3 三种主要的 awaitable

- **协程对象**：`async_func()` 的返回值。
- **Task**：封装了协程并由事件循环调度的对象。
- **Future**：表示未来某个时刻得到的结果，通常由框架或底层 I/O 接口使用。

`Task` 是 Future 类接口的一个子类/兼容对象；普通业务代码通常不用手动创建 `Future`，但理解它有助于看懂事件循环等待 I/O 结果的过程。

### 3.4 `await` 一个协程与 `await` 一个 Task 的关键区别

```python
# 形式一：沿当前任务直接等待子协程
answer = await query_database()

# 形式二：先创建独立 Task，再等待它
query_task = asyncio.create_task(query_database())
answer = await query_task
```

两种形式都能返回相同结果，但**第二种引入了独立的调度单元**。如果后续代码没有和它重叠的工作，单独创建 Task 通常不会带来并发性能收益，反而多了一层生命周期和错误处理责任。

“直接 `await` 协程在当前 Task 的执行链中推进”不意味着它无法与系统中的其他 Task 并发：当其内部真正挂起时，事件循环仍可运行其他已就绪任务。

## 4. 事件循环究竟负责什么

### 4.1 核心职责

事件循环是 `asyncio` 的调度与 I/O 协调中心，主要负责：

1. 保持已经就绪、可以继续运行的回调和 Task。
2. 管理定时器与截止时间。
3. 与操作系统 I/O 机制配合，处理网络读写等就绪/完成通知。
4. 让等待条件满足的 Task 恢复执行。
5. 维护任务异常、取消与运行时资源的处理机制。

在常见的单线程事件循环中，**同一时刻只有一个 Task 正在该线程中运行 Python 协程代码**。当该 Task 真正挂起，事件循环便可以运行另一个就绪 Task。多个 Task 的等待期可以重叠。

### 4.2 一次典型调度的时间线

以下是概念时间线，不承诺具体事件就绪顺序：

```text
时间        当前运行的任务       事件/状态
0.0 s       Task A             开始发起网络请求并等待
0.0 s       Task B             开始发起另一网络请求并等待
0.0~1.0 s   事件循环            等待 I/O / 处理其他回调
1.0 s       Task B             B 的结果先就绪；恢复并完成
2.0 s       Task A             A 的结果就绪；恢复并完成
```

单线程并发的时间优势主要来自**等待重叠**，不代表两段耗时 Python 计算真的同时运行。

### 4.3 `asyncio.run()` 的作用

```python
import asyncio

async def main() -> None:
    print('运行中')

if __name__ == '__main__':
    asyncio.run(main())
```

`asyncio.run()` 是普通脚本常用的顶层入口。它负责建立并运行事件循环，运行入口协程，并在结束时进行相应清理。通常对一个脚本入口调用一次。

**不要在已经运行的事件循环中再次调用 `asyncio.run()`**。例如 FastAPI/Uvicorn 的请求处理协程已经处于服务器管理的事件循环中，应直接使用 `await`，而不是嵌套运行另一个事件循环。

### 4.4 `get_running_loop()`、底层调度和回调

```python
import asyncio

async def main() -> None:
    loop = asyncio.get_running_loop()
    print('当前循环是否运行：', loop.is_running())
    loop.call_soon(lambda: print('稍后执行的回调'))
    await asyncio.sleep(0)

asyncio.run(main())
```

- `asyncio.get_running_loop()`：取得当前线程中正在运行的事件循环；没有运行中的循环则报错。
- `loop.call_soon(...)`：向事件循环登记回调，稍后调度，不会在调用这一行直接同步执行。
- `await asyncio.sleep(0)`：显式提供一个让出执行机会的点；不是承诺所有其他任务一定已经完成。

大多数应用业务不需要手动操作低层事件循环对象，使用 `asyncio.run()`、`await`、`TaskGroup` 等高层 API 更清晰。

## 5. Task 是什么、什么时间执行

### 5.1 创建 Task

```python
import asyncio

async def fetch(name: str) -> str:
    print(f'{name}: 开始')
    await asyncio.sleep(0.5)
    print(f'{name}: 结束')
    return name

async def main() -> None:
    task = asyncio.create_task(fetch('A'), name='fetch-A')
    print('Task 已创建')
    result = await task
    print('得到结果：', result)

asyncio.run(main())
```

在默认任务调度模式下，`create_task()` 安排协程**尽快运行**，通常不会在函数调用返回前直接执行整个协程函数体。然后当前任务需要继续执行或挂起，事件循环才有机会运行新 Task。

**版本细节**：Python 3.12+ 存在 eager task factory 等“急切启动”机制，可能在 Task 创建时立即执行协程的初始部分。不要把默认调度的某个具体打印顺序当成对所有任务工厂都成立的语言保证。

### 5.2 Task 管理哪些信息

Task 作为运行句柄，通常可以通过以下方法观察：

```python
import asyncio

async def calculate() -> int:
    await asyncio.sleep(0.1)
    return 100

async def main() -> None:
    task = asyncio.create_task(calculate(), name='calculation')
    print(task.get_name())
    print(task.done())      # 通常为 False
    result = await task
    print(result)           # 100
    print(task.done())      # True
    print(task.result())    # 100

asyncio.run(main())
```

其他常见方法：

- `task.cancel()`：**请求**取消 Task；并非立即强制终止。
- `task.cancelled()`：检查 Task 最终是否以取消状态结束。
- `task.exception()`：读取已结束任务的异常；未结束时不可调用，已取消时会抛出 `CancelledError`。
- `asyncio.current_task()`：当前正在执行的 Task。
- `asyncio.all_tasks()`：当前循环中尚未结束的任务集合。

注意：**`PENDING / RUNNING / SUSPENDED / DONE` 是理解任务生命周期的概念状态，并不是 Python 公开的固定 `Task.status` 枚举。**

### 5.3 Task 与操作系统线程的区别

| 比较 | asyncio Task | 操作系统线程 |
|---|---|---|
| 调度方 | 事件循环 | 操作系统线程调度器 |
| 是否自动获得新线程 | 否 | 是 |
| 切换方式 | 主要在等待点协作式切换 | 可以被系统抢占 |
| 典型优势 | 大量 I/O 等待任务 | 运行阻塞操作，或与适当计算场景配合 |
| 资源消耗 | 通常比线程轻量 | 每线程有系统调度和栈等成本 |
| 是否天然 CPU 多核并行 | 否 | 受运行时、GIL 和具体任务等约束 |

不要将 Task 理解成“轻量线程”的完全等价物；它们的调度、取消及隔离语义不同。

## 6. 为什么“使用了 async/await”仍然可能串行

### 6.1 串行等待：两个请求合计约三秒

```python
import asyncio
import time

async def api(name: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return name

async def main() -> None:
    start = time.perf_counter()
    a = await api('A', 1)
    b = await api('B', 2)
    print(a, b)
    print(f'耗时约 {time.perf_counter() - start:.2f} 秒')

asyncio.run(main())
```

`await api('A', 1)` 完成以后才执行第二个调用，故总等待时间约 `1 + 2 = 3` 秒（不计少量开销）。

### 6.2 创建 Task 再等待：约两秒

```python
import asyncio
import time

async def api(name: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return name

async def main() -> None:
    start = time.perf_counter()
    task_a = asyncio.create_task(api('A', 1))
    task_b = asyncio.create_task(api('B', 2))
    a = await task_a
    b = await task_b
    print(a, b)
    print(f'耗时约 {time.perf_counter() - start:.2f} 秒')

asyncio.run(main())
```

两个 Task 提前创建并被调度，因此等待阶段重叠。**即便接下来依次 `await task_a`、`await task_b`，也不等于它们串行执行。**

关键因素是：两个 Task 在等待其结果之前就已经被安排运行。

### 6.3 `gather()`：聚合多个并发结果

```python
import asyncio

async def api(name: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return name

async def main() -> None:
    results = await asyncio.gather(
        api('A', 2),
        api('B', 1),
    )
    print(results)  # ['A', 'B']

asyncio.run(main())
```

`gather()` 会安排其中的协程并发执行。虽然 B 先完成，**成功结果列表仍遵循传入参数的顺序**，而不是完成顺序。

### 6.4 `TaskGroup`：结构化并发

```python
import asyncio

async def api(name: str, delay: float) -> str:
    await asyncio.sleep(delay)
    return name

async def main() -> None:
    async with asyncio.TaskGroup() as group:
        task_a = group.create_task(api('A', 2), name='A')
        task_b = group.create_task(api('B', 1), name='B')

    # 离开 async with 时，两个 Task 均已正常完成，
    # 或失败/取消流程已经被 TaskGroup 处理。
    print(task_a.result(), task_b.result())

asyncio.run(main())
```

`TaskGroup` 从 Python 3.11 引入，适合生命周期相互关联的子任务。它将“谁创建了任务、谁负责等待任务结束、失败时如何处理其他子任务”集中在一个词法作用域内。

### 6.5 并发与数据依赖

并不是所有请求都适合并发：

```python
# 必须先拿到用户 ID，才能查询其订单：存在依赖，必须先后执行
user = await get_user()
orders = await get_orders(user.id)
```

反之，如果“查用户资料”和“查配置”相互独立，就可能并发。并发设计必须以业务依赖关系为依据，不能机械地把所有 `await` 改成 `create_task`。

## 7. 并发、并行、异步、同步到底如何对应

### 7.1 概念边界

- **同步（synchronous）**：调用者通常沿同步调用链等待操作完成并返回。它描述接口及执行关系。
- **异步（asynchronous）**：发起操作后，可通过 Future、回调、Task 等机制在稍后取得结果。它描述接口和完成通知方式。
- **并发（concurrency）**：多个任务在重叠时间段内推进，不要求同一时刻执行多个 CPU 指令流。
- **并行（parallelism）**：多个工作在同一时刻真实执行，例如不同 CPU 核心处理不同计算任务。

这四个词不是同一个维度。异步 API **有助于**组织并发，但不保证并发；多个 Task 的单线程并发通常也不等于 CPU 并行。

### 7.2 两项网络请求的时间图

**串行：**

```text
时间 ───────────────────────────►
A    [------- 等待 1 s -------]
B                             [------- 等待 2 s -------]
总耗时约 3 s
```

**并发：**

```text
时间 ───────────────────────────►
A    [------- 等待 1 s -------]
B    [------------------ 等待 2 s ------------------]
总耗时约 2 s
```

并发示例里两个请求的网络等待可以重叠，但在单线程事件循环内运行的 Python 代码并非同时在两个 CPU 核心执行。

### 7.3 性能何时不会改善

如果协程内部是长时间、没有让出控制权的同步运算：

```python
async def cpu_heavy() -> int:
    total = 0
    for i in range(20_000_000):
        total += i * i
    return total
```

把它包进 `create_task` 不会让这段 Python 循环自动并行，也不会让事件循环在循环运行期间及时处理其他任务。后续学习阻塞检测与线程池/进程池时再解决这类问题。

## 8. `asyncio.sleep` 与调度实验

### 8.1 `asyncio.sleep` 不阻塞当前事件循环线程

```python
import asyncio

async def first() -> None:
    print('A1')
    await asyncio.sleep(0.1)
    print('A2')

async def second() -> None:
    print('B1')
    await asyncio.sleep(0.1)
    print('B2')

async def main() -> None:
    async with asyncio.TaskGroup() as group:
        group.create_task(first())
        group.create_task(second())

asyncio.run(main())
```

常见输出为：

```text
A1
B1
A2
B2
```

不过事件循环调度受就绪时机影响。不要把并发日志的顺序作为业务正确性的唯一保证。

### 8.2 `sleep(0)` 是显式让出执行机会的工具

```python
import asyncio

async def worker() -> None:
    for step in range(3):
        print('worker', step)
        await asyncio.sleep(0)

async def main() -> None:
    task = asyncio.create_task(worker())
    for step in range(3):
        print('main', step)
        await asyncio.sleep(0)
    await task

asyncio.run(main())
```

此程序演示如何让已就绪任务获得调度机会。它**不是**替代真实异步 I/O 或解决 CPU 密集任务的通用办法，也不保证任务之间精确轮流执行。

## 9. `gather()`、`TaskGroup` 和裸 `create_task()` 的语义区别

| 机制 | 是否安排并发 | 何时完成 | 子任务失败时的典型行为 | 常见场景 |
|---|---|---|---|---|
| `await coro()` | 不额外创建 Task；直接等待 | 当前协程返回/抛异常 | 异常沿当前等待链传播 | 单一依赖步骤 |
| `asyncio.create_task(coro())` | 是 | Task 自行完成；创建者决定何时等待 | 如果无人取得异常，可能产生未检索异常日志 | 需要独立调度、取消或监控的操作 |
| `await asyncio.gather(...)` | 是 | 默认成功时全部完成；失败时可能提前向等待者传播 | 默认第一个异常向外传播，其他尚未完成的任务**不会因此自动取消** | 聚合多个相互独立的结果 |
| `async with asyncio.TaskGroup()` | 是 | 退出作用域时收束子任务 | 一个子任务发生非取消异常，通常取消其余任务并收集异常 | 生命周期相关的子任务组 |

`gather(return_exceptions=True)` 会把普通异常放入结果列表，应用方必须自行检查结果类型，不可直接把异常对象当成功结果使用。

**容易忽略的细节**：`gather()` 某个任务失败后，其他 Task 可能仍在执行；如果这时顶层 `main()` 直接因异常退出，`asyncio.run()` 的清理阶段又可能取消尚未完成的任务。不能把这种现象误判为 `gather()` 本身主动取消了兄弟任务。

## 10. Task 的生命周期、异常与取消的基础语义

一个 Task 的概念性生命周期可以理解为：

```text
创建 Task
   ↓
等待事件循环调度
   ↓
运行部分协程代码
   ├── 等待 Future/I/O ──→ 条件就绪 ──→ 恢复运行
   ├── 正常 return ──→ 完成并保存结果
   ├── raise 异常 ──→ 完成并保存异常
   └── 收到取消请求 ──→ 在适当位置注入 CancelledError
                                    └── 可能在清理后取消结束
```

`task.cancel()` 是提出取消请求，不是强制杀死线程。协程可能还需要执行 `finally` 清理，也可能捕获或抑制取消；因此取消请求与最终 `task.cancelled()` 为真之间存在区别。

```python
import asyncio

async def job() -> None:
    try:
        await asyncio.sleep(10)
    finally:
        print('清理资源')

async def main() -> None:
    task = asyncio.create_task(job())
    await asyncio.sleep(0)  # 给任务开始执行的机会
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        print('任务已取消')

asyncio.run(main())
```

应用代码通常应在必要的 `finally` 中清理资源，并让取消继续传播；不应无条件吞掉 `CancelledError`。后续超时、取消和资源清理章节再深入研究。

### 10.1 Task 的引用与生命周期管理

不要直接创建任务后完全不记录它：

```python
asyncio.create_task(some_operation())  # 不建议作为可靠后台任务方案
```

官方文档提醒，应保留任务的强引用，并处理完成后的异常。对于**必须在请求之后仍有持久状态、跨进程重启可恢复**的任务，`asyncio.create_task()` 不能取代 Kafka、任务数据库和独立 Worker。

## 11. `async def` 不保证非阻塞：两个常见误区

### 11.1 写了 `async def`，里面却调用 `time.sleep`

```python
import time

async def bad() -> None:
    time.sleep(2)  # 阻塞事件循环线程
```

这个函数形式上是协程函数，但在 `time.sleep` 期间当前事件循环线程无法继续执行其他 Task。

相对地：

```python
import asyncio

async def better() -> None:
    await asyncio.sleep(2)  # 定时等待期间允许调度其他 Task
```

真正的网络访问应使用支持异步的 HTTP/数据库客户端，而不是简单地把一个同步函数用 `async def` 包起来。

### 11.2 先 `create_task` 再做大量同步计算

```python
import asyncio
import time

async def child() -> None:
    print('子任务启动')

async def main() -> None:
    task = asyncio.create_task(child())
    time.sleep(1)  # 当前事件循环线程被阻塞
    await task

asyncio.run(main())
```

默认调度下，创建 Task 后立刻运行长时间同步阻塞操作，会延迟新 Task 开始执行。**`create_task` 只是安排任务，事件循环依然需要获得运行机会。**

## 12. 与 JavaScript 和 C++ 的异同

### 12.1 JavaScript `Promise` 与 Python 协程对象

在普通 JavaScript 的 `async function` 中，调用函数会**立即开始执行函数体的同步前缀**，直到首次 `await` 或返回；它返回的是一个 `Promise`：

```javascript
async function jsWork() {
  console.log('JS: 已执行到这里');
  await Promise.resolve();
  console.log('JS: await 之后');
}

const p = jsWork();
console.log('JS: 调用之后');
```

通常输出：

```text
JS: 已执行到这里
JS: 调用之后
JS: await 之后
```

而 Python：

```python
async def py_work():
    print('Python: 函数体已开始')

coro = py_work()
print('Python: 调用之后')
# 此处仅创建了协程对象；需 await / Task / asyncio.run 等驱动执行。
coro.close()  # 本例不运行，只显式关闭以避免未等待警告
```

输出：

```text
Python: 调用之后
```

核心差异：**不能简单把 JavaScript Promise 与 Python 协程对象看作同一类已经开始工作的对象。**

`Promise.all([a(), b()])` 在语义上更接近“并发聚合结果”的 `asyncio.gather(a(), b())`，但两种运行时的调度与错误传播机制并不完全等价。

### 12.2 C++20 协程

C++20 的协程由 `co_await`、`co_return`、`co_yield` 等语法支持，其具体启动、暂停和恢复策略取决于协程返回类型、`promise_type`、awaiter 及运行时/执行器设计。**C++ `co_await` 与 Python `await` 在“可能暂停”这一概念上相似，但不能把 `asyncio` 事件循环自动套用到任意 C++ 协程。**

| 方面 | Python `asyncio` | JavaScript | C++20 |
|---|---|---|---|
| 异步函数机制 | `async def` 返回协程对象 | `async function` 返回 Promise | 协程转换依赖返回类型等协议 |
| 等待语法 | `await` | `await` | `co_await` |
| 常见调度框架 | `asyncio` 事件循环 | 宿主环境事件循环与任务/微任务机制 | 依赖库、执行器与协程实现 |
| 任务开始时机 | 协程对象默认惰性，安排后执行 | 调用即运行同步前缀 | 由具体协程类型与配置决定 |

## 13. 一个完整的“AI 应用双查询”示例

假设 AI 服务需要同时读取玩家资料与规则文档，两个 I/O 操作互不依赖：

```python
import asyncio
import time

async def get_player(player_id: int) -> dict[str, object]:
    # 模拟数据库等待；实际项目用异步数据库客户端
    await asyncio.sleep(0.6)
    return {'player_id': player_id, 'level': 10}

async def get_rule(rule_id: str) -> dict[str, str]:
    # 模拟外部检索等待；实际项目用异步 HTTP/数据库客户端
    await asyncio.sleep(0.9)
    return {'rule_id': rule_id, 'content': '规则正文'}

async def handle_request(player_id: int, rule_id: str) -> dict[str, object]:
    async with asyncio.TaskGroup() as group:
        player_task = group.create_task(get_player(player_id), name='query-player')
        rule_task = group.create_task(get_rule(rule_id), name='query-rule')

    player = player_task.result()
    rule = rule_task.result()
    return {'player': player, 'rule': rule}

async def main() -> None:
    start = time.perf_counter()
    result = await handle_request(1001, 'rule-01')
    print(result)
    print(f'耗时约 {time.perf_counter() - start:.2f} 秒')

if __name__ == '__main__':
    asyncio.run(main())
```

该演示的两次等待可重叠，理想运行时间接近较长的 `0.9` 秒，而非 `0.6 + 0.9 = 1.5` 秒。实际运行存在调度和系统开销。

设计分析：

1. `handle_request` 自身是协程函数；`handle_request(...)` 产生协程对象。
2. `await handle_request(...)` 将业务处理纳入当前任务的等待链。
3. `TaskGroup` 创建两个独立子 Task，使两段模拟 I/O 等待重叠。
4. `async with` 成功退出后，两个任务结果均可读取。
5. 如果某个子任务抛出非取消异常，`TaskGroup` 按结构化并发规则处理其他子任务和异常；不能盲目假设所有结果可用。
6. 这里的 `asyncio.sleep()` 仅是模拟 I/O，不能当作真实数据库查询或模型 API 的实现。

## 14. 阅读异步代码时如何辨认“并发是否真的发生”

阅读下列代码时，核心是分析**协程对象何时被创建、何时安排为 Task、什么时刻第一次挂起、任务之间是否存在数据依赖**。

| 代码形态 | 是否产生新的 Task | 常见执行关系 |
|---|---:|---|
| `result = async_func()` | 否 | 只产生协程对象，不开始函数体 |
| `result = await async_func()` | 否（直接等待时） | 当前 Task 执行/等待子协程；连续两次通常串行 |
| `t = asyncio.create_task(async_func())` | 是 | 安排独立任务运行 |
| `t1 = create_task(a()); t2 = create_task(b()); await t1; await t2` | 是 | a、b 通常并发推进，虽然等待结果写在两行 |
| `await asyncio.gather(a(), b())` | 是（对协程自动调度） | a、b 并发，按传入顺序收集结果 |
| `async with asyncio.TaskGroup(): ...` | 是 | 结构化并发，作用域内等待并管理子任务 |
| `async def f(): time.sleep(1)` | 不是有效的非阻塞保证 | 一旦运行到 `time.sleep`，会阻塞所在事件循环线程 |

还有两个工程上重要的补充：

- 一段代码是否**能并发**与是否**值得并发**是两个问题。存在严格依赖的数据库写入与后续查询，不能为了提速而随意改成并发。
- 即使单个异步进程能服务多条并发请求，也不意味着其 Task 天然具有跨进程持久性。进程退出后，内存中的 Task 和协程执行状态不能自动恢复。

## 15. 高频误区与准确表述

| 误区 | 正确认识 |
|---|---|
| “写了 `async def` 就自动启动后台任务” | 调用只得到协程对象；需要被等待或安排执行 |
| “每遇到一个 `await` 就会切换一次任务” | 只在确实需要等待时才会挂起；可直接完成 |
| “`await` 会自动并发” | `await` 表示依赖；多个操作连续直接等待往往串行 |
| “两个 `Task` 就是两个线程” | Task 在事件循环中协作式调度，不自动创建线程 |
| “先创建 Task 再逐个 await，就是串行” | Task 已经被安排运行，等待结果的代码顺序不代表执行未重叠 |
| “`gather` 一报错就取消所有其他任务” | 默认第一个异常向外传播，其余未完成任务通常不会因 `gather` 本身而被取消 |
| “使用 `TaskGroup` 后可以忽略异常” | 任务组会组织子任务清理与异常传播，调用方仍需处理错误 |
| “协程适合一切高性能计算” | 单线程协程主要擅长大量 I/O 等待；CPU 密集代码可能阻塞事件循环 |
| “一个 Task 只要创建了，程序重启后还会继续” | Task 是进程内运行时对象，不提供持久化、消息重投递和断点续跑 |
| “取消 Task 会立即撤销外部操作” | 取消是协作式请求，外部副作用可能已经发生 |

### 知识归纳

理解 asyncio 的最准确方式，是区分四件事：

- **协程对象是可被驱动执行的工作描述及其状态**，不是天然已经运行的后台任务。
- **`await` 描述当前执行链对结果的依赖**，在必要时让出控制权，但不自动提供多个独立任务之间的并发。
- **Task 把协程变成事件循环可独立调度与追踪的工作单元**，可读取结果、异常并请求取消。
- **事件循环通过协作式调度把多个任务的等待时间重叠起来**，从而实现典型的单线程 I/O 并发，而非默认的 CPU 并行。

这四层逻辑弄清之后，阅读 FastAPI 的异步路由、Agno 的异步运行、HTTP 客户端与数据库异步访问代码时，就能够准确判断哪里发生了实际并发，哪里只是串行等待，哪里可能阻塞整个事件循环。
