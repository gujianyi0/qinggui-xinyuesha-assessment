## 1. 关系型数据库与 SQL 的基本模型

关系型数据库用**表（Table）**组织记录，每张表由列和行组成。表之间并不只是通过对象引用连接，而是通过键、约束和查询表达关系。

- **数据库（Database）**：数据与数据库对象的集合。
- **模式（Schema）**：PostgreSQL 中数据库内的命名空间；`public.users` 的 `public` 即 Schema。不要将此概念和 JSON Schema 混为一谈。
- **表（Table）**：具有固定列定义的数据集合。
- **行（Row）**：一条记录。
- **列（Column）**：具有数据类型与可选约束的数据属性。
- **键（Key）**：用于标识记录或表达关系的字段及字段组合。
- **查询（Query）**：用于获取或操作数据的 SQL 声明。

SQL 语句常按用途分为：

| 类型 | 常见语句 | 目的 |
|---|---|---|
| DDL（数据定义语言） | `CREATE`、`ALTER`、`DROP` | 定义或修改数据库结构 |
| DML（数据操纵语言） | `INSERT`、`UPDATE`、`DELETE` | 修改数据 |
| 查询 | `SELECT` | 获取数据；部分教程也把它归入 DML |
| TCL（事务控制语言） | `BEGIN`、`COMMIT`、`ROLLBACK`、`SAVEPOINT` | 控制事务边界 |
| DCL（数据控制语言） | `GRANT`、`REVOKE` | 管理数据库权限 |

SQL 是**声明式语言**。例如 `SELECT ... WHERE ...` 规定需要什么结果，而扫描表还是使用索引、采用怎样的 JOIN 算法，则由数据库优化器根据统计信息和代价模型选择。SQLAlchemy ORM 最终同样要通过 SQL 驱动数据库完成工作，并不会跳过数据库的约束与事务机制。

### 1.1 用一个业务例子贯穿全文

假设一个 AI 产品允许用户提交反馈：

- `users`：用户数据，包含所属租户、邮箱和姓名。
- `feedbacks`：反馈记录，包含创建者、标题、状态、请求幂等键和版本号。
- 同一租户不能重复提交同一个 `request_key`。
- 反馈属于某个真实用户，状态只允许 `draft`、`submitted` 或 `closed`。

为什么选择这种结构？因为它同时包含：**一对多关联、业务唯一性、状态限制、索引、事务和重复请求问题**。

## 2. 数据表、主键、外键及关系建模

PostgreSQL 风格的示例结构：

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    email TEXT NOT NULL,
    name TEXT NOT NULL,
    CONSTRAINT uq_user_tenant_email UNIQUE (tenant_id, email)
);

CREATE TABLE feedbacks (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    user_id BIGINT NOT NULL REFERENCES users(id),
    request_key TEXT NOT NULL,
    title TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'draft',
    version INTEGER NOT NULL DEFAULT 1,
    CONSTRAINT uq_feedback_request UNIQUE (tenant_id, request_key),
    CONSTRAINT ck_feedback_status
        CHECK (status IN ('draft', 'submitted', 'closed'))
);

CREATE INDEX ix_feedback_tenant_status
    ON feedbacks (tenant_id, status);
CREATE INDEX ix_feedback_user_id
    ON feedbacks (user_id);
```

上面是教学模式；真实多租户应用通常还需要更严格的复合外键、租户一致性检查和授权设计。**只在两个表上各自保存 `tenant_id` 并不能保证两表的租户值一定一致**。例如，某条反馈的 `tenant_id='t1'` 但 `user_id` 指向 `t2` 用户，以上简单外键仍可能通过。可采用复合键/复合外键或数据库约束与业务授权联合保证。

### 2.1 各种键的区别

- **主键（PRIMARY KEY）**：唯一标识每一行；不可为 `NULL`。
- **唯一键（UNIQUE）**：禁止约束范围内的重复值；PostgreSQL 默认允许多个 `NULL`，与其 `NULLS NOT DISTINCT` 扩展有区别。
- **外键（FOREIGN KEY）**：要求引用的值能在被引用的主键或符合条件的唯一键中找到，确保**引用完整性**。
- **候选键**：理论上可唯一标识记录的一组最小属性。
- **业务幂等键**：根据业务操作确定，通常通过唯一约束实现“同一请求不产生重复业务记录”。

### 2.2 一对多、多对多关系

一对多：一个用户可以有多条反馈；`feedbacks.user_id` 是外键。多对多：例如角色与标签，需要关系中间表；通常两个外键构成复合主键或唯一约束。

### 2.3 数据范式与冗余

规范化设计有助于减少同一事实的重复保存。也不是完全不能冗余：为了查询性能可保留计算字段或反范式字段，但必须定义谁是**事实来源（Source of Truth）**、怎样同步以及出错时如何修复。数据库约束优先保护关键一致性，不能只在前端或 Prompt 中检查。

## 3. SELECT、过滤、排序、分页和聚合

### 3.1 典型查询

```sql
SELECT id, title, status
FROM feedbacks
WHERE tenant_id = 't1'
  AND status = 'submitted'
ORDER BY id DESC
LIMIT 20 OFFSET 0;
```

`WHERE` 在行级过滤；`ORDER BY` 指定排序；`LIMIT/OFFSET` 限制返回的数据范围。若分页要求稳定，排序字段应具有稳定的并列处理方式，例如 `ORDER BY created_at DESC, id DESC`。大偏移量分页可能增加扫描成本，可以采用基于游标/键集的分页方式。

### 3.2 分组与聚合

```sql
SELECT user_id, COUNT(*) AS feedback_count
FROM feedbacks
WHERE tenant_id = 't1'
GROUP BY user_id
HAVING COUNT(*) >= 2
ORDER BY feedback_count DESC;
```

- `COUNT(*)`：统计行数。
- `COUNT(column)`：统计该列的非 `NULL` 值数量。
- `SUM`、`AVG`、`MIN`、`MAX`：聚合函数。
- `GROUP BY`：按键组合分组。
- `HAVING`：过滤聚合后的分组，与 `WHERE` 的过滤阶段不同。

### 3.3 三值逻辑与 NULL

SQL 的 `NULL` 表示未知/缺失，并非数字 0 或空字符串。`column = NULL` 不会得到“等于 NULL”的真值，应写：

```sql
WHERE column IS NULL
WHERE column IS NOT NULL
```

SQL 谓词可能是 `TRUE`、`FALSE`、`UNKNOWN`，`WHERE` 只保留条件为 `TRUE` 的行。这一点会影响 JOIN、约束和筛选。

### 3.4 避免 `SELECT *` 的误用

`SELECT *` 对教学无妨，但复杂业务查询应明确需要的列，否则可能增加数据传输、引入敏感字段和破坏接口的稳定性。ORM 读取整个实体同样可能查询不需要的列。

## 4. JOIN 的种类、结果基数及常见陷阱

JOIN 是按关联条件组合不同表中的记录。

### 4.1 INNER JOIN

```sql
SELECT f.title, u.name
FROM feedbacks AS f
JOIN users AS u ON f.user_id = u.id
WHERE f.tenant_id = 't1';
```

只返回两侧满足 JOIN 条件的组合。一个用户拥有三条反馈，就会产生三条关联结果；**JOIN 不保证“一人只返回一行”**。

### 4.2 LEFT JOIN

```sql
SELECT u.name, COUNT(f.id) AS feedback_count
FROM users AS u
LEFT JOIN feedbacks AS f ON f.user_id = u.id
WHERE u.tenant_id = 't1'
GROUP BY u.id, u.name;
```

返回所有左表用户，即使某人没有反馈，结果中仍会出现该用户，`COUNT(f.id)` 得到 0。

### 4.3 LEFT JOIN 的过滤陷阱

**写法 A：**

```sql
SELECT u.name, f.title
FROM users AS u
LEFT JOIN feedbacks AS f ON f.user_id = u.id
WHERE f.status = 'submitted';
```

`WHERE` 要求右表有匹配状态，会排除右侧是 `NULL` 的用户，效果近似转为内连接。

**写法 B：**

```sql
SELECT u.name, f.title
FROM users AS u
LEFT JOIN feedbacks AS f
  ON f.user_id = u.id AND f.status = 'submitted';
```

第二种保留没有匹配已提交反馈的用户；过滤位置影响结果语义。

### 4.4 其他 JOIN

- `RIGHT JOIN`：保留右侧所有行。
- `FULL OUTER JOIN`：保留两侧所有行，缺失处填充 `NULL`。
- `CROSS JOIN`：产生笛卡尔积，若 A 有 m 行、B 有 n 行，最多生成 m×n 行。
- 自连接（Self Join）：同一表以不同别名连接，例如员工与上级关系。
- 多对多 JOIN：常经由中间表连接，特别注意行数膨胀和重复记录。

### 4.5 存在性查询

如果需求是“是否存在符合条件的反馈”，常使用 `EXISTS` 更贴近语义：

```sql
SELECT u.id
FROM users AS u
WHERE EXISTS (
    SELECT 1 FROM feedbacks AS f
    WHERE f.user_id = u.id AND f.status = 'submitted'
);
```

`EXISTS` 与 `JOIN` 不完全可互换，因为后者可能放大结果行数；选择时要看业务目标与执行计划。

## 5. 约束的分类、执行时机与并发意义

约束是数据库自身维护的数据不变量，其意义不仅是“防止输入格式错误”，还包括**在多个并发请求下维持一致性**。

| 约束 | 解决问题 | 示例 |
|---|---|---|
| `PRIMARY KEY` | 行身份唯一性 | `id` |
| `UNIQUE` | 指定字段组合不可重复 | `(tenant_id, request_key)` |
| `NOT NULL` | 不允许缺值 | `title` |
| `CHECK` | 保证表达式约束 | `status IN (...)` |
| `FOREIGN KEY` | 引用对象存在 | `feedbacks.user_id` |
| `EXCLUDE`（PostgreSQL） | 特定操作符关系上的冲突约束 | 时间区间不能重叠 |

### 5.1 为什么“先查询再插入”不足以防重复？

两个并发事务都执行：

```text
事务 A：查询 request_key=k，不存在
事务 B：查询 request_key=k，不存在
事务 A：插入 k
事务 B：插入 k
```

如果没有数据库唯一约束，可能产生两条重复记录。即使应用层先检查，也仍然存在**竞态条件**。

数据库 `UNIQUE (tenant_id, request_key)` 是最终防线。冲突应由应用捕获并根据业务契约处理，例如返回已有请求结果或明确报告冲突。

### 5.2 约束是在什么时候检查？

许多约束在对应 SQL 语句执行时检查；PostgreSQL 也支持部分约束设置为 `DEFERRABLE`，延迟到事务结束时检查。并非所有类型的约束都支持延迟，也不能默认所有违反约束的错误都只会出现在 `commit()` 时。

对 ORM 而言，约束异常可能发生在显式 `flush()`、自动 `autoflush`，或 `commit()` 内置的 Flush 中。如果是延迟约束，则可能直到提交阶段才出现。

### 5.3 外键不等于授权

外键只能证明“此 ID 引用了一条存在的记录”，不能证明“当前用户有权限访问这条记录”，也不能自然保证跨租户一致性。需要应用级授权、数据库复合约束，必要时结合 PostgreSQL RLS（Row-Level Security）。

### 5.4 删除关联与级联

数据库 `ON DELETE RESTRICT`、`CASCADE`、`SET NULL` 与 ORM 的 `cascade` 是两个不同层次。数据库级级联在约束层执行，ORM 级级联由对象映射和 Flush 驱动；如果两者配置不协调，可能出现额外查询、外键错误或非预期删除。对生产数据删除应明确配置，不能假设默认会“自动清理一切”。

## 6. 索引的结构、选择与代价

**索引（Index）**是一种帮助数据库快速定位记录的数据结构，类似一本书的目录，但它不是简单的“给所有字段加索引就更快”。

### 6.1 B-tree 索引

PostgreSQL 中最常用的是 B-tree，适合多种等值和范围比较、某些排序需求。

```sql
CREATE INDEX ix_feedback_tenant_status
ON feedbacks (tenant_id, status);
```

当常见查询是：

```sql
WHERE tenant_id = 't1' AND status = 'submitted'
```

该复合索引可能较为有利。对于单独 `status = 'submitted'` 的查询，不应假设它一定具有同等效果；复合索引的列顺序、过滤条件与 PostgreSQL 规划器的选择都很重要。

### 6.2 其他索引

- **唯一索引**：帮助强制唯一性，PostgreSQL 的主键和唯一约束通常会自动建立相关索引。
- **部分索引（Partial Index）**：只索引符合条件的行，例如只索引 `submitted` 反馈。
- **表达式索引**：基于表达式，例如 `lower(email)`。
- **GIN**：适用于数组、JSONB、全文检索等多值结构的典型场景。
- **GiST**：适用于空间或多种复杂运算符类别等场景。
- **BRIN**：适合某些数据按物理顺序具有相关性的超大表。
- **HNSW/IVFFlat**：属于 pgvector 提供的向量近似索引策略，不是 PostgreSQL 通用 B-tree 的替代品。

### 6.3 索引不是免费优化

索引通常会：

1. 占用磁盘空间；
2. 增加 INSERT、UPDATE、DELETE 的维护成本；
3. 增加迁移、备份和维护复杂度；
4. 在低选择性、小表或规划器认为顺序扫描更划算时不一定被采用。

### 6.4 外键与索引的关键区别

在 PostgreSQL 中，外键**引用的目标列**必须具备适当唯一性；但外键**所在的引用列**不会因为声明 FOREIGN KEY 就自动创建索引。因此 `feedbacks.user_id` 可以考虑显式建立索引，支持按用户查询和某些关联/删除检查。

## 7. SQL 执行计划与性能分析

不能只看 ORM 表达式推断性能，必须观察数据库实际计划。

```sql
EXPLAIN
SELECT * FROM feedbacks
WHERE tenant_id = 't1' AND status = 'submitted';
```

`EXPLAIN` 展示计划与估计成本；`EXPLAIN (ANALYZE, BUFFERS)` 会**实际执行语句**并给出执行统计、部分缓冲信息。

主要关注：

- `Seq Scan`：顺序扫描，不一定错误；小表可能最快。
- `Index Scan`、`Index Only Scan`、`Bitmap ... Scan`：不同索引访问策略。
- Join 算法：Nested Loop、Hash Join、Merge Join。
- 估计行数与实际行数之间的差距。
- 排序、聚合、实际耗时、缓冲读取。
- 查询是否返回过多行或触发 N+1。

**危险细节**：不能随便对生产写入语句运行 `EXPLAIN ANALYZE`，它会实际执行语句。测试 `UPDATE/DELETE` 时应使用隔离环境，或通过事务和回滚等方式控制影响；外部副作用与序列递增等也不一定完全可逆。

统计信息不准确、参数分布偏斜、索引选择性低，都可能使优化器不使用某个索引。“索引建了没用上”需要基于执行计划分析，不应先断定是 ORM 错误。

## 8. 事务与 ACID 的准确含义

事务（Transaction）把多个数据操作组合成一个受数据库一致性与并发机制保护的操作单元。

| ACID | 解释 | 需要注意 |
|---|---|---|
| Atomicity 原子性 | 事务范围内的修改要么提交，要么回滚 | 不等于外部 API、文件、邮件与数据库一起原子化 |
| Consistency 一致性 | 从一个满足约束的状态转换到另一个满足约束的状态 | 数据库约束与应用业务不变量共同负责 |
| Isolation 隔离性 | 事务间的可见性与互相干扰有明确规则 | 不同隔离级别提供不同保证 |
| Durability 持久性 | 成功提交的数据遵守数据库的持久化承诺 | 仍涉及数据库配置、硬件和复制架构 |

### 8.1 事务原子性不等于业务完全正确

数据库可以保证在一次事务内同时写入“反馈”和“审计事件”，但不能自己判断“反馈属于合法用户”“文本符合产品要求”“用户是否已确认”。这些属于更广泛的业务规则，需要确定的程序与数据库约束共同完成。

### 8.2 事务不是全系统的魔法撤销按钮

例如：

```text
1. 调用邮件 API 成功发送通知
2. 向数据库写入反馈
3. 数据库约束失败 → ROLLBACK
```

数据库回滚后，**邮件依然可能已经送出**。因此要求高可靠的跨系统流程，应考虑事务内持久化待发送事件（Transactional Outbox）、独立派发、幂等键与结果状态管理。

## 9. BEGIN、COMMIT、ROLLBACK 与 SAVEPOINT

### 9.1 一个直观事务

```sql
BEGIN;

INSERT INTO feedbacks (tenant_id, user_id, request_key, title, status)
VALUES ('t1', 1, 'req-100', '技能描述不正确', 'draft');

UPDATE users SET name = 'Alice' WHERE id = 1;

COMMIT;
```

如果在提交前决定不保存，则使用 `ROLLBACK`。SQL 已经执行，不意味着其他事务就必然能够看到这些未提交修改。

### 9.2 不显式 BEGIN 时会发生什么？

PostgreSQL 客户端在通常的自动提交模式下，单条独立 SQL 语句会各自处于一个事务中。**但驱动与 ORM 可以自行开启一个事务并保持打开**。不能仅凭 SQL 字符串里没看到 `BEGIN` 就断言它是立即提交的。

### 9.3 SAVEPOINT 是局部回滚点

```sql
BEGIN;
INSERT INTO ...;             -- A
SAVEPOINT sp1;
INSERT INTO ...;             -- B
ROLLBACK TO SAVEPOINT sp1;  -- 撤销 B，不撤销 A
COMMIT;                     -- 提交 A
```

`SAVEPOINT` 允许回滚部分操作而保持外层事务继续进行。SQLAlchemy 对应 `Session.begin_nested()`；**在 SQLAlchemy 2.x 中调用 `Session.commit()` 会提交最外层事务，不是“只提交当前 SAVEPOINT”**，应由返回的嵌套事务对象或上下文管理器完成保存点操作。

## 10. 隔离级别、快照、锁和并发异常

数据库事务相互交错时，可能出现脏读、不可重复读、幻读、更新丢失、序列化异常等现象。不同数据库对隔离级别的实现不完全一样。

### 10.1 PostgreSQL 的主要隔离级别

| 级别 | 简化理解 | 注意 |
|---|---|---|
| Read Committed | 每条语句基于当时可见的已提交数据读取 | PostgreSQL 默认；同一事务的两次读取可能不同 |
| Repeatable Read | 一个事务中的读取通常依据固定快照 | PostgreSQL 实现较强，仍可能有序列化异常 |
| Serializable | 结果应与某个串行执行次序等价 | 可能中止事务，应用需重试完整事务 |

PostgreSQL 的 `READ UNCOMMITTED` 实际按 `READ COMMITTED` 处理，不应照搬其他数据库关于脏读的行为。

### 10.2 更新丢失（Lost Update）

两个请求读到相同旧值，都在应用层算出新值，然后分别覆盖写入时，可能出现一个写入覆盖另一个。解决方向包括：

- 使用数据库原子表达式 `UPDATE ... SET counter = counter + 1`；
- 行级锁 `SELECT ... FOR UPDATE`（PostgreSQL 语义）；
- 乐观版本号与条件更新；
- 需要时提高事务隔离并正确处理重试。

不要把 `SELECT ... FOR UPDATE` 的 PostgreSQL 行锁语义直接套用到 SQLite；SQLite 的锁模型不同。

### 10.3 版本号乐观锁

假设一条反馈 `version=3`：

```sql
UPDATE feedbacks
SET title = '新标题', version = version + 1
WHERE id = 42 AND version = 3;
```

如果影响行数为 0，说明记录可能不存在或版本已改变；业务应该重新读取并处理冲突，而非继续无条件覆盖。

SQLAlchemy 可以用映射器的 `version_id_col` 自动为常规 ORM 逐行更新添加版本检查。但该机制不能覆盖所有批量 UPDATE/DELETE 形式，需要看具体 API。

### 10.4 死锁与序列化失败

并发事务可能出现相互等待造成死锁，或在 Serializable 模式下发现无法序列化。应用应按数据库提供的错误类别判断是否允许重试，重试的是**整个事务**，不能无条件重试已经产生外部副作用的操作。PostgreSQL 中典型的 SQLSTATE 包括 `40001`（serialization_failure）和 `40P01`（deadlock_detected）。

## 11. ORM 的角色：对象映射与真实 SQL

ORM（Object-Relational Mapping，对象关系映射）把数据库表映射为 Python 类，把数据库行映射为 Python 对象。例如：

```python
class Feedback(Base):
    __tablename__ = "feedbacks"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(200), nullable=False)
```

ORM 的本质不是“直接存对象而不写 SQL”，而是：

```text
Python 对象变化
   ↓
Session 追踪变更（Unit of Work）
   ↓
生成 INSERT / UPDATE / DELETE
   ↓
数据库执行 SQL 与检查约束
   ↓
事务 COMMIT 或 ROLLBACK
```

### 11.1 SQLAlchemy Core 与 ORM

SQLAlchemy 包含：

- **Core**：Engine、Connection、SQL Expression Language，直接组织 SQL 和事务。
- **ORM**：在 Core 上提供映射对象、Session、关系加载和 Unit of Work。

ORM 操作需要理解最终发出的 SQL。熟悉 ORM 不等于可以不懂 JOIN、约束、事务与执行计划。

### 11.2 Engine、Connection、Session 的区别

| 层 | 职责 |
|---|---|
| Engine | 数据库方言、连接池及连接创建入口 |
| Connection | 某个数据库连接及其事务上下文 |
| Session | ORM 的工作单元、对象身份映射和事务协调 |
| ORM 实例 | Python 内存中的某条映射数据的表示 |

`Session` 不等于一个数据库连接：它可能在需要时才从 Engine 取得连接；一个 Session 会管理逻辑事务、对象状态并使用底层连接执行 SQL。不能在不相关的并发线程/异步任务之间共享一个 Session。

## 12. Session、Unit of Work 与对象状态

### 12.1 Unit of Work 的含义

一个 Session 可以先收集多个对象变更，在合适时机生成有依赖顺序的 INSERT/UPDATE/DELETE。例如先写入用户，再写入引用它的反馈。ORM 可以利用关系和外键排序操作，但最终约束正确性仍由数据库判定。

### 12.2 常见对象状态

| 状态 | 含义 |
|---|---|
| Transient | 刚构建的 Python 对象，还未被 Session 管理 |
| Pending | `session.add()` 后等待写入 |
| Persistent | 由 Session 管理、已有数据库身份的对象 |
| Deleted | 被标记删除并在 Flush 中执行删除、事务尚未结束 |
| Detached | 已脱离 Session 的映射对象 |
| Expired | 属性被标记为过期，后续访问可能重新查询数据库 |

`Persistent` 并不意味着对象所在事务必然已经提交；例如新对象 `flush()` 后已从 Pending 转为 Persistent，但仍处于未提交事务内。

### 12.3 Identity Map 不是通用缓存

Session 的 Identity Map 在同一 Session 中以主键组织对象身份，避免把相同数据库行无必要地映射成互不相关对象。但它不是跨请求缓存，更不能替代 Redis 或持久化数据库状态。提交、回滚与过期策略可能导致属性重新加载。

## 13. add / flush / autoflush / commit 的时间线

### 13.1 `session.add()`

```python
item = Feedback(...)
session.add(item)
```

通常只将对象标记为 Pending，**不立即发送 INSERT**。

### 13.2 `session.flush()`

```python
session.flush()
print(item.id)
```

Flush 会将待处理对象变更发送到数据库，在当前事务中执行 SQL。数据库可能在此时分配主键 ID、检查唯一约束、检查外键。**此时仍然没有 COMMIT。**

### 13.3 `autoflush` 可能让查询触发写入

```python
item.title = "修改后"
result = session.scalars(select(Feedback)).all()
```

默认情况下，ORM 查询前可能自动 Flush 待处理修改。因此一个看起来“仅查询”的调用之前，可能发出 UPDATE。不能只通过是否显式写 `flush()` 判断 SQL 是否执行。

### 13.4 `session.commit()`

```python
session.commit()
```

在通常事务配置下，提交会先 Flush 需要发送的变更，再执行数据库 COMMIT。成功返回说明事务完成；连接中断发生在提交阶段时，结果可能不确定，需要额外设计查询/幂等处理，不能简单认为数据库一定回滚。

### 13.5 完整时间线

```text
t0  obj = Feedback(...)      Python 内存中新建对象（Transient）
t1  session.add(obj)       Pending；没有 INSERT
t2  session.flush()        发出 INSERT；事务内已写入但未提交
t3  session.query(...)     当前事务可读到自己的写入
t4  session.commit()       COMMIT；修改对其他事务按隔离规则可见
t5  session.close()        释放 Session 资源
```

`flush()` 与 `commit()` 绝对不能混为一谈。数据“已经进数据库的事务”与“已经成为已提交的持久记录”有本质区别。

### 13.6 `with Session(...)` 与 `with Session.begin()`

```python
with Session(engine) as session:
    session.add(item)
    # 退出时会关闭会话，不会凭空自动提交
```

而：

```python
with Session(engine) as session, session.begin():
    session.add(item)
    # 无异常则提交；有异常则回滚
```

后一种明确建立并管理事务边界。通常业务服务层应让一项业务操作落在一个清晰的事务范围中，而不是每个 Repository 方法都随意提交。

## 14. rollback 的实际边界与失败后的 Session 状态

### 14.1 可以回滚什么？

假设：

```text
先前事务：INSERT A → COMMIT
当前事务：INSERT B → FLUSH → ROLLBACK
```

结果：A 仍在数据库，B 被撤销。

事务回滚通常覆盖该数据库事务中的未提交增删改及相关事务性状态；**不会自动撤销已经提交的旧事务**，也不会撤销邮件、外部 API、文件系统写入等事务外副作用。

### 14.2 不能假设回滚后序列 ID 连续

PostgreSQL `sequence`/`IDENTITY` 的序列取值通常不受事务回滚影响。插入失败后 ID 出现空洞是正常现象，不能把自增 ID 当作连续业务序号。

### 14.3 Flush 失败后为什么还要显式 rollback？

```python
try:
    session.add(item)
    session.flush()
except IntegrityError:
    session.rollback()
    raise
```

SQLAlchemy 在 Flush 出错后会令当前事务进入失败/非活动状态。即使底层数据库事务已回滚，Session 的逻辑事务状态仍需清理；否则继续使用同一 Session，可能触发 `PendingRollbackError`。

**错误写法：**

```python
try:
    session.commit()
except Exception:
    pass
# 然后继续使用同一个 session —— 隐藏错误并可能留下失效事务
```

推荐事务上下文自动处理异常回滚，同时将错误重新传播为上层可识别的业务结果。

### 14.4 SAVEPOINT 的局部回滚

使用 `session.begin_nested()` 可在事务内为一小段工作创建保存点，并在局部错误后继续外层事务。但 `begin_nested()` 会先 Flush 既有 Pending 数据，即使关闭了通常的 `autoflush` 也如此；因此要明确哪些修改属于保存点之前，哪些属于保存点之内。

### 14.5 回滚后 Python 对象状态也要关注

已经赋值的 Python 对象不一定立即在属性层显示“旧值”，Session 可能将其标记过期，后续读取重新加载。事务回滚的关键语义是数据库提交状态，不等于任意 Python 变量都会神奇恢复到先前值。需要通过 Session 的状态管理与刷新机制处理。

## 15. 一次业务操作中的原子性和事务边界

### 15.1 原子提交的业务示例

假设“确认反馈”需要：

1. 验证反馈属于当前用户；
2. 将草稿状态修改为 `submitted`；
3. 保存一条审计事件；
4. 让用户看到提交成功。

理想的事务边界是：

```python
with Session(engine) as session, session.begin():
    feedback = session.scalar(
        select(Feedback).where(
            Feedback.id == feedback_id,
            Feedback.tenant_id == authenticated_tenant_id,
            Feedback.user_id == authenticated_user_id,
        )
    )
    if feedback is None:
        raise PermissionError("未授权访问或记录不存在")
    if feedback.status != "draft":
        raise ValueError("状态不允许提交")
    feedback.status = "submitted"
    session.add(AuditEvent(...))  # 示意：需定义相应映射表
# 退出成功后一起 COMMIT；异常时一起 ROLLBACK
```

上面的 `AuditEvent` 是设计示意，不包含在附录完整运行示例中。

**不要在某个 Repository 函数里提前 `commit()`，然后期待 Service 外层的 rollback 还能撤销它。** 服务层应拥有清晰的事务控制权。

### 15.2 外部调用应该放在哪里？

如果业务需要同时调用模型或发送邮件，不建议在长事务内长期等待外部网络请求：

- 长事务可能长期持有锁和数据库连接；
- 外部服务耗时难以预测；
- 如果外部请求成功、数据库却回滚，就产生跨系统状态不一致。

通常先在事务内保存业务状态与 Outbox 事件，然后由独立 Worker 将事件发往外部系统，并保留重试、幂等和不确定结果处理。

### 15.3 事务边界与接口响应

调用方应在**成功提交之后**收到“业务已保存”的响应。如果数据库事务没有成功提交，不应提前向用户宣告永久保存成功。对异步后台任务可以先返回 `202 Accepted`，但这仅意味着接收任务，不代表最终业务完成。

## 16. ORM 查询关联、N+1 与加载策略

### 16.1 ORM JOIN

```python
stmt = (
    select(Feedback.title, User.name)
    .join(User, Feedback.user_id == User.id)
    .where(Feedback.tenant_id == "t1")
)
rows = session.execute(stmt).all()
```

大致生成：

```sql
SELECT feedbacks.title, users.name
FROM feedbacks JOIN users ON feedbacks.user_id = users.id
WHERE feedbacks.tenant_id = ?;
```

`?` 是 SQLite 占位符，PostgreSQL 驱动可能使用其他占位格式。调用端应使用参数绑定，**不能直接用 f-string 拼接用户输入生成 SQL**。

### 16.2 ORM `relationship()` 不等于自动 JOIN

映射中定义 `relationship()` 是声明对象间的关系，它本身不会保证所有查询都自动 JOIN。加载策略决定 ORM 什么时候发 SQL。

### 16.3 N+1 问题

```python
users = session.scalars(select(User)).all()        # 1 次 SELECT
for user in users:
    print(len(user.feedbacks))                      # 可能每个用户再发 1 次 SELECT
```

若有 N 个用户，可能发出 N+1 条查询。常见优化：

```python
from sqlalchemy.orm import selectinload
users = session.scalars(
    select(User).options(selectinload(User.feedbacks))
).all()
```

`selectinload()` 通常先查询用户，再以 `IN (...)` 批量查询其关联记录，显著减少 SQL 往返；具体次数会随参数数量和数据库限制变化。

### 16.4 `joinedload()` 与 `.join()` 的区别

- `.join()`：明确改变查询来源和筛选条件，可影响结果集行数。
- `.options(joinedload(...))`：主要改变对象关系的加载方式，目标是不改变主实体查询语义。

对一对多集合使用 `joinedload()` 时，SQLAlchemy 2.x 通常要求显式 `.unique()` 去重 ORM 主对象，否则会抛错。这并不是说数据库没有重复行，而是 ORM 在构建对象结果时需要明确去重。

### 16.5 如何选择

- 一对多集合：`selectinload()` 常是较稳妥的起点。
- 多对一/一对一：`joinedload()` 往往合适。
- 复杂筛选关联：使用明确 `.join()`，必要时再指定加载策略。
- 特别大的关联集合：不要无条件一次加载所有行，考虑分页与聚合查询。

优化应基于真实 SQL 数量、行数和执行计划，而不是盲目选某个 ORM 方法。

## 17. 乐观锁、幂等写入和并发修改

### 17.1 为什么唯一键还不够？

`UNIQUE(tenant_id, request_key)` 解决“重复创建同一个业务操作”的一部分问题，但不能自动防止两个编辑者同时修改同一条反馈造成覆盖。

### 17.2 乐观锁与 SQLAlchemy

```python
class Feedback(Base):
    # 映射字段略
    version: Mapped[int] = mapped_column(Integer, nullable=False, default=1)
    __mapper_args__ = {"version_id_col": version}
```

普通 ORM 更新会比较版本，类似：

```sql
UPDATE feedbacks
SET title = ?, version = ?
WHERE id = ? AND version = ?;
```

若更新匹配不到预期版本，ORM 可以抛出 `StaleDataError`，调用方应处理冲突。注意该版本检查主要适用于 ORM Flush 管理的逐对象更新，不保证对任意直接批量 SQL 自动生效。

### 17.3 幂等性与恢复

同一 `request_key` 重试时，数据库唯一约束防止重复记录；真正可靠的幂等 API 还应确认重试内容与首次请求是否相同，并将同键不同内容视为冲突，而不是直接默默返回旧成功结果。

### 17.4 防止跨用户或跨租户修改

```sql
UPDATE feedbacks
SET title = :title
WHERE id = :id
  AND tenant_id = :tenant_id
  AND user_id = :user_id;
```

后端身份必须来自已认证上下文，而不是信任用户自己传入的 `user_id`/`tenant_id`。检查影响行数并考虑对象版本；同样的授权边界也应应用于查询和删除。

## 18. SQL 调试、参数化查询与工程排错

### 18.1 打印 ORM 实际执行的 SQL

```python
engine = create_engine(DB_URL, echo=True)
```

`echo=True` 适合本地开发时查看 SQL 和参数。生产环境需要结构化日志与脱敏措施，不能无控制地输出密码、Token、邮箱和用户消息。

亦可使用 SQLAlchemy 事件捕获语句，例如 `before_cursor_execute`；可用于计数、追踪 N+1，但回调本身也有开销。

### 18.2 查询对象与最终 SQL

```python
stmt = select(Feedback).where(Feedback.tenant_id == "t1")
print(stmt.compile(engine))
```

编译出来的是针对指定方言的 SQL；可选的“把字面量直接内联”模式只用于受控调试，不应用于执行不可信输入，更不能把敏感字面量打印到生产日志。

### 18.3 参数绑定防止 SQL 注入

```python
sql = text("SELECT id FROM feedbacks WHERE title = :title")
rows = session.execute(sql, {"title": user_supplied_text}).all()
```

参数绑定把输入作为值传递，而不是当作 SQL 代码解释。表名、列名等 SQL 标识符不能靠普通值绑定随意替换，动态标识符应使用受控白名单或安全构造器。

### 18.4 从错误反向定位

| 现象 | 优先检查 |
|---|---|
| Python 对象已修改，但数据库没变 | 是否 `flush`、是否 `commit`、是否在另一事务读 |
| 业务认为成功，刷新网页后记录不见 | 是否提前返回、事务回滚、提交失败 |
| 抛出唯一约束异常 | 是否重复请求、并发竞态、错误幂等键设计 |
| 查询很慢 | SQL 数量、JOIN 基数、执行计划、索引、锁等待 |
| Session 再次查询时报 `PendingRollbackError` | 前一次 Flush 是否失败，是否未显式回滚 |
| 批量更新覆盖了别人的修改 | 是否缺少版本条件或锁机制 |
| 回滚后仍收到邮件 | 外部副作用不属于数据库事务 |
| 部分数据写入、部分没有 | 是否曾在多个地方独立 `commit()` |

### 18.5 正确理解 SQL 日志的事务边界

日志中的 `BEGIN (implicit)`、`INSERT`、`COMMIT`、`ROLLBACK` 是判断实际执行顺序的重要依据。但不同数据库驱动在开始事务的语义、SQL 输出格式和日志时间上存在差异；一定要结合使用的数据库和 Session 生命周期理解。

## 21. 常见误区与知识关系总结

1. **误区：`session.add()` 就写入数据库。** 实际上通常只成为 Pending；需要 Flush 才发出 INSERT。
2. **误区：`flush()` 就保存成功。** Flush 在事务内执行 SQL，仍可能被回滚。
3. **误区：查询只会发 SELECT。** ORM 的 autoflush 可能在查询前发 INSERT/UPDATE/DELETE。
4. **误区：`with Session(...)` 退出会自动 commit。** 普通 Session 上下文主要负责资源关闭；需要明确事务上下文。
5. **误区：出现 IntegrityError 后可以直接继续查询。** Session 需要回滚以清理失败事务状态。
6. **误区：唯一性只靠查询检查就够了。** 并发下必须依赖数据库唯一约束等机制作为最终防线。
7. **误区：索引越多越好。** 索引有维护和写入成本，优化需要执行计划。
8. **误区：ORM 关系属性自动意味着 JOIN。** 关系加载和查询 JOIN 是不同概念。
9. **误区：事务回滚能撤销任何副作用。** 它通常只能回滚本数据库事务管理的修改。
10. **误区：一个业务流程里每调用一次 Repository 都应该提交。** 提交边界应该按照一个完整的业务不变量来设计。
11. **误区：`PRIMARY KEY` 和 `FOREIGN KEY` 代表授权。** 标识与引用完整性不等于权限。
12. **误区：Serializable 不会失败。** 高隔离级别可能通过主动中止事务来保持一致性；程序需要正确重试完整事务。

### 21.1 一张知识地图

```text
业务目标与数据约束
  ├─ 表结构、主键、外键、唯一约束、CHECK
  ├─ SQL SELECT / JOIN / GROUP BY / ORDER BY
  ├─ 索引 → 执行计划 → 查询性能
  └─ 事务边界
      ├─ BEGIN
      ├─ ORM 追踪对象状态
      │   ├─ add → Pending（内存）
      │   ├─ flush → 真实 SQL（事务内）
      │   └─ commit → 提交成功
      ├─ rollback → 撤销本事务未提交的数据库修改
      ├─ 隔离级别 / 锁 / 版本号 → 管理并发
      └─ Outbox / 幂等 → 处理数据库之外的副作用
```

**最终应形成的理解**：读到一个 Python ORM 方法时，能够沿着对象映射找到实际表与约束，识别它会生成哪类 SQL、何时发送、谁负责提交、异常在哪一层发生，以及失败时哪些修改会回滚、哪些操作不会回滚。

```python
"""SQLAlchemy 2.x + SQLite 的教学示例；非生产服务。"""
from __future__ import annotations

from sqlalchemy import (
    CheckConstraint, ForeignKey, Index, Integer, String,
    UniqueConstraint, create_engine, event, func, select,
)
from sqlalchemy.orm import DeclarativeBase, Mapped, Session, mapped_column, relationship


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "users"
    __table_args__ = (
        UniqueConstraint("tenant_id", "email", name="uq_user_tenant_email"),
    )
    id: Mapped[int] = mapped_column(primary_key=True)
    tenant_id: Mapped[str] = mapped_column(String(40), nullable=False)
    email: Mapped[str] = mapped_column(String(255), nullable=False)
    name: Mapped[str] = mapped_column(String(80), nullable=False)
    feedbacks: Mapped[list[Feedback]] = relationship(back_populates="user")


class Feedback(Base):
    __tablename__ = "feedbacks"
    __table_args__ = (
        UniqueConstraint("tenant_id", "request_key", name="uq_feedback_request"),
        CheckConstraint("status IN ('draft', 'submitted', 'closed')", name="ck_feedback_status"),
        Index("ix_feedback_tenant_status", "tenant_id", "status"),
        Index("ix_feedback_user_id", "user_id"),
    )
    id: Mapped[int] = mapped_column(primary_key=True)
    tenant_id: Mapped[str] = mapped_column(String(40), nullable=False)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), nullable=False)
    request_key: Mapped[str] = mapped_column(String(80), nullable=False)
    title: Mapped[str] = mapped_column(String(200), nullable=False)
    status: Mapped[str] = mapped_column(String(20), nullable=False, default="draft")
    version: Mapped[int] = mapped_column(Integer, nullable=False, default=1)
    user: Mapped[User] = relationship(back_populates="feedbacks")
    __mapper_args__ = {"version_id_col": version}


def make_engine(url: str, echo: bool = False):
    engine = create_engine(url, echo=echo)
    if engine.dialect.name == "sqlite":
        @event.listens_for(engine, "connect")
        def enable_foreign_keys(dbapi_connection, _connection_record):
            cursor = dbapi_connection.cursor()
            cursor.execute("PRAGMA foreign_keys = ON")
            cursor.close()
    return engine


def init_schema(engine):
    Base.metadata.create_all(engine)


def create_feedback(
    session: Session, *, tenant_id: str, user_id: int,
    request_key: str, title: str, status: str = "draft",
) -> Feedback:
    """只安排 ORM 写入，不在此提交事务；调用方负责事务边界。"""
    item = Feedback(
        tenant_id=tenant_id, user_id=user_id,
        request_key=request_key, title=title, status=status,
    )
    session.add(item)
    return item


def feedbacks_with_users(session: Session, tenant_id: str):
    return session.execute(
        select(Feedback.title, User.name)
        .join(User, Feedback.user_id == User.id)
        .where(Feedback.tenant_id == tenant_id)
        .order_by(Feedback.id)
    ).all()


def feedback_count_by_user(session: Session, tenant_id: str):
    return session.execute(
        select(User.name, func.count(Feedback.id).label("count"))
        .outerjoin(Feedback, Feedback.user_id == User.id)
        .where(User.tenant_id == tenant_id)
        .group_by(User.id, User.name)
        .order_by(User.id)
    ).all()


if __name__ == "__main__":
    engine = make_engine("sqlite+pysqlite:///:memory:", echo=True)
    init_schema(engine)
    with Session(engine) as session, session.begin():
        user = User(tenant_id="demo", email="alice@example.test", name="Alice")
        session.add(user)
        session.flush()  # 获得 user.id；此时仍未提交
        create_feedback(
            session, tenant_id="demo", user_id=user.id,
            request_key="req-1", title="技能文本错误",
        )
    with Session(engine) as session:
        print("JOIN 查询：", feedbacks_with_users(session, "demo"))
        print("LEFT JOIN + GROUP BY：", feedback_count_by_user(session, "demo"))
    engine.dispose()
```

    def test_01_add_has_no_insert_until_flush(self):

        def track(_conn, _cursor, stmt, _params, _context, _many): statements.append(stmt)

                self.assertEqual([q for q in statements if q.lstrip().startswith("INSERT")], [])
                s.rollback()
        finally:

            self.assertIsNotNone(obj.id)
            self.assertEqual(s.scalar(select(func.count(Feedback.id))), 1)

                self.assertEqual(observer.scalar(select(func.count(Feedback.id))), 0)

    def test_20_selectinload_reduces_n_plus_one(self):

            self.add_feedback(f"k{idx}", user=uid, tenant="t2" if uid == self.c else "t1")

                queries.append(stmt)
        event.listen(self.engine, "before_cursor_execute", track)
        try:
            with Session(self.engine) as s:
                users = s.scalars(select(User)).all()
                _ = [len(u.feedbacks) for u in users]
            lazy_count = len(queries)
            queries.clear()
            with Session(self.engine) as s:
                users = s.scalars(select(User).options(selectinload(User.feedbacks))).all()
                _ = [len(u.feedbacks) for u in users]
            eager_count = len(queries)
        finally:
            event.remove(self.engine, "before_cursor_execute", track)
        self.assertEqual(lazy_count, 4)
        self.assertEqual(eager_count, 2)

        self.add_feedback("k1")
