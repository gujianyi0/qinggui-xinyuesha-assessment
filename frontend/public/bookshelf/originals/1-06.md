## 1. 为什么网络客户端与数据库连接必须管理生命周期

Web 服务不是一个执行一次就退出的脚本。它持续接收请求，并反复调用模型 API、业务接口和数据库。

一次模型请求表面上像 `await client.post(...)`，实际涉及 DNS 查询、TCP 连接、可能的 TLS 握手、发送 HTTP 请求、接收响应、读取响应体，以及连接能否被后续请求复用。一次数据库操作也可能涉及从连接池获取连接、开始事务、发送 SQL、获取结果、提交或回滚、归还连接。

在每次调用时重新建立网络连接，会增加连接建立成本与系统资源消耗；在连接不用后忘记释放，则可能消耗文件描述符、套接字、数据库连接数和内存。

必须区分三个动作：

- **复用（reuse）**：相同资源供连续或并发请求使用，减少重复初始化。
- **归还（release / return to pool）**：一次操作结束，把占用的连接交还连接池，连接可能仍保持打开。
- **关闭（close / dispose）**：结束资源生命周期，不再继续使用对应资源或池。

它们并不相同。把数据库 Session 关闭，通常不是把整个数据库 Engine 关闭；把 HTTP 响应体读取完，也不等于关闭 HTTP 客户端。

### 1.1 资源所有权原则

正确的资源设计必须回答：

1. 谁创建资源？
2. 谁能够共享它？
3. 谁负责关闭它？
4. 什么时候关闭？
5. 关闭时是否仍有人使用？

常见分层是：

```text
进程 / ASGI 应用生命周期
├── HTTPX AsyncClient             长生命周期，共享连接池
├── SQLAlchemy AsyncEngine        长生命周期，共享数据库连接池
├── async_sessionmaker           长生命周期，共享工厂
└── 应用级任务管理器               管理自行创建的后台 Task
    ├── HTTP 请求 A
    │   ├── HTTP 调用             临时借用 HTTP 客户端
    │   └── AsyncSession A       当前请求独占，不与并发任务共享
    ├── HTTP 请求 B
    │   └── AsyncSession B       与 A 完全独立
    └── 后台任务 C
        └── AsyncSession C       自行创建和关闭
```

注意：**共享的是能够协调连接池的 Engine、客户端和工厂，不是共享单个数据库事务状态。**

## 2. HTTP 连接的实际生命周期

### 2.1 为什么复用连接

以常见 HTTPS 请求为例，一个未缓存、未建立连接的请求可能先经过 DNS、TCP 建连、TLS 握手，然后才能发送 HTTP 数据。保持可复用的连接能够避免某些后续请求重复付出建立连接的成本。

HTTP/1.1 的 Keep-Alive 允许后续请求在符合条件时重用连接；HTTP/2 在支持并协商成功时可在同一连接上复用多个流。连接能否复用还受到服务器响应、空闲超时、连接错误、代理和客户端配置的影响。

复用连接不等于所有请求永远共享一个物理连接。HTTP 客户端通常同时管理多个连接，并按照目标地址、协议和池上限决定如何使用它们。

### 2.2 HTTPX 的客户端层次

```python
import httpx

# 每次调用顶层 API：方便，但不利于长期服务的连接池复用
response = httpx.get("https://example.com")

# 长期运行的异步服务：创建并复用一个 AsyncClient
async with httpx.AsyncClient() as client:
    first = await client.get("https://example.com/a")
    second = await client.get("https://example.com/b")
```

`AsyncClient` 管理底层连接池，支持异步请求，并可在多个并发任务间共享。**不要在频繁执行的每次 API 调用内部都创建一个新的 `AsyncClient`**，否则容易失去连接复用的主要收益。

错误倾向：

```python
async def call_model(prompt: str):
    async with httpx.AsyncClient() as client:
        return await client.post("https://model.example/api", json={"prompt": prompt})
```

在一个短期脚本中这是合法的资源管理，但在高频 Web 请求中通常不是最佳选择。

更适合长期服务：

```python
class ModelAPI:
    def __init__(self, client: httpx.AsyncClient):
        self._client = client

    async def generate(self, prompt: str) -> dict:
        response = await self._client.post(
            "https://model.example/api", json={"prompt": prompt}
        )
        response.raise_for_status()
        return response.json()
```

这里只是演示依赖传递。`ModelAPI` 不应在每次调用后关闭由整个应用共享的 `client`；关闭责任属于创建它的应用生命周期管理器。

### 2.3 HTTP 连接池的关键参数

HTTPX 的 `Limits` 常见选项：

- `max_connections`：允许的最大连接总数（针对该客户端连接池）。
- `max_keepalive_connections`：最多保留多少空闲的 Keep-Alive 连接。
- `keepalive_expiry`：空闲连接能保持多久才过期。

```python
limits = httpx.Limits(
    max_connections=40,
    max_keepalive_connections=15,
    keepalive_expiry=20.0,
)

client = httpx.AsyncClient(limits=limits)
```

这是客户端实例的参数，不是进程内所有 HTTP 客户端共享的全局限制，更不是模型服务商的 QPS 限制。

**连接池大小 ≠ 模型并发配额 ≠ 请求频率限制。** 一个连接上可能发生不同的 HTTP 协议行为；等待连接池也不等于已经访问到了模型服务器。

### 2.4 连接池的超时

HTTPX 区分四类常见超时：

| 类型 | 所限制的阶段 | 常见异常 |
|---|---|---|
| `connect` | 建立连接 | `ConnectTimeout` |
| `read` | 等待下一块响应数据 | `ReadTimeout` |
| `write` | 写入请求数据 | `WriteTimeout` |
| `pool` | 等待从连接池取得可用连接 | `PoolTimeout` |

```python
client = httpx.AsyncClient(
    timeout=httpx.Timeout(
        connect=3.0,
        read=30.0,
        write=10.0,
        pool=2.0,
    ),
    limits=httpx.Limits(max_connections=40),
)
```

注意：`read` 超时通常是两次接收数据之间的最长等待时间，不等于整个模型请求的绝对最长时长。一个长时间持续输出数据的模型响应可能不会触发 `read` 超时，却依然需要**请求总时限**控制，例如 `asyncio.timeout()`。

### 2.5 流式响应与连接泄漏

对于 LLM 流式输出，最重要的是确保响应关闭：

```python
async def read_stream(client: httpx.AsyncClient) -> list[str]:
    chunks = []
    async with client.stream("GET", "https://example.com/stream") as response:
        response.raise_for_status()
        async for chunk in response.aiter_text():
            chunks.append(chunk)
    return chunks
```

`async with client.stream(...)` 离开时会关闭对应响应，即使在正文读取中出现正常异常或协作式取消，也能执行其上下文退出逻辑。

如果采用 `client.send(request, stream=True)` 手动流模式，就必须显式安排 `await response.aclose()`；否则连接可能一直处于被占用状态。

### 2.6 什么时候关闭 AsyncClient

- 一次性脚本：在 `async with` 块结束时关闭。
- FastAPI Web 服务：在应用 `lifespan` 启动时创建，在关闭阶段调用 `await client.aclose()`，或由应用级 `async with` 管理。
- 独立 Worker：在 Worker 初始化时创建，在 Worker 停止时关闭。

**不要在请求函数内关闭其他请求仍在使用的共享客户端。**

## 3. 数据库连接池与 HTTP 连接池的异同

### 3.1 数据库连接为什么需要池

数据库连接不是廉价的纯 Python 对象。建立连接需要网络交互、服务端认证和数据库服务器资源。若每个请求都创建并销毁物理数据库连接，会增加延迟和数据库负担。

数据库连接池维护一组可复用的连接；业务操作向池借用连接，执行完毕后归还。

典型过程：

```text
请求 A 进入
   ↓
创建 Session A
   ↓
需要执行 SQL 时，向 Engine 连接池借用连接
   ↓
BEGIN / SELECT / UPDATE / COMMIT 或 ROLLBACK
   ↓
关闭 Session A，归还其持有的连接
   ↓
连接仍可能保留在池中供请求 B 使用
```

ORM 的 Session 本身不是 TCP 连接的代名词。Session 维护 ORM 对象、事务和数据库访问状态，并在需要时取得实际连接。

### 3.2 区分 Engine、Pool、Session、Connection、Transaction

| 名称 | 角色 | 推荐生命周期 |
|---|---|---|
| `AsyncEngine` | 数据库访问入口与连接池所有者 | 每个应用进程中的较长生命周期 |
| `Pool` | 管理数据库物理连接 | 随 Engine 存活 |
| `async_sessionmaker` | 生产 AsyncSession 的工厂 | 可跨请求共享 |
| `AsyncSession` | ORM 状态与数据库事务工作单元 | 通常每请求或每独立任务一个 |
| `AsyncConnection` | 某个数据库连接的操作接口 | 在具体数据库操作作用域内使用 |
| Transaction | 一组需要一致性保障的数据库操作 | 尽可能短，明确提交或回滚 |

### 3.3 正确创建和使用 SQLAlchemy 异步资源

```python
from sqlalchemy.ext.asyncio import (
    create_async_engine,
    async_sessionmaker,
    AsyncSession,
)

engine = create_async_engine(
    "postgresql+asyncpg://app:password@127.0.0.1:5432/game",
    pool_size=10,
    max_overflow=5,
    pool_timeout=5,
    pool_pre_ping=True,
)

SessionFactory = async_sessionmaker(
    engine,
    expire_on_commit=False,
)

async def read_data():
    async with SessionFactory() as session:
        # session.execute(...) 及业务逻辑
        ...

async def close_database():
    await engine.dispose()
```

上例要求安装 SQLAlchemy 与 PostgreSQL 异步驱动（例如 `asyncpg`），并且数据库真实可连接。连接串中的凭据仅为示意；实际应通过环境变量或密钥管理服务提供。

注意：**`create_async_engine()` 产生 Engine 并配置连接池，不意味着马上建立了全部数据库连接。** 实际连接通常在首次借用时按需创建。

### 3.4 为什么不能共享单个 AsyncSession

错误：

```python
shared_session = SessionFactory()

async def job_a():
    await shared_session.execute(...)

async def job_b():
    await shared_session.execute(...)

await asyncio.gather(job_a(), job_b())
```

两个并发任务使用同一个 `AsyncSession`，可能互相影响事务和 ORM 状态。SQLAlchemy 明确说明 `AsyncSession` 是可变、有状态的对象，不适合在并发任务之间不加协调地共享。

正确：

```python
async def job_a():
    async with SessionFactory() as session:
        await session.execute(...)

async def job_b():
    async with SessionFactory() as session:
        await session.execute(...)

await asyncio.gather(job_a(), job_b())
```

两个任务都能从同一个 Session 工厂创建自己的 Session，同时 Engine 仍在后台复用数据库连接池。

### 3.5 事务边界与 HTTP 调用边界

不推荐：

```python
async with SessionFactory.begin() as session:
    # 数据库事务已经开始
    await session.execute(...)
    model_result = await http_client.post("https://model.example/api", ...)
    await session.execute(...)
```

如果模型 API 等待 30 秒，可能导致数据库事务也持续占用 30 秒以上，产生长事务、连接占用和锁等待问题。

更常见的设计是：

1. 用一次短 Session 读取输入所需数据，结束该数据库作用域；
2. 在数据库事务外调用模型 API；
3. 再用独立的短事务写回结果；
4. 用版本号或并发控制条件检查读取与写入之间是否发生状态变化。

这样可以缩短数据库事务，但**也引入跨阶段一致性问题**：调用模型期间，其他请求可能已经修改了数据，所以写入前还需要检查业务状态。

数据库事务只能保障数据库内的事务行为，不能自动撤销已经发送出去的 HTTP 请求、邮件或模型费用。

### 3.6 常见数据库连接池参数

`pool_size=10`：池通常允许保留最多 10 个常规连接。

`max_overflow=5`：高峰时可额外建立一定数量的临时连接；因此本示例的同时连接上界可达到约 15 个（取决于池实现和配置）。

`pool_timeout=5`：当池无法及时提供连接时，最多等待约 5 秒，然后抛出池相关超时错误。

`pool_pre_ping=True`：借出连接前进行可用性检查，有助于发现已经断开的空闲连接。

`pool_recycle`：连接达到指定年龄后，在下一次取出时触发更换，不会抢夺任务正在使用的连接。

**`pool_pre_ping` 无法恢复已经执行到一半的事务。** 如果数据库在 SQL 执行期间断开，当前事务仍可能失败，应用需要决定是否能安全地重试整个业务操作。

### 3.7 连接池容量计算

假设应用部署 4 个 Uvicorn Worker，每个 Worker 创建一个 Engine，配置：

```text
pool_size = 10
max_overflow = 5
```

理论上单个应用部署最多可能使用大约：

```text
4 × (10 + 5) = 60 个数据库连接
```

这还未计入其他服务、管理工具、后台 Worker、数据库保留连接和故障转移等因素。

因此，连接池容量必须按照**每进程实例数 × 每进程连接上限**估算，而不是只看单个 Engine 的配置。

### 3.8 什么叫关闭 Session，什么叫释放 Engine

```python
async with SessionFactory() as session:
    result = await session.execute(...)
# 离开代码块后关闭 Session / 归还其占用的资源
```

```python
await engine.dispose()
# 释放 Engine 所维护的连接池资源
```

`AsyncEngine.dispose()` 主要清理池中已归还的连接；如果某些连接仍被活动任务借出，默认 `dispose()` 不保证立即关闭那些正在使用的连接。因此在应用停止时，应当先处理使用这些连接的任务和 Session，再释放 Engine。

## 4. FastAPI `lifespan`：资源初始化和统一关闭

### 4.1 为什么使用 lifespan

在 FastAPI 中，`lifespan` 可把“应用启动前创建共享资源”和“应用停止后释放共享资源”放在同一作用域中。

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI
import httpx

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with httpx.AsyncClient() as client:
        app.state.http_client = client
        yield
        # 退出 async with 时自动关闭客户端

app = FastAPI(lifespan=lifespan)
```

`yield` 之前属于应用初始化阶段；`yield` 之后属于关闭阶段。FastAPI 推荐在共享资源初始化和关闭时采用此方式。

### 4.2 用 AsyncExitStack 管理多个资源

`AsyncExitStack` 在资源初始化失败或应用退出时，可以集中管理多个资源的清理回调：

```python
from contextlib import asynccontextmanager, AsyncExitStack
import httpx
from fastapi import FastAPI
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

DB_URL = "postgresql+asyncpg://app:password@127.0.0.1:5432/game"

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with AsyncExitStack() as stack:
        engine = create_async_engine(DB_URL, pool_pre_ping=True)
        stack.push_async_callback(engine.dispose)

        client = await stack.enter_async_context(
            httpx.AsyncClient(timeout=20.0)
        )

        app.state.engine = engine
        app.state.session_factory = async_sessionmaker(
            engine, expire_on_commit=False
        )
        app.state.http_client = client

        yield
        # AsyncExitStack 先关闭 HTTP 客户端，再 dispose Engine

app = FastAPI(lifespan=lifespan)
```

适用于需要一次性初始化一组共享资源的服务。该示例仅演示资源的创建和清理；**如果服务还自行创建后台任务，必须在 Stack 退出之前先让那些任务完成或停止**。

### 4.3 资源创建顺序与清理顺序

一般遵循：

- 启动：先创建基础依赖，再创建依赖它们的服务。
- 停止：先停用依赖这些资源的任务，再释放资源本身。
- 若资源 A 依赖资源 B，通常先关闭 A，再关闭 B。

例如：

```text
启动：数据库 Engine → HTTP Client → Worker Task
停止：Worker Task → HTTP Client → 数据库 Engine
```

实际关闭顺序应由依赖关系决定，而不是固定记忆顺序。

### 4.4 为什么不是每个请求一个 Engine

错误架构：

```python
@app.get("/records")
async def records():
    engine = create_async_engine(DB_URL)
    ...
    await engine.dispose()
```

这相当于每个请求都重新建立并销毁自己的连接池，可能浪费资源并增加数据库连接压力。

更合理：应用初始化一次 Engine；每个请求创建自己的 Session，查询结束后归还连接；应用关闭时 dispose Engine。

## 5. 服务停止时，究竟有哪些“在途任务”

**在途任务（in-flight task）**指在收到停止信号时尚未完成的工作。它可能分属于不同的生命周期，不能一概而论。

| 类型 | 示例 | 谁负责管理 |
|---|---|---|
| HTTP 请求任务 | 用户正在等待一次模型回答 | ASGI 服务器 + 应用请求代码 |
| HTTP 流式响应 | 模型正在逐块返回文本 | ASGI 服务器、StreamingResponse 和应用生成器 |
| 框架后台任务 | 响应发送后执行的 Starlette / FastAPI BackgroundTask | ASGI 框架与服务器（仍属进程内任务） |
| 自建 `asyncio.Task` | `asyncio.create_task(import_doc())` | 创建该任务的应用或自建管理器 |
| 外部 Worker 任务 | Kafka 消费者索引文档 | Worker 进程和消息队列体系 |
| 数据库执行中事务 | 正在读取或提交数据 | 使用该事务的 Session / Worker |

最危险的误解是：**HTTP 请求返回成功、后台任务开始运行，就意味着这个任务已经可靠保存。**

一个纯内存的 `asyncio.Task` 在进程被强制结束后无法自动继续；需要跨重启可靠执行的任务，应使用持久化任务记录、消息队列、状态机和幂等机制。

## 6. 优雅停机（Graceful Shutdown）的顺序

### 6.1 为什么不能直接关闭连接池

假设请求 A 正在执行：

```text
任务 A：调用模型 API ────────────→ 准备写 PostgreSQL
                                  ↑
服务关闭：立即关闭 HTTP / DB 资源
```

如果服务在任务完成前就释放相关资源，任务 A 可能在下一次访问数据库或网络时失败，导致结果丢失、状态不一致或留下未完成任务。

正确原则：**先停止新工作进入，再允许在途工作完成或协作式取消，最后关闭共享资源。**

### 6.2 推荐的关闭阶段

```text
T0  收到停止请求（正常部署或终止信号）
 │
 ├─ 1. 停止接收新 HTTP 连接 / 从负载均衡摘除或准备摘除
 ├─ 2. 禁止接收新的内部后台任务
 ├─ 3. 等待已有 HTTP 请求完成，设置总宽限期
 ├─ 4. 对超出宽限期的任务提出取消请求
 ├─ 5. 等待任务执行 finally、回滚事务、关闭流等清理
 ├─ 6. 确保任务状态可恢复（若需要跨重启）
 ├─ 7. 关闭 HTTP 客户端、数据库 Session / Engine 和其他资源
 └─ 8. 进程退出
```

这是逻辑顺序。Uvicorn 的实现中，接收到正常关闭信号后会先停止接收新的连接，等待在途请求与受管理的后台任务，再触发应用 `lifespan.shutdown`。所以**当 `lifespan` 的 `yield` 后代码开始运行时，Uvicorn 的常规 HTTP 请求排空阶段通常已经发生**。

该顺序不保证任何情况下请求都能完成：进程被强制杀死、宿主机断电、Docker/Kubernetes 宽限期不足，以及取消不响应等情况仍可导致工作中断。

### 6.3 关闭超时是外层约束

例如启动时：

```bash
uvicorn app:app --timeout-graceful-shutdown 30
```

Uvicorn 会在配置的宽限时间内尽量完成请求和任务，超时后进入取消/终止阶段。`--timeout-keep-alive` 则是空闲 Keep-Alive 连接的超时，不是应用停机总宽限期。

另外应确保部署环境的实际停止宽限期覆盖服务器请求排空和资源清理的预期时间，否则外层进程管理器可能在清理完成前强制终止进程。

### 6.4 `lifespan` 不是万能“请求排空入口”

`lifespan` 的关闭代码不是在收到 SIGTERM 的瞬间就必定执行。通常 Uvicorn 会先处理已有请求，然后进入 `lifespan` 关闭阶段。

因此：

- **HTTP 请求排空**首先由 Uvicorn 管理；必要时与负载均衡器的摘流流程协调。
- **应用自建任务排空**需要自建 Task 集合或任务组进行管理。
- **跨进程可靠任务**应交给持久化任务系统。
- `lifespan` 负责在合适阶段释放应用资源，而非替代进程信号处理和流量接入控制。

## 7. 用纯 asyncio 管理应用自行创建的任务

对于短期、允许在进程退出时中断的任务，可以建立一个简单任务管理器。这不具备跨重启持久化能力。

```python
import asyncio
import logging
from collections.abc import Coroutine
from typing import Any

logger = logging.getLogger(__name__)

class TaskRegistry:
    def __init__(self) -> None:
        self._tasks: set[asyncio.Task[Any]] = set()
        self._stopping = False

    @property
    def active_count(self) -> int:
        return len(self._tasks)

    def spawn(self, coro: Coroutine[Any, Any, Any]) -> asyncio.Task[Any]:
        if self._stopping:
            # 如果已经创建了协程对象却拒绝调度，必须关闭它，避免警告
            coro.close()
            raise RuntimeError("服务正在关闭，不接受新后台任务")

        task = asyncio.create_task(coro)
        self._tasks.add(task)
        task.add_done_callback(self._on_done)
        return task

    def _on_done(self, task: asyncio.Task[Any]) -> None:
        self._tasks.discard(task)
        if not task.cancelled():
            try:
                task.result()  # 读取结果；任务失败时在这里记录异常
            except Exception:
                logger.exception("后台任务执行失败")

    async def shutdown(
        self, grace_seconds: float = 15.0,
        cancel_wait_seconds: float = 3.0,
    ) -> bool:
        self._stopping = True
        pending = set(self._tasks)
        if not pending:
            return True

        _, pending = await asyncio.wait(pending, timeout=grace_seconds)
        if not pending:
            return True

        for task in pending:
            task.cancel()

        _, still_pending = await asyncio.wait(
            pending, timeout=cancel_wait_seconds
        )
        if still_pending:
            logger.error(
                "取消后仍有 %d 个任务未结束；不能保证清理完成",
                len(still_pending),
            )
            return False
        return True
```

此管理器具备四个性质：

1. 使用强引用集合持有尚未完成的任务。
2. 任务完成后自动移出集合并获取异常结果。
3. 关闭时禁止创建新任务。
4. 在两个有限的等待窗口中先等待完成，再尝试协作式取消。

但也存在明确限制：

- 不能保存任务进度，也不能在进程重启后恢复任务。
- 不负责 HTTP 请求任务，这些由 ASGI 服务器管理。
- `task.cancel()` 只是取消请求，任务可能仍不结束。
- 如果取消后仍有运行中的任务，直接关闭其正在使用的共享资源存在风险。此时必须记录异常情况，交给部署层处理残留进程，或把任务迁移到有持久化和恢复能力的系统。
- `TaskRegistry` 的内存状态只属于当前进程；多 Worker 不会共享。

**因此，管理器的 `shutdown()` 返回 `False` 是明确的“不完全关闭”状态，不应被当成成功清理。**

## 8. 取消、回滚与清理的正确关系

### 8.1 asyncio 取消是协作式的

`Task.cancel()` 会请求任务在后续可取消的等待点抛出 `asyncio.CancelledError`。如果任务正在执行阻塞式 `time.sleep()` 或不会响应取消的同步操作，它可能不能及时中断。

```python
import asyncio

async def write_result(session):
    try:
        async with session.begin():
            await session.execute(...)
    except asyncio.CancelledError:
        # 退出事务上下文时会按其语义进行必要清理/回滚
        # 在这里可以补充不会破坏取消语义的记录
        raise
    finally:
        # 当前作用域的本地清理
        ...
```

注意此片段是异常传播示意，不能直接执行（省略了具体 SQL）。

通常应让 `CancelledError` 继续向上传播。吞掉取消会破坏关闭阶段对任务结果和退出状态的判断。

### 8.2 事务在什么时候回滚

当 `async with session.begin()` 正常离开时提交；发生异常时回滚未提交事务，并最终释放 Session 使用的资源。

需要区别：

- **已经 commit 的结果**：一般不会因为之后取消而自动撤销。
- **尚未提交的数据库事务**：通常可以在退出事务上下文时回滚；异常断线时由数据库连接/事务机制处理。
- **已经完成的外部 HTTP 请求**：无法通过本地数据库 rollback 自动撤销。
- **已经发送的邮件、支付、消息**：可能需要幂等键、补偿操作和状态查询。

### 8.3 取消发生在 commit 期间

一个更微妙的故障场景是：客户端等待 commit 返回期间网络断开，应用未收到成功响应。此时应用可能不知道数据库是否已经提交成功。

不能简单地假设“发生异常就一定没有提交”，否则重新执行可能造成重复业务记录。典型解决方式包括：业务幂等键、唯一约束、可查询的事务结果和重试前核对状态。

### 8.4 `asyncio.shield()` 不提供数据持久化

`asyncio.shield()` 可以阻止外层取消请求直接传递给被保护的子任务，但不能抵抗进程被终止，也不会自动保证子任务完成。且外层等待仍可能得到 `CancelledError`。

因此，不应该把 `shield()` 当作“重要数据一定写入”的通用方案。

## 9. FastAPI 组合示例：共享 HTTPX 与 SQLAlchemy，并处理后台 Task

下面展示一个应用结构。数据库部分需要真实 PostgreSQL 和 `asyncpg`；模型 URL 是示意，不可直接作为真实服务访问。示例展示资源归属和控制流程，未声明生产环境已经测试通过。

```python
# app.py
import asyncio
import logging
import os
from contextlib import asynccontextmanager, AsyncExitStack

import httpx
from fastapi import FastAPI, HTTPException, Request
from pydantic import BaseModel, Field
from sqlalchemy import text
from sqlalchemy.ext.asyncio import (
    create_async_engine, async_sessionmaker,
)

logger = logging.getLogger(__name__)
DB_URL = os.environ["DATABASE_URL"]
MODEL_URL = os.environ["MODEL_URL"]

class AskRequest(BaseModel):
    prompt: str = Field(min_length=1)

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with AsyncExitStack() as stack:
        engine = create_async_engine(
            DB_URL,
            pool_size=10,
            max_overflow=5,
            pool_timeout=5,
            pool_pre_ping=True,
        )
        stack.push_async_callback(engine.dispose)

        client = await stack.enter_async_context(
            httpx.AsyncClient(
                timeout=httpx.Timeout(
                    connect=3, read=20, write=10, pool=3
                ),
                limits=httpx.Limits(
                    max_connections=40,
                    max_keepalive_connections=15,
                ),
            )
        )

        app.state.http = client
        app.state.sessions = async_sessionmaker(
            engine, expire_on_commit=False
        )
        app.state.background = TaskRegistry()

        try:
            yield
        finally:
            # 对自行创建的、进程内后台 Task 进行排空和取消
            drained = await app.state.background.shutdown(
                grace_seconds=15, cancel_wait_seconds=3
            )
            if not drained:
                logger.error("仍有后台 Task 未停止；服务并非完全优雅退出")
            # 随后由 AsyncExitStack 执行 client.aclose() / engine.dispose()

app = FastAPI(lifespan=lifespan)

@app.get("/health/live")
async def live():
    return {"alive": True}

@app.get("/database/check")
async def database_check(request: Request):
    async with request.app.state.sessions() as session:
        result = await session.execute(text("SELECT 1"))
        return {"db": result.scalar_one()}

@app.post("/model/ask")
async def ask(body: AskRequest, request: Request):
    try:
        async with asyncio.timeout(25):
            response = await request.app.state.http.post(
                MODEL_URL, json={"prompt": body.prompt}
            )
            response.raise_for_status()
            return response.json()
    except (httpx.TimeoutException, TimeoutError):
        raise HTTPException(504, detail="模型请求超时")
    except httpx.HTTPError:
        logger.exception("模型服务通信失败")
        raise HTTPException(502, detail="模型服务暂不可用")
```

`TaskRegistry` 使用第 7 节定义的类，实际工程应把它放在独立模块并导入。

这个例子能够说明：

- HTTP 客户端与 Engine 的作用域是**应用生命周期**。
- 每次数据库调用自己创建并释放 `AsyncSession`。
- HTTP 客户端可以被多次请求复用。
- 自行创建的 Task 必须在释放其依赖资源前排空。
- 模型 API 总时限与 HTTPX 分阶段超时是不同的约束。

它仍不是完整生产方案：省略了身份认证、业务幂等、流式响应、数据库迁移、真正的模型 API 协议、跨进程任务恢复、就绪探针和统一监控。若底层任务忽略取消，`shutdown()` 会报告不完全停止，需要上层进程或任务系统负责后续处理。

## 10. 流式响应关闭与客户端中断

### 10.1 为什么流式调用更复杂

流式模型调用可能持续数十秒，期间保持一条活跃 HTTP 响应。前端关闭页面、反向代理超时、浏览器断网、服务停机都可能使读取方停止消费。

### 10.2 推荐写法

```python
import httpx
from fastapi import Request
from fastapi.responses import StreamingResponse

async def model_chunks(client: httpx.AsyncClient):
    async with client.stream("GET", "https://example.com/stream") as response:
        response.raise_for_status()
        async for data in response.aiter_bytes():
            yield data

@app.get("/model/stream")
async def stream_model(request: Request):
    return StreamingResponse(
        model_chunks(request.app.state.http),
        media_type="application/octet-stream",
    )
```

示例中的 `example.com/stream` 仅为演示地址。这里将上游响应的上下文放在生成器内部，流结束或生成器正常关闭时能够进入上下文退出代码。

若客户端已经断开、服务器取消传输或生成器被终止，应确保清理逻辑没有错误地吞掉取消异常。不要在流式响应转发期间关闭整个共享客户端，因为它还可能为其他请求服务。

### 10.3 资源先后关闭

对流式响应的理想顺序是：

1. 停止向客户端继续输出，或完成既定响应。
2. 结束/关闭当前上游 HTTP 响应。
3. 归还当前请求占用的连接。
4. 所有仍在使用客户端的请求都结束后，再关闭共享 `AsyncClient`。

对于非协作式代码、被外层强制杀死的进程，以上步骤可能无法全部完成。

## 11. 多 Worker 与 Kafka Worker 的额外边界

### 11.1 多个 Web Worker 不共享内存池

使用 `uvicorn --workers 4` 时，通常会有四个独立工作进程，各自维护它自己的：

- FastAPI 应用实例和 `lifespan`；
- HTTPX `AsyncClient`；
- SQLAlchemy `AsyncEngine` 与连接池；
- 应用级 Task 集合与内存缓存。

这些都是进程局部资源。进程间需要共享的状态，应使用数据库、Redis、消息队列等外部系统，而不是单个 Python 全局变量。

### 11.2 Kafka Consumer 的正确关闭过程

对于独立 Kafka Worker，关闭过程大致为：

1. 停止从 Kafka 获取新消息，或暂停分配分区上的新工作；
2. 跟踪并处理已领取消息对应的在途任务；
3. 允许可在宽限期内完成的任务完成并持久化结果；
4. 仅在业务结果达到可确认状态后推进消费位点；
5. 对未完成任务留下可恢复记录，避免错误提交位点；
6. 关闭 Consumer、HTTP 客户端、Session、Engine。

这里的**业务已写入但 Offset 未提交**仍会导致重投递，因此正确性依赖幂等设计，而不是仅靠“优雅停机”。

### 11.3 为什么 Kafka 不能直接替代关闭管理

Kafka 负责消息持久化与消费协调，仍需要 Worker 明确规定：

- 收到关闭信号是否停止拉取新消息；
- 在途批次要完成还是中断；
- 失败是否重试；
- 幂等键如何防止重复业务提交；
- 重平衡时如何处理尚未确认的消息；
- 什么时候关闭数据库与外部 HTTP 客户端。

一个“能启动 Kafka”的系统，不一定具有“任务可恢复”的可靠性。

## 12. 连接池耗尽、泄漏与停机故障的排查方式

### 12.1 症状与定位

| 症状 | 可能原因 | 优先检查 |
|---|---|---|
| HTTPX `PoolTimeout` | 连接数耗尽或响应未关闭 | 客户端池上限、活跃流、请求耗时 |
| HTTPX `ReadTimeout` | 上游迟迟无响应块 | 上游服务延迟、网络质量、read 超时 |
| SQLAlchemy `QueuePool` 超时 | Session 长事务、连接未归还、池太小 | Session 生命周期、连接占用、进程数 |
| PostgreSQL 连接数持续上升 | Engine/Session 创建过频繁、资源未释放 | Engine 数量、部署 Worker 数、池配置 |
| 停机过程很慢 | 在途请求或后台任务长时间不结束 | 活跃任务数、取消响应能力、外部依赖 |
| 服务已停但任务状态仍为 RUNNING | 任务状态没有恢复机制 | 心跳、租约、任务扫描、重试规则 |
| 关闭后报 Event loop is closed | 异步连接没有在循环结束前释放 | `await engine.dispose()`、`await client.aclose()` |

### 12.2 如何观察 SQLAlchemy 连接池

SQLAlchemy 提供 Pool 相关日志与检查能力；在调试环境可以考虑 `echo_pool="debug"` 观察借出和归还事件。但不要长期在生产环境无控制地输出高详细度日志。

还应结合 PostgreSQL `pg_stat_activity` 查看当前数据库连接、事务状态和等待情况。

### 12.3 必要的监控指标

- HTTP：活跃请求数、响应时间、连接池等待时间与超时次数。
- 数据库：连接池大小、借出数、等待数、长事务与失败回滚。
- 任务：运行中任务数、排空剩余数、取消次数和取消超时数。
- 关闭：停机总耗时、已完成/取消/未停止任务数。
- Worker：未确认消息数、重试次数、消费进度与重平衡事件。

### 12.4 关闭日志应该回答什么

一段足够有用的关闭日志至少能够重建：

```text
收到停止信号
停止接收新工作
当前活跃请求数 / 自建 Task 数
宽限时间内已完成任务数
被取消任务数、未能取消的任务数
关闭 HTTP 客户端完成
关闭数据库连接池完成
进程退出
```

不能只打印 `Shutdown completed`，却不知道是否有数据未处理完。

## 13. 常见误区总结

### 误区 1：“使用 async/await 就不需要连接池”

错误。异步机制解决等待时对事件循环线程的占用，连接池解决物理连接复用及连接数量管理。

### 误区 2：“每个请求都创建 AsyncClient 更安全”

没有必要。一个客户端实例通常可以安全地供多个异步任务共享，且这样有利于复用连接。正确的安全边界在于认证、请求参数、共享状态和连接配置。

### 误区 3：“数据库 Engine 和 Session 都是数据库连接，应该一起共享”

错误。Engine 可以共享；单个 AsyncSession 包含可变事务状态，不应并发共享。

### 误区 4：“离开 Session 上下文等于销毁整个数据库连接池”

错误。通常只是结束当前 Session 的作用域并归还占用的连接。

### 误区 5：“`pool_pre_ping` 可以避免所有数据库断线问题”

错误。它主要在连接取出前检测失效连接，无法自动恢复事务执行过程中出现的故障。

### 误区 6：“`Task.cancel()` 能保证任务在指定时间内停止”

错误。取消是协作式，任务可能无法及时响应。

### 误区 7：“关闭所有连接池后再等待任务完成也可以”

通常不正确。任务可能仍需要那些资源才能完成清理或提交，应该先处理任务再释放依赖。

### 误区 8：“FastAPI BackgroundTasks 能在重启后恢复”

错误。它是进程内任务机制，不能保证进程被终止后恢复执行。

### 误区 9：“四个 Worker 共享一个连接池”

错误。通常每个工作进程有独立 Engine / 客户端池，要计算总连接上限。

### 误区 10：“请求超时就说明外部操作没有发生”

错误。网络超时、取消与 commit 结果未知的场景，都可能产生已完成但尚未被调用方确认的副作用，必须使用幂等性和结果核对。

## 14. 综合示例：如何从慢模型请求推导正确的资源边界

假设同时有三个用户：

- 用户 A：模型调用需要 25 秒。
- 用户 B：模型调用需要 0.5 秒。
- 用户 C：查询数据库只需 20 毫秒。

合理的后端设计：

1. 共享一个长期存活的 HTTPX 客户端，而不是 A、B 各自创建连接池。
2. A 等待模型网络 I/O 时能够让出事件循环，B 和 C 可以获得调度机会。
3. C 创建自己的数据库 Session，完成 SQL 查询后及时关闭。
4. B、C 不应被 A 占用的数据库事务锁或 Session 阻塞。
5. HTTP 客户端本身限制最大连接数；如果并发模型请求多于模型服务配额，还需要额外的并发限额或限流机制。
6. 当服务收到正常关闭信号，Uvicorn 先等待 HTTP 请求在宽限期内结束；超时请求可能被取消。
7. 请求退出时关闭属于请求的流、Session 和事务；全部请求与自建后台任务结束后，才关闭共享 HTTP 客户端和 Engine。
8. 如果 A 的操作必须跨重启完成，就不应该仅依赖原 HTTP 请求或进程内 Task，而应转成可恢复的持久化后台任务。

最终原则：

> **应用级长生命周期资源可以共享；请求级事务状态必须隔离；任务完成、取消和恢复需要明确的责任边界；资源释放必须晚于最后一个仍依赖该资源的任务。**

## 16. 文档结论

本条学习目标最终围绕三个层次：

**第一层：正确复用连接。** 使用应用级 `httpx.AsyncClient`、`AsyncEngine` 和 `async_sessionmaker`，不要频繁新建连接池；每次数据库工作使用独立 Session，控制事务时长。

**第二层：正确关闭资源。** HTTP 流在消费结束后关闭，Session 在请求或任务作用域内关闭；整个应用停机时，先结束仍依赖网络与数据库资源的任务，再关闭客户端与数据库连接池。

**第三层：正确处理在途任务。** 区分 ASGI HTTP 请求、框架 BackgroundTask、手动创建的 `asyncio.Task` 和 Kafka Worker。通过宽限期、协作式取消、异常传播、状态记录与幂等处理，分别处理正常停止和异常中断。

资源管理解决的是**运行时生命周期正确性**；任务持久化与幂等性解决的是**跨重启业务可靠性**。两个问题相互关联，但不能用其中一个代替另一个。
