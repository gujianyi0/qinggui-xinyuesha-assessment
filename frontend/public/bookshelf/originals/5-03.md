## 1. 数据持久化的目标和边界

一个 AI 服务内可能同时出现四类数据：用户交互数据、知识资料、执行过程数据、最终业务结果。它们的保留时间、权限、索引及更新方式都不同。将全部内容放进一个巨大的 `history_json` 字段，虽然初期容易开发，但后续很难实现精确查询、唯一约束、事务一致性和审计。

**持久化**意味着数据写入具有持久化保证的存储系统，在应用进程退出、请求断开之后，仍能够重新获取。PostgreSQL 提供关系型约束、事务及 WAL 等基础能力；但这不等于“永不丢失”：实际持久性还受到磁盘故障、复制配置、备份、恢复点目标、运维误操作等因素影响。

需要区分：

- **状态记录**：系统知道某个任务曾经被创建、当前是什么状态。
- **执行快照**：能看到当时的模型、参数、资料版本和工具返回值。
- **可恢复任务**：系统有机制把未完成任务重新领取并继续执行。仅有数据库记录并不自动具有重新调度机制。
- **事实依据**：知识文件的版本、内容哈希及引用定位使回答能够被复核；并不表示文本本身一定真实。

推荐把高价值的结构化记录放在 PostgreSQL；体积很大的原始文件可以放对象存储，而 PostgreSQL 存储对象键、版本、哈希及元数据。不要把数据库当成不受限制的日志或文件存储。

## 2. PostgreSQL 数据结构与类型选择

| 数据 | 推荐类型 | 说明 |
|---|---|---|
| 主键 | `uuid` 或 bigint | UUID 适合跨服务生成；bigint 更紧凑，顺序写入特性不同 |
| 租户与用户 ID | 与对应主键同类型 | 必须与授权上下文关联，不能以客户端声明为准 |
| 会话/消息文本 | `text` | 长度不限的可变文本；仍应在应用层设置合理长度上限 |
| 时间 | `timestamptz` | 表示绝对时间点；展示时转换为用户所在时区 |
| 状态 | `text/varchar + CHECK` 或 PostgreSQL Enum | 状态增删频繁时 CHECK 有时更易演进；并非唯一方案 |
| 可变结构化元数据 | `jsonb` | 适合工具参数、已脱敏返回值、引用列表 |
| Token 用量 | `integer/bigint` | 需要注意 NULL 与零的区别 |
| 内容哈希 | `char(64)` / `varchar(64)` / `bytea` | 例如 SHA-256 的十六进制文本或原始字节 |
| 金额 | `numeric(p,s)` | 不用二进制浮点保存精确金额 |
| 版本标签 | `varchar` | 与资料内容哈希、创建时间、生效时间分别保存 |

`timestamp with time zone` 在 PostgreSQL 中也称 `timestamptz`。它保存可解释为时间点的值；不会保存最初输入的时区名称。若业务需要“原定于亚洲/上海当地 9 点”的日程语义，可能还须单独保存 IANA 时区标识。

在 SQLAlchemy 中常见写法：

```python
from sqlalchemy import DateTime, String, Text, Uuid, func
from sqlalchemy.orm import Mapped, mapped_column

id: Mapped[UUID] = mapped_column(Uuid(as_uuid=True), primary_key=True)
created_at: Mapped[datetime] = mapped_column(
    DateTime(timezone=True), server_default=func.now(), nullable=False
)
body: Mapped[str] = mapped_column(Text, nullable=False)
```

`server_default=func.now()` 是数据库侧默认值；`default=datetime.now(...)` 是 Python 侧默认值，两者发生的时机和依赖不同。跨 PostgreSQL 与 SQLite 运行时，日期时间类型的行为也可能不同，不应把 SQLite 测试当作 PostgreSQL 时区行为的证明。

## 3. 数据关系：五种基本身份

理解数据表之前，先确认这些标识的含义：

```text
Tenant（租户）
  └── User（用户）
       └── Conversation / Session（会话）
            ├── ChatMessage（按顺序排列的消息）
            └── AgentRun（某次执行）
                 ├── ToolExecution（每个调用及每次尝试）
                 └── FinalResult（可对外提供的最终结果）

Tenant（租户）
  └── KnowledgeDocument（逻辑资料）
       └── DocumentVersion（资料内容的某个具体版本）
```

- `tenant_id`：资源归属的组织或隔离域。
- `user_id`：经过认证的实际操作者。
- `conversation_id`：同一主题下的一组消息。
- `run_id`：一次模型/Agent 执行，其结果不一定成功。
- `call_id`：运行中的一次工具调用意图，应与实际工具记录关联。
- `document_id`：逻辑文档身份；`version_id` 才能指向不可变资料快照。

**会话 ID 不等于访问凭证**。即使用户猜中某个 UUID，也必须通过后端认证和资源所有权检查。执行过程数据与对话内容应能彼此关联，但不必混存在同一张表里。

## 4. 九张核心表

本章附录的演示定义了以下九张表：

| 表名 | 核心字段 | 主要用途 |
|---|---|---|
| `tenants` | `id`, `name` | 租户隔离域 |
| `app_users` | `id`, `tenant_id` | 租户内的用户主体 |
| `conversations` | `id`, `tenant_id`, `owner_id`, `next_message_seq` | 会话身份及有序消息分配 |
| `chat_messages` | `conversation_id`, `seq`, `role`, `content` | 持久化消息 |
| `knowledge_documents` | `id`, `tenant_id`, `slug` | 逻辑资料和可读名称 |
| `document_versions` | `document_id`, `label`, `content_sha256`, `body` | 具体资料版本、来源和原文 |
| `agent_runs` | `conversation_id`, `request_key`, `status` | 每次执行的状态、模型和用量 |
| `tool_executions` | `run_id`, `call_id`, `attempt`, `tool_name`, `status` | 工具调用和重试记录 |
| `final_results` | `run_id`, `answer`, `citations` | 一次执行的最终回答与引用 |

这是兼顾学习与可扩展性的最小逻辑结构，并非对所有企业系统都最优。例如真实平台往往需要独立的认证体系、事件流、附件表、资料分块表、审计日志表、任务队列表或对象存储。**本章没有把知识分块和向量索引额外纳入九张表**，因为这里的学习重点是持久化实体关系和迁移；RAG 分块可追加表并关联具体 `document_version_id`。

### 4.1 会话

会话需要至少保存创建者、租户、创建时间和排序所需信息。

```sql
CREATE TABLE conversations (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  owner_id uuid NOT NULL,
  title text NOT NULL,
  next_message_seq integer NOT NULL DEFAULT 1,
  created_at timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_conv_next_seq CHECK (next_message_seq >= 1),
  UNIQUE (tenant_id, id)
);
```

此处是用于说明字段的简化 SQL，完整模型还含外键与索引；**不要在实际系统中单独执行此简化 DDL，再认为已经建立完整约束**。

### 4.2 消息

一条消息不仅包含 `role` 和 `content`，还应具有稳定 `id` 与会话内递增的 `seq`。

```sql
SELECT seq, role, content
FROM chat_messages
WHERE tenant_id = :tenant_id
  AND conversation_id = :conversation_id
ORDER BY seq ASC;
```

时间戳不能充当严格消息顺序：并发请求可能拥有相同或接近的写入时间；正确顺序应该由明确的序号或者可证明有序的事件位置表示。

### 4.3 资料版本

`knowledge_documents` 保存逻辑文档；`document_versions` 保存实际版本：

```text
rules-character-A（逻辑资料）
  ├── version 1.0 | sha256=a... | 2026-08-01 生效
  ├── version 1.1 | sha256=b... | 2026-09-10 生效
  └── version 2.0 | sha256=c... | 草案，尚未发布
```

历史回答应能指回**当时使用的那个版本**，而不只是指向“规则文档最新页”。否则文档更新后，旧回答的证据可能无法重现。

### 4.4 工具执行与最终结果

工具执行需要区分“模型意图”和“程序真的做了什么”。至少保留：

- `run_id / call_id / attempt`：哪个执行产生了哪次工具尝试。
- 工具名和脱敏后的有效参数。
- 实际结果或结构化错误码。
- 执行时间、耗时、状态及可用的来源标识。
- 对外回答与其引用的具体版本/位置。

失败调用也需要记录。失败不是一条可随意覆盖的“空结果”；如果某个调用重试了两次，可以保留相同 `call_id` 下的 `attempt=1,2` 记录。这比只保存最后一次返回值更适合排障。

## 5. 联合唯一约束和复合外键

单独存一个 `tenant_id` 字段并不天然实现租户隔离。比如：

```text
messages.tenant_id = tenant_B
messages.conversation_id = tenant_A 的会话
```

如果只对 `conversation_id` 做外键，数据库无法保证消息的 `tenant_id` 与会话所属租户相同。

可以用**复合外键**做关系一致性保护：

```sql
ALTER TABLE chat_messages
ADD CONSTRAINT fk_msg_tenant_conv
FOREIGN KEY (tenant_id, conversation_id)
REFERENCES conversations (tenant_id, id);
```

被引用的 `(tenant_id, id)` 必须存在唯一约束或满足 PostgreSQL 相应唯一性要求。复合外键能够阻止跨租户错误关联，但**不能代替用户级授权**：同租户的普通用户也不一定有权查看他人的会话。

典型数据库约束分工：

- `PRIMARY KEY`：表内唯一记录身份。
- `UNIQUE (tenant_id, request_key)`：租户内幂等请求标识。
- `UNIQUE (tenant_id, conversation_id, seq)`：消息顺序唯一。
- `FOREIGN KEY`：父子数据关系完整性。
- `CHECK`：限定状态值、重试次数等基本规则。
- `NOT NULL`：区分必填与真正未知的数据。

应用应在写入前进行可理解的错误校验，但数据库约束必须作为并发下的最后一道一致性防线。

## 6. 有序消息写入与读取

### 6.1 普通 `max(seq)+1` 为什么有竞态

两个请求并发执行：

```text
请求 A：SELECT MAX(seq) → 7
请求 B：SELECT MAX(seq) → 7
请求 A：INSERT seq=8
请求 B：INSERT seq=8 → 冲突
```

唯一约束能防止两个消息都插入，但程序仍需要决定重试或采用不会冲突的分配方式。

### 6.2 通过锁住会话行分配序号

在 PostgreSQL 中，可以锁定对应会话行，获取并增加 `next_message_seq`：

```python
from sqlalchemy import select

async def append_message(db, tenant_id, owner_id, conversation_id, role, text):
    stmt = (
        select(Conversation)
        .where(
            Conversation.id == conversation_id,
            Conversation.tenant_id == tenant_id,
            Conversation.owner_id == owner_id,
        )
        .with_for_update()
    )
    conversation = (await db.scalars(stmt)).one_or_none()
    if conversation is None:
        raise PermissionError("会话不存在或无访问权限")

    seq = conversation.next_message_seq
    conversation.next_message_seq += 1
    message = ChatMessage(
        tenant_id=tenant_id,
        conversation_id=conversation_id,
        seq=seq,
        role=role,
        content=text,
    )
    db.add(message)
    await db.flush()
    return message
```

这段函数需要被调用方置于数据库事务中；`SELECT ... FOR UPDATE` 在 PostgreSQL 中提供对行的锁定，锁一般在事务结束时释放。SQLite 对 `FOR UPDATE` 的处理不同，不能用 SQLite 测试结果证明真实的 PostgreSQL 并发锁语义。

### 6.3 保存内容之前先判断授权

读取时不仅检查 `conversation_id`，还要检查认证来源的 `tenant_id` 和 `owner_id`。后者不能直接取前端 JSON 中声称的 `user_id`。列表接口、单条查询、导出功能与后台任务均应遵守同样规则。

## 7. 资料版本与不可变性

资料更新有两种完全不同的操作：

1. 修改可变的逻辑资料展示属性，例如标题、当前生效版本指针。
2. 创建新的内容版本，保留旧版本的原始文本、来源、哈希和版本标签。

对需要引用复核的知识，推荐采用**不可变内容快照**：发布新规则时插入 `document_versions` 新行，不覆盖旧 `body` 和 `content_sha256`。演示模型允许状态列变化（例如草案变为发布），但应避免修改已引用版本的内容。若生产系统要求数据库层强制内容不可变，还需要触发器、不可变版本对象或受限写入权限，单纯的应用约定不等于技术保证。

文本哈希示例：

```python
import hashlib

def content_sha256(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()
```

哈希能用于发现内容被修改或验证快照一致性，但不证明资料来源可靠；应同时保留原始来源、发布时间、适用版本和权限范围。

## 8. Agent 执行、工具记录与最终结果

一次完整运行通常经历：

```text
创建 AgentRun(PENDING)
    ↓
领取任务，更新 RUNNING
    ↓
模型输出 Tool Call
    ↓
ToolExecution(call_id, attempt=1, status=...)
    ↓
模型继续 / 工具可能重试
    ↓
结束前写入 FinalResult 和 Run 终态
```

`agent_runs` 中的 `request_key` 可以帮助处理重复提交。数据库唯一约束保护“同一租户的同一请求标识不会创建两条 Run”，但不能自动防止外部工具被执行两遍。

工具日志不等于对话历史。应记录**程序真正执行的工具请求及返回**，用于检查“模型最后的回答是否忠实于工具数据”。

结束时必须区分 `SUCCEEDED`、`FAILED`、`CANCELLED`。不能在取消已经确认后让较晚返回的模型结果覆盖取消终态。

另外，将回答保存为 `FinalResult` 并不自动在消息表生成助手消息。业务应明确决定是否把最终答复也写入 `chat_messages`，若两个记录必须同时出现，应在同一事务中写入，避免只保存了其中一项。

## 9. JSONB、结构字段与证据关联

适合用 JSONB 的内容：

- 已脱敏的工具参数与部分结果。
- 附带不同字段的结构化错误详情。
- `[{"document_version_id":"...", "chunk_id":"...", "start":20, "end":62}]` 形式的引用集合。

不适合简单丢进 JSONB 的内容：

- 需要严格唯一约束、外键关系或高频 JOIN 的字段。
- `tenant_id`、`status`、`run_id`、`created_at` 等高频过滤条件。
- 含密钥、密码、敏感信息的大量原始工具返回值。

例如：

```python
from sqlalchemy import JSON
from sqlalchemy.dialects.postgresql import JSONB

JSON_VALUE = JSON().with_variant(JSONB, "postgresql")
```

以上能使同一教学 ORM 模型在 PostgreSQL 使用 JSONB，在 SQLite 使用通用 JSON；不意味着两个数据库的 JSON 查询语义完全相同。

PostgreSQL 可对适合的 JSONB 查询建立 GIN 索引，但只有常用查询形式能够从中获益。不同 GIN operator class 支持的操作符与效率存在差异，不应该盲目为每个 JSONB 列加索引。

## 10. SQLAlchemy ORM 的工作机制

SQLAlchemy ORM 的关键组成：

- `DeclarativeBase`：所有 ORM 映射模型的共同基类。
- `mapped_column()` / `Mapped[T]`：声明数据库列及 Python 类型信息。
- `relationship()`：ORM 对象级关系，可帮助加载相关记录，但并不取代实际外键。
- `Session` / `AsyncSession`：Identity Map、Unit of Work 与事务管理。
- `select()` / `update()`：使用 SQLAlchemy 表达式构造 SQL。
- Dialect / Driver：将表达式适配 PostgreSQL、SQLite 等数据库以及相应驱动。

**ORM 不等于数据库。** 例如 `session.add(x)` 通常只是将对象纳入工作单元。`flush()` 把待同步修改写成 SQL 交给数据库，但尚未提交事务；`commit()` 则提交事务。若事务失败，仍需处理回滚和 Session 状态。

ORM 还不能在用户无权限时自动拒绝某条记录。对象级授权应在业务层或数据库 RLS 等受控机制中实现。

## 11. 异步 Engine、连接池与 Session 工厂

典型初始化过程如下：

```python
import os
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

DATABASE_URL = os.environ["DATABASE_URL"]
# 例如 postgresql+asyncpg://app_user:<url-encoded-password>@127.0.0.1:5432/agent_db

engine = create_async_engine(
    DATABASE_URL,
    pool_size=5,
    max_overflow=5,
    pool_pre_ping=True,
    pool_timeout=15,
)
SessionFactory = async_sessionmaker(
    engine,
    expire_on_commit=False,
)
```

解释：

| 对象 | 生命周期 | 作用 |
|---|---|---|
| `AsyncEngine` | 每个服务进程一般创建一个 | 维护数据库方言、驱动和连接池 |
| 连接池 | 与 Engine 关联 | 复用实际数据库连接、限制同时借出的连接数 |
| `async_sessionmaker` | 与 Engine 同生命周期 | 创建配置一致的 `AsyncSession` |
| `AsyncSession` | 一次独立请求/任务/事务 | 保存 ORM 状态与事务上下文 |
| 事务 | 一次业务原子操作 | 约束提交或回滚范围 |

`pool_size=5, max_overflow=5` 表示单个 Engine 对应池在相应条件下最多可借出约 10 条连接；多进程、多个服务实例还需要叠加计算，不能假设这是全系统上限。

`pool_pre_ping=True` 有助于在借出连接时检查失效连接，但不能保证网络在事务执行中途永远不出错，也不能无条件自动重试整个业务事务。

### 11.1 AsyncSession 不是线程安全/任务安全的共享对象

**错误**：

```python
session = SessionFactory()
await asyncio.gather(job_a(session), job_b(session))  # 两个任务共享同一 Session
```

**正确方向**：

```python
async def job_a():
    async with SessionFactory.begin() as session:
        # 独立事务
        ...

async def job_b():
    async with SessionFactory.begin() as session:
        # 独立事务
        ...

await asyncio.gather(job_a(), job_b())
```

同一个 Engine 和 Session 工厂可以复用；同一个 `AsyncSession` 不应同时交给多个并发任务。`expire_on_commit=False` 能减少提交后读取已加载属性的意外隐式 I/O，但不代表所有关系属性都能不经显式加载而直接访问。

## 12. asyncpg、AsyncSession 与查询代码

`asyncpg` 是 PostgreSQL 异步驱动，SQLAlchemy 的 URL 可以采用 `postgresql+asyncpg://`。实际程序大多通过 `AsyncSession` 调用 ORM，而不是手写底层驱动操作。

```python
from sqlalchemy import select

async def get_conversation_messages(
    session,
    tenant_id,
    current_user_id,
    conversation_id,
):
    conversation = (
        await session.scalars(
            select(Conversation.id).where(
                Conversation.id == conversation_id,
                Conversation.tenant_id == tenant_id,
                Conversation.owner_id == current_user_id,
            )
        )
    ).one_or_none()
    if conversation is None:
        raise PermissionError("无权访问此会话")

    return (
        await session.scalars(
            select(ChatMessage)
            .where(
                ChatMessage.tenant_id == tenant_id,
                ChatMessage.conversation_id == conversation_id,
            )
            .order_by(ChatMessage.seq.asc())
        )
    ).all()
```

`await session.execute(...)` 与 `await session.scalars(...)` 的区别在于获取结果的方式；后者适合获取 ORM 对象或单列标量。需要处理大量消息时，通常还要设计分页、最大返回数量和读取范围，不能一次性加载所有历史。

## 13. 事务：保存、提交与回滚什么

### 13.1 推荐明确一次业务事务的边界

```python
async with SessionFactory.begin() as session:
    await append_message(
        session,
        tenant_id=tenant_id,
        owner_id=current_user_id,
        conv_id=conversation_id,
        role="user",
        text="查询角色规则",
    )
# 代码块正常退出：提交事务；异常退出：回滚并关闭 Session
```

`SessionFactory.begin()` 是会创建 Session、开始事务并在退出时完成提交/回滚及关闭的上下文管理器。对需要精确处理异常的场景可捕获数据库异常，再进行领域错误映射。

### 13.2 flush 与 commit

```python
async with SessionFactory.begin() as session:
    session.add(AgentRun(...))
    await session.flush()   # SQL 已发送到数据库，仍处于事务中
# 正常退出后自动 commit
```

在 PostgreSQL 的默认 `READ COMMITTED` 隔离下，其他事务通常看不到尚未提交的修改；同一事务能够看到自己已经做出的修改。

### 13.3 错误时能回滚哪些内容

| 操作 | PostgreSQL 事务回滚可以撤销吗？ |
|---|---|
| 当前事务插入的消息 | 可以 |
| 当前事务更新的 Run 状态 | 可以 |
| 当前事务插入的工具执行记录 | 可以 |
| 已提交的上一事务 | 不可以 |
| 已经发给外部模型 API 的请求 | 不可以 |
| 已经实际发送的邮件或消息 | 不可以 |
| PostgreSQL sequence 已分配的编号 | 通常不会因事务回滚而收回 |

尤其要避免让数据库事务跨越耗时很长的模型调用：

```python
# 不推荐：事务和数据库锁可能被模型网络等待长期占用
async with SessionFactory.begin() as session:
    run = ...
    response = await external_model_call(...)  # 可能等待 30 秒以上
    ...
```

更可靠的设计：短事务创建 PENDING/RUNNING 记录 → 事务结束 → 外部模型调用 → 新事务保存执行结果与最终状态。若外部调用中断，应通过数据库状态和补偿/重试策略处理，而不是指望数据库回滚外部副作用。

## 14. FastAPI lifespan 与数据库访问

```python
from contextlib import asynccontextmanager
import os
from fastapi import FastAPI, Request, Depends
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker

@asynccontextmanager
async def lifespan(app: FastAPI):
    engine = create_async_engine(
        os.environ["DATABASE_URL"],
        pool_pre_ping=True,
    )
    app.state.db_session_factory = async_sessionmaker(
        engine, expire_on_commit=False
    )
    try:
        yield
    finally:
        await engine.dispose()

app = FastAPI(lifespan=lifespan)

async def get_db(request: Request):
    factory = request.app.state.db_session_factory
    async with factory() as session:
        yield session

@app.get("/health/db")
async def db_health(db=Depends(get_db)):
    from sqlalchemy import text
    await db.execute(text("SELECT 1"))
    return {"database": "reachable"}
```

注意：

1. `get_db()` 只是创建和关闭 Session，**并未自动提交业务事务**。
2. 写入接口应该明确使用 `async with session.begin()` 或在服务层管理事务，而不是假设 FastAPI 自动 commit。
3. 关闭应用时，应在资源仍可用的情况下结束在途任务，再释放 Engine。`lifespan` 的最终清理不等于所有自建后台 Task 都已被可靠处理。
4. `/health/db` 是演示；生产环境的健康检查应根据依赖类型和探针目的决定是否探测数据库，避免故障时大量健康检查进一步加压。

## 15. 并发、幂等和终态保护

### 15.1 请求幂等键

```sql
CREATE UNIQUE INDEX uq_run_request_key
ON agent_runs (tenant_id, request_key);
```

相同请求标识重复到达时，应返回此前任务或一个明确的冲突状态，而不是盲目再创建任务。唯一约束能够解决并发重复插入的一致性问题；客户端请求标识的定义、作用域和有效期应由业务设计明确规定。

### 15.2 最终结果唯一性

```sql
CREATE UNIQUE INDEX uq_result_per_run
ON final_results (tenant_id, run_id);
```

它防止某次 Run 生成两条最终结果记录，但不能保证答案符合事实，也不保证工具只执行一次。

### 15.3 原子化终态写入

需要在同一个事务中“检查 Run 当前状态 → 标记完成 → 创建最终结果”。可以采用 PostgreSQL 的条件更新：

```python
from sqlalchemy import update

async with SessionFactory.begin() as db:
    # 生产系统还应根据登录用户和该 Run 对应的会话检查授权
    result = await db.execute(
        update(AgentRun)
        .where(
            AgentRun.id == run_id,
            AgentRun.tenant_id == tenant_id,
            AgentRun.status == "RUNNING",
        )
        .values(status="SUCCEEDED")
        .returning(AgentRun.id)
    )
    updated_id = result.scalar_one_or_none()
    if updated_id is None:
        raise RuntimeError("任务已结束或状态不允许完成")

    db.add(FinalResult(
        tenant_id=tenant_id,
        run_id=run_id,
        answer=answer,
        citations=citations,
    ))
```

这利用单条 SQL 的条件更新保护状态前置条件，并将终态与最终结果纳入同一个事务。如果执行失败，二者一起回滚。真实应用要定义哪个 Worker 有资格提交结果，以及超时任务是否仍属于合法拥有者；可能需要 `lease_token` 或版本号防止过期 Worker 写回。

## 16. 多租户与用户级授权

数据库中的租户隔离需要多层防护：

- 通过认证中间件或可信身份系统获得 `tenant_id`、`user_id`，而非相信用户上传字段。
- 查询会话时同时验证租户及所有者。
- 子表通过复合外键阻止关联到其他租户的父记录。
- 关键访问可以增加 PostgreSQL RLS（Row Level Security）作为第二道防线。
- 工具执行器也必须独立校验当前 Run 是否属于用户可访问的会话。

RLS 的一个极简示例（仅为原理展示）：

```sql
ALTER TABLE conversations ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_conversations ON conversations
USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

使用连接池时，不能把租户身份作为跨请求长期保留的连接全局状态。可以在每个事务中使用 transaction-local 设置，并确认连接池复用、权限角色和失败回滚都不会泄漏上下文。PostgreSQL 的表拥有者及具备 `BYPASSRLS` 权限的角色有特殊行为，生产使用需要专门审查；**仅凭这段示例 SQL 不构成完整租户安全方案**。

即使实现 RLS，也仍需单独处理租户内的用户级授权、管理角色和数据共享策略。

## 17. Alembic 的作用：结构版本管理

ORM 定义了“程序期望的表结构”，数据库中则存在“实际已经部署的结构”。二者随时间可能不一致：

```text
应用版本 V1 → 表结构 Rev 001
应用版本 V2 → 表结构 Rev 002
应用版本 V3 → 表结构 Rev 003
```

Alembic 使用迁移文件组织这个演进过程。每份 Revision 通常包含：

```python
revision = "002_add_field"
down_revision = "001_initial"

def upgrade():
    ...

def downgrade():
    ...
```

它在数据库中维护 `alembic_version` 表以追踪当前迁移位置。`revision` 是迁移标识，`down_revision` 指向迁移依赖；它们与业务资料的 `document_versions.label` 完全不同。

注意：在生产中直接调用 `Base.metadata.create_all()` 通常不能替代迁移管理，因为 `create_all()` 并不会自动完成已有表的复杂修改、数据回填、索引构建和历史版本管理。

## 18. 异步 Alembic 环境

安装依赖（具体版本应在项目中锁定）：

```bash
python -m pip install "SQLAlchemy[asyncio]" asyncpg alembic fastapi uvicorn
```

初始化异步迁移模板：

```bash
alembic init -t async alembic
```

该命令生成 `alembic.ini`、`alembic/env.py`、`alembic/versions/` 等文件。`async` 模板并不意味着 Alembic 的所有迁移操作都会变成 Python `async def`；它使用异步 Engine 获得连接，再通过 `run_sync()` 执行传统迁移逻辑。

### 18.1 env.py 的核心改造

以下是适用于新项目的教学示例，省略了生成模板中的一些注释和日志配置：

```python
# alembic/env.py
import asyncio
import os

from alembic import context
from sqlalchemy import pool
from sqlalchemy.engine import Connection
from sqlalchemy.ext.asyncio import create_async_engine
from app.db.models import Base  # 必须导入包含全部表的 metadata

DATABASE_URL = os.environ["DATABASE_URL"]
target_metadata = Base.metadata


def run_migrations_offline():
    context.configure(
        url=DATABASE_URL,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )
    with context.begin_transaction():
        context.run_migrations()


def do_run_migrations(connection: Connection):
    context.configure(
        connection=connection,
        target_metadata=target_metadata,
        compare_type=True,
    )
    with context.begin_transaction():
        context.run_migrations()


async def run_async_migrations():
    engine = create_async_engine(DATABASE_URL, poolclass=pool.NullPool)
    try:
        async with engine.connect() as connection:
            await connection.run_sync(do_run_migrations)
    finally:
        await engine.dispose()


def run_migrations_online():
    asyncio.run(run_async_migrations())


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

**重要**：上述 `run_migrations_online()` 预期由 Alembic CLI 在不运行事件循环的顶层环境调用。在已有事件循环内部直接调用 `asyncio.run()` 会报错，需要使用 Alembic 官方程序化迁移相关模式，不能直接复制 CLI 模板到任意异步函数里执行。

## 19. 自动生成迁移与审查

常用命令：

```bash
# 查看当前数据库的迁移版本
alembic current

# 生成候选迁移文件
alembic revision --autogenerate -m "create chat and agent tables"

# 审查新生成的 alembic/versions/*.py 后再执行
alembic upgrade head

# 查看历史与当前最新版本
alembic history
alembic heads

# 在 CI 中检查 ORM 与数据库是否还存在未生成的差异
alembic check
```

`autogenerate` 通过比较目标 `MetaData` 和当前数据库结构发现候选变更。它通常能检测表/字段增删、可空性变化、许多索引与约束变更。但通常不能准确理解“改名”，因此可能把重命名错误生成成“删除旧列 + 新增列”。**如果直接应用，就可能丢失历史数据。**

### 19.1 需要回填的新字段

假设现有 `document_versions` 尚无 `source_checksum_algo` 字段，现计划增加且要求非空。不能直接添加不带默认值的非空列，因为已有数据不满足约束。较稳妥的迁移：

```python
from alembic import op
import sqlalchemy as sa

# 仅展示 upgrade/downgrade；真实 revision 还需要 revision、down_revision

def upgrade():
    op.add_column(
        "document_versions",
        sa.Column("source_checksum_algo", sa.String(20), nullable=True),
    )
    op.execute("""
        UPDATE document_versions
        SET source_checksum_algo = 'sha256'
        WHERE source_checksum_algo IS NULL
    """)
    op.alter_column("document_versions", "source_checksum_algo", nullable=False)


def downgrade():
    op.drop_column("document_versions", "source_checksum_algo")
```

这只是一个**明确知道所有已有哈希都来自 SHA-256** 的示例。如果旧数据并不全部符合这个事实，不能简单用 `'sha256'` 回填，而应根据真实数据校正或另行标记未知状态。完成数据库迁移后，还应同步修改 ORM 模型及读写代码。

### 19.2 为什么不能随意 downgrade

- 删除字段可能不可逆地丢掉数据。
- 某些迁移涉及大量后台数据回填或应用层协议变更。
- 多个服务版本并存时，回退到旧结构可能让仍在运行的新代码报错。
- PostgreSQL 的普通 DDL 具有事务特性，但并非所有操作都能放在普通事务内，例如 `CREATE INDEX CONCURRENTLY` 需要特殊执行方式。

迁移前应有备份、演练和明确的回滚/前进修复预案。

## 20. 线上数据库升级与兼容性

在持续运行的系统中，推荐遵循 **Expand → Migrate → Contract**：

1. **Expand**：先添加兼容新旧应用的可选字段或新表。
2. **Migrate**：发布能够兼容两种结构的代码，按批次回填旧数据。
3. **Contract**：确认所有实例使用新结构后，移除旧字段或施加最终约束。

原因在于数据库迁移和应用部署不一定在同一瞬间完成。若旧代码还在使用某个字段，先删字段就会直接导致旧实例失败。

注意数据库锁：长时间执行的 `ALTER TABLE`、大规模更新或索引操作可能阻塞线上流量。要关注锁等待、锁超时、事务存活时间、复制延迟和维护窗口。

建议把 `alembic upgrade head` 作为受控发布步骤，而不是让每个 FastAPI Worker 启动时都自动跑迁移。多实例同时自动迁移可能产生竞态和不必要的锁争用。

### 20.1 迁移文件如何验收

- 对空数据库执行 `upgrade head` 成功。
- 对有历史数据的旧数据库升级成功且原数据保持正确。
- `alembic current` 指向预期版本。
- `alembic check` 不存在未预期的差异（仍受自动生成限制）。
- 关键业务查询、约束、索引和权限规则正常。
- 回滚或前进修复的操作和风险已验证。

## 21. 查询性能和连接池容量

最常见查询：

```sql
-- 某用户最近会话
SELECT * FROM conversations
WHERE tenant_id = :tenant AND owner_id = :user
ORDER BY created_at DESC
LIMIT 20;

-- 某会话最近消息：实际应按应用分页边界调整
SELECT * FROM chat_messages
WHERE tenant_id = :tenant AND conversation_id = :conv
ORDER BY seq DESC
LIMIT 50;

-- 某运行的工具轨迹
SELECT * FROM tool_executions
WHERE tenant_id = :tenant AND run_id = :run
ORDER BY executed_at ASC;
```

应根据这些查询模式考虑复合索引，而不是机械地为每列创建单列索引。例如 `(tenant_id, conversation_id, seq)` 可以帮助按会话读取有序消息。值得注意的是，唯一约束通常已经由数据库建立支持它的唯一索引；重复创建完全等价的索引会浪费空间和写入开销。附录模型同时定义了部分演示性组合索引，实际部署应通过 `EXPLAIN (ANALYZE, BUFFERS)` 和真实负载检查并删除冗余索引。

连接池容量近似取决于每个进程的池参数、进程数量、服务实例数量以及其他程序消耗的数据库连接。若 PostgreSQL `max_connections` 不足，程序再增加 API 并发并不会提高数据库吞吐，反而可能加剧排队或出现连接池超时。

读写耗时还受到：数据量、索引命中率、事务持续时间、锁竞争、网络 RTT、查询计划、磁盘 I/O、连接池等待等因素影响。

## 22. 常见故障及正确归因

| 现象 | 可能原因 | 检查方向 |
|---|---|---|
| 程序启动时报 `ModuleNotFoundError: asyncpg` | 未安装驱动 | 环境依赖与解释器 |
| `MissingGreenlet` | 在异步 ORM 中触发隐式 lazy load 等 | 显式预加载、避免隐式 I/O |
| `PendingRollbackError` | 前一个数据库错误后未回滚 | 捕获异常、事务清理 |
| `IntegrityError` | 外键、唯一约束、非空或检查约束失败 | 原始 SQL 错误码、违反的约束 |
| 同一次反馈重复入库 | 缺幂等键或业务唯一约束 | 唯一约束 + 并发处理 |
| 同租户不同会话混入历史 | 查询没有限定 conversation_id | 所有查询的作用域过滤 |
| 跨租户能读记录 | 缺对象级授权、缓存键不带作用域等 | 认证身份与查询条件、RLS |
| 开发环境正常，部署后找不到字段 | 未执行 Alembic 迁移 | 当前 DB schema 和 migration 版本 |
| 迁移检测到删除一列、新增一列 | 实际是重命名，autogenerate 不识别 | 手工改为 rename |
| 任务状态一直 RUNNING | Worker 崩溃、缺恢复机制 | 租约、后台任务、状态重试 |
| API 很慢 | 长事务、锁竞争、连接池等待、SQL 不佳 | DB 日志、慢查询、EXPLAIN、指标 |
| 关闭服务仍有连接 | Engine 未 dispose 或后台任务仍使用 | lifespan、任务管理、连接池指标 |

**不要仅根据一次 HTTP 500 就推断数据库故障**：要结合异常链、数据库错误码、请求 ID、事务 ID、Run ID 等证据确定失败层次。

## 23. 一条端到端执行流程

以下是一个相对合理的会话问答持久化流程：

```text
请求到达 FastAPI
    ↓
认证用户身份 → 获取可信 tenant_id / user_id
    ↓
短事务 A：检查会话权限 → 写用户消息 → 创建 Run(PENDING)
    ↓ 事务提交
调用模型 / 检索知识 / 受控执行工具（避免长期持有数据库事务）
    ↓
短事务 B：保存实际工具结果、失败信息或进度状态
    ↓ 事务提交
结束时：短事务 C 将 Run 状态更新为终态，并写 FinalResult
    ↓ 事务提交
前端查询完成结果，引用指向具体资料版本和可核验位置
```

网络断开、进程重启或其他依赖故障发生时，数据库能保留先前已提交的状态；但要让未完成任务得到恢复，需要额外的 Worker 调度、幂等保障与超时状态清理机制。

**一句话概括**：PostgreSQL 保证持久数据与关系约束，SQLAlchemy 负责 Python 程序与数据库之间的读写工作单元，Alembic 负责结构的可追踪演进；用户数据隔离、业务正确性和任务可靠恢复仍需要应用层明确设计。

# Application functions below accept a Session and rely on the caller's transaction.
async def append_message(session, tenant_id: uuid.UUID, owner_id: uuid.UUID, conv_id: uuid.UUID, role: str, text: str):
    """PostgreSQL: SELECT ... FOR UPDATE serializes allocation of seq per conversation."""
    statement = (select(Conversation)
                 .where(Conversation.id == conv_id,
                        Conversation.tenant_id == tenant_id,
                        Conversation.owner_id == owner_id)
                 .with_for_update())
    conv = (await session.scalars(statement)).one_or_none()
    if conv is None:
        raise PermissionError("conversation not found or not authorized")
    number = conv.next_message_seq
    conv.next_message_seq += 1
    message = ChatMessage(tenant_id=tenant_id, conversation_id=conv_id, seq=number, role=role, content=text)
    session.add(message)
    await session.flush()
    return message


async def messages_for_user(session, tenant_id: uuid.UUID, owner_id: uuid.UUID, conv_id: uuid.UUID):
    can_view = (await session.scalars(
        select(Conversation.id).where(
            Conversation.id == conv_id,
            Conversation.tenant_id == tenant_id,
            Conversation.owner_id == owner_id
        )
    )).one_or_none()
    if can_view is None:
        raise PermissionError("conversation not found or not authorized")
    return (await session.scalars(
        select(ChatMessage)
        .where(ChatMessage.tenant_id == tenant_id, ChatMessage.conversation_id == conv_id)
        .order_by(ChatMessage.seq.asc())
    )).all()
