大模型原理、API 与输出校验（六）

普通响应与流式响应：文本增量、结束事件、超时和中途断开的处理

知识目标：理解模型 API 的普通响应（Non-streaming）与流式响应（Streaming）如何工作；正确处理文本增量、完成与失败事件、超时、用户取消及网络中断，防止把不完整输出误当成完整结果。

技术基准：Python 3.13+ 的 asyncio；FastAPI；HTTPX；基于公开接口的 Chat Completions 和 Responses API。不同模型提供商、协议与 SDK 版本的行为可能不同，须以当前服务的接口文档为准。文中示例分为可离线运行的演示与需要 API 密钥的远程调用，不可混淆。

1. 从一次模型请求的生命周期理解普通响应与流式响应

对于同一条用户请求，模型通常需要经历排队、输入处理（prefill）、生成输出（decode）和结果传输等阶段。普通响应和流式响应不必然意味着两套不同的模型生成算法，核心区别在于服务端何时把已经产生的数据交给客户端。

1.1 普通响应

text
客户端                           模型服务
  | POST /chat                      |
  |-------------------------------->|
  |                                 | 解析输入、推理、生成完整结果
  |                                 | ...
  |<--------------------------------| HTTP 200 + 完整 JSON
  | 展示完整答案                     |

普通响应（stream: false 或使用非流式方法）一般在模型完成此次生成后，返回包含全部内容、结束原因和用量的一个 JSON 响应。客户端可以一次读取并校验整体结果。

1.2 流式响应

text
客户端                           模型服务
  | POST /chat (stream=true)         |
  |-------------------------------->|
  |<--------------------------------| HTTP 200 + 事件流响应头
  |<--------------------------------| 文本增量 "你好"
  |<--------------------------------| 文本增量 "，我来"
  |<--------------------------------| 文本增量 "解释。"
  |<--------------------------------| 完成事件/结束标记
  | 展示完整答案                     |

流式响应通常允许客户端在模型仍在生成时持续得到增量，因此更快看到首段文字；它不保证模型最终完成更快。流式传输还会带来协议解析、中途断开、部分内容安全校验及资源管理等复杂性。

1.3 对比表

维度 普通响应 流式响应
返回方式 一次性返回整体结果 持续返回事件或数据片段
首字可见时间 接近完整生成结束 通常接近首次生成可发送输出的时间
数据组织 单个完整 JSON 对象 多个数据块 / SSE 事件，需聚合
最终结果判定 检查响应状态与结束原因 必须同时检查流事件顺序与终止事件
断线影响 可能没有任何答案 可能已经得到部分文本，但未完成
结构化输出 一次校验完整 JSON 先累计，再判断是否可解析和验证
用户体验 适合短文本、结构化批量任务 适合聊天、实时进度、较长生成
实现复杂度 相对低 更高；涉及保活、取消、重连、缓冲

注意：流式传输不是“每个 Token 对应一个网络包”；一个事件可包含多个字符、多个 Token 或非文本数据，网络分块又可能把一个事件拆开。

2. 关键时间指标：TTFT、总时长与吞吐量

理解响应速度时至少区分：

  • TTFT（Time To First Token / 首个可见增量延迟）：从请求发起到收到第一个有效输出增量的时间；在部分推理模型中，推理过程和工具调用会影响可见文本的开始时间。实践上也可单独统计 first_text_delta_ms。
  • TTLT / 完成耗时：从请求发起到收到协议规定的终止事件的时间。
  • 输出吞吐量：已生成的输出 Token 数除以相应生成时间区间；不等于字/秒。
  • 网络首字节时间（TTFB）：HTTP 响应头或首字节到达的时间，可能早于真正的文本生成。
  • 事件空闲时间（idle gap）：相邻网络事件之间的时间；不等于模型是否在后台推进的时间。

例如：接口 0.2 秒返回响应头、3 秒才发来首个文本、10 秒完成输出，则网络 TTFB、文本 TTFT 和总响应时间是三个不同值。若模型先进行工具调用，UI 的首个内容事件还可能是“工具已开始”，而不是文字。

3. 网络分块、SSE 事件和模型 Token 是不同层次

text
模型生成 Token
      ↓ 组合成服务端增量对象
ChatCompletionChunk / Responses Event
      ↓ 编码为 SSE 或其他传输格式
HTTP 响应字节流
      ↓ TCP/TLS/HTTP 网络传输
客户端读取 bytes / lines / protocol events
      ↓ 解析并组装
应用层文本、状态、工具调用、用量

关键区别：

  1. Token 是模型分词器的处理单位。
  2. Delta 是 API 的语义增量，可能是文本、角色字段、工具参数增量等。
  3. SSE Event 是通过 HTTP 传送的事件帧。
  4. 网络 Chunk 是底层数据到达的字节片段，边界不承诺对应一个 SSE 事件。

错误示例：每次 aiter_bytes() 得到一段字节，就立刻 json.loads(chunk)。一个 JSON 事件可能跨多个网络片段，或者多个事件共处一个网络片段，这样很容易抛出解析错误。

4. SSE：Server-Sent Events 的协议基础

SSE 是基于 HTTP 的服务器到客户端单向事件流。服务端通常设置：

http
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache

一条 SSE 事件可写为：

text
event: delta
id: 12
data: {"text":"你好"}

需要注意末尾的空行：它表示这个事件块结束。常用字段：

字段 语义
event: 事件名称；没有时浏览器 EventSource 默认视为 message
data: 数据；可以有多行，解析时按规范拼接
id: 事件 ID，浏览器重连时可携带最近收到的事件标识
retry: 浏览器 EventSource 重连延迟，单位毫秒
: 注释行，可作为连接保活，不会作为普通业务事件展示

示例：

text
: heartbeat

event: delta
data: {"text":"早上"}

event: delta
data: {"text":"好。"}

event: done
data: {"status":"completed"}

这段 done 是本例业务协议定义的事件名，不是 SSE 标准自动保证的结束标记。SSE 本身没有统一的“模型已经完成”语义，模型 API 通过额外的事件类型或标记给出这一信息。

4.1 SSE 与 WebSocket 的区别

SSE 主要用于服务端向客户端持续推送；WebSocket 是全双工通道。常见 AI 文本流只需要单向下发时，SSE 通常足够。要从浏览器向服务器发送新消息，可以另外发普通 POST 请求，并不意味着一定需要 WebSocket。

4.2 EventSource 与 fetch 的区别

浏览器原生 EventSource 以 GET 方式建立流，适合订阅式接口，可自动重连，但不能任意设置自定义请求头或直接发送 JSON POST 请求体。对于需要携带 JSON、鉴权头的聊天流，常用 fetch(..., { method: 'POST', body: ..., signal: ... }) 再手动解析响应体，或者通过兼容的服务端会话机制设计为 GET。

5. Chat Completions：普通响应与流式响应对象结构

5.1 普通响应的典型形态

json
{
  "id": "chatcmpl-example",
  "choices": [
    {
      "index": 0,
      "message": {"role": "assistant", "content": "你好，我可以帮你。"},
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 14,
    "completion_tokens": 8,
    "total_tokens": 22
  }
}

这只是示意结构与虚构数值，不是一次真实 API 响应。

5.2 流式响应的典型事件

text
data: {"id":"x","choices":[{"index":0,"delta":{"role":"assistant"},"finish_reason":null}]}

data: {"id":"x","choices":[{"index":0,"delta":{"content":"你好"},"finish_reason":null}]}

data: {"id":"x","choices":[{"index":0,"delta":{"content":"！"},"finish_reason":null}]}

data: {"id":"x","choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}

data: [DONE]

在流中，choices[i].delta 表示增量，不是完整的 message；finish_reason 通常在终止阶段才出现。[DONE] 是 Chat Completions 风格流的协议结束标记；收到普通文本片段不是完成的证据。

5.3 结束原因 finish_reason

值 含义 调用方处理建议
stop 自然结束或匹配停止序列 标记生成阶段正常完成；仍需校验内容
length 达到生成限制或相关容量边界 标记可能截断；不能当完整 JSON 使用
tool_calls 模型给出工具调用 需要校验并执行工具，然后继续任务流程
content_filter 被内容过滤机制处理 不能按普通正常回答解释
function_call 旧式函数调用标记 兼容旧接口时才处理

不同厂商可能增加其他结束原因。应以实际返回枚举作显式分支，未知值视为需排查的状态，而不是默认成功。

5.4 usage 的不同实现：不能假设所有服务一致

对于 OpenAI Chat Completions，请求 stream_options={"include_usage": True} 后，通常在 [DONE] 前额外返回 choices=[] 的用量统计块。如果流提前中断，可能收不到该统计块。

对于 DeepSeek Chat Completions（以所引官方说明为准），末尾带 finish_reason 的 choices 块还携带累计 usage；不单独发 choices=[] 的 usage-only 块。这是服务商特定的协议差异，不应统一写死。

因此，消费循环不能假设每个 chunk.choices[0] 都存在，也不能只在 choices=[] 时才读取用量。

6. Python：直接进行普通模型调用

以下示例使用兼容 Chat Completions 的 DeepSeek 端点。需要安装：

powershell
python -m pip install openai
$env:DEEPSEEK_API_KEY="你的密钥"

不要将密钥直接提交到代码仓库。示例模型名以当前对应服务商的官方 API 文档为准。

python
import os
from openai import AsyncOpenAI

async def non_streaming_call() -> None:
    async with AsyncOpenAI(
        api_key=os.environ["DEEPSEEK_API_KEY"],
        base_url="https://api.deepseek.com",
    ) as client:
        response = await client.chat.completions.create(
            model="deepseek-flash",
            messages=[{"role": "user", "content": "解释 Python 的 await"}],
            stream=False,
        )
        choice = response.choices[0]
        print("内容:", choice.message.content)
        print("结束原因:", choice.finish_reason)
        print("用量:", response.usage)

if __name__ == "__main__":
    import asyncio
    asyncio.run(non_streaming_call())

普通响应重点检查：HTTP 是否成功、choices 是否存在、content 是否符合预期、finish_reason 是否正常、usage 是否返回。仅凭 HTTP 200 或文本非空，都无法证明任务语义正确。

7. Python：用 SDK 处理 Chat Completions 流

python
import asyncio
import os
from openai import AsyncOpenAI

async def streaming_call() -> None:
    async with AsyncOpenAI(
        api_key=os.environ["DEEPSEEK_API_KEY"],
        base_url="https://api.deepseek.com",
    ) as client:
        stream = await client.chat.completions.create(
            model="deepseek-flash",
            messages=[{"role": "user", "content": "用三句话解释 SSE"}],
            stream=True,
            stream_options={"include_usage": True},
        )

        text_parts: list[str] = []
        finish_reason: str | None = None
        usage = None

        async for chunk in stream:
            if chunk.usage is not None:
                usage = chunk.usage

            for choice in chunk.choices:
                if choice.index != 0:
                    continue
                if choice.delta.content:
                    text_parts.append(choice.delta.content)
                    print(choice.delta.content, end="", flush=True)
                if choice.finish_reason is not None:
                    finish_reason = choice.finish_reason

        print("\n---")
        print("聚合文本:", "".join(text_parts))
        print("结束原因:", finish_reason)
        print("用量:", usage)
        if finish_reason != "stop":
            print("注意：生成未处于常规文本正常结束状态")

if __name__ == "__main__":
    asyncio.run(streaming_call())

这段代码采用两个重要的防御措施：

  1. 先遍历 chunk.choices，不假定数组永远非空。
  2. 把多个 delta.content 顺序拼接，而不是将每个 Delta 视为完整答复。

补充：上面的示例针对单个文本候选 index=0。如果启用多个候选、工具调用或多模态内容，必须分别按索引累积文本、工具调用参数和结束原因，不能简单合并成一段字符串。

8. Responses API：与 Chat Completions 不同的事件模型

Responses API 通常提供更明确的语义化事件。常见事件包括：

text
response.created
response.in_progress
response.output_item.added
response.output_text.delta
response.output_text.done
response.output_item.done
response.completed

失败或不完整时可能以：

text
response.failed
response.incomplete

结束。Responses API 不应仅依赖 Chat Completions 的 [DONE] 标记；在 OpenAI、DeepSeek 对应的 Responses 流中，终止事件由 response.completed / response.incomplete / response.failed 表达。

8.1 Python 示例

python
import asyncio
import os
from openai import AsyncOpenAI

async def responses_stream() -> None:
    async with AsyncOpenAI(
        api_key=os.environ["DEEPSEEK_API_KEY"],
        base_url="https://api.deepseek.com",
    ) as client:
        events = await client.responses.create(
            model="deepseek-flash",
            input="解释普通响应与流式响应的区别",
            stream=True,
        )

        chunks: list[str] = []
        terminal_status: str | None = None
        async for event in events:
            if event.type == "response.output_text.delta":
                chunks.append(event.delta)
                print(event.delta, end="", flush=True)
            elif event.type in {
                "response.completed", "response.incomplete", "response.failed"
            }:
                terminal_status = event.type
                # 完整响应对象中可能包含用量、错误等最终字段。

        print("\n终止事件:", terminal_status)
        print("完整文本:", "".join(chunks))

if __name__ == "__main__":
    asyncio.run(responses_stream())

如果只关心最终用户可见文本，可接收 output_text.delta；若产品包含工具执行、推理状态和多模态输出，还须处理相应事件类型及不同 output_index / item_id。工具参数在流式状态下往往只是 JSON 片段，应先完整拼接，再进行 JSON/Schema 校验，之后才允许执行工具。

9. 为什么不能把“连接关闭”视为“模型完成”

存在三种完全不同的情况：

text
A. 正常： delta → delta → finish_reason=stop → [DONE]
B. 截断： delta → delta → finish_reason=length → [DONE]
C. 断网： delta → delta → TCP 断开（没有终止标记）

三者都可能使客户端停止接收字节，但业务含义不同：

  • A：协议完成，后续仍要检验内容正确性。
  • B：生成正常结束了传输过程，但输出可能不完整。
  • C：没有可靠证据证明模型已经完成，也不知道服务端是否仍在运算。

对于 Responses API，也应区分 response.completed、response.incomplete、response.failed 与未收到任何终止事件就失去连接。

一旦没有收到可验证的终止状态，应把已收到内容标记为 interrupted、partial 或 unknown，不能直接提交为最终成功结果。流中途断开还意味着可能无法获得精确 Token 用量。

10. 传输级错误与业务级错误：HTTP 200 可能同时存在错误

普通响应的 HTTP 4xx/5xx 一般可以在响应体解析前被识别；但流式响应一旦开始发送 HTTP 200 和响应头，服务端通常无法再把状态码改成 500。

因此流式服务常用应用级错误事件表达中途失败：

text
event: error
data: {"code":"UPSTREAM_TIMEOUT","message":"模型响应超时","retryable":true}

客户端要检查两类错误：

  1. HTTP 层错误：401、429、502、503 等，通常发生在建立成功的事件流之前。
  2. 流内业务错误：已进入 text/event-stream 后的 event: error、response.failed 等。

如果既没有有效终止事件，也没有错误事件，而连接直接关闭，应该识别为不可证实完成的异常中断。

11. 超时不是单一数值：连接、读取空闲、首字和全程

在真实模型请求中，建议区分：

超时类型 约束对象 典型原因
Connect timeout 建立网络连接所需时间 DNS、TLS、网络不可达
Read timeout 等待网络数据的最长空闲时间 上游卡住、数据长时间不返回
Write timeout 发送请求数据的等待 网络拥塞、上传大输入
Pool timeout 等待连接池可用连接的时间 连接池满、资源排队
First-text deadline 从请求发起到首个可见文本的业务时限 长时间无可见输出
Overall deadline 整次任务最大允许时间 上游不断保活但始终不完成

HTTPX 的 timeout=30 不是“整个响应 30 秒内必须完成”的同义表达，其默认计时主要针对各阶段的网络空闲和资源等待。需要完整请求总时限时，可以在外层使用 asyncio.timeout()；还可以单独记录 TTFT 来识别体验问题。

11.1 HTTPX 的四种超时

python
import httpx

timeout = httpx.Timeout(
    connect=5.0,
    read=30.0,
    write=10.0,
    pool=5.0,
)

client = httpx.AsyncClient(timeout=timeout)
# 服务生命周期结束时调用 await client.aclose()。

11.2 总任务截止时间

python
import asyncio

async def run_with_deadline(operation):
    try:
        async with asyncio.timeout(60.0):
            return await operation()
    except TimeoutError:
        return {"status": "timeout"}

operation() 是演示用的可等待操作工厂。asyncio.timeout() 通过取消当前协程来实施超时，不是直接终止远端模型计算进程；必须配合客户端关闭、取消传播和服务商的可用取消机制。任务不响应取消时，清理甚至可能延长实际返回时间。

11.3 保活注释并不能证明模型仍有业务进展

若 SSE 每隔 10 秒发送 : ping，HTTPX 的读超时可能一直不会触发，因为网络不断收到数据。但模型可能在生成流程上完全没有可见进展。对于业务要求，还应单独设置首个有意义事件时限、最长无有效进度时限与总时限。

12. Python HTTPX：正确读取原始 SSE 流

当 SDK 已经能提供类型化事件时，优先使用 SDK；它会处理协议解析细节。只有在实现协议网关、调试兼容性或对接无 SDK 服务时，才需要手工解析。

下面实现一个简化但遵守核心 SSE 分帧规则的异步解析器：它支持注释、event、data 多行、id，按空行提交事件，不依赖底层网络分块边界。

python
from __future__ import annotations

from collections.abc import AsyncIterable, AsyncIterator

async def parse_sse_lines(lines: AsyncIterable[str]) -> AsyncIterator[dict]:
    name = "message"
    data_parts: list[str] = []
    event_id: str | None = None

    async for line in lines:
        if line == "":
            if data_parts:
                yield {
                    "event": name,
                    "data": "\n".join(data_parts),
                    "id": event_id,
                }
            name = "message"
            data_parts.clear()
            event_id = None
            continue

        if line.startswith(":"):
            continue  # SSE 注释/心跳

        key, has_colon, value = line.partition(":")
        if has_colon and value.startswith(" "):
            value = value[1:]

        if key == "event":
            name = value
        elif key == "data":
            data_parts.append(value)
        elif key == "id" and "\x00" not in value:
            event_id = value
        # retry 字段由需要重连策略的上层消费者处理

    # 根据 SSE 事件边界规则，末尾不完整的未分派事件不当成完成事件。

python
import asyncio
import httpx

async def consume(url: str) -> None:
    timeout = httpx.Timeout(connect=5, read=30, write=10, pool=5)
    async with httpx.AsyncClient(timeout=timeout) as client:
        async with client.stream("GET", url, headers={"Accept": "text/event-stream"}) as r:
            r.raise_for_status()
            if "text/event-stream" not in r.headers.get("content-type", ""):
                raise ValueError("不是 SSE 响应")

            received_done = False
            async for event in parse_sse_lines(r.aiter_lines()):
                if event["event"] == "delta":
                    print(event["data"])
                elif event["event"] == "done":
                    received_done = True
                elif event["event"] == "error":
                    raise RuntimeError(event["data"])
            if not received_done:
                raise RuntimeError("流关闭前未收到完成事件")

if __name__ == "__main__":
    asyncio.run(consume("http://127.0.0.1:8000/chat/stream"))

注意：parse_sse_lines() 演示的是一种应用自定义 delta / done / error 协议。原始 Chat Completions 仅有 data: 的 JSON 事件及 [DONE] 标记，Responses API 则使用不同的 event.type。调用现成大模型服务时必须匹配该服务的真实协议。完整实现还需要处理重连 ID、输入大小上限、未知事件、UTF-8 错误和流量攻击等问题。

13. FastAPI：实现一个完整的本地模拟流式聊天接口

本例不调用付费模型。它提供两个本地接口，展示普通和流式响应，以及流中途出错时的应用级事件。将以下内容保存为 demo_server.py：

python
from __future__ import annotations

import asyncio
import json
from collections.abc import AsyncIterator

from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field

app = FastAPI()

# 演示数据；真实应用替换为具有合理生命周期的模型客户端。
PARTS = ("普通响应", "会等到完整结果；", "流式响应", "会逐步返回。")

class ChatInput(BaseModel):
    message: str = Field(min_length=1)
    fail_after: int | None = Field(default=None, ge=0)


def sse(event: str, data: dict, seq: int) -> str:
    payload = json.dumps(data, ensure_ascii=False)
    return f"event: {event}\nid: {seq}\ndata: {payload}\n\n"


@app.post("/chat")
async def chat(request: ChatInput):
    await asyncio.sleep(0.08 * len(PARTS))
    return {"status": "completed", "answer": "".join(PARTS)}


@app.post("/chat/stream")
async def chat_stream(request: Request, body: ChatInput):
    async def generate() -> AsyncIterator[str]:
        sequence = 0
        parts: list[str] = []
        try:
            for index, part in enumerate(PARTS):
                # 检测连接断开只是一种辅助机制；还需依赖 ASGI 取消传播。
                if await request.is_disconnected():
                    return
                await asyncio.sleep(0.08)  # 模拟模型网络等待
                if body.fail_after is not None and index >= body.fail_after:
                    sequence += 1
                    yield sse("error", {
                        "code": "SIMULATED_UPSTREAM_ERROR",
                        "message": "模拟模型服务在流中失败",
                        "retryable": False,
                    }, sequence)
                    return
                parts.append(part)
                sequence += 1
                yield sse("delta", {"text": part}, sequence)

            sequence += 1
            yield sse("done", {"status": "completed", "text_length": len("".join(parts))}, sequence)
        except asyncio.CancelledError:
            # 不要吞掉取消异常，否则可能导致断开后仍消耗资源。
            raise
        except Exception:
            sequence += 1
            # 面向用户的错误信息不应包含密钥、请求头或内部堆栈。
            yield sse("error", {"code": "INTERNAL_STREAM_ERROR", "retryable": True}, sequence)
        finally:
            # 真实代码在这里释放本请求独占的临时资源。
            pass

    return StreamingResponse(
        generate(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )

13.1 真实工程中的注意点

本例使用局部变量收集文本。生产环境还应加上：请求身份和限流、模型连接复用、并发上限、整体截止时间、可观测性、结果存储、用户取消、反向代理配置及内容审查。若需要处理可靠后台任务，不能把 HTTP 流连接当作唯一的任务状态载体。

14. 前端消费流：为什么必须用增量 UTF-8 解码

JavaScript ReadableStream 返回的 Uint8Array 分块可能在一个汉字的 UTF-8 字节序列中间截断。直接对每块使用不保持状态的解码，可能出现乱码。应使用：

javascript
const decoder = new TextDecoder("utf-8");
const part = decoder.decode(bytes, { stream: true });

{ stream: true } 允许解码器保留不完整的多字节字符，下一段到达时继续处理。

但解码之后仍然不能按“每一块文本就是一条 SSE 事件”的逻辑处理。必须在字符串缓冲区中按 SSE 空行分隔符寻找事件边界，或使用经过测试的 SSE 客户端库。

15. 中途断开：取消、记录状态和重试如何设计

15.1 断开的常见来源

  • 用户关闭页面、点击停止生成、浏览器切换网络。
  • 客户端 AbortController.abort()、Python Task 取消。
  • 负载均衡器、反向代理或运营商网络超时。
  • 上游模型服务中断、重启、限流。
  • 服务端进程崩溃或被强制终止。

15.2 为什么“断开后自动重新调用模型”不等于续传

模型推理可能具有采样随机性、动态上下文及工具副作用。重新发送原来的 Prompt，可能重新生成不同文本、重复计费，甚至重复执行写入类工具。它是一轮新调用，不是原始生成的字节级续传。

若业务要求真正续传，必须额外设计：

  1. 任务 ID 与用户身份绑定。
  2. 持久化事件序号（seq / SSE id）。
  3. 服务器保存已经输出的事件日志。
  4. 客户端重连时提交已消费序号。
  5. 服务端重放遗漏事件，并继续订阅同一个仍在运行的任务（若支持）。
  6. 对写入类工具使用幂等键，避免重复副作用。

Last-Event-ID 只是 SSE 机制的一部分：有 ID 不代表服务端一定支持真正的模型续生成。如果没有持久化日志和会话复用能力，只能提示用户重新生成。

15.3 任务状态建议

text
CREATED → CONNECTED → STREAMING → COMPLETED
                         |              
                         ├─→ FAILED
                         ├─→ TIMED_OUT
                         ├─→ CANCELLED
                         └─→ INTERRUPTED / UNKNOWN

COMPLETED 需要明确的完成事件。INTERRUPTED 表示流失去连接且未得到可靠终态；不能简单写成 FAILED（模型可能已经完成）或 COMPLETED（也可能尚未生成完）。

15.4 部分输出可以保存，但必须带状态

例如：

json
{
  "request_id": "req_example_001",
  "status": "interrupted",
  "partial_text": "这是已经收到但尚未完成的回答",
  "finished_at": null,
  "finish_reason": null,
  "usage": null
}

存储结构还应区分 status（本应用结果）、finish_reason（模型生成结束原因）、transport_error（连接错误）和 usage（可能缺失的累计用量），避免混为一谈。

16. 上游流与下游流之间的代理转发

在浏览器 → FastAPI → 模型服务的结构中，其实存在两条不同的流：

text
浏览器 ←───── 下游 SSE ───── FastAPI ←──── 上游 SSE ──── 模型厂商
          自定义业务事件              第三方模型事件

FastAPI 要完成的事情包括：

  1. 验证用户输入与权限，创建请求 ID。
  2. 通过应用级共享 httpx.AsyncClient 或模型 SDK 建立上游流。
  3. 将上游文本、工具调用和结束原因转换成自身业务协议。
  4. 处理客户端断开时对上游流的取消与关闭。
  5. 在正常/异常/取消时记录业务终态和用量信息。
  6. 严格保证上游响应流结束时连接得到关闭，避免泄露连接池资源。

16.1 HTTPX 流必须关闭

python
import httpx

async def proxy_example(client: httpx.AsyncClient, url: str):
    async with client.stream("GET", url) as response:
        response.raise_for_status()
        async for text_line in response.aiter_lines():
            # 这里的 text_line 只是行，不代表一个完整 SSE 事件。
            yield text_line

通过 async with client.stream(...)，异步生成器正常完成或被取消时，通常能调用上下文管理器清理上游响应资源。若使用 client.send(..., stream=True) 的手动模式，则必须在 finally 或其他可靠的清理路径调用 response.aclose()。

16.2 一个常见生命周期错误

下面的写法不正确：

python
async def wrong(client):
    async with client.stream("GET", "https://example.com") as r:
        return r.aiter_lines()  # 返回时已经离开 async with，响应可能关闭

不能在上游响应对象生命周期结束后，还向下游返回依赖其连接的迭代器。正确方式是把整个上游流生命周期放在异步生成器内部。

17. 长时间流式运行的资源、并发和背压问题

17.1 流式连接会持续占用资源

与一次性短连接相比，长时间 SSE 可能长期占用：HTTP 连接、后端生成任务、连接池槽位、代理缓冲空间和应用状态。不能仅因为每次增量很小就忽略资源限制。

推荐同时实施：最大并发流数、单用户并发配额、单流总时长、上游连接池上限、队列上限、取消处理、可观测性和优雅停机。

17.2 背压（Backpressure）

若上游每秒产生 100 KB，而下游用户网络每秒只能接收 10 KB，直接无界地往内存列表或队列追加，会导致内存不断增长。

常用办法：使用有界队列，让生产者等待消费者；对于可丢弃的进度事件可以合并或降采样，但模型正文及完成/错误等关键事件不能随意丢弃。

17.3 代理缓存可能造成“假流式”

模型上游分块正常，但 Nginx、CDN 或反向代理把小块缓冲到一定大小才转发，用户就可能数秒后突然看到整段文字。需要检查代理的 buffering、gzip、缓存、空闲超时及平台 SSE 支持能力。X-Accel-Buffering: no 在部分 Nginx 配置下有帮助，但不是所有代理都遵循它。

17.4 并发连接与 HTTP/1.1

浏览器对相同源的 HTTP/1.1 连接数可能存在较低限制，多标签页长期占用 SSE 连接可影响其他请求。HTTP/2 的多路复用可以缓解部分连接压力，但仍需要后端资源限额。

18. 流式 JSON、工具调用及安全边界

18.1 增量文本不等于可验证的完整 JSON

例如模型先发：

text
{"name":"角色A","hp":

下一块才发：

text
4}

第一块不完整，所以在中间直接 json.loads() 不合适。应当在确定完整输出后进行 JSON 解析、Schema 验证和业务规则验证。除非使用专门的增量解析器，也不应将“现在解析失败”直接视为生成最终失败。

18.2 流式工具参数不能先执行后校验

可能依次到达：

text
{"user_id":
17,"action":
"delete"}

在工具参数完整、请求权限验证通过、需要的用户确认已完成以前，不能据部分字符串提前执行工具操作。

18.3 安全与 UI

流式输出意味着前端可能看到尚未完成的语句。这与非流式处理的内容审查方式不同；应用应设计必要的输出校验、风险拦截、敏感信息隐藏及失败撤回或提示策略。不要因为中间输出看似合理，就提前把部分内容当成最终的“有来源结论”。

19. 用量、成本和审计：结束事件并不总能收到

对于支持流式最终用量的 API，通常在完成阶段才能拿到可信的累计 Token 用量。若连接中断，可能只有部分文本而没有最终用量统计。

因此建议记录如下指标：

字段 意义
request_id 一次请求的唯一标识
session_id 所属会话
provider/model 模型来源与版本
mode 普通/流式
ttft_ms 首次有效文本增量耗时
duration_ms 完成或异常终止耗时
delta_events 文本增量事件数量
app_status 应用任务完成、失败、取消或未知
finish_reason 模型结束原因（如有）
usage_* 模型实际返回的用量（如有）
usage_observed 是否拿到可信的最终用量
error_type HTTP、超时、协议、上游业务或取消错误

不要用“已收到文本长度 × 固定系数”冒充服务商最终 Token 计费数据。若必须内部估算，应明确标记为估算，并与真实供应商用量账单分开存储。

20. 运行测试与故障注入的知识方法

可靠的流式程序应至少覆盖：

测试情景 预期结果
普通模型响应成功 能读取完整内容、结束原因和用量
多个文本增量 按顺序合并，不丢字、不重复
choices=[] 的用量块 不发生越界访问，正确读取 usage
finish_reason=length 不标记内容完整成功
上游发出流内错误 返回业务错误，不把 HTTP 200 当成功
流未发终止标记就关闭 标记 interrupted
连接超时 标记超时，清理上游连接
用户主动取消 终止读取并释放资源，不吞 CancelledError
中文 UTF-8 跨字节分片 解码后没有乱码
一个 SSE 事件跨多个网络块 能按协议还原完整事件
多行 data: 与心跳注释 正确解析或忽略
JSON/tool arguments 只到一半 不执行工具、不当成合法完整 JSON
服务端关闭/代理中断 任务状态正确，最终用量可缺失
代理缓冲 能区分模型慢、传输慢和前端渲染慢

20.1 离线可执行的 SSE 解析器断言

把第 12 节的 parse_sse_lines 函数放入 sse_parser.py，并创建：

python
import asyncio
from sse_parser import parse_sse_lines

async def simulated_lines():
    for line in [
        ": heartbeat",
        "",
        "event: delta",
        "id: 10",
        'data: {"text":"你好"}',
        "",
        "event: done",
        'data: {"status":"completed"}',
        "",
    ]:
        yield line

async def test():
    result = [event async for event in parse_sse_lines(simulated_lines())]
    assert len(result) == 2
    assert result[0]["event"] == "delta"
    assert result[0]["id"] == "10"
    assert result[1]["event"] == "done"
    print("SSE 解析断言通过")

asyncio.run(test())

httpx.ASGITransport 适合许多应用层集成测试，但测试真实的逐块到达时间、浏览器断开及反向代理行为时，最好使用真实本地 HTTP 端口进行端到端测试；不能仅靠内存传输推断网络时间行为。

21. 常见误解与准确表述

误解 准确理解
stream=True 会让模型推理更快 它通常改善首段反馈体验，不保证降低最终生成总耗时
yield 一次就对应一个 Token yield 输出的是应用层增量，不等于模型 Token
TCP 分块就是 SSE 分块 网络字节块与 SSE 事件边界没有一一对应关系
收到 HTTP 200 就表示成功 进入流后仍可发生业务错误和中途断开
客户端收到 EOF 就说明完成 未收到协议终止事件时只能认为状态未知或不完整
所有 Chat Completions 都有 choices=[] 用量块 OpenAI 和 DeepSeek 的最终用量事件方式存在差异
所有模型流都以 [DONE] 结束 Responses API 和 Anthropic 风格协议有自己的终止事件
HTTPX read timeout 是整个调用超时 主要针对网络读取的空闲等待；总时间需独立限制
SSE 心跳说明模型正在产生有效内容 心跳仅说明仍有传输活动，不证明业务进展
AbortController 能保证立刻停止外部计费 客户端取消不等于上游模型已立即停止
断线重发同样的 Prompt 就是续传 这通常是新请求，可能产生不同输出和重复副作用
流式 JSON 看到一部分就能执行 应等完整内容到达且完成验证，再执行高风险操作

22. 术语索引

  • Non-streaming：一次性返回完整的响应对象。
  • Streaming：按增量发送响应对象或事件。
  • SSE：Server-Sent Events，服务器向客户端推送事件的文本流协议。
  • Delta：增量片段，通常需要顺序拼接。
  • Chunk：API 或网络层分块，具体含义取决于所在层次。
  • Finish Reason：模型为什么结束一次生成。
  • Terminal Event：协议层表示完成、失败或不完整的最后状态事件。
  • TTFT：首个可见文本 Token/片段的延迟指标。
  • Read Timeout：连续等待网络读取数据的超时约束。
  • Overall Deadline：整个操作允许的最大时长。
  • Cancellation：向异步任务发出取消请求，通常是协作式的。
  • Backpressure：下游处理不过来时约束上游生产速度。
  • Resumption / Replay：断线后恢复接收同一个持久化任务的事件。
  • Idempotency：重复执行同一业务操作不会造成重复业务效果。

24. 本节知识归纳

普通响应的关键是一次性获取完整结果后再验证；流式响应的关键是在获得部分结果的同时，持续维护请求状态，直到明确的终止事件出现。

实现可靠的流式模型调用，必须同时分清：

  • 网络字节、SSE 事件与模型文本增量的边界；
  • 正常结束、截断、失败和意外断线的区别；
  • 网络读取空闲超时与业务总截止时间的区别；
  • 取消客户端读取与真正取消上游模型执行的区别；
  • 可显示的部分内容与可提交的最终业务结果的区别；
  • 自动重试与从持久化任务事件日志中真正续传的区别。

结论：流式传输不仅是前端逐字展示，更是一套关于协议、生命周期、错误传播、资源清理和结果一致性的工程机制。
