Python 请求调用链、数据与异常传播、代码变更影响分析

所属模块： Python 基础与异步编程
文档定位： 纯知识讲解、工程原理、代码示例与排查方法。
适用技术： Python 3.11+、FastAPI、Pydantic v2；数据库示例使用标准库 SQLite，拓展说明涉及 SQLAlchemy 2.x。

1. 请求调用链是什么

**请求调用链（request call chain）**指一个请求从进入服务开始，经过认证、参数验证、业务运算、数据库访问、外部服务调用，直到形成响应或失败的全过程。

它至少包含四种不同的关系，不能混为一谈：

  1. 调用关系（call graph）：哪个函数调用了哪个函数。
  2. 数据流（data flow）：输入数据经过哪些读取、转换、校验和存储。
  3. 控制流（control flow）：条件分支、提前返回、重试、超时、异常如何改变执行路径。
  4. 副作用（side effects）：数据库写入、发送消息、扣费、写文件、调用第三方接口等真实状态变化。

例如游戏规则问答服务的概念流程：

text
玩家在前端提交问题
  │ HTTP POST /ask
  ▼
Web Server / ASGI
  │
  ├─ Middleware：请求号、日志等
  ├─ 身份认证/授权依赖（如果启用）
  ├─ FastAPI 路由匹配与 Pydantic 输入校验
  ▼
API 路由函数
  │  把 AskRequest 交给业务服务
  ▼
业务服务 AskService
  ├─ 检查游戏版本、用户权限、业务条件
  ├─ RuleRepository → PostgreSQL / SQLite → 规则数据
  ├─ ModelClient → 外部大模型 API → 生成文本
  └─ AnswerRepository → 数据库 → 保存结果
  │
  ▼
输出对象 AskResponse → FastAPI 响应校验/序列化
  │
  ▼
HTTP 状态码 + JSON → 前端

这里的外部 API 调用与数据库访问是兄弟依赖，并不是数据库一定调用模型，也不是所有请求都必须经过所有节点。不同业务分支可能只有读取数据库，没有外部调用；也可能先发送任务到消息队列再返回 202 Accepted。

1.1 入口不等于 main.py

main.py、app.py 通常用于创建 FastAPI 应用或注册路由，但真正处理某个 HTTP 请求的入口通常是匹配的路由处理函数（path operation）。例如：

python
from fastapi import APIRouter

router = APIRouter(prefix="/rules")

@router.get("/{rule_id}")
def read_rule(rule_id: int):
    ...

调用该函数的不是源码中写出的另一行 read_rule(...)，而是框架在接收到匹配请求后执行它。因此，静态查找“谁显式调用了 read_rule”可能找不到调用者；必须同时查看路由注册和框架约定。

除了 HTTP 路由，以下也可能是程序入口：命令行入口、定时任务、Kafka Consumer 回调、后台 Worker、测试框架钩子和 WebSocket 处理函数。判断入口要看当前故障发生在哪一种运行路径。

2. 从请求入口开始阅读代码

2.1 先定位运行入口和路由

典型工程目录：

text
app/
├── main.py             # FastAPI 应用、路由注册、生命周期
├── api/
│   ├── routes.py       # HTTP 入口
│   └── dependencies.py # 认证、数据库 Session、外部 Client 注入
├── schemas/
│   └── question.py     # 请求/响应模型
├── services/
│   └── ask_service.py  # 业务规则与流程协调
├── repositories/
│   └── rule_repo.py    # 数据库查询与持久化
├── clients/
│   └── model_client.py # 外部 HTTP / SDK 调用
├── models/
│   └── rule.py         # ORM 数据模型
└── core/
    └── errors.py       # 业务异常

找一个接口时，先搜路径字符串、HTTP 装饰器、路由对象和 include_router，再沿函数实现阅读：

bash
# 在仓库根目录执行（需安装 ripgrep）
rg -n 'include_router|APIRouter|@app\.(get|post|put|delete)|@router\.(get|post|put|delete)' app
rg -n '"/ask"|"/rules"|AskRequest|AskService' app

阅读路线：

  1. main.py：应用创建、路由挂载、全局异常处理、生命周期。
  2. api/routes.py：HTTP 方法、路径、请求体、响应模型、依赖。
  3. schemas/：字段类型、默认值、限制、字段别名、是否可为空。
  4. services/：真正的业务规则、条件分支、调用次序。
  5. repositories/：SQL、ORM 查询、事务和写入位置。
  6. clients/：外部服务 URL、超时、鉴权、返回结果解析。
  7. errors.py 与日志：异常如何转换成调用方看得懂的失败。
  8. 测试和前端 API 客户端：接口的实际消费者与既有行为。

2.2 区分声明、注入、调用与执行

python
from typing import Annotated
from fastapi import Depends, FastAPI

app = FastAPI()

def get_user_id() -> int:
    return 123

@app.get("/profile")
def profile(user_id: Annotated[int, Depends(get_user_id)]):
    return {"user_id": user_id}

此处没有写 profile(get_user_id())。FastAPI 的依赖注入系统先执行 get_user_id()，再把结果交给 profile。所以调用链除了显式调用，还包含依赖注入边。依赖自身还可以依赖其他依赖。

装饰器、回调注册、事件订阅、反射、配置驱动和插件机制也会构成隐式调用关系。全文搜索不到函数名的显式调用，不代表它没有被执行。

3. 沿路径理解输入和输出

3.1 输入要分层看

同一个请求的数据可能依次变成不同表示：

所在层 数据形式 主要责任
前端 JS 对象 / 表单 收集用户数据，提示交互错误
HTTP JSON、Header、Path、Query 传输协议和身份凭据
API 边界 Pydantic AskRequest 类型、格式、长度及基础校验
业务层 领域对象或函数参数 版本、权限、业务不变量
数据访问层 SQL 参数 / ORM 对象 查询、写入、约束、事务
外部 Client 第三方 API 请求体 提供商协议、超时、鉴权

例如：

python
from pydantic import BaseModel, Field

class AskRequest(BaseModel):
    character: str = Field(min_length=1, max_length=40)
    version: str = Field(min_length=1, max_length=20)
    question: str = Field(min_length=1, max_length=2000)

请求校验能判断字符串是否为空，却不能证明“这个版本确实存在”，也不能证明“当前用户有权查看这份规则”。后两者通常属于业务层及权限层，不能因数据符合 Schema 就跳过。

3.2 输出也存在不同契约

数据库查询可能返回 ORM 对象，外部模型可能返回 JSON，业务服务可能返回领域结果，最终 API 返回 AskResponse。内部对象不应该未经筛选直接暴露给外部：可能泄露数据库字段、密钥或内部状态。

python
from pydantic import BaseModel

class AskResponse(BaseModel):
    answer_id: int
    answer: str
    source: str

FastAPI 的 response_model 可参与响应校验、序列化及字段过滤。若实际返回结果不符合响应模型，这是服务端契约错误，不能错误地当作用户输入非法。

3.3 数据流的关键问题

沿每个函数记录：

  • 参数从哪里来？是用户输入、数据库、缓存、环境变量还是外部 API？
  • 进入下一层时发生了哪些转换？有没有默认值、截断、标准化、过滤？
  • 返回值为空时是什么意思？“没有记录”“访问被拒绝”“服务失败”不能全部混为 None。
  • 什么数据被写入？写入是否发生在实际响应之前？写入失败是否会回滚？
  • 哪个字段是外部 API 契约？哪个字段只是内部临时变量？

4. 控制流与异常传播

异常和普通返回值是两条不同的传播渠道：

python
def repository():
    raise ConnectionError("DB unavailable")

def service():
    return repository()     # 不会得到正常返回值

def api():
    return service()        # 若无人捕获，异常继续向上

当异常在 repository() 抛出时，该函数之后的正常语句不会继续执行；异常沿调用栈向上传递，直到被相匹配的 except 捕获，或最终被框架的异常处理机制接管。

4.1 三种常见异常处理方式

A. 原样传播：当前层无法做有意义的恢复，通常应让上层处理。

python
try:
    return await repo.get_rule(rule_id)
except DatabaseError:
    logger.exception("查询规则失败")
    raise  # 保留异常类型和当前异常链

B. 转换为领域异常：把数据库或第三方实现细节转换为业务层理解的失败。

python
try:
    await provider.generate(prompt)
except ProviderTimeout as exc:
    raise AnswerGenerationUnavailable("上游模型超时") from exc

raise ... from exc 保留显式异常原因，便于排查根因。

C. 在 API 边界映射为 HTTP：业务层通常不需要直接依赖 HTTP 状态码。

python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

class AnswerGenerationUnavailable(Exception):
    pass

app = FastAPI()

@app.exception_handler(AnswerGenerationUnavailable)
async def upstream_error(request: Request, exc: AnswerGenerationUnavailable):
    return JSONResponse(
        status_code=503,
        content={"code": "MODEL_UNAVAILABLE", "message": "模型暂时不可用"},
    )

4.2 常见失败类型与边界行为

故障 最先发现的位置 典型处理 不应做的事
请求字段缺失 API/Pydantic 返回 422 把错误输入送给模型猜测
对象不存在 Repository / Service 返回 404 或业务空结果 假装数据库宕机
无权限 认证/授权 返回 401 或 403 仅在前端隐藏按钮
数据库不可达 Repository 记录详细错误，服务返回 5xx 假装查询结果为空
外部请求超时 Client 记录超时并返回 504/503，必要时有限重试 无限等待或无界重试
上游响应结构错误 Client 格式校验失败，返回 502 等 将损坏数据写入业务表
事务冲突/唯一性冲突 Database / Service 由业务判定 409、幂等成功或内部错误 单凭异常名猜测最终结果
响应模型校验失败 API 响应阶段 当作服务端缺陷定位 返回 422 指责用户

状态码选择要遵守具体 API 契约。例如 502 通常对应无效上游响应，503 表示服务暂不可用，504 更适合网关/代理等待上游超时的语义；实际系统应统一错误约定，不能机械套用。

4.3 不能吞异常

python
# 反例：失去根因和失败信号
try:
    result = await external_call()
except Exception:
    return {"answer": "", "success": True}

这段代码使调用方以为请求成功，也会污染结果统计。较好的做法是识别具体异常、记录根因、返回稳定的错误代码，并明确哪些错误可重试。

4.4 注意取消、超时和后台任务

异步请求还存在 CancelledError、超时和响应已发送后的错误。调用方断开不一定意味着后台执行已经停止；响应已经发送后，也不能把后续后台任务失败改写为同一个 HTTP 请求的另一个状态码。

尤其要区分：

  • HTTP 请求生命周期：客户端通常等待一次响应。
  • 进程内 Task：由事件循环调度，不天然跨重启持久化。
  • 独立后台任务：通常需要任务记录、队列、Worker 与可查询状态。

5. 数据库调用链与事务

数据库链路需要同时看查询条件、会话生命周期、事务边界、数据约束。

text
Service
  ├─ Repository.get(...) → SELECT → 返回记录/None
  └─ Repository.save(...) → INSERT/UPDATE → COMMIT

5.1 flush 与 commit 的区别

在 SQLAlchemy 中，flush 让待处理更改发送到数据库事务中，但不代表事务已提交；commit 才使当前事务提交。异常时，必须根据事务和 Session 状态执行正确的回滚或让事务上下文负责回滚。

python
# SQLAlchemy AsyncSession 示意
async with session_factory.begin() as session:
    session.add(answer_record)
# 正常离开事务上下文时提交，抛出异常时回滚

Session / AsyncSession 是可变、有状态的工作单元，不应跨并发请求或并发任务共享同一个实例。典型做法是每个请求或每个独立并发任务拥有独立 Session，而 Engine 和连接池可以长期复用。

5.2 数据库事务不能回滚外部 API

例如：

text
调用付费模型成功（费用已经发生）
→ INSERT 答案记录
→ COMMIT 失败

数据库回滚只负责数据库事务，不会撤销外部模型调用、已发送短信或已经提交给第三方的支付操作。对此要区分：

  • 本地数据库原子性：事务。
  • 对外副作用去重：幂等键、唯一约束、提供商幂等能力。
  • 跨系统协调：可靠状态机、Outbox、补偿操作等。

因此修改数据库调用链时必须检查外部副作用发生的顺序，不能简单认为 try/except + rollback 可以恢复整个世界。

6. 外部 API / SDK 调用链

外部服务边界至少应包含：

text
构造请求参数
  → 身份鉴权
  → 网络发送
  → 状态码校验
  → 响应体解析
  → 结构/业务校验
  → 转换为内部返回值或明确失败

Python 示例：

python
import httpx
from pydantic import BaseModel, ValidationError

class ProviderResult(BaseModel):
    answer: str

class ProviderUnavailable(Exception):
    pass

async def generate(client: httpx.AsyncClient, prompt: str) -> str:
    try:
        response = await client.post("/generate", json={"prompt": prompt})
        response.raise_for_status()
        data = ProviderResult.model_validate(response.json())
        return data.answer
    except (httpx.TimeoutException, httpx.RequestError) as exc:
        raise ProviderUnavailable("外部模型网络故障") from exc
    except httpx.HTTPStatusError as exc:
        raise ProviderUnavailable("外部模型返回错误状态") from exc
    except (ValueError, ValidationError) as exc:
        raise ProviderUnavailable("外部模型返回格式异常") from exc

此示例假设 client 已配置 base_url、超时、鉴权等。真实项目应进一步区分可重试与不可重试的上游状态、速率限制以及错误代码；不要将所有失败一律盲目重试。

应在服务生命周期中复用 HTTP Client / 连接池，并在结束时关闭。外部 API 返回的文本或工具结果是不可信数据，不能直接成为程序执行命令或越权修改数据库的依据。

7. 一份可离线运行的完整调用链示例

以下示例用一个文件展示 HTTP → 请求模型 → Service → Repository → SQLite → 外部 Client（模拟）→ 持久化 → 响应。它使用 FastAPI 的普通同步路由 def，配合同步 SQLite 和同步 httpx，避免在 async def 事件循环线程中执行阻塞 I/O。示例重点是读懂调用链，不是展示异步并发最佳实践。

此处“外部服务”通过 httpx.MockTransport 模拟，完全离线，不会请求真实模型或产生 API 费用。 生产系统需要替换为真实 Client、可靠数据库、认证授权和迁移机制。

将下面代码保存为 demo.py：

python
import json
import sqlite3
from contextlib import asynccontextmanager, closing
from pathlib import Path

import httpx
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field, ValidationError

DB_PATH = Path("demo.db")

# ---------- 领域异常：表达业务事实，不直接与 HTTP 耦合 ----------
class RuleNotFound(Exception):
    pass

class ProviderFailure(Exception):
    def __init__(self, message: str, status_code: int = 502):
        super().__init__(message)
        self.status_code = status_code

# ---------- API 的输入与输出契约 ----------
class AskRequest(BaseModel):
    character: str = Field(min_length=1)
    version: str = Field(min_length=1)
    question: str = Field(min_length=1)

class AskResponse(BaseModel):
    answer_id: int
    answer: str
    source: str

class ModelResponse(BaseModel):
    answer: str = Field(min_length=1)

# ---------- 数据库基础设施 / Repository ----------
def init_db() -> None:
    with closing(sqlite3.connect(DB_PATH)) as conn:
        with conn:
            conn.execute("""
                CREATE TABLE IF NOT EXISTS game_rules (
                    character TEXT NOT NULL,
                    version TEXT NOT NULL,
                    content TEXT NOT NULL,
                    PRIMARY KEY (character, version)
                )
            """)
            conn.execute("""
                CREATE TABLE IF NOT EXISTS answers (
                    id INTEGER PRIMARY KEY AUTOINCREMENT,
                    character TEXT NOT NULL,
                    version TEXT NOT NULL,
                    answer TEXT NOT NULL
                )
            """)
            conn.execute("""
                INSERT OR IGNORE INTO game_rules(character, version, content)
                VALUES (?, ?, ?)
            """, ("角色A", "1.0", "角色A的基础生命值为4"))

def find_rule(character: str, version: str) -> str | None:
    with closing(sqlite3.connect(DB_PATH)) as conn:
        row = conn.execute(
            "SELECT content FROM game_rules WHERE character=? AND version=?",
            (character, version),
        ).fetchone()
        return None if row is None else row[0]

def save_answer(character: str, version: str, answer: str) -> int:
    with closing(sqlite3.connect(DB_PATH)) as conn:
        with conn:  # 本地数据库事务：正常提交，异常回滚
            cursor = conn.execute(
                "INSERT INTO answers(character, version, answer) VALUES (?, ?, ?)",
                (character, version, answer),
            )
            answer_id = cursor.lastrowid
        assert answer_id is not None
        return answer_id

# ---------- 外部 Client：这里是离线模拟 ----------
def fake_provider(request: httpx.Request) -> httpx.Response:
    payload = json.loads(request.content)
    if payload["question"] == "simulate_timeout":
        raise httpx.ReadTimeout("模拟上游超时", request=request)
    return httpx.Response(
        200,
        json={"answer": f"依据资料：{payload['rule']}。问题：{payload['question']}"},
    )

def call_provider(client: httpx.Client, question: str, rule: str) -> str:
    try:
        response = client.post("/generate", json={"question": question, "rule": rule})
        response.raise_for_status()
        return ModelResponse.model_validate(response.json()).answer
    except httpx.TimeoutException as exc:
        raise ProviderFailure("上游超时", status_code=504) from exc
    except (httpx.RequestError, httpx.HTTPStatusError,
            ValueError, ValidationError) as exc:
        raise ProviderFailure("上游调用或响应校验失败") from exc

# ---------- Service：连接各个依赖，处理业务条件 ----------
def ask_service(data: AskRequest, client: httpx.Client) -> AskResponse:
    rule = find_rule(data.character, data.version)
    if rule is None:
        raise RuleNotFound("该版本没有对应规则")

    answer = call_provider(client, data.question, rule)
    answer_id = save_answer(data.character, data.version, answer)
    return AskResponse(
        answer_id=answer_id,
        answer=answer,
        source=f"{data.character}@{data.version}",
    )

# ---------- 应用生命周期：创建/释放复用的 Client ----------
@asynccontextmanager
async def lifespan(app: FastAPI):
    init_db()
    with httpx.Client(
        base_url="https://example.invalid",
        transport=httpx.MockTransport(fake_provider),
        timeout=3.0,
    ) as client:
        app.state.provider_client = client
        yield

app = FastAPI(lifespan=lifespan)

# ---------- API 边界：把领域异常映射为 HTTP 错误 ----------
@app.exception_handler(RuleNotFound)
async def rule_not_found(request: Request, exc: RuleNotFound):
    return JSONResponse(status_code=404, content={"code": "RULE_NOT_FOUND"})

@app.exception_handler(ProviderFailure)
async def provider_failed(request: Request, exc: ProviderFailure):
    return JSONResponse(
        status_code=exc.status_code,
        content={"code": "PROVIDER_FAILURE", "message": str(exc)},
    )

# ---------- 真实 HTTP 请求处理入口 ----------
@app.post("/ask", response_model=AskResponse)
def ask_route(data: AskRequest, request: Request) -> AskResponse:
    return ask_service(data, request.app.state.provider_client)

$body = @{character='角色A'; version='1.0'; question='它的生命值是多少？'} | ConvertTo-Json
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/ask' -Method Post -ContentType 'application/json' -Body $body

7.1 沿此例追踪一条成功请求

text
POST /ask
  → AskRequest 校验
  → ask_route(data, request)
  → ask_service(data, client)
  → find_rule(character, version)
  → sqlite3 SELECT
  ← 规则文本
  → call_provider(client, question, rule)
  → httpx.Client.post()
  → fake_provider() 模拟返回 JSON
  ← ModelResponse.answer
  → save_answer(...)
  → sqlite3 INSERT + COMMIT
  ← answer_id
  ← AskResponse
  → FastAPI response_model 序列化
  ← HTTP 200 + JSON

7.2 三条失败路径

路径 A：请求缺字段。AskRequest 校验失败，业务服务根本不会执行；一般返回 422。

路径 B：规则不存在。find_rule() 返回 None，ask_service() 抛 RuleNotFound，全局异常处理器映射为 404；外部 API 和数据库写入不会发生。

路径 C：外部服务超时。fake_provider() 抛 httpx.ReadTimeout，call_provider() 转换为 ProviderFailure(504)，异常一路返回到全局处理器；save_answer() 不会执行。

这里采用的是先调用外部 API、成功后才写数据库的顺序。即使最终保存失败，上游调用也可能已经花费资源；这与数据库事务的原子性并不冲突。

7.3 为什么这里不写 async def ask_route？

示例中 sqlite3 和 httpx.Client 是同步阻塞 API。FastAPI 的普通 def 路由通常运行于线程池，因此不会直接阻塞异步事件循环线程。若改为 async def 路由，应该将数据库层换成 SQLAlchemy AsyncSession + 异步驱动，并把 HTTP 层换成 httpx.AsyncClient，在相应位置 await。只把 def 改成 async def，不会自动使同步 I/O 异步化。

7.4 当前示例的限制

  • 无认证授权，不能直接用于真实多用户服务。
  • SQLite 适合演示，不代替生产 PostgreSQL 的事务/连接池/迁移设计。
  • 没有请求幂等键；每次成功请求都会新增一条答案记录。
  • 模型是离线 Mock，不是实际 LLM，也不代表模型答案可靠。
  • 尚未添加结构化日志、链路追踪、重试预算、业务超时和性能指标。

8. 修改已有代码前，如何找调用方

阅读函数定义只告诉你它做什么；搜索调用方才能知道改动会影响谁。

8.1 静态搜索

假设准备修改 ask_service：

bash
rg -n 'def ask_service|ask_service\(' .
rg -n 'from .* import ask_service|import .*ask_service' .
rg -n 'AskRequest|AskResponse|/ask' .

还要检查：

  • API 路由及其 Pydantic Schema；
  • 测试对服务的直接调用；
  • Worker、定时任务或脚本对同一服务的复用；
  • 是否被依赖注入、注册回调、路由装饰器或动态映射引用；
  • 前端的调用代码、移动端的调用协议、OpenAPI 文档；
  • 数据库迁移、缓存键、消息 Schema、监控指标中的隐式依赖。

VS Code 的 Find All References、Go to Definition、Call Hierarchy 可以快速查看符号关系；但动态语言中的反射、字符串路径、框架注册和外部消费者不一定能被静态工具完整发现。

8.2 区分正向依赖和反向依赖

text
ask_route ──调用──> ask_service ──调用──> find_rule
                                └──调用──> call_provider

对于 ask_service：

  • 下游依赖：find_rule、call_provider 等它所调用的对象。
  • 上游调用方：ask_route、其他脚本、测试、Worker 等调用它的对象。

修改一个函数的签名，主要先找上游调用方；改变查询逻辑、异常类型或副作用，则上下游都可能受影响。

9. 什么叫“影响范围”

影响范围不仅是“哪些文件需要改”，而是哪些契约、状态和行为可能变化。

变更维度 典型问题
输入契约 是否新增必填字段、改变默认值、字段别名或允许范围？
输出契约 是否删除/重命名字段，改变空值含义或状态码？
调用关系 是否有其他 API、Worker、测试复用同一函数？
数据库 是否需要新增列、索引、唯一约束和迁移？
外部 API 请求参数、授权、配额、超时和费用是否变化？
副作用 是否提前写库、重复发送、覆盖旧状态或多次计费？
并发 是否共享了可变对象、Session、Client 或锁？
缓存 缓存 Key、TTL、版本过滤及失效逻辑是否变化？
错误处理 旧的异常、错误码和重试行为是否还成立？
安全 身份与数据范围是否被后端强制验证？
可观测性 关键日志、请求号、Trace 和指标是否仍能定位问题？
兼容性 旧前端、旧数据、已有任务、第三方消费者是否还能工作？

9.1 具体案例：把“规则查询”改成“按版本查询”

旧接口：

python
def get_rule(character: str) -> str | None: ...

新需求：不同版本同名角色规则不同。准备改成：

python
def get_rule(character: str, version: str) -> str | None: ...

表面上只加了一个参数，实际需要核对：

  1. 调用方：所有 get_rule(...) 是否提供 version，包括任务和脚本。
  2. HTTP 契约：前端从哪里获得版本？旧请求没有版本时如何处理？
  3. 数据模型：是否真的保存了版本，旧记录如何迁移或标记未知？
  4. 查询语义：版本不存在返回 404、询问版本，还是使用默认版本？不能静默使用最新版本掩盖问题。
  5. 缓存：原 Key rule:角色A 必须考虑变为 rule:1.0:角色A，否则混用版本。
  6. RAG：向量检索元数据也要过滤版本，引用必须标识来源版本。
  7. 业务异常：RuleNotFound 是否区分角色不存在和版本不支持？
  8. 测试：覆盖旧版本、新版本、无版本、版本冲突、缓存命中等路径。
  9. 外部协议：如果有移动端旧版本，必须选择明确的兼容策略并更新文档。

这说明：局部参数变化可能造成全链路语义变化。

10. 如何系统地确定变更风险

10.1 基线、修改和回归验证

text
先重现既有行为
    ↓
确认入口、上下游依赖与外部契约
    ↓
查清数据流、异常流、资源和副作用
    ↓
明确新行为与兼容策略
    ↓
编写或更新最小测试
    ↓
实施尽量局部的修改
    ↓
运行相关测试、集成测试与真实调用
    ↓
检查日志、数据状态、性能与副作用

修改之前要有基线：当前测试通过多少、某个请求目前是什么响应、数据库原本写入什么、哪些失败能复现。没有基线，修改后很难证明“修复了问题而没有破坏其他功能”。

10.2 推荐使用的 Git / 搜索命令

bash
git status --short
git diff --stat
git diff -- app/services/ask_service.py
git grep -n 'get_rule'
rg -n 'get_rule\(' .

它们用于确定当前工作区是否干净、改了哪些文件、函数在哪些地方出现；但不能代替运行时测试。对于被多人共享的仓库，不能不检查当前修改就直接重置、覆盖或强推。

11. 调试调用链：日志、请求号与分布式追踪

11.1 日志和 Traceback 的角色

**日志（log）**记录发生了什么；**异常堆栈（traceback）**显示抛出异常时的 Python 调用栈；分布式 Trace 可跨 HTTP、数据库、服务和消息队列建立关联。

单次请求最好拥有一个 request_id；跨服务追踪可使用 trace_id、span_id。这两者可相关联，但语义不同：一个是应用层标识，一个属于追踪上下文。

推荐记录：

text
request_id=... route=/ask user_id=... （脱敏/最小化）
service=ask stage=rule_lookup duration_ms=...
service=ask stage=model_call duration_ms=... status=timeout
service=ask stage=persist result=skipped
error_code=PROVIDER_FAILURE trace_id=...

不应将 API Key、密码、完整私人聊天或敏感数据库内容直接写入日志。

11.2 先找第一个失败点，而不是最后一个报错位置

前端出现 500，只说明请求失败，不能证明错误发生在路由函数。应结合日志定位：

  1. 请求是否抵达后端？
  2. 是否通过认证和 Pydantic 校验？
  3. 哪个 Service 方法被执行？
  4. SQL 查询是否正常、记录是否存在？
  5. 是否进入外部 Client？外部状态码、超时和格式是否正常？
  6. 是否发生写库、提交、重试或副作用？
  7. 异常在何处被捕获、转换或吞掉？
  8. 最终为什么产生对应的 HTTP 状态码？

对异步/消息队列系统还需要判断：当前日志是否对应同一个请求，还是另一个独立的后台任务；是否存在跨进程的上下文传播中断。

12. 测试应覆盖什么

12.1 调用链测试的层次

  • 单元测试：Service 使用假 Repository、假模型 Client，验证业务条件和错误转换。
  • 接口测试：用 FastAPI TestClient 或异步测试客户端检查 HTTP 契约和状态码。
  • 数据库集成测试：验证 SQL、事务、唯一约束和数据迁移。
  • 外部契约测试：检查真实 SDK 或模拟响应格式变化时的行为。
  • 端到端测试：从前端实际交互到后端和持久化，核对用户感知结果。

针对前文 demo.py，最小接口测试：

python
from fastapi.testclient import TestClient
from demo import app

def test_rule_success():
    with TestClient(app) as client:
        response = client.post("/ask", json={
            "character": "角色A", "version": "1.0", "question": "生命值是多少？"
        })
        assert response.status_code == 200
        payload = response.json()
        assert payload["source"] == "角色A@1.0"
        assert payload["answer_id"] > 0

def test_rule_not_found():
    with TestClient(app) as client:
        response = client.post("/ask", json={
            "character": "不存在", "version": "1.0", "question": "技能是什么？"
        })
        assert response.status_code == 404
        assert response.json()["code"] == "RULE_NOT_FOUND"

def test_provider_timeout():
    with TestClient(app) as client:
        response = client.post("/ask", json={
            "character": "角色A", "version": "1.0", "question": "simulate_timeout"
        })
        assert response.status_code == 504

def test_invalid_input():
    with TestClient(app) as client:
        response = client.post("/ask", json={
            "character": "角色A", "version": "1.0", "question": ""
        })
        assert response.status_code == 422

14. 常见误区汇总

  1. 看到 main.py 就认为掌握了请求入口。 真正请求会执行哪个路由，取决于注册与匹配。
  2. 只搜索显式调用，不看 Depends、装饰器和回调。 可能遗漏隐藏的执行路径。
  3. 把 Pydantic 校验等同于业务正确。 格式正确不代表版本存在、用户有权限或答案有依据。
  4. 把数据库返回 None 等同于连接失败。 “记录不存在”与“查询执行失败”有不同语义。
  5. 把异常转成成功响应。 造成假成功和后续数据污染。
  6. 认为 async def 自动解决阻塞。 直接调用同步数据库或 HTTP 客户端仍会阻塞事件循环线程。
  7. 只改函数定义，不找调用方。 很容易破坏其他路由、任务或测试。
  8. 把一次 SQL 的 flush 当作已提交。 事务可能尚未提交，也可能稍后回滚。
  9. 认为数据库回滚能撤销外部 API。 跨系统副作用不能通过本地事务自动恢复。
  10. 以接口返回 200 作为唯一成功标准。 仍需检查落库、引用、权限、重试和用户可见结果。

15. 知识结论

读懂一个已有 Python 服务，核心不在于能够逐行翻译代码，而是能够重建以下四条路径：

  • 调用路径：请求入口 → 路由 → 业务 → 数据库/外部服务。
  • 数据路径：输入 Schema → 业务参数 → 持久化/外部数据 → 输出 Schema。
  • 错误路径：异常发生点 → 捕获/转换 → HTTP 或任务错误结果。
  • 状态路径：什么操作改变了真实状态、什么时候提交、失败时还能否恢复。

修改代码前则要完成反向追踪：谁在调用此功能、谁依赖其输入输出契约、哪些数据库记录或外部系统会受到影响。只有把调用链与影响面同时弄清楚，才能从“能修改代码”提升到“能可靠维护已有工程”。
