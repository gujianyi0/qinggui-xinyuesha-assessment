1. 从“至少一次投递”开始

1.1 At-least-once 的准确含义

Kafka 消费者常见的处理方式是：读取消息、完成业务、提交消费位点（Offset）。如果业务操作已经成功，但位点尚未提交便发生崩溃或重平衡，后续消费者就可能再次读到这条消息。

因此，在正确配置和满足相应持久性假设时，至少一次（At-least-once）语义允许同一逻辑消息被交付一次或多次。它重视不遗漏已可靠投递的消息，却不会自动保证下游业务只产生一次效果。

必须把以下概念拆开：

  • 交付（Delivery）：Kafka 将记录交给消费端。
  • 处理尝试（Attempt）：某个 Worker 试图处理它。
  • 数据库提交（Database Commit）：业务结果在数据库内完成提交。
  • 消费位点提交（Offset Commit）：Kafka 记录该消费组下一次从哪里继续读取。
  • 业务效果（Business Effect）：反馈记录被创建、余额被改变、邮件被发送、资料被索引等实际后果。

这些操作并不天然构成同一个原子事务。

1.2 为什么重投不是 Kafka 的 Bug

考虑如下故障时间线：

text
时刻 T1：Consumer 读到事件 E，位点 offset=15
时刻 T2：Consumer 将反馈记录写入 PostgreSQL
时刻 T3：PostgreSQL COMMIT 成功
时刻 T4：Worker 崩溃，还没提交 Kafka offset=16
时刻 T5：新的 Worker 从上次已提交的位置恢复
时刻 T6：事件 E 再次被读取

如果在 T6 无条件执行 INSERT，就会产生第二份业务记录。这个重复是消费恢复的正常后果；正确系统应当把它识别为既有操作，而非再次产生业务副作用。

1.3 重复发生的几种不同原因

  1. 消费端重新交付：业务完成后位点没有成功提交。
  2. 生产端重复发布：生产端在网络超时后无法确认先前发送是否成功，于是再次发布逻辑相同的事件。
  3. 重平衡与并发：消费者归属变化时，旧执行尚未完全结束，新消费者可能继续处理同一逻辑任务。
  4. 客户端重复发起：浏览器双击提交、网络重试或业务系统重新派发任务。
  5. 应用层错误：定时任务或恢复程序重新创建了已存在的操作。

这些来源不一定共享相同的 Kafka 物理位置或事件标识，需要从消息层和业务层同时处理。

2. 五种容易混淆的标识

2.1 标识对照表

标识 示例 表示什么 通常是否稳定
event_id / message_id evt-8c5 一条逻辑事件的身份 同一事件重投时应保持稳定
topic + partition + offset feedbacks/2/15 Kafka 日志中的一条物理记录的位置 对该条日志记录稳定；重复发布可能有新 Offset
business_idempotency_key confirm-2026-001 一次逻辑业务操作的身份 同一次操作的所有重试必须一致
correlation_id trace-user-request-31 将一组相关请求、事件或结果串起来 可以跨多条不同事件共用
attempt_id attempt-04 一次具体执行尝试 每次重试都可以不同

Kafka 自身并不自动为业务提供可用于跨重复发布去重的通用 event_id；需要生产端通过消息体或 Header 定义并维护稳定的事件身份。

2.2 Message Key 不是 Message ID

Kafka 记录还可以包含一个 key（消息键），它常用于分区选择或分组语义。例如 user-123 的消息可以通过一致分区策略路由到同一分区。但多个不同事件完全可以共享同一个 Kafka Key。

text
Kafka key = user-123
事件 1：用户注册
事件 2：用户修改昵称
事件 3：用户修改昵称（另一次真实操作）

因此不能直接把 Kafka 的 key 认作每条消息的唯一编号，也不能把 offset 认作业务操作 ID。

2.3 Correlation ID 不是幂等键

一个导入请求可能产生三条事件：DocumentParsed、EmbeddingCreated、IndexActivated。它们可能共用一个 correlation_id，用于追踪业务链路，但不是同一事件，也不能合并成一个结果。

错误设计：把所有使用同一 correlation_id 的事件都判定为重复。

正确设计：用 Correlation ID 建立关联；用 Event ID 识别事件；用业务操作键决定哪些副作用必须保持唯一。

2.4 标识必须带正确作用域

event_id 可能只在特定事件源内唯一；operation_id 可能只在特定租户内唯一。因此唯一约束应体现其真实作用域。例如：

sql
PRIMARY KEY (consumer_group, source, event_id)
UNIQUE (tenant_id, operation_id)

不能默认所有系统使用的字符串 ID 都天然全局唯一。

3. 三个核心机制到底分别解决什么问题

3.1 消息标识：辨认“是不是同一个事件”

如果同一事件 evt-001 在故障恢复后被再次交付：

text
第一次：event_id=evt-001 → 处理成功
第二次：event_id=evt-001 → 发现已处理，跳过业务操作

可以在 processed_events / Inbox 表中记录已处理的事件 ID。它主要解决同一逻辑事件的重复交付和审计。

但如果原生产者重新发布一条新事件，分配了新的 ID：

text
event_id=evt-001, operation_id=confirm-001

event_id=evt-002, operation_id=confirm-001

单靠 Event ID 会认为是两条不同事件。此时还需要业务层去重。

3.2 业务幂等键：辨认“是不是同一次操作”

业务幂等键（Idempotency Key）不是“消息出现在哪”的编号，而是“用户究竟想执行哪次业务”的编号。

例如用户确认一条反馈：

json
{
  "tenant_id": "team-a",
  "operation_id": "confirm-001",
  "event_id": "evt-1001",
  "content": "角色技能描述不准确"
}

客户端等待超时，重试时产生了新事件：

json
{
  "tenant_id": "team-a",
  "operation_id": "confirm-001",
  "event_id": "evt-1002",
  "content": "角色技能描述不准确"
}

对于业务而言，这仍然是同一次确认。需要把同一 tenant_id + operation_id 关联到相同的最终结果。

关键条件：业务幂等键必须由真正代表该次操作的可信流程产生并在重试中复用。 如果每次 HTTP 重试都生成新的业务键，幂等性便失效。

3.3 最终结果唯一约束：让数据库执行不可违反的规则

业务程序可以先查询“有没有相同结果”，但仅有这一步不够。两个并发 Worker 可能都读到“不存在”，随后都试图写入。

text
Worker A：SELECT → 不存在
Worker B：SELECT → 不存在
Worker A：INSERT → 成功
Worker B：INSERT → 如果没有 UNIQUE，也成功 → 重复记录

为最终结果建立唯一约束：

sql
CREATE UNIQUE INDEX uq_feedback_operation
ON feedback_results (tenant_id, operation_id);

数据库将该业务不变量放在最终写入处强制执行。对于 PostgreSQL，可配合 INSERT ... ON CONFLICT 处理冲突，但在冲突后还应核对同一业务键是否对应相同内容，不能静默接受不同内容。

3.4 三者的互补关系

text
Event ID / processed_events
      解决：重复交付、事件审计
                 ↓
Business Idempotency Key
      解决：多条消息代表同一次业务
                 ↓
UNIQUE + Transaction
      解决：并发情况下最终结果只创建一次，且不出现部分写入

数据库唯一约束是最终数据不变量的强制执行点；消息标识和业务幂等键为它提供不同层次的身份语义。

4. 幂等性在数学与业务中的含义

4.1 幂等性的状态含义

对同一个逻辑操作 x，当操作第一次执行产生状态 S1 后，再次执行它不应产生新的业务效果：

[ F(F(S,x),x)=F(S,x) ]

这不代表每一次执行的 HTTP 状态码、审计时间或执行次数都必须完全相同；它强调业务可观察的目标效果保持一致。

4.2 天然幂等与非幂等操作

操作 通常是否天然幂等 说明
SET balance = 100 在受控并发与相同前提下是 重复赋相同值不继续累积
balance = balance + 100 否 重试会重复增加
UPDATE task SET status='DONE' 在状态转换约束充分时可能是 不能用它掩盖终态覆盖风险
INSERT feedback 通常否 可能重复创建反馈
DELETE WHERE id=... 对最终资源不存在的状态通常是 仍需区分审计、级联与副作用
向外部 API 发邮件 不可默认幂等 请求重试可能重复发送

天然幂等性不能代替对象授权、事务、一致性和状态机控制。

4.3 幂等键冲突要区分“同操作重试”与“篡改内容”

如果调用方再次使用 confirm-001，但把反馈正文改为另一条内容，不能把它直接当成合法重试：

text
相同 operation_id + 相同规范化业务内容 → 返回已有结果
相同 operation_id + 不同规范化业务内容 → 拒绝，报告幂等键冲突

一个常用实现是记录 payload_hash，用稳定的业务字段经过规范化序列化后计算 SHA-256。要注意：JSON 对象字段顺序、浮点数表示、Unicode 规范化、时间精度以及不应计入身份的临时字段，都需要明确规范；简单哈希不能取代业务语义判断。

5. 正确设计业务幂等键

5.1 按“操作”而非“资源”设计

假设文档 document-88 在不同日期合法导入两次，对应版本 A 和版本 B。如果把 document-88 永远作为幂等键，第二次真正更新可能被误删。

更合适的是：

text
operation_id = import-document-88-version-A
operation_id = import-document-88-version-B

也可以使用由入口服务生成的稳定 UUID，再把文档 ID 与资料版本作为受控参数保存。

5.2 租户隔离

同一业务键在不同租户中可能合法重复。因此最终唯一键通常为：

sql
UNIQUE (tenant_id, operation_id)

如果一种操作同时涉及多个业务实体，可能还需要引入 operation_type，但不要在没有需求时堆砌标识。

5.3 生命周期与保留周期

若幂等记录只保留 24 小时，但 Kafka 中的旧消息可能在一周后重新处理，已过期的键可能失去去重能力。因此必须对齐：

  • Kafka 重投和人工重放的最长期限。
  • 消费组位点回退的可操作范围。
  • 业务允许再次执行的语义。
  • Inbox 去重记录的保留策略。
  • 最终结果的持久保存与归档策略。

删除 Inbox 记录后，只要最终结果的唯一键仍然存在，同一业务键的重复写入仍可被阻止。 但如果两层记录同时被清除，系统可能无法识别旧操作。

6. PostgreSQL 的数据模型

下面以“玩家反馈确认”作为固定业务场景：一个用户一次确认只能生成一条最终反馈，而系统可能收到同事件重投或多事件重复请求。

sql
CREATE TABLE feedback_results (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id       TEXT NOT NULL,
    operation_id    TEXT NOT NULL,
    payload_hash    TEXT NOT NULL,
    feedback_json   JSONB NOT NULL,
    status          TEXT NOT NULL DEFAULT 'SUCCEEDED',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, operation_id)
);

CREATE TABLE processed_events (
    consumer_group  TEXT NOT NULL,
    source          TEXT NOT NULL,
    event_id        TEXT NOT NULL,
    event_hash      TEXT NOT NULL,
    tenant_id       TEXT NOT NULL,
    operation_id    TEXT NOT NULL,
    processed_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_group, source, event_id)
);

processed_events 解决特定消费者处理过哪些逻辑事件的问题；feedback_results 保证业务结果唯一。两张表不能简单互相替代。

6.1 并发写入时使用 ON CONFLICT

sql
INSERT INTO feedback_results
    (tenant_id, operation_id, payload_hash, feedback_json)
VALUES
    ($1, $2, $3, $4)
ON CONFLICT (tenant_id, operation_id) DO NOTHING
RETURNING id;

如果插入没有返回记录，可能已经有相同业务键的结果。此时仍应在事务中查询旧结果，比较 payload_hash：

  • 一致：作为重复操作，使用已提交的最终结果。
  • 不一致：返回 Idempotency Conflict，而不是默默忽略新的不同内容。

注意在特定隔离级别或并发快照下，冲突处理与后续可见性可能需要额外处理（例如重新查询或重试事务）。不能仅凭一次没有返回行就武断判断全部原因。

6.2 业务结果与 Inbox 必须在同一个事务

text
BEGIN
  ├─ 检查消息是否已经处理
  ├─ 检查业务幂等键
  ├─ 首次执行则创建最终反馈
  └─ 插入 processed_events
COMMIT
↓
提交 Kafka Offset

如果把“最终反馈写入”和“已处理事件标记”拆成两个独立事务，就可能出现业务已经成功但 Inbox 记录未写入，增加恢复的复杂度。

6.3 为什么“先查再插”无法解决竞态

即使业务层写了：

python
if not exists(operation_id):
    insert_feedback()

多个 Worker 仍可能同时通过 exists() 判断。只有数据库约束、事务和正确的冲突处理，才能在真正并发的执行条件下保证不变量。

7. 完整的重复消费和故障恢复时间线

7.1 正常路径

text
Kafka E1 (offset=20)
    ↓
读取并校验 event_id、operation_id
    ↓
BEGIN 数据库事务
    ↓
创建业务结果 + Inbox 记录
    ↓
COMMIT 成功
    ↓
提交 Kafka offset=21

7.2 故障矩阵

故障发生位置 数据库状态 Kafka 位点 恢复处理
业务事务开始前 未写入 通常未推进 重新处理消息
业务事务执行中崩溃 未提交事务回滚 通常未推进 再次处理
业务事务提交成功后崩溃 业务结果已持久化 可能未推进 重投后由 Inbox / 业务键识别
Offset Commit 发出但结果未知 业务已持久化 可能已提交，也可能未提交 查询恢复位置；重复时幂等跳过
同事件被两个 Worker 并发执行 可能存在竞争 各自处理状态不确定 数据库 UNIQUE 与事务裁决

Kafka 提交进度为下一条应该读取的 Offset。如果已经安全完成 offset=20，则提交的是 21，而不是 20。

7.3 同分区并发处理的额外问题

如果分区的 offset=20 和 offset=21 同时交给两个内部任务处理：

text
offset=21 先完成
offset=20 还在运行

此时不能直接提交 offset=22，因为这样会越过尚未完成的 20，导致重启后可能漏掉 20。需要按分区维护“连续完成水位”，或先采用同分区顺序处理。

业务幂等保护的是重复产生的效果，不能替代正确的 Offset 提交顺序。

8. 消息标识和业务键冲突时应该怎样处理

8.1 相同 Event ID + 相同内容

这是典型的重复交付；可返回 ALREADY_PROCESSED_EVENT，无需再次执行业务。

8.2 不同 Event ID + 相同业务键 + 相同内容

这通常是同一业务操作被重新发布。应返回已有业务结果，但可以按消费者作用域记录第二条实际事件，方便追踪消息传播。

8.3 相同 Event ID + 不同内容

不应悄悄接受，因为逻辑事件身份被复用，却指向不同消息。应标记 EVENT_IDENTITY_CONFLICT，记录事件源，并进入人工排查或错误流程。

8.4 相同业务键 + 不同内容

不应把新内容覆盖旧内容，也不应返回“成功执行了新操作”。应标记 IDEMPOTENCY_KEY_CONFLICT，提示调用方换新操作身份，或重新确认真正想要执行的业务。

8.5 相同内容 + 不同业务键

两次真正独立的反馈确认，即使正文一致，也可能需要保存两条结果。不能单凭文本相似或哈希相同判定为重复。

9. 不同 Consumer Group 的去重状态为什么不同

如果 analytics-group 和 feedback-group 都订阅相同 Topic，它们负责不同的业务消费结果。

  • processed_events 一般以 consumer_group + source + event_id 为唯一键。
  • 相同 Event ID 可以被两个不同消费组分别处理。
  • 不应让分析系统处理过事件，就阻止反馈系统处理它。

本教程示例故意把全局业务最终结果设计成一份：两个组收到同一个 operation_id 时不会创建重复最终反馈，但各自可记录已处理事件。真实项目中，不同业务消费组通常维护各自不同的结果表或去重命名空间，不应误把所有消费组都绑定到同一个最终结果表。

10. Kafka 的幂等 Producer 与业务幂等不是一回事

Kafka 支持幂等 Producer，目的是抑制同一 Producer 会话中因协议级重试产生的重复日志写入。Kafka 事务还可以协调 Kafka 内部消息消费与生产的恰好一次处理场景。

但以下行为不会自动被 Kafka 的 Producer 幂等性识别为相同业务：

text
HTTP 请求 #1 → 应用构造 evt-A → Producer 发送
HTTP 重试   → 应用重新构造 evt-B → Producer 发送

两条应用层独立构造的事件并非 Producer 协议级的同一发送尝试。更重要的是，Kafka 内部 EOS（Exactly-Once Semantics）并不能自动使 PostgreSQL、邮件服务或支付系统中的副作用恰好发生一次。

传输层、事件层、业务层的“恰好一次”必须分别定义保障范围。

参考 Kafka 设计文档关于投递语义、幂等生产者及事务范围的说明：https://kafka.apache.org/documentation/

11. 外部副作用：为什么数据库唯一约束仍可能不够

假设 Worker 需要发送一封通知邮件：

  1. Worker 调用邮件 API。
  2. 邮件服务已经接受请求。
  3. Worker 在保存发送成功状态前崩溃。
  4. Kafka 重投消息。
  5. Worker 再次调用邮件 API。

数据库里面即使只有一条反馈结果，外部邮件也可能被发送两次。数据库事务无法回滚外部服务已经发生的动作。

可选解决方式包括：

  • 使用外部服务支持的幂等请求 ID，并保持重试使用同一个 ID。
  • 使用 Transactional Outbox 将发送意图与业务记录原子落库，再异步发送。
  • 记录 PENDING / SENDING / SENT / UNKNOWN 等状态，对结果未知的发送进行对账，而不是盲目重试。
  • 如果外部服务不具备可核查的幂等能力，要承认无法保证绝对“仅发送一次”。

Outbox 保证的是数据库事件意图不因发布过程故障而丢失；它本身并不自动消除消费者重复处理或第三方重复副作用。

12. 面向模型调用与资料导入的特殊考虑

12.1 批量 Embedding

资料版本 doc-55:v3 的 Embedding 任务可能重试多次。合理的业务键可以是：

text
embedding:<document_id>:<version>:<model_id>:<chunking_version>

其中真正影响结果语义的模型和分块配置应明确纳入操作身份，而不是把所有版本的索引混为一条。

12.2 大模型 API 调用

本地数据库幂等只能保证最终结果记录不会重复，不必然保证模型 API 没有被重复调用或计费。如果第一次模型返回成功但结果尚未持久化便崩溃，重试可能再次产生费用。要在预算管理中记录该风险。

12.3 用户确认操作

一次“确认提交”必须复用同一个 confirmation_id。若用户修改了内容，应创建新的草稿版本与新的确认操作身份，不能在相同业务键上偷偷替换待执行内容。

可以分别记录：

指标 解释

14. 易错实现与反例

14.1 错误：只用内存 Set 去重

python
processed_ids: set[str] = set()

进程重启、多个 Worker 或跨服务器部署后，状态无法可靠共享和恢复。可用于局部优化，不能作为最终可靠性保证。

14.2 错误：只用 Redis 的 SETNX

Redis 原子键操作可以帮助控制短期竞争，但键到期、主从故障、缓存丢失或锁租约过期时，仍可能再执行。关键业务结果应依赖数据库的唯一约束和事务。

14.3 错误：先查数据库，后插入，但没有 UNIQUE

并发请求都可能通过“检查不存在”，然后各自创建记录。必须在数据库层建立最终约束。

14.4 错误：同一个操作重试生成新的业务键

python
# 错误：每次重试都重新生成 operation_id
operation_id = str(uuid.uuid4())

如果这是同一次逻辑操作的重试，必须复用最初的 operation_id。

14.5 错误：只看 Kafka Offset 去重

Kafka Offset 标识具体分区日志位置。应用重复发布的两条事件可能拥有不同 Offset，却代表同一次业务。

14.6 错误：对所有重复消息直接抛异常并无限重试

已成功的重复业务应该作为可正常确认的处理结果，安全推进 Offset；不可恢复的数据冲突则应通过明确的失败记录与 DLQ/人工处理流程结束，避免阻塞分区。

import asyncio
import json
from aiokafka import AIOKafkaConsumer, TopicPartition

async def consume_forever(store):
    consumer = AIOKafkaConsumer(
        "feedback-events",
        bootstrap_servers="localhost:9092",
        group_id="feedback-worker-v1",
        enable_auto_commit=False,
        auto_offset_reset="earliest",
    )
    await consumer.start()
    try:
        async for msg in consumer:
            payload = json.loads(msg.value.decode("utf-8"))
            # 这里应通过 Pydantic 等机制校验 payload，
            # 并从经过认证的可信链路确定 tenant_id。
            event = Event(
                tenant_id=payload["tenant_id"],
                operation_id=payload["operation_id"],
                event_id=payload["event_id"],
                source=payload["source"],
                body=payload["body"],
            )
            # store.apply 是同步数据库操作。此处为示意，
            # 使用线程卸载，不阻塞 asyncio 事件循环。
            # 生产环境可替换为 SQLAlchemy AsyncSession。
            outcome = await asyncio.to_thread(store.apply, event)
            print("result:", outcome)
            tp = TopicPartition(msg.topic, msg.partition)
            await consumer.commit({tp: msg.offset + 1})
    finally:
        await consumer.stop()

接入示例的边界条件：

  • Event 与 Store 来自文档后面的本地示例代码；实际程序须显式导入。
  • 一次只处理一个获取到的消息，再提交该分区的位点；不展示批量乱序提交。
  • 异常时不推进当前消息的 Offset；生产环境还需要明确的错误分类、重试上限、DLQ、Rebalance Listener 和优雅停机控制。
  • 真实 tenant_id 不能只因为消息中写了该字段就直接视为已经授权。
  • 在外部消息内容已经损坏、永远无法处理时，不能无限卡住分区；要先持久记录失败，再按策略推进。

17. 常见问题的边界澄清

Q：有了 UNIQUE(tenant_id, operation_id)，还需要 Event ID 吗？
需要视业务而定。唯一约束能够确保最终业务结果不重复，但 Event ID 仍可用于事件级审计、检测消息身份异常、不同消费组独立去重与重放诊断。并非所有系统都必须建立两张表，但两种身份语义不能混为一谈。

Q：是否应该用请求正文哈希作为幂等键？
一般不建议直接这样做。同样的正文可能对应两次合法操作，而不同但语义等价的正文也未必应该重复执行。应先定义逻辑操作身份，再用哈希辅助检测同一键下的参数是否变化。

Q：只使用 Kafka Producer 的 enable.idempotence=true 可以吗？
不够。它主要解决生产端重试写入日志的特定重复问题，不能自动去重应用层重新发起的两个独立业务命令，也不能保护外部数据库副作用。

Q：为什么已处理重复消息仍应该提交 Offset？
因为它已经被安全识别且无需再次执行。若一直不提交，恢复时还会反复读到同一条消息。

Q：ON CONFLICT DO NOTHING 就已经完成业务幂等了吗？
不一定。它阻止冲突插入，但还需判断旧结果与新请求内容是否一致，并决定如何复用已有结果或报告冲突。

Q：从数据库看最终只有一条结果，就等于整个系统恰好执行一次吗？
不等于。模型请求、外部发送和执行日志都可能发生多次。更准确的结论是：在约束生效的作用域内，最终数据库业务结果至多有一条。

关键规律可以概括为：

  • Event ID 管理事件身份。
  • Business Idempotency Key 管理操作身份。
  • UNIQUE 管理最终数据的不变量。
  • Transaction 管理多个数据库修改的原子性。
  • Offset Commit 管理 Kafka 消费恢复的位置。
  • Outbox / 外部幂等接口管理跨系统副作用的不确定性。

这几种机制有联系，但互不等价。

19. 可直接运行的完整 Python 实现

以下代码保存为 idempotency_demo.py，只依赖 Python 标准库。为了让代码演示清晰，它在 SQLite 中维护 business_results 和 processed_events 两张表，并以同一事务写入最终业务数据与事件处理记录。

python
"""Kafka consumer idempotency: local SQLite teaching model (no broker required)."""
from __future__ import annotations

import hashlib
import json
import sqlite3
from dataclasses import dataclass
from pathlib import Path
from tempfile import gettempdir
from typing import Callable

class IdentityConflict(ValueError):
    """The same logical event identity was reused for different content."""

class BusinessConflict(ValueError):
    """The same business operation key was reused for different content."""

@dataclass(frozen=True)
class Event:
    tenant_id: str
    operation_id: str
    event_id: str
    source: str
    body: dict
    consumer_group: str = "feedback-worker-v1"


def digest(obj: object) -> str:
    raw = json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False)
    return hashlib.sha256(raw.encode("utf-8")).hexdigest()


def event_fingerprint(e: Event) -> str:
    return digest({"tenant": e.tenant_id, "operation": e.operation_id, "body": e.body})


def validate(e: Event) -> None:
    for value in [e.tenant_id, e.operation_id, e.event_id, e.source, e.consumer_group]:
        if not isinstance(value, str) or not value.strip():
            raise ValueError("Identifiers must be nonempty strings")
    if not isinstance(e.body, dict) or not isinstance(e.body.get("content"), str) or not e.body["content"].strip():
        raise ValueError("body.content must be a nonempty string")


class Store:
    def __init__(self, path: str | Path):
        self.path = str(path)
        conn = self.connect()
        try:
            conn.executescript("""
                PRAGMA journal_mode=WAL;
                CREATE TABLE IF NOT EXISTS business_results (
                    tenant_id TEXT NOT NULL,
                    operation_id TEXT NOT NULL,
                    payload_hash TEXT NOT NULL,
                    content TEXT NOT NULL,
                    result_status TEXT NOT NULL DEFAULT 'SUCCEEDED',
                    PRIMARY KEY(tenant_id, operation_id)
                );
                CREATE TABLE IF NOT EXISTS processed_events (
                    consumer_group TEXT NOT NULL,
                    source TEXT NOT NULL,
                    event_id TEXT NOT NULL,
                    event_hash TEXT NOT NULL,
                    tenant_id TEXT NOT NULL,
                    operation_id TEXT NOT NULL,
                    PRIMARY KEY(consumer_group, source, event_id)
                );
            """)
            conn.commit()
        finally:
            conn.close()

    def connect(self):
        conn = sqlite3.connect(self.path, timeout=5, isolation_level=None)
        conn.execute("PRAGMA busy_timeout=5000")
        return conn

    def apply(self, e: Event, before_event_record: Callable[[], None] | None = None) -> str:
        validate(e)
        fingerprint = event_fingerprint(e)
        payload_hash = digest(e.body)
        conn = self.connect()
        try:
            # SQLite teaching simplification: serialize writes. In PostgreSQL
            # rely on UNIQUE indexes + INSERT ... ON CONFLICT and transactions.
            conn.execute("BEGIN IMMEDIATE")
            seen = conn.execute(
                "SELECT event_hash FROM processed_events WHERE consumer_group=? AND source=? AND event_id=?",
                (e.consumer_group, e.source, e.event_id),
            ).fetchone()
            if seen:
                if seen[0] != fingerprint:
                    raise IdentityConflict("event identity reused for different payload")
                conn.commit()
                return "ALREADY_PROCESSED_EVENT"

            existing = conn.execute(
                "SELECT payload_hash FROM business_results WHERE tenant_id=? AND operation_id=?",
                (e.tenant_id, e.operation_id),
            ).fetchone()
            if existing and existing[0] != payload_hash:
                raise BusinessConflict("idempotency key reused for different business content")

            outcome = "REUSED_BUSINESS_RESULT" if existing else "CREATED_BUSINESS_RESULT"
            if not existing:
                conn.execute(
                    "INSERT INTO business_results(tenant_id, operation_id, payload_hash, content) VALUES(?,?,?,?)",
                    (e.tenant_id, e.operation_id, payload_hash, e.body["content"]),
                )

            if before_event_record is not None:
                before_event_record()  # test failure after result write, before event audit

            conn.execute(
                "INSERT INTO processed_events(consumer_group,source,event_id,event_hash,tenant_id,operation_id) "
                "VALUES(?,?,?,?,?,?)",
                (e.consumer_group, e.source, e.event_id, fingerprint, e.tenant_id, e.operation_id),
            )
            conn.commit()
            return outcome
        except BaseException:
            conn.rollback()
            raise
        finally:
            conn.close()

    def count_results(self, tenant_id: str | None = None) -> int:
        conn = self.connect()
        try:
            if tenant_id is None:
                return conn.execute("SELECT count(*) FROM business_results").fetchone()[0]
            return conn.execute("SELECT count(*) FROM business_results WHERE tenant_id=?", (tenant_id,)).fetchone()[0]
        finally:
            conn.close()

    def count_events(self) -> int:
        conn = self.connect()
        try:
            return conn.execute("SELECT count(*) FROM processed_events").fetchone()[0]
        finally:
            conn.close()


def example(path: str | None = None) -> None:
    p = Path(path) if path is not None else Path(gettempdir()) / "idempotency_demo.sqlite3"
    p.unlink(missing_ok=True)
    s = Store(p)
    e = Event("tenant-a", "confirm-001", "evt-101", "feedback-service", {"content": "技能描述错误"})
    print(s.apply(e))
    print(s.apply(e))  # same event redelivery after offset-commit failure
    new_event = Event("tenant-a", "confirm-001", "evt-102", "feedback-service", {"content": "技能描述错误"})
    print(s.apply(new_event))  # different event, same logical operation
    print("business_results=", s.count_results(), "processed_events=", s.count_events())

if __name__ == "__main__":
    example()

23. 术语速查

中文 英文 定义
至少一次投递 At-least-once Delivery 消息可能被交付一次或多次
幂等 Idempotency 对同一次逻辑操作重复执行不增加业务效果
业务幂等键 Business Idempotency Key 标识一次逻辑业务操作的稳定键
事件标识 Event ID 标识一条逻辑事件的身份
物理消息位置 Topic–Partition–Offset Kafka 分区日志中单条记录的位置
最终结果唯一约束 Final-result Uniqueness 数据库强制同一业务键至多有一份结果
去重记录 Inbox / Processed Events 记录某一消费主体已处理哪些逻辑事件
消费位点 Committed Offset 消费组用于故障恢复的下次读取位置
幂等消费者 Idempotent Consumer 能安全处理重复事件、避免重复业务效果的消费者
事务性发件箱 Transactional Outbox 业务修改与待发布事件意图在同一 DB 事务中持久化
并发竞争 Race Condition 同时操作依赖执行时序而导致结果不确定
数据不变量 Invariant 无论并发与重试如何发生都必须满足的规则

本节结论： Kafka 的至少一次投递意味着必须做好重复消费准备。event_id 用于辨认逻辑事件，业务幂等键用于辨认同一次操作，数据库 UNIQUE 用于约束最终结果，事务用于把处理记录和业务修改合成一个原子单元。只有将它们与 Offset 提交次序、错误分类和外部副作用处理共同设计，才能在故障和重试中获得可解释的可靠性。
