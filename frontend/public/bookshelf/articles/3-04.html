Agent、工具调用与执行边界（四）：工具超时、失败重试、执行步数、总耗时与调用预算

范围：解释执行控制器的原理与可验证实现。示例使用 Python 3.11+ 标准库、模拟模型和模拟工具；不需要真实 API Key，不将演示用量单位冒充真实 Token 或价格。

1. 为什么 Agent 需要独立的执行控制

普通聊天常表现为一次模型请求与一次模型响应；Agent 则可能形成：

text
用户任务
  ↓
模型 #1 → 请求 Tool A → 执行 → 返回结果
  ↓
模型 #2 → 请求 Tool B → 失败 → 重试 → 再次返回
  ↓
模型 #3 → 请求 Tool A → 执行 → 返回结果
  ↓
模型 #4 → ...

如果没有边界，模型可能反复调用相同工具；某个网络工具可能长期无响应；多个重试层叠加造成请求风暴；一次任务消耗的 Token、外部 API 费用、CPU 与并发连接可能不断增加。这些问题不是单靠提示词“请不要重复”就可以可靠解决的。

执行控制器（runner / orchestrator） 应在模型和工具之外维护一个独立的、确定性的策略层：

  1. 任务允许进行多少轮模型决策；
  2. 最多接受多少次工具调用；
  3. 单个工具最多尝试几次；
  4. 所有步骤累计最长运行多久；
  5. 还有多少 Token、费用或其他资源预算；
  6. 何时认为没有进展，并强制停止；
  7. 失败或终止后，如何向调用方报告精确状态。

本质原则： 模型可以选择下一步要做什么；是否允许继续执行，由程序根据权限、状态与预算判断。

2. 六个容易混淆的计数单位

单位 定义 示例
模型调用尝试（model attempt） 对模型 API 的一次实际请求，SDK 自动重试也可能产生多次尝试 某次 API 请求遭遇 503 后再次发出
Agent 模型轮次（turn） Runner 定义的一次逻辑模型决策回合；具体语义取决于框架 模型请求工具后进入下一轮
工具调用（tool call） 模型提出一次具体工具操作意图 search_rules(version="v2")
工具执行尝试（tool attempt） 实际执行该工具一次，重试会增加计数 同一工具超时后第二次执行
工具并发数（in-flight） 同一时刻正在运行的工具操作个数 同时请求三份资料
任务运行（agent run） 从接收任务到结束的整个生命周期 包含模型、工具、排队和退避等待

这些数字不能互相替代。一次模型响应可能包含多个工具调用；每个工具调用可能产生多次执行尝试；一个轮次内的传输重试可能不计为新模型轮次。OpenAI Agents SDK 的 max_turns 指逻辑模型调用轮次，而不是所有工具尝试次数。

例如一轮模型返回三个并行工具调用，每个工具最多执行三次，则该轮最多可能带来九次工具执行尝试。仅设置“最大模型轮次为 5”并不能自动把所有工具执行限定为 5 次。

3. 执行控制应当放在哪些层

text
                         全局 Run Deadline / 费用预算
 ┌───────────────────────────────────────────────────┐
 │   Runner: 最大模型轮次、工具调用次数、状态与循环检测  │
 │       ↓                                           │
 │   模型调用: 单次超时、供应商限流、用量统计            │
 │       ↓                                           │
 │   工具调用: 工具白名单、参数权限、超时、幂等检查      │
 │       ↓                                           │
 │   Tool Attempt: 网络超时、失败分类、有限重试、退避    │
 │       ↓                                           │
 │   外部系统: 数据库事务、外部 API、真实副作用           │
 └───────────────────────────────────────────────────┘

需要明确最内层的网络客户端、工具封装层、Agent 框架和应用入口谁负责重试与超时；多个层级不应互相不知道对方正在重试。

核心约束的应用顺序

在执行下一次模型或工具调用之前，建议按顺序检查：身份权限与参数合法性 → 当前任务状态 → 全局 Deadline → 剩余调用次数 → 剩余费用/用量预算 → 独立超时与并发许可。对于写入工具还应检查确认凭证、幂等键和对象版本。

4. 超时的四个层级

超时（timeout） 是对某一操作等待时间的限制，期限（deadline） 是绝对的最晚结束时刻。

层级 约束对象 典型失败
网络阶段超时 建连、发送、读取、连接池排队 ConnectTimeout、ReadTimeout、PoolTimeout
单次模型/工具超时 某一次完整模型或工具执行尝试 模型服务长期无响应
单个工具逻辑调用期限 当前工具含多次尝试与退避的总时长 每次都在重试但迟迟无法完成
整次 Agent 总期限 所有模型、工具、重试、排队及等待时间 总处理时间超过 SLA

注意： HTTPX 的 read 超时是等待收到一个数据块的最大空闲时长，并不自动代表整个请求的最长耗时。持续收到少量数据的流式请求可能持续很久，因此流式服务要另设总期限。

4.1 Python asyncio.timeout() 与 wait_for()

python
import asyncio

async def slow_tool():
    await asyncio.sleep(10)

async def run():
    try:
        async with asyncio.timeout(2):
            await slow_tool()
    except TimeoutError:
        print("本次操作超时")

asyncio.run(run())

asyncio.timeout() 到期时通过取消当前任务实现超时，并在上下文管理器边界把对应取消转换为 TimeoutError。正常应当在 async with 外捕获它。asyncio.wait_for() 会取消它等待的对象，并等待取消处理结束，因此实际返回时间可能超过传入的超时值。

4.2 取消是协作式的，不保证撤销副作用

  • Task.cancel() 发出取消请求；协程通常在挂起点收到 CancelledError。
  • 取消后执行的 finally、资源回收可能仍需要时间。
  • 同步阻塞、线程池中的阻塞函数、远端已经开始执行的操作不一定会立即停止。
  • HTTP 客户端本地超时，不代表服务器端操作没有成功。
  • 对 asyncio.CancelledError 通常应继续传播，不应宽泛吞掉后假装任务成功。

因此“调用超时”意味着本地没有在期限内确认结果，并不总是意味着“操作没有发生”。尤其对写入类工具，要将结果标记为 OUTCOME_UNKNOWN 并核验，而不是盲目重试。

5. 如何分类失败，决定是否重试

失败重试的前提是错误具有暂时性，且重复执行在业务上安全。这是两道独立条件。

失败情况 通常是否重试 理由
429 限流 在配额允许、尊重 Retry-After 时有限重试 过快请求可能短时恢复
502/503/504 上游故障 只对安全/幂等操作有限重试 服务可能暂不可用
短暂连接故障 视操作副作用与请求发送阶段判断 结果可能不确定
400/422 参数错误 不重试 相同参数重复发送通常仍错误
401/403 权限错误 不重试 重试不能代替身份认证或授权
404 资源不存在 通常不重试 需要核对资源 ID 或数据版本
409 状态冲突 一般先重新读取状态并按业务规则处理 不能机械地重复写入
工具返回资料不足 不应自动重复相同查询 需要调整问题或取得新依据
模型工具参数格式错误 先校验/纠错，限制纠错次数 不等于远端临时故障
写入操作后响应丢失 不应直接无条件重试 写入可能已经成功

这里的 408/429/5xx 只是常见的初步分类，并非一条无条件通用规则。API 语义、Retry-After、请求是否到达、是否具备幂等性，都会影响真实策略。

5.1 重试次数应明确口径

如果写 max_retries = 2，通常意味着：首次执行 1 次 + 最多重试 2 次 = 最多 3 次尝试。也有库使用 max_attempts = 3 直接表示最多三次。必须在配置名和日志中明确单位。

5.2 SDK 自动重试与业务重试叠加

如果模型 SDK 内部最多尝试 3 次，工具包装层又最多尝试 3 次，而 Agent 决策循环可能重新请求同一工具 3 次，那么某段外部调用路径的尝试次数可能被放大到 27 次。并不是所有架构必然如此，但只要存在多层各自重试，就有叠加风险。

尽量指定一个明确的重试责任层，统一统计所有实际尝试次数。

6. 退避（Backoff）和抖动（Jitter）

故障发生后不应立即无限重试。常见的指数退避窗口是：

[ W_n = \min(W_{\max}, b \cdot 2^{n-1}) ]

其中 b 是初始等待基数，n 是第几次失败后的重试等待。

加入 Full Jitter 后，从 0 到 W_n 的区间随机取值：

[ D_n \sim U(0, W_n) ]

示例：b=0.5s、上限 4s，则重试等待窗口依次为 [0,0.5]、[0,1]、[0,2]、[0,4]，不同客户端不会恰好在相同时间一起重试。

python
import random

def retry_delay(failure_number: int) -> float:
    window = min(4.0, 0.5 * 2 ** (failure_number - 1))
    return random.uniform(0.0, window)

注意：退避等待本身也消耗总运行时长。应在等待前再次确认全局 Deadline，而不是让每一轮重试都获得全新的“总时间”。当服务端返回合法的 Retry-After 时，优先结合该信息和预算做判断。

为什么不能无条件重试

当系统已经过载时，重复请求会制造额外负载，可能延长故障时间。这就是重试风暴（retry storm）。指数退避、随机抖动、全局重试预算、限流和熔断器可以组合降低风险；它们不是彼此的替代品。

7. 重试安全、幂等性与“结果未知”

工具应根据副作用属性分类：

  1. 只读工具：如查询游戏规则、读取文章，通常更容易安全重试（但仍可能受速率或成本限制）。
  2. 幂等写入：相同业务请求多次执行只产生一次业务效果，且由服务端唯一约束或幂等键保证。
  3. 非幂等写入：如重复发送消息、重复创建交易、重复扣款，不能在响应丢失后直接再做一次。

错误理解：“第一次请求超时，肯定没写入，因此再发一次。”

正确做法：写入操作提交前应生成稳定的业务幂等键（例如 confirmation_id），并让远端或数据库约束保证它只产生一次最终效果。若无法可靠判断成功与否，应先查询既有结果，或者返回 UNKNOWN 让上层人工/程序核查。

幂等键不能只依赖客户端随意传入的字符串。 必须把键绑定到用户、操作类型、目标对象和请求内容。重试时沿用原键，不能每次重新生成一个新键。

8. 最大执行步数：模型轮次、工具次数和尝试次数都要限制

建议至少单独维护：

python
max_model_turns = 6      # 逻辑模型决策轮次
max_tool_calls = 10      # 接受的工具调用意图
max_tool_attempts = 15   # 含失败重试的真实工具执行次数

这些数值只为说明计数方式，不是适用于任何 Agent 的推荐阈值。

还可设置：

  • 每轮模型最多允许调用多少个工具。
  • 同一工具在整个 Run 内的调用次数上限。
  • 单个工具的并发上限。
  • 深层子 Agent / handoff 的调用深度。
  • 结构化输出纠错的最大次数。

为什么光有步数上限还不够

一个步骤可能持续非常久，也可能调用非常昂贵的外部服务。两次模型推理加一次高成本工具执行，就可能比十次普通查询更昂贵。因此应同时限制步数、时间、预算与并发。

9. 总耗时：使用同一个单调时钟的 Deadline

假设整个 Agent 允许运行 30 秒。正确方法是在开始时固定绝对截止时间：

python
loop = asyncio.get_running_loop()
deadline = loop.time() + 30

async with asyncio.timeout_at(deadline):
    await run_agent_loop()

每次子操作的实际等待上限应由“自身上限”和“全局剩余时间”共同决定：

[ T_{\text{attempt}} = \min(T_{\text{per-attempt}}, D - t_{\text{now}}) ]

使用 loop.time() 等单调时钟，避免系统墙上时钟调整影响经过时间计算。每一次重试、排队、工具执行都共享相同 deadline。不要在每个循环重新设置一个 30 秒的所谓总超时。

注意： Python 取消是协作式的，timeout_at() 不是针对所有不可取消外部操作的硬实时杀死开关。要求强制隔离时，需要进程/容器级管理及外部服务自身的超时限制。

10. 调用预算：不仅是 Token

Agent 的资源预算可分为以下几类：

预算 衡量对象 典型限制方式
输入/输出 Token 预算 模型输入和生成量 使用量累计、生成上限
金额预算 模型费用、收费工具 API 价格表、费用计算、配额预留
API 调用预算 模型与工具的请求次数 计数器、共享配额
计算预算 CPU、GPU、执行时长 配额、并发池、作业隔离
外部业务预算 写入次数、邮件发送次数等 权限、状态机、特定业务额度

10.1 按 Token 计算费用

对于按输入和输出 Token 分别计费的模型，示意公式为：

[ C = \frac{N_{in}}{10^6}P_{in} + \frac{N_{out}}{10^6}P_{out} ]

其中 P 是每百万 Token 的价格。生产中还需要考虑缓存命中/未命中价格、非可见推理 Token、工具收费、不同模型价格及供应商账单规则；不能把缓存 Token 再作为额外一份完整输入重复计费。

10.2 预留预算与结算

模型调用前通常无法精确知道最终输出 Token。因此可先按最大可能用量和风险预留额度，调用后依据供应商实际 usage 对账。

[ B_{available}=B_{limit}-B_{settled}-B_{reserved} ]

如果响应超时或断开，实际计费量可能暂时未知；不能简单把它当作零。配额需要保留未结算状态并后续对账。

对于多进程 Agent，共享余额检查和预留应是原子操作（数据库事务或其他可靠配额系统），不能靠一个普通 Python 全局变量。要做到真实的硬成本上限，还需要服务端配额/供应商账户限额等配合；本地取消不能保证上游立即停止收费。

11. 识别循环调用与无进展状态

并不是每次调用都比上一次更有进展。常见问题：

  • 同一个 search() 不断使用相同关键词，返回相同网页。
  • 同一个数据库查询连续返回“找不到”。
  • 模型被错误信息诱导，在两个工具之间往返。
  • 工具成功返回了结果，但模型忽略结果，继续请求相同工具。
  • 反复调用“检查任务状态”，但任务一直没有推进。

一种简单启发式是构建：

text
(tool_name, normalized_arguments, normalized_result)

在没有新数据、任务状态或结果变化的情况下，若相同签名出现多次，可判断“疑似无进展”。

但指纹去重不是万能规则： 查询任务进度、轮询价格、逐步分页或分页游标轮换都可能合法重复。更可靠的是定义业务层的进展度量（progress metric）：新增有效证据数、完成的子任务数、状态变化、可验证结果增量等。

对于轮询类工具，优先用程序定义轮询间隔与次数，而不是让模型每隔极短时间自行重复询问。

12. 一个合格的停止条件集合

Agent 不应只有“模型给出最终答案”这一种退出方式。合理的终止状态至少包括：

状态 含义 调用方处理方向
SUCCESS 任务完成 展示结果
MODEL_TURNS_EXHAUSTED 模型轮次用完 展示阶段结果，不继续调用
TOOL_CALLS_EXHAUSTED 工具调用次数用完 提示操作边界
TOOL_ATTEMPTS_EXHAUSTED 实际执行尝试总数用完 停止重试
TOTAL_TIMEOUT 总运行期限到达 返回超时状态和可查询的任务标识
MODEL_TIMEOUT 单次模型请求超时 根据业务策略决定是否可重试
RETRY_EXHAUSTED 当前工具的重试次数耗尽 返回工具故障原因
WORK_BUDGET_EXHAUSTED 资源配额不足 不继续消耗资源
NO_PROGRESS_LOOP 检测到重复且无进展 请求额外信息或终止
OUTCOME_UNKNOWN_NO_RETRY 写入结果可能已经发生但未确认 先核验，禁止盲目重发
PERMISSION_DENIED 操作无授权 终止且保留审计记录
CANCELLED 用户或系统明确请求取消 协作式取消、检查副作用

上述是应用自行设计的状态名称，不是 Python 或某模型 SDK 统一规定的内置状态。

“部分完成”与“成功”不能混淆

任务因为预算耗尽而停止时，即便已经取得一些资料，也不应强行标成 SUCCESS。应返回独立状态、已完成步骤及未完成原因。若存在已发生的写入副作用，还应保存幂等键和可核验的业务结果。

13. 并发工具与预算竞态

多个工具同时执行时，还需要额外控制：

  1. 调用配额预留： 在真正安排 Task 之前，原子地分配预算。
  2. 并发上限： 使用 Semaphore 或更高层分布式配额，避免同时占满上游连接池。
  3. 失败传播： 决定某个子任务失败是否取消其他子任务；TaskGroup 的默认行为与 gather(return_exceptions=True) 不同。
  4. 总 Deadline： 所有并行分支共享一个最晚截止时间。
  5. 副作用隔离： 某个分支成功写入而其他分支失败，并不能自动事务回滚远端业务。

单进程中的计数器或 asyncio.Lock 不保证跨多个 Worker 的全局额度。分布式环境应使用数据库事务、原子计数/预留或专门限额服务。

  "cost_status": "PENDING_RECONCILIATION"
}

真实系统还应记录模型 usage（包含计费口径）、trace ID、会话 ID、幂等键、相关工具结果摘要/哈希、API 状态码和最后的终止原因。不要把密钥、完整私人资料和不必要的隐私内容直接写入日志。

诊断时应能区分：

  • 工具本身慢，还是等待连接池/信号量慢？
  • 一次调用慢，还是多次退避累计慢？
  • 工具真实失败，还是模型在没有进展时反复调用？
  • 超出的是步数、时间、Token 还是费用预算？
  • 远程操作已经成功，但本地响应丢失了吗？

15. Python 完整可运行示例：有限执行控制器

以下是标准库、离线模拟示例。它包含：

  • 最大模型轮次、最大工具调用与最大工具执行尝试数；
  • 单次模型/工具超时与总 Deadline；
  • 有限重试、指数退避和抖动；
  • 临时错误与永久错误区分；
  • 不安全写入操作禁止自动重试；
  • 角色白名单和基本参数类型校验；
  • 模拟工作量单位预算（非真实 Token / 金额）；
  • 相同工具参数和结果的循环启发式检测；
  • 明确终止状态与事件记录。

边界声明： 这不是生产级 Agent 或收费配额系统。它不连接真实模型；未实现 Pydantic 业务 Schema、分布式原子余额、持久化恢复、真实幂等服务端和上游用量对账。work_units 只用来证明限额控制逻辑。

将下方代码保存为 runner_demo.py，可运行 python runner_demo.py。

python
"""Agent execution control demo. Python >=3.11, standard library only.
No real LLM/network; work units are deliberately NOT API fees.
"""
from __future__ import annotations

import asyncio
import json
import random
from collections import Counter
from dataclasses import dataclass, field
from typing import Any, Awaitable, Callable


class TransientToolError(Exception):
    """A retryable failure if and only if the operation is retry-safe."""


class PermanentToolError(Exception):
    """A non-retryable error: invalid input, authorization, missing resource, etc."""


@dataclass(frozen=True)
class Limits:
    max_model_turns: int = 5
    max_tool_calls: int = 4
    max_tool_attempts: int = 6
    max_work_units: int = 20  # illustrative quota, NOT tokens or money
    total_seconds: float = 2.0
    model_timeout: float = 0.4
    tool_timeout: float = 0.2
    retry_per_call: int = 2  # number of retries, excludes first attempt
    backoff_base: float = 0.01
    backoff_cap: float = 0.03
    duplicate_results_limit: int = 2


@dataclass(frozen=True)
class ToolCall:
    call_id: str
    name: str
    arguments: dict[str, Any]


@dataclass(frozen=True)
class Decision:
    answer: str | None = None
    tool_call: ToolCall | None = None


@dataclass(frozen=True)
class ToolSpec:
    handler: Callable[[dict[str, Any]], Awaitable[dict[str, Any]]]
    permitted_roles: frozenset[str]
    retry_safe: bool = True


@dataclass
class Outcome:
    status: str
    answer: str | None
    turns: int
    tool_calls: int
    tool_attempts: int
    work_units: int
    events: list[dict[str, Any]] = field(default_factory=list)


class ScriptModel:
    """Offline fake model, with explicit actions and optional delay."""
    def __init__(self, actions: list[Decision], delay: float = 0):
        self.actions = actions
        self.delay = delay
        self.index = 0

    async def __call__(self, history: list[dict[str, Any]]) -> Decision:
        if self.delay:
            await asyncio.sleep(self.delay)
        if self.index >= len(self.actions):
            return Decision(answer="script ended")
        action = self.actions[self.index]
        self.index += 1
        return action


class AgentRunner:
    def __init__(self, model: Callable[[list[dict[str, Any]]], Awaitable[Decision]],
                 tools: dict[str, ToolSpec], role: str, limits: Limits,
                 rng: random.Random | None = None):
        self.model = model
        self.tools = tools
        self.role = role
        self.limits = limits
        self.rng = rng or random.Random(42)
        self.turns = 0
        self.tool_calls = 0
        self.tool_attempts = 0
        self.units = 0
        self.history: list[dict[str, Any]] = []
        self.events: list[dict[str, Any]] = []
        self.repeated: Counter[tuple[str, str, str]] = Counter()

    def result(self, status: str, answer: str | None = None) -> Outcome:
        return Outcome(status, answer, self.turns, self.tool_calls,
                       self.tool_attempts, self.units, list(self.events))

    def consume(self, units: int) -> bool:
        if self.units + units > self.limits.max_work_units:
            return False
        self.units += units
        return True

    async def run(self) -> Outcome:
        loop = asyncio.get_running_loop()
        deadline = loop.time() + self.limits.total_seconds
        try:
            async with asyncio.timeout_at(deadline):
                return await self._run_loop(deadline)
        except TimeoutError:
            self.events.append({"event": "total_deadline_exceeded"})
            return self.result("TOTAL_TIMEOUT")
        # Caller cancellation deliberately propagates. Never swallow CancelledError.

    async def _run_loop(self, deadline: float) -> Outcome:
        loop = asyncio.get_running_loop()
        while True:
            if self.turns >= self.limits.max_model_turns:
                return self.result("MODEL_TURNS_EXHAUSTED")
            if not self.consume(2):
                return self.result("WORK_BUDGET_EXHAUSTED")
            self.turns += 1
            try:
                remaining = max(0.000001, deadline - loop.time())
                decision = await asyncio.wait_for(
                    self.model(self.history), min(self.limits.model_timeout, remaining)
                )
            except TimeoutError:
                self.events.append({"event": "model_timeout", "turn": self.turns})
                return self.result("MODEL_TIMEOUT")

            if decision.answer is not None:
                self.events.append({"event": "final", "turn": self.turns})
                return self.result("SUCCESS", decision.answer)
            call = decision.tool_call
            if call is None:
                return self.result("INVALID_MODEL_OUTPUT")
            if self.tool_calls >= self.limits.max_tool_calls:
                return self.result("TOOL_CALLS_EXHAUSTED")
            self.tool_calls += 1
            spec = self.tools.get(call.name)
            if spec is None:
                return self.result("UNKNOWN_TOOL")
            if self.role not in spec.permitted_roles:
                return self.result("PERMISSION_DENIED")
            if not isinstance(call.arguments, dict):
                return self.result("INVALID_TOOL_ARGUMENTS")

            result: dict[str, Any] | None = None
            for per_call_attempt in range(1, self.limits.retry_per_call + 2):
                if self.tool_attempts >= self.limits.max_tool_attempts:
                    return self.result("TOOL_ATTEMPTS_EXHAUSTED")
                if not self.consume(1):
                    return self.result("WORK_BUDGET_EXHAUSTED")
                self.tool_attempts += 1
                try:
                    remaining = max(0.000001, deadline - loop.time())
                    result = await asyncio.wait_for(
                        spec.handler(call.arguments), min(self.limits.tool_timeout, remaining)
                    )
                    self.events.append({"event": "tool_success", "call_id": call.call_id,
                                        "attempt": per_call_attempt})
                    break
                except PermanentToolError as exc:
                    self.events.append({"event": "tool_permanent_error", "type": type(exc).__name__})
                    return self.result("TOOL_FAILED")
                except (TimeoutError, TransientToolError) as exc:
                    self.events.append({"event": "tool_transient_error", "type": type(exc).__name__,
                                        "attempt": per_call_attempt})
                    if not spec.retry_safe:
                        return self.result("OUTCOME_UNKNOWN_NO_RETRY")
                    if per_call_attempt >= self.limits.retry_per_call + 1:
                        return self.result("RETRY_EXHAUSTED")
                    # Full-jitter exponential backoff: all waits count toward total deadline.
                    window = min(self.limits.backoff_cap,
                                 self.limits.backoff_base * 2 ** (per_call_attempt - 1))
                    await asyncio.sleep(self.rng.uniform(0, window))

            assert result is not None
            # Detect same (tool, args, result) multiple times, a heuristic only.
            signature = (
                call.name,
                json.dumps(call.arguments, ensure_ascii=False, sort_keys=True),
                json.dumps(result, ensure_ascii=False, sort_keys=True),
            )
            self.repeated[signature] += 1
            self.history.append({"role": "tool", "call_id": call.call_id,
                                 "name": call.name, "result": result})
            if self.repeated[signature] >= self.limits.duplicate_results_limit:
                return self.result("NO_PROGRESS_LOOP")


async def get_rule(arguments: dict[str, Any]) -> dict[str, Any]:
    if arguments.get("version") != "v2":
        raise PermanentToolError("unsupported version")
    await asyncio.sleep(0.003)
    return {"character": "hero_a", "hp": 4, "version": "v2"}


async def demo() -> None:
    model = ScriptModel([
        Decision(tool_call=ToolCall("call_1", "get_rule", {"version": "v2"})),
        Decision(answer="已查询 v2 规则：hero_a 的生命值为 4。"),
    ])
    runner = AgentRunner(model, {"get_rule": ToolSpec(get_rule, frozenset({"reader"}))},
                         "reader", Limits())
    print(runner_result := await runner.run())
    assert runner_result.status == "SUCCESS"


if __name__ == "__main__":
    asyncio.run(demo())

15.1 示例中的重要代码选择

  • Limits 用 dataclass(frozen=True) 定义配置，避免运行中无意改变限制。
  • run() 使用同一绝对期限保护完整执行；asyncio.wait_for() 保护一次调用尝试。
  • tool_calls 统计模型已经提出且被接受进入校验流程的工具意图；tool_attempts 统计真实执行次数。
  • 预算在调用前扣除模拟单位，避免先执行后才发现配额不足。
  • 如果 retry_safe=False，超时或临时故障后返回 OUTCOME_UNKNOWN_NO_RETRY，阻止不安全重试。
  • 外部调用者取消任务时，CancelledError 继续传播，而不转成普通成功结果。
  • NO_PROGRESS_LOOP 只是相同参数与结果的启发式判断，不是完整的业务进展检测算法。

18. 与 OpenAI Agents SDK / Agno 等框架的关系

框架可能已经提供：模型调用循环、工具错误结果、单工具超时、模型尝试超时或 max_turns 等能力，但这些只是部分边界。对 SDK 与版本应逐一核实：

  • max_turns 的定义：模型轮次还是工具执行次数？
  • Tool Timeout 是返回给模型可见错误，还是直接中断整次执行？
  • 内部是否自动重试模型调用？自动重试是否计入预算？
  • 多工具调用并发执行时，配额如何扣除？
  • Agent 切换、子 Agent、任务续接后，预算是否延续？
  • 出现断开或关闭时，未完成的写入能否核验？

以当前 OpenAI Agents SDK 官方文档为例，Runner 有 max_turns 限制；异步 Function Tool 可以设置单次超时，并选择把超时作为工具错误交还模型或向外抛出异常；模型调用也可配置尝试级 timeout。但模型调用 timeout 不会自动限制整个 Run 或工具执行时间。这些设置不等于完整的任务费用/时长预算。具体行为随版本可能变化，开发时必须使用项目锁定版本的文档。

Agno 同样需要检查所用版本是否有运行取消、工具超时、事件钩子、持久化状态等功能；如果缺少某一层边界，应由应用 Runner 或底层服务补足，不能靠在提示词中要求“执行不要超过五步”代替。

19. 常见误区汇总

误区 正确理解
给每个请求加 30 秒超时，整个 Agent 就最多 30 秒 多次请求与退避会累计，总期限必须覆盖完整 Run
wait_for(..., 5) 保证 5 秒整返回 取消与清理可能额外耗时
只要 max_turns=5，最多执行 5 次工具 单轮可能多个工具，单工具可能多次尝试
超时必定意味着写入失败 本地结果未知不等于远端未生效
所有 5xx 都应该立刻再试 是否重试还取决于幂等性、成本、上游负载与预算
429 一定要持续重试直到成功 应尊重限流，并受总 Deadline 与最大尝试次数控制
Semaphore 就是每日 API 费用上限 它限制并发，不等于累计用量预算
一直没报错说明 Agent 正常推进 可能在相同工具调用间循环，必须检查进展
模型自己知道什么时候该停 停止规则必须由程序实现并可验证
本地日志的花费估算就是最终账单 超时、缓存和供应商计费口径可能导致差异，需对账
