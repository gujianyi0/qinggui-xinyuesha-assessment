大模型原理、API 与输出校验（五）

用 Python 直接调用模型：请求、响应、结束状态、Token 用量与 AI 编程工具的区别

整理日期：2026-11-11。接口细节以调用时的供应商官方文档和 SDK 版本为准。
阅读定位：独立技术知识手册。所列网络调用代码需要实际 API Key、网络和可用余额；离线解析示例可在没有 API Key 时运行。没有实际连接供应商接口的操作，不应当记作“真实模型调用成功”。

1. 模型 API 调用到底是什么

**模型调用（model inference request）**是应用程序向已部署的模型推理服务提交输入、配置生成行为，并取得输出和用量信息的过程。它不会因为被调用而自动更新模型参数，也不代表应用程序具备检索、读文件、执行命令等能力。

一个典型的请求链路是：

text
Python 程序
  │ 组装消息、模型名称和生成参数
  ▼
模型 SDK / HTTP 客户端
  │ HTTPS：URL、Authorization、JSON 请求体
  ▼
API 网关（身份验证、配额/限流、路由）
  ▼
模型推理服务（分词、上下文处理、推理、生成）
  ▼
HTTP 响应（结果、停止原因、用量、标识等）
  ▼
Python 程序（检查状态、提取文本、记录用量、处理异常）

必须区分三个层次：

  1. HTTP 层：请求是否成功抵达服务、HTTP 状态码是多少、是否超时。
  2. 模型协议层：响应对象里有没有 choices 或 output，生成为什么结束，是否要求工具调用。
  3. 业务层：答案是否有依据，是否符合输出格式与业务规则，能否交给用户或继续执行后续操作。

HTTP 200 表示请求在协议层被接受并返回成功响应，并不意味着文本事实正确、JSON 合法或业务已完成。

1.1 SDK 与 API 的关系

  • HTTP API 是服务器提供的网络接口，例如 POST /chat/completions。
  • SDK 是语言封装。Python SDK 负责创建 HTTP 请求、序列化 JSON、认证、解析响应，以及提供部分重试/异常功能。
  • 模型 是实际承担生成任务的推理系统；SDK 不是模型本身。
  • API Key 是请求服务的凭证；它决定身份和配额权限，不提供独立的“智能能力”。

同一个服务可以通过 Python、JavaScript、curl 或其他 HTTP 客户端访问。使用 Python SDK 并不必然意味着调用了对应 SDK 厂商自家的模型：例如 DeepSeek 提供兼容 OpenAI SDK 的 API 地址。

2. 一次 HTTP 请求由哪些部分构成

以 Chat Completions 风格接口为例：

http
POST /chat/completions HTTP/1.1
Host: api.deepseek.com
Authorization: Bearer <YOUR_API_KEY>
Content-Type: application/json

{
  "model": "deepseek-flash",
  "messages": [
    {"role": "system", "content": "你是一名准确、简洁的技术助手。"},
    {"role": "user", "content": "用一句话解释 Python 协程。"}
  ],
  "max_tokens": 256,
  "stream": false,
  "thinking": {"type": "disabled"}
}

上面请求体展示的是 DeepSeek 当前文档支持的一种非思考模式调用形式。具体模型、参数范围和兼容性可能随服务版本变化；不要把一个提供商的扩展字段认为所有兼容 API 都支持。

字段 所在层 含义 注意事项
URL / base_url HTTP / SDK 服务入口 写错会导致 404、连接错误或路由错误
Authorization HTTP API 访问凭据 不应写入源码、仓库或日志
model 请求体 指定模型标识 不存在或无权限会导致错误
messages 请求体 输入对话内容 包含 system/user/assistant 等角色
max_tokens 请求体 限制本次生成的 Token 上限 不保证精确输出长度；推理 Token 可能计入该预算
stream 请求体 非流式/流式 本节以 false 为主；流式另有事件协议
thinking 服务商扩展 控制 DeepSeek 思考模式 非通用 OpenAI 参数；通过 extra_body 传入
timeout 客户端配置 网络调用等待时间 客户端超时不保证服务端立即停止执行

请求中的消息与模型返回的回答是两个方向的数据。messages 不是模型的“持久数据库”；多数无状态接口要求程序自行维护并在下次请求时提供必要历史。尤其 DeepSeek 的 Responses API 当前官方文档明确标注为无状态，不支持 previous_response_id 的服务端延续会话语义。

3. Python 直接调用：DeepSeek Chat Completions 完整入门

3.1 准备项目与 Python 环境

在 Windows PowerShell 下：

powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade openai

给当前 PowerShell 会话注入密钥：

powershell
$env:DEEPSEEK_API_KEY = "请替换为你自己的真实Key"

实际操作应避免把密钥放进提交到 Git 的脚本、终端录屏或共享日志。也可使用受保护的环境变量、CI Secret 或密钥管理系统。DEEPSEEK_API_KEY 应由调用 DeepSeek API 的 Python 进程读取；ChatGPT 网页订阅和 API 服务不是同一个凭据体系。

3.2 可运行的非流式调用示例

保存为 call_model.py：

python
import os
import time
import openai
from openai import OpenAI


def main() -> None:
    api_key = os.getenv("DEEPSEEK_API_KEY")
    if not api_key:
        raise RuntimeError("缺少 DEEPSEEK_API_KEY 环境变量")

    started = time.perf_counter()

    # OpenAI SDK 是 HTTP 客户端封装，此处真正访问的是 DeepSeek。
    with OpenAI(
        api_key=api_key,
        base_url="https://api.deepseek.com",
        timeout=30.0,
        max_retries=1,
    ) as client:
        try:
            response = client.chat.completions.create(
                model="deepseek-flash",
                messages=[
                    {"role": "system", "content": "你是一名准确、简洁的技术助手。"},
                    {"role": "user", "content": "用一句话解释 Python 协程。"},
                ],
                max_tokens=256,
                stream=False,
                extra_body={"thinking": {"type": "disabled"}},
            )
        except openai.APITimeoutError:
            print("模型请求超时；无法由此断定服务端没有产生用量")
            return
        except openai.APIConnectionError as exc:
            print(f"网络连接失败：{type(exc).__name__}")
            return
        except openai.APIStatusError as exc:
            print(f"API HTTP 错误：{exc.status_code}")
            print(f"请求 ID：{getattr(exc, 'request_id', None)}")
            return

    elapsed = time.perf_counter() - started

    if not response.choices:
        print("响应中没有可用的 choices")
        return

    choice = response.choices[0]
    finish_reason = choice.finish_reason
    content = choice.message.content

    print("实际返回模型：", response.model)
    print("请求响应 ID：", response.id)
    print("结束原因：", finish_reason)
    print("耗时（秒）：", round(elapsed, 3))

    if finish_reason == "stop" and content and content.strip():
        print("文本内容：", content)
    elif finish_reason == "tool_calls":
        print("模型请求调用工具，不等于工具已经执行")
        print("工具请求：", choice.message.tool_calls)
    else:
        print("回答尚不可直接当作完整有效结果：", repr(content))

    if response.usage is not None:
        # 使用 model_dump 避免服务商扩展字段被 SDK 类型提示遗漏。
        usage = response.usage.model_dump(exclude_none=True)
        print("用量信息：", usage)
    else:
        print("服务未提供 usage；不能据此把用量记作 0")


if __name__ == "__main__":
    main()

运行：

powershell
.\.venv\Scripts\python.exe call_model.py

该脚本会发起真实网络请求并可能产生 API 费用。 没有密钥和网络时，不能通过它完成端到端调用。脚本中的 max_retries=1 表示 SDK 可在规定的可重试错误下进行至多一次额外尝试；不代表 HTTP 请求最多只能发送一次，具体行为以 SDK 实现为准。

3.3 为什么代码要先看 finish_reason 再消费文本

因为返回的 content 即使非空，也可能是：

  • 超出长度限制前生成的不完整半句话；
  • 模型提出工具调用的同时附带的内容；
  • 一段格式上完整但缺少业务事实依据的文字；
  • 遭到内容限制或服务资源中断后的部分结果。

所以**“取得字符串”不是“得到可交付结果”**。正常完成后仍要按任务进行 JSON、Schema、事实和业务校验。

4. 不使用 SDK：直接通过 HTTP 观察请求

SDK 并不是必需品。下面的 httpx 示例能够直观看到 HTTP 状态和响应 JSON。

安装：

powershell
.\.venv\Scripts\python.exe -m pip install httpx
python
import os
import httpx

api_key = os.environ["DEEPSEEK_API_KEY"]
payload = {
    "model": "deepseek-flash",
    "messages": [
        {"role": "user", "content": "解释一次 HTTP POST 请求"}
    ],
    "max_tokens": 128,
    "stream": False,
    "thinking": {"type": "disabled"},
}

with httpx.Client(timeout=30.0) as client:
    response = client.post(
        "https://api.deepseek.com/chat/completions",
        headers={"Authorization": f"Bearer {api_key}"},
        json=payload,
    )
    print("HTTP 状态码：", response.status_code)
    response.raise_for_status()
    data = response.json()

print("完成原因：", data["choices"][0]["finish_reason"])
print("模型回答：", data["choices"][0]["message"].get("content"))
print("用量：", data.get("usage"))

SDK 与 httpx 的主要区别不是“谁更智能”，而是 SDK 封装了参数类型、认证、异常与部分重试策略。使用裸 HTTP 需要自行处理更多协议细节；使用 SDK 仍需要理解底层 HTTP 请求是什么。

如果服务返回 400、401、429、500 等状态，raise_for_status() 将抛出 HTTPX 异常；它和 openai.APIStatusError 属于不同客户端库的异常体系，不要混着捕获。

5. 如何逐层读懂模型响应

下面是为讲解而构造的示例 JSON，结构取自当前 Chat Completions 文档；其中 ID、数字和回答文本不是真实调用记录。

json
{
  "id": "example_completion_001",
  "object": "chat.completion",
  "created": 1790000000,
  "model": "deepseek-flash",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "协程是可以在等待时挂起、由事件循环调度继续执行的代码单元。"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 52,
    "completion_tokens": 27,
    "total_tokens": 79,
    "prompt_cache_hit_tokens": 0,
    "prompt_cache_miss_tokens": 52
  }
}
字段 含义 正确理解
id 此次生成的响应标识 适合做日志关联；不等于业务会话 ID
object 对象类型 这里是 chat.completion
created 服务端创建时间 通常是 Unix 秒时间戳，不是耗时
model 实际返回的模型标识 可用于审计模型配置
choices 候选生成结果列表 不能无条件假设必有一项
index 候选结果序号 与业务消息编号无关
message.role 消息角色 常见为 assistant
message.content 回答正文 可以为空或 null；并非所有输出都是文本
finish_reason 为什么停止生成 必须检查，不能与 HTTP 状态混淆
usage 本次用量统计 是 Token 统计，不是直接的美元金额

5.1 choices[0].message.content 为什么有时是 None

可能原因包括：模型要求客户端调用工具、发生特殊终止、供应商/模式下回答在其他字段、服务端只生成推理内容但尚未给出最终文本等。应先看 finish_reason、tool_calls、模型响应结构和对应接口文档，而非简单调用 .strip() 导致 AttributeError。

5.2 其他有价值的元数据

部分服务返回 system_fingerprint、请求 ID、缓存命中详情或推理 Token 详情。它们适合用于版本回归、成本统计与故障定位，但并不能保证重放同一请求就得到逐字相同的回答。

6. 结束状态（finish_reason）的语义

以下是 DeepSeek 当前 Chat Completions 文档列出的停止原因；其他厂商、接口版本可能有所不同。

值 语义 应用程序应如何处理
stop 正常停止或触发指定停止序列 可以进入下游内容校验；不能直接视为事实正确
length 达到生成 Token 或上下文等长度限制 视为可能截断；重要 JSON 应拒绝直接采用并按策略重试
tool_calls 模型提出工具调用 校验参数与授权、执行工具并回传结果；此时还不是最终文本答案
content_filter 内容被过滤或省略 记录受限状态，不能将空值当成功
insufficient_system_resource 推理系统资源不足导致中断 作为服务端资源问题处理，可按规则有限重试
aborted 生成被中断 标记中断，不应当将部分输出当作完成

不要把 finish_reason 当 HTTP 状态码。 服务器可以返回 HTTP 200，但选择的候选结果标记为 length，这表示这次生成在业务上可能不完整。

6.1 常见判定流程

text
获得 HTTP 响应
  ├─ 非 2xx → 网络/认证/参数/限流/服务器错误分支
  └─ 2xx
      ├─ 缺少候选输出 → 协议异常或异常响应
      └─ 有候选输出
          ├─ stop → 读取内容 → 格式/事实/业务校验
          ├─ length → 截断处理
          ├─ tool_calls → 校验并执行工具循环
          └─ 其他 → 记录中断或受限状态

注意：stop 时如果 content 为空，也不能当作有效答案；服务商的 JSON 模式在某些条件下可能产生空白内容，所以实际系统需要判空。

7. Token 用量与费用怎样计算

7.1 输入与输出的含义

  • 输入 Token（prompt_tokens / input_tokens）：为本次调用提供给模型的内容，常包含系统指令、用户消息、历史消息、工具定义或资料等；最终统计按供应商规则计算。
  • 输出 Token（completion_tokens / output_tokens）：模型在本次生成中产生并计入输出的 Token；推理模式可能还包含不直接呈现在最终正文中的推理 Token。
  • 总 Token（total_tokens）：通常是输入与输出用量之和。

Chat Completions 结构中常见字段：

text
usage.prompt_tokens
usage.completion_tokens
usage.total_tokens
usage.prompt_cache_hit_tokens
usage.prompt_cache_miss_tokens
usage.completion_tokens_details.reasoning_tokens

其中缓存命中 Token 是输入 Token 的分类，不是在总量之外额外增加的一份 Token。DeepSeek 当前文档给出：

text
prompt_tokens = prompt_cache_hit_tokens + prompt_cache_miss_tokens

但不是所有服务都提供上述所有字段。必须允许某些细分字段缺失。

7.2 成本公式

假设供应商对缓存未命中输入、缓存命中输入、输出分别采用不同单价（以每百万 Token 的货币金额计）：

[ \text{估算成本}=\frac{T_{miss}P_{miss}+T_{hit}P_{hit}+T_{out}P_{out}}{10^6} ]

这是一种常见的估算方式，不能代替供应商最终账单。额外的工具调用、特殊推理服务、存储、图像或其他资源可能有独立计费项目。输入和输出价格、地区、服务层级、模型版本均可能变化，必须使用调用时有效的价格表。

示例（所有价格均为演示假设，不代表实际供应商价格）：

  • 缓存未命中输入 1200 Token，单价 1.00/百万 Token。
  • 缓存命中输入 800 Token，单价 0.20/百万 Token。
  • 输出 600 Token，单价 2.00/百万 Token。

那么估算成本：

[ (1200\times1+800\times0.2+600\times2)/10^6=0.00256 ]

金额单位取决于上述假设单价所采用的货币单位。

7.3 读取用量的 Python 代码

python
def summarize_usage(usage: dict) -> dict:
    input_tokens = usage.get("prompt_tokens", usage.get("input_tokens"))
    output_tokens = usage.get("completion_tokens", usage.get("output_tokens"))
    total_tokens = usage.get("total_tokens")

    # 无统计字段时不要伪造 0；None 表示未知。
    if total_tokens is None and input_tokens is not None and output_tokens is not None:
        total_tokens = input_tokens + output_tokens

    return {
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "total_tokens": total_tokens,
        "cache_hit": usage.get("prompt_cache_hit_tokens"),
        "cache_miss": usage.get("prompt_cache_miss_tokens"),
    }

usage 为 None 时应在调用函数外单独处理，不能假定一切失败请求都会返回完整的 Token 用量。服务端超时或客户端断开之后仍可能产生计费，应以服务商账单为最终结算依据。

7.4 为什么“输出文本很短”用量仍可能很高

可能的原因包括：系统提示词和检索资料很长、历史消息重复发送、工具定义占用输入、思考模式消耗不可见的推理 Token，或调用链进行了多次模型请求。不要仅根据最后显示给用户的字数推断成本。

8. 模型调用和程序业务调用之间的区别

当一段 Python 代码写成：

python
response = client.chat.completions.create(...)

它通常只是一次模型 API 请求，不意味着完成了整个产品业务流程。

例如一个“游戏规则查询”业务需要：

  1. HTTP 接口接收用户问题；
  2. 检索数据库中的相关版本规则；
  3. 将可靠资料和问题组织成模型输入；
  4. 调用模型 API；
  5. 解析 finish_reason 与用量；
  6. 检查引用是否真实支持答案；
  7. 保存会话及日志；
  8. 向前端返回最终结果。

第 4 步才是直接模型调用，其余属于应用层工程设计。因此，掌握 SDK 是必要条件，却不足以证明已实现可靠 AI 产品。

9. Chat Completions 与 Responses API：不同的返回结构

同一个 SDK 可能支持多类接口。

9.1 Chat Completions 风格

python
completion = client.chat.completions.create(...)
text = completion.choices[0].message.content
finish_reason = completion.choices[0].finish_reason
usage = completion.usage

关注点：choices[*].message、finish_reason、usage.prompt_tokens、usage.completion_tokens。

9.2 Responses 风格

DeepSeek 当前也支持兼容 Responses API 的接口：

python
import os
from openai import OpenAI

with OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
) as client:
    response = client.responses.create(
        model="deepseek-flash",
        instructions="请清晰回答技术问题。",
        input="什么是 Python 协程？",
    )

print("文本：", response.output_text)
print("响应状态：", response.status)
print("用量：", response.usage)

Responses 风格通常关注 output/output_text、status、usage.input_tokens、usage.output_tokens 和 incomplete_details 等，而不是 choices[0].finish_reason。

要注意跨供应商兼容并不意味着每个参数都具有相同的语义。DeepSeek 当前 Responses 文档明确标注 previous_response_id、store、background 等能力不受支持或被忽略；因此不能把另一家服务的会话状态行为直接套用到 DeepSeek。

两个 API 风格都能完成一次模型调用；应用应根据实际返回协议编写解析逻辑。

10. 真实请求常见错误与异常处理

HTTP 状态 / 事件 典型原因 合理处理
400 / 422 JSON 或参数不符合接口要求 修改请求，不要盲目重试
401 API Key 错误或失效 更新凭据，不应自动重试相同凭据
402 余额不足（DeepSeek 示例） 检查余额与配额
403 权限被拒绝 检查账户及模型授权
404 模型或接口路径不存在 核实模型名与 base_url
429 速率或并发限制 退避重试、削峰与限流
500 / 503 服务端错误、过载 有界退避重试，并结合幂等性判断
Timeout 客户端等待时间超出限制 记录超时，不应直接推断零成本或零执行
网络断开 DNS、代理、TLS、网络波动 记录错误类别并按策略重试

10.1 何时不要盲目重试

  • 错误原因是 400 / 401 / 402 等用户或配置问题。
  • 生成操作会触发实际工具动作（发送消息、支付、写入数据），但没有幂等保证。
  • 之前请求可能已被服务端处理，程序只是没有收到最终响应。
  • 重试预算、延迟预算或费用预算已经耗尽。

官方 Python SDK 可能默认重试部分网络或 5xx 错误。应用若再套一层重试，需要计算总体实际尝试次数，否则可能无意中扩大费用和时延。

10.2 可记录与不可记录的信息

建议记录：业务请求号、响应 ID、模型标识、请求耗时、结束原因、Token 用量、错误类别、提示词版本、必要时经过脱敏的输入摘要。

不建议记录：API Key、Authorization Header、完整私人聊天、原样的敏感提示词或未经允许的业务资料。

“请求 ID”有多个层次：业务请求 ID 由应用生成，供应商响应 ID 由模型服务生成，HTTP 请求追踪 ID 由网关或传输层生成。它们最好关联，但并不是同一个字段。

11. 代码层面：输出解析的最小可信判定器

下面的示例不调用网络，也不消耗 API 费用。它展示为什么在读取文本之前需要检查模型结束状态，以及怎样将 Token 用量与正文分开处理。

python
from dataclasses import dataclass
from typing import Any


@dataclass(frozen=True)
class ParsedResult:
    status: str
    text: str | None
    finish_reason: str | None
    input_tokens: int | None
    output_tokens: int | None


def parse_chat_completion(data: dict[str, Any]) -> ParsedResult:
    choices = data.get("choices")
    if not isinstance(choices, list) or not choices:
        return ParsedResult("protocol_error", None, None, None, None)

    choice = choices[0]
    if not isinstance(choice, dict):
        return ParsedResult("protocol_error", None, None, None, None)

    reason = choice.get("finish_reason")
    message = choice.get("message") or {}
    content = message.get("content") if isinstance(message, dict) else None
    usage = data.get("usage") or {}
    if not isinstance(usage, dict):
        usage = {}

    if reason == "tool_calls":
        status = "requires_tool"
    elif reason == "length":
        status = "incomplete"
    elif reason == "stop" and isinstance(content, str) and content.strip():
        status = "completed_unverified"
    elif reason == "stop":
        status = "empty_output"
    else:
        status = "interrupted_or_restricted"

    return ParsedResult(
        status=status,
        text=content if isinstance(content, str) else None,
        finish_reason=reason,
        input_tokens=usage.get("prompt_tokens"),
        output_tokens=usage.get("completion_tokens"),
    )


if __name__ == "__main__":
    complete = {
        "choices": [{"finish_reason": "stop", "message": {"content": "你好"}}],
        "usage": {"prompt_tokens": 8, "completion_tokens": 3},
    }
    truncated = {
        "choices": [{"finish_reason": "length", "message": {"content": "未完成的"}}],
        "usage": {"prompt_tokens": 8, "completion_tokens": 10},
    }
    assert parse_chat_completion(complete).status == "completed_unverified"
    assert parse_chat_completion(truncated).status == "incomplete"
    print(parse_chat_completion(complete))

这里刻意使用 completed_unverified，而不是 success，因为生成正常结束只解决了协议完成问题，并未验证答案是否符合业务规则。

12. 一次模型请求与 AI 编程工具到底差在哪

AI 编程工具通常是在模型调用之外叠加工程环境感知、文件系统访问、项目搜索、计划、工具执行和结果反馈的应用或代理系统，例如 Codex、Claude Code、IDE 中的 AI 编程扩展等。

维度 直接调用模型 API AI 编程工具
主要输入 消息与调用参数 编程目标、仓库状态、用户授权、工程上下文
主要输出 文本、结构化内容、工具调用意图 代码改动、命令执行结果、测试报告、解释说明等
文件访问 默认没有 在权限允许时可读写工作区文件
执行终端命令 默认没有 有些工具提供受控命令执行
多步迭代 需要开发者自己编排 通常内置一定的代理循环或工作流
项目上下文 开发者手动提供 可能自动搜索文件、读取差异和诊断信息
测试与验证 开发者自己实现 工具可能自动运行测试；仍需核对结果
权限 API 密钥权限与应用自身控制 还涉及工作区、终端、网络、批准策略
费用 常按模型 Token 和附加资源计费 可采用订阅额度、API 用量或工具自己的计费方式
责任 应用开发者负责业务可靠性 人类使用者和工具实现仍需对变更与验证负责

12.1 一个对比实例

假设需求是“给 FastAPI 项目增加会话记录”。

仅调用模型 API：

python
answer = client.chat.completions.create(
    model="deepseek-flash",
    messages=[{
        "role": "user",
        "content": "请给出使用 SQLAlchemy 保存会话记录的代码示例"
    }],
    extra_body={"thinking": {"type": "disabled"}},
)

得到的是“建议或生成的代码文本”。除非自己编写后续程序，否则它不会自动打开项目、修改文件、运行 Alembic、执行测试或创建 Git 提交。

使用 AI 编程工具：

工具在获得相应权限后可能依次：读取仓库结构 → 查找模型/路由 → 修改文件 → 生成迁移 → 运行测试 → 发现错误 → 修复 → 给出差异和结果。

关键区别不在于“模型智力高低”，而在于工具环境、执行权、上下文管理、工作流和验证能力。同一个模型可以用于聊天 API，也可以作为编程代理的后端；使用 AI 编程工具仍可能在底层发生多次模型 API 请求。

12.2 使用 AI 工具不等于已经掌握 API 开发

熟练使用 IDE 中的 AI 辅助工具，不必然意味着理解：

  • HTTP 请求怎样构造，认证失败在哪里发生；
  • finish_reason 为 length 时如何防止截断结果入库；
  • Token 用量怎样统计和控制；
  • 重试在超时与费用层面造成什么影响；
  • 如何在后端隔离不同用户的会话和密钥；
  • 如何将一次模型调用封装成可靠业务 API。

反过来，会写一次 client.chat.completions.create() 也不意味着掌握多文件改造、系统调试和代理式开发。这是两个相关但不同层次的能力。

13. 两个调用层面的常见误解

误解一：“我在 ChatGPT 里能聊天，Python 直接使用同一个账号就能调用 API。”

不成立。 ChatGPT 产品登录、订阅与开发者 API 的认证和计费可能分别管理。应按照相应 API 平台创建凭据、查看可用模型及配额。

误解二：“用了 OpenAI Python SDK，就一定在调用 OpenAI 模型。”

不成立。 SDK 支持配置 base_url；DeepSeek 等服务通过兼容接口允许使用同一 SDK 访问其模型。兼容并不保证所有参数和事件语义完全一致。

误解三：“返回 HTTP 200 代表任务成功。”

不成立。 还要检查响应结构、完成状态、内容完整性、格式与业务正确性。

误解四：“finish_reason='stop' 表示答案正确。”

不成立。 stop 只反映生成停止方式，不证明事实性。

误解五：“输入 Token 只有用户那一句话。”

不成立。 系统指令、历史消息、检索资料、工具描述等都可能消耗输入 Token。

误解六：“只调用一次 SDK 方法，就只会产生一次 HTTP 请求。”

不一定。 SDK 自动重试和应用层重试可能增加实际请求次数。

误解七：“模型告诉我已经修改文件，就是工程已经修改。”

不成立。 除非有受控工具真实执行并检查实际文件、命令、Git diff，否则模型文本不是文件操作证据。

误解八：“所有兼容 OpenAI 的 API 都支持 Responses 的全部能力。”

不成立。 第三方兼容服务可能仅支持一部分字段，忽略不支持的字段，或提供不同的会话状态行为。必须查阅对应供应商的兼容性说明。

14. 把一次模型调用纳入可观测的工程系统

实际工程可以记录一条简化调用元数据（以下为数据结构示例，不含用户原文）：

json
{
  "business_request_id": "req_example_001",
  "provider": "deepseek",
  "model": "deepseek-flash",
  "api_family": "chat_completions",
  "prompt_version": "v1.2",
  "response_id": "example_completion_001",
  "finish_reason": "stop",
  "latency_ms": 752,
  "prompt_tokens": 52,
  "completion_tokens": 27,
  "total_tokens": 79,
  "validation_status": "passed",
  "error_type": null
}

上述数据是演示记录，不是真实模型调用结果。

建议将 validation_status 与 finish_reason 分开。一个请求可能生成正常结束但校验失败，也可能生成部分文本后因超时失败。为了能进行同一组问题的 A/B 回归，还应保存经批准的模型版本、提示词版本、测试样本 ID 和必要的参数配置。

在多次工具调用的 Agent 中，一个用户请求可能派生多个模型调用，需分别记录其 Token 用量和响应状态，再汇总到业务请求维度。

text

   ├── 直接调用模型 API：开发者自行编排
   │    ├── 组装输入消息

这一条学习目标的本质，是掌握 “直接模型推理接口”与“构建在模型之上的工程工具”之间的责任边界。仅有模型文本不等于业务成功；只有在协议、输出、业务与操作证据均被检查之后，结果才可以进入后续流程。

附录 B：关键术语简释

  • API（Application Programming Interface）：程序之间约定的调用接口。
  • SDK（Software Development Kit）：封装接口、类型与开发辅助能力的工具库。
  • Inference（推理）：使用已训练模型的参数计算输出。
  • Request / Response：发送给服务的请求与服务返回的结果。
  • Completion：模型基于输入产生的生成结果。
  • Finish reason：模型生成停止的原因。
  • Usage：本次调用的用量统计。
  • Prompt Token：输入侧使用的 Token。
  • Completion Token：输出侧产生的 Token。
  • Rate Limit：单位时间或并发维度的请求限制。
  • Retry：遇到可重试错误后重新发送请求。
  • Idempotency（幂等）：重复执行不会造成重复业务副作用的性质。
  • Coding Agent：在模型推理基础上具备项目感知、工具执行、反馈循环的编程代理系统。
