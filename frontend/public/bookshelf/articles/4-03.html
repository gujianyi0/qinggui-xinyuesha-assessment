RAG、来源引用与知识更新（三）：资料来源、章节、版本与引用证据核验

文档性质：独立的技术知识手册。所有示例中的游戏设定和数值均为教学构造，不代表任何实际游戏规则。

适用范围：Python、FastAPI、PostgreSQL/pgvector、RAG 检索、Agent 工具调用及审计日志。

1. 问题的本质：引用与证据不是一回事

RAG（Retrieval-Augmented Generation）通过外部资料辅助模型生成回答，但存在一个容易被忽略的区别：

  • 资料存在：知识库里有某个文档。
  • 资料被检索到：某个分块进入检索结果。
  • 资料进入上下文：模型确实收到了该分块内容。
  • 模型给出了引用：回答附上了源文档、编号或链接。
  • 引用真实支持说法：被引用的原文能够证明对应陈述，且其版本、适用范围与当前问题一致。

只有最后一步才是“可信引用”的核心。一个完全真实的网址，也可能被错误地用于支持网站中根本没有提及的结论。

例：

  • 已核实的原文：版本 1.1 中，角色青霄的基础生命值为 4。
  • 合理回答：版本 1.1 中，青霄的基础生命值为 4。〔规则文档 v1.1，第 1 章〕
  • 错误引用：版本 1.1 中，青霄的生命值为 6。〔规则文档 v1.1，第 1 章〕
  • 范围错误：青霄在所有版本中的生命值都为 4。〔规则文档 v1.1，第 1 章〕

第二和第三种回答都带有看似“正确”的来源，却没有获得该来源的实际支持。我们必须分别检查引用定位是否有效、证据是否支持陈述和陈述是否适用于当前条件。

2. RAG 引用体系中的四个对象

2.1 Source Document：源文档

源文档是用户实际上传、系统同步或通过合法渠道获得的原始资料。例如 PDF、Markdown、HTML 页面、数据库规则记录和官方 API 数据。通常需要记录：

元数据 含义 典型示例
document_id 文档逻辑身份，跨版本稳定 game-rules
source_type 来源类别 pdf, web, database
source_uri 文档原始地址或内部存储位置 https://example.org/rules
title 文档标题 战斗规则
publisher 发布主体 官方规则维护组
tenant_id 所属租户，控制数据访问范围 team-A
license 授权和使用限制 internal-use
retrieved_at 系统获取资料的时间 ISO 8601 时间戳
source_status 来源的当前管理状态 active, archived

source_uri 不能代替文档版本 ID：网页内容可能原地更新，URL 不变而正文发生变化。

2.2 Document Version：文档版本

一个逻辑文档可能有多个内容快照。对同一份规则，可以存在 v1.0、v1.1、v1.2；每个版本都应视为独立、不可悄悄覆盖的可追溯数据对象。

核心字段：

  • version_id：内部唯一主键，不应仅由文档标题推导。
  • document_id：关联逻辑文档。
  • business_version：来源声明的业务版本，例如 1.2。
  • content_sha256：原始内容快照哈希，用于完整性检查。
  • published_at：来源宣称的发布时间。
  • valid_from / valid_to：规则在业务上生效的时间范围（可能为空）。
  • ingested_at：系统实际导入时间，和业务生效时间不是一回事。
  • status：草稿、已发布、弃用、撤销等状态。
  • parser_version：本次解析流水线的软件版本。

四种“版本”不能混淆：

  1. 业务版本：游戏规则 1.2、政策 2026-11 版。
  2. 源文件版本：内容变更记录、哈希或仓库提交。
  3. 解析版本：不同解析器可能得到不同段落或坐标。
  4. 索引版本：分块策略、Embedding 模型或索引构建批次。

即使业务版本没变，重新 OCR 或重新分块也会改变检索对象；反过来，即使使用同一 Embedding，来源内容改变也必须重新判断引用是否仍指向正确文本。

2.3 Chunk / Node：检索分块

Chunk 是为搜索或模型上下文而产生的内容片段，它通常只是原始资料的一部分。一个分块至少应保留：

json
{
  "chunk_id": "ck-001",
  "document_id": "game-rules",
  "version_id": "game-rules@1.2:sha256-prefix",
  "section_path": ["第一章", "角色参数", "青霄"],
  "page_start": 6,
  "page_end": 6,
  "start_char": 3421,
  "end_char": 3496,
  "text_sha256": "...",
  "parser_version": "parser-2",
  "index_batch_id": "index-20261111-A",
  "tenant_id": "team-A",
  "visibility": "internal"
}

上述字段是推荐的应用数据契约，并非所有 RAG 框架的默认字段。LlamaIndex 文档区分 Document 和 Node，Node 可以关联来源并携带元数据及关系信息；LangChain 的 Document 同样有 page_content、metadata 和可选 id。它们提供基础能力，实际版本治理仍需要业务层设计。

2.4 Evidence / Citation：引用与证据关系

一个引用至少需要关联：

  • claim_id：回答中的哪条陈述。
  • version_id / chunk_id：使用哪个版本、哪块资料。
  • anchor：原文精确位置（页、行、字符区间、表格单元格等）。
  • quote 或 quote_hash：被引用的实际内容或其完整性校验值。
  • support_status：该内容是否支持该陈述，及由何种方式判定。

这形成了 Claim → Evidence Span → Chunk → Document Version → Source 的证据链。

3. 来源溯源（Provenance）的理论基础

来源溯源不仅回答“答案引用了什么”，还回答“这些数据是怎样形成的”。

W3C PROV 将来源关系分成若干概念：

  • Entity：资料、文件、版本、分块、答案等实体。
  • Activity：上传、解析、分块、索引、检索、生成、审核等活动。
  • Agent：执行活动的用户、系统或组织。
  • Derivation：一个实体从另一个实体派生的关系。

一个典型的来源关系可以写成：

text
原始 PDF（Entity）
    │
    ├── [解析活动 / parser v2]
    ↓
解析文本（Entity）
    │
    ├── [分块活动 / splitter v3]
    ↓
Chunk（Entity）
    │
    ├── [Embedding / 索引活动]
    ↓
索引记录（Entity）
    │
    ├── [检索活动]
    ↓
检索证据集合（Entity）
    │
    ├── [生成活动 / model / prompt version]
    ↓
带引用的答案（Entity）

如果无法追溯这些关系，就容易出现“答案带有引用，但原文已经更新、引用坐标失效”的问题。

4. 资料解析时怎样保存章节与原文坐标

4.1 Markdown / HTML / 纯文本

应同时保存：

  • 文档标题和章节层级，例如 第 2 章 > 2.3 技能 > 2.3.1 使用限制。
  • 原始字符串中的字符偏移 start_char、end_char。
  • 解析后文本对应的来源位置；如果清洗改变偏移，应保留映射关系。
  • 原始文档快照、原始哈希和解析后的文本哈希。

字符区间常采用 Python 风格的半开区间 [start, end)。必须在数据契约中声明偏移单位，例如 Unicode 码点索引、UTF-8 字节偏移或 UTF-16 code unit。Python 的字符串切片使用 Unicode 码点索引；浏览器 JavaScript 字符串下标按 UTF-16 code unit 计数，两者对某些补充平面字符的偏移会不同。

4.2 PDF

PDF 引用可能需要：

  • 页码（注意物理页序号和印刷页码可能不同）。
  • 页面上的文本块、坐标边框 bbox。
  • 表格行列、单元格位置。
  • 原始页文本和解析器输出的对照。
  • 扫描件的 OCR 结果及置信度（当 OCR 技术支持提供时）。

页码通常比纯分块 ID 更适合用户核对，但只有页码仍然不够精确。一页可能包含多个互相矛盾的条件和大量文字。更好的是在同一页面中定位具体原文范围。

4.3 表格、图片和多模态内容

  • 表格需要保留行头、列头和单位。单独抽取 15 而丢失 价格（元） 无法判断含义。
  • 图片中的结论应标记图像或图表 ID、页码以及对应区域；不要把模型对图片的描述伪装成源文件本来具有的文字。
  • OCR 错误会影响引用可信度；高风险场景需要与原始版面交叉校验。

5. 分块必须保留父子关系

5.1 典型错误

python
# 错误方向：只保留文本，丢弃来源元数据
chunks = [text[i:i+500] for i in range(0, len(text), 500)]

如果后续只把字符串写进向量数据库，再想恢复章节、版本与页码，就非常困难。

5.2 正确原则

分块之前先明确并持久化源文档和版本身份；分块之后将来源身份、章节路径和精确偏移复制或关联到每个分块。

python
chunk = {
    "chunk_id": "...",
    "document_version_id": version_id,
    "section_path": ["第 1 章", "技能规则"],
    "start_char": start,
    "end_char": end,
    "text": source_text[start:end],
}

应优先将可复用的元数据与版本主键保持关联，而不是完全依赖向量库中嵌入的一份冗余字符串。

5.3 重叠分块与引用

如果相邻 Chunk 有重叠，同一原文可能被检索到两次：

  • 不要因为同一句话出现于两个 Chunk，就把它当成两份独立来源。
  • 引用去重应考虑 (version_id, start_char, end_char) 或等价的原文定位信息。
  • 评测覆盖率时要避免将重复的分块计为独立证据。
  • 若文本被规范化（合并空格、删脚注），引用锚点应映射回来源快照，而不是只定位规范化后的索引文本。

6. 版本治理：版本存在、版本有效与版本适用

6.1 最新版本不一定适用

用户问“1.1 版本的角色生命值”，应检索 1.1 的规则，即使当前最新版本已经是 1.3。

用户问“现在的规则”，则需要定义“现在”的判定条件，例如依据有效期、发布状态或用户指定的运行环境；不能简单拿 MAX(version_string) 或“最新导入的一份文件”当成唯一权威。

6.2 文档时间的四个常见字段

字段 含义 不能互相替代的原因
published_at 来源公开发布时间 发布日不一定是生效日
valid_from 规则开始适用的时间 可能提前发布
ingested_at 系统导入时间 导入可能晚于生效
indexed_at 向量索引完成时间 索引可能滞后于导入

在法规、合同、游戏补丁、价格政策等有时间效力的领域，保留这几个时间点十分重要。

6.3 推荐的版本处理策略

  1. 新内容写入新的不可变 document_version，不要覆盖旧版本。
  2. 同步记录发布状态、有效期和来源权威等级（权威等级应有明确维护规则）。
  3. 变更资料时重新解析、重新分块或重建索引，并保存新批次标识。
  4. 查询时先确定租户与访问权限，再按业务版本、发布时间、有效期过滤。
  5. 新旧版本冲突时标记冲突，不能把两个版本的片段直接拼成一个没有版本说明的结论。
  6. 回答引用锁定具体版本快照；历史答案可继续核对其当时依据的版本，即使新版本已发布。
  7. 撤销、过期或删除后的资料应有明确治理状态；是否允许历史审计访问应由权限政策决定。

7. 来源可靠性、权限与优先级

来源身份清晰不代表来源一定正确。 外部网页可能包含错误，内部文档可能过期，用户上传文件可能只是草稿。来源元数据应与可信度判断分离。

一套可解释的证据优先级规则可能包含：

  • 官方正式发布资料优先于未经验证的转述，但应结合具体问题。
  • 当前适用版本优先于旧版本（除非问题明确要求旧版）。
  • 具体规则条款优先于没有可核实依据的概述。
  • 有效时间、适用对象、地域或角色必须一致。
  • 同等级权威资料产生实质冲突时，明确告知冲突并请求补充信息或人工核实。

还需要 对象级访问控制。即使一个分块与查询高度相关，也不能将另一租户或无权访问的资料提供给当前用户。检索前、索引后和引用展开时均应有授权保护。

例如 PostgreSQL 支持 Row-Level Security，但 RLS 的设置并不自动消除所有风险；数据库角色、表所有者、超级用户权限及连接管理都会影响其实际效果。正式服务应结合后端授权和行级策略设计。

8. 引用格式：用户能否真正核查

推荐一个机器与前端都容易处理的响应契约：

json
{
  "answer": "在 1.1 版本中，青霄的基础生命值为 4。",
  "claims": [
    {
      "claim_id": "c1",
      "text": "在 1.1 版本中，青霄的基础生命值为 4。",
      "citation_ids": ["e1"]
    }
  ],
  "citations": [
    {
      "citation_id": "e1",
      "document_id": "game-rules",
      "version_id": "rules-v1.1-immutable",
      "title": "游戏规则 1.1",
      "section_path": ["第 1 章", "角色参数"],
      "page": 6,
      "quote": "青霄的基础生命值为 4。",
      "anchor": {"start_char": 120, "end_char": 133},
      "support_status": "verified"
    }
  ]
}

这是示意格式；实际项目必须依据源文件计算偏移值，不能直接把这里的示意数字当作有效坐标。

前端可以把引用显示为 〔游戏规则 1.1，第 1 章，p.6〕，点击后打开来源片段，并突出显示支持该句的原文。

引用交互应提供：

  • 清晰的标题、版本、章节、页码或时间位置。
  • 可展开的原文片段，而非仅仅一个打不开的 URL。
  • 来源已被撤销或没有权限时的明确提示。
  • 版本不一致或证据冲突时的提示。
  • 引用定位失败时的错误状态，而不是悄悄显示错误片段。

9. Claim-level Attribution：按陈述逐条绑定证据

一段回答可能包含多条事实：

青霄在 v1.1 的生命值为 4，v1.2 提升到 5，而且从未削弱过。

它至少有三条可拆分的陈述：

  1. v1.1 的基础生命值为 4。
  2. v1.2 的基础生命值为 5。
  3. 从未削弱过。

前两条可以分别由 v1.1、v1.2 文档支持；第三条是涵盖所有历史版本的整体判断，只有两个版本的片段通常无法证明“从未”。

因此实际系统应将回答拆为可核验的原子陈述，然后为每条陈述提供一条或多条足够的证据；不能只给整段文字附一个来源编号就视为正确。

9.1 证据支持的常见类型

类型 示例 判断
直接支持 原文：基础生命值为 4 → 回答：基础生命值为 4 支持
合理推导 两条独立有效规则结合可得到结论 需明确推导过程
仅主题相关 文档讲角色技能，未给生命值 不支持
直接矛盾 原文为 4，回答为 5 不支持
条件遗漏 原文说“夜间技能生效”，回答省略夜间条件 不充分
版本错配 引用 v1.0，回答声称 v1.2 不支持
过度概括 文档只覆盖某个版本，回答声称所有版本 不支持
只引用出处但无原文 链接存在，但未定位相关论据 待核实

9.2 “支持”与“真实”仍有差别

即使被引用的文档确实写着某句话，也不保证文档的内容与外部现实一致。

  • Faithfulness / Groundedness：回答能否从给定证据中得到支持。
  • Factual correctness：回答是否与独立、可信的事实基准一致。

两者要分别评测。Ragas 的 Faithfulness 文档便使用“拆分陈述、判断证据支持关系”的方式描述其指标。

10. 引用的两层验证

10.1 第一层：机械完整性校验

可由确定性程序验证：

  • citation_id 是否在本次允许的证据集合中。
  • version_id、chunk_id 是否真实存在。
  • 版本是否属于指定文档且用户有权访问。
  • 原文字符区间是否合法。
  • 引用摘录是否与不可变源快照中的文本一致。
  • 摘录哈希、源版本哈希是否一致。
  • 当前问题的版本条件是否匹配。

这层校验相对容易可靠自动化。

10.2 第二层：语义支持校验

需要判断：证据的含义是否支持该陈述。

可以采用：

  • 规则型验证：对结构化字段或确定性计算，例如数值、日期、版本约束。
  • 人工审核：关键条款、外部来源真实性和复杂推理。
  • NLI（自然语言推断）模型或 LLM Judge：辅助判断 entailment / contradiction / neutral，但不能保证零误判。
  • 多证据推理检查：答案依赖两个以上片段时，检查每个前提和推导步骤。

禁止将“引用 ID 存在”“关键词重叠”“相似度高”直接标记为语义支持已通过。

11. 引用验证推荐流水线

text
用户问题
   ↓
身份认证、租户权限与任务约束
   ↓
解析版本、时间和其他查询条件
   ↓
检索 → 重排 → 选择允许使用的证据
   ↓
冻结本次上下文的证据快照和引用 ID
   ↓
模型生成结构化回答与 Claim-Citation 映射
   ↓
检查输出 Schema 和引用 ID 合法性
   ↓
按引用 ID 读取实际原文并核对偏移/版本/权限
   ↓
对每条 Claim 进行语义支持验证
   ↓
标记 Supported / Contradicted / Not Enough Evidence
   ↓
生成可点击的最终回答；无法证明时拒绝编造或明确说明不确定

对于可信度要求较高的系统，不应只在提示词中要求“请引用来源”，而是由程序执行引用回查，并建立独立的证据关系表。

12. 检索结果编号为什么不能直接当长期引用

一些实现会在当前请求中用 [1]、[2]、[3] 表示资料片段。这种编号适合当前回答，但不适合永久存储，因为：

  • 下次检索排序可能变化。
  • 不同问题可能使用相同编号指向不同来源。
  • 重新分块后 Chunk ID 可能变化。
  • 来源可能新增、删除或变更版本。

应该在当前请求中维护 临时编号 → 稳定 version_id / anchor 的映射，长期记录保存稳定的来源键和本次上下文快照标识。

一个稳定的引用 ID 可以由不可变文档版本 ID 和原文定位派生，但需要考虑偏移规范、编码、碰撞以及不同解析版本下锚点是否仍然有效。

13. PostgreSQL 关系表设计示例

以下为简化结构，省略用户、租户、ACL、索引和部分外键；不能直接视为生产数据库完整迁移脚本。

sql
CREATE TABLE source_documents (
    document_id TEXT PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    title TEXT NOT NULL,
    source_uri TEXT,
    source_type TEXT NOT NULL
);

CREATE TABLE document_versions (
    version_id TEXT PRIMARY KEY,
    document_id TEXT NOT NULL REFERENCES source_documents(document_id),
    business_version TEXT NOT NULL,
    content_sha256 TEXT NOT NULL,
    original_text TEXT NOT NULL,
    status TEXT NOT NULL,
    published_at TIMESTAMPTZ,
    valid_from TIMESTAMPTZ,
    valid_to TIMESTAMPTZ,
    ingested_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE(document_id, business_version, content_sha256)
);

CREATE TABLE source_chunks (
    chunk_id TEXT PRIMARY KEY,
    version_id TEXT NOT NULL REFERENCES document_versions(version_id),
    section_path TEXT[] NOT NULL,
    page_start INTEGER,
    page_end INTEGER,
    start_char INTEGER NOT NULL,
    end_char INTEGER NOT NULL,
    text_sha256 TEXT NOT NULL,
    CHECK (end_char > start_char)
);

CREATE TABLE answer_claims (
    claim_id TEXT PRIMARY KEY,
    answer_id TEXT NOT NULL,
    claim_text TEXT NOT NULL
);

CREATE TABLE claim_evidence (
    claim_id TEXT NOT NULL REFERENCES answer_claims(claim_id),
    chunk_id TEXT NOT NULL REFERENCES source_chunks(chunk_id),
    evidence_start INTEGER NOT NULL,
    evidence_end INTEGER NOT NULL,
    support_status TEXT NOT NULL,
    reviewer_type TEXT,
    review_version TEXT,
    PRIMARY KEY (claim_id, chunk_id, evidence_start, evidence_end)
);

工程注意事项：

  • SQL 约束 end_char > start_char 只验证两者大小，不保证偏移在源文本范围内；这种验证还要由应用层执行。
  • content_sha256 是完整性检查工具，不构成来源可信度证明。
  • reviewer_type 需要区分人工复核、规则算法、模型裁判，避免混淆。
  • 多租户生产场景需要租户键、组合外键及 RLS 或同等级权限体系，防止跨租户外键关联。
  • 版本如果已用于历史引用，应保留其不可变快照或有明确的合法删除与审计替代方案。
  • PostgreSQL 的数组和全文检索能力可与 pgvector 结合，但本节重点是引用数据模型，不是向量相似度 SQL。

14. Python 完整示例：保存版本、章节与原文锚点

下面的示例仅依赖 Python 标准库，能实际执行。它实现四个基本功能：

  1. 保存不可变的教学文档版本。
  2. 创建精确定位的原文证据锚点。
  3. 验证引用位置、原文哈希、版本和租户访问权限。
  4. 将“机械定位正确”与“已经人工复核语义支持”严格区分。

14.1 完整代码 provenance_demo.py

python
from __future__ import annotations

from dataclasses import dataclass
from enum import Enum
from hashlib import sha256


def digest(text: str) -> str:
    return sha256(text.encode("utf-8")).hexdigest()


@dataclass(frozen=True)
class DocumentVersion:
    document_id: str
    version_id: str
    business_version: str
    tenant_id: str
    title: str
    source_uri: str
    section: str
    text: str
    content_hash: str

    @classmethod
    def create(
        cls, *, document_id: str, business_version: str,
        tenant_id: str, title: str, source_uri: str,
        section: str, text: str,
    ) -> "DocumentVersion":
        content_hash = digest(text)
        return cls(
            document_id=document_id,
            version_id=f"{document_id}@{business_version}:{content_hash[:16]}",
            business_version=business_version,
            tenant_id=tenant_id,
            title=title,
            source_uri=source_uri,
            section=section,
            text=text,
            content_hash=content_hash,
        )


@dataclass(frozen=True)
class Citation:
    citation_id: str
    claim_id: str
    version_id: str
    start_char: int
    end_char: int
    quoted_text: str
    quote_hash: str


class Status(str, Enum):
    ANCHOR_INVALID = "ANCHOR_INVALID"
    VERSION_NOT_FOUND = "VERSION_NOT_FOUND"
    FORBIDDEN = "FORBIDDEN"
    REVIEW_REQUIRED = "REVIEW_REQUIRED"
    SUPPORTED = "SUPPORTED"
    NOT_SUPPORTED = "NOT_SUPPORTED"


class ProvenanceStore:
    def __init__(self) -> None:
        self.versions: dict[str, DocumentVersion] = {}
        # (claim_id, citation_id) → 人工/独立流程复核的支持判断。
        self.reviews: dict[tuple[str, str], bool] = {}

    def add(self, doc: DocumentVersion) -> None:
        if doc.version_id in self.versions:
            if self.versions[doc.version_id] != doc:
                raise ValueError("版本 ID 冲突，禁止覆盖不可变快照")
            return
        if digest(doc.text) != doc.content_hash:
            raise ValueError("文档快照哈希无效")
        self.versions[doc.version_id] = doc

    def anchor(
        self, *, doc: DocumentVersion, claim_id: str, exact_quote: str
    ) -> Citation:
        if not exact_quote:
            raise ValueError("引用文字不能为空")
        start = doc.text.find(exact_quote)
        if start < 0:
            raise ValueError("原文中不存在该引用片段")
        end = start + len(exact_quote)
        citation_id = digest(
            f"{doc.version_id}:{start}:{end}:{exact_quote}"
        )[:20]
        return Citation(
            citation_id=citation_id,
            claim_id=claim_id,
            version_id=doc.version_id,
            start_char=start,
            end_char=end,
            quoted_text=exact_quote,
            quote_hash=digest(exact_quote),
        )

    def review_support(
        self, *, claim_id: str, citation_id: str, supports: bool
    ) -> None:
        # 教学示例：假定该入口只能由已授权的审核流程调用。
        # 生产环境必须验证审核人员身份、版本和审核对象。
        self.reviews[(claim_id, citation_id)] = supports

    def verify(self, *, citation: Citation, tenant_id: str) -> Status:
        doc = self.versions.get(citation.version_id)
        if doc is None:
            return Status.VERSION_NOT_FOUND
        if doc.tenant_id != tenant_id:
            return Status.FORBIDDEN
        if digest(doc.text) != doc.content_hash:
            return Status.ANCHOR_INVALID
        start, end = citation.start_char, citation.end_char
        if start < 0 or end <= start or end > len(doc.text):
            return Status.ANCHOR_INVALID
        actual = doc.text[start:end]
        if actual != citation.quoted_text:
            return Status.ANCHOR_INVALID
        if digest(actual) != citation.quote_hash:
            return Status.ANCHOR_INVALID
        expected_id = digest(
            f"{doc.version_id}:{start}:{end}:{actual}"
        )[:20]
        if citation.citation_id != expected_id:
            return Status.ANCHOR_INVALID
        reviewed = self.reviews.get((citation.claim_id, citation.citation_id))
        if reviewed is None:
            return Status.REVIEW_REQUIRED
        return Status.SUPPORTED if reviewed else Status.NOT_SUPPORTED


def example() -> None:
    store = ProvenanceStore()
    v11 = DocumentVersion.create(
        document_id="demo-game-rules", business_version="1.1",
        tenant_id="tenant-a", title="演示规则 1.1",
        source_uri="internal://demo/rules/1.1",
        section="第 1 章 / 角色参数",
        text="第 1 章 角色参数\n版本 1.1 中，青霄的基础生命值为 4。\n",
    )
    v12 = DocumentVersion.create(
        document_id="demo-game-rules", business_version="1.2",
        tenant_id="tenant-a", title="演示规则 1.2",
        source_uri="internal://demo/rules/1.2",
        section="第 1 章 / 角色参数",
        text="第 1 章 角色参数\n版本 1.2 中，青霄的基础生命值为 5。\n",
    )
    store.add(v11)
    store.add(v12)

    cite = store.anchor(
        doc=v11, claim_id="claim-1",
        exact_quote="版本 1.1 中，青霄的基础生命值为 4。",
    )
    print(store.verify(citation=cite, tenant_id="tenant-a"))
    # 在独立审核人员确认陈述与原文语义一致之后：
    store.review_support(
        claim_id="claim-1", citation_id=cite.citation_id, supports=True
    )
    print(store.verify(citation=cite, tenant_id="tenant-a"))
    print(store.verify(citation=cite, tenant_id="tenant-b"))


if __name__ == "__main__":
    example()

运行：

bash
python provenance_demo.py

预期状态为 REVIEW_REQUIRED、SUPPORTED、FORBIDDEN。前两者说明：原文定位正确时，也不能自动声称已经通过语义支持校验。

14.2 该示例的边界

这个教学实现并非完整 RAG，也不是真实模型评测：

  • 不执行 Embedding、向量索引和语义检索。
  • 不自动判定陈述是否被证据支持；语义支持结果由独立审核流程传入。
  • 假设 review_support() 只能由可信后端调用；尚未实现审核权限与不可变审核记录。
  • anchor() 查找首次完全相同的子串；真实资料中重复文本应携带章节及位置消歧。
  • 使用进程内字典而非数据库；正式系统应持久化来源快照、审核记录和权限信息。
  • 未实现 OCR 坐标映射、文档撤销和生效时间过滤。
  • 示例状态只描述本次调用的单条引用；生产系统还要做 Claim → 多证据关系的完整校验。

16. 真实 RAG 中的证据验证指标

16.1 引用有效率（Anchor Validity）

text
引用有效率 = 可定位到正确原文快照的引用数 / 总引用数

检查的是 version_id、锚点、权限和原文一致性；不能证明内容支持回答。

16.2 引用支持率（Citation Support Rate）

text
引用支持率 = 经核验支持其关联陈述的引用数 / 参与核验的引用数

应说明哪些引用被人工审核、哪些由模型裁判审核；分母是否包含定位失败、未核验和拒绝处理的引用，也要在评测协议中预先规定。

16.3 陈述证据覆盖率（Claim Coverage）

text
陈述证据覆盖率 = 拥有充分证据支持的事实陈述数 / 总事实陈述数

一句话可能有多个子事实，评测要按独立陈述计算，防止一个宽泛引用覆盖多个互不相关的主张。

16.4 版本一致率（Version Consistency）

text
版本一致率 = 引用版本满足问题版本/时间条件的陈述数 / 需要版本约束的陈述数

16.5 Faithfulness / Groundedness

Faithfulness 通常表示回答的陈述能够从已检索的上下文中得到多少支持。Ragas 将其建立在“拆分陈述—判断每条是否被上下文支持”的基础上。它与事实真实度不同，尤其不能替代来源本身的权威性检查。

16.6 评测集建议

至少覆盖：

  • 单文档精确事实。
  • 同文档多章节联合推导。
  • 新旧版本差异。
  • 发布日期与生效时间差异。
  • 未收录资料。
  • 检索到相关但不支持结论的资料。
  • 明确矛盾或条件缺失。
  • 需要多个来源共同支持的结论。
  • 无权限资料不得出现在引用中。
  • 分块重叠导致的重复引用。
  • 文档更新后历史答案能否回溯。
  • OCR 错位、表格单位丢失和锚点变更。

对同一组样例比较不同模型、索引、分块或提示词版本，分开报告检索质量、引用有效率、语义支持率及最终答案正确率。

17. 常见故障与定位方法

故障 表现 首先检查
来源丢失 只剩 Chunk 文本，无法打开原文 导入阶段是否保存 document_id、version_id
章节错误 引用显示了其他章节 Parser 结构识别和 metadata 继承
页码错位 引用打开的 PDF 页面不匹配 印刷页码与物理页码映射
版本混淆 回答混用 v1.0 与 v1.2 查询过滤条件与生效时间
锚点漂移 重新清洗后字符位置失效 原始快照与偏移映射
引用幻觉 模型输出未检索到的引用 ID 引用 ID 是否从本次证据列表校验
相关而不支持 引用主题相关，却没有结论 Claim-level 语义支持审核
跨用户泄露 用户看到了其他租户资料 后端授权与检索过滤
证据互相矛盾 不同正式文档存在不同规则 来源优先级、版本、日期与冲突处理
历史引用失效 新文档覆盖了旧原文 不可变版本快照及历史锚点
UI 无法核查 只有文件名没有原文片段 引用解析接口和前端高亮定位

19. 归纳：本节知识的三个层次

第一层：资料可追溯。 保存源文档、章节层级、版本与时间、生效范围、原始快照及分块关联，确保引用能找到“哪一版资料的哪一处文字”。

第二层：引用可验证。 由程序校验引用 ID、权限、版本、页码或字符锚点、原文哈希，避免无效、越权、过期或漂移的引用。

第三层：陈述可证明。 将答案拆成事实陈述，再分别判断证据是否真正支持该说法；缺失、矛盾、跨版本或超出来源范围时，不把相关文档伪装成可靠证据。

最终结论：保存来源只是起点；真正可信的 RAG 引用需要“可追溯的原始证据 + 可核验的定位信息 + 逐条陈述的语义支持关系”。
