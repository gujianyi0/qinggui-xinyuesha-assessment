1. 模型生成与确定性计算的职责边界

大语言模型通常根据上下文概率分布生成后续 Token。它能理解复杂问题、转换文本、抽取字段、选择工具、组织答案，但它的自然语言输出并不是由强制数学正确性的执行器生成。即使模型能正确写出算式，也不能将其结果直接等价为经过业务规则验证的计算结果。

实际系统至少存在三类不同的工作：

工作类型 典型问题 建议的责任主体 主要验证机制
确定性计算 总价、税额、概率公式、时差、库存差额、余额 程序、数据库查询或受控计算工具 单元测试、边界值、数值不变量
事实查询 某版本角色生命值、制度生效日期、合同条款 可信结构化数据与带版本的原始资料 引用定位、版本一致性、数据血缘
语言生成与任务理解 解释规则、总结报告、生成草稿、选择工具 语言模型 事实校验、输出校验、人工评测

正确的职责划分不等于完全禁止模型参与计算。 模型可以识别用户表达、抽取参数，甚至生成候选计算表达式；但对于有金钱、权限、数量、时间或安全后果的数字，最终的运算、验证与业务决策应由可信代码完成。

典型结构如下：

text
用户：角色 A 使用 3 件单价 19.99 的商品，折扣 15%，税率 6%，总价多少？
    │
    ├── 模型理解意图，提取单价、数量、折扣、税率（仍需校验）
    │
    ▼
Pydantic / 业务输入校验：数量 >= 0，折扣在 [0,1]，单位和币种正确
    │
    ▼
确定性计算工具：Decimal + 约定的折扣/税额/舍入顺序
    │
    ▼
模型引用工具结果，用自然语言解释
    │
    ▼
输出验证：禁止把工具结果替换成模型自己重新计算的数字

对于“重要数值”，系统设计上可以让程序直接生成固定字段或表格，由模型只负责解释其含义。若程序计算结果与模型叙述不一致，应以程序为准并拦截不一致回答。

2. 重要数值为什么要由程序计算

2.1 模型的数值输出与程序执行不同

程序中的表达式 19.99 * 3 由指定的算术运算执行；模型可能通过训练学到运算模式或推理策略，但生成文字并不自动证明其遵循正确的数值语义。对于非常长的数字、数量级换算、跨字段计算和复杂的多步骤业务规则，错误风险更高。

此外，正确的数字也可能建立在错误的输入上：

  • 折扣被识别成 15 而不是 0.15；
  • 税率应在折扣后计算，却在折扣前计算；
  • 把人民币金额按美元处理；
  • 用当前规则计算旧版本角色数值；
  • 参与求和的记录被遗漏或重复；
  • 一项计费数值包含缓存 Token，另一项又将缓存 Token 重复累加。

因此一条可靠的数值处理链应区分：输入正确性 → 运算规则正确性 → 程序结果正确性 → 输出展示正确性。

2.2 哪些数值应优先由程序计算

  • 资金、费用、折扣、税费、结算和余额；
  • 配额、额度、库存、数量与百分比；
  • 游戏中的伤害、生命值、概率、冷却与规则修正；
  • 时间、时区、日期差、过期时间与限流窗口；
  • 模型的 Token 成本、质量指标、延迟统计；
  • 排名、阈值判定、合格/不合格条件。

关键不是数字“看起来简单”，而是计算是否需要可重复、可审计、可纠错和可复现。

3. Decimal、单位、舍入和计算规则

3.1 float 不是通用的十进制金额类型

二进制浮点数不能精确表示所有十进制小数。例如 0.1 + 0.2 在典型的 Python 浮点实现中不会精确等于 0.3。一般科学计算中这未必是问题；但财务、账单等领域需要明确的十进制运算规则。

python
from decimal import Decimal

print(0.1 + 0.2)  # 典型输出：0.30000000000000004
print(Decimal("0.1") + Decimal("0.2"))  # Decimal('0.3')

用字符串构造 Decimal，避免先经历二进制浮点近似：

python
from decimal import Decimal, ROUND_HALF_UP

amount = Decimal("19.99")
quantity = 3
discount = Decimal("0.15")
tax = Decimal("0.06")

# 示例业务规则：先将折后金额舍入到分，再计算并舍入税额
subtotal_after_discount = (amount * quantity * (1 - discount)).quantize(
    Decimal("0.01"), rounding=ROUND_HALF_UP
)
tax_amount = (subtotal_after_discount * tax).quantize(
    Decimal("0.01"), rounding=ROUND_HALF_UP
)
final = subtotal_after_discount + tax_amount
print(final)  # 54.03

舍入顺序属于业务规则。 逐行舍入、订单合计后舍入、税前舍入、税后舍入可能产生不同金额；不应默认这里的示例政策适用于所有国家、产品或合同。

3.2 数值结果要携带单位与口径

单独存储 100 可能含糊不清：它是 100 元、100 分、100 毫秒，还是百分比的基点？建议在数据模型中明确 currency、unit、rounding_mode、calculation_version、effective_at 等字段。

json
{
  "amount": "54.03",
  "currency": "USD",
  "calculation_version": "order-tax-v3",
  "rounding": "ROUND_HALF_UP",
  "tax_basis": "discounted_subtotal"
}

跨货币转换还需要明确使用的汇率、来源、时间与手续费策略；历史金额重算必须固定适用的汇率和政策版本。

3.3 计算结果应附带校验条件

例如 quantity >= 0、0 <= discount_rate <= 1、tax_rate >= 0、余额不能低于允许下限。数据库约束和事务可以进一步防止并发修改导致结果不一致。单靠模型输出一个看似正确的数值无法替代这些约束。

4. 重要事实如何建立依据与证据链

事实回答与“模型生成的句子”必须区分。对于有明确来源的事实，应保留证据对应关系（provenance，来源血缘）：这个事实来自哪份资料、哪个版本、哪个章节，以及如何验证它支持当前结论。

4.1 证据记录的最小结构

json
{
  "fact_key": "character.hero_a.base_hp",
  "fact_value": 4,
  "source_id": "rules/hero-a",
  "document_version": "1.2",
  "section": "角色属性",
  "excerpt": "角色 A：基础生命值为 4。",
  "effective_at": "示例版本生效时间",
  "retrieved_at": "2026-11-11T00:00:00Z",
  "source_hash": "由原始资料内容计算的 SHA-256"
}

其中 effective_at 描述事实生效时间，retrieved_at 描述系统获取资料的时间，两者含义不同。source_hash 只可证明对照的内容字节与某个哈希一致，不能单独证明内容真实或来源合法。

4.2 信息来源的层次

  1. 权威结构化事实：经过验证的数据库字段、正式规则参数、官方发布数据。通常优先用于精确数值。
  2. 原始文档：官方发布说明、法规原文、技术标准、产品手册等。需要保留版本和定位信息。
  3. 二手资料：报道、博客、社区帖子与非官方摘要。应与原始资料核对。
  4. 模型内部知识：可作为线索，但不能直接视为已核查的外部事实。

来源权威性还取决于所问的问题：公司内部的业务规则应以公司批准的当前版本为准，而不是把外部百科当作最终依据。

4.3 引用存在，不代表引用支持结论

假设回答写“角色 A 的生命值是 7”，同时附上 rules/hero-a 文档 ID。即便文档真实存在，若其内容写的是“生命值 4”，引用仍然不支持该断言。

引用核验至少需要三层：

  • 存在性：来源 ID 和片段是否存在？
  • 适用性：版本、时间、范围、对象是否与问题匹配？
  • 支持性：来源是否真的支持对应的原子化断言？

对于结构化规则数据可以通过精确键比较。对于长篇自然语言，则需要更细的证据片段匹配、规则化检查、必要时人工复核。字符串相似、引用链接可打开或模型自称有依据，都不是事实核验的充分条件。

5. 事实、引用、来源版本及冲突处理

5.1 版本必须进入查询条件

用户说“角色 A 的生命值是多少？”时，系统若同时存在 v1.1 和 v1.2 的规则，需要根据上下文确定适用版本。不能任意挑一条检索结果回答。

一种查询过程：

text
用户提问 → 提取对象与所需版本
                  │
          版本是否确定？
             /       \
           否         是
           │          │
      澄清版本     查询该版本权威资料
                       │
                  核对字段与来源
                       │
                  生成带依据的答案

5.2 来源之间发生冲突怎么办

可能原因包括旧版本与新版本混合、资料解析错误、规则例外未检索到、相同术语指向不同对象，以及真实的官方资料互相矛盾。

处理顺序应为：

  1. 核对资料的生效时间、正式版本与适用范围；
  2. 查找正式修订记录和更高权威的资料；
  3. 如果依据不足，明确说明存在冲突及各自来源；
  4. 不让模型靠“多数资料支持”自行替代权威性和适用性判断；
  5. 在需要时要求人工确认，再写入后续业务结果。

5.3 不确定性要能传给调用方

事实不完整时可返回结构化状态，例如：

json
{
  "status": "needs_evidence",
  "answer": null,
  "missing": ["规则版本", "有效原始资料"],
  "candidate_sources": ["rules/hero-a/v1.1", "rules/hero-a/v1.2"]
}

这样前端可以显示“需要补充版本”或“资料尚未核实”，而不是把模型的猜测作为正常答案展示。

6. 模型调用中应记录的元数据

为了在后续定位质量变化、成本激增或延迟退化，模型调用记录不能只有用户提问与回答。最低应包括以下字段：

类别 建议字段 作用
请求定位 request_id、trace_id、时间戳 跨前端、接口、模型和工具关联一次调用
模型信息 provider、请求的 model、响应实际模型 识别供应商与模型变更
模型配置 采样参数、最大输出限制、思考预算（若支持） 解释生成行为的差异
提示词信息 prompt_version、模板哈希、渲染版本哈希 追踪配置变更与实际输入差异
业务输入 数据集/案例 ID、知识库版本、工具版本 保证评测可比较
结果 成功/失败、结束状态、错误类型、输出校验结果 区分真正成功与仅 HTTP 成功
延迟 总耗时、首字延迟、模型耗时、工具耗时 定位性能瓶颈
用量 输入、输出、缓存、推理 Token（可用时） 计算资源和成本
成本 计费方案版本、估算成本、实际账单状态 比较改动经济性
风险 来源依据状态、拒答、越权、敏感数据检测 监测可靠性与合规性

6.1 一次用户请求可能包含多次模型调用

一个 Agent 任务可能先调用模型选择工具，再调用模型总结证据，期间还请求 Embedding 和第三方检索 API。因此要区分：

  • 调用级记录：一次真实模型 API 调用的耗时和用量；
  • 请求级记录：完整 HTTP 请求中的多个模型调用、工具和数据库操作；
  • 任务级记录：跨后台 Worker、重试和服务重启的完整业务任务成本。

如果只记录最终一次模型调用的 Token，就会低估整个 Agent 任务的实际开销。

7. 模型版本、提示词版本与结果可复现性

7.1 “模型名称相同”不一定等于后端完全相同

服务商可能更新模型的权重、基础设施或路由。公开 API 中的模型别名有时指向可更新版本。若提供快照版本号、响应模型字段、后端指纹（例如部分接口的 system_fingerprint），应将其记录下来。

然而，后端指纹不是通用的严格复现保证，供应商也可能不提供这一字段。即使模型版本与采样参数一致，推理仍可能受非确定性因素影响。

7.2 提示词版本包含两个层次

  • 模板版本：System/Developer 指令、变量位置、工具规范、输出 Schema 的版本；
  • 渲染后输入版本：实际填入的用户输入、历史片段、检索文档、规则版本形成的请求内容。

两次请求即使模板版本相同，也可能因为检索资料版本不同而产生不同回答。因此应该同时保存模板哈希与必要的检索数据版本，必要时保存受控、脱敏且权限受限的可复现输入快照。

python
from hashlib import sha256

prompt_template = "只根据给定规则回答，并提供来源。"
prompt_sha256 = sha256(prompt_template.encode("utf-8")).hexdigest()
print(prompt_sha256)

哈希不是加密。 它适合记录内容指纹，但不能代替访问控制、密钥保护或敏感数据脱敏；短而可猜的输入甚至可能被枚举比对。

7.3 一次可比较的改动，需要固定哪些变量

变量 举例
模型 同一模型 ID 或明确仅比较模型差异
提示词 A、B 两个版本，各有哈希
输入样例 同一组 case_id 与固定内容
知识库 同一版资料、同一检索配置
工具实现 数据查询和计算工具版本固定
采样 温度等参数记录在案
环境 同一类部署、并发负载及网络条件
评分 同一版本的评分规则和参考答案

如果一次修改同时换了模型、提示词和知识库，就不能仅凭质量提升断言“是提示词修改有效”。这属于因果归因问题。

8. 输入、输出、缓存和推理 Token 的用量口径

8.1 用量字段不是跨供应商完全一致的

同一次模型调用可能返回的统计包括：

  • input_tokens / prompt_tokens：本次模型处理的输入 Token，具体字段依接口而定；
  • output_tokens / completion_tokens：输出 Token，可能包含不可见的推理、结构化或控制 Token；
  • cached_tokens / prompt_cache_hit_tokens：输入中命中缓存的部分；
  • reasoning_tokens：某些推理模型在输出 Token 中用于推理的部分；
  • server_tool_use：部分供应商另外统计的服务端工具调用使用量。

例如 DeepSeek Chat Completions 的 prompt_tokens 包括缓存命中与未命中 Token，prompt_cache_hit_tokens + prompt_cache_miss_tokens = prompt_tokens；completion_tokens 用于统计生成 Token，某些模型还可能报告 reasoning_tokens。不要把缓存命中数与输入总量相加，也不要把推理 Token 与已包含它的输出总量再次相加。

类似地，OpenAI Responses API 的输出用量中，reasoning_tokens 可以作为 output_tokens_details 的子项；最终用户能看到的字符数不能替代服务端用量统计。

8.2 各类统计应各司其职

text
输入总量 input_tokens  ─── 包含 ──> 缓存命中的 cached_input_tokens
输出总量 output_tokens ─── 包含 ──> 推理使用的 reasoning_output_tokens

如果计费规则将缓存命中输入与普通输入区分价格，可拆成：

[ N_{\text{input, uncached}} = N_{\text{input,total}} - N_{\text{input,cached}} ]

[ N_{\text{output,total}} \supseteq N_{\text{output,reasoning}} ]

这里的包含关系针对提供相应字段且采用此口径的接口，不能无条件套用于每一种供应商；具体应以官方文档为准。

8.3 流式响应时尤其容易漏记用量

SSE 增量通常不是完整的用量记录。某些 API 需要等到结束事件才返回累积 Token 统计。若客户端提前断开、代理丢包或生成被取消，可能没有拿到最终 usage。这时应记录 usage_status: "missing" 或类似状态，而不是把缺失用量默认为零。

供应商控制台、计费账单、请求级 usage 和本地 Token 估算属于不同数据口径。实际费用以对应合同和供应商账单为最终依据；内部估算适用于日常对比与预算预警。

9. 模型调用成本计算与账单核对

9.1 基本计费公式

假设价格按每百万 Token 报价，且缓存输入有独立费率：

[ C_{\text{tokens}} = \frac{(N_{in}-N_{cache})P_{in} + N_{cache}P_{cache} + N_{out}P_{out}}{10^6} ]

其中：

  • N_in：输入 Token 总数；
  • N_cache：已包含在总输入中的缓存命中 Token；
  • N_out：输出 Token 总数，按该供应商的实际计费口径；
  • P_in、P_cache、P_out：对应每百万 Token 费率。

若还有缓存写入、搜索、浏览器、文件、音频、推理服务附加费、区域服务费或其他计费项，应按供应商的具体定价规则增加对应项，而不是强行塞入上述三项公式。

9.2 示例：使用虚构价格计算一次请求

下列价格仅用于演示计算逻辑，不是任何厂商的实时价格。

text
输入总数：500 tokens
其中缓存命中：200 tokens
输出总数：140 tokens（已包含 40 reasoning tokens）

每百万普通输入：$0.80
每百万缓存输入：$0.08
每百万输出：$3.20

成本 = (300 × 0.80 + 200 × 0.08 + 140 × 3.20) / 1,000,000
     = 0.000704 USD

正确逻辑是将缓存命中部分从普通输入中扣除。上述 140 已包含 40 推理 Token，因此不能再加 40 × 输出费率。

9.3 为什么要给价格表加版本

模型价格会调整，合同可能有折扣，服务等级和长上下文档位也可能改变费率。建议维护配置：

json
{
  "provider": "demo-provider",
  "model": "demo-model",
  "effective_date": "2026-11-11",
  "currency": "USD",
  "billing_unit": 1000000,
  "uncached_input_rate": "0.80",
  "cached_input_rate": "0.08",
  "output_rate": "3.20",
  "note": "仅为教学示例价格"
}

成本记录既要保存当时使用的费率版本，也应允许之后根据真实账单进行对账和修正。估算成本不是已结算费用。

9.4 成本指标不能只有“每次调用多少钱”

  • 单次 API 调用成本；
  • 单个用户请求的全链路成本（含多次模型调用）；
  • 单个后台任务成本（含重试和工具）；
  • 每次成功任务的平均成本；
  • 处理 1,000 次实际业务请求的总成本；
  • 错误重试成本与缓存命中收益。

设某版本总成本为 C，成功处理的任务数为 S：

[ \text{Cost per Success} = \frac{C}{S},\quad S>0 ]

成功率提高后，单次调用更贵不代表整个方案一定不划算；反过来，调用变便宜但成功率大幅下降也不一定是改进。

10. 延迟、吞吐量和请求生命周期测量

10.1 不要将“模型耗时”与“整个请求耗时”混为一谈

一次 AI 请求常经历：

text
接入请求
  ├── 认证与参数校验
  ├── 知识检索／数据库查询
  ├── 等待并发槽位
  ├── 发出模型请求
  │      ├── 网络连接与排队
  │      ├── 服务端计算
  │      └── 流式文本增量
  ├── 工具调用／再次模型调用
  ├── 输出校验与事实核对
  └── 持久化、返回最终结果

因此应记录不同层级：

指标 含义 解释
请求总耗时 前端/服务端从开始到结束 体现完整用户体验
模型调用耗时 单次 API 调用开始至完成 体现模型及网络路径的综合耗时
首字延迟 TTFT 发送调用到收到首个有意义文本增量 主要用于流式用户体验
工具耗时 检索、SQL、外部工具调用阶段 找到非模型瓶颈
排队时长 等候 Semaphore、队列和限流配额 区分容量不足与推理慢
p50 / p95 / p99 延迟分布分位数 识别尾部慢请求
吞吐量 单位时间处理请求数或 Token 数 衡量系统处理能力

首个 HTTP 字节、首个 SSE 事件、首个文本 Token 可能是三个不同时间点。工具事件或心跳事件先到达时，不能假装“用户已经看到答案”。

10.2 perf_counter() 与系统时钟的区别

datetime.now(timezone.utc) 可记录时间戳、用于跨记录定位；time.perf_counter() 适合测量本进程内的经过时长。墙上时钟可能因时间同步和手动修改而跳变，不能用两次普通日历时钟的差值替代精确的本地性能测量。

python
from datetime import datetime, timezone
from time import perf_counter

started_at = datetime.now(timezone.utc).isoformat()
start = perf_counter()
# 执行一次请求
elapsed_ms = (perf_counter() - start) * 1000

跨服务器或跨进程测量的时间关系，需要分布式追踪、可靠的时间戳以及对时钟偏差的理解。不同节点上独立 perf_counter() 读数不可直接相减。

10.3 分位数比单一平均值更能显示尾延迟

假设 100 个请求里 95 个在 1 秒完成，5 个在 30 秒完成：平均值无法充分展示尾部体验。p95 可以辅助观察慢请求，但必须记录样本数量、测量窗口和分位数算法；对非常小的数据集，p95 的解释力有限。

单独优化延迟时也不能忽略质量：将输出截断或跳过事实核验可能使响应更快，却让系统变得不可靠。

11. 一次改动的 A/B 配对评测方法

11.1 一次满意的回答为什么不够

生成式模型可能在相同输入下产生不同结果。单次正确只代表一个观察值，无法说明总体质量分布，也无法证明修改没有让其他问题退步。

应先建立固定评测集：

json
{"case_id":"c001","question":"角色 A 的基础生命值？","version":"1.2","expected_hp":4,"category":"fact"}
{"case_id":"c002","question":"计算折扣后金额","expected_total":"54.03","category":"calculation"}
{"case_id":"c003","question":"未知版本的规则是什么？","expected_behavior":"ask_version","category":"clarification"}

这里只展示三种类别。真实评测集还应包含容易出错的边界条件、多轮上下文、版本冲突、无答案、错误输入和引用无效等场景。

11.2 配对实验（Paired Comparison）

相同的 case_id 分别交给修改前版本 A 与修改后版本 B。只有这样才能对照同一问题的改进与退步：

案例 A 结果 B 结果 归类
c001 错误 正确 改进
c002 正确 正确 持平
c003 正确 错误 回归退步
c004 错误 错误 持平（都失败）

总体准确率提升并不代表所有案例均改善。 特别是安全、权限、账单、事实性等关键案例，单个严重退步就可能不符合发布条件。

11.3 质量指标应绑定任务

问答场景可使用：

  • 答案正确率：按预先定义的可核查标准判断；
  • 引用支持率：断言能否被对应来源实际支持；
  • 版本匹配率：是否使用了正确版本；
  • 拒绝编造率：证据不足时是否正确说明；
  • 结构校验通过率：JSON / Schema 是否满足契约；
  • 工具选择正确率：模型是否使用适当工具；
  • 业务任务成功率：用户问题是否真正解决。

评测员模型可以辅助评分，但应定期与人工标注的标准答案核对一致性。评价标准本身发生变化时，需要记录评分器版本，否则不能直接比较前后结果。

11.4 多次重复与抽样偏差

为了观察随机性，可以在同一固定样例上分别运行多个独立重复，并记录各次运行。还应避免数据集只包含容易样例：应包含典型任务、长输入、冲突、边界、失败和高风险案例。

如果重复次数不足、样本规模过小或数据分布与真实用户不同，最多只能得到“在该样本上的观察结果”，不能断言生产总体一定提升。

11.5 统计比较的简单表达

设数据集包含 N 个唯一案例，版本 A 成功数为 S_A，版本 B 成功数为 S_B：

[ Acc_A = S_A/N,\qquad Acc_B = S_B/N ]

[ \Delta Acc_{pp} = 100(Acc_B - Acc_A) ]

这里 pp 表示百分点，不是“相对提升百分比”。如正确率从 80% 增加到 90%，提升为 10 个百分点，相对提升为 12.5%。

可进一步记录配对改进数 n_improve 与退步数 n_regress，必要时使用适合成对二分类数据的统计方法（如 McNemar 检验）或置信区间分析，而不是只报告一个准确率数字。

12. 质量、耗时、成本和风险的综合决策

12.1 一个模拟的 20 条样例比较

假设两版模型在同一组测试中的结果如下（全部为示例数据）：

指标 修改前 A 修改后 B 变化
正确样例数 16 / 20 18 / 20 +2
正确率 80% 90% +10 个百分点
20 条样例合计成本 $0.08 $0.12 +$0.04
每个成功案例平均成本 $0.005 约 $0.00667 上升
p95 延迟 3.0 秒 4.4 秒 变慢
关键引用错误 1 0 改善

可以看到，B 的质量更高，但也更慢、更贵。不能只靠其中一个指标判定 B 必然更好。

在演示数据下，每新增一个成功案例对应的整个测试集增量支出是 $0.04 / 2 = $0.02。这是针对这一测试集的描述性比值，并不自动等于生产中的真实边际成本或商业收益。

12.2 有约束的优化更符合生产要求

一种产品策略是：

  • 正确率达到最低门槛；
  • 关键事实和权限错误为零或低于明确容忍标准；
  • p95 延迟满足服务级目标；
  • 单请求预期成本不超过预算；
  • 在全部约束均满足的候选方案中，选择质量更高或成本更低的一版。

形式化表达为：

[ \max Q(x) \quad \text{subject to}\quad L_{95}(x) \le L_{max},\ C(x) \le C_{max},\ R(x) \le R_{max} ]

其中 Q 表示质量，L95 为 p95 延迟，C 为成本，R 为风险指标。具体权重和阈值取决于产品目标，不能由通用公式直接决定。

12.3 修改收益并非只看模型能力

收益可能包括减少人工审核时间、缩短用户等待、降低外部工具调用次数、提高任务完成率以及减少事故修复支出。反之，成本也不止模型账单，还可能包括服务器、存储、向量检索、日志、人工标注、维护和安全审计成本。

因此成熟的评估需要区分：模型层成本、工作流层成本、用户任务层效果、产品业务层收益。

13. 日志结构、可观测性和敏感数据保护

13.1 为什么需要统一结构化记录

普通文本日志如“模型调用成功”很难进行大规模统计。结构化日志让程序能按 model、prompt_version、case_id、错误类型和时间聚合。一个简化 JSON 记录如下：

json
{
  "request_id": "示例请求 ID",
  "trace_id": "示例追踪 ID",
  "timestamp_utc": "2026-11-11T08:00:00+00:00",
  "provider": "demo-provider",
  "requested_model": "demo-model",
  "actual_model": "demo-model",
  "prompt_version": "rules-v2",
  "prompt_template_sha256": "sha256-值",
  "dataset_version": "evalset-v3",
  "source_versions": ["rules-v1.2"],
  "latency_ms": 1530.5,
  "ttft_ms": 410.2,
  "usage": {
    "input_tokens": 500,
    "cached_input_tokens": 200,
    "output_tokens": 140,
    "reasoning_output_tokens": 40
  },
  "estimated_cost_usd": "0.000704",
  "rate_card_version": "demo-2026-11-11",

需要注意 JSON 内的 sha256-值 只是说明字段含义的占位符；真实程序应输出 SHA-256 的十六进制摘要。上面同样是教学用数据，而非真实 API 日志。

13.2 Traces、Metrics 与 Logs 各自的作用

  • Trace（追踪）：展示一次业务请求穿过路由、数据库、工具、模型等步骤的调用链与耗时；
  • Metric（指标）：聚合成功率、耗时分布、Token 消耗、队列深度等数值；
  • Log（日志）：提供某次调用的具体事件和错误信息。

OpenTelemetry 允许通过 Span 表达父子调用关系，并将关键字段附加在 Span 属性中。记录时应控制属性的数量和敏感程度，例如通常记录模型 ID、提示词版本、用量，而不默认记录完整的个人对话内容。

python
# 可选示例：需要安装 opentelemetry-api 和 opentelemetry-sdk
from opentelemetry import trace

tracer = trace.get_tracer("llm-service")

with tracer.start_as_current_span("model.request") as span:
    span.set_attribute("app.prompt_version", "rules-v2")
    span.set_attribute("app.model_id", "demo-model")
    # 调用模型并记录结果；具体字段遵循项目约定和可用的标准语义约定

注意：仅安装 API 或获取 Tracer 不一定意味着数据已经被持久导出；实际应用还需配置 SDK、Processor、Exporter、采样与后端存储。GenAI 的 OpenTelemetry 语义约定也会演进，应依照项目锁定版本配置。

13.3 敏感信息保护是设计要求，不是上线后的补救

完整 Prompt、外部检索文档、工具结果、用户聊天、API Key、身份证明、财务信息可能包含敏感内容。默认将这些原文全部写进日志，会扩大数据暴露面。实践中应：

  • 默认仅记录必要元数据；
  • 优先存 case_id、资料版本、Prompt 哈希而非敏感原文；
  • 对确需复现的输入使用授权、脱敏、加密存储和短期保留；
  • 记录访问审计、配置保留期限及删除策略；
  • 错误堆栈和 HTTP Header 中不得泄漏密钥；
  • 不将个人信息无条件上传第三方可观测性平台。

OpenTelemetry 官方安全指南明确强调数据最小化，必要时通过 Collector 处理器过滤、删除或修改敏感属性。

14. 超时、失败、流式中断时如何记录

14.1 失败本身也是观测结果

假设模型调用超时，有时可能没有最终的 Token 统计。如果把用量写成 0，就会错误地表达“确定没有任何 Token 消耗”。更合理的形式是：

json
{
  "status": "timeout",
  "error_code": "MODEL_READ_TIMEOUT",
  "latency_ms": 30005,
  "usage": null,
  "usage_status": "missing",
  "estimated_cost_usd": null,
  "billing_reconciliation_required": true
}

这里 null 的含义是“未知/缺失”，不是零。真实计费可能与客户端拿到的部分响应不同。

14.2 不同失败阶段的记录重点

失败阶段 记录重点 不应该假设的事
输入校验失败 输入错误类型、请求 ID 模型一定已经调用
排队超时 等待时长、并发队列 模型已经接收请求
网络连接失败 连接类型、网络错误、重试次数 供应商未计费
模型执行超时 已观测耗时、取消状态、可用 usage 远端生成已终止
流式中断 已收到的文本片段、最后事件、缺失最终状态 已经正常完成
Schema 校验失败 字段错误、实际结束状态 生成输出可用于业务
事实校验失败 断言、资料 ID、资料版本、核验结论 引用存在即代表事实成立
写库失败 事务状态、幂等键、重试计划 外部工具操作也被回滚

14.3 重试成本应该按实际尝试汇总

重试 3 次后成功的业务任务，其实际成本可能包括前面 2 次的模型费用、第三次的费用与工具开销。日志设计应保留 attempt_id、attempt_number、父任务 ID，避免只记录最终成功调用。

同一业务任务的重试应具备幂等边界；不过模型生成、搜索和外部调用的成本并不因业务幂等而自动免除。

15. 端到端案例：规则问答与确定性计算

以下以虚构的游戏角色规则为例，串联这一节各知识领域。

用户提问：“在 v1.2 中，角色 A 的基础生命值是多少？如果 3 件道具每件 19.99、打 85 折、再加 6% 税，最终金额是多少？”

业务系统可按以下过程执行：

  1. 意图识别：模型或传统路由器识别出“规则事实查询 + 金额计算”两个任务。
  2. 资料查询：按角色 ID 和规则版本 v1.2 读取结构化数值，得到 base_hp = 4，并保留规则来源。
  3. 输入校验：校验金额字符串、数量整数、折扣率、税率和币种。
  4. 确定性运算：Python Decimal 按约定顺序计算最终金额 54.03。
  5. 模型说明：模型根据已确认的事实与数值生成自然语言答复，并附来源；结果数值不允许擅自替换。
  6. 输出核验：检查模型展示的生命值和金额是否与可信数据一致，并核对引用是否指向正确版本。
  7. 观测记录：保存请求 ID、模型和提示词版本、数据版本、用量、耗时、状态与估算费用。
  8. 实验比较：版本 B 修改 Prompt 或选择不同模型后，使用相同输入与同一数据版本比较 A、B 的正确率、引用质量、p95 延迟和任务成本。

关键的工程分界是：事实被查询且验证，数值被执行且验证，语言由模型生成但不能绕过前两者的结果约束。

15.1 一个合理的分层接口

    unit = Decimal(unit_price)
    discount = Decimal(discount_rate)
    tax = Decimal(tax_rate)
    if unit < 0 or quantity < 0 or not (0 <= discount <= 1) or tax < 0:
        raise ValueError("Invalid order inputs")
    after_discount = money(unit * quantity * (Decimal(1) - discount))
    return after_discount + money(after_discount * tax)


@dataclass(frozen=True)
class AuthoritativeFact:
    source_id: str
    version: str
    value: int
    excerpt: str


def check_fact(claimed_value: int, fact: AuthoritativeFact) -> bool:
    """Structured authoritative-data consistency; not a general semantic citation verifier."""
    return type(claimed_value) is int and claimed_value == fact.value


@dataclass(frozen=True)
class Usage:
    input_tokens: int
    output_tokens: int
    cached_input_tokens: int = 0
    reasoning_output_tokens: int = 0

    def __post_init__(self) -> None:
        if (self.input_tokens < 0 or self.output_tokens < 0 or
                self.cached_input_tokens < 0 or self.reasoning_output_tokens < 0 or
                self.cached_input_tokens > self.input_tokens or
                self.reasoning_output_tokens > self.output_tokens):
            raise ValueError("Inconsistent usage counters")


@dataclass(frozen=True)
class RateCard:
    # Example rates ONLY, NOT any provider's live prices.
    model_id: str
    effective_date: str
    input_per_million: Decimal
    cached_input_per_million: Decimal
    output_per_million: Decimal
    currency: str = "USD"


def estimate_cost(usage: Usage | None, rates: RateCard) -> Decimal | None:
    """Cached input is INCLUDED in input_tokens; reasoning in output_tokens."""
    if usage is None:
        return None
    non_cached = usage.input_tokens - usage.cached_input_tokens
    return (
        Decimal(non_cached) * rates.input_per_million
        + Decimal(usage.cached_input_tokens) * rates.cached_input_per_million
        + Decimal(usage.output_tokens) * rates.output_per_million
    ) / MILLION


def prompt_hash(template: str) -> str:
    return sha256(template.encode("utf-8")).hexdigest()


class FakeModel:
    """Deterministic stand-in, intentionally NOT a real LLM API client."""
    def generate(self, _: str) -> tuple[dict[str, Any], Usage]:
        sleep(0.002)
        return (
            {"answer": "角色 A 的基础生命值为 4", "hp": 4, "source_id": "rules/hero-a"},
            Usage(input_tokens=500, output_tokens=140, cached_input_tokens=200,
                  reasoning_output_tokens=40),
        )


def run_example(output_path: Path) -> dict[str, Any]:
    template = "仅依据给定版本的规则回答问题，并提供来源 ID。"
    fact = AuthoritativeFact("rules/hero-a", "v1.2", 4, "角色 A：基础生命值 4。")
    rates = RateCard("demo-model", "2026-11-11", Decimal("0.80"),
                     Decimal("0.08"), Decimal("3.20"))
    start = perf_counter()
    started_at = datetime.now(timezone.utc).isoformat()
    status = "error"
    error_code = None
    usage: Usage | None = None
    try:
        response, usage = FakeModel().generate(template)
        if response["source_id"] != fact.source_id or not check_fact(response["hp"], fact):
            raise ValueError("Unsupported claim")
        status = "success"
    except (KeyError, ValueError, TypeError) as exc:
        error_code = type(exc).__name__
    elapsed_ms = (perf_counter() - start) * 1000
    record = {
        "request_id": str(uuid.uuid4()),
        "started_at_utc": started_at,
        "provider": "demo",
        "requested_model": "demo-model",
        "actual_model": "demo-model",
        "prompt_version": "rules-answer-v2",
        "prompt_template_sha256": prompt_hash(template),
        "dataset_version": "testset-v1",
        "source_versions": {fact.source_id: fact.version},
        "latency_ms": round(elapsed_ms, 3),
        "usage": asdict(usage) if usage is not None else None,
        "estimated_cost_usd": str(estimate_cost(usage, rates)) if usage is not None else None,
        "rate_card_effective_date": rates.effective_date,
        "status": status,
        "error_code": error_code,
    }
    output_path.parent.mkdir(parents=True, exist_ok=True)
    with output_path.open("a", encoding="utf-8") as stream:
        stream.write(json.dumps(record, ensure_ascii=False) + "\n")
    return record


@dataclass(frozen=True)
class EvalRow:
    case_id: str
    passed: bool
    latency_ms: float
    cost_usd: Decimal


def summarize(rows: list[EvalRow]) -> dict[str, Any]:
    if not rows:
        raise ValueError("Need evaluation rows")
    latencies = sorted(row.latency_ms for row in rows)
    p95_index = max(0, (95 * len(latencies) + 99) // 100 - 1)  # nearest-rank
    return {
        "n": len(rows),
        "success_rate": sum(row.passed for row in rows) / len(rows),
        "p50_ms": median(latencies),
        "p95_ms": latencies[p95_index],
        "total_cost_usd": sum((row.cost_usd for row in rows), Decimal(0)),
    }


def paired_compare(before: list[EvalRow], after: list[EvalRow]) -> dict[str, Any]:
    a = {r.case_id: r for r in before}
    b = {r.case_id: r for r in after}
    if len(a) != len(before) or len(b) != len(after) or a.keys() != b.keys():
        raise ValueError("Case IDs must be unique and identical for paired comparison")
    wins = sum(not a[k].passed and b[k].passed for k in a)
    regressions = sum(a[k].passed and not b[k].passed for k in a)
    a_summary, b_summary = summarize(before), summarize(after)
    return {
        "before": a_summary,
        "after": b_summary,
        "improved_cases": wins,
        "regressed_cases": regressions,
        "success_rate_delta_pp": 100 * (b_summary["success_rate"] - a_summary["success_rate"]),
        "cost_delta_usd": b_summary["total_cost_usd"] - a_summary["total_cost_usd"],
    }

16.3 如何替换成真实模型 API

将 FakeModel.generate() 替换为实际 SDK 调用后，应：

  • 将供应商返回字段映射到统一 Usage 类型，保留原始 provider usage 以便对账；
  • 从真实响应读取模型 ID、结束原因与可用的后端指纹；
  • 在 try/finally 中完整记录成功、异常、超时和取消；
  • 对无法取得最终用量的请求记录 usage_status="missing"；
  • 使用真实知识数据源进行版本与引用校验；
  • 用实际有效的费率表记录估算费用；
  • 让多次模型调用聚合到父业务请求，而不是只记录最后一次。

不要把模拟的成功次数当作真实模型效果评测。 真实评测需要运行实际模型并保存每条案例的输出、评定依据和对照结果。

17. 常见误区与边界条件

误区 1：“模型会推理，所以可以代替金额计算器。”

推理能力和程序执行的确定性不是同一回事。重要数字要经过可验证的规则和代码计算。

误区 2：“模型给出了来源链接，事实就一定正确。”

引用只是定位线索。事实必须核实来源内容、版本、适用范围和支持关系。

误区 3：“temperature=0 可以保证任何一次输出都完全相同。”

低温可以减少某些随机性，但不能保证所有模型、服务路由、硬件与 API 版本下都逐字确定。

误区 4：“记录模型名和 Prompt 就可以百分百复现。”

还需要考虑实际检索资料、工具返回、配置、模型后端版本、外部系统时间和潜在非确定性。

误区 5：“模型输出的 reasoning_tokens 应加到 output_tokens 上。”

对于将推理 Token 作为输出明细子项的 API，这是重复计数。必须先确认供应商口径。

误区 6：“cached_tokens 是输入总量之外的新 Token。”

在常见的 OpenAI/DeepSeek 用量结构中，缓存输入包含在输入 Token 总量内；成本计算时应拆分价格，不应重复加总。

误区 7：“没有拿到 usage 就代表没有费用。”

流式中断、网络超时或工具故障可能导致客户端缺失统计。未知应记为未知，按账单对账。

误区 8：“模型平均响应更快，所以用户体验一定更好。”

慢请求尾部、首字延迟、失败率、输出质量和排队延迟都可能改变用户体验。

误区 9：“新 Prompt 在一次问题上更好，说明整体提升。”

必须在相同评测集上比较，并关注回归案例。关键任务的单项严重退步可能高于总体提升价值。

误区 10：“只存模型请求内容才能查问题。”

元数据、请求 ID、提示词版本、资料版本、结构化错误和安全的可复现样本往往足以定位许多问题。完整原文日志应经过必要性、安全和权限评估。

18.2 术语速查

术语 含义
Deterministic Computation 给定同样输入与规则，计算得到可重复结果的程序化过程
Provenance 数据或结论从哪里来、经过怎样处理的来源链
Ground Truth 经过定义和核验的评测参考事实或标准答案
Prompt Version 提示词模板及相关行为规则的版本
Fingerprint 提示词、资料或供应商后端状态的特征标识；不等同严格复现保证
Usage 模型调用资源消耗统计，主要包括各类 Token 和工具使用
TTFT Time To First Token，首个有意义文本增量的延迟，具体测量口径应注明
p95 在给定分位数定义下，约 95% 样本不超过的统计位置
Pairwise Evaluation 使用同一案例成对比较两个模型或提示词版本
Regression 改动后此前正确的案例变成错误或质量退步
Cost per Success 总资源花费除以成功业务任务数
Telemetry 用于观测系统行为的追踪、指标和日志数据

本节结论：可靠的 AI 应用不能只有“生成回答”。它必须能够证明重要数字来自确定性计算，重要事实来自可追踪的资料，并对每次模型调用保留足以解释质量、延迟和成本变化的元数据。只有使用相同测试集并同时衡量正确率、风险、耗时与费用，才能判断一次修改是否真正有益。
