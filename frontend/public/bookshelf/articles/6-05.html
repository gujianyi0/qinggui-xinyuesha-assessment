消息队列与后台任务可靠性（五）：同分区并发处理、连续完成水位与安全 Offset 提交

知识范围：Apache Kafka 消费组、aiokafka 手动提交、异步 Worker、故障恢复、数据库幂等。
示例环境：Python 3.13；教学代码仅使用 Python 标准库和 SQLite；Kafka 客户端代码展示集成模式，未进行真实 Broker 验证。

1. 一句话理解问题

Kafka 一个分区内的日志是按 Offset 排列的，但一个 Worker 可以把同一分区的多条消息交给多个协程同时处理。此时消息的读取顺序、完成顺序、提交顺序是不同的：

  • 读取顺序：通常是分区日志顺序，例如 100、101、102。
  • 完成顺序：可能是 102、100、101，因为各消息耗时不同。
  • 提交进度：必须保守地表示“该 Offset 之前需要处理的消息已经得到可持久化的处理结论”，不能直接取“已完成的最大 Offset + 1”。

核心不变量：任何一个提交给 Kafka 的下一消费位置 C，都不能越过当前仍需恢复、且尚未持久化完成的已消费消息。

Kafka 记录的 committed offset 是重启后下一条要读取的位置，不是“最近成功执行的消息编号”。在常规手动提交模式下，提交 103 表示从 103 开始恢复，默认不再从 100、101、102 恢复。参见 aiokafka Consumer 文档 和 Kafka 4.4 Consumer API。

2. 为什么分区有序，处理结果仍可能乱序

单个 Kafka Partition 的记录具有日志顺序，但异步消费者经常使用以下结构：

text
Partition P0
  offset=100  ──────┐  模型调用耗时 2 秒 ─────────────→ 完成时刻 T=2.0
  offset=101  ──────┼  模型调用耗时 8 秒 ───────────────────────→ 完成时刻 T=8.0
  offset=102  ──────┘  缓存命中耗时 0.2 秒 ──→ 完成时刻 T=0.2

消费者可以按 100 → 101 → 102 取出记录，并使用 asyncio.create_task(...) 调度并发处理。然而 asyncio 不保证执行完成顺序等于创建 Task 的顺序。有序消费不代表有序完成，更不代表有序提交。

在批量 Embedding、外部模型 API、文档解析等 I/O 耗时不一致的业务中，这种乱序很常见。

3. 一个会导致漏处理的具体时间线

假设该 Consumer Group 当前已提交 Offset 为 100，分区内有三条待处理记录。

时间 Offset 100 Offset 101 Offset 102 错误操作
T0 处理中 处理中 处理中 无
T1 处理中 处理中 成功 按最大完成号提交 103
T2 处理中 处理中 已完成 进程崩溃
T3 — 未完成且未恢复 — 重启后从 103 读取

T1 的错误提交等价于“宣布 100、101、102 都可以跳过”。但事实上只有 102 完成。Kafka 只保存一条线性提交位置，通常不会替应用记住“101 未完成、102 已完成”。

结果：Offset 101 对应的业务可能被永久跳过。 如果消息仍留在 Kafka，仍可以通过人工调整 Offset 补救；但系统不会自动发现这个遗漏，且消息保留期与补偿条件可能使修复变困难。

3.1 错误实现

python
# 错误：仅看本次完成的最高 offset
latest_done = max(completed_offsets)       # 例如 102
await consumer.commit({tp: latest_done + 1})  # 提交 103：越过了未完成的 101

另一个常见错误是：

python
# 错误：fetch 已经推进到 103，但业务任务可能还没完成
next_position = await consumer.position(tp)
await consumer.commit({tp: next_position})

position() 表示消费者读取位置，不能作为业务完成证明。

4. 正确原则：按“已处理前缀”推进水位

解决办法是为每个 TopicPartition维护独立的消息处理状态，按读取顺序记录消息，然后只推进到“前面的消息均已完成”的位置。这一位置称为：

  • 安全提交水位（safe commit frontier）
  • 连续完成水位（contiguous completion watermark）
  • Highest committable offset

其中“连续”指按本消费者实际交付的记录序列，前面的待处理项没有空洞，不是强制 Kafka Offset 数值每次都相差 1。

例如：

记录 处理状态 是否允许提交到该记录之后
100 成功 是：可以提交 101
101 处理中 否
102 成功 否：不能单独提交 103
103 成功 否：仍被 101 阻挡

当 101 随后成功时，如果 102、103 已经持久化成功，水位可以一次前进到 104。

4.1 操作时序

text
初始 committed=100
   ↓
读取 100、101、102
   ↓
102 成功        → safe_next=100（不能推进）
   ↓
100 成功        → safe_next=101（可提交 101）
   ↓
101 成功        → safe_next=103（100..102 均完成）
   ↓
Kafka 确认 commit(103)

注意：如果 100 先完成、101 未完成、102 已完成，提交 101 是安全的。重启后 Kafka 将从 101 重新读取；102 可能被重复消费，因此下游业务必须幂等。

5. Kafka 的 Offset 数值可能有空洞

Kafka Offset 单调递增，但在日志压缩、事务可见性等情况下，消费者实际收到的记录可能是：

text
offset=10
（没有交付 offset=11）
offset=12
（没有交付 offset=13、14）
offset=15

因此下面这种实现并不通用：

python
# 不够通用：假设每条消息的 offset 数字都连续
while next_offset in finished_offsets:
    next_offset += 1

它可能永远等待本就不可能收到的物理 Offset。

更稳妥的教学算法维护实际按顺序接收到的记录列表。当这些记录的前缀都完成时，将安全位置设为最后一条完成记录的 offset + 1。此处依赖同一分区的消费端按顺序交付记录，且不能在未处理未知中间记录的情况下擅自跳跃。

例如已收到 [10,12,15]：10 和 12 完成，15 未完成，可以提交 13。15 完成后可以提交 16。由于已经读取到 12，11 没有在该消费视图中作为一条需要处理的可见记录被交付。

Kafka 对事务与压缩等情况的处理应以具体消费隔离级别、日志配置和官方客户端行为为准。不要把 Offset 差值当成实际消息条数。

6. 三种处理策略的取舍

策略 是否允许同分区并发 结果顺序 提交难度 适用情况
同分区串行处理 否 可按消费顺序完成 低 必须逐条按顺序修改业务状态
同分区并发、提交有序 是 结果可能乱序 中 相互独立的文档、图片、模型请求
按消息 Key 顺序并发 不同 Key 可以并行，同 Key 串行 同 Key 有序 较高 订单、用户、同一资料版本的更新

注意：提交顺序有序，不代表业务副作用有序。 如果消息 100 表示“设置余额为 10”，101 表示“设置余额为 20”，即使按安全水位提交，若 101 的数据库写入先于 100，也可能留下错误的余额 10。此类业务需要同 Key 串行执行、数据库版本检查或事件序列控制，不能仅靠提交水位解决。

7. 核心数据结构与算法

在一个分区里维护四类状态：

  1. safe_next_offset：从已收到且已持久化完成的消息前缀计算出的安全提交目标。
  2. acknowledged_offset：Kafka 已确认保存的 Offset（教学代码中的本地镜像）。
  3. ordered：按该分区读取顺序登记、尚未越过水位的消息记录。
  4. done：某条消息对应的业务结果已经完成持久化，而不是“协程不再运行”。

简化伪代码：

python
on_message(msg):
    partition_state.register(msg.offset)
    schedule_async_business_task(msg)

on_business_durably_finished(msg):
    partition_state.mark_done(msg.offset)

    # 从队头开始，只弹出已完成的前缀
    while first_registered_message_is_done():
        completed = remove_first_registered_message()
        safe_next_offset = completed.offset + 1

    if safe_next_offset > last_confirmed_commit:
        serialize_commit(safe_next_offset)

关键条件： 必须在数据库事务提交成功、幂等重放被确认已完成，或失败消息已被可靠地转入可追踪的终态之后，才能把消息标为 done。单纯捕获异常、打印日志，或者把消息交给一个尚未确认持久化的队列，不能算完成。

8. 安全提交和数据库事务之间的边界

以下阶段不能混为一谈：

text
Kafka 消息交付
      ↓
异步业务处理
      ↓
数据库事务执行
      ↓
COMMIT 成功
      ↓
标记该记录 done
      ↓
推进安全前缀
      ↓
Kafka commit(offset)
      ↓
Broker 确认
  • 若数据库事务尚未成功，不能认定 done。
  • 若数据库成功、Kafka Commit 失败，消息可能重投，因此业务结果要有幂等键、唯一约束或等效的重复识别机制。
  • 若 Kafka Commit 被错误推进到未完成记录之后，数据库幂等机制无法让这条尚未执行过的业务凭空补回来。
  • Kafka Commit 失败不应推进本地 acknowledged_offset；可以保留安全候选值并之后重试提交，但不能把未确认提交当成已持久化进度。

8.1 业务结果重复与顺序控制是不同目标

UNIQUE(event_id) 允许重复消费后不重复创建结果，但它不能阻止用户 101 的更新先于 100 执行。对于有序业务，可能需要 (resource_id, event_version) 的条件更新规则、数据库锁或同 Key 串行处理。

9. 有一个更难的场景：前面的消息失败，后面的都成功

假设 100 因模型服务持续失败，101–130 已处理完毕：

text
100 FAIL/RETRYING
101 DONE
102 DONE
...
130 DONE

安全提交水位依然不能越过 100。否则重启后 100 被跳过。

有三种常见策略：

  1. 重试并阻塞推进：保留 100，按有限次数和退避重试；适合确实必须成功的任务。
  2. 可靠失败终态 / DLQ：将 100 的失败原因和必要上下文持久化，确认死信记录已可靠保存，再将它视为“已经得到最终处理结论”。适合允许单条任务失败但不阻断整体吞吐的场景。
  3. 暂停或重新分配该分区：在故障或资源不足时，不再继续接收该分区的新工作，控制内存积压。

不能为了让 Offset 前进而简单把失败记录标成成功。业务侧应区分 SUCCEEDED、FAILED、RETRYING、CANCELLED 等状态。

10. Head-of-Line Blocking 与内存压力

当最早未完成消息很慢时，后面完成的结果无法推进提交位置，这称为提交层面的 Head-of-Line Blocking（队头阻塞）。

它可能造成：

  • 持续积累在途任务、内存、工具连接和缓存结果；
  • Broker committed offset 长时间不前进，消费组 Lag 看上去很大；
  • 发生重启时大量已成功但尚未提交进度的消息重新投递；
  • 重复处理费用上升，甚至再次对外部模型收费。

典型缓解：

  • 为每个分区设置最大 in_flight 数；
  • 根据未完成队列长度 pause(tp) / resume(tp)；
  • 缩小获取批量 max_records；
  • 对模型请求设置有限超时与业务幂等；
  • 在允许的情况下使用 Key 顺序并发、分区扩展或独立任务队列；
  • 对长期失败的记录实施可审计的终态处理。

注意：pause() 通常暂停后续获取，并不会自动取消已经投递给业务的任务。需要显式追踪、回收在途任务。

11. Consumer Group Rebalance 时必须重新确认所有权

当 Consumer Group 发生重新平衡，某个分区可能从 Worker A 转移到 Worker B。此时，A 内部还可能有尚未完成的协程。

如果旧 Worker 在分区已撤销后仍提交 Offset，或把结果覆盖到新 Worker 的业务状态，就可能造成进度、结果和权限问题。推荐处理顺序：

  1. 收到分区撤销信号后，不再为撤销分区创建新的业务任务。
  2. 尽量在允许的关闭时间内等待该分区在途任务完成。
  3. 对已经真正持久化完成的前缀尝试最后一次安全提交。
  4. 停止、取消或失效该分区的旧异步任务，清理本地分区状态。
  5. 新 Worker 从其被分配后的 committed offset 恢复，并使用幂等约束处理可能的重投。

aiokafka 文档明确建议手动提交的批处理消费者配合 ConsumerRebalanceListener，处理撤销前的在途数据；分区重新分配期间提交也可能失败。见 aiokafka Consumer 文档。

对于 数据库已经被旧 Worker 修改的问题，还可能需要租约代际或 Fencing Token、条件更新等机制；仅靠消费者提交前判断分区归属，不足以撤销已经发生的外部副作用。

12. 优雅停机与强制终止

正常关闭时：

text
停止接收新消息
  → 暂停/限制新任务入队
  → 等待在途任务在截止时间前完成
  → 保存成功结果和失败终态
  → 按分区提交安全水位
  → 关闭 Consumer、HTTP 客户端、数据库池

若 Worker 收到 SIGKILL、进程崩溃或机器断电，以上步骤可能无法执行。因此不能把优雅停机当作唯一的可靠性机制。必须预期：已完成数据库写入却没有提交 Kafka Offset、未完成任务被重新交付，以及已处理消息的重放。

13. aiokafka 的集成思路：批内并发、分区内有序提交

下面代码展示核心编排形态，前提是实现 process_business_durably()：它必须以数据库事务或等效机制完成持久化和幂等保护，且只有成功之后才返回。此示例用于解释 API 与处理边界，未连接真实 Kafka 服务执行，也不是完善的生产级恢复框架。

python
import asyncio
import logging
from aiokafka import AIOKafkaConsumer
from offset_tracker import PartitionCommitTracker

log = logging.getLogger(__name__)

async def process_business_durably(msg):
    """业务层自行实现：数据库事务提交、唯一约束、结果恢复等。"""
    raise NotImplementedError

async def consume():
    consumer = AIOKafkaConsumer(
        "document-tasks",
        bootstrap_servers="localhost:9092",
        group_id="document-workers",
        enable_auto_commit=False,
        auto_offset_reset="earliest",
    )
    trackers = {}
    await consumer.start()
    try:
        while True:
            batches = await consumer.getmany(timeout_ms=500, max_records=24)
            for tp, messages in batches.items():
                if not messages:
                    continue
                if tp not in trackers:
                    # 演示在当前分区最初接收到的消息位置建立局部水位；
                    # 真正系统还需管理分区初次分配、撤销及提交位置。
                    trackers[tp] = PartitionCommitTracker(messages[0].offset)
                tracker = trackers[tp]
                for msg in messages:
                    tracker.register(msg.offset)

                # 只并发执行本批消息，等待本批任务全部给出结果。
                results = await asyncio.gather(
                    *(process_business_durably(msg) for msg in messages),
                    return_exceptions=True,
                )
                failed = False
                for msg, result in zip(messages, results):
                    if isinstance(result, BaseException):
                        failed = True
                        log.error("business failed partition=%s offset=%s error=%r",
                                  tp, msg.offset, result)
                    else:
                        tracker.mark_done(msg.offset)  # 仅成功持久化后

                if tracker.needs_commit():
                    candidate = tracker.safe_next_offset
                    # 同一消费者中的提交操作要保持串行；
                    # 分区撤销后也必须阻止旧 Worker 再发出提交。
                    await consumer.commit({tp: candidate})
                    tracker.commit_success(candidate)

                if failed:
                    # 教学实现故意 fail-fast：停止消费，让未提交的
                    # 消息在故障恢复后重放，而不是积累无界失败空洞。
                    raise RuntimeError("batch failed; restart with idempotent replay")
    finally:
        await consumer.stop()

if __name__ == "__main__":
    asyncio.run(consume())

这段代码的局限需要明确：

  • 未提供真正的 process_business_durably()，不可直接当成完整应用运行；
  • 没有实现 ConsumerRebalanceListener 与分区撤销时的任务处理；
  • 没有持久化或管理跨批次的重试/失败终态，只通过 fail-fast 保守恢复；
  • 一个批次会等待该批全部处理完成，可能造成队头阻塞；
  • 没有完整的背压、运行监控、锁代际和终止信号管理；
  • 在复杂分区切换、Kafka 提交失败和进程中断情形下，需要端到端集成测试验证。

在真实系统中，建议进一步将消费循环、工作调度、完成事件收集、提交协调器与分区生命周期管理拆分为独立模块。

14. 常见实现错误清单

错误 可能造成的结果 正确处理方向
任何 Task 完成就提交其 offset+1 越过更早的未完成任务 按分区维护连续完成前缀
使用 consumer.position() 作为完成水位 读取进度领先于业务持久化 业务完成后独立计算安全水位
以最大成功 Offset 为提交目标 未完成消息被跳过 检查所有更早的已交付消息
只记录成功，不记录失败和重试 消息长期堵塞且不可解释 持久化任务状态、有限重试与失败终态
成功结果只存在内存 崩溃后丢失业务完成证明 数据库事务、持久化业务结果
Kafka Commit 成功才写业务结果 重启可能漏业务 先持久化业务，再提交 Offset
同时有多个未协调的提交协程 后到达的旧提交可能回退位置 单分区串行化提交并验证成功
同分区乱序修改同一资源 状态更新顺序错乱 同 Key 串行或版本条件更新

15. 诊断与指标

建议记录以下字段：topic、partition、offset、consumer_group、run_id、event_id、business_idempotency_key、processing_status、attempt_count、start_time、finished_at、safe_next_offset、committed_offset、assignment_generation、last_error。

核心观测指标：

  • In-flight Count：每分区尚未完成的业务任务数。
  • Completion Gap Count：已经完成但受更早消息阻挡、尚不能推进水位的数量。
  • Commit Frontier Lag：客户端安全水位与最高已完成 Offset 之间的差距（并非 Kafka 标准 Lag）。
  • Kafka Consumer Lag：通常基于 Broker 末端位置与已提交消费进度计算，需要注意日志空洞、事务与管理工具的差异。
  • Commit Failure Count：Kafka 提交失败次数。
  • Replay/Duplicate Count：重启或重平衡后的重复消费次数。
  • Old Owner Rejected Count：旧执行者被拒绝提交或更新的次数。

当某分区 in_flight 增多而 safe_next_offset 长时间不变，应优先查找最早未完成 Offset 的真实错误，而不是盲目提高并发。

16. 故障注入实验矩阵

场景 操作 期望结果
乱序完成 102 → 100 → 101 水位从 100 → 100 → 101 → 103
最早消息失败 101、102 成功，100 失败 不允许提交越过 100
Kafka 提交失败 业务结果已持久化 保留安全候选，Broker 仍使用旧位点；重放幂等
提交前崩溃 100、102 已持久化，101 未完成 重启从旧位点恢复，数据库不重复写入
不同分区 P0 阻塞，P1 成功 P1 独立推进提交水位
日志存在空洞 收到 10、12、15 不要求虚构的 11、13、14 执行
Rebalance A 的分区转交 B A 停止提交；B 重放未提交消息
数据库写入失败 101 事务回滚 101 不能标记 done
失败终态 101 进入持久化 DLQ 确认 DLQ 成功后才可继续推进

17. 可运行的安全水位示例

下面的文件 offset_tracker.py 只实现单分区的内存水位追踪；它不直接与 Kafka 通信。使用者需要在业务持久化完成后调用 mark_done()，并在 Kafka 真正确认 Commit 后调用 commit_success()。源码作为文档的一部分完整列出。

python
"""Pure-Python teaching example: per-partition safe commit frontier.

Only mark_done() AFTER business results have been committed durably.
Does not speak to a Kafka broker; a real consumer must serialize commits.
"""
from __future__ import annotations
from collections import deque
from dataclasses import dataclass


@dataclass
class Entry:
    offset: int
    done: bool = False


class PartitionCommitTracker:
    def __init__(self, start_offset: int) -> None:
        if start_offset < 0:
            raise ValueError("start_offset must be nonnegative")
        self.safe_next_offset = start_offset
        self.acknowledged_offset = start_offset
        self._last_registered = start_offset - 1
        self._ordered: deque[Entry] = deque()
        self._by_offset: dict[int, Entry] = {}

    @property
    def outstanding(self) -> tuple[int, ...]:
        return tuple(entry.offset for entry in self._ordered if not entry.done)

    def register(self, offset: int) -> None:
        if offset < self.safe_next_offset:
            raise ValueError("offset already past safe frontier")
        if offset <= self._last_registered:
            raise ValueError("fetched offsets must be registered in increasing order")
        entry = Entry(offset)
        self._ordered.append(entry)
        self._by_offset[offset] = entry
        self._last_registered = offset

    def mark_done(self, offset: int) -> int:
        """Call after durable business work, or durable DLQ resolution."""
        if offset < self.safe_next_offset:
            # A late duplicate completion after the frontier moved is safe.
            return self.safe_next_offset
        entry = self._by_offset.get(offset)
        if entry is None:
            raise ValueError("unknown offset; cannot claim it succeeded")
        entry.done = True
        while self._ordered and self._ordered[0].done:
            completed = self._ordered.popleft()
            del self._by_offset[completed.offset]
            self.safe_next_offset = completed.offset + 1
        return self.safe_next_offset

    def commit_success(self, submitted_next_offset: int) -> None:
        """Update local ack only after Kafka confirms commit; do not overlap commits."""
        if submitted_next_offset > self.safe_next_offset:
            raise ValueError("attempt to commit beyond durable prefix")
        if submitted_next_offset < self.acknowledged_offset:
            raise ValueError("stale commit acknowledgement")
        self.acknowledged_offset = submitted_next_offset

    def needs_commit(self) -> bool:
        return self.safe_next_offset > self.acknowledged_offset


if __name__ == "__main__":
    tracker = PartitionCommitTracker(10)
    for off in (10, 11, 12):
        tracker.register(off)
    print("done 12 -> next", tracker.mark_done(12))
    print("done 10 -> next", tracker.mark_done(10))
    print("done 11 -> next", tracker.mark_done(11))
    print("safe commit:", tracker.safe_next_offset)

19. 进一步的高级问题：能否越过失败消息但不丢失？

传统 Kafka Consumer Group 只持久记录每个分区的一个线性提交位置。如果想在同一分区高度并发地处理许多消息，又避免重启后重复消费已经完成的后续消息，可能需要额外记录每条消息的完成状态图（completion / offset map），并在恢复时重新构造这些状态。Confluent 的 Parallel Consumer 提供这种思路的实现。

但是：

  • 扩展完成状态图并不会自动保证外部数据库或 API 的 Exactly-once 业务效果；
  • 恢复元数据本身也存在大小、持久化和版本兼容问题；
  • 单分区必须严格按业务顺序执行的场景，仍然不能通过乱序并发来满足业务不变量。

因此，在学习阶段先掌握连续完成水位 + 业务幂等 + 有界并发，是更容易分析和验证的方案。

20. 本节核心结论

  1. 分区日志有序 ≠ 异步执行完成有序。
  2. Kafka Committed Offset 是恢复起点，不是最大已完成消息编号。
  3. 只能提交已经持久化完成的消息前缀之后的位置；后完成的消息不能越过更早的未完成消息。
  4. 前面的消息失败时，可以重试、暂停或可靠地记录失败终态，但不能凭空跳过。
  5. 安全提交水位防止漏处理，业务幂等负责处理必要的重复消费；两者缺一不可。
  6. 同分区按序提交不保证业务副作用按序发生；涉及顺序依赖的资源，应采取同 Key 串行或事务级版本控制。
  7. 重启、Rebalance、提交失败、日志 Offset 空洞和无界积压，都是生产系统必须明确设计的边界。
