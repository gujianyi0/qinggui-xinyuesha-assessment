1. 认证、授权与数据范围的根本区别

1.1 Authentication：你是谁

身份认证的任务是把一次 HTTP 请求与一个可信身份主体（Principal）关联起来。主体可以是用户、服务账户、后台 Worker 或代表某个用户执行的代理。认证一般需要校验凭据，而不是直接读取客户端传入的 user_id。

认证的常见输入包括：登录后颁发的 Access Token、带保护的 Cookie 会话、API Key、服务间工作负载身份。有效凭据仅支持“此请求可归属于哪个主体”这一结论；它不能直接证明该主体拥有任何特定数据的读取权。

1.2 Authorization：你可以做什么

授权判断至少需要四类信息：

  • Subject（主体）：已经认证的用户或服务身份，以及当前角色、所属租户等属性。
  • Action（动作）：读取、创建、修改、删除、导出、发送、调用工具等。
  • Resource（资源）：具体笔记、订单、对话、反馈、工具执行结果等。
  • Context（上下文）：所属组织、所有者、记录状态、时间、任务用途及其他业务条件。

可把授权判定抽象为：

text
allow = Policy(subject, action, resource, context)

策略未允许的操作应默认拒绝（deny by default）。authenticated = True 并不推出 authorized = True。

1.3 数据访问范围（Data Scope）

范围不仅是“接口是否可调用”，更是“接口能够触及哪些记录”。例如，拥有 GET /conversations 权限的普通用户，仅应看到被授权的会话，而不能看到全站所有会话。

三层检查要分别存在：

  1. 功能级：可否执行 list_notes、delete_note？
  2. 对象级：可否访问 note_id=102？
  3. 字段级：可否读取或修改 owner_id、role、is_admin 等字段？

只做第一层而忽略后两层，会造成严重的越权风险。

2. 身份信息如何成为可信上下文

客户端能够控制 URL、请求体、查询参数、绝大多数请求头，甚至能够在自己本地修改前端代码。因此这些内容都只能视为请求数据，而不能自动视为权限依据。

2.1 可信主体的建立

一个典型的 Bearer Token 认证过程：

text
Authorization: Bearer <access_token>
        ↓
检查凭据存在、形式正确
        ↓
验证签名或向可信认证服务校验
        ↓
校验过期时间、签发者、受众、必要声明
        ↓
解析 sub 等稳定身份标识
        ↓
查询用户是否存在、是否停用
        ↓
建立 RequestPrincipal(user_id=...)

对 JWT，特别需要检查：

  • iss：谁签发；
  • aud：令牌供哪一个服务使用；
  • exp：何时失效；
  • iat、nbf：签发与生效时间（按使用的令牌契约验证）；
  • sub：身份主体标识；
  • 签名算法：必须由服务器配置允许列表，而非信任令牌头部要求；
  • 账户状态与撤销策略：签名有效不等于当前账号仍然有权访问。

2.2 为什么不能相信客户端发送的 user_id

以下写法存在越权风险：

python
@app.get('/users/{user_id}/messages')
def list_messages(user_id: int):
    return database.get_messages(user_id=user_id)

如果没有认证与授权，任何人可以把 URL 改成其他用户的 ID。

正确策略是：从服务器认证产生的 principal.user_id 开始，构造受限查询。如果确实是管理员代查，也需要通过独立的管理员授权路径，而不是默认信任传入的 user_id。

2.3 账号停用与权限撤销

JWT 可以在签发后继续有效直至过期，但用户的角色或账号状态可能已经改变。因此：

  • 需要及时撤销的角色、成员资格等，应以当前可信服务端状态为依据；
  • 会话撤销可使用短有效期、令牌版本、撤销记录等机制；
  • 多级缓存会影响权限撤销传播延迟，必须建立可接受的时效策略。

3. Token、JWT、服务端 Session 与 Cookie

3.1 JWT 是一种携带声明的令牌格式

JWT 的常见签名形式为 header.payload.signature。签名不等于加密：普通 JWT 的载荷可以被解码查看，不能把敏感秘密当作安全地存放在签名 JWT 中。

JWT 的优点是服务端可以在符合信任前提时直接验证签名；但撤销、权限变化和密钥轮换需另外设计。

3.2 不透明 Token 与服务端 Session

不透明 Token 本身不暴露业务声明，后端通过数据库、缓存或认证服务查找会话主体。优点包括服务端可以直接失效；代价是增加状态查询或认证服务依赖。

3.3 Cookie 与 Bearer Token 的安全差异

  • Cookie 常用于浏览器登录态；应评估 HttpOnly、Secure、SameSite、CSRF 防护等。
  • Authorization: Bearer 常用于 API；应重视令牌泄漏、前端存储方式、XSS 与 HTTPS。
  • 使用 Bearer Token 不代表没有任何浏览器安全问题；具体风险取决于令牌如何保存和发送。

Access Token、Refresh Token 和 ID Token 的目的不应混用。对外部身份提供方的 OIDC ID Token，不能未经 API 接口受众检查便当作本 API 的 Access Token。

4. 权限模型：RBAC、ABAC、ReBAC

4.1 RBAC：基于角色

定义角色与权限关系，例如：

角色 查看自己的笔记 修改自己的笔记 查看本租户所有笔记 修改其他租户笔记
普通成员 允许 允许 拒绝 拒绝
本租户管理员 允许 允许 允许 拒绝

注意“管理员”通常也需要作用域：租户管理员不等于平台全局管理员。

4.2 ABAC：基于属性

由用户属性、记录属性和环境条件共同决策，例如：

python
allow = (
    actor.active
    and actor.tenant_id == document.tenant_id
    and (actor.id == document.owner_id or actor.role == 'admin')
    and document.status != 'locked'
)

这段只说明判断思想，真实实现还需要避免把客户端提供的 actor.role 当作可信值。

4.3 ReBAC：基于关系

某个用户是否可以访问一份文件，由 user → belongs_to → team → owns → file 等关系决定。适合文档共享、组织协作、项目成员和复杂资源授权。

4.4 多种模型往往同时使用

真实系统通常组合：功能级 RBAC、数据级所有者判断、资源分享关系以及状态约束。单独使用角色名不足以表达所有权限。

5. 对象、功能、字段与租户四种授权维度

5.1 功能级：能否调用这个动作

例如，普通用户可以查看反馈，但不能导出全租户反馈；管理员可能有导出权限。这是功能级授权。

5.2 对象级：能否访问这个具体 ID

例如，用户 A 可以调用 GET /notes/{id}，但只能读取自己拥有或被分享的那条记录。不能用“接口对普通用户开放”推出“所有 note 都可以读取”。

5.3 字段级：能否读取、修改具体字段

一条记录可能包括：

json
{
  "title": "一个反馈",
  "body": "正文",
  "owner_id": 1,
  "tenant_id": 10,
  "internal_risk_score": 0.91,
  "approved": false
}

普通用户可以修改 title 和 body，但不能传入 owner_id、tenant_id、approved 改变归属或审批结果，也不一定能读取 internal_risk_score。

应定义不同的 Pydantic 输入与响应模型，并尽可能把后台控制字段完全排除出用户可写 Schema。

5.4 租户级：任何用户操作都不能跨越租户隔离边界

多租户系统中，通常应同时约束：

text
resource.tenant_id == authorized_tenant_id
AND (
  resource.owner_id == current_user.id
  OR current_user.has_tenant_admin_permission
)

这里只是示意；如果业务存在共享记录或团队权限，需要把真实分享关系加入策略，而不是随意放宽到整租户。

6. BOLA / IDOR：为什么知道 ID 不等于有权限

OWASP API1:2023 Broken Object Level Authorization（BOLA）描述了 API 接受对象标识，却没有对该对象执行充分授权检查的问题。IDOR（Insecure Direct Object Reference）是与此高度相关的传统术语。

脆弱示例：

python
@app.get('/notes/{note_id}')
def get_note(note_id: int, db: Session):
    return db.get(Note, note_id)

它能查到任何存在的笔记，完全没有考虑当前用户、租户或权限。

加上随机 UUID 可能降低“猜测”便利性，却不会使越权访问自动安全。对象 ID 可能通过日志、链接、浏览器缓存、搜索接口或正常业务泄露，权限验证仍不可省略。

正确思路是把授权范围直接合并到查询：

python
stmt = select(Note).where(
    Note.id == note_id,
    Note.tenant_id == allowed_tenant_id,
    Note.owner_id == authenticated_user_id,
)

如果业务允许管理员查看本租户所有记录，应根据可信成员资格改变额外条件，而不是删除所有范围约束。

7. 从 FastAPI 请求到数据库查询的安全执行链

text
HTTP Request
  │
  ├─ Bearer Token / Cookie
  ▼
Authentication Dependency
  │ 检查签名、过期、用户存在与状态
  ▼
Authenticated Principal
  │ 当前可信 user_id
  ▼
Authorization Policy
  │ 校验当前 tenant membership、role、action
  ▼
Scoped Repository Query
  │ WHERE tenant_id = ... AND owner_id = ...
  ▼
Database Transaction
  │ 执行受限 SELECT/INSERT/UPDATE/DELETE
  ▼
Response Model
  │ 只序列化被允许的字段
  ▼
HTTP Response

7.1 FastAPI Dependency 的职责

Depends() 可以集中管理认证依赖，避免每个路由独立解析 Token。业务授权则应继续在资源访问处做检查，因为身份有效不代表能访问某条记录。

7.2 不应把全部授权放到前端

前端可以隐藏不可用操作、减少误触，但这只是用户体验。用户可以跳过网页直接发送 HTTP 请求，所以最终授权必须由服务器端检查。

7.3 不应把全部授权放到 Prompt

对 Agent / AI 服务，模型可以建议读取某个资源；真正的工具执行层必须依据可信主体验证参数、操作和目标。Prompt 不能替代数据库查询的访问范围限制。

8. SQL 层的访问范围约束

8.1 列表查询也要过滤

最常见的安全漏洞之一是详情接口做了授权，但分页列表、搜索、导出、统计接口没有限制数据范围。

普通成员的查询：

sql
SELECT id, tenant_id, owner_id, title, body
FROM notes
WHERE tenant_id = :tenant_id
  AND owner_id = :current_user_id
ORDER BY id
LIMIT :limit;

本租户管理员的查询：

sql
SELECT id, tenant_id, owner_id, title, body
FROM notes
WHERE tenant_id = :tenant_id
ORDER BY id
LIMIT :limit;

其中 tenant_id 必须经过成员资格验证，current_user_id 来自可信认证上下文。

8.2 授权前过滤还是查询后检查

建议优先将范围约束加入查询本身，减少误把未授权记录加载到应用层、缓存层或日志中的机会。额外的应用层检查可以存在，但不应取代受限查询。

8.3 防止复杂 JOIN 泄漏数据

当查询中存在 JOIN 时，权限条件不能因为关联关系变化而丢失。例如某笔记属于租户 10，其附件表如果通过不充分的关联条件加载，仍可能泄漏其他租户的附件。

跨租户关联可考虑复合外键、联表条件、数据库 RLS 与自动化测试共同保护。

8.4 SQL 参数化

WHERE owner_id = :uid 这种绑定参数形式与字符串拼接 SQL 不同。权限约束应通过 ORM 表达式或安全参数化 SQL 构造，不能把用户输入直接拼到 SQL 文本中。

9. 修改与删除：把权限检查纳入实际 SQL

9.1 典型竞态：先查权限，再执行无范围 UPDATE

错误的思路：

text
SELECT 找到 note 101 → 检查所有权
        ↓ 另一事务改变归属
UPDATE notes SET ... WHERE id = 101

权限依赖的资源状态可能发生变化。尤其在并发环境中，应把目标资源、租户、所有权与版本条件纳入最终修改语句，必要时再结合事务锁或更严格隔离级别。

9.2 带范围和版本的条件更新

sql
UPDATE notes
SET title = :title,
    version = version + 1
WHERE id = :note_id
  AND tenant_id = :tenant_id
  AND owner_id = :current_user_id
  AND version = :expected_version;

检查受影响行数：

  • 行数为 1：本次有条件修改成功，可进入事务提交；
  • 行数为 0：可能是记录不存在、无权限或版本冲突；
  • 需要区分版本冲突时，只能在授权范围内进一步查询，不应通过额外查询泄漏未经授权记录的存在。

WHERE version = ... 是乐观并发控制，能够防止旧版本覆盖新版本；它与身份授权是两个不同条件。

9.3 删除同理

sql
DELETE FROM notes
WHERE id = :note_id
  AND tenant_id = :tenant_id
  AND owner_id = :current_user_id;

只有通过所有范围条件的记录才会被删除。在涉及共享资源、合规保留、软删除与审计的场景，需要更复杂的业务规则。

10. 创建操作与字段级授权

10.1 创建时不要接受客户端传入的归属字段

错误：

python
note = Note(**request.model_dump())

如果 request 中包含 owner_id 或 tenant_id，可能触发 Mass Assignment（批量赋值越权）。

正确做法：

python
note = Note(
    owner_id=authenticated_user.id,
    tenant_id=authorized_tenant_id,
    title=request.title,
    body=request.body,
)

10.2 字段白名单优于字段黑名单

明确只允许 title 和 body，比允许所有字段后排除若干敏感字段更稳健。Pydantic ConfigDict(extra="forbid") 能帮助拒绝未声明字段，但重要字段的业务权限仍需在后端检查。

10.3 响应字段也需要控制

即便 SQL 查询到了更多字段，也不应该直接返回 ORM 实例的所有内部数据。可使用独立的 NoteOut 响应模型，仅暴露已授权的字段。

11. HTTP 状态码与错误信息边界

状态码 通常表示 例子
401 Unauthorized 没有通过认证 Token 缺失、过期或签名无效
403 Forbidden 身份有效，但不允许该操作 普通用户尝试调用管理员专用功能
404 Not Found 资源不存在，或选择隐藏无权限对象的存在 读取别人的私有笔记
409 Conflict 业务状态冲突 记录版本已变化
422 Unprocessable Content 输入不满足契约 试图修改 owner_id 等不允许字段

选择对越权对象返回 403 还是 404，取决于产品与安全策略。对于私有数据，统一的 404 往往可以减少对象存在性泄漏；但应避免通过不同响应体、耗时和列表总数暴露敏感信息。

认证失败与授权失败必须区分，不能把所有权限问题都响应 500。

12. PostgreSQL Row-Level Security（RLS）

12.1 RLS 的定位

PostgreSQL 的 Row-Level Security 可以让数据库在执行 SELECT、INSERT、UPDATE、DELETE 时直接应用行访问策略，成为应用层授权的补充防线。

基本示意（假设 notes 已有 tenant_id、owner_id 两列，且值为 BIGINT）：

sql
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;
ALTER TABLE notes FORCE ROW LEVEL SECURITY;

CREATE POLICY notes_owner_select ON notes
FOR SELECT
USING (
  tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint
  AND owner_id = NULLIF(current_setting('app.user_id', true), '')::bigint
);

CREATE POLICY notes_owner_insert ON notes
FOR INSERT
WITH CHECK (
  tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint
  AND owner_id = NULLIF(current_setting('app.user_id', true), '')::bigint
);

CREATE POLICY notes_owner_update ON notes
FOR UPDATE
USING (
  tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint
  AND owner_id = NULLIF(current_setting('app.user_id', true), '')::bigint
)
WITH CHECK (
  tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::bigint
  AND owner_id = NULLIF(current_setting('app.user_id', true), '')::bigint
);

这个例子表达的是“普通成员只能访问自己的记录”，没有实现管理员访问规则；真实系统要结合完整角色模型、表权限与不同操作的策略。管理员需求不能简单通过信任客户端传入 app.is_admin=true 实现。

12.2 将可信用户上下文绑定到数据库事务

在连接池环境下，应避免把上一个请求的租户 ID 永久保留在数据库连接中。一种思路是为当前事务设置会话参数：

sql
SELECT set_config('app.user_id', :authenticated_user_id, true);
SELECT set_config('app.tenant_id', :authorized_tenant_id, true);

第三个参数 true 指事务局部有效。应用必须先完成可信身份验证与租户授权，然后才设置这些参数；在事务中执行受保护查询，完成后事务结束。

12.3 RLS 的边界

  1. 数据库超级用户与具有 BYPASSRLS 属性的角色会绕过 RLS。
  2. 表所有者通常可绕过 RLS；FORCE ROW LEVEL SECURITY 能让表所有者也受策略约束，但不影响超级用户等其他绕过角色。
  3. RLS 不是替代身份认证的机制；它需要可信的数据库角色或安全设置的会话上下文。
  4. 外键与唯一性检查具有特殊的完整性语义，不能假设所有数据库机制都遵循相同的 RLS 过滤视图。
  5. 多条策略的 OR/AND 组合、复杂视图、SECURITY DEFINER 函数、后台任务和迁移账号，都需要专门审查。
  6. 单独启用 RLS，不会自动实现复杂的功能级权限或所有字段级权限。

因此推荐使用非特权应用数据库账户，并实测不同身份与租户的 RLS 行为。

13. SQLAlchemy Session、事务与权限变更

13.1 Session 生命周期

SQLAlchemy Session 是单个工作单元的状态容器；AsyncSession 不应在并发任务之间共享同一个实例。通常可以共享 Engine 和 Session 工厂，为每个请求或独立后台任务创建各自的 Session。

13.2 权限检查与业务修改的事务边界

典型过程：

text
创建 Session / 开始事务
    ↓
查询可信身份及成员资格
    ↓
执行带访问范围的 UPDATE / DELETE
    ↓
检查实际受影响行数
    ↓
提交事务；失败时回滚

某些场景需要更强的一致性：如果业务要求撤销成员身份后绝不允许尚在执行中的更新继续完成，就必须明确其事务串行化、锁或版本验证策略。简单地在业务修改前读一次成员资格，并不能自动覆盖所有并发撤销场景。

13.3 约束和授权不是同一回事

  • 外键、唯一约束和 CHECK 保证数据结构或业务不变量；
  • 授权策略保证某个主体是否可以执行某项操作；
  • 事务保证相关修改的一致提交或回滚；
  • 乐观锁解决并发修改冲突。

这几种机制应组合使用，不应彼此替代。

14. 缓存、后台任务、Agent、RAG 的权限传递

14.1 Redis 与缓存

不能用只有资源 ID 的缓存键存放“某用户可见的私有数据”，然后无条件返回给其他用户。例如 note:101 若缓存了包含私有字段的结果，必须在读取缓存前重新验证访问范围，或者使用经过验证的用户/租户上下文及明确的授权结果策略设计缓存。

权限变化时，缓存 TTL 可能导致撤销延迟；应设计短期缓存、显式失效或版本化授权策略。

14.2 后台 Worker 与队列

后台任务脱离原始 HTTP 请求后，仍然必须有可信身份上下文。不能只信任 Kafka 消息体里的 user_id 或 is_admin。消息的生产者、完整性、任务授权范围和身份传递方式都需要控制。

处理延迟较长的任务时应区别：

  • 提交任务时是否有权操作；
  • 实际执行时是否仍有权操作；
  • 是否属于一次事先批准且有确定内容的执行授权。

具体检查时机取决于业务语义，必须显式定义。

14.3 Agent 工具调用

模型决定调用某工具时，工具实现仍应通过可信主体检查目标对象。工具不应接受模型任意声明的 tenant_id 和 user_id 作为授权来源。资料检索、数据读取与写入工具都必须遵循相同的访问边界。

14.4 RAG 向量检索

检索前应限制租户、资料权限和发布版本；检索结果不得跨租户泄漏。仅依赖模型在 Prompt 中“不要引用其他用户资料”无法构成后端数据访问控制。

14.5 SSE、WebSocket 与持续任务

建立连接时需要认证。长时间订阅或推送时，还需考虑权限发生变化、连接取消、重新连接后的认证，以及每个事件/频道的资源访问边界。

15. 授权策略架构与审计

15.1 PEP、PDP、PIP

常见授权架构把职责拆成：

  • PEP（Policy Enforcement Point）：执行点，拦截操作并实际阻止未授权访问。
  • PDP（Policy Decision Point）：决策点，根据策略判断允许或拒绝。
  • PIP（Policy Information Point）：属性来源，提供当前角色、租户、资源状态等事实。

即使把策略集中管理，服务和工具的执行点仍必须落实拒绝结果。策略服务故障时应有明确的失败行为，避免默认放行。

15.2 审计日志该记录什么

有用的最小字段包括：

json
{
  "request_id": "req-...",
  "actor_id": 17,
  "tenant_id": 10,
  "action": "note.update",
  "resource_type": "note",
  "resource_id": 101,
  "decision": "DENY",
  "reason_code": "OWNER_MISMATCH",
  "policy_version": "authz-v3"
}

拒绝原因可保存在服务器端审计日志中，但不一定需要原样暴露给客户端。不要记录原始访问令牌、密码、私钥或不必要的敏感业务正文。

审计日志能说明系统观察到什么决策，不等于能证明不存在隐藏代码路径绕过授权。

16. 常见错误写法与修复

错误做法 为什么错误 正确方向
前端隐藏删除按钮 可以绕过 UI 调用 API 后端强制授权
直接信任 user_id 参数 可被客户端修改 使用已认证主体
db.get(Note, id) 后立即返回 未检查对象归属 增加租户及对象过滤
仅验证是否登录 登录不代表拥有对象权限 功能、对象、字段分别授权
全站共用 role=admin 管理员范围可能仅限一个租户 授权角色必须带作用域
直接把请求体写进 ORM 可以篡改归属/状态字段 输入字段白名单与后端赋值
详情接口授权但列表未过滤 列表可批量泄漏 所有读取入口都做范围限制
修改前查询权限，更新时只按 ID 存在状态变化与竞态风险 修改 SQL 中包含范围与版本约束
UUID 难猜就省略授权 ID 可能从其他渠道获取 每个对象都要验证权限
Prompt 声明不允许越权 模型文本约束不是执行控制 工具层和数据库授权
Redis 缓存结果全局复用 可能泄漏私有数据 访问前校验或安全分区缓存
通过 JWT 中的旧角色永远授权 权限撤销不会立即生效 查服务端成员资格或设计撤销机制
RLS 应用连接使用超级用户 数据库策略可能被绕过 非特权账号与实测策略
401/403/404 完全混用 调用方无法理解状态且可能泄漏对象存在 明确 API 错误契约

17. 完整 FastAPI + SQLAlchemy 教学实现

下面的示例使用：

  • FastAPI HTTPBearer 获取 Access Token；
  • PyJWT 校验签名、受众、签发者、有效期；
  • 通过数据库查询用户是否停用以及是否属于目标租户；
  • 普通成员只读写自己的笔记；
  • 租户管理员可以读写本租户记录，但不能越过租户边界；
  • Pydantic 禁止客户端指定或修改 owner_id、tenant_id；
  • UPDATE 使用资源范围条件和 expected_version 防止旧版本覆盖；
  • 用明确响应模型限制字段暴露。

示例边界：为了使权限验证本身能够在无外部服务的环境中运行，数据库使用 SQLite；令牌签发函数仅供本地测试。生产系统应由真实认证服务签发令牌，并使用 HTTPS、安全密钥管理、审计、限流和适用的数据库策略。本示例是同步 SQLAlchemy 代码；真正使用 PostgreSQL 异步驱动时应采用 AsyncSession，但授权原则相同。

安装依赖（使用兼容版本，正式项目应锁定版本）：

bash
python -m pip install 'fastapi' 'sqlalchemy>=2,<3' 'pyjwt>=2,<3' 'httpx' 'pytest'

将下面的 Python 代码保存为 authz_demo.py，再将第 18 节测试保存为 test_authz_demo.py，运行 python -m pytest -q。

python
"""可独立测试的 FastAPI + SQLAlchemy 授权教学示例。
注意： SQLite 只用来验证教学逻辑。正式部署需配置实际身份提供方、PostgreSQL、审计与限流。
"""
from __future__ import annotations

from datetime import datetime, timedelta, timezone
from typing import Annotated

import jwt
from fastapi import Depends, FastAPI, HTTPException, Query, status
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
from jwt.exceptions import InvalidTokenError
from pydantic import BaseModel, ConfigDict, Field
from sqlalchemy import Boolean, ForeignKey, Integer, String, Text, UniqueConstraint
from sqlalchemy import delete, select, update
from sqlalchemy.orm import DeclarativeBase, Mapped, Session, mapped_column, sessionmaker

ISSUER = "https://auth.example.internal"
AUDIENCE = "game-api"
bearer_scheme = HTTPBearer(auto_error=False)


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    active: Mapped[bool] = mapped_column(Boolean, nullable=False, default=True)


class Tenant(Base):
    __tablename__ = "tenants"
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    name: Mapped[str] = mapped_column(String(100), nullable=False)


class Membership(Base):
    __tablename__ = "memberships"
    __table_args__ = (UniqueConstraint("tenant_id", "user_id"),)
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    tenant_id: Mapped[int] = mapped_column(ForeignKey("tenants.id"), nullable=False)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), nullable=False)
    role: Mapped[str] = mapped_column(String(20), nullable=False)


class Note(Base):
    __tablename__ = "notes"
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    tenant_id: Mapped[int] = mapped_column(ForeignKey("tenants.id"), nullable=False)
    owner_id: Mapped[int] = mapped_column(ForeignKey("users.id"), nullable=False)
    title: Mapped[str] = mapped_column(String(100), nullable=False)
    body: Mapped[str] = mapped_column(Text, nullable=False)
    version: Mapped[int] = mapped_column(Integer, nullable=False, default=1)


class NoteCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    title: str = Field(min_length=1, max_length=100)
    body: str = Field(min_length=1, max_length=5000)


class NotePatch(BaseModel):
    model_config = ConfigDict(extra="forbid")
    expected_version: int = Field(ge=1)
    title: str | None = Field(default=None, min_length=1, max_length=100)
    body: str | None = Field(default=None, min_length=1, max_length=5000)


class NoteOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: int
    tenant_id: int
    owner_id: int
    title: str
    body: str
    version: int


def create_demo_token(user_id: int, secret: str, *, expire_seconds: int = 3600,
                      audience: str = AUDIENCE) -> str:
    """仅用于本地教学/测试。生产环境由认证服务签发令牌。"""
    now = datetime.now(timezone.utc)
    return jwt.encode({
        "sub": str(user_id), "iss": ISSUER, "aud": audience,
        "iat": now, "exp": now + timedelta(seconds=expire_seconds),
    }, secret, algorithm="HS256")


def create_app(session_factory: sessionmaker[Session], jwt_secret: str) -> FastAPI:
    app = FastAPI(title="访问授权教学示例")

    def get_db():
        with session_factory() as db:
            yield db


    def authenticate(
        credential: Annotated[HTTPAuthorizationCredentials | None, Depends(bearer_scheme)],
        db: Session = Depends(get_db),
    ) -> User:
        err = HTTPException(
            status_code=401, detail="无效或缺失的身份凭据",
            headers={"WWW-Authenticate": "Bearer"},
        )
        if credential is None:
            raise err
        try:
            payload = jwt.decode(
                credential.credentials, jwt_secret,
                algorithms=["HS256"], audience=AUDIENCE, issuer=ISSUER,
                options={"require": ["sub", "iss", "aud", "iat", "exp"]},
            )
            user_id = int(payload["sub"])
            if user_id <= 0:
                raise ValueError("invalid subject")
        except (InvalidTokenError, ValueError, TypeError, KeyError):
            raise err from None
        user = db.get(User, user_id)
        if user is None or not user.active:
            raise err
        return user


    def require_role(db: Session, actor: User, tenant_id: int) -> str:
        role = db.scalar(select(Membership.role).where(
            Membership.tenant_id == tenant_id,
            Membership.user_id == actor.id,
        ))
        # 对未授权的租户使用 404，避免暴露租户是否存在。
        if role not in {"member", "admin"}:
            raise HTTPException(404, detail="资源不存在")
        return role

    def note_filter(actor: User, tenant_id: int, role: str):
        criteria = [Note.tenant_id == tenant_id]
        if role != "admin":
            criteria.append(Note.owner_id == actor.id)
        return criteria

    @app.get("/me")
    def get_me(actor: User = Depends(authenticate)):
        return {"user_id": actor.id}

    @app.get("/tenants/{tenant_id}/notes", response_model=list[NoteOut])
    def list_notes(tenant_id: int, db: Session = Depends(get_db), actor: User = Depends(authenticate),
                   limit: int = Query(50, ge=1, le=100)):
        role = require_role(db, actor, tenant_id)
        stmt = (select(Note).where(*note_filter(actor, tenant_id, role))
                .order_by(Note.id).limit(limit))
        return list(db.scalars(stmt))

    @app.get("/tenants/{tenant_id}/notes/{note_id}", response_model=NoteOut)
    def get_note(tenant_id: int, note_id: int, db: Session = Depends(get_db), actor: User = Depends(authenticate)):
        role = require_role(db, actor, tenant_id)
        stmt = select(Note).where(Note.id == note_id,
                                  *note_filter(actor, tenant_id, role))
        note = db.scalar(stmt)
        if note is None:
            raise HTTPException(404, detail="资源不存在")
        return note

    @app.post("/tenants/{tenant_id}/notes", response_model=NoteOut, status_code=201)
    def create_note(tenant_id: int, request: NoteCreate, db: Session = Depends(get_db), actor: User = Depends(authenticate)):
        require_role(db, actor, tenant_id)
        # 归属字段完全由已验证身份与后端资源上下文决定。
        note = Note(tenant_id=tenant_id, owner_id=actor.id,
                    title=request.title, body=request.body, version=1)
        db.add(note)
        try:
            db.commit()
        except Exception:
            db.rollback()
            raise
        db.refresh(note)
        return note

    @app.patch("/tenants/{tenant_id}/notes/{note_id}", response_model=NoteOut)
    def patch_note(tenant_id: int, note_id: int, request: NotePatch,
                   db: Session = Depends(get_db), actor: User = Depends(authenticate)):
        role = require_role(db, actor, tenant_id)
        changes = request.model_dump(exclude_unset=True, exclude={"expected_version"})
        if not changes or any(v is None for v in changes.values()):
            raise HTTPException(422, detail="必须提供至少一个有效的可修改字段")
        predicates = [Note.id == note_id, Note.version == request.expected_version,
                      *note_filter(actor, tenant_id, role)]
        stmt = update(Note).where(*predicates).values(**changes, version=Note.version + 1)
        try:
            result = db.execute(stmt)
            if result.rowcount != 1:
                exists = db.scalar(select(Note.id).where(
                    Note.id == note_id, *note_filter(actor, tenant_id, role)))
                if exists is not None:
                    raise HTTPException(409, detail="数据版本冲突，请重新读取")
                raise HTTPException(404, detail="资源不存在")
            db.commit()
        except Exception:
            db.rollback()
            raise
        return db.scalar(select(Note).where(Note.id == note_id,
                                              *note_filter(actor, tenant_id, role)))

    @app.delete("/tenants/{tenant_id}/notes/{note_id}", status_code=204)
    def delete_note(tenant_id: int, note_id: int, db: Session = Depends(get_db), actor: User = Depends(authenticate)):
        role = require_role(db, actor, tenant_id)
        stmt = delete(Note).where(Note.id == note_id,
                                  *note_filter(actor, tenant_id, role))
        try:
            result = db.execute(stmt)
            if result.rowcount != 1:
                raise HTTPException(404, detail="资源不存在")
            db.commit()
        except Exception:
            db.rollback()
            raise
        return None

    return app

19. 测试结果与验证边界

本节示例使用本地 Python 解释器运行，测试命令：

bash
python -m pytest -q

实际结果：

text
29 passed in 1.06s

覆盖项目包括：

  • Token 缺失、签名错误、过期和受众不匹配 → 401；
  • 用户已停用、用户不存在 → 401；
  • 正确认证后取得当前用户 ID；
  • 正常读取自己拥有的数据；
  • 跨用户、跨租户、不属于租户的读取 → 404；
  • 租户管理员读取本租户数据，但不能越权读取其他租户；
  • 列表接口只返回授权记录；
  • 创建数据自动绑定可信主体；
  • 请求体伪造 owner_id → 422；
  • 更新自己的记录、阻止更新他人记录；
  • 乐观锁版本冲突 → 409；
  • 更新时伪造所有者字段、空修改、非法可空字段 → 422；
  • 只能删除有权限的对象；
  • 对路径 ID 的非法输入进行类型校验；
  • 响应模型仅暴露定义字段。

未验证范围：

  • PostgreSQL 实例上真实启用 RLS 的测试；
  • 数据库多连接、多进程和跨节点并发；
  • 真实 OAuth2/OIDC 身份提供方、Refresh Token、密钥轮换和撤销流程；
  • 严格撤销竞态（成员权限恰在写事务中被移除）；
  • Redis 缓存授权和跨节点同步；
  • Kafka、Agent 及真实生产日志与审计系统的集成；
  • 浏览器端 Cookie / CSRF 与端到端身份登录流程。

这些部分需要在真实业务环境中单独进行集成、并发和安全测试，不能因为本节 29 项教学测试通过就推断完整生产系统安全。
