测试、部署与效果验证（六）：GitHub Actions 自动化检查、测试与运行环境复现

知识范围：Workflow / Event / Job / Step / Runner、Python CI、uv 锁文件、格式与静态检查、pytest、接口/数据库/后台任务测试、报告归档、运行环境清单、重现与排障、权限与供应链安全。

文档编写日期：2026-11-12。涉及 GitHub Actions 和第三方 Action 的版本、产品限制与配置项，会随着时间变化；最终执行时以实际工作流日志及官方文档为准。

1. CI、CD 与自动化验证的根本概念

CI（Continuous Integration，持续集成） 是在代码变更时自动执行一组事先定义的检查，使不同开发者提交的代码尽早暴露集成问题。它的价值不在于自动显示一个绿色勾选，而在于建立可重复、可追踪、失败可定位的质量门槛。

CD 有两种常见展开：Continuous Delivery（持续交付）强调软件始终具备可发布条件，Continuous Deployment（持续部署）进一步自动部署已通过门槛的更改。执行测试并不意味着必须自动部署。 在涉及数据库迁移、Agent 高权限工具和真实模型 API 的系统中，部署往往需要独立审批、回滚策略和部署环境权限。

一次典型的 Python 项目 CI：

text
Git Push / Pull Request / 手动触发
          ↓
选择 Workflow 与触发事件
          ↓
分配 Runner / Checkout 代码
          ↓
选择 Python 解释器和依赖管理器
          ↓
根据 lockfile 安装依赖
          ↓
静态检查 + 格式检查 + 单元测试
          ↓
接口/数据库/Worker 集成测试（按组件划分）
          ↓
生成 JUnit、覆盖率与环境证据
          ↓
上传 Artifact，输出工作流结论

其中“可以执行”和“验证过”严格不同：CI 绿灯仅证明在该次工作流所覆盖的环境与断言条件下通过，不能证明真实模型准确、生产 Kafka 恢复、所有浏览器交互正确。

1.1 必须区分的四种版本

层次 示例 为什么需要记录
源码版本 Git commit SHA 明确是哪一次提交被测试
工具版本 Python、uv、ruff、pytest 工具升级可能改变检查和行为
依赖版本 fastapi、httpx、SQLAlchemy 等 同一份源码配不同依赖可能结果不同
外部环境版本 Ubuntu Runner、PostgreSQL 镜像、模型 API 外部服务与运行环境也影响结果

仅有 requirements.txt 或 pyproject.toml 不足以证明本次具体安装了什么；还需要锁文件、运行时依赖列表和工作流执行记录。

2. GitHub Actions 的对象模型

2.1 Workflow、Event、Job、Step、Action、Runner

  • Workflow：位于 .github/workflows/*.yml（或 .yaml）的自动化流程定义。
  • Event：触发条件，例如 push、pull_request、workflow_dispatch。
  • Job：在一个 Runner 上执行的一组步骤；不同 Job 默认彼此隔离，除非指定 needs 或共享 Artifact/外部服务。
  • Step：Job 内单次操作，可以执行 shell 命令（run），也可以调用 Action（uses）。同一 Job 的 Step 通常共享工作空间，但运行在不同进程中。
  • Action：可复用步骤，例如 actions/checkout、astral-sh/setup-uv、actions/upload-artifact。
  • Runner：执行 Job 的机器，可由 GitHub 托管，也可自行托管。
yaml
name: CI
"on": [push, pull_request]
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
      - run: python --version

"on" 与不加引号的 on 对 GitHub Actions 都是合法的 YAML 键。这里用引号是为了避免某些 YAML 1.1 解析器（例如默认 PyYAML）把 on 误判成布尔值 true。

2.2 Job 与 Step 的环境范围

每个 Step 是新进程，因此 export X=1 通常不会自动让后续 Step 继承 X。应使用 env: 声明，或按 GitHub 官方机制向 $GITHUB_ENV 写入被允许的环境变量。共享文件则可以保留在同一 Job 的工作空间。

不同 Job 不应该假设共享同一文件系统，传递测试结果应使用 Artifact、明确的 Job Output 或外部存储，而不是依赖上一个 Job 的临时路径。

2.3 触发条件与检查范围

  • push：合并或直接推送后验证代码状态。
  • pull_request：在代码评审阶段验证待合并更改。
  • workflow_dispatch：手动运行，适用于诊断和不宜每次自动执行的较重检查。
  • schedule：需要周期性巡检的情况下使用，但不是普通 PR 检查的必要组成。

使用路径过滤时要特别注意：如果被分支保护规则要求的检查因路径过滤没有执行，可能出现状态一直 Pending 的情况。应按仓库规则设计检查名称、触发条件和 Required Status Checks。

3. 运行环境不是“默认一致”的

3.1 Python 版本

runs-on: ubuntu-latest 是可移动的系统镜像标签，不能保证任意两次运行的工具版本完全相同。runs-on: ubuntu-24.04 固定了系统发行版本系列，但 GitHub 仍会更新相应 Runner 镜像及预装组件，因此应保存运行时信息。

Python 可以通过 actions/setup-python 指定：

yaml
- uses: actions/setup-python@v7
  with:
    python-version: "3.13"
- run: python --version

其中 3.13 表示兼容的 3.13.x 补丁版本，而非一个固定补丁号。需要严格复现时，指定准确补丁版本并记录 python --version。

也可使用 uv python install 3.13。一个项目选定一种明确的 Python 安装方式即可，不必无理由叠加 setup-python 和 uv 的解释器安装。

3.2 开发机与 CI 系统差异

Windows 开发机与 Ubuntu CI 之间存在路径、换行、文件大小写、编码、可执行权限以及服务地址差异。因此：

  • 核心单元测试尽量跨平台；
  • Linux 生产部署使用至少一个 Linux CI Job 验证；
  • 若 Windows 行为关键，可通过 strategy.matrix.os 增加 Windows Runner；
  • 依赖真实数据库的测试应使用明确的数据库服务，而不能仅用 SQLite 冒充 PostgreSQL。

3.3 Python 环境、venv、依赖声明和锁文件

不同概念分别是：

文件/工具 作用
pyproject.toml 声明项目、最低 Python 版本与直接依赖范围
uv.lock 记录解析出的依赖图与具体版本，是项目可复现安装的关键输入
.python-version 约定 Python 解释器版本
.venv/ 本地实际安装依赖的环境，通常不提交仓库
CI 环境清单 记录某次运行实际安装的包与版本，属于执行证据

uv sync --locked 将检查锁文件是否与项目要求一致；若需要更新锁文件则报错，而不是静默修改。uv run --locked ... 同样可防止运行前自动改锁。--frozen 的语义不同，不应简单当作 --locked 的同义词。

推荐在修改依赖时：

powershell
uv add fastapi
uv add --group dev pytest ruff httpx
uv lock
uv sync --locked --all-groups
uv run --locked pytest -q

把 pyproject.toml、uv.lock 和必要的项目配置一起提交。CI 不应该通过“发现依赖不匹配 → 自动重新锁定 → 继续测试”掩盖声明与锁文件漂移。

4. 检查与测试应分层

层级 典型命令 测试什么 不证明什么
语法 python -m compileall -q . Python 能否解析/编译 类型正确、业务行为正确
格式 ruff format --check . 代码格式符合团队约定 是否能运行
静态检查 ruff check . 常见错误和编码规范 运行时所有异常均可发现
单元测试 pytest -q tests/unit 核心函数和失败分支 数据库真实协议一致
API 测试 FastAPI TestClient 路由、校验、错误契约 网络代理、真实生产负载
数据库集成 PostgreSQL + ORM 事务、约束、迁移、SQL Kafka Offset 提交与外部系统一致性
后台任务集成 Kafka + Worker 消费与恢复、重试、幂等 完整生产灾难恢复
模型效果评测 真实模型与固定样例 回答、工具选择、引用正确性 确定性程序在所有故障下正确

普通 PR 的 CI 应优先运行快速且无真实模型费用的测试。真实模型评测可放在手动或隔离的受控工作流，并设置费用与权限边界。无需为了 CI 自动作业而向不可信 PR 暴露 API Key。

4.1 断言要验证结果而非只看状态

错误测试：

python
assert response.status_code == 200

这只能证明 HTTP 请求成功。更完整的测试应检查业务输出：

python
assert response.status_code == 200
assert response.json() == {"total_cents": 250}

对于异常分支，必须明确输入、预期的 HTTP 状态、错误结构和数据库副作用。后台任务测试还需要对照任务状态与最终持久化记录，不能只看 Worker 进程是否活着。

5. 使用 uv 构建一个最小可复现的 Python CI 项目

下面使用 FastAPI 报价接口作为教学项目。其目的不是构建生产业务，而是展示从代码检查、API 测试到环境留证的一整套最小 CI。

项目文件结构：

text
ci-learning-demo/
├── .github/
│   └── workflows/
│       └── ci.yml
├── .python-version
├── app.py
├── pyproject.toml
├── uv.lock                   # 执行 uv lock 后生成并提交
├── tests/
│   ├── test_app.py
│   └── test_record_environment.py
├── scripts/
│   └── record_environment.py
└── evidence/                 # CI 产生，不应提交

5.1 最小项目依赖

toml
[project]
name = "ci-learning-demo"
version = "0.1.0"
requires-python = ">=3.13"
dependencies = ["fastapi>=0.115,<1"]

[dependency-groups]
dev = ["pytest>=8,<10", "httpx>=0.27,<1", "ruff>=0.9,<1"]

[tool.uv]
package = false

[tool.pytest.ini_options]
testpaths = ["tests"]

[tool.ruff]
line-length = 88
target-version = "py313"

以上是教学用版本约束，并非安装后实际得到的具体版本。实际结果由 uv.lock 和运行时清单决定。[tool.uv] package=false 表示此示例不是发布到 PyPI 的安装包；将 app.py 放在项目根目录让测试直接导入即可。复杂系统可改用 src/ 包布局并配置构建后端。

5.2 本地准备与运行命令

powershell
uv lock
uv sync --locked --all-groups
uv run --locked --no-sync ruff check .
uv run --locked --no-sync ruff format --check .
uv run --locked --no-sync pytest -q
uv run --locked --no-sync python scripts/record_environment.py

--no-sync 表示运行时不再次同步环境；前提是已成功执行 uv sync，不能用于跳过依赖安装。添加新依赖时应重新生成并提交 uv.lock。

6. GitHub Actions 完整 CI Workflow

如下示例使用 GitHub-hosted Ubuntu Runner，Python 3.13 与固定 uv 工具版本，执行 Ruff 检查和 pytest，并归档运行环境清单和 JUnit 报告。

使用条件：将示例工程代码及实际生成的 uv.lock 提交至仓库的 main 分支；其中固定 Action SHA 取自对应项目官方示例。第三方 Action 的 SHA 与工具版本应随着项目维护进行审查更新。

yaml
name: Python CI

"on":
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  checks:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    steps:
      - name: Checkout source
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1

      - name: Install uv
        uses: astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9 # v9.0.0
        with:
          version: "0.10.0" # example: update deliberately with the project
          enable-cache: true

      - name: Prepare Python
        run: uv python install 3.13

      - name: Install locked dependencies
        run: uv sync --locked --all-groups

      - name: Record runtime and dependencies
        run: uv run --locked --no-sync python scripts/record_environment.py

      - name: Lint
        run: uv run --locked --no-sync ruff check .

      - name: Check formatting
        run: uv run --locked --no-sync ruff format --check .

      - name: Unit and API tests
        run: |
          mkdir -p evidence
          uv run --locked --no-sync pytest -q --junitxml=evidence/junit.xml

      - name: Upload evidence
        if: ${{ !cancelled() }}
        uses: actions/upload-artifact@v4
        with:
          name: ci-evidence-${{ github.run_id }}-${{ github.run_attempt }}
          path: evidence/
          if-no-files-found: warn
          retention-days: 14

6.1 逐项解释

  1. permissions: contents: read：遵循最小权限，仅允许 CI 获取仓库内容。部署和写入外部服务需要另行设计权限。
  2. "on"：推送、PR 和手动执行均可触发。手动按钮依赖工作流已存在于默认分支等 GitHub 规则。
  3. concurrency：同一分支的旧运行可以被取消，避免连续推送浪费计算；但若任务具有不可中断的外部副作用，不应贸然使用 cancel-in-progress: true。
  4. runs-on: ubuntu-24.04：减少操作系统系列漂移，不代表镜像内容完全冻结。
  5. timeout-minutes：限制卡住的 CI Job，避免无边界执行。
  6. 固定的 checkout 和 setup-uv Action SHA：减少 Action 标签漂移风险，实际仍需验证来源与审计更新。
  7. uv sync --locked --all-groups：根据仓库锁文件安装所有依赖组，检查 lock 与项目配置一致性。
  8. Ruff：不满足检查即返回非零退出码，Job 标记失败。
  9. pytest：输出 JUnit XML 供后续审计或测试报告工具消费。
  10. 环境清单：在测试前生成，确保即使后续测试失败，也能保留安装版本与配置哈希。
  11. Artifact：在工作流未被取消时尝试上传证据，if-no-files-found: warn 避免早期依赖安装故障额外触发“没有 Artifact”的次生失败。

6.2 关于固定 Action 版本与 SHA

actions/checkout@v7 追随可更新的标签；actions/checkout@<40位SHA> 锁定具体提交。后者更加可审计，但需要定期升级并核查发布方。对第三方 Action 应优先采用完整提交 SHA；示例中 upload-artifact@v4 为便于阅读的版本引用，严格生产环境应换成由官方发布信息核实的完整提交 SHA。

不要从搜索结果、评论或非官方片段随意复制 SHA 并假设可信。 需要核对仓库所有者、发布标签与提交指向。固定 Action 不等于固定运行镜像、依赖服务器或上游 API。

7. 记录实际依赖版本和运行方式

这是本条学习目标最容易被忽略、同时也是最重要的交付要求。

7.1 仅保存锁文件为什么仍不够？

uv.lock 证明依赖解析快照，但一次 CI 执行还受这些因素影响：

  • Runner 系统镜像及其更新；
  • 实际 Python 补丁版本与架构；
  • 实际安装包集合（包含环境附加包）；
  • uv 工具版本与 Action 版本；
  • 源码提交及具体 Job 运行次数；
  • 执行的测试命令和是否采用了附加环境变量；
  • 外部服务镜像和数据库迁移版本。

因此建议为每次运行生成 evidence/environment.json，记录允许记录的元数据，而不是将 env、所有请求头或秘密完整输出到日志。

7.2 建议的运行环境清单字段

字段 含义 来源
git_commit 本次代码版本 GITHUB_SHA 或 Git
ci.GITHUB_RUN_ID 工作流运行 ID GitHub Runner
ci.GITHUB_RUN_ATTEMPT 同一 Run 的重试次数 GitHub Runner
python 实际 Python 版本 sys.version
uv 实际 uv 版本 uv --version
platform 运行系统与架构 platform
installed_packages 安装包的名称与实际版本 importlib.metadata
sha256.uv.lock 锁文件内容指纹 hashlib.sha256
sha256.pyproject.toml 项目定义内容指纹 hashlib.sha256
commands 该 CI 定义的主要执行命令 明确维护的命令清单

commands 是预定义执行命令记录，不是 shell 实际执行成功的证明；实际执行成败还要看每个 Step 的退出码、Job 日志与 JUnit 测试记录。

7.3 最小权限与日志安全

  • 只读取白名单环境变量，避免记录 OPENAI_API_KEY、DATABASE_URL、GITHUB_TOKEN 等秘密；
  • 不把完整模型 Prompt、用户输入或数据库记录直接上传 Artifact；
  • 依赖包名称在企业内部也可能敏感，对 Artifact 设定访问控制和保留期；
  • 将真实执行结果与测试数据分开保存，避免用手工生成的成功报告冒充 CI 结果。

8. 生成并保存 CI 测试证据

8.1 JUnit XML 报告

bash
mkdir -p evidence
uv run --locked --no-sync pytest -q --junitxml=evidence/junit.xml

JUnit 格式包含测试套件、测试名、失败/错误情况和执行时间等，供 CI 报告页面或审计工具读取；它与代码覆盖率报告不是同一件事。

8.2 GitHub Artifact 与 Cache 的本质区别

  • Artifact：应当保留给用户或后续 Job 的产物，例如测试报告、失败截图、依赖清单、静态分析报告。
  • Cache：为了节约重复下载与构建时间而保存的可再生缓存，例如 uv 包缓存。缓存命中不等于依赖版本已锁定，也不能当作可靠的审计记录。

上传 Artifact 应限制范围：上传 evidence/ 比上传整个工作空间更可控。retention-days 决定存储保留期限，并受仓库/组织策略约束。Artifact 过期后，Git commit 和锁文件可能仍在，但历史运行证据不一定能够找回。

8.3 输出 Job Summary

GitHub 提供 $GITHUB_STEP_SUMMARY 文件路径，可追加 Markdown 作为该次 Job 的摘要。示例：

bash
{
  echo "## Python CI"
  echo "- Commit: $GITHUB_SHA"
  echo "- Python: $(python --version 2>&1)"
  echo "- uv: $(uv --version)"
} >> "$GITHUB_STEP_SUMMARY"

摘要适合记录版本与跳转说明，不适合输出所有环境变量和敏感路径。若需要在测试失败后仍生成摘要，应单独处理失败路径和退出码。

9. 如何加入真实数据库集成测试

SQLite 对 SQLAlchemy 模型和事务行为的测试有价值，但不能证明 PostgreSQL 的 RLS、行锁、JSONB、并发隔离和 Alembic 迁移全部正确。需要真实数据库时，可使用 GitHub Actions 的 PostgreSQL service container：

yaml
jobs:
  postgres-test:
    runs-on: ubuntu-24.04
    services:
      postgres:
        image: postgres:17
        env:
          POSTGRES_USER: ci_user
          POSTGRES_PASSWORD: ci_password_local_only
          POSTGRES_DB: ci_db
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U ci_user -d ci_db"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 10
    env:
      TEST_DATABASE_URL: postgresql+psycopg://ci_user:ci_password_local_only@127.0.0.1:5432/ci_db
    steps:
      - uses: actions/checkout@v7
      # 这里继续安装 Python 与项目依赖
      # 安装 Alembic 与 psycopg 后执行数据库迁移与测试
      - run: uv run --locked alembic upgrade head
      - run: uv run --locked pytest -q tests/integration_db

上述是需要已有 Alembic 工程和 PostgreSQL 驱动的增量模板，不是本节最小项目可原样运行的完整 Job。数据库口令仅为独立 CI 容器内的演示凭据，不应复制到真实环境，尤其不要在拥有外部生产网络权限的 Runner 上使用。

在直接运行于 Ubuntu Runner 的 Job 中，通过映射的主机端口访问服务通常是 127.0.0.1:5432；如果 Job 自身运行在容器中，通常使用服务名 postgres:5432。两者不要混淆。服务健康不代表数据库迁移已完成，也不代表业务表一定存在。

9.1 PostgreSQL / Kafka 集成测试的边界

  • CI 部署测试数据库应与生产环境完全隔离；
  • 测试启动前执行 alembic upgrade head，而不是自动 create_all() 掩盖迁移缺失；
  • 并发测试应使用独立、清理明确的测试数据；
  • Kafka 故障恢复测试应验证消息重投、Worker 崩溃与最终结果幂等，而不仅是 Broker 能启动；
  • 较耗时的真实服务测试可以使用独立 Job，并设置 needs、超时和明确的触发条件。

10. 多版本测试与 Matrix

在需要支持多种 Python 或系统环境时，使用 Matrix：

yaml
strategy:
  fail-fast: false
  matrix:
    python-version: ["3.12", "3.13"]
steps:
  - uses: actions/checkout@v7
  - uses: astral-sh/setup-uv@v9
    with:
      python-version: ${{ matrix.python-version }}
  - run: uv sync --locked --all-groups
  - run: uv run --locked pytest -q

注意： 这个 Matrix 是单独的机制示例；上面最小项目的 requires-python = ">=3.13" 不支持 3.12，若按原样使用应保留 3.13 或调整项目的 Python 兼容范围并验证代码与依赖。若矩阵包含多个 Job，Artifact 名称必须互不冲突，建议带 Python 版本和操作系统后缀。

fail-fast: false 可以避免某个版本失败就取消其余版本，便于收集完整兼容性证据；代价是增加执行时间和资源消耗。

11. 测试结果与合并门槛

Required Status Check 指合并前必须通过的指定检查。建议按真实团队规则设置：

  • 静态检查和格式检查；
  • 快速单元及接口测试；
  • 关键数据库迁移检查；
  • 必要的授权与跨用户数据隔离测试。

不要将总是跳过的 Job 错误配置为唯一合并门槛；不要使用 continue-on-error: true 隐藏必须通过的关键测试；也不要把 pytest ... || true 当作“容错”，否则 CI 可能假绿。

如果某些检测仅供观察，可以在单独 Job 明确标记为实验性或非阻断，并保留真实失败结果。

12. 安全：CI 执行的是代码，不能忽略权限

Pull Request 可能带来不可信代码。执行测试本身就会运行项目的 Python 代码或构建脚本，必须遵循以下安全原则。

最低权限原则： 使用 permissions: contents: read。只有确实需要写入评论、发布包或部署时才增加精确权限。

避免提权运行未知代码： 普通 PR 检查使用 pull_request；不应在带有仓库密钥的 pull_request_target 工作流中 checkout 并执行不可信 PR 代码，这可能暴露秘密和写权限。

密钥分离： 普通测试使用替身或本地服务，不能随意给外部贡献者提交的 PR 注入生产 API Key。真实模型评测可通过人工触发、受保护环境和权限批准独立运行。

供应链： 优先使用官方 Action、经审查的完整 SHA 固定、锁文件、最小化依赖源。对私有包索引和自托管 Runner 应额外考虑凭据和网络隔离。

Artifact 安全： 只有经过数据筛选的报告可以上传。Trace、原始请求和数据库快照可能含密钥、个人数据或内部资料，不应默认公开。

13. 常见故障的定位方法

现象 典型原因 排查切入点
Workflow 没触发 文件路径错误、事件过滤、分支不符 .github/workflows/、on、提交到哪个分支
uv sync --locked 报错 修改了依赖但未提交新锁文件 对比 pyproject.toml、uv.lock、Python 约束
本地能跑、CI ModuleNotFoundError 本地环境额外安装依赖、包路径有误 uv.lock、CI 依赖组、导入路径
Ruff 失败 代码规范、import 顺序、格式问题 本地运行完全相同的命令
pytest 失败 行为错误、并发竞态、未隔离测试状态 JUnit、pytest 输出、失败用例原始输入
数据库连接拒绝 容器未健康、主机名或端口不对 Service Health、localhost/服务名区分
Alembic 迁移失败 版本链不一致、数据库账号无权限 alembic current、alembic heads、SQL 错误
测试超时 死锁、无限重试、外部网络等待 timeout-minutes、单测试超时、业务日志
Artifact 不见了 路径错误、上传 Step 被跳过、保留期到期 上传日志、if 条件、Artifact 设置
CI 绿灯但功能故障 测试没有覆盖真实组件或场景 测试分层、契约与真实集成边界

排障顺序建议遵循：先确认有没有触发 → 再确认 Runner 与依赖 → 再找第一个失败的 Step → 再看失败测试与环境证据 → 最后重现同一版本的命令。

14. 如何回答“这次 CI 实际用了什么版本、怎么运行的”

一份可复现的运行记录，至少应包括：

text
Source: GITHUB_SHA = <40位提交哈希>
Run: GITHUB_RUN_ID / GITHUB_RUN_ATTEMPT
Runner: Ubuntu image + RUNNER_ARCH
Python: 实际 python --version
uv: 实际 uv --version
Declared deps: pyproject.toml 哈希
Resolved deps: uv.lock 哈希
Installed deps: 本次 environment.json 的 package name/version
Commands: Ruff check / Ruff format --check / pytest ...
Test results: JUnit 报告 / Step 退出状态
External dependencies: 若有 PostgreSQL/Kafka，记录镜像版本与迁移版本
Artifacts: 报告名称、生成时间、保留期

Git SHA + lockfile + 实际依赖清单 + Runner 信息 + 执行命令 + 测试结果 才构成有意义的复现证据链。

即使这些证据齐全，外部包源和模型 API 的可变性也可能影响完全重现；对于高度敏感的生产构建还应考虑容器镜像 Digest、可验证构建和软件物料清单（SBOM）。

15. 与 AI 应用工程的联系

对于使用 FastAPI、Agno、PostgreSQL、Redis、Kafka 的 AI 应用，CI 应分清两大目标：

  1. 程序可靠性： 使用模型替身验证超时、拒答、非法 JSON、工具越权、会话隔离、数据库回滚、消息重复和 Worker 恢复。大部分可以在每次 PR 运行，且不需要付费模型。
  2. 模型效果： 使用固定样例和独立参考依据，验证回答、引用、工具选择、用量和耗时。根据费用和保密要求单独运行，不应将真实模型随机性误当成 Python 单元测试的不稳定性。

在 CI 里记录 Agent 模型、提示词模板哈希和 RAG 知识库快照版本，可以帮助把一次效果退步与具体配置变更关联起来。模型 API 版本和模型后端部署状态不一定完全由你控制，因此实际能力评测还需要随运行留存结果。

from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI(title="CI example")


class QuoteRequest(BaseModel):
    quantity: int = Field(ge=1, le=100)
    unit_price_cents: int = Field(ge=0, le=1_000_000)


class QuoteResponse(BaseModel):
    total_cents: int


def calculate_total(quantity: int, unit_price_cents: int) -> int:
    if not (1 <= quantity <= 100):
        raise ValueError("invalid quantity")
    if not (0 <= unit_price_cents <= 1_000_000):
        raise ValueError("invalid price")
    return quantity * unit_price_cents


@app.get("/healthz")
def healthz() -> dict[str, str]:
    return {"status": "ok"}


@app.post("/quote", response_model=QuoteResponse)
def quote(req: QuoteRequest) -> QuoteResponse:
    return QuoteResponse(
        total_cents=calculate_total(req.quantity, req.unit_price_cents)
    )

附录 D：scripts/record_environment.py

python
"""Record non-secret, reproducibility-oriented CI evidence."""

from __future__ import annotations

import hashlib
import json
import os
import platform
import subprocess
import sys
from importlib import metadata
from pathlib import Path

ALLOWED_CI_KEYS = (
    "CI", "GITHUB_REPOSITORY", "GITHUB_SHA", "GITHUB_RUN_ID",
    "GITHUB_RUN_ATTEMPT", "GITHUB_WORKFLOW", "RUNNER_OS", "RUNNER_ARCH",
)


def digest(path: str) -> str | None:
    p = Path(path)
    return hashlib.sha256(p.read_bytes()).hexdigest() if p.is_file() else None


def command_version(*args: str) -> str | None:
    try:
        result = subprocess.run(
            args, text=True, capture_output=True, check=True, timeout=5
        )
        return result.stdout.strip() or result.stderr.strip()
    except (OSError, subprocess.SubprocessError):
        return None


def build_manifest() -> dict[str, object]:
    packages = sorted(
        (
            {"name": (dist.metadata.get("Name") or "unknown"), "version": dist.version}
            for dist in metadata.distributions()
        ),
        key=lambda p: (str(p["name"]).casefold(), str(p["version"])),
    )
    return {
        "python": sys.version.split()[0],
        "python_implementation": platform.python_implementation(),
        "platform": platform.platform(),
        "uv": command_version("uv", "--version"),
        "git_commit": os.getenv("GITHUB_SHA") or command_version("git", "rev-parse", "HEAD"),
        "ci": {key: os.environ[key] for key in ALLOWED_CI_KEYS if key in os.environ},
        "sha256": {
            path: digest(path)
            for path in ("pyproject.toml", "uv.lock", ".github/workflows/ci.yml")
        },
        "installed_packages": packages,
        "commands": [
            "uv sync --locked --all-groups",
            "uv run --locked --no-sync ruff check .",
            "uv run --locked --no-sync ruff format --check .",
            "uv run --locked --no-sync pytest -q --junitxml=evidence/junit.xml",
        ],
    }


def main() -> None:
    output = Path("evidence")
    output.mkdir(exist_ok=True)
    (output / "environment.json").write_text(
        json.dumps(build_manifest(), ensure_ascii=False, indent=2) + "\n",
        encoding="utf-8",
    )
    print("Wrote evidence/environment.json")


if __name__ == "__main__":
    main()
