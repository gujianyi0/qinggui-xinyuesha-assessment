1. 为什么 Redis 缓存与 PostgreSQL 持久化数据必须分工

在常见的 Cache-Aside（旁路缓存） 模式中，PostgreSQL 是业务记录的权威存储（source of truth），Redis 是一份可丢弃、可重建的加速副本。典型读取路径：

text
客户端请求
   │
   ▼
FastAPI → Redis GET(cache:key)
             ├─ 命中 → 返回缓存副本
             └─ 未命中 / 过期 / 故障 → PostgreSQL SELECT
                                      │
                                      ├─ 读取成功 → 可尝试回填 Redis
                                      └─ 读取失败 → 依业务策略返回错误

“可丢弃”是架构设计选择，不是 Redis 的固有属性。Redis 也支持 AOF、RDB 持久化、Streams 等用途，能够承载有持久化要求的特定场景；但如果一个系统明确将 PostgreSQL 作为权威业务数据库，则不能因为 Redis 支持持久化而把缓存里的一次临时写入视为业务正式提交。

必须区分以下三个目标：

目标 典型要求 主要承担机制
可用性 Redis 异常时，核心查询仍可用 数据库回源、超时、熔断、限流
一致性 规则更新后不能混淆新旧版本 版本标识、事务、缓存失效、读写契约
正确性 不重复提交反馈、不产生半成品记录 PostgreSQL UNIQUE、事务、幂等键

Redis 锁一般用于减少重复执行或协调竞争，而不是最终证明业务唯一性与正确性。

2. 缓存失效的四种不同原因

2.1 TTL 到期（Expiration）

text
SET doc:001:v3 '{"text":"..."}' EX 60
TTL doc:001:v3
GET doc:001:v3

TTL 表示键被允许继续存在的剩余时限。Redis 的 TTL 返回正的剩余秒数时，表示设置了过期时间；-1 代表键存在但没有到期设置；-2 代表键不存在。Redis 采用访问时的惰性过期检查和后台主动清理结合的方式。

**重要差别：**键在逻辑上已过期后，不应继续作为正常缓存命中返回；但是 Redis 的 expired 发布通知不保证恰好在到期瞬间发出。因此，不应把过期通知当作精确的业务定时器，也不能依赖它确保定时执行某项不可丢失的操作。

2.2 主动失效（Invalidation）

业务写入后执行 DEL key 或切换版本键，可以使后续访问重新读取数据库。它用于“资料更新后的缓存刷新”，与 TTL 的自然到期是两个不同机制。

2.3 内存淘汰（Eviction）

Redis maxmemory-policy 可能根据 LRU、LFU、TTL 等策略提前删除仍未过期的 Key。TTL 未到不代表键一定仍在缓存。 当缓存数据丢失后应能够从权威存储重新构建。

2.4 故障导致的数据不可访问或丢失

网络中断、Redis 重启、主从切换、连接池耗尽等情况下，应用可能无法读取缓存。Redis 故障与缓存未命中不同：前者是依赖异常，后者是正常运行中的无数据状态。日志和监控必须区分。

还有一个容易忽略的细节：普通 SET key value 覆写旧值时通常会清除旧 TTL，除非使用合适的保留/重新设置 TTL 参数。无意中丢失 TTL，可能导致缓存长期陈旧。

3. 缓存过期后应如何处理

3.1 Cache-Aside 基本流程

  1. 读取 Redis；命中则快速返回。
  2. 未命中时访问 PostgreSQL。
  3. 取回权威数据并返回。
  4. 尝试写入缓存及新 TTL。缓存回填失败通常不应该导致已经成功的只读请求失败。

这个流程可以降低数据库读负载，但它提供的通常是有界陈旧或最终一致性，而不是强一致性。缓存读取速度和数据新鲜度需要权衡。

3.2 缓存空值与“没有找到”

假设数据库没有 document_id=foo 的记录，简单的 cache.get(key) is None 无法判断 Redis 里是“没有 Key”还是“缓存里恰好存放了 None”。一般应使用明确的空值哨兵，例如 {"status":"NOT_FOUND"}，并设置较短 TTL。

空值缓存可以抑制重复无效查询，但记录新创建后应清除对应负缓存，否则会继续返回“找不到”。还须做好租户边界，不能让无权限查询得到的结果被无区分地复用于其他用户。

3.3 不能盲信旧缓存

对于身份权限、余额、资金交易、写入确认等高正确性场景，不应把缓存是否存在作为唯一裁决依据。缓存的失效窗口通常无法提供业务级强一致保证。

4. 资料更新的并发竞态：数据库提交后删除缓存仍可能返回旧值

4.1 典型时间线

设数据库规则值原来是 A，更新后是 B：

text
时刻    请求 R1（读取）                 请求 W（写入）
 t1    Redis 未命中
 t2    从数据库读到旧值 A
 t3                                      数据库事务提交新值 B
 t4                                      删除 Redis 缓存 key
 t5    将旧值 A 写回 Redis ← 竞争窗口
 t6    另一个读请求命中旧值 A

即使严格遵守“先提交数据库，后删除缓存”，仍存在在途旧读将旧数据写回的竞态。反过来先删缓存再更新数据库，还可能让并发请求在数据库更新前把旧值重新填回，因此通常更不理想。

4.2 应对手段有不同强度

  • **设置短 TTL：**限制陈旧数据可能存在的时长；不保证实时一致性。
  • **缓存失效事件 + 重试：**缩短旧值窗口；需要可靠的事件发布与消费。
  • **写入/读取版本标识：**让缓存内容附带资料版本；读取时验证版本是否与所需版本一致。
  • **版本化 Key：**使用 rule:001:v12、rule:001:v13，旧读回填只能写旧版本 Key，不能覆盖新版本 Key。
  • **从权威数据库读取当前版本：**严格版本要求下，读取对应版本前必须从可靠来源确认版本，或者使用能证明版本的新鲜度协议；只靠 Redis 中的“当前版本指针”仍可能陈旧。

例：

text
PostgreSQL: (doc_id=001, version=13, content=B)
Redis:      rule:001:v12 = A   # 旧资料仍可能存在
            rule:001:v13 = B   # 新资料

若当前业务版本由 PostgreSQL 确认是 13，系统只会查询 v13，即使旧请求晚到，也无法把 v12 覆盖到 v13。这只解决“旧值覆盖新版本 Key”的问题，不自动保证读到的是最新数据库版本；如果版本判断本身陈旧，仍然可能读旧资料。

4.3 版本化读取的取舍

每次先查 PostgreSQL 当前版本可实现较清晰的正确性边界，但会增加数据库请求，削弱缓存的性能收益。另一种方式是维护版本指针、发布更新事件或给指针很短的 TTL；这些方案性能更好，但一致性承诺必须弱化，并验证故障时的行为。不能同时宣称“完全不查数据库”和“缓存总是严格最新”，除非另外建立了可证明的协调机制。

5. 四种缓存写入模式

模式 谁先被修改 优点 风险与限制
Cache-Aside 应用写 DB，后删/更新缓存 常用、简单 写入与失效之间存在竞争
Write-Through 写入经过缓存层并同步持久化 读缓存更容易保持更新 需要明确失败的原子性，跨存储无法天然事务化
Write-Behind 先写缓存，异步落 DB 写入快 Redis 丢失、异步失败可能丢业务数据
Versioned Cache Key 包含业务版本 旧回填无法覆盖新版本 Key 版本发现与旧 Key 清理仍需设计

特别是 Write-Behind，不适合未经可靠性设计就用于资金、订单确认或最终反馈记录。如果 Redis 写成功但数据尚未入 PostgreSQL，不能直接视为最终持久化成功。

6. 资料更新与 RAG 索引的不同生命周期

对 RAG 系统，“更新数据库规则”和“新版本向量索引可用”不一定同时发生。一个可靠的版本发布流程：

text
创建文档版本 v13（DRAFT）
    ↓
解析、分块、Embedding、构建 v13 索引
    ↓
核对分块数量、来源与检索评测
    ↓
将 v13 标记 READY
    ↓
数据库事务中切换当前可用版本指针 → v13
    ↓
让请求按明确版本检索；旧 v12 保留一段时间
    ↓
根据保留策略清理旧缓存与旧索引

只有资料版本已发布且相应索引就绪，才应把新版本用于当前问答。 否则可能出现“文本资料是 v13、向量索引却仍是 v12”的混合回答。

相关字段可设计为 document_id、version、source_hash、index_status、published_at、effective_at。它们应来自权威记录，而不是只保存在具有 TTL 的 Redis Key 中。

7. Redis 不可用时如何降级

7.1 缓存只读业务：优先回源

对普通公开文档查询，如果 Redis 不可用，可以从 PostgreSQL 直接读取；但应限制回源并发，避免 Redis 故障使数据库瞬间承受所有流量。

7.2 需要 Redis 实现限流/锁的场景：按风险分级

Redis 不可用时，对高风险写入不应通过“默认允许”绕过锁与权限校验。这种场景往往需要 fail closed：拒绝执行或使用独立、可证明正确的数据库控制路径。

对于普通页面内容缓存，则可能选择 fail open：直接读数据库，允许性能下降但继续服务。Fail open 和 fail closed 是业务容错策略，不是 Redis 自动提供的功能。

操作 Redis 故障时的推荐语义
展示公开规则 数据库回源，设置并发上限
查询自己的反馈状态 直接从数据库查询，仍执行权限校验
创建唯一反馈 PostgreSQL 事务 + UNIQUE + 幂等，不能只依赖 Redis 锁
用户登录风控/限流 按风险策略拒绝、切换可靠备用机制或降低权限
发起付款/转账 不可绕过业务一致性和授权校验
启动批量索引 Worker 若锁用于防重复，应以持久化任务状态、租约/DB 约束作为最后一道防线

7.3 故障类型与响应原则

  1. 连接建立失败：可能网络、DNS、服务停机；短超时并有界重试。
  2. 读超时：结果可能未知；缓存 GET 可安全回源，但写命令尤其要关注“操作可能已经发生”。
  3. 连接池耗尽：应限制并发，排查未关闭连接和峰值。
  4. 内存不足：确认 maxmemory 与淘汰策略，不要把它误判为 Redis 完全停机。
  5. 缓存 Key 不存在：正常 miss，不是依赖故障。

需要隔离缓存依赖的错误，避免异常冒泡成整个应用的 500；但是数据库本身不可用时不能伪造业务成功。

7.4 熔断、重试和回退

  • 设置较短 Redis 网络超时（依据服务 SLO，不是固定数值）。
  • 限制 Redis 重试次数，指数退避与 Jitter，避免所有请求同步重试。
  • 熔断 Redis 探测，停止持续向故障实例发起大量请求。
  • 数据库回源增加并发上限和队列限制，防止流量转移引发级联故障。
  • 监控回源成功率与数据库连接池占用，必要时对非关键功能返回 503 或显示受限状态。

8. 缓存穿透、击穿、雪崩

穿透（Penetration）：大量查询不存在的记录，缓存长期 miss，数据库反复处理。可用短期负缓存、入参校验、布隆过滤器（有误判特性）、限流。

击穿（Stampede / Hot-key expiration）：一个热门 Key 到期，大批请求同时回源。可用请求合并（Singleflight）、短租约、提前刷新、Stale-While-Revalidate（前提是允许陈旧数据）。

雪崩（Avalanche）：大量 Key 同时到期或整个 Redis 不可用，大量请求一起回源。可为非强一致 Key 的 TTL 增加随机扰动，控制并发，预热缓存，并建立降级策略。

重要： 使用 Redis 锁减少热门 Key 的重复计算，并不能替代负载保护；锁竞争也可能导致所有请求排队。缓存刷新和业务写入要使用不同风险级别的锁策略。

9. Redis 锁的基本语义：竞争协调，不是最终数据证明

单实例 Redis 中的经典获取方式：

text
SET lock:document:001 <random-token> NX PX 30000

NX 要求 Key 不存在，PX 设置租约过期时间，随机 Token 证明本客户端是当前锁的持有者。这只能在锁有效期间协调访问，不保证相关数据库数据永远不会被其他进程修改。

错误的释放方式：

text
DEL lock:document:001

如果旧客户端暂停到锁过期，新的客户端已经重新取得锁，旧客户端再执行普通 DEL 可能删除新客户端的锁。

正确的释放方式是原子比较持有者 Token 并删除。Redis 8.4 起可使用 DELEX key IFEQ token；需兼容较早版本时可使用如下 Lua 脚本：

lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end

这里的原子性仅限 Redis 单次脚本执行及对应 Redis 数据，不自动扩展到 PostgreSQL 和外部 API。

9.1 锁应该加在哪里

用于缓存刷新互斥时：阻止上百个请求同时重复计算相同缓存，错过锁的请求可以等待短时间或直接采用允许的回退路径。

用于业务唯一性时：即使已经取得 Redis 锁，仍要在数据库中使用 UNIQUE / 事务 / 版本约束来兜底，保证竞争与故障情况下业务正确。

10. 锁过期与 Fencing Token

10.1 一个典型的锁失效竞态

text
A 取得锁（TTL 10 秒）
A 卡顿 / 暂停 20 秒
Redis 中 A 的锁过期
B 取得同一资源的新锁
B 更新数据库为版本 12
A 恢复并继续执行陈旧任务，尝试写版本 11 的结果

即使 A 发现自己无法再释放锁，A 之前或之后的副作用仍可能损害数据。这意味着“释放时检查 Token”只防止误删新锁，不等于防止过期持有者继续写入。

10.2 Fencing Token 是什么

为每次取得写入资格分配单调递增的序号，例如 41、42、43。受保护的资源（通常是数据库或受控存储服务）必须记录已接受的最高序号，并拒绝低于已接受序号的陈旧写入。

text
A: fence=41 ─── 延迟 ────────────────── 写入（拒绝：41 < 42）
B: fence=42 ─── 写入成功（资源已接受 42）

关键前提： Token 必须来自能为本资源保证单调性的可信协调源，且真正执行写操作的资源方必须执行 Token 检查。仅生成一个递增数但数据库忽略它，没有任何保护作用。以 Redis 单实例 INCR 生成 fencing 序号也必须评估其故障恢复和持久化语义，不能默认重启/切主后仍保持全局单调。

对数据库行更新，使用 UPDATE ... WHERE version = expected 这样的乐观锁往往比另建复杂分布式锁系统更直接。

11. 单实例锁与 Redlock 的限制

Redis 官方讨论了单实例锁的限制、主从异步复制导致的锁丢失风险，以及 Redlock 方案。Redlock 试图在多个相对独立节点上取得多数锁，以减少单节点故障的影响，但其正确性假设和极端时钟/故障条件存在争议。对于强一致业务数据，不能因为“使用了 Redlock”就省去数据库约束、事务与 fencing 检查。

若锁仅用于降低重复缓存刷新开销，允许偶发重复计算，单实例短租约可能已经足够；若用于防止资金重复划扣、订单重复落库等正确性要求极高的操作，应让数据库或具备清晰一致性承诺的协调服务承担最终裁决。

12. Redis 锁不能代替 UNIQUE 约束

设同一用户同一次确认只能生成一条反馈：

sql
CREATE TABLE feedback (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    confirmation_id TEXT NOT NULL,
    content TEXT NOT NULL,
    CONSTRAINT feedback_confirmation_unique
        UNIQUE (tenant_id, confirmation_id)
);

即使两个 Worker 同时执行 INSERT，数据库唯一约束仍会阻止出现同一 (tenant_id, confirmation_id) 的重复行。Redis 锁则可能因为 TTL 过期、连接失败、切主或程序没有正确遵守锁协议而失效。

数据库 UNIQUE 表达的是持久化不变量（Invariant）；Redis 锁表达的是协作式互斥意图（Coordination）。两者职责不同。

ON CONFLICT 可以处理唯一冲突：

sql
INSERT INTO feedback (tenant_id, confirmation_id, content)
VALUES (:tenant_id, :confirmation_id, :content)
ON CONFLICT (tenant_id, confirmation_id) DO NOTHING;

但“冲突就忽略”还不够：必须核对同一幂等键对应的旧记录是否与此次请求内容一致，否则用户用相同确认 ID 发送不同内容，可能被错误地当作同一操作。

13. Redis 锁不能代替数据库事务

假设一次确认操作需要：写入反馈、更新草稿状态、生成审计记录。

text
BEGIN
  INSERT INTO feedback ...
  UPDATE feedback_drafts SET status='CONFIRMED' ...
  INSERT INTO audit_log ...
COMMIT

如果第三步失败，而这些修改属于同一个 PostgreSQL 事务，那么整个事务可以 ROLLBACK。只有 Redis 锁不能让已完成的第一、第二次 SQL 自动撤销。

13.1 原子性覆盖范围

机制 能原子保护什么 不能保护什么
Redis SET NX PX 获取一个键的竞争租约 PostgreSQL 多表提交
Redis Lua / 原子命令 Redis 上该操作的原子执行 与外部数据库的联合事务
PostgreSQL UNIQUE 被约束的唯一性不变量 未定义在该约束里的业务正确性
PostgreSQL 事务 同一事务内的数据库修改 事务外发送的邮件和 HTTP 调用
乐观锁 WHERE version = ? 防止同版本的并发覆盖 未执行检查的其他写入路径
Transactional Outbox 业务变更与待发布事件同库原子写入 下游 exactly-once 执行（需去重）

13.2 为什么锁不能保证完整业务结果

即使进程完全独占某个 Redis 锁，它也可能在写完一张数据库表后崩溃。Redis 不知道 SQL 事务是否完成，也不能对 PostgreSQL 下达跨库回滚。

14. PostgreSQL 并发控制的几种工具

14.1 唯一约束

适合“同一用户 + 确认 ID 只能有一条记录”或“业务单号不可重复”的不变量。

14.2 事务

适合需要全成功或全失败的多次数据库操作。注意避免在事务中等待用户审批或进行长时间网络调用，否则可能长时间占用行锁和连接。

14.3 乐观锁

对于对象更新时的冲突检测：

sql
UPDATE documents
SET body = :new_body, version = version + 1
WHERE id = :id AND version = :expected_version;

检查受影响行数：更新到 1 行代表版本仍匹配；0 行代表对象不存在或版本发生变化，需进一步查询并按业务规则处理。

14.4 行级锁

sql
BEGIN;
SELECT id, status FROM tasks WHERE id = :id FOR UPDATE;
-- 验证业务状态，再进行相关写入
COMMIT;

SELECT ... FOR UPDATE 让其他更新/锁定同一行的事务按数据库规则等待，但应尽量保持事务短小。PostgreSQL 默认隔离级别和较高级别的事务隔离语义不同，出现序列化失败时需要正确重试整个事务，而不是只重试最后一条 SQL。

14.5 Advisory Lock

PostgreSQL 还提供由应用定义含义的 Advisory Lock，可用于某些不方便由行锁表达的协调，但它同样依赖调用方正确使用，不能取代唯一约束和事务。

15. 跨系统原子性：不能假设数据库与 Redis 同时成功

text
PostgreSQL COMMIT 完成
    ↓
Redis DEL cache:key 失败

这里 DB 已是新值，但缓存可能仍然有旧值。直接回滚 PostgreSQL 已提交事务通常不可能。需要事先选择一致性方案：TTL 容忍、版本化读、可靠事件失效、或强一致时直接查权威数据。

若业务还要发送 Kafka 事件或调用外部服务，Transactional Outbox 的基本思想是：

text
同一个 PostgreSQL 事务：
  更新业务记录
  INSERT outbox_event(...)
COMMIT

独立发布器：读取 outbox → 发布事件 → 标记已发送

这样可以降低“业务提交成功而发布事件永久丢失”的风险；但发布器崩溃后可能重复发布，因此接收方仍要使用幂等键和唯一约束。Outbox 不能直接使 Redis、Kafka 和 PostgreSQL 组成一个原子事务。

16. 典型故障场景矩阵

故障场景 可观察现象 业务风险 主要措施
Key TTL 到期 Redis miss DB 读量增加 回源、回填、限流
大量热点 Key 同时过期 DB 峰值激增 超时、雪崩 TTL 抖动、Singleflight、背压
Redis 整体不可用 连接错误/超时 缓存与锁不可用 读降级、关键写入 fail closed 或走 DB 正确性路径
数据库更新成功但 DEL 失败 旧 Key 未删除 读到旧值 版本键、异步补偿、短 TTL
旧读在 DEL 后回填 旧值重新出现 不一致窗口延长 版本化 Key、版本校验
A 的 Redis 锁过期、B 获锁 两个 Worker 可能继续执行 双写、旧结果覆盖 业务版本控制、fencing、事务
Worker 取得锁后进程崩溃 锁最终过期 长任务中断 持久任务状态、租约恢复、幂等
重复 HTTP 请求 同一确认重复 重复业务记录 幂等键 + UNIQUE + 事务
Redis 重启失去锁 两个进程以为独占 互斥失效 不以 Redis 锁作为唯一正确性保证
DB 事务提交后外部事件发送失败 业务成功，通知缺失 系统状态不一致 Outbox + 重试 + 消费幂等
PostgreSQL 失败 权威资料不可读 无法确认正确结果 失败显式告知，不能用任意旧缓存伪造成功

17. FastAPI + Redis 异步读缓存的代码示意

下面展示运行时设计，不声称单独粘贴即可形成完整生产服务。示例假设依赖 redis（redis-py）、sqlalchemy、asyncpg、fastapi，并已定义 ORM 模型及认证机制。

python
import json
import logging
import redis.asyncio as redis
from redis.exceptions import RedisError
from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

logger = logging.getLogger(__name__)

async def get_public_rule(
    rule_id: str,
    cache: redis.Redis,
    db: AsyncSession,
):
    cache_key = f"public-rule:{rule_id}"
    try:
        cached = await cache.get(cache_key)
        if cached is not None:
            return json.loads(cached)
    except (RedisError, TimeoutError) as exc:
        logger.warning("redis_cache_read_unavailable: %s", type(exc).__name__)

    # Rule 是示意 ORM 类型，需由实际项目定义。
    row = (await db.execute(
        select(Rule).where(Rule.id == rule_id)
    )).scalar_one_or_none()
    if row is None:
        return None
    result = {"rule_id": row.id, "version": row.version, "text": row.text}
    try:
        await cache.set(cache_key, json.dumps(result, ensure_ascii=False), ex=30)
    except (RedisError, TimeoutError) as exc:
        logger.warning("redis_cache_write_unavailable: %s", type(exc).__name__)
    return result

这个 Cache-Aside 示例只能视为基础最终一致方案。 写入后删除缓存仍有第 4 章所述竞态。如果业务必须看到指定资料版本，应在数据库中查询权威版本，并使用版本化 Key 或其他明确的一致性协议。

17.1 正确管理连接池

python
from contextlib import asynccontextmanager
from fastapi import FastAPI
import redis.asyncio as redis

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.redis = redis.Redis.from_url(
        "redis://localhost:6379/0",
        decode_responses=True,
        socket_connect_timeout=0.3,
        socket_timeout=0.3,
    )
    try:
        yield
    finally:
        await app.state.redis.aclose()

app = FastAPI(lifespan=lifespan)

Redis 客户端与连接池可以在应用生命周期内复用；Redis Pipeline / PubSub 等具有独立状态的对象不应无条件跨任务共享。数据库 Engine 可复用，但并发任务应使用独立的 SQLAlchemy Session。

17.2 Redis 单实例锁的安全释放

python
import secrets

UNLOCK_SCRIPT = """
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
"""

async def try_acquire(redis_client, name: str, ttl_ms: int = 15000):
    token = secrets.token_hex(16)
    acquired = await redis_client.set(name, token, nx=True, px=ttl_ms)
    return token if acquired else None

async def release_if_owner(redis_client, name: str, token: str):
    return bool(await redis_client.eval(UNLOCK_SCRIPT, 1, name, token))

限制： 获取锁后并不是“安全执行任何数据库操作”的证明。应给操作设置独立截止时间，并使用 DB 事务、版本或 fencing 检查作为最终正确性边界。对于 Redis 8.4+ 也可评估 DELEX key IFEQ token。锁释放期间 Redis 失联，租约可能持续到自然到期；不能靠本地 finally 保证 Redis 一定收到释放操作。

18. 数据库模型和 SQL 示例

18.1 版本记录和当前指针

sql
CREATE TABLE document_versions (
    document_id TEXT NOT NULL,
    version BIGINT NOT NULL CHECK (version > 0),
    content TEXT NOT NULL,
    source_hash TEXT NOT NULL,
    index_status TEXT NOT NULL CHECK (index_status IN ('DRAFT','BUILDING','READY','FAILED')),
    PRIMARY KEY (document_id, version)
);

CREATE TABLE document_heads (
    document_id TEXT PRIMARY KEY,
    published_version BIGINT NOT NULL,
    FOREIGN KEY (document_id, published_version)
        REFERENCES document_versions(document_id, version)
);

数据库外键能保证 published_version 指向现存版本，但“该版本是否 READY”需要发布事务中的业务校验、状态转换规则或进一步数据库机制约束；不能误以为上述外键自动保证索引就绪。

18.2 CAS 更新版本指针

sql
UPDATE document_heads
SET published_version = :new_version
WHERE document_id = :doc_id AND published_version = :expected_version;

若更新行数为 0，说明版本不匹配或目标不存在，需要重新读取或返回冲突。实际发布事务还要在同一事务中检查新版本的准备状态。

18.3 写入与幂等

sql
CREATE TABLE feedbacks (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id TEXT NOT NULL,
    confirmation_id TEXT NOT NULL,
    body TEXT NOT NULL,
    CONSTRAINT uq_feedback_confirmation UNIQUE(tenant_id, confirmation_id)
);

仅有 Redis 锁时无法覆盖“持锁进程崩溃、锁过期、新 Worker 接管、旧请求重试”的全部场景；数据库约束则可以在每一次写入时实际检查唯一性。

19. 可观测性和验证方法

建议把 Redis、数据库和业务状态分别记录，避免把“性能下降”误判为“业务错误”：

监控指标 说明
Redis hit / miss 命中率及其变化
Redis timeout / connection error 依赖是否健康
PostgreSQL QPS / p95 / pool wait 故障回源是否压垮数据库
Cache fallback count 缓存失败时有多少请求回源
Cache stale-version count 缓存版本与权威版本不匹配次数
Lock contention / lease expired 协调性能及过期风险
Unique conflict / idempotent replay 业务重复提交情况
Retry count / breaker state 降级是否变成重试风暴
Document index version mismatch RAG 资料与索引是否混用版本

19.1 正式环境的测试矩阵

  1. Redis 关闭后普通规则查询能否正确从 PostgreSQL 返回。
  2. Redis 关闭后业务确认是否仍由数据库唯一约束保护。
  3. 资料发布 v13 后，旧 v12 的长尾读取能否覆盖新版本缓存。
  4. 在 DB 提交后、缓存 DEL 前强制进程退出会怎样。
  5. Redis 锁过期后，旧 Worker 继续执行会不会覆盖新结果。
  6. 人为制造大量热点 Key 失效，数据库负载是否被限流控制。
  7. Redis 返回超时，但 SET 操作实际可能已执行时，重试是否安全。
  8. 数据库事务第三步失败后，前面两个数据库修改是否全部回滚。
  9. 两个重复反馈请求并发进入，最终是否只有一条业务记录。
  10. RAG 新版本索引尚未 READY 时，是否仍使用已发布旧版本。

可以使用 Docker Compose 启动真实 PostgreSQL/Redis，并配合 Toxiproxy、网络限流和进程终止进行故障注入。离线模拟器的通过结果不能取代真实 Redis 的 TTL、复制、主从切换、多连接并发测试。

20. 常见认识错误

  • “设置 TTL 就不会读到旧数据”——错误。 TTL 未到时旧值仍可能被读到，更新失效也有并发窗口。
  • “缓存 miss 就是 Redis 故障”——错误。 miss 是正常结果，网络或服务器错误是异常。
  • “写数据库后 DEL 缓存就保证强一致”——错误。 在途旧读取可能晚回填旧值。
  • “Redis 原子命令保证整个业务原子性”——错误。 原子性范围仅是对应 Redis 操作。
  • “Redis 锁没有过期就一定只有一个 Worker 写数据库”——不能保证。 复制、暂停、长请求与故障模型必须纳入分析。
  • “使用 Redlock 就不需要唯一约束”——错误。 锁协调与业务不变量是不同层面的保证。
  • “数据库事务能撤销邮件/外部 API”——错误。 它只能管理相应数据库事务覆盖的修改。
  • “Redis 不可用时放开所有限制最能保证可用性”——危险。 不同业务应采用不同 fail-open/fail-closed 策略。
  • “版本化 Key 必然实现最新读”——错误。 仍要证明当前版本发现过程的可靠性。
  • “Redis 故障就可以忽略测试”——错误。 正常状态与故障状态都应验证。

21. 可运行的离线教学实现与验证

为了将本节的抽象原理变成可验证的行为，附录中的单文件 Python 示例使用：

  • FakeRedis 模拟 Key、TTL、SET NX、原子 token 条件释放及 Redis 不可用；
  • sqlite3 模拟权威数据库、版本号、唯一约束与事务；
  • read_versioned() 先获取权威资料版本，只缓存对应版本 Key；
  • unittest 覆盖 TTL 到期、旧版本缓存、Redis 故障回源、CAS 更新、幂等重复请求、锁过期和错误释放。

**测试性质：**它验证教学代码在单进程、模拟时钟与 SQLite 条件下的预期结果，不宣称已验证真实 Redis 的集群锁、网络分区、主从切换，也不宣称已验证 PostgreSQL 的行锁与隔离等级。特别注意 read_versioned() 每次读取数据库版本与内容，不用于演示缓存加速效果，其设计意图只是展示“旧版本 Key 不会被误认为新版本”的一个较容易推理的边界。

以下为完整可运行源码；保存为 redis_failure_demo.py 并执行 python redis_failure_demo.py 即可运行离线测试。无需第三方依赖。

python
"""离线教学模拟：TTL、缓存失效、数据库事务与租约 token。
不连接真正 Redis / PostgreSQL，不是生产级分布式锁。
"""
import sqlite3
import unittest
from dataclasses import dataclass

class CacheUnavailable(Exception):
    pass

class VersionConflict(Exception):
    pass

@dataclass
class FakeClock:
    now: float = 100.0
    def advance(self, seconds: float) -> None:
        self.now += seconds

class FakeRedis:
    def __init__(self, clock: FakeClock):
        self.clock, self.available, self.data = clock, True, {}
    def _check(self):
        if not self.available:
            raise CacheUnavailable('Redis unavailable')
    def _current(self, key):
        row = self.data.get(key)
        if row and row[1] is not None and row[1] <= self.clock.now:
            self.data.pop(key, None)
            return None
        return self.data.get(key)
    def get(self, key):
        self._check()
        row = self._current(key)
        return None if row is None else row[0]
    def set(self, key, value, ex=None, nx=False):
        self._check()
        if nx and self._current(key) is not None:
            return False
        self.data[key] = (value, self.clock.now + ex if ex is not None else None)
        return True
    def delete(self, key):
        self._check()
        self.data.pop(key, None)
    def release_if_owner(self, key, token):
        self._check()
        if self.get(key) == token:
            self.delete(key)
            return True
        return False

class DocStore:
    def __init__(self):
        self.db = sqlite3.connect(':memory:', isolation_level='DEFERRED')
        self.db.executescript('''
            CREATE TABLE docs (id TEXT PRIMARY KEY, version INTEGER NOT NULL CHECK(version>0), content TEXT NOT NULL);
            CREATE TABLE feedback (id INTEGER PRIMARY KEY, tenant_id TEXT NOT NULL, confirm_id TEXT NOT NULL, body TEXT NOT NULL, UNIQUE(tenant_id, confirm_id));
            INSERT INTO docs VALUES ('rule', 1, '生命值为4');
        ''')
    def read(self, document_id):
        return self.db.execute('SELECT version,content FROM docs WHERE id=?', (document_id,)).fetchone()
    def update(self, document_id, expected_version, content):
        with self.db:
            cur = self.db.execute('UPDATE docs SET version=version+1,content=? WHERE id=? AND version=?', (content, document_id, expected_version))
            if cur.rowcount != 1:
                raise VersionConflict('Version changed')
    def submit_feedback(self, tenant_id, confirm_id, body):
        with self.db:
            try:
                self.db.execute('INSERT INTO feedback(tenant_id,confirm_id,body) VALUES(?,?,?)',(tenant_id,confirm_id,body))
            except sqlite3.IntegrityError:
                old = self.db.execute('SELECT body FROM feedback WHERE tenant_id=? AND confirm_id=?',(tenant_id,confirm_id)).fetchone()
                if old is None or old[0] != body:
                    raise ValueError('Same idempotency key with different payload')
            return self.db.execute('SELECT id FROM feedback WHERE tenant_id=? AND confirm_id=?',(tenant_id,confirm_id)).fetchone()[0]
    def count_feedback(self):
        return self.db.execute('SELECT COUNT(*) FROM feedback').fetchone()[0]
    def close(self):
        self.db.close()

def read_versioned(store: DocStore, cache: FakeRedis, doc_id: str, ttl=60):
    """每次先读数据库版本与内容，保证缓存键匹配此版本；不减少 DB 读取。"""
    row = store.read(doc_id)
    if row is None:
        return None
    version, actual_content = row
    key = f'doc:{doc_id}:v{version}'
    try:
        cached = cache.get(key)
        if cached is not None:
            return version, cached
        cache.set(key, actual_content, ex=ttl)
    except CacheUnavailable:
        pass
    return version, actual_content

class Tests(unittest.TestCase):
    def setUp(self):
        self.clock = FakeClock()
        self.cache = FakeRedis(self.clock)
        self.store = DocStore()
    def tearDown(self):
        self.store.close()
    def test_cache_ttl(self):
        self.cache.set('a', 1, ex=2)
        self.assertEqual(self.cache.get('a'), 1)
        self.clock.advance(2)
        self.assertIsNone(self.cache.get('a'))
    def test_overwrite_replaces_ttl_in_simulation(self):
        self.cache.set('a', 1, ex=2)
        self.cache.set('a', 2)
        self.clock.advance(3)
        self.assertEqual(self.cache.get('a'),2)
    def test_cache_miss_rehydrates(self):
        self.assertEqual(read_versioned(self.store,self.cache,'rule'),(1,'生命值为4'))
        self.assertEqual(self.cache.get('doc:rule:v1'),'生命值为4')
    def test_version_update_never_reads_old_key(self):
        read_versioned(self.store,self.cache,'rule')
        self.store.update('rule',1,'生命值为5')
        self.assertEqual(read_versioned(self.store,self.cache,'rule'),(2,'生命值为5'))
        self.assertEqual(self.cache.get('doc:rule:v1'),'生命值为4')
    def test_cache_unavailable_database_fallback(self):
        self.cache.available=False
        self.assertEqual(read_versioned(self.store,self.cache,'rule'),(1,'生命值为4'))
    def test_no_document(self):
        self.assertIsNone(read_versioned(self.store,self.cache,'missing'))
    def test_version_conflict(self):
        self.store.update('rule',1,'新内容')
        with self.assertRaises(VersionConflict):
            self.store.update('rule',1,'覆写')
    def test_idempotent_same_key(self):
        a=self.store.submit_feedback('u1','k1','正文')
        b=self.store.submit_feedback('u1','k1','正文')
        self.assertEqual(a,b)
        self.assertEqual(self.store.count_feedback(),1)
    def test_idempotency_key_payload_conflict(self):
        self.store.submit_feedback('u1','k1','正文')
        with self.assertRaises(ValueError):
            self.store.submit_feedback('u1','k1','改写')
        self.assertEqual(self.store.count_feedback(),1)
    def test_tenant_scoped_unique(self):
        self.store.submit_feedback('u1','k1','正文')
