Python 基础与异步编程（五）：超时、取消、异常传播、资源清理与并发限制

对应学习目标：超时、取消、异常传播、资源清理和并发限制；一个模型请求很慢时，其他请求仍能得到响应。

技术范围：Python 3.13、asyncio、FastAPI、HTTPX；核心机制也适用于相近的 Python 3.11+ 版本。代码中没有依赖真实付费模型的示例可本地运行。

核心结论：异步系统是否可靠，不只取决于用了多少 async def，更取决于等待是否会让出事件循环、超时与取消能否正确传播、资源能否释放、容量是否受到限制，以及失败能否被准确表示。

1. 为什么“一个慢模型请求”可能拖慢整个服务

想象一个服务同时收到三次请求：

  • A 请求调用模型，响应需 8 秒。
  • B 请求查询账户信息，正常需要 50 毫秒。
  • C 请求健康检查，正常需要 5 毫秒。

正确的异步执行是：A 的网络请求处于等待时，事件循环去处理 B、C。A 耗时长，不应天然导致 B、C 也耗时 8 秒。

text
时间 →
A:  [请求模型 ------------------等待网络------------------ 返回]
B:       [校验 → 查询 → 返回]
C:               [健康检查 → 返回]

但以下代码把事件循环线程直接阻塞住：

python
import time

async def ask_model_wrong() -> str:
    time.sleep(8)  # 阻塞当前线程，而不是异步等待
    return "回答"

即使外层是 async def，只要执行的是同步阻塞操作，事件循环就无法按预期调度其他协程。同样有问题的调用包括在事件循环中直接运行同步 requests.get()、大规模纯 Python 计算、阻塞式 SDK 方法。

非阻塞的模拟等待则是：

python
import asyncio

async def ask_model() -> str:
    await asyncio.sleep(8)  # 当前 Task 挂起，事件循环可以运行其他任务
    return "回答"

但是，这只解决“不阻塞事件循环”的问题，仍需要解决另外两类风险：

  1. 资源占满：即使每个请求都异步等待，数千个挂起请求仍可能消耗连接、内存和上游 API 配额。
  2. 无限等待/故障扩散：模型失去响应、网络半开、重试风暴等，会使请求一直积压。

所以真正的服务设计是：非阻塞 I/O + 合理超时 + 正确取消 + 资源清理 + 并发与排队限制 + 故障分类。

1.1 两种“慢”必须区分

现象 可能原因 关键处理手段
某个模型请求耗时很长，但其他请求正常 模型生成慢或网络慢 网络超时、请求总期限、限流、响应状态
一个请求变慢后，其他接口也同时明显卡住 同步阻塞、事件循环饥饿、连接池/线程池耗尽 排查同步调用与 CPU 占用、资源池隔离、调整容量

异步不保证所有请求都快：如果一个模型接口有全局并发槽位限制，那么后续模型请求可能在等待该槽位；这与整个事件循环被阻塞不是一回事。健康检查和不依赖模型的 API 仍应能正常处理。

2. 超时（Timeout）不是单一的一个数字

“设置 30 秒超时”可能包含许多不同含义，必须知道时间限制施加在哪一层。

2.1 常见超时种类

类型 控制的阶段 常见意义
连接超时 connect 建立到上游主机的连接 网络不可达或建立连接过慢
读取超时 read 等待接收下一批响应数据 服务器长时间未发送数据
写入超时 write 向网络写入请求数据 上传或发送受阻
连接池等待超时 pool 等待取得可用连接 已达到连接数限制
业务总超时 deadline 从开始处理到要求结束的总时间 包括排队、网络等待、业务处理等
代理/网关超时 反向代理或负载均衡器一侧 即使应用内部允许更久，客户端也可能先断开
用户交互超时 客户端愿意等待多久 超过后提示用户、重试或转成后台任务

HTTPX 的四种网络阶段超时是 connect/read/write/pool。其中 read timeout 通常表示两次数据接收之间允许的最大无数据时长，不是整个流式回答的总时长。因此一个不停输出数据的模型流，可能持续超过单个读取超时而不触发它。

python
import httpx

timeouts = httpx.Timeout(
    connect=3.0,
    read=20.0,
    write=5.0,
    pool=2.0,
)

limits = httpx.Limits(
    max_connections=30,
    max_keepalive_connections=15,
)

# 应在应用生命周期中创建并复用，而非每个请求都新建
client = httpx.AsyncClient(timeout=timeouts, limits=limits)
# 用完后必须 await client.aclose()，详见资源清理部分

这些参数是解释机制的示例值，应该根据模型服务、并发预算、网络环境与实际监控调整。

2.2 Python asyncio.timeout()：限定一个操作块的执行时间

python
import asyncio

async def call_model() -> str:
    await asyncio.sleep(2)
    return "完成"

async def main() -> None:
    try:
        async with asyncio.timeout(0.3):
            result = await call_model()
            print(result)
    except TimeoutError:
        print("模型请求超过允许时间")

asyncio.run(main())

asyncio.timeout() 在超过期限时，会对当前 Task 发起取消，随后由上下文管理器把其内部触发的取消转换成可在外部捕获的 TimeoutError。

因此通常应把 except TimeoutError 放在 async with 外面。在上下文内部，代码首先遭遇的是取消，且清理操作可能影响最终耗时。

2.3 asyncio.wait_for()：等待指定对象并设置期限

python
result = await asyncio.wait_for(call_model(), timeout=0.3)

这个形式也可能触发被等待对象的取消，并在超时后抛出 TimeoutError。

常见区别：

  • asyncio.timeout() 适合包裹一个包含多个 await 的业务代码块。
  • asyncio.wait_for() 适合为一次等待设置超时。
  • 两者都依赖正常的异步取消机制；不保证到达时限的那个时刻，底层操作已经物理停止。
  • wait_for() 等待取消完成，所以实际返回耗时可能略长于指定值。

2.4 总预算与局部预算的叠加

例如业务允许最多 12 秒：

text
HTTP 业务总预算：12 秒
   ├── 等候并发槽位：最多受到总预算约束
   ├── 建立上游连接：单次 3 秒
   ├── 每次等待网络数据：20 秒（但业务总预算可更早结束）
   └── 结果整理和保存：同样占用总预算

业务总预算应当包含排队时间，而不只是获得信号量之后的模型调用时间，否则高负载时可能出现“排队 2 分钟 + 模型调用 12 秒”的情况。

python
async def guarded_model_call(
    semaphore: asyncio.Semaphore,
    prompt: str,
) -> str:
    async with asyncio.timeout(12):  # 超时也覆盖等待 semaphore
        async with semaphore:
            return await call_model_with_prompt(prompt)

call_model_with_prompt 代表真正的异步模型客户端调用。这里没有定义它，是展示组合方式的示意代码。

2.5 单一 deadline 比层层重置 timeout 更可靠

如果调用链是路由 → Service → 工具 A → 模型 B，每层重新给 30 秒，就可能产生超过预期的整体耗时。可以在入口形成单调时钟的截止时间，并向下传递剩余预算：

python
import asyncio

async def parent_operation() -> None:
    loop = asyncio.get_running_loop()
    deadline = loop.time() + 5.0

    async with asyncio.timeout_at(deadline):
        await asyncio.sleep(0.4)
        await asyncio.sleep(0.5)

loop.time() 是单调时钟，适合计算持续时间；不要直接用可能被系统校时改变的墙上时间计算内部耗时。

3. 取消（Cancellation）到底发生了什么

3.1 task.cancel() 是“请求取消”，不是强制杀死线程

python
import asyncio

async def slow_job() -> None:
    try:
        await asyncio.sleep(100)
    finally:
        print("清理已经执行")

async def main() -> None:
    task = asyncio.create_task(slow_job())
    await asyncio.sleep(0.01)
    task.cancel()

    try:
        await task
    except asyncio.CancelledError:
        print("任务已被取消")

asyncio.run(main())

cancel() 发起取消请求。协程在后续适当的挂起点观察到取消，通常抛出 asyncio.CancelledError，执行 finally，然后任务结束。

如果协程一直运行 CPU 密集型循环或 time.sleep()，可能迟迟没有机会接收取消。此时“已经调用 cancel()”不代表“工作已经停止”。

3.2 CancelledError 不是普通业务错误

在现代 Python 中，asyncio.CancelledError 直接继承自 BaseException，不是 Exception：

python
try:
    await some_operation()
except asyncio.CancelledError:
    # 可记录状态、释放资源，但通常必须继续抛出
    raise
except Exception as exc:
    # 处理其他实际执行故障
    handle_error(exc)

不应该为了“防止报错”而吞掉取消：

python
# 错误：破坏取消语义，结构化并发和超时可能失效
try:
    await some_operation()
except asyncio.CancelledError:
    return "假装成功"

更常见的正确模式是直接使用 try/finally 做清理，让取消自然传播：

python
async def job() -> None:
    resource = await open_resource()
    try:
        await work(resource)
    finally:
        await resource.aclose()

其中 open_resource 与 work 是示意函数。

3.3 取消与客户端断开不是完全等价的

浏览器关闭、HTTP 连接断开，不意味着所有 Web 框架、所有响应形式都会立刻取消当前的路由协程。具体行为依赖 ASGI 服务器、框架、代理和响应方式。

对于流式响应，需要留意断开检测、发送任务取消、生成器清理；对于不应受客户端断开影响的持久任务，应保存任务记录并使用独立 Worker，而非简单 create_task() 后丢弃引用。

3.4 取消线程池里的工作有什么局限

python
result = await asyncio.to_thread(blocking_function)

取消正在 await 的 Task，通常不能直接停止已在线程池中运行的同步函数。线程可能仍在运行、消耗资源或继续产生副作用。这是为什么数据库写入、文件删除等操作不能仅靠 task.cancel() 保证不发生的原因。

对无法中途停止的工作，应该使用明确的协作终止机制、可检查的取消标志或独立可恢复任务架构。

3.5 asyncio.shield() 的真正含义

shield(task) 可以让被等待的内部任务不因外层等待者取消而直接受到同一次取消传播影响，但外层等待仍会抛出 CancelledError。

这不等于“该任务永远不会取消”，也不是常规请求必须使用的保护伞。对数据库一致性，应优先使用事务、幂等记录和可靠后台任务；对长运行任务，应保存强引用并明确生命周期。

4. 异常传播：哪一层应该处理哪个问题

一次模型请求大致可能经历：

text
FastAPI Router
  ↓
ChatService
  ↓
ModelClient / HTTPX
  ↓
上游模型 API

如果上游模型超时，HTTPX 可能抛出 httpx.ReadTimeout 或其他 httpx.TimeoutException。Service 可以把上游技术异常转换为自己的领域异常，例如 ModelTemporarilyUnavailable。Router 最后负责决定 HTTP 响应状态码与面向用户的错误内容。

4.1 区分不同类型的失败

情况 典型异常/信号 常见处理
连接模型失败 httpx.ConnectError 记录上游不可用，可有限重试
读取上游超时 httpx.ReadTimeout 报告模型响应超时，检查是否可安全重试
业务总超时 TimeoutError 结束当前请求，返回明确失败原因
超出上游限流 HTTP 429 按 Retry-After 和预算退避；不能无限重试
上游 5xx httpx.HTTPStatusError 根据请求幂等性决定重试
模型输出格式无效 解析/验证错误 单独归类，不与网络故障混为一谈
用户或服务器取消 asyncio.CancelledError 清理后传播，不伪装成功
本地程序 Bug 其他异常 记录诊断信息，不能一概归类为超时

应避免：

python
try:
    return await model_call()
except Exception:
    return {"answer": "模型没有回答"}

这里把格式错误、数据库错误、编程错误和网络错误全部掩盖成同一种“无答案”，造成数据不可信和排障困难。

更好的方式是先在 Service 中建立稳定的错误分类，再由 Router 转换成 HTTP 错误。若业务本身已经定义了清晰的返回联合类型，也可以使用结果对象表达可预期失败。

4.2 raise ... from ... 保留根因

python
class UpstreamModelError(RuntimeError):
    pass

async def request_model(client):
    try:
        response = await client.get("https://example.com/")
        response.raise_for_status()
        return response.text
    except httpx.TimeoutException as exc:
        raise UpstreamModelError("模型网络调用超时") from exc

使用该片段时需要 import httpx。raise ... from exc 保留异常链，便于日志追踪真实根因。

4.3 TaskGroup 与 gather 的异常传播区别

asyncio.TaskGroup 以结构化方式管理子任务。通常当一个子任务抛出非取消异常，它会取消尚未结束的兄弟任务，等待结束，然后把异常作为 ExceptionGroup 抛出。

python
import asyncio

async def failed():
    await asyncio.sleep(0.01)
    raise ValueError("模拟错误")

async def sibling():
    try:
        await asyncio.sleep(10)
    finally:
        print("兄弟任务执行清理")

async def main():
    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(failed())
            group.create_task(sibling())
    except* ValueError as errors:
        print("捕获业务异常：", len(errors.exceptions))

asyncio.run(main())

相对地，asyncio.gather(..., return_exceptions=False) 在某个子任务抛异常时，会向等待者传播异常，并不保证自动取消其他正在运行的兄弟任务。需要根据应用语义选择合适机制。

5. 资源清理：取消时最容易出错的部分

一个模型接口可能使用多个有限资源：

  • 网络连接和 HTTP 连接池；
  • 数据库连接与数据库事务；
  • Semaphore 信号量额度；
  • StreamingResponse / SSE 生成器与上游流；
  • 缓冲队列、临时文件和应用内 Task。

这些资源的生命周期应当清晰且可验证。

5.1 try/finally

python
resource = await create_resource()
try:
    await use_resource(resource)
finally:
    await resource.aclose()

即使 use_resource 抛异常或收到取消，仍会尝试执行清理。注意：异步清理本身也是可等待操作，也可能失败或在某些情况下再次被取消。因此并不能把 finally 理解成“任何故障下保证完成全部外部操作”。

5.2 async with：把资源与代码块绑定

python
import asyncio

limiter = asyncio.Semaphore(3)

async def limited_call():
    async with limiter:
        await asyncio.sleep(0.1)

使用 async with 可以在离开上下文时自动释放信号量额度；不建议分散在多个分支中手工 acquire/release，避免异常路径漏释放。

5.3 HTTP 客户端应当复用并在关闭服务时释放

错误模式：每次请求都新建 httpx.AsyncClient，增加握手、连接开销，还容易漏掉 aclose()。

更合适的是在 FastAPI 应用生命周期内创建：

python
from contextlib import asynccontextmanager
import httpx
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with httpx.AsyncClient(
        timeout=httpx.Timeout(20.0, connect=3.0),
        limits=httpx.Limits(max_connections=30),
    ) as client:
        app.state.http = client
        yield

app = FastAPI(lifespan=lifespan)

生命周期里的 yield 之前用于初始化，之后用于释放资源。若代码包含独立后台 Worker，它们的生命周期需要另外设计；FastAPI lifespan 不会替其他进程自动管理资源。

5.4 数据库 Session 不应不受控地共享

通常应为一个请求或一个独立并发任务创建独立的 SQLAlchemy AsyncSession，在结束时关闭或回收；取消与异常发生时还要确保事务正确回滚。共享一个 Session 给互相并发的 Task 可能产生状态和事务竞争。

5.5 流式响应必须处理异常结束

在 SSE / 流式模型输出场景，应区分：

  • 正常完成：发送最终结束事件；
  • 可处理错误：发送带错误代码的终止事件（前提是连接仍可用）；
  • 客户端断开：停止相关处理并关闭上游流；
  • 已发送 HTTP 响应头后失败：不能再随意把 HTTP 状态码改成 500；
  • 超时结束：明确是整个生成超时，还是等待下一块数据超时。

不能假定 try/finally 一定足以完成所有跨系统的清理和撤销；已产生的外部副作用需要用事务、业务幂等和补偿机制处理。

6. 并发限制：Semaphore、连接池和排队是三个问题

6.1 Semaphore 限制正在执行的操作数

python
import asyncio

semaphore = asyncio.Semaphore(3)

async def call_model(prompt: str) -> str:
    async with semaphore:
        await asyncio.sleep(0.5)
        return f"回答：{prompt}"

该代码在同一进程中的这个信号量实例上，最多允许 3 个协程同时进入被保护的代码段；其他调用者异步等待额度。

信号量并不等于：

  • 进程间/多机器的全局限流器；
  • 每秒请求次数（RPS）限流器；
  • 自动限制等待队列长度；
  • 根据用户 ID 的公平排队；
  • 上游 HTTP 连接池的最大连接数；
  • 对 CPU 密集计算的自动加速。

6.2 连接池限制与模型并发上限不是同一回事

httpx.Limits(max_connections=30) 控制客户端连接池容量，不等于“最多向模型提交 30 个完整推理任务”。部分请求可能复用连接、使用 HTTP/2 多路复用，或者在其他阶段等待。

因此常采用两个不同层次：

text
用户请求
  ↓
业务模型并发上限（Semaphore）
  ↓
HTTPX 网络连接池（Limits + pool timeout）
  ↓
模型服务 / 网关（其自身的配额与限流）

6.3 排队本身也需要容量管理

Semaphore(3) 只限制同时执行的数量。若同一时刻有 10000 个请求，其他 9997 个可能都挂起等待信号量，导致内存和请求处理资源累积。

因此还需要：

  1. 排队等待超时：在排队等待阶段就执行总期限。
  2. 有界队列：限制系统愿意接纳的等待任务数量。
  3. 过载拒绝：容量超过阈值时尽早返回 429 或 503，并尽可能提供重试建议。
  4. 独立容量池：模型接口与健康检查、账户接口、数据库接口不应无条件共用同一个长时间占用的模型信号量。
  5. 全局容量控制：多 Worker 进程各持有一个 Semaphore(3)，实际总并发可能接近 3 × 进程数，要与上游整体配额协调。

6.4 限制应该放在哪个层级

级别 常见实现 目的
单次请求 Deadline / Timeout 避免无限等待
单进程模型并发 asyncio.Semaphore 限制模型同时调用数
单进程 HTTP 连接 HTTPX Limits 连接资源控制
单用户/租户 用户标识 + 计数/令牌桶 防止某个用户占满配额
全服务实例组 网关/Redis 原子计数/分布式协调 多进程、多主机统一预算
上游供应商 API 侧配额与 429 供应商保护其服务

分布式计数需要考虑 TTL、进程崩溃和原子操作；Redis 方案不是自动严格正确，必须明确失效与恢复语义。

7. 一个可以实际运行的 FastAPI 完整示例

本示例用 asyncio.sleep() 模拟模型请求，不依赖外部模型服务。它展示：

  • 慢请求在等待时不会阻塞同一个事件循环上的快请求；
  • 每个模型请求受到总期限保护；
  • Semaphore 保护模型容量；
  • 普通 HTTP 接口在模型调用期间仍可以处理；
  • 超时与其他故障被明确区分；
  • finally 记录资源退出事件。

7.1 app.py

python
import asyncio
import logging
from contextlib import asynccontextmanager

from fastapi import FastAPI, HTTPException, Request
from pydantic import BaseModel, Field

logger = logging.getLogger("model_demo")

MODEL_CONCURRENCY = 2
MODEL_DEADLINE = 0.30


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.model_slots = asyncio.Semaphore(MODEL_CONCURRENCY)
    yield


app = FastAPI(lifespan=lifespan)


class ChatRequest(BaseModel):
    message: str = Field(min_length=1)
    simulated_delay: float = Field(ge=0.0, le=5.0)


async def fake_model(message: str, delay: float) -> str:
    try:
        await asyncio.sleep(delay)
        return f"模型回答：{message}"
    finally:
        # 模拟统计/清理点；这里不代表外部模型调用一定已停止
        logger.info("模型协程离开: %s", message)


@app.get("/health")
async def health():
    return {"status": "ok"}


@app.post("/chat")
async def chat(payload: ChatRequest, request: Request):
    try:
        # 总预算覆盖等待并发槽位的时间与模型响应时间
        async with asyncio.timeout(MODEL_DEADLINE):
            async with request.app.state.model_slots:
                answer = await fake_model(
                    payload.message, payload.simulated_delay
                )
                return {"answer": answer}
    except TimeoutError as exc:
        raise HTTPException(
            status_code=504,
            detail={"code": "MODEL_TIMEOUT", "message": "模型处理超时"},
        ) from exc
    # 不捕获 CancelledError，允许由框架/服务器处理取消

如果 simulated_delay 为 0.05，通常可较快返回；若设置 1.0，则因为业务超时设置为 0.30 秒，通常返回 HTTP 504。

8.1 更严格的并发额度验证

下面是纯 asyncio 的验证，不依赖 FastAPI：

python
import asyncio

async def main() -> None:
    sem = asyncio.Semaphore(2)
    active = 0
    maximum = 0

    async def work() -> None:
        nonlocal active, maximum
        async with sem:
            active += 1
            maximum = max(maximum, active)
            try:
                await asyncio.sleep(0.03)
            finally:
                active -= 1

    await asyncio.gather(*(work() for _ in range(12)))
    assert maximum == 2
    assert active == 0
    print("最大同时运行数:", maximum)

asyncio.run(main())

这证明在一个事件循环实例里，最多只有 2 个协程进入信号量保护区，且正常执行后额度释放。

8.2 超时触发清理验证

python
import asyncio

async def main() -> None:
    cleaned = False

    async def model():
        nonlocal cleaned
        try:
            await asyncio.sleep(1)
        finally:
            cleaned = True

    try:
        async with asyncio.timeout(0.02):
            await model()
    except TimeoutError:
        pass

    assert cleaned
    print("已执行 finally 清理")

asyncio.run(main())

这验证取消进入协程后会执行其 finally 路径，不表示所有外部服务副作用都已撤销。

9. 重试：避免把一次慢请求变成十次慢请求

超时后立即无条件重试，可能放大供应商和本地系统负载。

一个合理的重试机制至少考虑：

  • 可重试性：暂时性网络故障、部分 5xx、429 有时可重试；非法输入通常不应重试。
  • 幂等性：上一次请求可能已经被上游执行，即使本地没有收到响应；涉及写入、扣费、发送消息或工具调用时，不能假定重试安全。
  • 最大次数：有限次数，避免无限循环。
  • 退避与抖动：指数退避加随机抖动，减少同步重试风暴。
  • 总期限：所有尝试与退避时间都必须包含在业务总预算内。
  • 取消传播：收到取消后不应继续无谓重试。

简化的示意：

python
import asyncio
import random

async def limited_retry(call, attempts: int = 3):
    for i in range(attempts):
        try:
            return await call()
        except TransientUpstreamError:
            if i == attempts - 1:
                raise
            await asyncio.sleep(min(0.2 * 2**i + random.uniform(0, 0.1), 2))

TransientUpstreamError 是需要在业务代码中定义的自定义异常。实际使用时，应在函数外部施加总期限，确保全部重试都受同一预算约束。

10.1 如何理解事件循环延迟

一个定时协程计划在 100 毫秒后恢复，但实际 600 毫秒后才恢复，额外的 500 毫秒可表现为事件循环调度延迟。它可能意味着：同步阻塞、CPU 计算、线程争用或运行环境调度抖动。

事件循环延迟是诊断线索，不足以单独证明“某一个函数就是根因”；需要配合线程栈、性能剖析和请求日志。

11. 异常、取消、超时、并发与资源的关系图

text
                 ┌──────────────────────────────┐
HTTP 请求 ──────>│ 入口校验、身份验证、总期限   │
                 └──────────────┬───────────────┘
                                ↓
                      有界排队 / 并发控制
                                ↓
                        HTTP 客户端连接池
                                ↓
                          上游模型 API
                                ↓
                     结果校验与业务处理
                                ↓
                           HTTP 响应

异常路径：网络/上游错误 → 业务异常分类 → API 错误响应
取消路径：超时/外部取消 → CancelledError → 清理 → 传播
资源路径：获取连接与额度 → try/finally 或 async with → 释放
容量路径：排队上限 + 同时执行上限 + 连接池上限 + 上游配额

几条必须牢记的边界：

  1. 超时是终止等待的策略，不等于保证上游绝对停止执行。
  2. 取消是协作机制，不等于杀死线程或撤销外部副作用。
  3. finally 确保进入清理路径，不等于不可失败的分布式事务。
  4. Semaphore 限制“进入保护区的并发任务数”，不自动限制等待任务数和全局 RPS。
  5. 单个慢请求不应阻塞事件循环，但共享模型槽位的其他模型请求仍可能排队。
  6. 网络超时、业务超时、取消、输入错误与程序 Bug 应分别建模。

13. 更严格的工程含义：怎样让慢模型不影响其他用户

当要求“一个模型请求很慢，其他请求仍能得到响应”时，至少应检验四个层次：

层次一：事件循环不被阻塞。 模型调用通过真正的异步 I/O 进行，不在事件循环线程上使用同步网络调用或长期 CPU 密集计算。

层次二：资源隔离。 健康检查、账户查询等非模型 API 不依赖等待同一个模型并发槽位；模型调用使用独立的容量控制。

层次三：有限等待。 每个请求有总期限，连接/读取/连接池等待有局部超时，排队不允许无限膨胀。

层次四：可靠退出。 超时、取消、网络失败、用户断开之后能释放连接与额度，记录真实状态；对已经发生的外部副作用采用独立的幂等和恢复机制。

这四层共同成立，才更有把握在慢模型和故障场景下保持服务可用。它们也必须通过有代表性的并发、故障注入和压力测试验证，而不是只根据代码表面存在 async def 或 Semaphore 就认定合格。

14. 术语速查

  • Deadline：业务操作应完成的截止时间。
  • Timeout：等待超过规定限制后的行为或异常。
  • Cancellation：向异步任务发出终止执行的请求。
  • CancelledError：协程观察到取消时可能收到的特殊异常。
  • Exception propagation：异常沿调用链向上返回、传播或被转换。
  • try/finally：保证执行退出路径中的清理代码。
  • Semaphore：限制同时进入临界区的任务数量。
  • Backpressure：通过拒绝、暂停或减速输入，防止系统超过承载能力。
  • Connection pool：复用并限制网络连接的机制。
  • Tail latency：请求耗时分布高分位（例如 p95、p99）的延迟。
  • Cooperative cancellation：任务在合适位置主动响应取消信号。
  • Structured concurrency：子任务生命周期与父任务作用域绑定的并发管理方式。
