  • Redis 7.4.11社区Windows构建下载成功，归档SHA256与既定值匹配；启动前另核对可执行文件哈希，只监听127.0.0.1，不安装Windows服务。该构建不是官方Linux容器，Compose验证单列。
  • 初步脚本6组实际检查已通过：首次未命中/再次命中、默认TTL赋值、加速1秒失效、发布代次改变、坏JSON、停机回源、重连填充。它使用隔离SQLite及测试向量，不代替PG/BGE组合证据。

复现并修复的实际缺口

缓存读原来只做json.loads，合法JSON但结构错误的对象也会进入工具返回。已保存修复前stale_canary复现：现在检查检索模式、快照、结果列表长度、资料项与引用关键字段，错误结构视为未命中，回源并修复缓存。新增9类损坏回归及正常命中不重扫资料的检查，既有发布代次和模型revision边界保持。

准备脚本在Redis运行时重新执行，会碰到Windows已加载DLL不可覆盖。现先对比已存在成员的哈希，完全相同则跳过写入；可执行文件哈希写入准备清单并在启动时检查。实际运行中重复准备已成功，不结束运行进程或放宽文件校验。

API健康信息增加独立cache字段；Redis不通仍返回API/数据库可用，标记unavailable_fallback。缓存不可用不能将数据库任务状态改为丢失。原生监督器独立有限重启Redis，沿用Worker/Kafka退避及熔断实现。

Compose与复现边界

Compose已补Kafka的512 MiB堆/32 MiB去重缓存、后台服务有限重启、Redis64 MiB可丢弃缓存策略；Worker移除不必要的Redis健康前置依赖。Redis仅缓存公共资料，任务状态仍由PG保存。Docker构建上下文排除本地Git副本。

本机没有Docker/Podman可执行文件，WSL没有已安装发行版；7服务YAML结构检查通过，但未实际构建、启动容器。没有安装系统组件或修改虚拟化配置。这仍是P10及容器矩阵的真实缺口。
