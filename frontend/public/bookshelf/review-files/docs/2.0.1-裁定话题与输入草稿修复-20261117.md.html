2.0.1 本地修复：裁定话题误继承与回答期间编辑草稿

日期：2026-11-17（Asia/Shanghai）。版本：2.0.1-local.1。范围：延续v2本地内测，不上传GitHub；15174与公网的前端静态版本仍为1.13。两个入口共用的问答API已应用本轮修复，因此共用后端的问答行为同时生效。

两个问题及实际原因

普通问题被裁定兜底覆盖

实际记录中，同一会话先查看SC03固定记录，随后发送“孙权技能”“刘备技能”“曹操技能”，三轮都被ruling_guard替换成“本轮未取得受控裁定结果”。模型虽然执行了普通数据查询，最终文字仍被应用层覆盖。此项不是资料库没有这些武将，也不是供应商服务没有返回内容。

旧逻辑只要没有匹配“查询、介绍、换个问题”等少数开头，就向前扫描最多32条用户消息找SC场景。普通的“曹操技能”没有命中这些开头，会错误继承很早以前的SC03。后面的普通追问也继续受到旧场景影响。

修复方式：

  • 仅明确的上下文追问继承历史裁定，例如“那如果改成仁王盾呢”“会造成几滴伤害”“为什么”。独立问题形成扫描边界，不继续跨过它寻找旧SC记录。
  • 对“孙权技能”“那刘备的技能呢”等实体资料查询单独识别；明确SC编号或交互组合仍优先进入裁定校验。
  • 本轮不需要裁定时，只向模型提供资料检索与数据查询工具，避免模型受到旧场景影响而错误调用裁定工具；当前问题需要裁定时继续提供裁定工具与原有必要条件约束。
  • 保留“条件不匹配不能发布确定结论、不能用固定记录冒充当前局面、模型自填条件不能代替玩家确认”的原有保护。

实现：ruling_policy.py、runtime.py。这是有限领域的路由规则，不能视为对任意自然语言意图的完美识别；仍可能需要用户明确具体场景。

回答生成时无法输入

原输入框使用disabled={isBusy}，整个生成期间不可编辑。原代码还在异步创建会话之后清空输入；单纯移除disabled会造成用户新写的草稿被迟到的创建响应清空，恢复旧请求时也会丢失新草稿。

现在：

  • 回答期间输入框保持可编辑，显示“正在回答，可编辑下一条，完成后再发送”。
  • 正在回答时Enter是换行，不会静默吞掉按键，也不会另发一个模型请求。
  • 新问题在开始提交时清空原输入，异步创建返回与后续流式事件不清空用户新草稿；创建失败时，没有新草稿才恢复原问题。
  • 恢复上一条请求时保留当前正在编辑的下一条草稿。
  • 当前回答完成后，草稿仍在，用户可自行发送。此功能没有把未提交草稿追加进正在进行的模型调用，也没有自动排队付费请求。

实现：chat-screen.tsx。
