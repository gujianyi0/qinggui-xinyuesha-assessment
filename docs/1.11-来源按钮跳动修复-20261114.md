# 1.11 来源按钮跳动修复

日期：2026-11-14。用户进一步说明：“点击链接按钮，按钮会跑开”。这条反馈把问题定位到来源交互，不能继续仅用整机内存压力解释。

## 复现与原因

在实际1.10网页打开已有STYLE01曹操回答，不新增模型调用。来源按钮最初横向位置约为0.7、96、191.3px；展开第一份资料后，第二个按钮变为358.1px，向右移动约262.1px。再点第二个，第一份详情关闭，第二个按钮跳回96px。

原因是紧凑来源卡片把详情放在每个按钮自己的flex项目内部。展开内容改变项目宽度，其他按钮被挤走；换到另一条时又重新排版。该问题已复现，独立于此前未确证的整个浏览器挂起原因。

另发现聊天每次正文/进度更新都会对末尾执行smooth scrollIntoView，可能把正在查看旧回答或来源的用户反复拉走。这是另一处明确的滚动干扰。

修前证据：[实际1.10按钮坐标](evidence/v111-source-buttons-before.json)。

## 修改

- 来源按钮保持在独立的按钮排，详情统一在按钮排下方展开；详情宽度不再参与按钮排布局。
- 切换、关闭或键盘展开详情时保留所有按钮节点、顺序及可访问名称。
- 自动跟随只移动聊天内部滚动区域，取消每次更新的平滑滚动与祖先窗口滚动。用户上滚、离开底部或点击来源后停止跟随；主动滚回底部或发送新问题再跟随。
- 提示词、裁定策略、数据库Schema、模型配置、预算和会话内容均未改。无新增依赖。

## 验证范围

本轮前端25项行为测试通过，TypeScript及生产构建通过。新增覆盖：切换长引用时详情不在按钮排内、阅读历史时新token不强拉底部、滚回底部恢复跟随、打开来源后暂停跟随。原有引用展示、焦点/IME、断线提交恢复测试一并执行。

证据：[Vitest原始JSON](evidence/v111-frontend-tests.json)。真实浏览器修前/修后使用同一份已保存回答，不把组件结构断言冒充像素位置测试。

本轮未重新运行付费模型或32条评测，后端业务代码保持1.10。1.10的GitHub main和tag自动检查已通过，仍按各自提交解释。

源码版本1.11，包元数据1.11.0。本机只重建网页容器；现有API/Worker仍为已验证的1.10.0镜像，业务文件未改，不为了网页修复重启正在服务的模型进程。PostgreSQL、Kafka、Redis、模型账本和数据卷保持运行。

本机入口仍为http://127.0.0.1:15174/。已有页面须刷新才能加载新前端。公网Worker静态页面及独立下载客户端没有在本轮重新部署。

## 修后实际网页结果

本机网页重建完成后，使用同一STYLE01保存回答检查来源1、来源2、键盘关闭以及相同屏幕坐标连续开/关：三个按钮相对来源区的位置完全不变，最大位移0px，屏幕坐标也保持一致。相同点位开启和关闭均成功。

证据：[实际1.11坐标与同点点击](evidence/v111-source-buttons-after.json)。该项是实际部署的浏览器操作，且没有提交新问答。组件模拟流式验证与浏览器已有记录验证分别报告，不声称本轮做了新的真实模型流式调用。
