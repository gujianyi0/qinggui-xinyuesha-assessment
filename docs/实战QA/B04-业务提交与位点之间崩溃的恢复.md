# B04 业务提交与位点之间崩溃的恢复

核对日期：2026-11-14。代码基线：1.9（`7453cd3673b02d52b110b16503d283e97e3dac9a`）。

## 对应要求（原段要点，转述）

在业务写入后但Kafka位点提交前退出，重启仍应正确处理并避免任务丢失或永久运行。

## 回答

核心顺序是先持久化业务结果或可恢复重试安排，再手动确认Kafka位点。若业务已经成功提交、Worker尚未提交位点便退出，消息会重放，但数据库终态会使重复领取失败，Worker只确认消息而不重新发布索引。

## 本项目如何实现

Worker设置enable.auto.commit=false、enable.auto.offset.store=false，handle完成持久处理后同步commit。处理未持久化的异常会回退本地消费位置，防止随后提交更高位点顺带跳过失败消息。

中途崩溃与“已完成后未提交位点”分开处理：中途Job还处于running，租约过期后recover增加generation并重新排队；旧执行者被代次隔离。超过最大尝试次数进入failed，仍保留记录。需要恢复循环实际运行，不能在所有服务停机时承诺任务会自行前进。

## 怎样核对或演示

按证据中的Job号、generation和Offset，对比退出前数据库succeeded、退出后消息重放、最终发布指针和位点推进。若做新实验，使用独立库/Topic和显式测试故障点，不能在主服务打开ASSESSMENT_CRASH_AT。

## 结论与边界

恢复是从持久状态决定跳过、重新执行或终止，不是把进程内Task原样复活。旧代次暂存可保留，但不会变成当前发布；目前不是多API/多Worker集群可用性或所有重平衡场景的完整证明。
