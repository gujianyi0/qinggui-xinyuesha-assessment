# Worker 内存、退出与网页可用性排查

更新：2026-11-10。当前阶段：修复已实现，自动化及故障恢复已验证，一小时实时时钟验证正在执行，尚未计为通过。

## 已观察到的原因与证据

| 现象 | 核对结果 | 证据及范围 |
| --- | --- | --- |
| 原 Worker 日志只有 MemoryError 名称 | outbox 捕获所有 Exception 后继续重试，日志缺少调用栈；后台循环意外结束未被消费主循环检查 | `before-worker.log` 与原实现；缺少原始故障时刻完整栈，不能补造精确分配位置 |
| 网页拒绝连接 | 原监督逻辑任一子进程退出便进入全组 finally，Worker 退出连带停止网页、API、Kafka 和 PostgreSQL | `before-status.json`、原 native_demo.py 及上轮中断记录 |
| 系统虚拟内存不足 | Windows Event 2004 多次记录资源耗尽，Python PID 31420 占约7.7 GiB | `windows-resource-exhaustion.json`；现有进程映射不足，不能认定该PID必然是本次Worker |
| 模型占用在导入结束后不释放 | 修复前真实PG/Kafka/BGE导入采样，Worker进程树私有内存约57 MiB → 峰值1644 MiB → 任务结束30秒后仍约1607 MiB | `baseline-samples.jsonl`、`baseline-job.json`，不是根据模型文件大小推算；仅证明常驻占用，不等于已证明泄漏 |

上述排查原始文件位于[evidence/worker-memory-20261110](evidence/worker-memory-20261110)。最近一次告警的系统提交量为68,297,216,000字节，上限68,564,348,928字节，约99.61%；其中Python PID 31420启动于14:48:29，早于该轮预览，不能把它直接认作Worker。系统整体提交量耗尽与Worker的持续模型占用共同构成风险，但现有历史证据不足以证明最初MemoryError的唯一根因。

## 已实施修复

1. 本地 BGE 仅由任务所属的独立向量化子进程加载；任务完成、失败或取消后关闭。长期运行的 Kafka Worker 不再导入 torch 或持有模型。标准输入/输出是有界批次JSON，诊断输出走stderr；沿用原分块、512维向量及锁定模型revision。
2. Windows Job Object 约束所属进程树。Worker异常退出、被替换或监督程序停机时清理所属模型子进程；覆盖venv启动器和实际解释器PID不同的情况，避免只结束启动器而遗留模型进程。
3. Worker退出只触发后台服务的独立恢复，不再停止网页、API、Kafka及数据库。退避1/2/4/8/16秒，10分钟内最多5次重启，连续失败进入可见的`circuit_open`，保留网页与诊断，避免无休止重启。
4. Worker进程树私有内存超过3 GiB时回收这一Worker并按相同规则恢复；这是本机工程保护参数，不是公司评分标准。未通过实际耗尽系统内存测试该上限，阈值路径用可控指标夹具验证。
5. MemoryError不再作为普通依赖失败在耗尽进程内继续分配重试；异常传至进程边界，低分配诊断并以75退出。后台outbox异常会传播；下一实例依据数据库租约、代次和Outbox恢复任务。
6. 普通异常记录完整调用栈和任务号；Worker每30秒记录资源与协程数，监督进程每5秒记录所属进程树、系统物理内存/提交余量、退出码及重启原因。资源采样文件有大小轮转限制，不采集聊天内容、密钥或无关进程命令行。
7. Kafka客户端设置适合单任务消费的有限预取与发送缓存；数据库恢复每批只锁定最多100个真正到期任务，不每秒加载所有运行任务。

复查时发现本轮初版资源采样函数在每次调用中重新定义ctypes结构，导致内部指针类型缓存增长。已将结构与API绑定改为模块级复用，并以类型缓存和Windows句柄不增长测试防回归。第一轮短时实测保留为中断记录，未用来冒充完整长时验证。

## 运行和诊断

- 正常启动：`pwsh -File scripts/start_native.ps1`，默认关闭模型评测故障注入。
- 停止：`pwsh -File scripts/stop_native.ps1`，只停止本项目所属进程，保留数据库和任务状态。
- Worker状态与重启次数：`.local/native-demo/status.json`的`worker`字段；`backoff`或`circuit_open`时网页保持运行，后台任务需等待恢复或处理熔断原因。
- 资源、退出码、重启原因：`.local/native-demo/resources.jsonl`及轮转文件；详细栈和任务号：`worker.log`。
- 重现受控MemoryError：`python scripts/verify_worker_memory_recovery.py`，使用独立DB和Topic，不给正常预览开启故障注入。
- 长时验证：`python scripts/soak_native_worker.py --label 唯一标签 --seconds 3600`。此命令明确终止本项目Worker进行恢复测试，不终止网页/API或其他程序，不调用付费模型。

参数与资源耗尽解释参照[微软故障排查说明](https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-application-service-memory-leaks)、[Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[librdkafka官方参数](https://docs.confluent.io/platform/current/clients/librdkafka/html/md_CONFIGURATION.html)。本报告中的故障归因和修复效果以本机保存的证据为准。
