## 定位与修复

1. Worker原来在导入结束后仍常驻BGE，实测约57 MiB升至约1.6 GiB且任务后不回落。现将向量化放在按任务关闭的子进程，Windows Job Object负责异常退出时清理所属进程树；本次重复导入/取消后均回落。
2. 原监督程序因Worker退出而停止全组。现Worker和Kafka各有独立有限重启、退避、连续失败熔断；错误及资源采样留档。受控MemoryError的75退出和租约恢复另有隔离证据，没有实际耗尽用户电脑内存。
3. 上次文件替换WinError5导致停机。状态写入已改为唯一临时文件、有限重试和不传播IO异常；本轮真实锁测试覆盖此路径。资源采样ctypes结构复用，避免监控本身增加类型缓存和句柄。
4. Kafka原256 MiB堆在LogCleaner/SkimpyOffsetMap分配时OOM；设置堆512 MiB、去重缓冲32 MiB、单清理线程并保持压缩开启，原数据恢复启动及强制退出后的恢复均成功。[Apache Kafka 3.9参数说明](https://kafka.apache.org/39/configuration/broker-configs/)。

原始MemoryError的精确分配位置缺失，不能认定唯一根因或断言所有内存问题已消失。Windows历史告警证明当时系统提交量接近上限；其中大内存Python PID尚不能归属到Worker。数据库、API或整个操作系统故障也不在“后台进程退出不连带关闭网页”的保证范围内。
