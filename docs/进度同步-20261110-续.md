## 已定位的故障根因（新）

一小时 soak `worker-soak-20261110-02` 在 **1570.983 秒**开始出现连续 `ConnectError`，至 1802.11 秒共 58 次，`worker` 变为 `null`，网页/API 全部拒绝连接。这不是付费模型或 Worker 内存问题：

- `.local/native-demo/status.json` 记录了 `[WinError 5] 拒绝访问: status.tmp -> status.json`。
- `supervisor-error.log` 的完整栈显示 `scripts/native_demo.py` 第 62 行 `temporary.replace(status_file)` 抛出 `PermissionError`，冒泡到 `run()` 的 `except`，随后 `finally` 停掉 web/worker/api/kafka/postgres 全组服务。
- Windows 上另一进程（杀软、索引器或采样读取）短暂持有 `status.json` 句柄时，`Path.replace` 会偶发失败。**状态文件只是可观测性产物，不应成为整组服务的存活条件。**

## 已实施修复

1. 新增 `backend/app/status_file.py`：`atomic_write_text` / `atomic_write_json` 使用每次唯一的临时文件、有限重试（6 次 × 50ms）、失败返回 `False` 而**不抛异常**，并保留上一份可读状态。
2. `scripts/native_demo.py` 的 `report()` 改走该模块；写盘失败只打印 warning，不再拖垮监督进程。
3. `diagnostic()` 的日志轮转 `path.replace` 同样收敛为不冒泡，避免采样循环再被文件锁中断。
4. 异常路径（`report("failed")` / `report("stopped")`）因此不会二次抛错掩盖原始根因。
5. 顺手修复 `scripts/run_rulings.py` 既有的 Ruff I001 import 排序（全范围检查才暴露，与本次故障无关）。
