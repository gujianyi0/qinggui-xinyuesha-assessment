# Docker 主库备份与恢复（1.9）

当前业务权威是 `qinggui-assessment-live` 的 PostgreSQL。旧原生迁移归档只代表迁移时点，不能覆盖今天的会话、反馈和费用账本。备份命令应在项目根目录执行。

## 备份内容与维护窗口

```powershell
uv run python -m scripts.backup_docker_primary backup --label daily-20261113-01
```

标签必须唯一。脚本暂停本项目公网转发，停止 API、Worker、网页写入，检查运行、任务、Outbox、未结算用量和预算预留均已清零，再执行 `pg_dump -Fc`。仍有业务时拒绝备份，不把处理中状态伪装成一致快照。无论成功失败都会尝试恢复原有服务；失败时检查 `.local/backups/last-command-error.log` 和服务健康状态。

备份只写入 `.local/backups/<标签>/`，包括业务归档、逐表数量与内容哈希、迁移/pgvector 版本、费用账本，以及 `.env.docker-live`、主库标记和公网连接配置的本地副本及哈希。这些文件含会话和凭据，已被 Git 排除。公开证据只保存校验结果，不上传归档或配置原文。

建议每个工作日结束及升级前手动备份。本轮没有添加定时任务；可恢复的数据截至最近一次成功备份。备份仍在同一台电脑，同盘损坏无法靠这份副本恢复。需要另外把整个备份目录复制到本人控制的其他介质，复制后核对 manifest 中哈希；本轮未进行异地复制。

## 不覆盖主库的恢复演练

```powershell
uv run python -m scripts.backup_docker_primary restore-check --label daily-20261113-01 --database assessment_restore_20261113_01
uv run python -m scripts.verify_restored_service --label daily-20261113-01 --database assessment_restore_20261113_01
```

第一条只接受 `assessment_restore_` 前缀且尚不存在的新库；拒绝 `assessment`、`postgres`、已有目标库以及任意 SQL 字符。先核对归档哈希，再创建新库并在单事务中恢复；比较所有表的数量/内容、已花与预留费用、迁移版本和向量扩展。失败目标保留排查，不自动清空或覆盖。

第二条必须有相同目标的成功恢复证据。它在 18086 启动独立 API，明确使用 mock、空模型密钥、关闭故障注入且不重置身份密码，验证备份密码登录、历史会话及消息读取、账本不变，最后停下探测容器。其登录会在恢复库新增一个 token，因此全表指纹比较在启动探测前完成。不会对真实模型发请求，也不会把恢复库设成主库。每轮演练使用新目标；探测容器名称已存在时先核对其归属，不强行覆盖。

## 真正发生故障时

1. 停止本项目公网入口及写入进程，保留故障库与日志。确认所选备份时间、哈希和可能丢失的数据区间。
2. 用与备份相符的发布标签准备代码和依赖，恢复到独立新库，先完成上述指纹及 mock 读取检查。配置凭据来自私有备份，不从 GitHub 获取。
3. 若代码比备份新，在该恢复副本运行 Alembic 升级并复核；不要对业务主库执行降级，也不要为了运行旧标签删除新增数据。恢复 1.9 应使用 migration `0002`。
4. 确认恢复后账本没有遗失备份之后的已发生费用；必要时先补记保守费用，再允许真实调用。不能用较旧的低费用账本重新获得额度。
5. 经核对后，单独调整 `.env.docker-live` 的数据库目标和主库标记，仅启动一个正式 API 与一个 Worker，检查网页、历史、预算与新任务，再恢复公网转发。当前脚本仅做隔离验证，**不会自动切换主库**。
6. 本轮已经验证隔离恢复与历史读取；灾难后人工选择备份、补账和正式切换尚未演练。不能把一次恢复检查写成零数据丢失或高可用保证。

Kafka、Redis、BGE 下载缓存均不能替代 PostgreSQL 业务备份。Redis 可重建；BGE 按锁定 revision 获取并验哈希；只在任务/Outbox 全部完成后备份，恢复时不借旧 Kafka 位点推断业务完成。电脑重启后仍需执行本项目启动脚本和公网入口脚本。

本轮实测记录见 [1.9 报告](1.9-裁定约束断线恢复与完整回归-20261113.md)。QQ 和真人试用保持移除。
