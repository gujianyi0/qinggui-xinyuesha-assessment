# 本机浏览器无响应排查

日期：2026-11-14。用户明确描述为“整个浏览器无响应”，不是仅一条请求等待。

## 观察与结论

截图中的“查询凯撒技能”对应Run `398007e2-1f21-51eb-a0db-ccd4d61b8b02`，已于5.593秒完成，无error；之后“介绍曹操”也完成。问答快照未收录凯撒，回答资料不足本身不是卡死。排查时15174和18081健康检查均200，PostgreSQL/真实模型模式/发布索引正常。

整机存在明显内存压力：约15.86GiB物理内存一度只剩400～600MiB可用；提交内存约59.78GiB／63.86GiB。Windows今天15:33、15:53等时间记录事件2004“虚拟内存不足”，当时报告WSL约8GB、Edge约5.5GB等占用；另有15:33的Edge异常退出事件。这些事件早于截图对应的17:12请求，不能混写成同一时刻崩溃证据。

当前Docker Worker约62.38MiB、API509.5MiB、网页15.75MiB，未观察到本次Worker再次失控。WSL整机预留、其他浏览器/编辑器/构建进程共同占用应分别分析，不能把WSL约8GB直接等同于Worker约8GB。

在实际本机网页打开同一保存会话，滚轮上移650px成功、输入框可编辑、下一帧约11.1ms；未发送新问题或重放原付费请求。因此确认排查时页面可交互，尚未复现用户当时整个浏览器挂起，也没有该次renderer崩溃转储。**整机内存不足是有证据的高优先级原因，不能宣称已经证明唯一根因或永久解决。**

## 处置与后续

- 不清浏览器资料、不删会话、不重置账本、不重发已完成问题。
- 回归使用单Worker顺序运行，避免叠加多个重型构建；本次未擅自终止其他项目进程或更改全局WSL/分页文件。
- 再次整浏览器无响应时，记录准确时间及Windows事件；若能打开浏览器任务管理器，核对对应标签页/扩展/GPU进程的内存与CPU，而不是把所有Edge进程相加后断言本网页泄漏。
- 需要持久降低内存时，由用户选定可关闭的其他构建或空闲程序，再评估WSL内存上限与回收策略。调整WSL通常涉及重启，不能在共享服务运行时直接执行`wsl --shutdown`。
- 正文/引用展示的1.10改动另见版本报告；它改善可读性，不作为整机内存不足已修复的证据。
